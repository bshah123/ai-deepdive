A Python program is a text file, and before a single line of it runs, Python decodes it, cuts it into tokens and groups them into a tree. In this lesson you will watch each of those steps happen, read the indentation rule that makes Python blocks work, and explain why a mistake on line 90 can stop line 1 from ever running.

**You need:** to have run a Python script once. Nothing else. Lesson 1.2 follows the program further (bytecode and the virtual machine).

## The problem: "Python reads your file line by line" is wrong

A common first mental model is that Python reads a line, runs it, then reads the next. It predicts that a typo on line 90 can only hurt you when execution reaches line 90. It does not work that way, and the wrong model makes real errors confusing: you see no output at all, and nothing seems to have run.

What actually happens, in CPython (the standard implementation; others are in Lesson 1.3), is a chain of translation steps applied to the whole file, followed by execution:

1. **Bytes to characters.** The file holds bytes; Python decodes them into text.
2. **Characters to tokens.** The text is cut into words and symbols: names, numbers, operators.
3. **Tokens to a tree.** The tokens are grouped by the grammar into a *syntax tree*.
4. **Compile, then run.** The tree is translated for the virtual machine (Lesson 1.2), and only then does anything execute.

The rest of the lesson takes these in order, with code you can run in the browser.

## Step 1: bytes become characters

A file on disk is just bytes. The same bytes can be different programs, depending on how they are decoded:

![The 15 bytes of the line name = "café" followed by a newline, decoded as UTF-8 into 14 characters, or as latin-1 into 15 characters](diagrams/1.1-bytes-to-text.svg "Bytes c3 a9 are one character (é) in UTF-8 and two (Ã and ©) in latin-1.")

Python's default is UTF-8 (the 8-bit Unicode encoding). The Language Reference says: "If no encoding declaration is found, the default encoding is UTF-8", and PEP 3120 made that the default from Python 3.0. A comment such as `# coding: latin-1` on the first or second line overrides it. Bytes that cannot be decoded raise a `SyntaxError`.

```python
# The same bytes are two different programs, depending on the declared encoding.
raw = 'name = "café"\n'.encode("utf-8")       # the file's bytes as UTF-8 writes them
print(raw)

ns = {}
exec(compile(raw, "demo.py", "exec"), ns)      # no declaration: UTF-8 is the default
print("default (UTF-8):", ns["name"], len(ns["name"]))

ns = {}
exec(compile(b"# coding: latin-1\n" + raw, "demo.py", "exec"), ns)
print("latin-1        :", ns["name"], len(ns["name"]))

try:
    compile(b'name = "caf\xe9"\n', "demo.py", "exec")   # 0xe9 alone is not valid UTF-8
except SyntaxError as e:
    print(type(e).__name__)
```

```output
b'name = "caf\xc3\xa9"\n'
default (UTF-8): café 4
latin-1        : cafÃ© 5
SyntaxError
```

## Step 2: characters become tokens

A **token** is the smallest meaningful piece of source: a name, a number, an operator, a newline. The standard library's `tokenize` module runs the same kind of scanner on a string, so you can look at one line:

![The line total = price * 3 followed by a comment, cut into seven tokens, then grouped into a tree with Assign at the root and BinOp below it](diagrams/1.1-text-to-tree.svg "Text, then tokens, then tree. The comment becomes a token for tools but is ignored by the grammar.")

```python
import io
import tokenize

src = "total = price * 3  # with tax\n"
for tok in tokenize.generate_tokens(io.StringIO(src).readline):
    print(f"{tokenize.tok_name[tok.type]:<8} {tok.string!r}")
```

```output
NAME     'total'
OP       '='
NAME     'price'
OP       '*'
NUMBER   '3'
COMMENT  '# with tax'
NEWLINE  '\n'
ENDMARKER ''
```

Two details. The stream ends with an `ENDMARKER`, which the diagram leaves out. And `tokenize` reports the comment as a token because its documentation says its scanner "returns comments as tokens as well", for tools like code colourisers. The Language Reference says "Comments are ignored by the syntax", so the tree in step 3 has no trace of it. (That the interpreter's own tokenizer drops them is my inference from those two statements.)

### Indentation is made of tokens too

Other languages mark blocks with `{ }`. Python's tokenizer turns changes of indentation into `INDENT` and `DEDENT` tokens, using a stack of indentation widths. The rule, quoted from the Language Reference:

- A single zero is pushed on the stack before the first line, and is never popped.
- At the start of each logical line, compare its width with the top of the stack. Equal: nothing happens.
- Larger: push it, and generate one `INDENT`.
- Smaller: it *must* be a number already on the stack. Pop every larger number, one `DEDENT` per pop.
- At the end of the file, one `DEDENT` per number left above zero.

![A four-line function traced against the stack: widths 0, 4, 8, 4 give the stacks [0], [0,4], [0,4,8], [0,4], with INDENT, INDENT, DEDENT and a final DEDENT at end of file](diagrams/1.1-indent-stack.svg "The stack after each line. Two pushes, then two pops.")

Check that rule by implementing it and comparing with the real tokenizer:

```python
import io
import tokenize

src = """\
def f(x):
    if x:
        return 1
    return 0
"""

# The rule from the Language Reference: keep a stack of indentation widths, starting at [0].
def indent_events(text):
    stack, events = [0], []
    for n, line in enumerate(text.splitlines(), start=1):
        if not line.strip():
            continue                                  # blank lines do not count
        width = len(line) - len(line.lstrip(" "))
        if width > stack[-1]:
            stack.append(width)
            events.append((n, "INDENT"))
        while width < stack[-1]:
            stack.pop()
            events.append((n, "DEDENT"))
    events += [(len(text.splitlines()) + 1, "DEDENT")] * (len(stack) - 1)   # end of file
    return events

mine = indent_events(src)
real = [(t.start[0], tokenize.tok_name[t.type])
        for t in tokenize.generate_tokens(io.StringIO(src).readline)
        if t.type in (tokenize.INDENT, tokenize.DEDENT)]
print("mine:", mine)
print("real:", real)
print("same:", mine == real)
```

```output
mine: [(2, 'INDENT'), (3, 'INDENT'), (4, 'DEDENT'), (5, 'DEDENT')]
real: [(2, 'INDENT'), (3, 'INDENT'), (4, 'DEDENT'), (5, 'DEDENT')]
same: True
```

> [!NOTE]
> My version handles only spaces and ignores tabs, continuation lines (a statement split across lines inside brackets) and comment-only lines. It matches on this input, not on all Python.

## Step 3: tokens become a tree

The **parser** groups tokens using the grammar. The result is an **abstract syntax tree** (AST): each node is an operation, its children are its operands. `ast.parse` gives it to you; the `ast` documentation says the tree can also be produced by passing `ast.PyCF_ONLY_AST` to `compile()`.

Take `1 + 2 * 3`. The tokens are a flat list, and the tree is where precedence (multiplication before addition) becomes structure: `2 * 3` sits *below* the `+`, so it is evaluated first. Walking the tree children-first gives the answer:

```python
import ast

tree = ast.parse("1 + 2 * 3", mode="eval")
print(ast.dump(tree.body, indent=2))

def evaluate(node):
    """Evaluate the tree bottom-up: children first, then the operator."""
    if isinstance(node, ast.Constant):
        return node.value
    if isinstance(node, ast.BinOp):
        left, right = evaluate(node.left), evaluate(node.right)
        if isinstance(node.op, ast.Add):
            return left + right
        if isinstance(node.op, ast.Mult):
            return left * right
    raise NotImplementedError(type(node).__name__)

print("tree walk:", evaluate(tree.body), "| eval():", eval("1 + 2 * 3"))
```

```output
BinOp(
  left=Constant(value=1),
  op=Add(),
  right=BinOp(
    left=Constant(value=2),
    op=Mult(),
    right=Constant(value=3)))
tree walk: 7 | eval(): 7
```

> [!KEY-INSIGHT]
> Parentheses, indentation and operator precedence all disappear into the *shape* of the tree. The tree is what the next stage reads, not your text.

The exact node classes can change between Python versions ("the abstract syntax itself might change with each Python release", per the `ast` docs). Treat the dump above as Python 3.12 output.

## Step 4: the whole file is translated before anything runs

`compile()` turns source (or a tree) into a **code object** that `exec()` can run. Everything before this point, steps 1 to 3, happens to the entire text. Syntax errors are raised here. Only when compilation has succeeded does execution start. Two files that differ only in the kind of mistake on line 3:

![Left: a runtime bug on line 3 compiles, prints step 1 and step 2, then raises NameError. Right: a syntax bug on line 3 fails in phase 1 and nothing prints](diagrams/1.1-compile-then-run.svg "Phase 1 translates the whole file; phase 2 runs it. A syntax error never reaches phase 2.")

```python
runtime_bug = 'print("step 1")\nprint("step 2")\nprint(undefined_name)\n'
syntax_bug  = 'print("step 1")\nprint("step 2")\nprint("step 3"\n'

for label, src in [("runtime bug on line 3", runtime_bug), ("syntax bug on line 3", syntax_bug)]:
    print("==", label)
    try:
        code = compile(src, "demo.py", "exec")        # phase 1: translate the WHOLE file
    except SyntaxError as e:
        print("  compile failed:", type(e).__name__, "on line", e.lineno, "- nothing ran")
        continue
    print("  compile ok")
    try:
        exec(code)                                     # phase 2: run it
    except NameError as e:
        print("  run failed:", e)
```

```output
== runtime bug on line 3
  compile ok
step 1
step 2
  run failed: name 'undefined_name' is not defined
== syntax bug on line 3
  compile failed: SyntaxError on line 3 - nothing ran
```

Compilation checks *grammar*, not meaning. It does not look up names and it does not check type hints. Both are decided only when the code runs:

```python
def double(x: int) -> int:
    return x * 2

print(double(21), double("ab"))        # the hints are stored, never checked
print(double.__annotations__)

def broken():
    return undefined_name              # compiled now, looked up only when called

print("defined without error")
try:
    broken()
except NameError as e:
    print("NameError:", e)
```

```output
42 abab
{'x': <class 'int'>, 'return': <class 'int'>}
defined without error
NameError: name 'undefined_name' is not defined
```

## Which file is "the program"? The `__main__` guard

Any `.py` file can be started directly or imported by another file. Python tells the file which case it is through the variable `__name__`. In the *top-level code environment* (a script run as `python file.py`, `python -m module`, or `python -c "..."`) `__name__` is `"__main__"`; the `__main__` documentation lists these. When the file is imported, `__name__` is the module's name.

![tool.py started with python tool.py has __name__ equal to __main__ so the guard runs main(); the same file imported has __name__ equal to tool so only top-level code runs](diagrams/1.1-main-guard.svg "The same file, two launches. Top-level code always runs; the guarded block only when started directly.")

```python
src = '''
def main():
    print("  main() running, __name__ =", __name__)

print("  top-level code runs on every start, __name__ =", __name__)
if __name__ == "__main__":
    main()
'''
code = compile(src, "tool.py", "exec")

print("like `python tool.py`:")
exec(code, {"__name__": "__main__"})       # the launcher sets __name__ to "__main__"
print("like `import tool`:")
exec(code, {"__name__": "tool"})           # the import system sets it to the module name
```

```output
like `python tool.py`:
  top-level code runs on every start, __name__ = __main__
  main() running, __name__ = __main__
like `import tool`:
  top-level code runs on every start, __name__ = tool
```

The block fakes the two launches by setting `__name__` by hand. A real check:

<details><summary>Run locally: real launches with subprocess (standard library only)</summary>

```

python -m tool
  __name__ = __main__
python -c 'import tool'
  __name__ = tool
```

</details>

## Common traps

> [!TRAP]
> **Mixing tabs and spaces.** Tabs are expanded to the next multiple of eight columns, so a tab and eight spaces can look identical in your editor. If the meaning would depend on the tab width, Python raises `TabError`. Configure your editor to insert spaces.

```python
# 1. A tab and eight spaces look the same on screen, but mean different things for different tab widths.
src = "if True:\n        x = 1\n\ty = 2\n"        # line 2: 8 spaces; line 3: one tab
try:
    compile(src, "t.py", "exec")
except TabError as e:
    print(type(e).__name__, "-", e.msg)

# 2. Identifiers are normalised (NFKC) when parsed; strings are not.
ns = {}
exec("ﬁnal = 3", ns)                            # starts with the one-character ligature U+FB01
print("ﬁnal" == "final", [k for k in ns if not k.startswith("__")])
```

```output
TabError - inconsistent use of tabs and spaces in indentation
False ['final']
```

> [!TRAP]
> **Look-alike names.** The second case above: the ligature `ﬁ` in a *name* is converted to `fi` while parsing (NFKC normalisation), so the variable is stored as `final`. But a *string* containing `ﬁ` is left alone, so `"ﬁnal" == "final"` is `False`, and `globals()["ﬁnal"]` would fail. Normalisation is lexical only, as the Language Reference says.

> [!TRAP]
> **Believing type hints are checked.** `double("ab")` ran and returned `"abab"`. Hints are stored in `__annotations__` and ignored at run time; a separate tool such as a type checker reads them.

> [!TRAP]
> **Expecting output before a syntax error.** One unclosed bracket on the last line means the first 99 lines never run. If a script prints nothing and shows a `SyntaxError`, that is why.

> [!TRAP]
> **Putting work at the top level of a module.** Top-level code runs on `import` as well as on direct start. Put the program's behaviour in functions and call them from the `if __name__ == "__main__":` block.

## Summary

- A `.py` file is bytes. Python decodes them (UTF-8 unless a `# coding:` line says otherwise), cuts the text into tokens, and groups the tokens into a syntax tree.
- Indentation is part of the token stream: a stack of widths, with one `INDENT` per push and one `DEDENT` per pop.
- The whole file is compiled before anything runs, so a syntax error stops everything and a runtime error stops only from that line on. Name lookups and type hints are not part of compilation.
- `__name__` is `"__main__"` when a file is started directly and the module name when it is imported; guard script behaviour with it.

## Quiz time

### Question 1: Count the tokens

How many `INDENT` and how many `DEDENT` tokens does this file produce? Include the end of the file.

```python
if a:
    if b:
        if c:
            x
    y
z
```

<details><summary>Show solution</summary>

3 `INDENT` and 3 `DEDENT`. Widths are 0, 4, 8, 12, 4, 0, so the stack grows to `[0, 4, 8, 12]` (three pushes). The line `y` has width 4: pop 12 and pop 8, two `DEDENT`. The line `z` has width 0: pop 4, one `DEDENT`. Nothing is left above zero at the end. I confirmed these counts with `tokenize` on Python 3.12.

</details>

### Question 2: What prints?

```python
code = compile("print('a')\nprint('b'\n", "q.py", "exec")
print("compiled")
```

<details><summary>Show solution</summary>

Nothing is printed except a `SyntaxError` traceback: the second line has an unclosed bracket, so `compile()` raises on its second line before `exec` is even involved, and `print("compiled")` is never reached. In this check the message was `'(' was never closed`, reported for line 2 (Python 3.12).

</details>

### Question 3: Spot the bug

`stats.py` is imported by a test file and prints `2.0` on every import. Fix it without deleting the example.

```python
def mean(xs):
    return sum(xs) / len(xs)

print(mean([1, 2, 3]))
```

<details><summary>Show solution</summary>

The `print` is top-level code, so it runs whenever the file is imported. Guard it:

```python
def mean(xs):
    return sum(xs) / len(xs)

if __name__ == "__main__":
    print(mean([1, 2, 3]))
```

</details>

### Question 4: Indentation that does not fit

The stack is `[0, 8]` and the next line is indented by 4. What happens, and why?

<details><summary>Show solution</summary>

An `IndentationError` ("unindent does not match any outer indentation level"). A smaller width must equal a number already on the stack, and 4 is not on `[0, 8]`. I ran a similar case (`if a:` then a line indented 8, then a line indented 4) and got that message.

</details>

### Question 5: Explain

Why is `"ﬁnal" == "final"` false, while a variable assigned as `ﬁnal = 3` can be read back as `final`?

<details><summary>Show solution</summary>

Names are converted to NFKC form when the source is parsed, and the ligature `ﬁ` normalises to `fi`. A string literal is data and is never normalised, so the one-character ligature stays different from the two letters `fi`.

</details>
