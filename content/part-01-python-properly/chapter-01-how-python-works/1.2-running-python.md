When you finish this lesson you will be able to name the stages between typing `python script.py` and the first line running, predict which errors appear before any output, and say what the `__pycache__` folder is for and when Python trusts it.

**You need:** Lesson 1.1 (a program is a text file, and what `__main__` means) and a terminal. Everything here was run on CPython 3.12.13; opcode names and offsets differ in other versions.

## The problem: "interpreted line by line" is not what happens

A common picture says Python reads your file one line at a time and runs each line as it goes. Test it. Both files below start with the same line. The first has a typo on line 2, the second fails at run time on line 2.

![Two files with the same first line: the one with a syntax error prints nothing, the one with a runtime error prints line 1 and then fails](diagrams/1.2-fail-stage.svg "Same first line, different outcome. I ran both files with python 3.12.13.")

`syn.py` printed nothing at all, although its first line is valid. So Python read the whole file before running any of it. The next section shows the stages that explain this.

## The pipeline, on a two-line program

CPython (the standard implementation, see Lesson 1.3) turns text into running code in stages. Our program is `price = 4` then `total = price * 3 + 1`.

![Source text goes through a tokenizer to 13 tokens, a parser to a 16-node syntax tree, a compiler to a code object with 10 instructions, and an eval loop that runs it](diagrams/1.2-pipeline.svg "The four stages. Everything left of the amber box happens before the first line runs.")

1. **Tokenizer.** Splits text into tokens: names, numbers, operators, and the end-of-line and end-of-file markers. By hand: `price`, `=`, `4`, NEWLINE is 4; `total`, `=`, `price`, `*`, `3`, `+`, `1`, NEWLINE is 8; plus ENDMARKER makes 13.
2. **Parser.** Arranges tokens into a tree that follows the grammar, so `price * 3 + 1` becomes "(price times 3) plus 1". The tree is an AST (abstract syntax tree). Counting by hand: 1 Module, 2 Assign, 3 Name, 3 context markers (Store, Store, Load), 3 Constant, 2 BinOp, 2 operators (Mult, Add) is 16.
3. **Compiler.** Turns the tree into a **code object**: a list of bytecode instructions plus its constants and names.
4. **Eval loop.** The bytecode interpreter (the "virtual machine" of Lesson 1.1), which executes instructions one at a time.

The diagram merges what the CPython developers' internals document splits into five steps (tokenize, parse, transform the tree into an instruction sequence, build and optimise a control-flow graph, emit bytecode). Syntax errors are found by the first three stages, which is why `syn.py` printed nothing. Errors such as `NameError` and `ZeroDivisionError` can only happen in the last stage, when the instruction that causes them runs.

Check the counts:

```python
import ast, dis, io, tokenize

src = "price = 4\ntotal = price * 3 + 1\n"

tokens = list(tokenize.generate_tokens(io.StringIO(src).readline))
print("tokens:", len(tokens))
print([t.string for t in tokens])

tree = ast.parse(src)
print("syntax tree nodes:", sum(1 for _ in ast.walk(tree)))
print(ast.dump(tree.body[1], indent=1))

code = compile(src, "<demo>", "exec")
print("instructions:", len(list(dis.get_instructions(code))))
dis.dis(code)
```

In `LOAD_CONST 0 (4)` the last column is the constant's value and `0` is its index in the code object's constants. `RESUME` is a bookkeeping instruction. Older tutorials, including the previous version of this lesson, show `BINARY_ADD`; since Python 3.11 the instruction is `BINARY_OP` (added in 3.11, per the `dis` documentation).

## The eval loop in twelve lines

The eval loop is a **stack machine**: instructions push values onto a stack and pop them to compute. This toy version handles only the instructions above, using the real bytecode:

```python
import dis

src = "price = 4\ntotal = price * 3 + 1\n"
code = compile(src, "<demo>", "exec")

names, stack = {}, []
ops = {"+": lambda a, b: a + b, "*": lambda a, b: a * b}
for ins in dis.get_instructions(code):          # straight-line code only: no jumps
    if ins.opname == "LOAD_CONST":
        stack.append(ins.argval)
    elif ins.opname == "LOAD_NAME":
        stack.append(names[ins.argval])
    elif ins.opname == "BINARY_OP":
        b, a = stack.pop(), stack.pop()
        stack.append(ops[ins.argrepr](a, b))
    elif ins.opname == "STORE_NAME":
        names[ins.argval] = stack.pop()
    print(f"{ins.opname:<12} {str(ins.argrepr):<6} stack={stack}")

real = {}
exec(code, real)
print("toy:", names, " real:", real["total"])
```

```output
RESUME              stack=[]
LOAD_CONST   4      stack=[4]
STORE_NAME   price  stack=[]
LOAD_NAME    price  stack=[4]
LOAD_CONST   3      stack=[4, 3]
BINARY_OP    *      stack=[12]
LOAD_CONST   1      stack=[12, 1]
BINARY_OP    +      stack=[13]
STORE_NAME   total  stack=[]
RETURN_CONST None   stack=[]
toy: {'price': 4, 'total': 13}  real: 13
```

Follow `price * 3 + 1`: push 4, push 3, `*` pops both and pushes 12, push 1, `+` pops both and pushes 13, store it as `total`. The real loop is written in C and handles jumps, calls and many more instructions, but the idea is the same.

## Code objects nest

A function or class body is compiled into its own code object, stored among the constants of the code that contains it. Executing `def f` later wraps that stored object into a function object.

![A module code object contains outer and A; outer contains inner; A contains m](diagrams/1.2-code-tree.svg "Each def and class adds one node.")

```python
import dis

src = """
def outer(x):
    def inner(y):
        return x + y
    return inner

class A:
    def m(self): pass

y = 2 + 3 * 4
"""
module = compile(src, "n.py", "exec")

def show(code, depth=0):
    print("  " * depth + code.co_name)
    for const in code.co_consts:
        if hasattr(const, "co_code"):       # a nested code object
            show(const, depth + 1)

show(module)
dis.dis(compile("y = 2 + 3 * 4", "<d>", "exec"))
```

```output
<module>
  outer
    inner
  A
    m
  0           0 RESUME                   0

  1           2 LOAD_CONST               0 (14)
              4 STORE_NAME               0 (y)
              6 RETURN_CONST             1 (None)
```

The second half shows something else: `2 + 3 * 4` is a `BinOp` tree after parsing (you can check with `ast.dump`), but the code object holds the single constant `14`. In this build, the arithmetic on constants is done during compilation, after parsing. This is an optimisation of CPython 3.12, not a language rule.

## `python` has several front doors

All four front doors run your code through the same pipeline. They differ in what `sys.argv`, `__file__` and `sys.path[0]` hold.

![A table of four commands: script, -m, -c and stdin, with the values of sys.argv, __file__ and sys.path[0] for each](diagrams/1.2-run-modes.svg "Measured with the script below. D is the folder of the experiment.")

Two rules to remember, both from the command-line documentation. With a script, Python puts *the script's folder* first on `sys.path`; with `-m`, `-c` or stdin it puts the *current folder* first. The list `sys.path` decides which file `import` finds, and Lesson 1.4 covers it. Also, with `-m` the code runs as `__main__` with `sys.argv[0]` set to the module file's full path.

## Why `__pycache__` exists

Compiling costs time, and a module imported by many programs does not change between runs. So when you `import` a module, CPython saves its compiled code object to a `.pyc` file and reuses it next time.

![Flow chart of import: if a cached pyc matches the source's recorded modification time and size it is loaded with marshal, otherwise the source is compiled and a pyc written; below, the 16-byte header of a real pyc](diagrams/1.2-import-cache.svg "The import-time decision, and the layout of a real .pyc file.")

The header is four 32-bit numbers (PEP 552): a magic number that identifies the bytecode version, a flags word, and the source file's modification time and size. Flags `0` means a *timestamp-based* pyc, the default: it is valid if the recorded time and size match the source file. Other flag values mark hash-based pycs, which PEP 552 describes. After the header comes the code object, serialised by the `marshal` module. Verify on a real file:

<details><summary>Run locally: inspect a real .pyc (standard library only)</summary>

```python
import importlib.util, marshal, os, struct, subprocess, sys, tempfile

with tempfile.TemporaryDirectory() as d:
    with open(f"{d}/mod.py", "w") as f:
        f.write("X = 1\nprint('mod body ran')\n")
    subprocess.run([sys.executable, "-c", "import mod"], cwd=d, check=True, capture_output=True)

    cached = os.listdir(f"{d}/__pycache__")
    print("cache dir:", cached)
    raw = open(f"{d}/__pycache__/{cached[0]}", "rb").read()
    magic, flags, mtime, size = struct.unpack("<4sIII", raw[:16])
    src = os.stat(f"{d}/mod.py")
    print("magic matches this interpreter:", magic == importlib.util.MAGIC_NUMBER)
    print("flags (0 = timestamp-based):", flags)
    print("recorded mtime == source mtime:", mtime == int(src.st_mtime))
    print("recorded size  == source size :", size == src.st_size, size)
    body = marshal.loads(raw[16:])
    print("rest of file is a:", type(body).__name__, body.co_names)
```

```output
cache dir: ['mod.cpython-312.pyc']
magic matches this interpreter: True
flags (0 = timestamp-based): 0
recorded mtime == source mtime: True
recorded size  == source size : True 28
rest of file is a: code ('X', 'print')
```

</details>

The file name `mod.cpython-312.pyc` carries a version tag, so different Python versions keep separate caches side by side (PEP 3147).

How much does the cache save? Loading skips the tokenizer, parser and compiler, but not running the module body.

![Importing a 12,000-line module takes 40.3 ms without a cache and 1.8 ms with one; compile takes 35.2 ms, marshal.loads 1.06 ms, exec of the body 0.43 ms](diagrams/1.2-timing.svg "Measured once on one machine. Absolute times vary; the ratio is the point.")

The run below prints only a comparison, because exact milliseconds depend on your machine:

```python
import marshal, statistics, time

source = "".join(f"def f{i}(a, b):\n    c = a * {i} + b\n    return c - {i}\n\n" for i in range(3000))

def median_ms(fn, runs=5):
    times = []
    for _ in range(runs):
        t0 = time.perf_counter()
        fn()
        times.append(time.perf_counter() - t0)
    return statistics.median(times) * 1000

code = compile(source, "big.py", "exec")
blob = marshal.dumps(code)                     # what a .pyc stores after its header
t_compile = median_ms(lambda: compile(source, "big.py", "exec"))
t_load = median_ms(lambda: marshal.loads(blob))

print("source lines:", source.count("\n"))
print("loading a code object is at least 5x faster than compiling:", t_compile > 5 * t_load)
# The exact milliseconds depend on your machine, so only the comparison is printed.
```

```output
source lines: 12000
loading a code object is at least 5x faster than compiling: True
```

Switches you may need, from the command-line documentation: `python -B` (or the environment variable `PYTHONDONTWRITEBYTECODE`) stops Python writing `.pyc` files; `PYTHONPYCACHEPREFIX` writes them into a mirror folder tree elsewhere instead of next to the sources.

## Calling the pipeline yourself

`compile(source, filename, mode)` runs the first three stages and returns a code object. The mode is `'exec'` for statements, `'eval'` for one expression, `'single'` for one interactive statement. `exec` and `eval` run source or a code object:

```python
print(eval("1 + 2"))
print(exec("a = 1"))
try:
    eval("a = 1")
except SyntaxError as e:
    print(type(e).__name__, "-", e.msg)
```

```output
3
None
SyntaxError - invalid syntax
```

`eval` returns the value of one expression; `exec` runs statements and always returns `None`. Both execute arbitrary code, so never pass them untrusted text (the Python documentation says so for both).

## Common traps

> [!TRAP]
> **"Python runs line by line, so errors appear when reached."** Syntax errors are found while compiling, before the first line of that file runs. Only run-time errors wait for their line. (An imported module is compiled when it is imported, so its syntax error appears later.)

> [!TRAP]
> **Trusting a stale cache.** A timestamp-based `.pyc` is checked only by the source's modification time and size, not its content. Same-size edit plus restored timestamp gives the old behaviour (Question 3). My own reasoning: build tools that normalise timestamps could trigger it.

> [!TRAP]
> **Naming your file like a library.** `random.py` in the folder you run from shadows the standard `random` module, because that folder comes first on `sys.path`. I confirmed this with `python -c "import random"` run in such a folder; see Lesson 1.4.

> [!TRAP]
> **Thinking a `.pyc` makes your program run faster.** It only skips compilation at import. Once loaded, the same bytecode runs at the same speed. The script you start directly is never cached at all.

> [!TRAP]
> **Treating bytecode as stable.** The cache file name carries a version tag (`cpython-312`) and the header holds a magic number that versions the bytecode format. Do not ship `.pyc` files across Python versions or to other Python implementations.

## Summary

- CPython tokenizes, parses, compiles, then runs: the whole file is compiled first, so syntax errors appear before any output.
- Compiling produces code objects, one per module, function and class body, executed by a stack-based eval loop.
- `python file.py`, `-m`, `-c` and stdin all use the same pipeline but set `sys.argv` and `sys.path[0]` differently.
- Imported modules are cached in `__pycache__/*.pyc`; a timestamp-based pyc is reused if the recorded modification time and size match. The directly-run script is never cached.
- The cache saves compile time only: in the measurement above, about 22 times on import for a large module on one machine.

## Quiz time

### Question 1: Predict the output

A file contains these two lines. What does `python file.py` print?

```text
print("a")
x = = 3
```

<details><summary>Show solution</summary>

Nothing on standard output. The parser rejects line 2 with a `SyntaxError` before any instruction runs, so `print("a")` never executes.

</details>

### Question 2: Count the tokens

How many tokens does `tokenize.generate_tokens` yield for the single line `y = x + 1` followed by a newline?

<details><summary>Show solution</summary>

7: NAME `y`, OP `=`, NAME `x`, OP `+`, NUMBER `1`, NEWLINE, ENDMARKER. I confirmed this by running it.

</details>

### Question 3: Find the stale cache

`mod.py` contains `X = 1` and has been imported once. A deploy script overwrites it with `X = 2` and sets its modification time back to the old value. The next `python -c "import mod; print(mod.X)"` prints `1`. Why, and how do you fix it?

<details><summary>Show solution</summary>

The file size is unchanged (both versions are 6 bytes) and the modification time equals the one recorded in the `.pyc` header, so the timestamp check passes and the cached code object is loaded. I reproduced this: the output was `1`. Fix it by deleting the `__pycache__` file, giving the new file a different modification time, or building hash-based pycs with `check_source` enabled (PEP 552).

</details>

### Question 4: eval versus exec

What do `exec("a = 1")` and `eval("a = 1")` return or raise, and why?

<details><summary>Show solution</summary>

`exec` runs the statement and returns `None`. `eval` expects one expression and `a = 1` is a statement, so it raises `SyntaxError: invalid syntax` (message from 3.12.13).

</details>
