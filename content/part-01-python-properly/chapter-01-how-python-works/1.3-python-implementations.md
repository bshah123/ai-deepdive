"Python" names a language, but the program that runs your file is a separate thing, and there is more than one. In this lesson you will tell the main implementations apart, measure how much faster PyPy is than CPython on four workloads (and where it is slower), and see one visible behaviour that differs.

**You need:** the pipeline from Lesson 1.2 (source, then bytecode, then execution) and a terminal. The PyPy parts are optional to run.

## The problem: "Python" is two things

A **language** is a written description: which syntax is legal and what each statement must do. An **implementation** is a program that follows that description and runs your code. The Python documentation lists several, and warns that each "varies in some way from the language as documented" (Python Language Reference, chapter 1).

![The Python language described in the Language Reference at the top, with three programs below it: CPython written in C, PyPy written in RPython with a tracing JIT, and Jython written in Java running on the JVM](diagrams/1.3-spec-vs-impl.svg "One language, three programs that run it. Facts from the Python Language Reference, the PyPy documentation and jython.org.")

- **CPython** is the original and most-maintained implementation, written in C. When this course says "Python", it means CPython unless stated otherwise.
- **PyPy** is written in **RPython**, a Python-like language that PyPy's toolchain translates to C. It adds a **JIT** (just-in-time compiler: it compiles code to machine code while the program runs).
- **Jython** is Python implemented in Java, running on the **JVM** (Java Virtual Machine). On jython.org (checked November 2026) the current release "only supports Python 2", so it cannot run modern Python 3 code.
- IronPython targets Microsoft's .NET platform. I did not test it.

Ask the running program which one it is. This block runs in the browser:

```python
import sys, platform

print(sys.implementation.name)
print(platform.python_implementation())
print(hasattr(sys, "getrefcount"))
```

```output
cpython
CPython
True
```

`sys.implementation` was added so that programs and libraries can ask this question (Python `sys` documentation). Under PyPy 3.11 on my machine the same three lines print `pypy`, `PyPy`, `False`: PyPy has no `sys.getrefcount`, a difference explained below.

## Same front half, different back half

All of them start the way Lesson 1.2 showed: read the source, compile it to an internal instruction list called **bytecode**, then run that. They differ in the second half.

![Three lanes from hello.py to bytecode to execution: CPython runs it with a loop in C, PyPy with an interpreter plus a JIT, Jython on the Java Virtual Machine; a note shows that CPython 3.12 and PyPy 3.11 produce different bytecode for a + b](diagrams/1.3-three-pipelines.svg "The second half differs. Even the bytecode is private to each implementation.")

- **CPython** executes bytecode with a loop written in C, one instruction at a time. CPython 3.12, which I used here, has no JIT, but since 3.11 it rewrites hot instructions to type-specific versions (Lesson 1.6). An experimental JIT arrived in 3.13 and is also covered in Lesson 1.6.
- **PyPy** also compiles to bytecode, but not the same bytecode (see the note in the diagram, from `dis.dis` on both). Its JIT is a tracing JIT, and PyPy's architecture documentation says it "traces the interpreter written in RPython, rather than the user program".
- **Jython** compiles Python to Java bytecode (stated in Jython's archived 2.1 documentation; I could not run Jython, because this machine has no Java runtime, so nothing below measures it).

> [!KEY-INSIGHT]
> Bytecode is an implementation detail, not part of the language. A `.pyc` file from CPython 3.12 means nothing to PyPy, which is why `sys.implementation.cache_tag` differs (`cpython-312` versus `pypy311` on my machine).

## Measured: where a JIT helps and where it does not

Same four functions, same machine, one process per interpreter, median of 5 runs. The benchmark script is in the collapsed block below.

![Horizontal bars for four workloads: integer loop 0.550 s versus 0.014 s, fib(30) 0.088 s versus 0.007 s, objects 0.433 s versus 0.073 s, sort and join 0.272 s versus 0.198 s](diagrams/1.3-speedups.svg "CPython 3.12.13 versus PyPy 7.3.23 (Python 3.11.15), Apple M-series. Timings depend on the machine.")

The ratios, by hand: $0.550 / 0.014 \approx 39$ (I say "about 40×": 0.014 is rounded to three decimals, so this ratio is good to roughly ±4%), $0.088 / 0.007 \approx 13$, $0.433 / 0.073 \approx 6$ and $0.272 / 0.198 \approx 1.4$.

Why such different gains? This part is my own reasoning (speculation, label c), consistent with the numbers but not tested by me. The loop and the recursive calls spend all their time running Python bytecode, which is exactly what a JIT can compile. In `sort+join`, most time goes into `list.sort`, `str`, and `join`, which are already native code in both implementations, so there is little left to speed up.

> [!WARNING]
> The 40× is a best case: a tiny loop of integer arithmetic. Real programs spend time in libraries, I/O and C extensions, and those do not speed up. Measure your own workload.

<details>
<summary>Run locally: needs PyPy installed (I used uv python install pypy)</summary>

Save as `bench.py`, run `python bench.py` and `pypy3 bench.py`. Versions: CPython 3.12.13, PyPy 7.3.23 (Python 3.11.15).

```python
import sys, time, random

def loop_kernel(n):
    total = 0
    for i in range(n):
        total += (i * i) % 7
    return total

def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

def builtin_kernel(n):
    random.seed(0)
    data = [random.random() for _ in range(n)]
    data.sort()
    return len("".join(map(str, range(n // 5)))) + int(data[n // 2] * 1000)

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y
    def dot(self):
        return self.x * self.y

def object_kernel(n):
    pts = [Point(i, i % 7) for i in range(n)]
    return sum(p.dot() for p in pts)

def seconds(f, *args):
    t = time.perf_counter()
    f(*args)
    return time.perf_counter() - t

print(sys.implementation.name, sys.version.split()[0])

# warm-up: the same call twelve times, fresh process
print("fib(24) call 1..12, ms:", " ".join(f"{seconds(fib, 24) * 1000:.2f}" for _ in range(12)))

# steady state: median of 5 runs
for name, f, arg in [("loop 10M", loop_kernel, 10_000_000), ("fib(30)", fib, 30),
                     ("sort+join 1M", builtin_kernel, 1_000_000), ("objects 1M", object_kernel, 1_000_000)]:
    runs = sorted(seconds(f, arg) for _ in range(5))
    print(f"{name:13s} {runs[2]:.3f} s")
```

Output of one run on my machine (the third of three; the other two differed by a few percent). Timings change with hardware, so yours will differ.

```text

fib(24) call 1..12, ms: 4.89 5.04 4.91 4.89 5.01 4.89 4.90 5.04 4.92 4.84 4.82 5.19
loop 10M      0.550 s
fib(30)       0.088 s

objects 1M    0.433 s
```


## Warm-up: the JIT is not free

Look at the `fib(24)` line above. CPython takes about 4.9 ms on every call. PyPy takes 10.79 ms on call 1, then about 0.84 ms.

![Twelve pairs of bars for successive calls of fib(24): CPython about 4.9 ms each; PyPy 10.79 ms on call 1 then about 0.84 ms](diagrams/1.3-warmup.svg "Per-call time of the same function. Call 1 includes the JIT's recording and compiling work.")

My explanation, from first principles and consistent with the numbers, is that call 1 pays for deciding what is hot and compiling it, and later calls reuse the result. The exact number of slow calls varied between my runs (one slow call in the script above, three in an earlier variant of it), so treat the shape as the stable part, not the count.

Worked example: when does the JIT pay for itself? Add up the time per call and find the first call where PyPy's total is lower. This block uses only the standard library and the numbers printed above:

```python
# ms per call of fib(24), calls 1..12, copied from the benchmark run in the previous section
cpython = [4.89, 5.04, 4.91, 4.89, 5.01, 4.89, 4.90, 5.04, 4.92, 4.84, 4.82, 5.19]
pypy    = [10.79, 0.88, 0.82, 0.83, 0.84, 0.83, 0.83, 0.83, 0.84, 0.82, 0.85, 0.88]

total_c = total_p = 0.0
for n, (c, p) in enumerate(zip(cpython, pypy), start=1):
    total_c += c
    total_p += p
    flag = "  <- PyPy total is now lower" if total_p < total_c else ""
    if n <= 4 or flag:
        print(f"after call {n}: CPython {total_c:6.2f} ms, PyPy {total_p:6.2f} ms{flag}")
    if flag:
        break
print("steady-state ratio:", round(sum(cpython[1:]) / sum(pypy[1:]), 1))
```

```output
after call 1: CPython   4.89 ms, PyPy  10.79 ms
after call 2: CPython   9.93 ms, PyPy  11.67 ms
after call 3: CPython  14.84 ms, PyPy  12.49 ms  <- PyPy total is now lower
steady-state ratio: 5.9
```

By hand for call 3: CPython $4.89 + 5.04 + 4.91 = 14.84$ ms; PyPy $10.79 + 0.88 + 0.82 = 12.49$ ms. Here the break-even is at about 12 ms of total run time. A script that finishes in a few milliseconds never reaches it.

## Another difference: when objects die

CPython frees most objects the moment their **reference count** (the number of names and containers pointing at them) drops to zero. PyPy's documentation says its garbage collectors "are not based on reference counting, so the objects are not freed instantly when they are no longer reachable", and that the timing of `__del__` (a method run just before an object is freed) "is not reliable or timely in PyPy". It also says PyPy does not implement `sys.getrefcount`, matching the `False` above.

```python
import gc

class Resource:
    def __del__(self):
        print("  __del__ ran")

a = Resource()
print("del a ...")
del a
print("after del a")
gc.collect()
print("after gc.collect()")
```

```output
del a ...
  __del__ ran
after del a
after gc.collect()
```

That is the CPython output. Under PyPy 3.11 on my machine the `__del__` line moved to after `after del a`, as the next picture shows.

![Two columns of printed lines: in CPython __del__ ran appears directly after del a; in PyPy it appears after the line after del a, when the garbage collector runs](diagrams/1.3-del-timeline.svg "Order of printed lines, top to bottom. The highlighted line is the __del__ call.")

The same documentation says files are not promptly closed when they go out of scope. Code that works on CPython only because a refcount happened to close a file or release a lock is therefore a latent bug on PyPy. The fix is portable: use `with`.

C extension modules also behave differently. The same PyPy page says its compatibility layer for CPython's C extensions, `cpyext`, "adds complexity and is slow", and recommends cffi. I did not test NumPy or PyTorch on PyPy, so check your dependencies before switching.

| You have | Reasonable default |
|---|---|
| Normal code, NumPy, PyTorch, the libraries in this course | CPython |
| Long-running, CPU-bound, pure-Python code with few C extensions | Try PyPy, and measure |
| A Java application that must embed Python 2.7 scripts | Jython |

## Common traps

> [!TRAP]
> "PyPy is 40 times faster than Python." On my four workloads the gain ran from 1.4× to about 40×. A speed-up belongs to a workload, a machine and two versions, not to an implementation name.

> [!TRAP]
> Timing one short call on a JIT. `fib(24)` once on PyPy was 2× slower than CPython here. Time the steady state, and time something that lasts as long as your real job.

> [!TRAP]
> Cleaning up with `__del__` or relying on a refcount to close a file. It works on CPython by an implementation detail. Use `with` or an explicit `close()`.

> [!TRAP]
> Mixing up the two version numbers. On my PyPy, `sys.version_info` is `(3, 11, 15)` (the language) and `sys.implementation.version` is `(7, 3, 23)` (PyPy itself). Only on CPython are they equal.

## Summary

- A language is a description; CPython, PyPy and Jython are different programs that implement it, and they can behave differently.
- All of them compile to bytecode first; the bytecode is private to each implementation.
- On my machine PyPy was about 1.4× to 40× faster than CPython 3.12, depending on how much time the workload spent in compiled-away Python code.
- A JIT has a warm-up cost: PyPy lost on the first call of `fib(24)` and won from the third call on.
- Do not depend on CPython-only behaviour such as immediate `__del__`, `sys.getrefcount` or fast C extensions.

## Quiz time

### Question 1: Calculation

Suppose a PyPy function needs 20 ms on its first call and 1 ms on every later call, while CPython needs 5 ms on every call. After how many calls is PyPy's total time lower?

<details>
<summary>Show solution</summary>

PyPy total after $n$ calls: $20 + (n - 1)$. CPython total: $5n$. The first $n$ with $20 + n - 1 < 5n$, that is $19 < 4n$, is $n = 5$ (24 ms versus 25 ms). At $n = 4$ it is 23 ms versus 20 ms, so PyPy is still behind.

</details>

### Question 2: Predict

What does the `Resource` program print under CPython, and what is the likely output under PyPy?

<details>
<summary>Show solution</summary>

CPython: `del a ...`, `  __del__ ran`, `after del a`, `after gc.collect()`, because the reference count reaches zero at `del a`. On my PyPy the order was `del a ...`, `after del a`, `  __del__ ran`, `after gc.collect()`. PyPy's documentation calls the timing unreliable, so another run or version may differ.

</details>

### Question 3: Find the flaw

A colleague runs `t = time.perf_counter(); fib(24); print(time.perf_counter() - t)` once on both interpreters, sees 10.79 ms on PyPy versus 4.89 ms on CPython, and concludes that PyPy is 2× slower. What is wrong?

<details>
<summary>Show solution</summary>

One call measures PyPy's warm-up, not its steady state. Repeat the call (or run the real job for long enough) and compare the later calls. In the lesson's run, calls 2 to 12 took about 0.84 ms against about 4.9 ms.

</details>

### Question 4: Explain

On a machine with PyPy 7.3.23, `sys.version_info[:3]` is `(3, 11, 15)`. Which number tells you whether the `match` statement (added in Python 3.10) is available, and why is `sys.implementation.version` the wrong one?

<details>
<summary>Show solution</summary>

`sys.version_info` reports the language version the interpreter conforms to, so 3.11 means `match` is available. `sys.implementation.version` is the version of the implementation itself (PyPy 7.3.23), a separate numbering (Python `sys` documentation). They coincide only for CPython.

</details>

### Question 5: Explain

Can you run a script that uses Python 3.12 features on Jython?

<details>
<summary>Show solution</summary>

No. On jython.org (checked November 2026) the current release supports only Python 2, so Python 3 code will not run on it.

</details>
