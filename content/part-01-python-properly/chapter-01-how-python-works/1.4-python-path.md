When you write `import something`, Python looks through an ordered list of folders and takes the first match. In this lesson you will read that list, predict which file an import loads, and explain two classic failures: a `ModuleNotFoundError` for a package you installed, and a file of yours that silently replaces a standard-library module.

**You need:** to have run a Python script and used `import` (Lesson 1.2 shows what an import executes). Everything below was run on Python 3.12.

## The problem: which file did that import load?

A **module** is one Python file that other code can `import`. A **package** is a folder of modules. Python does not know where your modules live; at every `import` it searches a list of folders called `sys.path`.

Two symptoms come from not knowing this list:

- **A missing module.** You installed a package, yet `import` raises `ModuleNotFoundError`, because the folder the package was installed into is not on this interpreter's list.
- **The wrong module.** You name a helper file `random.py`, and later `random.randint(1, 6)` crashes, because your file was found before the standard library's.

## What `sys.path` contains

`sys.path` is an ordinary Python list of strings, one folder (or zip file) per entry. It is built once at start-up, in this order:

![sys.path from top to bottom: the script's folder, PYTHONPATH entries, python312.zip, the standard library folder, lib-dynload, site-packages, and lines from .pth files](diagrams/1.4-sys-path-order.svg "The order of sys.path on Python 3.12 in a virtual environment. Searching goes top to bottom.")

The Python docs describe the same order: the input script's folder first (the current directory when there is no script), then the `PYTHONPATH` environment variable (a list of folders you set in your shell, separated by `:` on macOS and Linux), then the directories of the standard library and the compiled extension modules it needs, and finally the `site` module, which adds the `site-packages` folders. The standard-library zip entry is added even if the archive does not exist.

To see your own list, run `python -c "import sys; print(*sys.path, sep='\n')"`. The folders are specific to your machine, so this lesson labels them by role rather than printing them.

## What `import mod` does with the list

The search is one step of a short procedure:

![Import steps: check sys.modules; ask the built-in, frozen and path finders in order; the path finder asks each sys.path folder in turn; inside a folder a package directory is tried first, then module files, then a folder without __init__.py is only a candidate](diagrams/1.4-import-lookup.svg "The lookup behind import. The right-hand note is the rule inside one folder.")

1. **Cache.** `sys.modules` is a dictionary of every module already imported. A hit ends the import with no search (Import reference, section 5.3.1).
2. **Finders.** `sys.meta_path` holds the *finders*, objects that know where modules can come from. The default three handle built-in modules, frozen modules (bytecode embedded in the interpreter) and files on `sys.path`. Built-ins come first, so a file named after a built-in module is never looked at (Tutorial, section 6.1.2). In the virtual environment I used, two helper finders from other tools sat in front of these three, so the list on your machine can be longer.
3. **Path walk.** The path finder asks each `sys.path` entry in order. The first entry that has the module wins, and later entries are never consulted.

## Worked example: first match wins, and the cache remembers

Two folders each hold a file `mod.py` that says which folder it lives in. The code asks the search step alone (`PathFinder.find_spec`) where `mod` would be found, and then really imports it, three times:

![Three panels: path [dir_a, dir_b] imports dir_a; after inserting dir_b at the front the import still gives dir_a from the cache; after deleting the cache entry the import gives dir_b](diagrams/1.4-first-match-cache.svg "Reordering sys.path changes what a fresh search finds, but not what is already in sys.modules.")

```python
import importlib.machinery
import os
import sys
import tempfile

root = tempfile.mkdtemp()
for d in ("dir_a", "dir_b"):
    os.mkdir(os.path.join(root, d))
    with open(os.path.join(root, d, "mod.py"), "w") as f:
        f.write(f"WHO = {d!r}\n")

a, b = os.path.join(root, "dir_a"), os.path.join(root, "dir_b")
sys.path[:0] = [a, b]                       # a is searched before b

def where(name):                            # the search step alone: PathFinder walks sys.path
    return os.path.relpath(importlib.machinery.PathFinder.find_spec(name).origin, root)

print("search finds     :", where("mod"))
import mod
print("1st import       :", mod.WHO)

sys.path.insert(0, b)                       # now b is searched first
print("search finds now :", where("mod"))
import mod                                  # no search happens: "mod" is in sys.modules
print("2nd import       :", mod.WHO)

del sys.modules["mod"]                      # forget the cached module
import mod
print("after del        :", mod.WHO)
```

```output
search finds     : dir_a/mod.py
1st import       : dir_a
search finds now : dir_b/mod.py
2nd import       : dir_a
after del        : dir_b
```

The fourth line is the one to study. The search would now find `dir_b/mod.py`, yet the import returns `dir_a`, because `import` checks `sys.modules` before it looks at `sys.path`. The Import reference says deleting a key from `sys.modules` makes Python "search anew" on the next import, which is the last line.

> [!KEY-INSIGHT]
> `sys.path` is only consulted on a cache miss. Editing it after a module has been imported cannot change that module; it affects only modules not yet imported.

## Inside one folder: package, module, or namespace

A single folder can hold a package and a module with the same name, and a folder without `__init__.py` is a special case (an *implicit namespace package*, a folder that can be imported but has no code of its own). Which one wins?

```python
import importlib.util
import os
import sys
import tempfile

root = tempfile.mkdtemp()
def make(path, text=""):
    full = os.path.join(root, path)
    os.makedirs(os.path.dirname(full), exist_ok=True)
    with open(full, "w") as f:
        f.write(text)

make("one/thing.py")                        # one folder holding thing.py ...
make("one/thing/__init__.py")               # ... and a package called thing
make("two/ns/data.txt")                     # a folder with no __init__.py
make("three/ns.py")                         # a plain module with the same name

sys.path[:0] = [os.path.join(root, p) for p in ("one", "two", "three")]
for name in ("thing", "ns"):
    spec = importlib.util.find_spec(name)
    print(name, "->", os.path.relpath(spec.origin, root))
```

```output
thing -> one/thing/__init__.py
ns -> three/ns.py
```

Inside one folder the package directory beats `thing.py`. The folder `two/ns` comes earlier on `sys.path` but has no `__init__.py`, so it is only a candidate: the search keeps going, and the real module `three/ns.py` wins. A candidate is used only when no later entry has anything better. This precedence comes from my reading of CPython 3.12's `FileFinder.find_spec` (in `Lib/importlib/_bootstrap_external.py`) and from the run above; the Import reference describes namespace packages but does not state this ordering.

## Who writes the front of the list

The first entry depends on how you start Python. This is the entry the lesson's later bug hangs on.

![Table of launch modes: python show.py puts the script's folder first; python -m show puts the current directory; python -c puts an empty string; python -P puts nothing; PYTHONPATH adds entries after the front entry](diagrams/1.4-launch-modes.svg "The entry placed in front of the standard library for each way of starting Python 3.12.")

<details><summary>Run locally: starts Python as a subprocess, so the browser runner cannot</summary>

```python
import os, subprocess, sys, tempfile

def label(p, T):
    if p == "": return "''"
    if p == T: return "<T>"
    if p.startswith(T + os.sep): return "<T>" + p[len(T):]
    return "<std>"                          # stdlib zip, stdlib, lib-dynload, site-packages

with tempfile.TemporaryDirectory() as T:
    T = os.path.realpath(T)
    os.makedirs(f"{T}/extra"); os.makedirs(f"{T}/elsewhere")
    with open(f"{T}/show.py", "w") as f:
        f.write("import sys\nfor p in sys.path: print(repr(p))\n")
    env = {k: v for k, v in os.environ.items() if k not in ("PYTHONPATH", "PYTHONSAFEPATH")}
    show = "import sys\nfor p in sys.path: print(repr(p))"
    runs = [
        ("python show.py", ["show.py"], T, {}),
        ("python /T/show.py, cwd=elsewhere", [f"{T}/show.py"], f"{T}/elsewhere", {}),
        ("python -m show", ["-m", "show"], T, {}),
        ("python -c '...'", ["-c", show], T, {}),
        ("python -P show.py", ["-P", "show.py"], T, {}),
        ("PYTHONPATH=extra python show.py", ["show.py"], T, {"PYTHONPATH": f"{T}/extra"}),
    ]
    for name, args, cwd, extra in runs:
        r = subprocess.run([sys.executable] + args, capture_output=True, text=True, cwd=cwd, env={**env, **extra})
        ents = [label(eval(l), T) for l in r.stdout.splitlines()]
        print(f"{name:<34}", [e for e in ents if e != "<std>"] or "(nothing added)")
```

```output
python show.py                     ['<T>']
python /T/show.py, cwd=elsewhere   ['<T>']
python -m show                     ['<T>']
python -c '...'                    ["''"]
python -P show.py                  (nothing added)
PYTHONPATH=extra python show.py    ['<T>', '<T>/extra']
```

</details>

`<T>` is the temporary folder that holds `show.py`. In the second row the script's folder, not the current directory (`elsewhere`), is what gets added. The `-m` row shows the current directory, which for `-m` is the folder you ran the command from. For `-c`, the empty string means the current directory, and the Import reference adds that this entry is looked up fresh at each import rather than cached.

The `-P` flag (and the `PYTHONSAFEPATH` environment variable) was added in Python 3.11 to skip this front entry. The docs call that entry "potentially unsafe"; the reason, in my reading, is that anyone who can put a file into that folder can replace a module you import.

## How `site-packages` and `.pth` files join the list

The `site` module runs at start-up, appends the `site-packages` folder, and reads every `.pth` file (path configuration file) it finds there. Each line of a `.pth` file names one more folder to append. The docs say that non-existent folders are never added, that no item is added twice, and that blank lines and lines starting with `#` are skipped. The next block does by hand what `site` does for each `site-packages` folder:

```python
import os
import site
import sys
import tempfile

root = tempfile.mkdtemp()
site_dir = os.path.join(root, "site_dir")
os.makedirs(os.path.join(site_dir, "pth_lib"))
with open(os.path.join(site_dir, "demo.pth"), "w") as f:
    f.write("# comment lines are ignored\npth_lib\nno_such_dir\n")

before = len(sys.path)
site.addsitedir(site_dir)                   # what Python does for each site-packages folder
for p in sys.path[before:]:
    print(os.path.relpath(p, root))
```

```output
site_dir
site_dir/pth_lib
```

Two entries appeared: the folder itself, then `pth_lib` from the `.pth` line. `no_such_dir` was dropped. A bare name is joined onto the folder that holds the `.pth` file (visible in CPython's `site.py`; the docs show it only by example). Lines that begin with `import` are *executed* by `site`, a feature the docs list as deprecated from Python 3.15 and slated to be ignored in 3.18; I did not run that here.

A **virtual environment** (a project-private copy of the install layout, made by `python -m venv`) changes only the last part of the list. Its `pyvenv.cfg` file moves `sys.prefix` to the environment, so its `site-packages` is the one that is searched, while the standard library still comes from the base install.

<details><summary>Run locally: creates a virtual environment (about a second)</summary>

```python
import os, subprocess, sys, tempfile

probe = ("import sys, os\n"
         "print('prefix != base_prefix :', sys.prefix != sys.base_prefix)\n"
         "print('os comes from base     :', os.__file__.startswith(sys.base_prefix))\n"
         "sp = [p for p in sys.path if p.endswith('site-packages')]\n"
         "print('site-packages entries  :', len(sp), '| inside the venv:', all(p.startswith(sys.prefix) for p in sp))\n")
with tempfile.TemporaryDirectory() as T:
    subprocess.run([sys.executable, "-m", "venv", "--without-pip", f"{T}/venv"], check=True)
    r = subprocess.run([f"{T}/venv/bin/python", "-c", probe], capture_output=True, text=True, cwd=T)
    print(r.stdout.rstrip() or r.stderr[-300:])
```

```output
prefix != base_prefix : True
os comes from base     : True
site-packages entries  : 1 | inside the venv: True
```

</details>

This is the likely cause of the missing-module symptom (my reasoning from the result above, not checked against pip's documentation): a package installed by one interpreter's `pip` lands in that interpreter's `site-packages`, and a different interpreter does not have that folder on its list.

## Shadowing: your file in front of the standard library

Because the script's folder sits at index 0, ahead of the standard library, a file of yours with a standard-library name hides the real module. The Tutorial states this and calls it "an error unless the replacement is intended".

![Left, python main.py: the cwd's random.py is found first and the stdlib one is never reached, so random.randint does not exist. Right, python -P main.py: the cwd is not added and the stdlib random is imported](diagrams/1.4-shadowing.svg "The same two files with and without the front entry.")

<details><summary>Run locally: starts Python as a subprocess, so the browser runner cannot</summary>

```python
import os, subprocess, sys, tempfile

with tempfile.TemporaryDirectory() as T:
    os.makedirs(f"{T}/cwd")
    with open(f"{T}/cwd/random.py", "w") as f:                # an innocent-looking helper file
        f.write("print('local random.py is running')\n")
    with open(f"{T}/cwd/main.py", "w") as f:
        f.write("import os, random\n"
                "print('random is the local file:', os.path.dirname(random.__file__).endswith('cwd'))\n"
                "print('random.randint exists   :', hasattr(random, 'randint'))\n")
    env = {k: v for k, v in os.environ.items() if k not in ("PYTHONPATH", "PYTHONSAFEPATH")}
    for flags in ([], ["-P"]):
        r = subprocess.run([sys.executable, *flags, "main.py"], capture_output=True, text=True, cwd=f"{T}/cwd", env=env)
        print("python", " ".join(flags + ["main.py"]))
        print(r.stdout.rstrip() or r.stderr.strip().splitlines()[-1])
```

```output
python main.py
local random.py is running
random is the local file: True
random.randint exists   : False
python -P main.py
random is the local file: False
random.randint exists   : True
```

</details>

Without `-P`, the harmless-looking `random.py` ran, and `main.py` then got an `AttributeError` at the first `random.randint` call, with no hint about the cause. In the same experiment I also ran `python random.py` on a file named `random.py` that does `import random`; it found itself and raised `AttributeError: partially initialized module 'random' has no attribute 'randint' (most likely due to a circular import)`.

## Common traps

> [!TRAP]
> **Naming your file after a standard-library module.** `random.py`, `email.py`, `json.py`, `string.py`, `types.py` all shadow something. A file `email.py` next to a script that imports `smtplib` fails with `No module named 'email.utils'; 'email' is not a package`, an error that mentions a module you never imported. Check the name against `sys.stdlib_module_names` (Python 3.10+).

> [!TRAP]
> **Expecting a `sys.path` change to re-import.** After a module is in `sys.modules`, reordering the list does nothing for it. Use `importlib.reload` to re-run a module, or delete the cache entry as above (the Import reference warns that old references then point at a different module object).

> [!TRAP]
> **Assuming a name is shadowable.** Built-in modules are searched first, so a local `math.py` is ignored on builds where `math` is compiled in (it was on mine). Whether a module is built in depends on how Python was built; `sys.builtin_module_names` lists them. Never rely on either outcome.

> [!TRAP]
> **`python script.py` and `python -m package.script` import differently.** They put different folders at the front (script's folder versus current directory), so code that works one way can fail the other. Do not fix it with `sys.path.insert(0, ...)` inside library code. In my own judgement, installing the project (for example with `pip install -e .`) or running it with `-m` from its root is more portable, because the path no longer depends on where a file sits.

## Summary

- `sys.path` is a list of folders, built at start-up: front entry (script folder, current directory, or nothing with `-P`), `PYTHONPATH`, standard library, then `site-packages` and `.pth` lines.
- `import` checks `sys.modules` first, then the built-in and frozen finders, then walks `sys.path` top to bottom; the first match wins.
- Inside a folder, a package directory beats a same-named module file, and a folder with no `__init__.py` is used only if nothing later provides the name.
- Changing `sys.path` affects only modules not yet imported.
- Shadowing and wrong-interpreter problems are diagnosed by printing `module.__file__` and `sys.path` for the interpreter that failed.

## Quiz time

### Question 1: Predict the file

`sys.path` is `['/p', '/q', '/r']`. Folder `/p` is empty. `/q` holds `a.py` and a folder `b/` containing only `data.txt`. `/r` holds `a.py` and `b.py`. Which file does `import a` load, and which does `import b` load?

<details><summary>Show solution</summary>

`import a` loads `/q/a.py`: `/p` has nothing, and `/q` is the first entry with a match. `import b` loads `/r/b.py`: the folder `/q/b` has no `__init__.py`, so it is only a namespace candidate, and the search continues to `/r`, which has a real module. (This is the pattern of the `ns` example above.)

</details>

### Question 2: What does this print?

Using the setup of the first code block (`mod` already imported from `dir_a`):

```text
sys.path.remove(a)
import mod
print(mod.WHO)
```

<details><summary>Show solution</summary>

It prints `dir_a`, with no error. `mod` is in `sys.modules`, so no search happens and the removed folder is irrelevant. A fresh interpreter with `a` removed would find `dir_b/mod.py` instead.

</details>

### Question 3: Find the bug

A folder contains `email.py` (a helper for drafting messages) and `tool.py`, which starts with `import smtplib`. `python tool.py` fails with `ModuleNotFoundError: No module named 'email.utils'; 'email' is not a package`. Why, and what are two fixes?

<details><summary>Show solution</summary>

The script's folder is first on `sys.path`, so when `smtplib` runs `import email.utils`, Python finds the local `email.py`, which is a module and not a package. Fixes: rename `email.py` (best); or run with `python -P tool.py`, which keeps the folder off the path (and then the helper must be imported another way). I ran both cases: the first fails with the message above, the second prints normally.

</details>

### Question 4: Explain

In an empty folder you run `python -c "import sys; print(repr(sys.path[0]))"`. What prints, and how does it differ from running a script in that folder?

<details><summary>Show solution</summary>

It prints `''`, the empty string, which means the current directory (resolved at each import). For `python script.py` the first entry is the script's folder as an actual path, and it stays that folder even if you run the command from elsewhere.

</details>
