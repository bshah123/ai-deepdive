When you finish this lesson you will be able to read the output of `dis`, say where each instruction's argument points, find the jumps in a loop, tell what the compiler already computed before the program ran, and use all of that to explain a measured speed difference. You will also know where `dis` output stops being trustworthy.

**You need:** Lesson 1.2 (source becomes a code object, and the eval loop is a stack machine). Everything here was run on CPython 3.12.13. Opcode names and offsets differ in other versions; one section shows how.

## The problem: the source hides what runs

Three things are invisible in Python source. How many steps a line takes. Which kind of access each name uses. What the compiler already worked out. `dis` is a standard-library module that prints the instructions of a code object, so you can look. Lesson 1.2 used it to count instructions. This lesson teaches you to read every column, and ends with a loop that runs in 48 ms at module level and 25 ms inside a function, with the same source line in both.

## Reading one function

![dis output for the function bill, with the columns named, and arrows from three arguments to the tables co_varnames, co_names and co_consts](diagrams/1.5-anatomy.svg "Real 3.12.13 output for bill. An argument is usually an index into a table stored on the code object.")

Run it and compare with the picture:

```python
import dis

def bill(price, qty):
    total = price * qty
    return round(total, 2)

dis.dis(bill)
code = bill.__code__
print("co_varnames:", code.co_varnames)
print("co_names:   ", code.co_names)
print("co_consts:  ", code.co_consts)
```

```output
  3           0 RESUME                   0

  4           2 LOAD_FAST                0 (price)
              4 LOAD_FAST                1 (qty)
              6 BINARY_OP                5 (*)
             10 STORE_FAST               2 (total)

  5          12 LOAD_GLOBAL              1 (NULL + round)
             22 LOAD_FAST                2 (total)
             24 LOAD_CONST               1 (2)
             26 CALL                     2
             34 RETURN_VALUE
co_varnames: ('price', 'qty', 'total')
co_names:    ('round',)
co_consts:   (None, 2)
```

The columns, left to right: the source line (printed only on the first instruction of each line), the **offset** (position in bytes), the **opname**, the **arg** (a number), and in parentheses `argrepr`, the `dis` module's reading of that number.

The number is usually an index into a table on the code object. `LOAD_FAST 1` pushes `co_varnames[1]`, which is `qty`. `LOAD_CONST 1` pushes `co_consts[1]`, which is `2`. One exception shows why you must read the documentation rather than guess: `LOAD_GLOBAL 1` does not read `co_names[1]`. The documentation says it loads `co_names[namei>>1]`, and the low bit asks for an extra `NULL` to be pushed for the call that follows. So `1 >> 1 = 0`, and the name is `round`. (`co_consts[0]` is `None`; no instruction here uses it.)

Now follow the stack by hand for `bill(2.5, 3)`. `LOAD_FAST price` pushes 2.5, `LOAD_FAST qty` pushes 3, `BINARY_OP *` replaces both with 7.5, `STORE_FAST total` empties the stack. `LOAD_GLOBAL` pushes `NULL` and `round` (depth 2), `LOAD_FAST total` pushes 7.5 (3), `LOAD_CONST 2` pushes 2 (4), and `CALL 2` pops the callable, the `NULL` and two arguments and pushes the result (depth 1). `RETURN_VALUE` pops it. `dis.stack_effect` gives each instruction's change in depth, so the code can check that bookkeeping and the offset gaps:

```python
import dis

def bill(price, qty):
    total = price * qty
    return round(total, 2)

depth = 0
for ins in dis.get_instructions(bill):
    depth += dis.stack_effect(ins.opcode, ins.arg)
    print(f"{ins.offset:>3} {ins.opname:<13} {str(ins.arg):>4}  depth after: {depth}")

slots = len(list(dis.get_instructions(bill, show_caches=True)))
print(len(list(dis.get_instructions(bill))), "instructions,", slots, "slots,", len(bill.__code__.co_code), "bytes")
```

```output
  0 RESUME           0  depth after: 0
  2 LOAD_FAST        0  depth after: 1
  4 LOAD_FAST        1  depth after: 2
  6 BINARY_OP        5  depth after: 1
 10 STORE_FAST       2  depth after: 0
 12 LOAD_GLOBAL      1  depth after: 2
 22 LOAD_FAST        2  depth after: 3
 24 LOAD_CONST       1  depth after: 4
 26 CALL             2  depth after: 1
 34 RETURN_VALUE  None  depth after: 0
10 instructions, 18 slots, 36 bytes
```

The offsets go 6, 10, 12, 22, 26, 34 instead of counting by 2. Each instruction is one 2-byte slot, and some are followed by hidden **inline cache** slots (shown as `CACHE` with `show_caches=True`) that the interpreter uses to store lookup results. The `dis` documentation says logically that space belongs to the preceding instruction. Here 10 instructions plus 8 cache slots fill 18 slots, which is 36 bytes. One consequence: `len(co_code) / 2` is not the instruction count. In 3.13 and later `get_instructions` no longer yields separate cache items (the docs deprecate `show_caches` there), so the slot count line above is a 3.12 result.

## Loops are jumps

A `for` loop has no loop instruction. It is a `FOR_ITER` that either pushes the next item or jumps past the loop, and a `JUMP_BACKWARD` at the bottom of the body.

![Control flow of the function total: setup, a FOR_ITER block that is a jump target, a body that ends with a backward jump, and an exit block reached when the iterator is exhausted](diagrams/1.5-loop-jumps.svg "The three colours match the source lines on the left.")

```python
import dis

def total(xs):
    s = 0
    for x in xs:
        s += x
    return s

dis.dis(total)
print("jump targets at offsets:", [ins.offset for ins in dis.get_instructions(total) if ins.is_jump_target])
```

```output
  3           0 RESUME                   0

  4           2 LOAD_CONST               1 (0)
              4 STORE_FAST               1 (s)

  5           6 LOAD_FAST                0 (xs)
              8 GET_ITER
        >>   10 FOR_ITER                 7 (to 28)
             14 STORE_FAST               2 (x)

  6          16 LOAD_FAST                1 (s)
             18 LOAD_FAST                2 (x)
             20 BINARY_OP               13 (+=)
             24 STORE_FAST               1 (s)
             26 JUMP_BACKWARD            9 (to 10)

  5     >>   28 END_FOR

  7          30 LOAD_FAST                1 (s)
             32 RETURN_VALUE
jump targets at offsets: [10, 28]
```

The `>>` marks an instruction that some jump lands on. Check the arithmetic against the 3.12 documentation, which says a jump's argument is relative to the instruction after the jump's cache entries. `FOR_ITER 7 (to 28)` sits at offset 10 with one cache slot, so the next instruction is at 14, and 14 + 7 × 2 = 28. `JUMP_BACKWARD 9 (to 10)` sits at 26, the next instruction is at 28, and 28 − 9 × 2 = 10. From 3.13 the output prints labels instead of offsets (docs, 3.13 change note), so the picture is the same and the numbers are not.

## What the compiler already did

The compiler can replace some work with a constant. These five functions show what it did and did not do:

```python
import dis

def a(): return 60 * 60 * 24
def b(n): return 60 * 60 * 24 * n
def c(n): return n * 60 * 60 * 24
def d(x): return x in [1, 2, 3]
def e(x): return x in {1, 2, 3}

for f in (a, b, c, d, e):
    n = sum(1 for ins in dis.get_instructions(f) if ins.opname != "RESUME")
    print(f"{f.__name__}: {n} instructions, constants {f.__code__.co_consts[1:]}")
```

```output
a: 1 instructions, constants (86400,)
b: 4 instructions, constants (86400,)
c: 8 instructions, constants (60, 24)
d: 4 instructions, constants ((1, 2, 3),)
e: 4 instructions, constants (frozenset({1, 2, 3}),)
```

![Three cards: 60*60*24 is one instruction, 60*60*24*n is four, n*60*60*24 is eight; below, a list literal after in becomes a tuple constant and a set literal becomes a frozenset constant](diagrams/1.5-folding.svg "Instructions per call, without RESUME. Observed on 3.12.13.")

`60 * 60 * 24 * n` and `n * 60 * 60 * 24` are the same number but cost 4 and 8 instructions. My explanation, from first principles (label b): Python evaluates left to right, so in the second form `n * 60` is the first product and it is not a constant. I checked the result, not the stage that does it: the CPython compiler documentation lists optimisation passes but I did not trace which one folds constants.

The `in` rows are a practical gain. A list or set literal after `in` never gets built per call; the function holds one ready-made tuple or frozenset. That only holds when every element is a constant.

## Using dis to explain a measurement

Same source line `s += i`, three places to run it. First predict from the opcode descriptions in the documentation: `LOAD_FAST` reads `co_varnames[var_num]`, a numbered slot; `LOAD_NAME` looks a name up "within the locals, then the globals, then the builtins". Prediction: slot access is cheaper than name lookup, and a function that declares `global` should be slow too. Test it:

```python
import dis, timeit

N = 300_000
module_code = compile(f"s = 0\nfor i in range({N}):\n    s += i\n", "<module>", "exec")
ns = {}
exec(f"def run_local():\n    s = 0\n    for i in range({N}):\n        s += i\n", ns)
exec(f"def run_global():\n    global s, i\n    s = 0\n    for i in range({N}):\n        s += i\n", ns)

def kinds(code):
    return sorted({ins.opname for ins in dis.get_instructions(code) if ins.opname.startswith(("LOAD_", "STORE_"))})

print("module: ", kinds(module_code))
print("global: ", kinds(ns["run_global"]))
print("local:  ", kinds(ns["run_local"]))

t_module = min(timeit.repeat(lambda: exec(module_code, {}), number=1, repeat=7))
t_global = min(timeit.repeat(ns["run_global"], number=1, repeat=7))
t_local = min(timeit.repeat(ns["run_local"], number=1, repeat=7))
print("module slower than local:", t_module > t_local)
print("global slower than local:", t_global > t_local)
```

```output
module:  ['LOAD_CONST', 'LOAD_NAME', 'STORE_NAME']
global:  ['LOAD_CONST', 'LOAD_GLOBAL', 'STORE_GLOBAL']
local:   ['LOAD_CONST', 'LOAD_FAST', 'LOAD_GLOBAL', 'STORE_FAST']
module slower than local: True
global slower than local: True
```

The times depend on the machine, so the code prints only the comparisons. My own run, with a million iterations:

![Three columns listing the five loop-body instructions at module level, in a function with global declarations, and in a function with locals; below, bars of 48.3, 43.8 and 25.0 milliseconds](diagrams/1.5-name-vs-fast.svg "Best of 9 runs on one Apple M5 laptop, CPython 3.12.13. Instruction counts include RESUME.")

The prediction held, and the control mattered. Module level and the `global` function are close (48.3 and 43.8 ms) and both are slower than locals (25.0 ms), by factors of 1.93 and 1.75. So the cause is the kind of variable access, not "module versus function". The `global` function and the local one both have 16 instructions, yet the first is 1.75 times slower, which is why instruction count alone is not a speed measure.

What I did not show is why name access costs more inside the interpreter; the docs only describe what the instructions do. Treat the mechanism as a hypothesis the timing supports, not a result.

## Bytecode changes between versions

![The disassembly of swap on 3.12.13, 3.13.14 and 3.14.6, as chains of instructions, with changed ones in amber, and a table of two more opcodes that changed name](diagrams/1.5-versions.svg "Same source, run on three interpreters.")

```python
import dis, sys

def swap(a, b):
    return a * b

print(sys.version.split()[0], [ins.opname for ins in dis.get_instructions(swap)])
```

```output
3.12.13 ['RESUME', 'LOAD_FAST', 'LOAD_FAST', 'BINARY_OP', 'RETURN_VALUE']
```

I ran the same file on the other two interpreters; their lines, copied as printed:

```text
3.13.14 ['RESUME', 'LOAD_FAST_LOAD_FAST', 'BINARY_OP', 'RETURN_VALUE']
3.14.6 ['RESUME', 'LOAD_FAST_BORROW_LOAD_FAST_BORROW', 'BINARY_OP', 'RETURN_VALUE']
```

The documentation says bytecode "is an implementation detail of the CPython interpreter", with no guarantee that opcodes are added, removed or changed between versions, and that the module should not be expected to work across Python virtual machines. A tutorial's bytecode listing is therefore a dated photograph. Always print your own.

What `dis` shows by default is also the unspecialised form. The interpreter rewrites hot instructions at run time (Lesson 1.6 covers how). `adaptive=True` shows the rewritten form:

```python
import dis

def mul(a, b):
    return a * b + 1

for _ in range(2000):
    mul(3, 4)

print("default: ", [ins.opname for ins in dis.get_instructions(mul)])
print("adaptive:", [ins.opname for ins in dis.get_instructions(mul, adaptive=True)])
```

```output
default:  ['RESUME', 'LOAD_FAST', 'LOAD_FAST', 'BINARY_OP', 'LOAD_CONST', 'BINARY_OP', 'RETURN_VALUE']
adaptive: ['RESUME', 'LOAD_FAST__LOAD_FAST', 'LOAD_FAST', 'BINARY_OP_MULTIPLY_INT', 'LOAD_CONST', 'BINARY_OP_ADD_INT', 'RETURN_VALUE']
```

## Common traps

> [!TRAP]
> **Disassembling a string disassembles a module.** `dis.dis("x = 1")` compiles it first, so the name is stored with `STORE_NAME`, not `STORE_FAST`. To see how a function compiles, define it inside the string or pass the function. `dis.dis` recurses into nested code objects, so a `def` inside prints the module and then each function body.

> [!TRAP]
> **Copying bytecode from an old article.** Listings with `BINARY_ADD`, `CALL_METHOD` or a `PRINT` opcode do not match what 3.12 prints. The previous version of this lesson showed such output, including a `PRINT` instruction that does not exist (the documentation lists only an `INTRINSIC_PRINT` operand used in the interactive prompt).

> [!TRAP]
> **Counting instructions as if they were time.** The experiment above has two functions with the same instruction count (16) whose times differ by 1.75 times. Use `dis` to form a hypothesis and `timeit` or a profiler to test it.

> [!TRAP]
> **Treating `len(co_code) // 2` as the instruction count.** Hidden cache slots are in `co_code`. For `bill` that gives 18 for 10 instructions.

## Summary

- `dis` prints a code object's instructions: line, offset, opname, argument, and the argument's meaning. Arguments usually index `co_varnames`, `co_consts` or `co_names`; `LOAD_GLOBAL` packs an extra flag into the low bit.
- Loops compile to `FOR_ITER` and a backward jump; jump arguments count 2-byte slots, after any hidden caches.
- The compiler can fold constant expressions, but only when the whole sub-expression is constant: `60*60*24*n` and `n*60*60*24` differ.
- Opcode names, offsets and even instruction counts change between CPython versions. Report the version with every listing.
- `dis` explains what the interpreter is asked to do. It does not measure time; test any speed hypothesis with a timing run.

### Question 3: Find the bug

A student asserts that every function satisfies `len(f.__code__.co_code) == 2 * len(list(dis.get_instructions(f)))`. It fails for `bill`. Why, and what would make the check true?

<details><summary>Show solution</summary>

`co_code` includes the hidden `CACHE` slots: 36 bytes, 18 slots, for 10 instructions. On 3.12, counting with `show_caches=True` gives 18 slots, and then `len(co_code) == 2 * slots` holds. From 3.13 `get_instructions` no longer yields cache items, so that check needs another approach.

### Question 4: Explain

A teammate says the loop with fewer bytecode instructions is the faster one. Refute it using this lesson's measurements.

<details><summary>Show solution</summary>

The function with `global s, i` and the function with locals both have 16 instructions, yet took 43.8 ms against 25.0 ms. Instructions differ in cost: `LOAD_GLOBAL` and `STORE_GLOBAL` do name-based work, `LOAD_FAST` and `STORE_FAST` use numbered slots. Module level has 17 instructions and took 48.3 ms, so there the longer list and the slower time agree; the equal-count pair is the one that refutes the claim. These are one machine and one version, so the claim is about this experiment, not a law.
