CPython does not run the bytecode you see in `dis` exactly as printed: since Python 3.11 it rewrites hot instructions while the program runs. In this lesson you will watch one instruction specialize, lose its specialization and recover, measure what unstable types cost, and see where the experimental JIT (just-in-time compiler) of 3.13 fits.

**You need:** bytecode and `dis` (Lesson 1.5), and that CPython is the reference implementation (Lesson 1.3). Everything here is about CPython, not PyPy.

## The problem: `a + b` does not know its types

The compiler emits one instruction, `BINARY_OP`, for `a + b`. At run time that instruction must discover what `a` and `b` are, look up how those types add, call that code, and allocate the result object. For two ints that is a lot of work to reach an obvious answer.

Real programs are mostly type-stable: a given `+` in a given function nearly always sees the same types. The Specializing Adaptive Interpreter (PEP 659) bets on that: once an instruction has run, replace it with a version that assumes the types it just saw, and check the assumption cheaply each time.

## Watching one instruction change

![Four moments of one BINARY_OP instruction: generic, int-specialized after two int calls, still int-specialized after 52 float calls, float-specialized after 53](diagrams/1.6-moments.svg "The same instruction in the same function. Counts are from the code below.")

`dis.get_instructions(fn, adaptive=True)` shows the instructions as the interpreter now runs them. The plain call shows what the compiler emitted. Both parameters were added in 3.11 (`dis` docs).

```python
import dis

def add(a, b):
    return a + b

def binary_op(fn, adaptive=True):
    """Name of the BINARY_OP instruction (adaptive=True: as the interpreter now runs it)."""
    return next(i.opname for i in dis.get_instructions(fn, adaptive=adaptive)
                if i.opname.startswith("BINARY_OP"))

print("never called         :", binary_op(add))
add(1, 2)
print("after 1 int call     :", binary_op(add))
add(1, 2)
print("after 2 int calls    :", binary_op(add))
for _ in range(52):
    add(1.5, 2.5)
print("then 52 float calls  :", binary_op(add))
add(1.5, 2.5)
print("then 53 float calls  :", binary_op(add))
print("plain bytecode       :", binary_op(add, adaptive=False))
```

```output
never called         : BINARY_OP
after 1 int call     : BINARY_OP
after 2 int calls    : BINARY_OP_ADD_INT
then 52 float calls  : BINARY_OP_ADD_INT
then 53 float calls  : BINARY_OP_ADD_FLOAT
plain bytecode       : BINARY_OP
```

Read it as a small state machine (established, from the 3.12 source header `Include/internal/pycore_code.h`, and reproduced above on 3.12.13 and 3.13.14):

1. **Warm-up.** The instruction is specialized the *second* time it executes. One execution is too little evidence of "hot"; waiting longer only delays the benefit.
2. **Guard.** A specialized instruction checks its assumption on every execution (here: both operands are exactly `int`). If it holds, the fast path runs.
3. **Miss.** If it fails, the generic code runs, so the answer is still correct, and a counter ticks down.
4. **Re-specialize.** After 53 misses (counter starts at 52; 53 is prime to avoid patterns when every n-th value differs) the instruction reverts to the generic form and specializes again, now for what it sees.

> [!NOTE]
> The numbers 2 and 53 are CPython 3.12 and 3.13 behaviour. In 3.11 the same experiment needed 8 calls before the first specialization (measured; I did not read 3.11's source), and names such as `BINARY_OP_ADAPTIVE` existed. The *idea* is stable across versions; the constants and instruction names are not.

## Where the rewrite lives

![The six 2-byte units of add(a, b) as compiled and as running: BINARY_OP becomes BINARY_OP_ADD_INT, LOAD_FAST pair merges, and the unit after BINARY_OP is a cache holding a counter](diagrams/1.6-in-place.svg "The running copy is the same 12 bytes. Only some units changed.")

The specialized instruction replaces the original in the code object's own bytecode. After the instruction come **inline cache** entries: 16-bit slots that "immediately follow the instruction" and hold what the specialization learned (PEP 659). `BINARY_OP` has one such slot (`dis._inline_cache_entries`, 3.12), used here as the counter. The `dis` docs warn that populated caches "can look like arbitrary instructions", so treat raw adaptive bytes with care.

CPython also fuses some neighbours into superinstructions; the figure shows `LOAD_FAST__LOAD_FAST`. There it replaces the first of the two `LOAD_FAST` units.

## What specializes

Specialization covers the instructions that dominate ordinary code: arithmetic, comparisons, attribute loads, global loads, subscripts, calls, loops. This function exercises nine of them; the code lists every instruction whose name changed after 200 warm-up calls.

```python
import dis

class P:
    def __init__(self, x):
        self.x = x
    def get(self):
        return self.x

def survey(p, xs, i):
    t = 0
    for v in xs:
        t += v
    if i < 10:
        t += 1
    t += p.x
    t += len(xs)
    t += xs[0]
    t += p.get()
    return t

p, xs = P(3), [1, 2, 3]
for i in range(200):
    survey(p, xs, i % 20)

plain = list(dis.get_instructions(survey))
fast = list(dis.get_instructions(survey, adaptive=True))
seen = set()
for a, b in zip(plain, fast):
    if a.opname != b.opname and "__" not in b.opname and (a.opname, b.opname) not in seen:
        seen.add((a.opname, b.opname))
        print(f"{a.opname:12} -> {b.opname}")
```

```output
FOR_ITER     -> FOR_ITER_LIST
BINARY_OP    -> BINARY_OP_ADD_INT
COMPARE_OP   -> COMPARE_OP_INT
LOAD_ATTR    -> LOAD_ATTR_INSTANCE_VALUE
LOAD_GLOBAL  -> LOAD_GLOBAL_BUILTIN
CALL         -> CALL_NO_KW_LEN
BINARY_SUBSCR -> BINARY_SUBSCR_LIST_INT
LOAD_ATTR    -> LOAD_ATTR_METHOD_WITH_VALUES
CALL         -> CALL_PY_EXACT_ARGS
```

## What unstable types cost

A site that always sees the same type stays on its fast path. A site that sees several types keeps missing. The loop below does `o.x` over lists holding 1, 2 or 4 different classes; each class is a different type, so an assumption cached for one class does not hold for the others.

```python
import time

class A:
    def __init__(self): self.x = 1
class B:
    def __init__(self): self.y = 0; self.x = 1
class C:
    def __init__(self): self.z = 0; self.x = 1
class D:
    def __init__(self): self.w = 0; self.x = 1

N = 400_000
SRC = "def run(objs):\n    t = 0\n    for o in objs:\n        t += o.x\n    return t\n"

def ns_per_load(objs):
    ns = {}
    exec(SRC, ns)              # a fresh function per case: no site remembers an earlier case
    run = ns["run"]
    for _ in range(3):
        run(objs)              # warm up
    times = []
    for _ in range(9):
        t0 = time.perf_counter()
        run(objs)
        times.append(time.perf_counter() - t0)
    return min(times) / len(objs) * 1e9

cases = {"1 class":   [A()] * N,
         "2 classes": [A(), B()] * (N // 2),
         "4 classes": [A(), B(), C(), D()] * (N // 4)}
for name, objs in cases.items():
    print(f"{name:10} {ns_per_load(objs):5.1f} ns per iteration")
```

```text
1 class     18.4 ns per iteration
2 classes   22.2 ns per iteration
4 classes   24.0 ns per iteration
```

Timings depend on hardware and load; this is CPython 3.12.13 on one laptop, and a second run gave 18.5, 22.2 and 24.2. Compare the three lines with each other, not with your machine.

![Bars: 18.4 ns with one class, 22.2 ns (+21%) with two, 24.0 ns (+30%) with four](diagrams/1.6-classes.svg "Cost per loop iteration of the same o.x, versus how many classes it sees.")

The slowdown is measured; the mechanism is my reasoning (c), not something I traced in the C source: with several classes the guard fails most iterations, so most loads take the generic path. The whole iteration is only 30% slower because the loop, the add and the store are unchanged. The same direction appeared on 3.11, 3.13 and 3.14 (4-class over 1-class ratio between 1.27 and 1.46 in my runs; see `1.6_data.py`).

> [!KEY-INSIGHT]
> Specialization rewards code whose types are stable at each *site*, not code that is annotated or "typed". It makes ordinary Python code somewhat faster; it does not make a pure-Python loop compete with NumPy or PyTorch, where the loop runs in compiled code.

## Tier 2 and the experimental JIT

![Specialized bytecode (tier 1) is always on; when hot it can be translated to micro-ops (tier 2), optimized, then compiled to machine code or run by a tier 2 interpreter](diagrams/1.6-tiers.svg "Everything right of 'hot' exists only in builds configured with the experimental JIT option.")

What you have seen so far is **tier 1**. Python 3.13 added a second tier, described in "What's New in Python 3.13" as follows: when tier 1 bytecode "gets hot enough" it is translated to an internal representation of **micro-ops** (smaller steps than bytecode instructions), optimized, and, if the JIT is on, translated to machine code by **copy-and-patch** (pre-built machine-code templates with the operands filled in). The tier 2 interpreter exists "mostly" to debug the earlier stages.

Facts to know, each from the docs I read (3.13 and 3.14 "What's New", PEP 744):

- It is **experimental** and absent from a default build. A source build needs `--enable-experimental-jit` and a build-time dependency on LLVM (a compiler toolkit); the value `yes-off` builds it but leaves it off until you set `PYTHON_JIT=1`.
- PEP 744 says that, on most platforms, the JIT is "about as fast as the existing specializing interpreter", and "should not be used in production" until it is non-experimental.
- 3.14 ships it in the official macOS and Windows binaries, still not recommended for production, with a typical effect "from 10% slower to 20% faster, depending on workload". Free-threaded builds do not support it.

Whether it helps your code is therefore a measurement. This is mine: three small loops, median of 8 runs of 2 million iterations each, JIT off and on, using `python3.13` and `python3.14` builds configured with `yes-off`.

<details><summary>Run locally: needs a 3.13+ build with the JIT compiled in</summary>

```python
import sys, time, statistics
def loop(n):
    t = 0
    for i in range(n):
        t += i * 2 % 7
    return t
def floaty(n):
    x = 0.0
    for i in range(n):
        x = x * 0.999 + 1.5
    return x
def callee(a, b):
    return a + b if a > b else b - a
def calls(n):
    t = 0
    for i in range(n):
        t = callee(t, i) & 1023
    return t
N = 2_000_000
res = {}
for name, f in (("int_loop", loop), ("float_loop", floaty), ("call_loop", calls)):
    ts = []
    for k in range(9):
        t0 = time.perf_counter(); f(N); ts.append(time.perf_counter() - t0)
    res[name] = {"first_ms": round(ts[0]*1e3, 1), "median_ms": round(statistics.median(ts[1:])*1e3, 1)}
if hasattr(sys, "_jit"): res["jit_enabled"] = sys._jit.is_enabled()
import json; print(json.dumps(res))
```

Save it as `bench_jit.py` and run `PYTHON_JIT=0 python3.13 bench_jit.py`, then the same with `PYTHON_JIT=1`. Medians in ms from my run (3.13.14; the 3.14.6 runs are in the figure):

```text
PYTHON_JIT=0  int_loop 88.3   float_loop 47.9   call_loop 129.7
PYTHON_JIT=1  int_loop 94.8   float_loop 52.4   call_loop 129.3
```

On 3.14, `python3.14 -c "import sys; print(sys._jit.is_available(), sys._jit.is_enabled())"` printed `True False` without the variable and `True True` with `PYTHON_JIT=1`. Python 3.13 has no `sys._jit`, so I could not confirm from inside Python that the JIT was active there.

</details>

![Median milliseconds for three loops with the JIT off and on, on 3.13 and 3.14: on is slower in five of six cases](diagrams/1.6-jit.svg "Lower is faster. Positive percentages mean slower with the JIT on.")

On these loops the JIT never won: 3.13 was 7% and 9% slower on two loops and level on the third; 3.14 was 10% to 22% slower. The 3.14 int loop (22% slower) is outside the documented range. I did not investigate why; candidates are that these loops are tiny and dominated by allocating ints and floats, and that my interpreters are python-build-standalone builds rather than the official binaries. One machine, one run per configuration: treat it as a reminder to measure, not as a verdict on the JIT.

## Common traps

> [!TRAP]
> **"Type hints make the interpreter specialize."** The runtime ignores annotations (`typing` docs: it "does not enforce" them). In Question 3 a function annotated `int` is called with floats and specializes for floats.

> [!TRAP]
> **"`dis.dis(f)` shows what runs."** It shows the compiler's output. Add `adaptive=True` after the function has run a few times.

> [!TRAP]
> **Treating `BINARY_OP_ADD_INT` and friends as an interface.** Names and constants change between releases (`CALL_NO_KW_LEN` in 3.12, `CALL_LEN` in 3.13). Use them to understand, not in tools.

> [!TRAP]
> **Timing a function once.** The first calls run the generic code and do the specializing; time after warm-up, repeat, and report the minimum or median.

> [!TRAP]
> **Turning the JIT on for speed.** The documentation calls it experimental and not for production, and the measurement above shows no gain on simple loops.

## Summary

- Since 3.11, CPython specializes an instruction on its second execution, guards the assumption each time, and falls back to generic code on a miss; 3.12 and 3.13 re-specialize after 53 misses.
- The rewrite happens inside the code object, with inline cache slots after the instruction. `dis.dis(f, adaptive=True)` shows it; plain `dis` does not.
- Stable types per site are what matter: the same `o.x` cost 18.4 ns with one class and 24.0 ns with four in my 3.12 run.
- Tier 2 (micro-ops) and the copy-and-patch JIT arrived in 3.13 as an opt-in, experimental feature; in my small loops it did not speed anything up.
- Names, thresholds and timings are version- and hardware-specific. Measure, with warm-up.

## Quiz time

### Question 1: Calculation

Using the figure for `o.x`, how much longer does a loop of 10 million iterations take with 4 classes than with 1? Which part of that is the attribute load alone?

<details><summary>Show solution</summary>

$(24.0 - 18.4)\ \text{ns} \times 10^7 = 0.056$ s, about 30% more time. The loop also runs `FOR_ITER`, the add and the store at the same cost in both cases. The extra 5.6 ns comes from the one thing that differs, the load. The load's own time is not measured separately, so its relative slowdown is larger than 30%, because the 18.4 ns includes everything else.

</details>

### Question 3: Bug-spotting a claim

A colleague says: "I added `int` hints, so Python now uses the integer fast path." Test it.

```python
import dis

def g(a: int, b: int) -> int:
    return a + b

g(1.5, 2.5)
g(1.5, 2.5)
print(next(i.opname for i in dis.get_instructions(g, adaptive=True) if i.opname.startswith("BINARY_OP")))
```

<details><summary>Show solution</summary>

```output
BINARY_OP_ADD_FLOAT
```

The function is annotated `int` but called with floats, and the interpreter specialized for floats. Annotations are for type checkers; specialization follows the types seen at run time.

</details>

### Question 4: Explanation

A benchmark calls a fresh function once and reports the time. Why is the result misleading for long-running code, and what should be changed?

<details><summary>Show solution</summary>

A fresh function has not been specialized (each instruction needs a second execution before it specializes), so one call measures generic code plus the cost of specializing. Warm up with a few calls, then repeat the timed call several times and report the minimum or median. If the real workload sees varied types, the benchmark must use that variety too, or it will overstate the benefit.

</details>
