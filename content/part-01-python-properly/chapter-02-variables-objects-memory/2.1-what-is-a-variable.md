In Python a variable is not a box that holds a value. It is a name attached to an object, and that one change of picture explains most of the surprises in this chapter: why `b = a` followed by `b.append(3)` changes `a`, why `del` does not delete anything, and why a function can change its argument. By the end of this lesson you will be able to trace any short program by drawing names and objects, and to say where each name lives.

**You need:** to have run a few lines of Python (Lesson 1.2). Nothing else.

## The problem: the "box" picture predicts the wrong thing

If you learned C, Java or most other languages first, you probably think of a variable as a labelled box in memory. `int x = 5;` reserves a box named `x` and puts 5 in it. `int y = x;` reserves a second box and copies 5 into it. Boxes never share contents, so changing one never changes the other.

That picture is fine for numbers in C, and wrong for Python. In Python, `y = x` copies nothing. The next diagram runs the same two statements through both models, using a list because a list can be changed in place:

![Left: two boxes, each holding its own copy of the list; appending to b leaves a unchanged. Right: names a and b both point to one list; appending to b is visible through a](diagrams/2.1-box-vs-name.svg "Box model versus name model. The only difference is whether assignment copies the object or copies the arrow.")

The Python column is the one that matches the language definition. The language reference puts it in one sentence: "Names refer to objects. Names are introduced by name binding operations." (Python Language Reference, section 4.2.1, "Binding of names").

## A variable is a name bound to an object

Three facts are enough:

1. **An object exists on its own.** Every object has an identity, a type and a value, and its identity and type never change (Language Reference, section 3.1). Lesson 2.2 looks inside one.
2. **A name is a label that refers to an object.** The name has no type, no value and no memory of its own. It is an entry in a table that maps a string such as `"x"` to an object.
3. **Assignment binds a name; it never copies the object.** `y = x` evaluates the right-hand side, which gives an object, and makes `y` refer to that same object. Ned Batchelder's essay states the consequence as "Fact: Assignment never copies data" (see References).

The documentation does call these names "variables" ("If a name is bound in a block, it is a local variable of that block"), so the word is fine as long as you read it as *name binding*. Many operations bind names, not only `=`: `for` loops, `with ... as`, `except ... as`, `import`, `def`, `class`, function parameters and the walrus operator `:=` (Language Reference, section 4.2.1). Also `del name` removes a binding.

## Worked example, by hand

Trace this program one statement at a time. For each statement, ask two questions: which name moved, and was any object changed?

1. `x = 5`: build an `int` object 5 and bind `x` to it.
2. `y = x`: evaluate `x`, which gives that same object, and bind `y` to it. No new object.
3. `x = x + 1`: evaluate `x + 1`. Integers cannot change (Lesson 2.6), so this builds a *new* object 6 and rebinds `x` to it. `y` still refers to 5, because nothing ever told it to follow `x`.
4. `z = [x, y]`: build a list whose two slots refer to the objects 6 and 5.
5. `w = z`: a second name for the same list.
6. `w.append(7)`: a method call on the list object. It changes the list, so `z` and `w` both see it. No name moved.

![Six snapshots of the worked example showing, after each statement, which names point to which objects; the last snapshot shows z and w pointing to one list holding 6, 5 and 7](diagrams/2.1-trace.svg "Green marks what each statement adds or moves. Step 3 moves a name; step 6 changes an object.")

Steps 3 and 6 are the two ways a program can "change a variable". One **rebinds** a name (the arrow moves). The other **mutates** an object (the object changes, and every name that reaches it sees the change). Every bug in this chapter comes from confusing the two. The code reproduces the trace; `is` asks whether two names refer to the same object (Lesson 2.4 explains it fully):

```python
x = 5
y = x          # a second name for the same object; nothing is copied
x = x + 1      # builds a NEW int 6 and rebinds x; y still names 5
z = [x, y]     # a list holding references to those two int objects
w = z          # another name for the same list
w.append(7)    # mutate the list through w

print("x =", x, " y =", y)
print("z =", z, " w =", w)
print("z and w name the same list:", z is w)
print("y and z[1] name the same int:", y is z[1])
```

## Where do names live?

A name has to be stored somewhere. In CPython (the standard implementation, Lesson 1.3) it depends on the kind of code block:

- **Module level** (the top of a script or imported file): a real Python `dict`, which `globals()` returns. Binding `x` means storing the key `"x"` in it.
- **Inside a function**: numbered slots in the function's call frame, one per local name. The compiler decides at compile time which names are local, so a call needs no dictionary.
- **A class body**: the namespace of the class definition becomes the attribute dictionary of the class (Language Reference, section 4.2.2).

The module-level case is easy to check, because the dictionary is right there:

```python
a = 10
b = a
print(type(globals()))
print("'a' in globals():", "a" in globals())
print("same object under both names:", globals()["a"] is globals()["b"])

globals()["c"] = [1, 2]        # create a variable by writing into the dict
print("c =", c)

del a                          # removes the entry "a"; the object 10 is untouched
print("'a' in globals():", "a" in globals(), "| b =", b)
try:
    print(a)
except NameError as e:
    print("NameError:", e)
```

```output
@@
```

Function locals do not appear in any dictionary. The compiled function records them by position, and names it uses but does not bind (such as `max` or a module-level constant) are looked up by name at run time:

```python
LIMIT = 100

def f(p, q):
    r = p + q
    return max(r, LIMIT)

print("function locals live in numbered slots:", f.__code__.co_varnames)
print("names it looks up in globals/builtins :", f.__code__.co_names)

module_code = compile("n = 1\nprint(n)", "<demo>", "exec")
print("module-level names (dict keys)        :", module_code.co_names)
```

```output
@@
```

![Left: a module namespace drawn as a dictionary table with keys a, b and c pointing to the int 10 and a list. Right: the three slots p, q, r of one call of f pointing to the ints 1, 2 and 3](diagrams/2.1-namespaces.svg "Same idea, two storage layouts: a dict at module level, numbered slots inside a call. > [!NOTE]
> Dictionary-versus-slots is a CPython detail; the language only promises the name-resolution rules. The reference says so about the related point of immediate cleanup: "Other implementations act differently and CPython may change." (section 3.1). Treat `co_varnames` as a way to look, not a contract.

## `del` removes a name, not an object

`del a` is a binding operation: it unbinds the name. The object disappears only if nothing else can reach it any more. A *weak reference* (`weakref.ref`) lets you watch an object without keeping it alive, so it works as a probe:

```python
import weakref

class Box:
    pass

a = Box()
b = a                        # two names, one object
r = weakref.ref(a)           # a weak reference does not keep the object alive

del a
print("after del a, object still alive:", r() is not None)
del b
print("after del b, object still alive:", r() is not None)
```

```output
@@
```

The first `del` leaves the object alive because `b` still reaches it. The second prints `False` on CPython because CPython frees an object the moment its reference count reaches zero (Lesson 2.7). On PyPy 7.3.23 (Python 3.11) the same program prints `True` twice, since PyPy frees objects later, in batches; the language reference says explicitly that code should not depend on immediate cleanup (section 3.1).

## Names have no type; objects do

Rebinding a name to an object of another type is legal, because the name never promised anything:

```python
x = 1
print(type(x).__name__)
x = "one"
print(type(x).__name__)
x = [1]
print(type(x).__name__)

n: int = "hello"             # the annotation is a note, not a check
print(n, type(n).__name__)
```

```output
@@
```

Annotations such as `n: int` document intent for tools like type checkers. Python itself does not enforce them: "The Python runtime does not enforce function and variable type annotations" (`typing` documentation).

## Common traps

> [!TRAP]
> **`a = b = []` makes one list, not two.** An assignment evaluates the right-hand side once and binds every target to that single object. Write `a, b = [], []` (or two lines) when you want two lists.

> [!TRAP]
> **A name assigned anywhere in a function is local in all of it.** `count = count + 1` inside a function makes `count` local for the whole body, so reading it first fails instead of falling back to the global.

> [!TRAP]
> **Loop variables outlive the loop.** After `for i in range(3): pass`, the name `i` is still bound, to the last value. A `for` loop is a binding operation, not a scope.

```python
for i in range(3):
    pass
print("loop variable survives the loop: i =", i)

a = b = []                   # ONE list, two names
a.append(1)
print("a = b = []   ->", b)

a, b = [], []                # two lists
a.append(1)
print("a, b = [], [] ->", b)

count = 0
def bump():
    count = count + 1        # assignment makes count local to bump for its whole body
try:
    bump()
except UnboundLocalError as e:
    print("UnboundLocalError:", e)
```

```output
@@
```

(The exact wording of the `UnboundLocalError` message is from Python 3.12; older versions say "local variable 'count' referenced before assignment".)

## Summary

- A Python variable is a **name bound to an object**: an entry in a namespace (a dict at module level, numbered slots in a function) that refers to the object.
- **Assignment never copies the object.** `y = x` makes a second name for the same object.
- A program can **rebind** a name (the arrow moves) or **mutate** an object (every name that reaches it sees the change). Tracing a program means keeping track of both.
- `del name` unbinds the name only. Names have no type; annotations are not enforced by the interpreter.

## Quiz time

### Question 1: Predict the output

What does this print? Draw the names and objects before you answer.

```python
a = [1, 2]
b = a
a = a + [3]
b.append(4)
print(a, b)
```

<details><summary>Show Solution</summary>

`a + [3]` builds a *new* list `[1, 2, 3]`, and `a = ...` rebinds `a` to it. `b` still refers to the original list `[1, 2]`. Then `b.append(4)` mutates that original list. So the program prints `[1, 2, 3] [1, 2, 4]`. (The next lesson on aliasing, 2.5, shows when `a += [3]` would behave differently.)

</details>

### Question 2: What survives?

After `x = 1000`, `y = x`, `del x`, is the integer object 1000 still available? What does `print(x)` do?

<details><summary>Show Solution</summary>

Yes: `y` still refers to it, so it stays alive, and `print(y)` prints 1000. `print(x)` raises `NameError: name 'x' is not defined`, because `del x` removed the binding of the name `x`.

</details>

### Question 3: Why does this raise?

```python
total = 0
def add(n):
    total += n
add(5)
```

<details><summary>Show Solution</summary>

`total += n` is an assignment to `total`, so the compiler treats `total` as a local variable of `add` for the whole function body. The statement first has to read the local `total`, which has no value yet, so Python raises `UnboundLocalError`. If you really want the module-level name, declare `global total` inside the function (or, better, return the new value).

</details>

### Question 4: Does the annotation protect you?

`n: int = "hello"` runs without an error. Explain why in one sentence, and say what kind of tool would flag it.

<details><summary>Show Solution</summary>

The annotation is stored as information but never checked at run time, and the name `n` has no type of its own; the object `"hello"` has type `str`. A static type checker such as mypy or pyright, run separately from your program, would report the mismatch.

</details>

## Exercise: swap two names by their strings

Because module-level names are dictionary keys, you can write a function that swaps what two *global* names refer to, given the names as strings. Write `swap(name1, name2)` using `globals()`, and test it.

<details><summary>Show Solution</summary>

`globals()` is the live dictionary of the module in which the function was defined, so assigning into it rebinds the names. The tuple assignment evaluates the right side completely (two objects) before storing, so it needs no temporary:

```python
def swap(name1, name2):
    g = globals()
    g[name1], g[name2] = g[name2], g[name1]

first = [1]
second = "two"
swap("first", "second")
print(first, second)
```

```output
@@
```

Only the two arrows moved; no object was copied or changed.

</details>
