By the end you will be able to tell a real leak (memory that stays reachable and grows with the work) from a reference cycle that the collector can free. You will check which one you have with `gc.collect()` and `tracemalloc`, then apply the fix that matches.

**You need:** Python 3.12, and the ideas of reference counting (2.7), the cyclic garbage collector (2.8) and reference cycles (2.9). All numbers were measured on CPython 3.12.13 (macOS). Byte counts change between builds and platforms; the trends hold.

## The problem

CPython frees most objects as soon as their reference count reaches zero (2.7). Memory can still grow in two ways. A reference you no longer need can keep an object reachable, so the collector has to keep it. Or objects can form a cycle, which reference counting alone never frees (2.9); only the cyclic collector can (2.8). From outside, both look the same: the process gets bigger. The fixes differ, so first find out which one you have.

Two terms. A *root* is a name the interpreter always treats as live, such as a module-level variable. An object is *reachable* if a chain of references leads from a root to it. An unreachable object is garbage.

## Two situations that look alike

![Left: a global dict keeps 1 KiB entries reachable, so gc.collect() cannot free them. Right: two nodes reference each other after their names are deleted, so gc.collect() frees both.](diagrams/2.10-three-leaks.svg "Reachable growth versus an unreachable cycle")

The left case is a true leak. A global cache stores one result per request and never removes entries. Each entry is reachable through the global name, so `gc.collect()` keeps all of them. The right case is a cycle. Nothing outside the pair refers to either node, so `gc.collect()` frees both.

The test: call `gc.collect()` and see whether memory drops. Reachable growth stays. Cycles disappear.

## Cycles: reference counting cannot free them

Two `Node` objects that point at each other keep each other's reference count at 1 after their names are deleted. The first experiment holds 20,000 such pairs with the automatic collector disabled, so the numbers show what is held before any collection runs.

![Bar chart of bytes held: 104 B for acyclic pairs freed by reference counting, 3,831,776 B for 20,000 cyclic pairs before gc.collect(), and 284 B after it.](diagrams/2.10-cycle-bytes.svg "Held memory for 20,000 cyclic pairs, to scale")

Check by hand: 3,831,776 bytes over 20,000 pairs is 191.6 bytes per pair. After `gc.collect()` the cyclic pairs hold 284 bytes, about 0.01 byte per pair. The collector returned 40,000, which is the number of `Node` objects it freed. Acyclic pairs, freed by reference counting, leave 104 bytes. I did not identify those bytes, so treat 104 B as the measurement floor.

This block shows the same behaviour on one pair, using only the standard library.

```python
import gc
import weakref

class Node:
    def __init__(self, value):
        self.value = value
        self.next = None

gc.disable()                      # so the demo controls when collection happens
a = Node(1)
b = Node(2)
a.next = b
b.next = a
alive = weakref.ref(a)            # a weak reference does not keep a alive
del a, b                          # the names are gone; each node is still referenced by the other
print("alive after del:", alive() is not None)
freed = gc.collect()
print("objects freed by gc.collect():", freed)
print("alive after collect:", alive() is not None)
gc.enable()
```

```output
alive after del: True
objects freed by gc.collect(): 2
alive after collect: False
```

The `gc` documentation defines the return value of `gc.collect()` as the sum of collected and uncollectable objects. The exact count can differ between Python versions, so read the output as "two objects were freed", not as a fixed constant.

## When the collector runs

The collector does not run on every allocation. The `gc` documentation says a collection starts when the number of allocations minus deallocations exceeds `threshold0`. `gc.get_threshold()` returns the thresholds. On this build they are `(700, 10, 10)`, which I read at runtime; the documentation page does not list the defaults. So a cycle is freed when the counter trips, not when `del` runs. That is why a leak can look as if it resolves itself, and why an explicit `gc.collect()` is the right test.

![Four boxes in a row: ten cyclic pairs are made, gc.get_count() reads (21, 0, 0), gc.collect() returns 20, and gc.get_count() reads (0, 0, 0) afterwards.](diagrams/2.10-gc-counts.svg "The generation-0 counter around one explicit collection")

The counter reads 21 after ten pairs, not 20. I did not identify the extra allocation, and the exact value can change with what else the interpreter is doing.

```python
import gc

class Node:
    def __init__(self, value):
        self.value = value
        self.next = None

def make_pairs(n):
    for i in range(n):
        a, b = Node(i), Node(i)
        a.next, b.next = b, a

gc.collect()
gc.disable()                         # the automatic collector stays off for this demo
make_pairs(10)                       # 20 Node objects in 10 reference cycles
after_make = gc.get_count()
freed = gc.collect()
after_collect = gc.get_count()
gc.enable()
print("count after 10 pairs:", after_make)
print("collect returns:", freed)
print("count after collect:", after_collect)
```

```output
count after 10 pairs: (21, 0, 0)
collect returns: 20
count after collect: (0, 0, 0)
```

## Break the cycle with a weak reference

The common cycle is parent and child: the parent holds the child, and the child holds the parent. If the child refers back through `weakref.ref`, it does not own the parent, so no cycle forms. A weak reference does not keep its target alive. The target is freed once its strong references are gone.

![Two panels for 20,000 parent and child pairs. Strong back-pointer: 2,880,000 B held before gc.collect(), about 0 B after. Weak back-pointer: 104 B, freed by reference counting with no collection needed.](diagrams/2.10-weakref-backptr.svg "Strong versus weak parent back-pointers")

Check by hand: 2,880,000 bytes over 20,000 families is 144 bytes per family. After `gc.collect()` the strong version leaves nothing behind; the measured −44 bytes is noise from the baseline. With a weak back-pointer the same workload holds 104 bytes, the same floor as before.

The same tool makes caches that do not leak. A `WeakValueDictionary` removes an entry when its value has no strong references left. The block shows both cases.

```python
import weakref

class Session:
    def __init__(self, k):
        self.k = k

cache = weakref.WeakValueDictionary()
for k in range(1000):
    cache[k] = Session(k)            # nothing else holds these sessions
print("unowned:", len(cache))
owners = [Session(k) for k in range(1000)]
cache2 = weakref.WeakValueDictionary({k: s for k, s in enumerate(owners)})
print("owned:", len(cache2))
del owners
print("after owners gone:", len(cache2))
```

```output
unowned: 0
owned: 1000
after owners gone: 0
```

Entries stay only while other code holds the value. That suits a cache of objects built elsewhere. It is the wrong tool when the cache itself must keep its values alive.

## Reachable growth: bound the cache

The collector cannot solve reachable growth, so you bound the structure: evict entries, or hold them weakly.

![Line chart of memory held after gc.collect() against requests handled, from 1,000 to 8,000. The unbounded dict rises from 1.14 MB to 9.19 MB. The lru_cache with maxsize 256 stays flat near 0.32 MB.](diagrams/2.10-unbounded-vs-bounded.svg "Unbounded dict versus lru_cache(maxsize=256)")

Check by hand: each request with a new key stores a 1,024-byte payload, so 8,000 entries hold 8,192,000 bytes of payload. The measured 9,191,256 bytes is 1,148.9 bytes per entry. `sys.getsizeof` reports 1,081 bytes for one `bytearray(1024)`, which is the 1,024-byte buffer plus a 57-byte object header. The remaining 67.9 bytes per entry is dict storage; that split is my reading, not something I measured separately. The bounded version holds 317,992 bytes at its last checkpoint, about 0.32 MB, because it keeps only 256 results.

`functools.lru_cache` is a least-recently-used (LRU) cache: when it is full, it discards the entry used longest ago. The functools documentation says the cache "keeps references to the arguments and return values until they age out of the cache or until the cache is cleared". Setting `maxsize=None` turns off the bound, and then the cache "can grow without bound".

## Finding the leak with tracemalloc

`tracemalloc` records where each memory block was allocated. `tracemalloc.start(nframe)` turns it on and keeps up to `nframe` frames of traceback per block. `take_snapshot().compare_to(old, "lineno")` ranks allocation lines by growth. The procedure: start tracing early, take a snapshot, run the suspect workload, call `gc.collect()`, take a second snapshot, and compare. A line that still grows after the collection is a reachable leak. A line that shrinks back was cyclic garbage or temporary churn.

The block below uses only the standard library. Byte counts vary by build, so it sits in a collapsed section.

<details><summary>Run locally (standard library only; byte counts vary by build)</summary>

```python
import gc, tracemalloc

CACHE = {}

def handle_leaky(key):
    CACHE[key] = bytearray(1024)     # a result stored forever

tracemalloc.start(5)
gc.collect()
start = tracemalloc.get_traced_memory()[0]
before = tracemalloc.take_snapshot()
for i in range(1000):
    handle_leaky(i)
gc.collect()                         # runs, and frees nothing: the cache still references every entry
held = tracemalloc.get_traced_memory()[0] - start
top = tracemalloc.take_snapshot().compare_to(before, "lineno")[0]
print("held after gc.collect() is over 0.9 MB:", held > 900_000)
print("top allocation line:", top.traceback[0].lineno)
print("new blocks at that line over 1000 calls:", top.count_diff)
tracemalloc.stop()
```

```output
held after gc.collect() is over 0.9 MB: True
top allocation line: 6
new blocks at that line over 1000 calls: 2001
```

</details>

The top line is 6, the store into `CACHE`, which is the leak. The count of 2001 is more than one block per call. My reading is two blocks per `bytearray` (its object and its buffer), plus one from dict resizing. I did not check that in the CPython source.

## Common traps

> [!TRAP]
> Calling `gc.collect()` in a loop does not fix a reachable leak. It frees cycles only, and each call costs time without freeing any reachable object.

> [!TRAP]
> Not every object accepts a weak reference. Measured on 3.12.13, `int`, `str`, `tuple`, `list` and `dict` raise `TypeError`, while subclasses such as `class MyDict(dict): pass` accept one. The weakref documentation calls the `int` and `tuple` restriction a CPython implementation detail.

> [!TRAP]
> A finalizer whose callback is a bound method keeps its object alive. `weakref.finalize(self, self.cleanup)` makes the finalizer registry hold `self`, so the object is never collected during the run. In my test the callback printed only at interpreter exit, after "end of script". Pass a module-level function plus only the data it needs, such as `weakref.finalize(self, release, self.buffer)`.

> [!TRAP]
> `tracemalloc` sees Python-level allocations. It does not see operating-system handles such as open files or sockets. That is my reasoning from how it is documented; close those resources with `with` blocks.

> [!TRAP]
> `lru_cache(maxsize=None)` looks like a convenience but is an unbounded cache. Give any function with a large argument space a finite `maxsize`.

## Summary

- A leak is either memory that stays reachable from a root, or a cycle that reference counting cannot free.
- `gc.collect()` separates them: reachable memory stays, and unreachable cycles are freed.
- Cycles linger until the generation-0 counter trips, so a test needs an explicit collection.
- Use weak references for back-pointers and for caches of objects owned elsewhere.
- Bound caches with an eviction limit, and find growth with `tracemalloc` snapshots.

## Quiz time

### Question 1: Calculation

A cache keeps one 1 KiB result for each of 8,000 unique keys. After `gc.collect()` it holds 9,191,256 bytes. How many bytes per entry is that, and how much of it is payload?

<details><summary>Show Solution</summary>

9,191,256 divided by 8,000 is 1,148.9 bytes per entry. The payload is 1,024 bytes. The rest, about 124.9 bytes, is 57 bytes of object header (from `sys.getsizeof`, 1,081 minus 1,024) and about 67.9 bytes of dict storage. The dict part is my reading.

</details>

### Question 2: Prediction

The block with `gc.disable()` prints `alive after del: True`. If you delete the `gc.disable()` and `gc.enable()` lines and run the same code, is that first line guaranteed to print True?

<details><summary>Show Solution</summary>

No. The automatic collector can run during an allocation and free the cycle before the `print`. The `gc.disable()` line makes the demo deterministic.

</details>

### Question 3: Bug-spotting

```python
import weakref

class Connection:
    def __init__(self):
        self.buffer = bytearray(1 << 20)
        weakref.finalize(self, self.cleanup)

    def cleanup(self):
        print("released")
```

When this script ends, `released` prints, but only after the last line of the script, not when the object is dropped. Why, and how do you make it print when the object is freed?

<details><summary>Show Solution</summary>

`self.cleanup` is a bound method, so the finalizer registry holds a reference to `self`. The object is therefore never unreachable during the run, and it is finalized only at interpreter exit. Pass a module-level function and only the data it needs, for example `weakref.finalize(self, release, self.buffer)` with `def release(buffer): ...`. Then the finalizer can run as soon as the object is freed.

</details>

### Question 4: Explanation

Why does `gc.collect()` leave the 8,000-entry cache in the lesson at 9.19 MB?

<details><summary>Show Solution</summary>

Every entry is reachable through the global `CACHE` dict, which is a root. The collector frees only unreachable objects, so it must keep every entry. The fix is to evict entries or hold them weakly, not to collect more often.

</details>
