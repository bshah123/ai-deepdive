In this lesson you will learn what every Python object carries in memory: a reference count and a pointer to its type. From that model you will predict the numbers that `sys.getsizeof()` and `sys.getrefcount()` return, and check the predictions against a real run.

**You need:** Lesson 2.1 (a name is a label bound to an object).

## The problem

Lesson 2.1 showed that `x = 1000` binds the name `x` to an object. That leaves three questions. What type is the object, so that `x + 1` knows to do integer arithmetic? How many names refer to it, so Python knows when it may free it? And where are those answers stored: on the name, or on the object? Python stores them on the object. That is why one value can be shared by many names, and why `type(x)` asks the object, not the name.

## Intuition: every object starts with the same header

![A 16-byte header made of ob_refcnt and ob_type, followed by the value bytes; ob_type points to the int type object](diagrams/2.2-header.svg "Every CPython object begins with the same two fields.")

CPython is the reference implementation of Python, written in C. Its C API documentation says that in a release build an object's header contains "only the object's reference count and a pointer to the corresponding type object" ([Python C API, Structures](https://docs.python.org/3.12/c-api/structures.html)). In the header file `Include/object.h` the first field is `ob_refcnt`, a signed integer (`Py_ssize_t`), and the second is `ob_type`, a pointer to a type object (`PyTypeObject *`) ([CPython 3.12, Include/object.h](https://github.com/python/cpython/blob/3.12/Include/object.h)). On a 64-bit build each field is 8 bytes, so the header is 16 bytes. You can check this without any C code: `sys.getsizeof(object())` returns 16, and an `object()` has no fields of its own.

The header is the same for every object. What differs is the value: an int, a list and a function store different bytes after the header.

Type objects are objects too. The Python data model says every object has "an identity, a type and a value", and that the type "determines the operations that the object supports" and the values it can take ([Python Language Reference, Data model](https://docs.python.org/3/reference/datamodel.html)). Follow the type of a type and the chain ends in a loop:

![The chain 1 to int to type, with type pointing to itself; len points to builtin_function_or_method, which points to type](diagrams/2.2-type-chain.svg "Following type() from a value leads to type, which is its own type.")

Functions, classes, modules and `None` are objects in the same way. `type(len)` is `builtin_function_or_method`, and `type(None)` is `NoneType`.

## Worked example, by hand

Trace `x = int("1000")` inside a function. The call creates a new int object, and `x` is its only name. Its header holds:

- `ob_refcnt` = 1, because one name holds the object
- `ob_type` = the `int` type object
- the value 1000 in the remaining bytes

`sys.getsizeof` reports 28 bytes. The header takes 16, so the value takes 12. The layout of those 12 bytes belongs to the int type, and we do not break it down here.

Now run `y = x`. No new int is created. `y` is a second name for the same object, so the stored count goes from 1 to 2. `del y` removes that name, and the count goes back to 1.

![Two names, x and y, point at one object with ob_refcnt = 2 and value 1000; the object's ob_type points to the int type object](diagrams/2.2-names.svg "After y = x, both names share one object, and the stored count is 2.")

The count you can print is one higher than the stored count. `sys.getrefcount(x)` receives `x` as an argument, and that argument is a temporary reference. So the stored count of 2 prints as 3. The next sections check this.

## Measuring it

Here is a run of object sizes and types. `sys.getsizeof` is shallow: it counts the object's own bytes, not the objects it refers to ([Python `sys` module](https://docs.python.org/3/library/sys.html)).

```python
import sys

class Plain:
    def __init__(self, value):
        self.value = value

# Shallow sizes: each object's own bytes, not the objects it refers to
samples = {
    "None": None, "float 1.0": 1.0, "int 1000": 1000, "int 2**60": 2**60,
    "str 'hello'": "hello", "list [1, 2, 3]": [1, 2, 3],
    "tuple (1, 2, 3)": (1, 2, 3), "dict {'a': 1}": {"a": 1},
    "set()": set(), "Plain(42)": Plain(42),
}
for label, obj in samples.items():
    print(f"{label:18} {type(obj).__name__:10} {sys.getsizeof(obj):4} bytes")

print("type(1) is int:", type(1) is int)
print("type(int) is type:", type(int) is type)
print("type(type) is type:", type(type) is type)
print("type(len):", type(len).__name__, "| type(None):", type(None).__name__)
```

```output
None               NoneType     16 bytes
float 1.0          float        24 bytes
int 1000           int          28 bytes
int 2**60          int          36 bytes
str 'hello'        str          46 bytes
list [1, 2, 3]     list         88 bytes
tuple (1, 2, 3)    tuple        64 bytes
dict {'a': 1}      dict        184 bytes
set()              set         216 bytes
Plain(42)          Plain        48 bytes
type(1) is int: True
type(int) is type: True
type(type) is type: True
type(len): builtin_function_or_method | type(None): NoneType
```

![Horizontal bars of sys.getsizeof values: None 16 bytes, float 24, int 1000 28, int 2**60 36, str 'hello' 46, Plain(42) 48, tuple 64, list 88, dict 184, empty set 216](diagrams/2.2-sizes.svg "Measured sizes. The list's three ints are not included in its 88 bytes.")

Two things stand out. The size depends on the value, not only on the type: `int 2**60` is 8 bytes larger than `int 1000`, which fits the idea that a larger value needs more storage (our reasoning; we did not measure the layout). The list is 88 bytes, but the three ints inside it are not counted. Those sizes come from 64-bit CPython 3.12 on arm64 macOS. Another build or version can give other numbers, so treat them as a measurement, not a constant.

## Measuring the count

The next block follows one object's count through a short life. It uses `int("1000")` so that the object is created at run time, not shared with the compiler's constants.

```python
import sys

def demo():
    x = int("1000")                      # a fresh object, made at run time
    print("fresh x:", sys.getrefcount(x))
    y = x
    print("after y = x:", sys.getrefcount(x))
    del y
    print("after del y:", sys.getrefcount(x))
    items = [x]
    print("inside [x]:", sys.getrefcount(x))
    items.clear()
    print("after clear:", sys.getrefcount(x))

demo()
print("small int 5:", sys.getrefcount(5))
print("None:", sys.getrefcount(None))
```

```output
fresh x: 2
after y = x: 3
after del y: 2
inside [x]: 3
after clear: 2
small int 5: 4294967295
None: 4294967295
```

![The reported sys.getrefcount values across five steps: 2, 3, 2, 3, 2, with the names that hold the object under each step](diagrams/2.2-refcount.svg "The printed count follows the names, plus one for the call's argument.")

Each printed value is the stored count plus one. The last two lines show immortal objects. Since Python 3.12, runtime-global objects such as `None`, `True`, `False` and small ints are immortal ([PEP 683, Immortal Objects](https://peps.python.org/pep-0683/)). Their count is set to a fixed large value, and the interpreter never frees them. The Python `sys` documentation says that immortal objects "have a very high refcount that does not reflect the actual number of references" ([Python `sys` module](https://docs.python.org/3/library/sys.html)). The exact value is an implementation detail; on this build it is 4294967295, which is 2^32 - 1.

### Under the hood: reading the header

The next block reads the two header fields from memory. This uses `ctypes`, the standard-library module that reads C-level memory. It is CPython-specific, and a wrong address can crash the interpreter, so run it only as an experiment.

<details><summary>Run locally (CPython only; reads raw memory with ctypes, no pip install)</summary>

```python
import sys, ctypes

def demo():
    x = int("1000")
    addr = id(x)                                             # the object's address
    refcnt = ctypes.c_ssize_t.from_address(addr).value       # ob_refcnt: first 8 bytes
    type_ptr = ctypes.c_void_p.from_address(addr + 8).value  # ob_type: next 8 bytes
    print("stored ob_refcnt:", refcnt)
    print("sys.getrefcount(x):", sys.getrefcount(x))
    print("ob_type is the int type:", type_ptr == id(int))
    print("sizeof(object()):", sys.getsizeof(object()))

demo()
```

```output
stored ob_refcnt: 1
sys.getrefcount(x): 2
ob_type is the int type: True
sizeof(object()): 16
```

</details>

The stored count is 1, and `sys.getrefcount` reports 2. The difference is the argument, as the worked example predicted. The type pointer equals the address of the `int` type object, which is `id(int)` in CPython. The `id()` function returns the address only in CPython; the language reference says the identity is "you may think of it as the object's address in memory" ([Python Language Reference, Data model](https://docs.python.org/3/reference/datamodel.html)).

### Under the hood: what the header costs

The 16-byte header is a fixed cost per object. A debug build of CPython adds two more pointers to the header when the `Py_TRACE_REFS` macro is defined ([CPython 3.12, Include/object.h](https://github.com/python/cpython/blob/3.12/Include/object.h)). We did not test a debug build, so the 16-byte figure holds for the build used here.

## Common traps

> [!TRAP]
> The printed refcount is not the number of names. `sys.getrefcount` adds its own argument, and the interpreter can hold other references (for example, constants stored with code). Compare how the number changes, not its absolute value. Expect 2 for a fresh object with one name, not 1.

> [!TRAP]
> Immortal objects report huge counts. `sys.getrefcount(None)` returning 4294967295 does not mean `None` leaks memory. Its count is a fixed marker, and the object is never freed.

> [!TRAP]
> `sys.getsizeof` is shallow and build-specific. `sys.getsizeof([1, 2, 3])` does not include the three ints. Deep sizes need a recursive traversal, which the `sys` documentation discusses but does not provide. The numbers also change with the build and version.

> [!TRAP]
> An `id()` value is only meaningful while its object lives. An object's identity never changes once it is created ([Python Language Reference, Data model](https://docs.python.org/3/reference/datamodel.html)). After the object is freed, a new object can get the same address. Do not store an `id()` and use it later to find an object.

## Summary

- Every CPython object starts with a header: a reference count (`ob_refcnt`) and a pointer to its type (`ob_type`). On this 64-bit build the header is 16 bytes.
- Types are objects too. `type(1)` is `int`, `type(int)` is `type`, and `type(type)` is `type`, so the chain ends in a loop.
- `sys.getsizeof` counts an object's own bytes only. `sys.getrefcount` reports the stored count plus one for its argument.
- Immortal objects such as `None` report a large fixed count. Read changes in counts, not their absolute values.

## Quiz time

### Question 1: Prediction

A fresh int `x` has a stored count of 1. The code runs `y = x` and then `items = [x]`. What does `sys.getrefcount(x)` print?

<details><summary>Show Solution</summary>

It prints 4. Three references are stored: the name `x`, the name `y`, and the list slot in `items`. `sys.getrefcount` adds one for its argument. The stored count is 3, and the printed count is 4.

</details>

### Question 2: Explanation

Why does `sys.getsizeof([1, 2, 3])` give 88 bytes when the three ints inside take up memory of their own?

<details><summary>Show Solution</summary>

`sys.getsizeof` is shallow. It counts only the memory attributed to the list object itself, not the objects it refers to ([Python `sys` module](https://docs.python.org/3/library/sys.html)). The ints are counted by their own `sys.getsizeof` calls. Adding them up requires a recursive traversal of the structure.

</details>

### Question 3: Bug-spotting

A student writes `if sys.getrefcount(obj) == 2: obj is unused, so delete it.` Why is this test wrong?

<details><summary>Show Solution</summary>

The printed count includes the argument, so a value of 2 means the stored count is 1: one reference. That can be true for an object still in use. The `sys` documentation says not to rely on the returned value "to be accurate, other than a value of 0 or 1" ([Python `sys` module](https://docs.python.org/3/library/sys.html)). Object lifetime is decided by the interpreter, not by this check.

</details>

### Question 4: Prediction

What does `type(type(1))` return, and what does `type(type(type(1)))` return?

<details><summary>Show Solution</summary>

`type(1)` is `int`, and `type(int)` is `type`, so `type(type(1))` is `type`. Applying `type` once more gives `type` again, because `type(type)` is `type`. The chain stops at `type` because `type` is its own type.

</details>
