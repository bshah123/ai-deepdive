By the end of this lesson you will be able to tell whether two names refer to the same object, predict when a change made through one name is visible through another, and avoid the identity mistakes that cause most surprises.

**You need:** names and variables (Lesson 2.1) and the fact that every object has a type and a value (Lesson 2.2).

## The problem identity solves

Suppose `a` and `b` both hold `[1, 2]`. Does a change made through `b` show up through `a`? It depends on whether they are the **same object**, not on whether the two lists look alike. `==` compares values. Identity compares objects. Python needs both, and this lesson is about the second.

The Python Language Reference puts it this way: an object's identity "never changes once it has been created; you may think of it as the object's address in memory" (Python Software Foundation, Data model, Section 3.1).

## What id() returns

Every object has three things: an identity, a type and a value. The built-in `id(x)` returns the identity of `x` as an integer. The official description makes one guarantee and one note (Python Software Foundation, Built-in Functions, `id`):

- **Guarantee:** the integer is unique and constant for the object during its lifetime.
- **Note:** two objects whose lifetimes do not overlap may get the same `id()` value.
- **CPython detail:** in CPython, the reference implementation, the id is the address of the object in memory. This is not part of the language specification.

The `is` operator tests identity directly: `x is y` is True when `x` and `y` are the same object. For two objects that both exist, `x is y` and `id(x) == id(y)` always agree. Use `is` when identity is the question, such as `x is None`, which asks whether `x` is the single `None` object. Use `==` when the question is whether two values are equal.

![Two names share one list and one id; an equal list has its own id](diagrams/2.3-names-and-ids.svg "Names point at objects. Equal contents do not make one object.")

## Worked example by hand

Trace three statements:

```
a = [1, 2]    # object A is created; the name a points to A
b = a         # the name b also points to A; nothing is copied
c = [1, 2]    # object C is created; same contents, different object
```

Line 2 copies nothing. It adds a second name for object A, and that is the whole mechanism behind aliasing (Lesson 2.5). Line 3 creates a new object that happens to have equal contents.

So `id(a) == id(b)` is True, `id(a) == id(c)` is False, `a is c` is False, and `a == c` is True. The code below checks each of these. The actual `id()` numbers change on every run, so the code compares them instead of printing them.

```python
a = [1, 2]
b = a
c = [1, 2]

print(id(a) == id(b))   # same object
print(id(a) == id(c))   # different object
print(a is b, a is c)   # is compares identity
print(a == c)           # == compares values
```

```output
True
False
True False
True
```

## Mutation changes the object; rebinding changes the name

There are two ways to change what a name holds. A **mutation** changes the object the name already points to. **Rebinding** (`x = ...`) makes the name point to a different object. Only the second one can change the id of `x`.

![Mutation keeps the object and its id; rebinding x to a new object leaves the old list with no name](diagrams/2.3-mutation-rebind.svg "Three steps, one name. The id changes only when the name moves.")

`append` mutates the list, so its identity is unchanged. `x = x + [4]` builds a new list and rebinds `x` to it. The old list has no name left, so Python can reclaim it (Lesson 2.7 explains how).

```python
x = [1, 2]
before = id(x)

x.append(3)                  # mutation
print(id(x) == before)       # the same object was changed in place

x = x + [4]                  # rebinding to a new object
print(id(x) == before)
print(x)
```

```output
True
False
[1, 2, 3, 4]
```

Augmented assignment (`+=`) can look like rebinding, but for a list it mutates in place. Tuples are immutable (Lesson 2.6), so `+=` on a tuple has to build a new tuple and rebind the name:

```python
x = [1, 2]
before = id(x)
x += [3]
print(id(x) == before, x)

t = (1, 2)
before_t = id(t)
t += (3,)
print(id(t) == before_t, t)
```

```output
True [1, 2, 3]
False (1, 2, 3)
```

Read the statement carefully before you assume either behaviour. The same symbol, `+=`, can keep the object or replace it, depending on the type of the object on the left.

## Function arguments: the object is shared, the name is not

A function parameter starts as a second name for the object the caller passed. The Python FAQ states the rule: arguments are passed by assignment, and since assignment creates references to objects, "there's no alias between an argument name in the caller and callee, and consequently no call-by-reference" (Python Software Foundation, Programming FAQ, "How do I write a function with output parameters").

Think of a call in two steps. First, Python binds the parameter name to the caller's object, so both names exist and point to one object. Second, the body runs. `lst.append` works on that shared object. `lst = [...]` changes only what the parameter name refers to, and the caller's name never moves.

Put the two cases side by side:

![A parameter starts as the caller's object; mutation is shared, rebinding the parameter is local](diagrams/2.3-call-by-assignment.svg "Mutation crosses the function boundary. Rebinding the parameter does not.")

```python
def mutate(lst):
    print("same object at entry:", lst is p)
    lst.append("m")

def rebind(lst):
    print("same object at entry:", lst is q)
    lst = ["r"]              # rebinds the local name only

p = [0]
mutate(p)
print(p)

q = [0]
rebind(q)
print(q)
```

```output
same object at entry: True
[0, 'm']
same object at entry: True
[0]
```

The FAQ's rule also explains the first line of each output: at entry, the parameter is the same object as the caller's name. The two functions differ only in what they do next.

## Small integers are shared (CPython detail)

Two separate computations of the same small integer can return one shared object. The code below builds each value twice at run time, so the compiler cannot merge them.

```python
for n in (5, 256, 257):
    u = int(str(n))
    v = int(str(n))
    print(n, u is v)
```

```output
5 True
256 True
257 False
```

In our run on CPython 3.12.13, the cache covers -5 through 256 (we checked -6, -5, 256, 257 and 1000 as well). This is an implementation detail that the language reference does not specify, so do not rely on it. Use `==` to compare numbers (Lesson 2.4). The practical point is that `is` answers a question about objects, and for numbers that is almost never the question you want to ask.

![CPython reuses small integers; larger values are new objects in this run](diagrams/2.3-small-int-cache.svg "Observed results on CPython 3.12. The axis is not to scale.")

## Ids can be reused after an object is freed

The uniqueness guarantee covers objects that are alive at the same time. When an object is freed, its address can go to a new object, and then the two objects have the same id.

```python
t = [1]
freed = id(t)
del t

u = [2]
print(id(u) == freed)
```

```output
True
```

In our run, the new list took the freed address. CPython does not promise this, so do not build code that depends on it. The point is what the guarantee does not cover.

The documentation's wording is precise for this reason: the guarantee is about objects that exist at the same time. Two objects that never coexist can share a number. An id is safe to compare only while both objects are alive, and it is never a record that outlives the object.

![A freed address comes back as a new object's id](diagrams/2.3-id-reuse.svg "The guarantee holds only while both objects exist.")

> [!ADVANCED]
> In CPython the id is the address of the object's header. We checked the round trip in our run: `ctypes.cast(id(obj), ctypes.py_object).value is obj` returned True. Do not do this in real code. A wrong address crashes the interpreter. The check only confirms the documented CPython detail.

## Common traps

> [!TRAP]
> **Equal literals in one block look identical.** In the same function body, `a = 1000` and `b = 1000` give `a is b` as True, because the compiler stores one constant for both. `int("1000") is int("1000")` is False. Identity results on literals in one block do not show runtime behaviour.

> [!TRAP]
> **Ids are not stable across runs.** An address changes from run to run and machine to machine. Do not save ids to a file, use them as test expectations, or print them as if they meant something.

> [!TRAP]
> **Storing an id is not keeping the object.** A dictionary keyed by `id(obj)` still holds the number after `obj` is freed. A new object may then take that number, and the lookup returns the wrong data. Keep the object itself as the key or the value.

> [!TRAP]
> **Rebinding a parameter does not change the caller.** `lst = ["r"]` inside a function leaves the caller's name alone. Only mutation is visible outside.

> [!TRAP]
> **`id()` is not an identifier you can assign.** Its values are memory addresses, so they are not stable, not small and not meant for records. Give your own objects an identifier that you choose and store.

## Summary

- Identity is what makes an object itself. `id()` returns it as an integer, unique only while the object is alive.
- `is` compares identity and `==` compares values. For live objects, `x is y` and `id(x) == id(y)` agree.
- Mutation keeps an object's id. Rebinding (`x = x + [4]`) moves the name to a new object.
- Arguments are passed by assignment. Mutation is shared with the caller, but rebinding a parameter is local.
- In CPython, small integers are shared and ids can be reused after an object is freed. Both are implementation details.

## Quiz time

### Question 1: Predict the output

What does this print?

```python
a = [1, 2]
b = a
b.append(3)
print(a)
print(a is b)
```

<details><summary>Show Solution</summary>

```
[1, 2, 3]
True
```

`b = a` makes both names point to one list. `append` mutates that list, so `a` sees the change. The two names are the same object, so `a is b` is True.

</details>

### Question 2: Find the bug

This function should add `"apple"` to `cart`, but it does not. Explain why and fix it.

```python
def add_item(items, item):
    items = items + [item]
    return None

cart = []
add_item(cart, "apple")
print(cart)
```

<details><summary>Show Solution</summary>

The output is `[]`. `items + [item]` builds a new list and rebinds the parameter `items` to it. That rebinding is local, so the caller's `cart` is unchanged. The fix mutates the object the caller passed:

```python
def add_item(items, item):
    items.append(item)

cart = []
add_item(cart, "apple")
print(cart)
```

```
['apple']
```

</details>

### Question 3: Explain the identity result

After this code runs, what do `y is x` and `y` print, and why?

```python
x = [1, 2]
y = x
x = x + [3]
print(y is x, y)
```

<details><summary>Show Solution</summary>

It prints `False [1, 2]`. `y = x` makes both names point to the first list. `x = x + [3]` builds a second list and rebinds only `x`. Now `x` and `y` are different objects, and the first list still holds `[1, 2]`.

</details>

### Question 4: Explain the risk

A program stores `id(obj)` in a dictionary, deletes `obj`, and later creates a new object. It then looks up the stored id, expecting the old object. Why is this unsafe?

<details><summary>Show Solution</summary>

The guarantee that an id is unique covers only objects that are alive at the same time. After `obj` is freed, its address can belong to the new object, so the lookup can return the new object or its data. The fix is to keep a reference to the object itself, not its id.

</details>
