In this lesson you will predict whether `is` and `==` agree for a given pair of objects, say which one asks "same object?" and which one asks "same value?", and explain why a check that passes on small test values can fail on real data.

**You need:** Lesson 2.3 (what `id()` returns). Nothing else.

## The problem: two checks that look alike

Both `is` and `==` can return `True` for two names, so they are easy to mix up. `is` asks whether two names refer to the same object. `==` asks whether the two objects compare equal, which is up to the type. The mix-up is dangerous because it often hides: `is` on two equal numbers can return `True` in a quick test and `False` in production, depending on how the numbers were made.

Consider a status check written as `if status is "ok"`. In a test where `status` is a literal, it may pass. When `status` is built at run time, for example by joining pieces of text, it is equal to `"ok"` but is a different object, so the check fails. The rule that prevents this is simple: use `==` to compare values, and `is` only to ask about identity, such as `is None`. The rest of this lesson shows where each rule comes from and what the measured numbers are.

## Intuition: names point at objects

A variable is a name bound to an object (Lesson 2.1). Two names can point at one object, or at two different objects that hold equal values.

![Three names: a and c point at one list object, b points at a second list object with the same contents](diagrams/2.4-names-and-objects.svg "a and c share one object. b holds an equal value in a different object.")

## Worked example by hand

Start with `a = [1, 2, 3]`, `b = [1, 2, 3]` and `c = a`. Each `[...]` display creates a new list, so `a` and `b` are two objects. The line `c = a` creates no list: it binds a second name to the first object.

- `a is b` is `False`: two different objects.
- `a == b` is `True`: the same elements in the same order.
- `a is c` is `True`: one object, two names.

Then `c.append(4)` changes that object. `a` shows the change; `b` does not. The code below reproduces each number.

```python
a = [1, 2, 3]
b = [1, 2, 3]
c = a

print("a is b:", a is b, "| a == b:", a == b)
print("a is c:", a is c, "| a == c:", a == c)
print("id(a) == id(c):", id(a) == id(c))

c.append(4)
print("a:", a)
print("b:", b)
```

```output
a is b: False | a == b: True
a is c: True | a == c: True
id(a) == id(c): True
a: [1, 2, 3, 4]
b: [1, 2, 3]
```

## The rules: what each operator calls

`x is y` is true if and only if `x` and `y` are the same object, as the Language Reference states in its Comparisons section (https://docs.python.org/3/reference/expressions.html#comparisons). `is` is not overridable: it compares identity and nothing else.

`x == y` calls a method on `x`'s type, `__eq__`. The Data Model says that `object`, the base class of every class, implements it "by using `is`, returning `NotImplemented` in the case of a false comparison" (https://docs.python.org/3/reference/datamodel.html#object.__eq__). `NotImplemented` is a sentinel that means "I cannot decide; ask the other operand". The dispatch goes in three steps.

![Dispatch of a == b: first type(a).__eq__, then type(b).__eq__ if that returns NotImplemented, then a fallback to a is b](diagrams/2.4-eq-dispatch.svg "A bool from either __eq__ is the answer. Only two NotImplemented results reach the identity fallback.")

The code below defines two classes. `Plain` uses the inherited `__eq__`. `Point` defines its own and returns `NotImplemented` for non-`Point` values.

```python
class Plain:
    pass

class Point:
    def __init__(self, x):
        self.x = x

    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented  # let Python try the other operand
        return self.x == other.x

p, q = Plain(), Plain()
print("Plain: p == q", p == q, "| p == p", p == p)

r, s = Point(1), Point(1)
print("Point: r == s", r == s, "| r is s", r is s)
print("Point: r == 1", r == 1, "| 1 == r", 1 == r)
print("Point.__hash__ is None:", Point.__hash__ is None)
```

```output
Plain: p == q False | p == p True
Point: r == s True | r is s False
Point: r == 1 False | 1 == r False
Point.__hash__ is None: True
```

`r == 1` does not raise. `Point.__eq__` returns `NotImplemented`, then `int.__eq__` also does, and `==` falls back to identity, which is `False`. The Language Reference says the same: "When no appropriate method returns any value other than `NotImplemented`, the `==` and `!=` operators will fall back to `is` and `is not`". The last line shows a side effect. Defining `__eq__` without `__hash__` makes the class's instances unhashable, so they cannot be dictionary keys or set members. The Data Model says: "if it defines `__eq__()` but not `__hash__()`, its instances will not be usable as items in hashable collections."

## Equal values are sometimes one object

CPython (the reference implementation of Python, written in C; Lesson 1.3) reuses some immutable objects. It keeps one shared integer for each value from -5 to 256, and one shared object for each single-character string in the Latin-1 range. Nothing in the language promises this. The diagram shows what one run on CPython 3.12 gave for values built at run time.

![Measured results of x is y for values built at run time: True for -5, 0, 256 and chr(97); False for -6, 257, 1000, chr(8364) and a joined string](diagrams/2.4-identity-cache.svg "One run, CPython 3.12. Values were built with int(str(v)) and str functions, so the compiler did not share them.")

```python
import sys

for v in [-6, -5, 256, 257, 1000]:
    x = int(str(v))  # built at run time, so no compile-time sharing
    y = int(str(v))
    print(f"{v:>5}: x is y -> {x is y}")

print("chr(97) is chr(97):", chr(97) is chr(97))
print("chr(8364) is chr(8364):", chr(8364) is chr(8364))

lit = "hello"
built = "".join(["hel", "lo"])
print("built == lit:", built == lit, "| built is lit:", built is lit)
print("after sys.intern:", sys.intern(built) is lit)
```

```output
   -6: x is y -> False
   -5: x is y -> True
  256: x is y -> True
  257: x is y -> False
 1000: x is y -> False
chr(97) is chr(97): True
chr(8364) is chr(8364): False
built == lit: True | built is lit: False
after sys.intern: True
```

`sys.intern` returns the one canonical copy of a string, so after interning, the identity check passes. Strings written as literals in the same code are often shared, but that is an optimisation. Code that depends on it works until the code is moved, rebuilt or read from a file. Different types are a related trap: `1 == 1.0` is `True` but `1 is 1.0` is `False`, and `True == 1` is `True` while `True is 1` is `False`.

## NaN: equal to nothing, including itself

NaN ("Not a Number") is the IEEE 754 floating-point value for undefined results; `float("nan")` creates one. (Note that `0.0 / 0.0` raises `ZeroDivisionError` in Python rather than returning NaN.) A NaN is not equal to itself: `n == n` is `False`. Its identity is still itself, so `n is n` is `True`. The Language Reference explains how containers handle this: "The built-in containers typically assume identical objects are equal to themselves. That lets them bypass equality tests for identical objects." A list therefore compares equal to a list holding the same NaN object, but not to a list holding a different NaN object.

![Two pairs of lists: [x] and [x] point at one NaN object and compare True; [nan] and [nan] point at two NaN objects and compare False](diagrams/2.4-nan-containers.svg "Container equality checks identity first for each element. The identity shortcut is documented as typical, not guaranteed.")

```python
nan1 = float("nan")
print("nan1 == nan1:", nan1 == nan1, "| nan1 is nan1:", nan1 is nan1)
print("[nan1] == [nan1]:", [nan1] == [nan1])
print('[float("nan")] == [float("nan")]:', [float("nan")] == [float("nan")])
```

```output
nan1 == nan1: False | nan1 is nan1: True
[nan1] == [nan1]: True
[float("nan")] == [float("nan")]: False
```

## Cost: why `is None` is the idiom

`is` compares two pointers. `==` on a class with a Python-level `__eq__` calls a Python function. The diagram shows one run of a timing loop on CPython 3.12 with a class whose `__eq__` returns `False`.

![Bar chart of ns per operation: obj is None 8.6 ns, obj == None 43.8 ns, v is 0 7.4 ns, v == 0 8.4 ns](diagrams/2.4-is-vs-eq-cost.svg "One run on one machine. The integer rows show no real difference, because no Python code runs.")

The absolute numbers depend on your machine. The ratio, about 5x, applies when a Python `__eq__` is called. Correctness matters more than speed here. A class is free to make `x == None` return `True`, so `==` does not reliably ask "is this None?". PEP 8 says: "Comparisons to singletons like None should always be done with `is` or `is not`, never the equality operators" (https://peps.python.org/pep-0008/). The `is` operator cannot be overridden (see the identity rule above), so `x is None` always asks the right question.

## Common traps

> [!TRAP]
> Do not use `is` to compare numbers or strings built at run time. `int(str(257)) is int(str(257))` is `False`, while the same comparison for 256 is `True`. Use `==`.

> [!TRAP]
> CPython 3.12 printed `SyntaxWarning: "is" with 'int' literal. Did you mean "=="?` when it compiled `x is 5`. This comes from my run, not from the docs. Write `x == 5`.

> [!TRAP]
> `[nan] == [nan]` can be `True` and `[float("nan")] == [float("nan")]` is `False`, although the two look the same. The result depends on whether the NaN object is shared.

> [!TRAP]
> A class that defines `__eq__` and not `__hash__` cannot be used as a dictionary key or set member. Check with `Point.__hash__ is None`, which is `True` in the run above.

## Summary

- `is` asks whether two names refer to the same object. It cannot be overridden.
- `==` calls the left operand's `__eq__`, then the right operand's, and falls back to `is` only when both return `NotImplemented`.
- Equal values may or may not be one object. CPython's small-int and character caching is an implementation detail, so do not rely on it.
- Compare to `None` with `is`, and compare values with `==`.

## Quiz time

### Question 1: Conceptual

What does `a is b` test, what does `a == b` call, and when does `==` fall back to identity?

<details><summary>Show solution</summary>

`a is b` tests whether `a` and `b` are the same object. `a == b` calls `type(a).__eq__(a, b)`; if that returns `NotImplemented`, it calls `type(b).__eq__(b, a)`; if that also returns `NotImplemented`, `==` falls back to `a is b`.

</details>

### Question 2: What does this code print?

```python
x = [0]
y = x
z = [0]
print(x is y, x == z, x is z)
y.append(1)
print(x)
```

<details><summary>Show solution</summary>

```output
True True False
[0, 1]
```

`x` and `y` name one list; `z` is a second list with equal contents. Appending through `y` changes the object that `x` names.

</details>

### Question 3: Find the bug

```python
def is_ok(status: str, expected: str) -> bool:
    return status is expected

built = "".join(["o", "k"])
print(is_ok(built, "ok"))
```

<details><summary>Show solution</summary>

The output is `False`. `built` is a new string object, not the one `"ok"` refers to, so `is` fails even though the text matches. The fix compares values:

```python
def is_ok(status: str, expected: str) -> bool:
    return status == expected

built = "".join(["o", "k"])
print(is_ok(built, "ok"))
```

```output
True
```

</details>

### Question 4: Predict the output

```python
n = float("nan")
print([n] == [n], [n] == [float("nan")], n in [n])
```

<details><summary>Show solution</summary>

```output
True False True
```

`[n] == [n]` is `True` because the element is the same object. `[n] == [float("nan")]` is `False` because the two NaN objects are different and NaN is not equal to itself. `n in [n]` is `True` because `in` tests `x is e or x == e` (Language Reference, Comparisons).

</details>

### Question 5: Explain

Why does PEP 8 recommend `x is None` rather than `x == None`, even when both give the same answer for `None`?

<details><summary>Show solution</summary>

`x == None` calls `type(x).__eq__`, which a class may define to return `True` for `None`, so the result depends on the class. `x is None` compares identity with the single `None` object and cannot be overridden. (The reasoning is mine, from the Data Model rules quoted above.)

</details>
