By the end of this lesson you will predict what every name refers to after an assignment, a method call, a function call or a copy, and you will know why `b = a` costs almost nothing in memory. Most "why did my list change?" bugs come from one fact: assignment copies a reference, not the object.

**You need:** names and assignment (Lesson 2.1), objects (Lesson 2.2), and `is` versus `==` (Lesson 2.4).

## The problem

You write `b = a`, then `b.append(4)`. Does `a` change?

It does. Assignment never copies data. It makes a second name refer to the same object. Ned Batchelder's article "Facts and myths about Python names and values" states the rule as "Assignment never copies data" and treats names as labels attached to values.[1] The Python data model says the same thing from the other side: an object's identity "never changes once it has been created", and `is` compares identities.[2]

The same rule explains two facts you will meet often. A function can change a list you passed in, but it cannot change a number you passed in, because numbers cannot be mutated. Copying a list also costs memory, while assigning it does not. This lesson covers references only. Reference counting (Lesson 2.7) frees an object when its count reaches zero, and cycles need the garbage collector (Lessons 2.8 and 2.9).

## Intuition: names are arrows

A name is a label, and each arrow in the picture is one reference from a name to an object. Assignment adds an arrow. It does not add a list.

![Two name boxes a and b with arrows into one list object holding 1, 2, 3](diagrams/2.5-names.svg "b = a adds a second arrow. No list is copied.")

There are two different operations, and only one of them is visible through another name:

- **Mutation** changes the object a name refers to, as in `x.append(4)`. Every name that refers to that object sees the change.
- **Rebinding** moves a name to a different object, as in `x = [5, 6, 7]`. Only that name moves. Other names still refer to the old object.

Before you run any code, ask two questions for each line: which object does it touch, and which names point at that object? The answers decide what every name shows afterward.

![Left: x.append(4) changes the one shared list, so x and y both show four items. Right: x = a new list moves only x; y still points at the old list](diagrams/2.5-mutate-rebind.svg "Mutate changes the object. Rebind moves one arrow.")

## Worked example by hand

Trace four lines and track the arrows.

1. `a = [1, 2, 3]` creates one list. One arrow points at it, from `a`.
2. `b = a` adds a second arrow, from `b`. The list has two names.
3. `b.append(4)` changes the list itself. Both `a` and `b` now show `[1, 2, 3, 4]`.
4. `a = [5, 6, 7]` creates a new list and moves the arrow from `a` to it. The old list still has one arrow, from `b`.

CPython (the standard Python interpreter, written in C) keeps a reference count for each object, which is the number of arrows pointing at it. `sys.getrefcount(x)` reports one more than that, because passing `x` to the function is a temporary third reference. The `+1` comes from the call itself.

Step 4 frees nothing. The old list still has one arrow, from `b`, so it stays alive. Each rebinding removes one arrow from the old object, and an object becomes a candidate for freeing only when no arrows remain.

```python
import sys

a = [1, 2, 3]
print("refcount with one name:", sys.getrefcount(a))   # 2: name a + the call argument
b = a                                                   # no copy: b is a second name
print("b is a:", b is a)
print("refcount with two names:", sys.getrefcount(a))   # 3

b.append(4)                                             # mutate the object through b
print("a after b.append(4):", a)

a = [5, 6, 7]                                           # rebind a: only the name moves
print("a after rebinding:", a)
print("b still refers to:", b)
print("refcount of the old list now:", sys.getrefcount(b))  # 2
```

```output
refcount with one name: 2
b is a: True
refcount with two names: 3
a after b.append(4): [1, 2, 3, 4]
a after rebinding: [5, 6, 7]
b still refers to: [1, 2, 3, 4]
refcount of the old list now: 2
```

### Function arguments are assignments

A call binds each parameter to the argument's object, as an assignment would.[1] The parameter is a local name. So a function can change the caller's list, but it cannot rebind the caller's name.

Two habits follow. If a function must not change its input, copy the input first (`items = list(items)`). If a function must produce a new result, return a new object instead of editing the argument and hoping the caller notices.

![A caller name lst and a parameter p both point at one list; after p.append(99) the caller sees 99. In the rebind case, p moves to a new list and lst still shows the list with 1 and 99](diagrams/2.5-call-frames.svg "Parameters are names too. The same two rules apply.")

```python
def mutate_param(p: list) -> None:
    p.append(99)           # changes the object the caller passed

def rebind_param(p: list) -> None:
    p = [0]                # changes only the local name p

lst = [1]
mutate_param(lst)
print("after mutate_param:", lst)
rebind_param(lst)
print("after rebind_param:", lst)
```

```output
after mutate_param: [1, 99]
after rebind_param: [1, 99]
```

`rebind_param` returns nothing. Its new list is discarded when the function returns, because no name refers to it any more.

## Copies: shallow and deep

A copy is a new object, but a list can hold references too. The `copy` module defines two kinds. A shallow copy "constructs a new compound object and then ... inserts references" to the original's contents. A deep copy "recursively inserts copies".[3]

![Shallow copy: the nested list and the shallow list each point at the same inner lists A and B. Deep copy: the deep list points at new inner lists C and D](diagrams/2.5-shallow-deep.svg "Shallow copies the outer list. Deep copies everything below it.")

```python
import copy

nested = [[1], [2]]
shallow = copy.copy(nested)     # new outer list, same inner lists
deep = copy.deepcopy(nested)    # new outer list, new inner lists

print("shallow[0] is nested[0]:", shallow[0] is nested[0])
print("deep[0] is nested[0]:", deep[0] is nested[0])

nested[0].append(9)
print("shallow:", shallow)
print("deep:", deep)
```

```output
shallow[0] is nested[0]: True
deep[0] is nested[0]: False
shallow: [[1, 9], [2]]
deep: [[1], [2]]
```

A shallow copy is enough when the elements are immutable, such as numbers, strings or tuples of numbers, because nothing inside can change. It is not enough when the elements are lists or dictionaries, since those are exactly the objects you would mutate.

`list.copy()`, `a[:]` and `list(a)` each copy only the outer list. They behave like a shallow copy (my own reasoning from what they create).

The deep copy keeps its own inner lists. Changing `nested[0]` left `deep` unchanged, because `deepcopy` never shared them.

## Copy cost: what allocates memory

Assignment allocates nothing. A flat copy allocates one array of references, 8 bytes per slot on a 64-bit build. A deep copy also allocates every inner list.

![Bar chart of bytes allocated: b = a 0 B; a.copy() of 1,000,000 slots 8.0 MB; copy.copy() of 100,000 lists 0.8 MB; copy.deepcopy() of the same 100,000 lists 9.6 MB](diagrams/2.5-copy-cost.svg "Bytes that stay allocated after each operation, measured with tracemalloc.")

The measurement uses `tracemalloc`, the standard-library memory tracer. It is not runnable in the browser, so it is shown as a local run:

<details><summary>Run locally: CPython 3.12, standard library only (tracemalloc)</summary>

```python
import copy
import sys
import tracemalloc

def alive_bytes(make):
    tracemalloc.start()
    before = tracemalloc.get_traced_memory()[0]
    kept = make()
    after = tracemalloc.get_traced_memory()[0]
    tracemalloc.stop()
    return after - before, kept

big = [0] * 1_000_000
print("b = a:", alive_bytes(lambda: big)[0], "bytes")
print("a.copy():", alive_bytes(lambda: big.copy())[0], "bytes")
print("getsizeof(big):", sys.getsizeof(big), "bytes")
nested = [[i] for i in range(100_000)]
print("copy.copy(nested):", alive_bytes(lambda: copy.copy(nested))[0], "bytes")
print("copy.deepcopy(nested):", alive_bytes(lambda: copy.deepcopy(nested))[0], "bytes")
```

```output
b = a: 0 bytes
a.copy(): 8000000 bytes
getsizeof(big): 8000056 bytes
copy.copy(nested): 800112 bytes
copy.deepcopy(nested): 9601048 bytes
```

</details>

Read the numbers this way. `[0] * 1_000_000` holds one shared `0` object in every slot, so `a.copy()` allocates only the reference array: 8,000,000 bytes. The shallow copy of 100,000 inner lists allocates only the outer array, 800,112 bytes. The deep copy allocates the 100,000 new inner lists as well. Subtracting gives about 88 bytes per inner list (9,601,048 − 800,112 = 8,800,936, divided by 100,000). That per-list figure depends on the allocator and the build, so treat it as a measurement, not a constant.

The practical consequence: passing a reference costs the same whatever the list length, while a copy costs memory in proportion to the length (and, for nested data, to the number of inner objects). Copy only when the old version must survive a later change. Otherwise pass the reference and let the caller see the change.

## Common traps

> [!TRAP]
> `b = a` does not copy. If you want an independent list, use `b = a.copy()` or `copy.deepcopy(a)` for nested data.

> [!TRAP]
> `[[0] * 3] * 2` makes two references to one inner list. See Question 2 below.

> [!TRAP]
> A shallow copy shares every inner object. Mutating `shallow[0]` changes `nested[0]` too.

> [!TRAP]
> A tuple cannot rebind its slots, but a tuple can hold a mutable object. In the Python run below, `t[0].append(2)` works and `t[0] = [3]` raises `TypeError`.

> [!TRAP]
> Do not use `is` to compare values. `int("256") is int("256")` is `True` in CPython, which caches small integers (my reasoning; the 256/257 split below matches it). The language reference says this behaviour is implementation-dependent and should not be relied on.[2]

```python
t = ([1],)
t[0].append(2)                  # allowed: the tuple holds a reference to the list
print("t:", t)
try:
    t[0] = [3]                  # not allowed: this would rebind a slot of the tuple
except TypeError as err:
    print("TypeError:", err)

def add_item(item, bag=[]):     # the default list is created once, at def time
    bag.append(item)
    return bag

first = add_item(1)
second = add_item(2)
print("first:", first)
print("second:", second, "same object:", first is second)

print("int 256:", int("256") is int("256"))
print("int 257:", int("257") is int("257"))
```

```output
t: ([1, 2],)
TypeError: 'tuple' object does not support item assignment
first: [1, 2]
second: [1, 2] same object: True
int 256: True
int 257: False
```

The default-argument case is in the Python tutorial: the default value "is evaluated only once", so a mutable default accumulates across calls.[4]

## Summary

- `b = a` adds a second reference to one object. It copies no data and allocates no list.
- Mutation changes the object, so every name sees it. Rebinding moves one name only.
- A function parameter is a local name bound to the caller's object. It can mutate, but rebinding does not reach the caller.
- A shallow copy shares inner objects. A deep copy copies them recursively.

## Quiz time

Each solution explains the arrows, not just the output.

### Question 1: Predict the output

```python
x = [0]
y = x
x = x + [1]
print(y)
```

<details><summary>Show Solution</summary>

```text
[0]
```

`x + [1]` builds a new list and binds `x` to it. The old list, which `y` still refers to, is unchanged. Only `x.append(1)` would change `y`.

</details>

### Question 2: Find the bug

```python
grid = [[0] * 3] * 2
grid[0][1] = 5
print(grid)
```

<details><summary>Show Solution</summary>

```text
[[0, 5, 0], [0, 5, 0]]
```

`[row] * 2` repeats one reference, so both rows are the same list. Build each row separately: `grid = [[0] * 3 for _ in range(2)]`.

</details>

### Question 3: Calculate

A list of 10,000 references is copied with `a.copy()` on a 64-bit CPython build, where each reference takes 8 bytes. How many bytes does the copy allocate for its reference array, and how many bytes does `b = a` allocate?

<details><summary>Show Solution</summary>

The copy allocates 10,000 × 8 = 80,000 bytes for the reference array, about 80 KB. `b = a` allocates 0 bytes. The 8-byte figure is an assumption about the build (the pointer size), not something this lesson measured for 10,000 items. The measured 1,000,000-slot case gave 8,000,000 bytes, which is consistent with it.

</details>

### Question 4: Explain

Why does `copy.copy(a)` not protect a list of lists from mutation?

<details><summary>Show Solution</summary>

`copy.copy` creates a new outer list, but it inserts the same inner list objects. Changing an inner list through either outer list changes the shared object. `copy.deepcopy(a)` creates new inner lists, so the two structures are independent.

</details>
