In this lesson you will predict whether an operation changes an object or builds a new one, and explain why `a += [4]` and `t += (4,)` behave differently. You will then meet the four traps this difference causes: aliased changes, mutable default arguments, immutable containers that hold lists, and shallow copies.

**You need:** how names refer to objects (Lesson 2.5, Object References & Aliasing) and basic list and tuple syntax.

## The problem mutability solves

Lesson 2.5 showed that two names can refer to one object. If that object can change, a change made through one name is visible through the other. Whether this can happen depends on the object's type. The Python data model defines the two categories this way: "Objects whose value can change are said to be mutable; objects whose value is unchangeable once they are created are called immutable" (Python Language Reference, data model, section 3.1).

The table below sorts the common built-in types. "Hashable" means `hash()` works, so the object can be a dictionary key or a set member. That property matters in section 3.

![Six immutable built-in types, each hashable (tuple only when its contents are), next to four mutable types that are unhashable](diagrams/2.6-type-table.svg "Built-in types by mutability and hashability.")

## Same operator, two outcomes

The key idea is that `+=` does not always mean "create a new value and rebind the name". For a list, `a += [4]` extends the list that `a` refers to. For a tuple, `t += (4,)` cannot change the tuple, so it builds a new one and binds `t` to it. Any other name that referred to the old object keeps it.

![Two panels. Shared list: after the extension, both names see the one list with four items. Shared tuple: after the concatenation, t points to a new four-item tuple and u still points to the old three-item tuple.](diagrams/2.6-same-object.svg "The same += on a shared mutable object and on a shared immutable one.")

Worked example by hand. Start with `a = b = [1, 2, 3]`: one list, two names. Then `a += [4]` extends that list, so `b` also reads `[1, 2, 3, 4]`. Now start with `t = u = (1, 2, 3)`. Then `t += (4,)` creates a new tuple `(1, 2, 3, 4)`, binds `t` to it, and leaves `u` on `(1, 2, 3)`. The code below checks every case with the same rule: bind the result of the operator back to the name, then see whether the alias changed.

```python
import operator

cases = [
    ("list", lambda: [1, 2, 3], operator.iadd, [4]),
    ("dict", lambda: {"a": 1}, operator.ior, {"b": 2}),
    ("set", lambda: {1, 2, 3}, operator.ior, {4}),
    ("bytearray", lambda: bytearray(b"ab"), operator.iadd, b"c"),
    ("int", lambda: 5, operator.iadd, 1),
    ("str", lambda: "ab", operator.iadd, "c"),
    ("tuple", lambda: (1, 2, 3), operator.iadd, (4,)),
    ("frozenset", lambda: frozenset({1, 2}), operator.ior, frozenset({3})),
]
for label, make, op, rhs in cases:
    a = make()
    b = a
    a = op(a, rhs)  # what `a += rhs` does: the result is bound back to a
    print(f"{label:10s} same_object={a is b!s:5s} alias_now={b!r}  new_value={a!r}")
```

```output
list       same_object=True  alias_now=[1, 2, 3, 4]  new_value=[1, 2, 3, 4]
dict       same_object=True  alias_now={'a': 1, 'b': 2}  new_value={'a': 1, 'b': 2}
set        same_object=True  alias_now={1, 2, 3, 4}  new_value={1, 2, 3, 4}
bytearray  same_object=True  alias_now=bytearray(b'abc')  new_value=bytearray(b'abc')
int        same_object=False alias_now=5  new_value=6
str        same_object=False alias_now='ab'  new_value='abc'
tuple      same_object=False alias_now=(1, 2, 3)  new_value=(1, 2, 3, 4)
frozenset  same_object=False alias_now=frozenset({1, 2})  new_value=frozenset({1, 2, 3})
```

The first four types are mutable: the operator returns the same object, so the alias sees the change. The last four are immutable: the operator returns a new object, and the alias keeps the old value. The Python Language Reference says that augmented assignment performs the operation in place "when possible" (section on augmented assignment statements). The mechanism for tuples and integers, which have no in-place method, is my reasoning from this result; I did not check it against the data model's section on emulating numeric types.

## Hashing: why lists cannot be dictionary keys

A dictionary looks up keys by their hash value. If a key could change, its hash would change too, and the dictionary would lose it. So Python only allows hashable keys. The following block runs `hash()` on one object of each kind:

```python
samples = [1, "a", (1, 2), [1], {"a": 1}, ([1],)]
for x in samples:
    try:
        hash(x)
        print(f"{type(x).__name__:6s} hashable")
    except TypeError as e:
        print(f"{type(x).__name__:6s} TypeError: {e}")
```

```output
int    hashable
str    hashable
tuple  hashable
list   TypeError: unhashable type: 'list'
dict   TypeError: unhashable type: 'dict'
tuple  TypeError: unhashable type: 'list'
```

The last line is the tuple from the table's footnote. It is immutable in its own slots, but hashing it hashes the list inside, and that list can change.

## Functions receive the same object

Python passes arguments by assignment. The argument name inside the function is a new name for the caller's object (Python FAQ, "How do I write a function with output parameters?"). A function that rebinds its parameter changes nothing outside. A function that mutates its parameter changes the caller's object. The default-argument trap below depends on this.

A default value is created once, when `def` runs. It is not created again for each call. The Python tutorial states the consequence: "The default value is evaluated only once. This makes a difference when the default is a mutable object such as a list, dictionary, or instances of most classes" (Python Tutorial, section 4.9.1).

![One function object holds one default list. Three calls each append to it, so the returned list grows from one item to three items.](diagrams/2.6-default-arg.svg "The default is a single object shared by every call.")

```python
def add_item(item, bag=[]):
    bag.append(item)
    return bag

print(add_item(1))
print(add_item(2))
print("__defaults__ =", add_item.__defaults__)
print("same default object:", add_item.__defaults__[0] is add_item(3))
```

```output
[1]
[1, 2]
__defaults__ = ([1, 2],)
same default object: True
```

The usual fix is a sentinel: `def add_item(item, bag=None)`, then `if bag is None: bag = []` inside the body.

## An immutable container can change

A tuple cannot replace its items, but it can hold a mutable object, and that object can change. The Python data model says so directly: "the value of an immutable container object that contains a reference to a mutable object can change when the latter's value is changed" (section 3.1).

Now consider `t[0] += [2]`. Python does three steps: it reads `t[0]`, extends that list in place, then stores the result back into `t[0]`. The first step changes the list. The last step fails, because tuples refuse item assignment. The error appears, but the list has already changed.

![A tuple with one slot pointing to a list of two items. Step 1 extends the list in place and succeeds. Step 2 tries to store into slot 0 of the tuple and fails.](diagrams/2.6-tuple-trap.svg "Why the error does not undo the change.")

```python
t = ([1],)
try:
    t[0] += [2]
except TypeError as e:
    print("TypeError:", e)
print("t =", t)
```

```output
TypeError: 'tuple' object does not support item assignment
t = ([1, 2],)
```

## Copies: shallow vs deep

To copy a list, you can use `list.copy()`, slicing (`lst[:]`), or `copy.copy()`. All three are shallow: they build a new outer list whose items are the same objects as before. The copy module defines a shallow copy as one that "inserts references into it to the objects found in the original", and a deep copy as one that "recursively, inserts copies" of them (Python docs, `copy` module).

![Three outer lists. The original and the shallow copy point to the same two inner lists. The deep copy points to new inner lists, so changing the original does not change it](diagrams/2.6-copy.svg "Shallow copies share the inner lists; deep copies do not.")

```python
import copy

orig = [[1, 2], [3]]
shallow = copy.copy(orig)
deep = copy.deepcopy(orig)
orig[0].append(99)
print("shallow =", shallow)
print("deep    =", deep)
print("shallow[0] is orig[0]:", shallow[0] is orig[0], "| deep[0] is orig[0]:", deep[0] is orig[0])
```

```output
shallow = [[1, 2, 99], [3]]
deep    = [[1, 2], [3]]
shallow[0] is orig[0]: True | deep[0] is orig[0]: False
```

## Cost: why rebuilding is slower than mutating

Building a list with `lst = lst + [i]` creates a new list at every step and copies everything already built. For $n$ items it copies about $n(n-1)/2$ items in total. Building it with `lst.append(i)` writes one slot per step, and the backing array is occasionally resized; the cost per append is constant on average. This is reasoning from how CPython lists work. The timings below are measured.

```python
import time

def build_concat(n):
    lst = []
    for i in range(n):
        lst = lst + [i]
    return lst

def build_append(n):
    lst = []
    for i in range(n):
        lst.append(i)
    return lst

def best(f, n):
    times = []
    for _ in range(3):
        t0 = time.perf_counter()
        f(n)
        times.append(time.perf_counter() - t0)
    return min(times)

for n in [5000, 10000, 20000, 40000]:
    print(n, round(best(build_concat, n) * 1000, 1), round(best(build_append, n) * 1000, 3))
```

One run on a laptop with Python 3.12.13 gave 24.10 ms for `lst + [i]` against 0.101 ms for `append` at $n = 5000$, and 2210.37 ms against 0.735 ms at $n = 40000$. These numbers depend on the machine, so the code block does not print them. The ratio is the useful part. When $n$ doubles, the concatenation time grew by 4.1 to 5.1 times, close to the quadratic prediction of 4. The append time grew by 1.9 to 2.0 times, close to the linear prediction of 2.

![Two bars: doubling n multiplies the concatenation time by about 4 to 5, and the append time by about 2. Dashed reference lines mark x2 for linear growth and x4 for quadratic growth.](diagrams/2.6-growth.svg "Time multiplier when n doubles, measured over 5,000 to 40,000 items.")

The fix is to mutate the list you already have: use `lst.append(i)`, or `lst += [i]`, which extends the same list. Use `lst + [i]` only when you need a second list and must keep the first.

## Common traps

> [!TRAP]
> `+=` depends on the type. `a += [4]` changes the list that `a` and every alias share. `a = a + [4]` always creates a new list and leaves the aliases alone.

> [!TRAP]
> A default argument such as `bag=[]` is one shared object. Use `bag=None` and create the list inside the function.

> [!TRAP]
> An error inside `t[0] += ...` does not roll back the change. The list inside the tuple has already been extended.

> [!TRAP]
> `list.copy()`, `lst[:]` and `copy.copy()` are shallow. Nested lists are still shared. Use `copy.deepcopy()` when inner objects must be independent.

> [!TRAP]
> Lists, dicts and sets cannot be dictionary keys or set members, because they are unhashable. A tuple can be one only if everything inside it is hashable.

## Summary

- A type is mutable if its value can change in place, and immutable otherwise. Python decides this per type, not per variable.
- `a += x` mutates a mutable object, so every alias sees the change. For an immutable object it creates a new object and rebinds only `a`.
- Default argument values are created once, so mutable defaults are shared across calls.
- Shallow copies share nested objects. Deep copies do not. Dictionary keys must be hashable: the built-in immutable types are, and the built-in mutable types are not.

## Quiz time

### Question 1: Prediction

```python
x = (1, 2)
y = x
x += (3,)
print(y)
```

<details><summary>Show solution</summary>

The output is `(1, 2)`. A tuple has no in-place `+=`, so `x` is rebound to a new tuple `(1, 2, 3)`. `y` still refers to the original `(1, 2)`.

</details>

### Question 2: Bug-spotting

```python
def add_tag(tag, tags=[]):
    tags.append(tag)
    return tags

print(add_tag("python"))
print(add_tag("ml"))
```

<details><summary>Show solution</summary>

The output is `['python']` and then `['python', 'ml']`. The default list is created once, so the second call sees the first call's tag. Fix it with `tags=None` and `if tags is None: tags = []` inside the body.

</details>

### Question 3: Explanation

Why does `t[0] += [2]` change the list even though the statement ends with a `TypeError`?

<details><summary>Show solution</summary>

The statement runs in three steps. It reads `t[0]`, which is the list. It extends that list in place with `+=`, which changes the object. Then it tries to store the result in `t[0]`, and the tuple rejects the assignment. The list was already changed in the first step, and nothing undoes it.

</details>

### Question 4: Calculation

Building a list with `lst = lst + [i]` for $n$ items copies about $n(n-1)/2$ items in total. Roughly how much longer does it take when $n$ doubles, and why does that differ from `append`?

<details><summary>Show solution</summary>

Doubling $n$ multiplies $n(n-1)/2$ by about $(2n)^2 / n^2 = 4$, so the time is about four times larger. `append` does constant work on average per item, so doubling $n$ roughly doubles the time. The measured ratios in this lesson were 4.1 to 5.1 for concatenation and 1.9 to 2.0 for append.

</details>
