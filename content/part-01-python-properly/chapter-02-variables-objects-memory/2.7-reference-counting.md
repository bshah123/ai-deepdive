In this lesson you will predict how many references point at an object, read that number with `sys.getrefcount()`, and watch CPython free an object the moment its count reaches zero. You will also learn why the number you see is one higher than the true count, and why a reference cycle keeps an object alive after its names are gone.

**You need:** names and assignment (Lesson 2.1), and aliasing, where two names share one object (Lesson 2.5).

## The problem reference counting solves

Suppose you write `del o`. Should the object that `o` pointed to be freed? Only if nothing else still uses it. Another name, a list element or an attribute might still hold it. Free it too early and a running program reads freed memory; free it too late and memory piles up. CPython, the reference implementation of Python, answers the question with a count: each object records how many references point at it, and the object is freed when that count reaches zero.

A **reference** here is any pointer that keeps an object alive: a variable name, a slot in a list or dict, an attribute, or an argument held by a running call. Lesson 2.5 showed that `p = o` does not copy the object. It adds one reference.

## Intuition: the count belongs to the object

![Two names, o and p, point at one object whose stored count is 2; a temporary call argument adds one more to the number that sys.getrefcount reports](diagrams/2.7-names-and-count.svg "The count is stored with the object, not with the names.")

The names are cheap labels. The count is a number held by the object itself, so every name added or removed changes it. The rose box is the subtle part: while `sys.getrefcount(o)` runs, its argument is one more reference. The function therefore reports 3 even though only 2 names exist.

## Worked example, by hand

Start with `o = Obj()`. One name holds the new object, so the stored count is 1. Calling `sys.getrefcount(o)` adds a temporary reference, so the reported value is 2. Follow the steps from there:

1. `p = o` adds a name: stored count 2, reported 3.
2. `del p` removes a name: stored 1, reported 2.
3. `lst = [o]` puts the object in a list: stored 2, reported 3.
4. `lst.clear()` empties the list: stored 1, reported 2.
5. `del o` removes the last name: stored 0, and the object is freed.

![Bars show the reported count after each step: 2, 3, 2, 3, 2, then the object is freed](diagrams/2.7-trace.svg "Values from the experiment below. Subtract 1 from a bar to get the stored count.")

Now check every number in Python. The code uses only the standard library (`sys`, `gc`, `weakref`), so it runs in the browser. The `Tracer` class shows the moment `__del__` runs, and the `Node` class shows a cycle.

```python
import sys
import gc
import weakref

class Obj:
    pass

o = Obj()                                    # one name, o, points at the new object
print("after o = Obj():", sys.getrefcount(o))   # counts o plus the getrefcount argument

p = o                                        # second name, same object
print("after p = o:", sys.getrefcount(o))

del p                                        # drop one name; the count goes back down
print("after del p:", sys.getrefcount(o))

lst = [o]                                    # a list element is a reference too
print("after lst = [o]:", sys.getrefcount(o))

lst.clear()                                  # the list releases its element
print("after lst.clear():", sys.getrefcount(o))

class Tracer:
    def __del__(self):
        print("Tracer freed")                # runs when the count reaches zero

t = Tracer()
alias = t
del t
print("del t: still alive, alias holds it")
del alias                                    # count hits zero: __del__ runs now
print("after del alias")

class Node:
    pass

a = Node()
a.self = a                                   # the object refers to itself
watch = weakref.ref(a)                       # a weak reference does not keep the object alive
del a                                        # the name is gone; the self-reference keeps count at 1
print("cycle alive after del:", watch() is not None)
gc.collect()                                 # the cyclic collector finds the unreachable cycle
print("cycle alive after gc.collect():", watch() is not None)
```

```output
after o = Obj(): 2
after p = o: 3
after del p: 2
after lst = [o]: 3
after lst.clear(): 2
del t: still alive, alias holds it
Tracer freed
after del alias
cycle alive after del: True
cycle alive after gc.collect(): False
```

Read the output against the table. Each `print` shows the reported value, so subtract 1 for the stored count. The `del t` line shows that dropping one name does not free an object that another name still holds. The `Tracer freed` line appears only when the last name goes. The weak reference `watch` did not keep the object alive: in the experiment, `weakref` reported the object dead right after the last name was deleted.

## How the count moves

Three operations change the count:

- Binding a name (`p = o`) adds one.
- Dropping a name (`del p`, or rebinding it to something else) subtracts one.
- Putting the object into a container adds one, and removing it subtracts one.

![Flow: a name is dropped, the count goes down by one, and the count is tested for zero. No: the object stays alive. Yes: __del__ runs and the memory is freed](diagrams/2.7-decref-flow.svg "What runs on each decrement.")

`del x` does not call `x.__del__()` directly. It decrements the count, and `__del__` is called only when the count reaches zero (Python Language Reference, data model, `object.__del__`). In the `Tracer` example, `del t` left the object alive because `alias` still held it. `del alias` took the count to zero, and `__del__` printed at that moment.

## The +1 trap

Passing an object to a helper function adds one more reference: the helper's parameter. Run this:

```python
import sys

def rc(o):
    return sys.getrefcount(o)

x = [1, 2, 3]
print("direct:", sys.getrefcount(x))
print("through rc():", rc(x))
```

```output
direct: 2
through rc(): 3
```

The `x` name is the only reference in both calls. Calling directly adds the `getrefcount` argument, so 2. Calling through `rc()` adds the parameter `o` as well, so 3. The `sys.getrefcount` documentation says the count is "generally one higher than you might expect, because it includes the (temporary) reference as an argument to getrefcount()" (Python standard library docs, `sys`).

## Immortal objects: the count stops meaning anything

Some objects have a fixed, very large count. On the CPython 3.12.13 build used for these runs, `sys.getrefcount(None)`, `sys.getrefcount(0)` and `sys.getrefcount(True)` each returned 4294967295 (2 to the power 32, minus 1). PEP 683 introduced immortal objects in Python 3.12. For those objects the runtime no longer changes the count, so it cannot track references. The `sys` documentation says the value "may not actually reflect how many references to the object are actually held", and advises not to rely on it except for the values 0 and 1. The exact number is build-dependent; the lesson is only that a huge count means "immortal", not "many references".

## Cycles: when the count never reaches zero

![Left: a Node refers to itself; no name is left, but the count is 1. Right: the cyclic collector sees it as unreachable and frees it](diagrams/2.7-cycle.svg "A self-reference keeps the count at 1 after the last name is deleted.")

`a = Node()` followed by `a.self = a` gives the object two stored references: the name `a` and its own attribute. Calling `sys.getrefcount(a)` at that point reports 3: two stored references plus the argument. `del a` removes the name, leaving one stored reference from the object to itself. The count never reaches zero, so reference counting alone cannot free it. The output shows the object still alive after `del a` (`True`) and gone after `gc.collect()` (`False`).

The Language Reference states the general rule: "It is possible for a reference cycle to prevent the reference count of an object from going to zero. In this case, the cycle will be later detected and deleted by the cyclic garbage collector." The `gc` documentation says the collector "supplements the reference counting already used in Python". Lessons 2.8 and 2.9 cover the collector and cycles in detail.

## Common traps

> [!TRAP]
> The number from `sys.getrefcount(x)` is one higher than the stored count, because the call itself holds a reference. Passing `x` through a helper adds another one. Compare like with like: use the same call pattern on both sides of a comparison.

> [!TRAP]
> `del x` destroys nothing by itself. It removes one name. The object is freed only when no references remain, and `__del__` runs only at that point.

> [!TRAP]
> A reference cycle keeps its count above zero after every name is gone. Reference counting alone will not free it; only the cyclic collector will.

> [!TRAP]
> Immortal objects (for example `None` on CPython 3.12) report a huge count. Do not use `sys.getrefcount` to decide whether two names share an object. Use `is` (Lesson 2.4).

> [!TRAP]
> The counting rules here describe CPython. The Language Reference calls the cycle behaviour a CPython implementation detail, so code should not depend on exact count values or on when `__del__` runs.

## Summary

- Each CPython object stores a count of references that point at it, and the object is freed when that count reaches zero.
- Binding a name or adding the object to a container adds one. Dropping it subtracts one.
- `sys.getrefcount(x)` reports one more than the stored count, because its own argument is a reference.
- `__del__` runs when the count reaches zero. A reference cycle keeps the count above zero until the cyclic garbage collector runs.
- Immortal objects (Python 3.12 and later) report a huge, fixed count that does not track references.

## Quiz time

### Question 1: Predict the output

```python
import sys

a = [0]
b = a
c = [a]
print(sys.getrefcount(a))
```

<details><summary>Show Solution</summary>

It prints `4`. The references are: the name `a`, the name `b`, the element of the list `c`, and the temporary argument to `getrefcount`. Stored count 3, reported 4.

</details>

### Question 2: Calculation

In the worked example, right after `lst = [o]`, how many references does the object hold, not counting the `getrefcount` argument?

<details><summary>Show Solution</summary>

Two. The name `o` (the name `p` was deleted in step 2) and the list element. The reported value in the trace is 3, which adds the argument.

</details>

### Question 3: Find the wrong expectation

```python
import sys

def count(obj):
    return sys.getrefcount(obj)

x = []
print(count(x))  # the author expects 1
```

<details><summary>Show Solution</summary>

The program prints `3`, and the expectation is wrong. The three references are the name `x`, the parameter `obj`, and the temporary argument to `getrefcount`. The author forgot that the call itself adds two references, so the expectation of 1 is wrong. Nothing in the code is buggy; the printed number is simply the count including those references.

</details>

### Question 4: Explain

In the cycle example, why does `del a` not free the `Node`, and what does free it?

<details><summary>Show Solution</summary>

The object's attribute `self` refers to the object itself, so after the name `a` is removed the count is still 1. Reference counting never reaches zero for this object. The cyclic garbage collector finds the object unreachable from any name and frees it. `gc.collect()` runs that collector on demand.

</details>
