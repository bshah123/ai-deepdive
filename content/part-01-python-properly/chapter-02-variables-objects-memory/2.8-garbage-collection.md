In this lesson you will predict when CPython frees an object without help, explain why a reference cycle survives `del`, and use the `gc` and `weakref` modules to see the cyclic garbage collector (GC) at work.

**You need:** lesson 2.7 (reference counts and `sys.getrefcount()`). The code uses only the standard library. Outputs are from CPython 3.12.13; see the version note near the end.

## The problem

Reference counting frees an object as soon as its count reaches zero (lesson 2.7). That is enough for a chain of objects that only point forward. It is not enough for a cycle. In a cycle, each object holds a reference to another object in the cycle, so no count ever reaches zero, even when your program can no longer reach any of them. A program that creates cycles and drops them would grow without bound. The cyclic GC exists to find and free those unreachable cycles.

![Left: a chain a to b, freed as its names are deleted. Right: a two-object cycle x and y, where each count stays at 1 after the names are deleted.](diagrams/2.8-refcount-vs-cycle.svg "Refcounting frees a chain. It cannot free a cycle.")

## Worked example by hand

Take two objects that point at each other, `x <-> y`. While the names `x` and `y` exist, the count of `x` is 3. One reference comes from the name `x`, one from `y.ref`, and one from the temporary argument of `sys.getrefcount(x)` itself. After `del x, y`, the names are gone, but `y.ref` still holds `x` and `x.ref` still holds `y`. Each count is now 1 and neither reaches zero. Refcounting has nothing left to do.

The code below shows both cases. Garbage collection is switched off so that the cycle is not freed by accident. A `weakref` does not add to the count, so it can tell us whether an object is still alive. The `__del__` method appends the object's name to a log when the object is freed.

```python
import gc
import sys
import weakref

gc.disable()  # switch off the cyclic GC so this demo is deterministic

log = []

class Tracked:
    def __init__(self, name):
        self.name = name
        self.ref = None

    def __del__(self):
        log.append(self.name)

# 1. Acyclic chain a -> b: reference counting frees both.
a = Tracked("a")
b = Tracked("b")
a.ref = b
wb = weakref.ref(b)   # a weak reference does not add to the count
del b
print("after del b, b alive:", wb() is not None)
del a
print("after del a, log:", log, "| b alive:", wb() is not None)

# 2. Cycle x <-> y: reference counting cannot free it.
log.clear()
x = Tracked("x")
y = Tracked("y")
x.ref = y
y.ref = x
wx = weakref.ref(x)
print("refcount of x while the names exist:", sys.getrefcount(x))
del x, y
print("after del, x alive:", wx() is not None, "| log:", log)
found = gc.collect()
print("gc.collect() found", found, "unreachable objects")
print("after collect, x alive:", wx() is not None, "| log:", log)
```

```output
after del b, b alive: True
after del a, log: ['a', 'b'] | b alive: False
refcount of x while the names exist: 3
after del, x alive: True | log: []
gc.collect() found 2 unreachable objects
after collect, x alive: False | log: ['x', 'y']
```

In part 1, `del b` leaves `b` alive because `a.ref` still holds it. `del a` frees `a`; freeing `a` drops its reference to `b`, so `b` is freed next. The log order shows this. In part 2, the two `del` statements free nothing. Only `gc.collect()` frees the pair, and it runs both `__del__` methods while doing so.

The same happens to any cycle, including a ring of three nodes:

```python
import gc
import weakref

gc.disable()

class Node:
    def __init__(self, value):
        self.value = value
        self.next = None

def make_ring():
    n1, n2, n3 = Node(1), Node(2), Node(3)
    n1.next = n2
    n2.next = n3
    n3.next = n1
    return weakref.ref(n1), weakref.ref(n2), weakref.ref(n3)

refs = make_ring()
print("alive after make_ring returns:", [r() is not None for r in refs])
print("gc.collect() found", gc.collect(), "unreachable objects")
print("alive after collect:", [r() is not None for r in refs])
```

```output
alive after make_ring returns: [True, True, True]
gc.collect() found 3 unreachable objects
alive after collect: [False, False, False]
```

`make_ring` has returned, so no local name refers to the nodes. The ring keeps them alive all the same, until the collector runs.

## How the cyclic GC finds cycles

CPython, the reference implementation of Python, runs the cyclic collector alongside reference counting. The `gc` documentation describes three generations, numbered 0 to 2, which hold container objects such as lists, dicts and class instances. New containers are counted against generation 0. The documentation states the trigger rule this way: "When the number of allocations minus the number of deallocations exceeds threshold0, collection starts. Initially only generation 0 is examined. If generation 0 has been examined more than threshold1 times since generation 1 has been examined, then generation 1 is examined as well." `gc.get_threshold()` returns the three numbers, which are `(700, 10, 10)` on 3.12.

![Three boxes from left to right: gen0 (young), collected when allocations minus deallocations exceed 700; gen1, examined when gen0 has run more than 10 times; gen2 (oldest), collected least often. Survivors move right.](diagrams/2.8-generations.svg "Three generations, youngest first")

The idea behind the algorithm is simple. For the generation being examined, the collector subtracts, for each container, the references that come from other containers in the same generation. Whatever keeps a positive count after this step is referenced from outside the generation, so it is reachable, and so is everything it refers to. What is left over is unreachable and can be freed. This is my own description of the idea, not a reading of CPython's source, which I did not open for this lesson.

## Measured: how often collections run

The next block creates lists that stay alive, and counts how many collections of each generation run. A callback in `gc.callbacks` receives a `stop` event after each collection.

```python
import gc

print("thresholds (threshold0, threshold1, threshold2):", gc.get_threshold())

hits = {}

def count_hits(phase, info):
    if phase == "stop":
        g = info["generation"]
        hits[g] = hits.get(g, 0) + 1

for n in (7_000, 70_000, 200_000):
    gc.collect()
    hits.clear()
    gc.callbacks.append(count_hits)
    kept = [[i] for i in range(n)]
    gc.callbacks.remove(count_hits)
    print(f"{n:>7} kept lists: gen0={hits.get(0, 0)} gen1={hits.get(1, 0)} gen2={hits.get(2, 0)}")
    del kept
```

```output
thresholds (threshold0, threshold1, threshold2): (700, 10, 10)
   7000 kept lists: gen0=9 gen1=0 gen2=0
  70000 kept lists: gen0=91 gen1=8 gen2=0
 200000 kept lists: gen0=260 gen1=23 gen2=2
```

Generation 0 ran 260 times for 200,000 lists. The naive estimate, 200,000 / 700 ≈ 286, is close but not equal. I did not find out why the difference exists. Generation 1 ran about once for every ten generation 0 runs, as the rule predicts. The `gc` documentation does not state the trigger for generation 2, so this lesson makes no claim about it beyond the counts measured here.

![Bar chart of collections for 7,000, 70,000 and 200,000 live lists. Generation 0 bars are 9, 91 and 260; generation 1 bars are 0, 8 and 23; generation 2 bars are 0, 0 and 2.](diagrams/2.8-collections.svg "Collections while N containers stay alive (CPython 3.12.13)")

## Measured: memory stays bounded

Here the program makes 100,000 two-object cycles, first with the cyclic GC off and then on. Each cycle is dropped at the end of its loop iteration.

```python
import gc

live = 0

class Tracked:
    def __init__(self):
        global live
        live += 1
        self.ref = None

    def __del__(self):
        global live
        live -= 1

def run(n_cycles):
    global live
    live = 0
    peak = 0
    for _ in range(n_cycles):
        p, q = Tracked(), Tracked()
        p.ref, q.ref = q, p   # two-object cycle, dropped every iteration
        del p, q
        peak = max(peak, live)
    return peak, live

gc.disable()
peak, end = run(100_000)
print("gc disabled: peak live", peak, "| live at end", end)
gc.enable()
gc.collect()
peak, end = run(100_000)
print("gc enabled: peak live", peak, "| live at end", end)
```

```output
gc disabled: peak live 200000 | live at end 200000
gc enabled: peak live 762 | live at end 278
```

With the collector off, all 200,000 objects stay alive, so the program's memory grows with every iteration. With the collector on, the peak was 762. The peak depends on how many other container objects are alive at the time, so this is one run, not a fixed property. The count stays bounded because generation 0 is collected each time allocations minus deallocations pass 700. Each collection frees the cycles that are already unreachable.

![Two bars. A tall bar labelled 200,000 live shows gc disabled. A very short bar labelled peak 762 shows gc enabled.](diagrams/2.8-bounded-memory.svg "Live objects after 100,000 two-object cycles, GC off vs on")

> [!NOTE]
> The numbers in this lesson come from CPython 3.12.13. Python 3.14.0 to 3.14.4 shipped an incremental collector, which the 3.14 release notes say was reverted in 3.14.5 to the generational collector of 3.13. The `gc` documentation also says that `threshold2` is ignored in 3.14 and "restored to match Python 3.13 behavior" in 3.14.5. Check your version before you quote a threshold.

## Common traps

> [!TRAP]
> **`del` does not free a cycle.** Deleting the names only lowers the counts. In the first demo the log stays empty after `del x, y`. Only the collector frees the pair.

> [!TRAP]
> **`gc.disable()` switches off only cycle collection.** Refcounting still frees chains at once (part 1 of the first demo). Cycles are what pile up, as the 200,000 live objects in the last demo show.

> [!TRAP]
> **`__del__` in a cycle runs when the collector runs, not at `del`.** The log in the first demo is empty after `del`. PEP 442 (Python Enhancement Proposal 442) made objects with `__del__` collectable in cycles from Python 3.4. The finalizer runs during the collection, as the log shows.

> [!TRAP]
> **`gc.collect()` counts every unreachable object, not only yours.** In a script that calls `gc.disable()` and then `gc.collect()` as its first collection, the call returned 32 in my run, before the script made any cycle. Read the returned number as "objects found", not "bytes freed". The `gc` documentation defines it as the sum of collected and uncollectable objects.

> [!TRAP]
> **Do not treat thresholds as constant.** The `(700, 10, 10)` default is for 3.12 here. The version note above lists the changes in 3.14.

## Summary

- Refcounting frees acyclic garbage as soon as the last reference goes. It cannot free a cycle, because every object in the cycle keeps a positive count.
- The cyclic GC examines generations, youngest first. On 3.12 a generation 0 collection starts when allocations minus deallocations exceed 700.
- `gc.collect()` forces a collection and returns the number of unreachable objects it found, including ones unrelated to your code.
- With the collector disabled, the cycles in the last demo stayed alive, 200,000 of them. With it enabled, the peak was 762.

## Quiz time

### Question 1: Calculation

Three nodes form a ring `a -> b -> c -> a`. You delete the names `a`, `b` and `c`, and no collection has run. What is the reference count of `b` now, ignoring temporary references? Why can refcounting never free it?

<details><summary>Show Solution</summary>

The count is 1. Only `a.next` refers to `b`. The count never reaches zero, because `b` is referenced from inside the ring, and the same is true of `c` and `a`. Only the cyclic collector can free the ring.

</details>

### Question 2: Prediction

With the collector disabled, your program runs a loop 1,000 times. Each pass creates `a = Node()` and `b = Node()`, sets `a.next = b`, and rebinds the names `a` and `b` on the next pass. No `next` reference points back to `a`. How many of the 2,000 objects are still alive after the loop, other than the last pair held by the names?

<details><summary>Show Solution</summary>

None. There is no cycle, so each rebinding drops the previous `a`, which frees the previous `b` as well. Refcounting frees each pass at once, and `gc.disable()` does not change that. Only the last pair remains, held by the names.

</details>

### Question 3: Find the bug

```python
import gc
gc.disable()  # "saves time during the loop"

class Job:
    def __init__(self):
        self.me = self  # a one-object cycle

def run():
    for _ in range(1_000_000):
        Job()

run()
```

<details><summary>Show Solution</summary>

Each `Job` refers to itself, so its count never reaches zero. With `gc.disable()`, the collector never frees these objects, and memory grows with every iteration. The fix is to remove the self-reference, or to leave the collector enabled. If the object must refer to itself, call `gc.collect()` after the loop, or use `weakref` for the self-reference.

</details>

### Question 4: Explanation

In the first demo, why is `wx()` still alive after `del x, y`, but `wb()` is dead after `del a`?

<details><summary>Show Solution</summary>

`b` was in a chain. Deleting `a` dropped its count to zero, which freed `a`, and that freed `b`. `x` is in a cycle. Its count stays at 1, held by `y.ref`, so refcounting cannot free it until `gc.collect()` runs.

</details>
