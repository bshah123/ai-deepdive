After this lesson you will be able to build a reference cycle, predict which objects survive `del`, use a weak reference to break a cycle, and measure what cycles cost in memory. Everything here runs on CPython 3.12 (the standard Python interpreter) with the standard library only.

**You need:** reference counting (Lesson 2.7) and the cyclic garbage collector (Lesson 2.8).

## The problem a cycle creates

Reference counting frees an object the moment its count reaches zero (Lesson 2.7). A **reference cycle** is a loop of objects that point at each other. Each object in the loop keeps a count of at least one, so the count never reaches zero, even after the program has no name left for any of them.

![Two Node objects that point at each other. The names a and b are deleted, but each object still has refcount 1 from its partner.](diagrams/2.9-cycle-after-del.svg "Deleting both names leaves two live objects, each kept alive by the other.")

Each diagram box is one object, and the arrows are attributes. Nothing outside the loop refers to either object, so the program can never reach them again. Reference counting alone cannot see that. Python's cyclic garbage collector can, so a cycle delays the reuse of memory; it does not corrupt anything.

## Worked example, by hand

Start with two objects and two names, `a` and `b`:

- `a` has two references: the name `a` and the attribute `b.other`. Refcount 2.
- `b` has two references: the name `b` and the attribute `a.other`. Refcount 2.

Now `del a, b`. The names go away, and each object keeps the reference from its partner, so each refcount drops to 1 and neither reaches zero. A reference count also includes the temporary argument reference that `sys.getrefcount()` makes, so the code below subtracts 1. That offset is the first thing that trips people up.

The collector asks a different question: is any reference coming from outside the group of objects? Its working value is `gc_refs`, which starts at the reference count. For each reference that comes from another object in the group, it subtracts 1. My summary of the rule, which I did not check against CPython's source:

- While the names exist: refcount 2, internal references 1, so `gc_refs` = 2 − 1 = 1. The name is an outside reference, so the pair is reachable.
- After `del`: refcount 1, internal references 1, so `gc_refs` = 1 − 1 = 0. Nothing outside the group refers to either object, so both are garbage.

![Two panels. While names a and b exist, refcount 2, internal 1, gc_refs 1: reachable. After del, refcount 1, internal 1, gc_refs 0: unreachable, freed by gc.collect().](diagrams/2.9-gc-refs-worked.svg "The same cycle before and after the names are deleted, using the gc_refs rule.")

## Code: watch a cycle survive `del`

The block below uses `gc.disable()` so that the collector cannot run on its own. Otherwise the cycle might be freed at a moment you did not choose.

```python
import gc
import sys
import weakref

class Node:
    def __init__(self, name):
        self.name = name
        self.other = None

    def __repr__(self):
        return f"Node({self.name})"

gc.disable()                        # keep automatic collection out of this demo

a = Node("a")
b = Node("b")
a.other = b                         # a -> b
b.other = a                         # b -> a: now a cycle

print("refcount(a) while names exist:", sys.getrefcount(a) - 1)
ra = weakref.ref(a, lambda _: print("callback: a freed"))
rb = weakref.ref(b, lambda _: print("callback: b freed"))

del a, b                            # drop both names
print("after del: a alive?", ra() is not None, "| b alive?", rb() is not None)

print("gc.collect() found", gc.collect(), "unreachable objects")
print("after gc.collect(): a alive?", ra() is not None, "| b alive?", rb() is not None)
gc.enable()
```

```output
refcount(a) while names exist: 2
after del: a alive? True | b alive? True
callback: a freed
callback: b freed
gc.collect() found 2 unreachable objects
after gc.collect(): a alive? False | b alive? False
```

The `weakref.ref` objects do not count as references. They let us ask whether an object is still alive, and they run a callback when it is freed. The callbacks fire during `gc.collect()`, not at `del`. `gc.collect()` returns the number of unreachable objects it found (Python documentation, `gc` module). Here it is 2: the two `Node` objects.

## Weakref breaks the cycle

A tree is the common case. A child needs to find its parent, but a parent that holds its child and a child that holds its parent form a cycle. The fix is to make the back-pointer a weak reference. The weak reference lets the child reach the parent while the parent's count depends only on the parent's owners.

![Left: a strong parent pointer forms a loop, and both counts stay above zero after del. Right: a weakref back-pointer, dashed, so the root is freed at once.](diagrams/2.9-strong-vs-weakref.svg "A strong back-pointer makes a cycle; a weak one does not.")

```python
import weakref

class TNode:
    def __init__(self, name):
        self.name = name
        self.children = []
        self._parent = None

    @property
    def parent(self):
        return self._parent() if self._parent is not None else None

    def add(self, child):
        child._parent = weakref.ref(self)   # back-pointer does not count as a reference
        self.children.append(child)

root = TNode("root")
leaf = TNode("leaf")
root.add(leaf)
print("leaf.parent before:", leaf.parent.name)
del root                                     # no cycle: root is freed at once
print("leaf.parent after del root:", leaf.parent)
print("trap check, weakref to a temporary:", weakref.ref(TNode("x"))())
```

```output
leaf.parent before: root
leaf.parent after del root: None
trap check, weakref to a temporary: None
```

Here `del root` frees the root immediately, with no collector involved. The leaf reads `None` for its parent, which is the behaviour a weak reference promises: it does not keep its target alive (Python documentation, `weakref` module).

## Under the hood: what the collector does

The collector does not need to search for loops. It works on the groups of container objects that Python tracks, which include class instances and lists. For each group it computes `gc_refs` as above. In my reading (see References), objects whose `gc_refs` stays above zero are reachable from outside, and everything reachable from them is kept. The rest is garbage. The worked example in the earlier section is the two-object case of this rule.

Two facts from this lesson are checked against running code rather than the source. First, with `gc.set_debug(gc.DEBUG_SAVEALL)` the unreachable objects are kept in `gc.garbage` instead of freed; my test found two `Node` objects there, which matches the cycle. Second, a cycle that holds only lists is collected too: `gc.collect()` returned 2 for a two-list cycle in my experiment (`scripts/diagrams/lessons/2.9_experiment.py`, section 2).

## Cost: what a cycle holds in memory

Collection runs in generations, and the thresholds control how often each one is examined. The Python documentation describes `gc.set_threshold()` and `gc.get_threshold()`, but it does not state the defaults, so the tuple below is what this build reports.

The block below allocates 10,000 pairs and drops them. It measures the bytes still held, using `tracemalloc` (the standard memory tracer).

```python
import gc
import tracemalloc

class Node:
    def __init__(self, name):
        self.name = name
        self.other = None

N = 10_000

def make_acyclic(n):
    for _ in range(n):
        a = Node("a")
        b = Node("b")
        a.other = b                 # one-way reference: no cycle

def make_cycles(n):
    for _ in range(n):
        a = Node("a")
        b = Node("b")
        a.other = b
        b.other = a                 # two-way reference: a cycle

def held_bytes(fn, gc_on):
    gc.collect()
    gc.enable() if gc_on else gc.disable()
    tracemalloc.start()
    base = tracemalloc.get_traced_memory()[0]
    fn(N)
    held = tracemalloc.get_traced_memory()[0] - base
    tracemalloc.stop()
    gc.enable()
    gc.collect()
    return held

print("gc.get_threshold():", gc.get_threshold())
print("acyclic pairs, gc off:", held_bytes(make_acyclic, False), "bytes")
print("cycles,  gc off:", held_bytes(make_cycles, False), "bytes")
print("cycles,  gc on :", held_bytes(make_cycles, True), "bytes")
```

```output
gc.get_threshold(): (700, 10, 10)
acyclic pairs, gc off: 104 bytes
cycles,  gc off: 1600104 bytes
cycles,  gc on : 31944 bytes
```

![Bar chart of bytes still held after 10,000 pairs: acyclic with gc off 104 bytes, cycles with gc off 1,600,104 bytes, cycles with gc on 31,944 bytes.](diagrams/2.9-held-bytes.svg "Bytes still held after 10,000 pairs are dropped, by GC setting.")

Without the collector, 10,000 cycles hold about 1.6 MB, or about 160 bytes per pair. With the collector on, the same loop holds 31,944 bytes, because the collector reclaims cycles as it goes. The residue is most likely the pairs created since the last automatic collection. These byte counts come from one CPython 3.12 build, and they depend on the build and on the order of earlier allocations. Another run in the same session gave a slightly different figure for the collector-on case, which is why the lesson quotes only the block output above.

## Common traps

> [!TRAP]
> `del x` does not necessarily free `x`. It removes one name. An object is freed when its count reaches zero, and a cycle keeps every member's count above zero until the collector runs.

> [!TRAP]
> `gc.disable()` is not a fix. It only postpones the work. In the measurement above, turning the collector off held about 50 times the bytes of the collector-on run.

> [!TRAP]
> A weak reference is not a substitute for ownership. An object that is referenced only weakly is freed at once, as the `TNode("x")` check showed. Keep one strong owner for every object you need.

> [!TRAP]
> Since Python 3.4, objects with a `__del__` method inside a cycle are collected, as PEP (Python Enhancement Proposal) 442 describes. Before that, such cycles could not be collected at all, so check `__del__` code paths in older projects.

> [!TRAP]
> Do not read the `getrefcount` value as exact. `sys.getrefcount()` counts its own argument, and a function parameter adds another reference. Measure from the call site and subtract 1, as the code above does.

## Summary

- A reference cycle is a loop of objects that keep each other's counts above zero, so reference counting alone never frees them.
- The cyclic collector finds cycles by subtracting internal references from each object's count (my reading of the rule); objects with nothing outside the group left are freed by `gc.collect()`.
- A weak reference, such as a child's pointer to its parent, does not keep its target alive, so it breaks the cycle and frees the target at `del`.
- Without the collector, a cycle holds its memory indefinitely; the measured cost was about 160 bytes per pair for this build.
- Use `gc.collect()` to find cycles in tests and use weak back-pointers in the design, rather than disabling the collector.

### Question 1: Predict the refcount

```python
import sys

class Node:
    def __init__(self, name):
        self.name = name
        self.other = None

x = Node("x")
y = Node("y")
y.other = x
print(sys.getrefcount(x) - 1)
```

<details><summary>Show Solution</summary>

The output is `2`. The name `x` is one reference, and `y.other` is a second. The `- 1` removes the temporary reference that `sys.getrefcount()` takes for its own argument.

</details>

### Question 2: Will this be freed?

A student writes this and expects `del parent` to free the parent:

```python
class Node:
    def __init__(self, name):
        self.name = name
        self.parent = None
        self.children = []

parent = Node("parent")
child = Node("child")
child.parent = parent
parent.children.append(child)
del parent
```

<details><summary>Show Solution</summary>

No, not at once. `child.parent` and `parent.children` are both strong references, so the two objects form a cycle. After `del parent`, the parent still has a count of 1 from `child.parent`. It is freed only by the collector (`gc.collect()`), or at interpreter exit. The fix is to make `child.parent` a `weakref.ref(parent)`, as in the code block above.

</details>

### Question 3: Calculate gc_refs

Three objects form a ring: `a.other = b`, `b.other = c`, `c.other = a`. The name `a` is still bound, and `b` and `c` have no other names. Give the refcount, the internal references, and the `gc_refs` of each object, and say whether the collector frees anything.

<details><summary>Show Solution</summary>

| Object | Refcount | Internal references | gc_refs |
|---|---|---|---|
| a | 2 (name a, c.other) | 1 (from c) | 1 |
| b | 1 (from a.other) | 1 (from a) | 0 |
| c | 1 (from b.other) | 1 (from b) | 0 |

Only `a` has an outside reference, so the group stays reachable and nothing is freed. The refcounts and internal counts follow from the references in the code; the collector's treatment of the group is my reading of the rule above.

</details>

### Question 4: Explain the memory numbers

The cost block reports 1,600,104 bytes with the collector off and 31,944 bytes with it on. Explain why the two numbers differ, and say what the 31,944 bytes are.

<details><summary>Show Solution</summary>

With the collector off, nothing reclaims cycles, so all 10,000 pairs are still held (about 160 bytes each). With it on, the collector runs as allocations cross its threshold and frees the earlier cycles. The 31,944 bytes are most likely the pairs created since the last automatic collection, which the collector has not yet examined.

</details>
