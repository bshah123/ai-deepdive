By the end of this lesson you will be able to count one string three ways (code points, UTF-8 bytes and UTF-16 units), predict what `s += t` does to other names that point at `s`, and explain why two equal strings are sometimes the same object and sometimes not.

**You need:** object identity and the `is` operator (Lessons 2.3 and 2.4). The identity results below are CPython 3.12 behaviour, not language guarantees.

## The problem: how long is a string?

The word *café* can be stored two ways. In one, the accented letter is a single character. In the other, the letter *e* is followed by a separate combining accent. Both print the same, but they have different lengths.

![Four strings with their code point, UTF-8 byte and UTF-16 unit counts: café in NFC has 4, 5 and 4; café in NFD has 5, 6 and 5; one emoji has 1, 4 and 2; a family emoji has 5, 18 and 8](diagrams/3.3-code-points.svg "The same text has different counts depending on what you measure.")

`len()` counts **code points**, the numbers that Unicode (the standard that assigns a number to every character) defines. Files and networks count **bytes**, which depend on an **encoding**, a rule for turning code points into bytes. Python 3 strings are sequences of code points, and each count answers a different question.

Here is the same measurement in code:

```python
import unicodedata

samples = {
    "café (NFC: one code point for é)": "café",
    "café (NFD: e plus combining accent)": "café",
    "one emoji": "\U0001F600",
    "family emoji (ZWJ sequence)": "\U0001F468‍\U0001F469‍\U0001F467",
}
print(f"{'text':36} {'code points':>11} {'UTF-8 bytes':>11} {'UTF-16 units':>12}")
for name, text in samples.items():
    print(f"{name:36} {len(text):>11} {len(text.encode('utf-8')):>11} {len(text.encode('utf-16-le')) // 2:>12}")

nfc, nfd = "café", "café"
print("NFC == NFD:", nfc == nfd)
print("normalize(NFD) == NFC:", unicodedata.normalize("NFC", nfd) == nfc)
```

```output
text                                 code points UTF-8 bytes UTF-16 units
café (NFC: one code point for é)               4           5            4
café (NFD: e plus combining accent)            5           6            5
one emoji                                      1           4            2
family emoji (ZWJ sequence)                    5          18            8
NFC == NFD: False
normalize(NFD) == NFC: True
```

The two spellings of *café* are different strings. `unicodedata.normalize` converts one to the other (Normalization Form C (NFC) is the one with precomposed characters, and Normalization Form D (NFD) splits them). Compare user text after normalizing it, or the same word will fail to match. In the family emoji, ZWJ (zero-width joiner, U+200D) is an invisible code point that joins the people into one emoji sequence.

## Code points and UTF-8 bytes

**UTF-8** (Unicode Transformation Format, 8-bit) is the encoding used by most files and web pages. It uses one byte for code points below 128 (plain ASCII, the American Standard Code for Information Interchange) and up to four bytes for the rest. RFC (Request for Comments) 3629 fixes the bit patterns: a one-byte code point starts with `0`, a two-byte one with `110`, a three-byte one with `1110`, and a four-byte one with `11110`. Every continuation byte starts with `10`, so a decoder can always find where a character starts.

Here is the encoding worked by hand for `é` (U+00E9, which is 233 in decimal):

1. 233 is between 128 and 2047, so UTF-8 uses two bytes, shaped `110xxxxx 10xxxxxx`: 11 payload bits.
2. 233 in 11 bits is `000 1110 1001`, which splits into `00011` and `101001`.
3. Fill the pattern: `110` + `00011` = `11000011` = `C3`; `10` + `101001` = `10101001` = `A9`.

The emoji U+1F600 has 21 payload bits, `000 011111 011000 000000`, which give `F0 9F 98 80`.

![The three characters é, 世 and 😀 with their code points, UTF-8 bytes: C3 A9 (2 bytes), E4 B8 96 (3 bytes), F0 9F 98 80 (4 bytes), total 9 bytes and 4 UTF-16 units](diagrams/3.3-worked-bytes.svg "Each code point becomes one to four bytes, and the lead byte says how many.")

The code below reproduces the hand result and adds a second encoding, so you can see that the byte count is a property of the encoding:

```python
text = "é世\U0001F600"   # é, 世, 😀
for ch in text:
    b = ch.encode("utf-8")
    print(f"U+{ord(ch):04X}  {b.hex(' '):>12}  ({len(b)} bytes)")
print("total UTF-8 bytes:", len(text.encode("utf-8")))
print("latin-1 bytes for é:", len("é".encode("latin-1")))
try:
    "é".encode("ascii")
except UnicodeEncodeError as err:
    print("ascii fails:", type(err).__name__)
```

```output
U+00E9         c3 a9  (2 bytes)
U+4E16      e4 b8 96  (3 bytes)
U+1F600   f0 9f 98 80  (4 bytes)
total UTF-8 bytes: 9
latin-1 bytes for é: 1
ascii fails: UnicodeEncodeError
```

UTF-16 (16-bit Unicode Transformation Format) is the third count. It uses one 16-bit unit for each code point up to U+FFFF and a pair of units (a surrogate pair) above it, which is why the emoji has 2 UTF-16 units and 1 code point. Python's own `len()` never reports units; the number appears only when you encode the text for a system that uses UTF-16, such as some Windows APIs and JavaScript strings.

## Strings are immutable

A Python `str` cannot be changed in place. Trying to do so raises an error, and `+=` builds a new object. The old name keeps pointing at the old object.

```python
s = "Hello"
try:
    s[0] = "J"
except TypeError as err:
    print("TypeError:", err)

t = s
s += ", world"
print("s:", s)
print("t:", t)
print("s is t:", s is t)

b = bytearray(b"Hello")
b[0] = ord("J")
print("bytearray:", b.decode())
```

```output
TypeError: 'str' object does not support item assignment
s: Hello, world
t: Hello
s is t: False
bytearray: Jello
```

![Before t = s, names s and t both point to the object "Hello". After s += ", world", s points to a new object "Hello, world" while t still points to "Hello"](diagrams/3.3-rebind.svg "Augmented assignment rebinds the name; it does not edit the object.")

Immutability is what makes strings safe to share as dictionary keys and function arguments. A `bytearray` is the mutable alternative: its `b[0] = ...` edits the object that every name sees.

## Memory: one width per string

CPython, the reference implementation of Python, does not store every string as UTF-32. PEP (Python Enhancement Proposal) 393, Flexible String Representation, chooses one width for the whole string, based on its widest character: 1 byte per character if every character is in Latin-1 (the first 256 code points, which includes ASCII), 2 bytes if the widest is in the Basic Multilingual Plane (code points up to U+FFFF), and 4 bytes otherwise.

The per-character cost shows up when you measure:

```python
import sys

for name, ch in [("ASCII", "a"), ("Latin-1", "é"), ("BMP", "世"), ("astral", "\U0001F600")]:
    per_char = sys.getsizeof(ch * 2000) - sys.getsizeof(ch * 1000)
    print(f"{name:8} {per_char // 1000} byte(s) per character")
```

```output
ASCII    1 byte(s) per character
Latin-1  1 byte(s) per character
BMP      2 byte(s) per character
astral   4 byte(s) per character
```

The absolute sizes on the 64-bit CPython 3.12 build I measured (macOS) were 1041 bytes for 1000 ASCII characters, 1057 for 1000 Latin-1 characters, 2058 for 1000 BMP characters and 4060 for 1000 astral characters. An empty string takes 41 bytes. These absolute numbers vary with build and platform, so treat the per-character widths as the stable fact.

![Bar chart of bytes for a 1000-character string by widest character: ASCII 1041, Latin-1 1057, BMP 2058, astral 4060](diagrams/3.3-flexible-width.svg "The widest character sets the width of every character.")

One consequence: a single emoji in a long text quadruples the memory for the whole string. A string of 999 BMP characters plus one ASCII letter costs as much as 1000 BMP characters, because the width is set by the widest character.

## String interning: one object per value

**Interning** means keeping one shared object for each distinct value. The `sys` module documents the operation: `sys.intern(string)` enters the string in "the table of 'interned' strings and return[s] the interned string – which is string itself or a copy". Interning helps dictionary lookups because keys that are interned can be compared by pointer.

CPython also interns some strings for you, mainly the names in source code. Two cases differ, and the code below shows which:

```python
import sys

def f():
    return "hello world"

def g():
    return "hello world"

def h():
    return "hello " + "world"

print("f() is g():", f() is g())
print("h() is f():", h() is f())
print("'hello world' is a constant of h:", "hello world" in h.__code__.co_consts)

ns1, ns2 = {}, {}
exec(compile("def f():\n    return 'hello world'\n", "<one>", "exec"), ns1)
exec(compile("def f():\n    return 'hello world'\n", "<two>", "exec"), ns2)
print("two compile() calls, f() is f():", ns1["f"]() is ns2["f"]())

joined = "".join(["hello", " world"])
print("joined is f():", joined is f())
print("sys.intern(joined) is f():", sys.intern(joined) is f())
print("sys.intern(joined) is sys.intern('hello world'):", sys.intern(joined) is sys.intern("hello world"))

hello = "hello"
built = "".join(["hel", "lo"])
print("built is hello:", built is hello)
print("sys.intern(built) is hello:", sys.intern(built) is hello)
```

```output
f() is g(): True
h() is f(): True
'hello world' is a constant of h: True
two compile() calls, f() is f(): False
joined is f(): False
sys.intern(joined) is f(): False
sys.intern(joined) is sys.intern('hello world'): True
built is hello: False
sys.intern(built) is hello: True
```

![Seven identity checks with the object layout and the measured result for each: literal sharing within one module is True, two compile calls is False, constant folding is True, runtime join is False, sys.intern of a runtime string is False against the literal, identifier-like string is False before sys.intern and True after](diagrams/3.3-identity.svg "Identity depends on how the string was made.")

Read the rows as follows.

- `f() is g()` is True because both functions were compiled in the same module, and the compiler appears to share equal constants within one compilation unit. Two separate `compile()` calls do not share them (the fourth line). This is a compiler detail, so do not rely on it.
- `h() is f()` is True because the compiler folds `"hello " + "world"` into one constant at compile time.
- Strings built at run time are new objects. `sys.intern(joined)` returns the table's entry for the value, but the table does not hold `f()`'s literal, so the answer is False.
- `built is hello` is False, but `sys.intern(built) is hello` is True. Here the literal `"hello"` is an identifier-like constant, and the value is already in the table, so `sys.intern` returns that same object.

> [!ADVANCED]
> Everything in the last block is observed behaviour on CPython 3.12 (measured in this lesson's experiment script), not a documented rule. Literals in one module shared an object even with a space in them, but `sys.intern()` did not return that object: the intern table is a separate structure. Identifier-like literals (`"hello"`) were already in the table, which is why `sys.intern(built) is hello` is True. Single Latin-1 characters also came back as shared objects: `"".join(["a"])` was the same object as a variable holding `"a"`. Check the CPython source before you depend on any of this.

## Common traps

> [!TRAP]
> `is` tests identity, not value. Use `==` to compare text. `if name is "admin":` works only when the two strings happen to be the same object.

> [!TRAP]
> `len(s)` counts code points, not bytes. A file of `s.encode("utf-8")` can be several times longer than `len(s)` for CJK (Chinese, Japanese and Korean) text or emoji.

> [!TRAP]
> Two strings that print the same can be unequal. Normalize user input (for example with `unicodedata.normalize("NFC", s)`) before comparing or using it as a key.

> [!TRAP]
> `s += t` does not change other names bound to `s`. If another list or dictionary holds the old value, it still holds the old value.

> [!TRAP]
> One astral character (code point above U+FFFF) makes every character in its string 4 bytes wide. Measure memory with `sys.getsizeof`, and keep in mind that it counts only the string object.

## Summary

- A string is a sequence of Unicode code points. `len()` counts code points, while files and networks count bytes produced by an encoding such as UTF-8.
- UTF-8 uses 1 to 4 bytes per code point. The lead byte tells the decoder how many bytes follow (RFC 3629).
- A `str` is immutable. Operations such as `+=` create a new object and rebind the name, so other names keep the old value.
- CPython stores each string at the width of its widest character: 1, 2 or 4 bytes per character (PEP 393).
- `is` compares identity. Equal strings may or may not be the same object, so use `==` for values and `sys.intern()` only when you need the shared-object guarantee for dictionary keys.

## Quiz time

### Question 1: Calculation

The word *naïve* is spelled with the code point U+00EF for *ï*. How many code points, UTF-8 bytes and UTF-16 units does it have?

<details><summary>Show solution</summary>

It has 5 code points (n, a, ï, v, e), 6 UTF-8 bytes (ï takes 2 and each other letter takes 1), and 5 UTF-16 units (each code point is below U+FFFF). The values match a run of `len("naïve")`, `len("naïve".encode("utf-8"))` and `len("naïve".encode("utf-16-le")) // 2`.

</details>

### Question 2: Prediction

```python
t = "Hello"
s = t
s += "!"
print(t)
```

<details><summary>Show solution</summary>

It prints `Hello`. The `+=` builds a new string and rebinds `s` to it. `t` still refers to the original object, which was never changed.

</details>

### Question 3: Bug-spotting

```python
def is_admin(role):
    return role is "admin"
```

<details><summary>Show solution</summary>

`is` compares identity. A role read from user input is a new object, so `is` returns False even for the text "admin". Use `role == "admin"`. The bug is hard to see because a literal typed in the same source file often looks like it works.

</details>

### Question 4: Explanation

Why does `sys.intern()` help dictionary lookups, and why does it not replace `==`?

<details><summary>Show solution</summary>

Dictionary lookups first compare hashes and then compare keys. If both keys are interned, the comparison can succeed on identity, which is a pointer comparison, instead of comparing characters. `sys.intern()` does not change what equality means: `==` still compares values, and two equal strings that were never interned are simply different objects that compare equal.

</details>
