By the end of this lesson you will be able to say which integers CPython (the standard C implementation of Python) shares between uses, predict when `is` gives a surprising answer, and measure what the sharing saves.

**You need:** integers are objects (Lesson 3.1) and the difference between `is` and `==` (Lesson 2.4).

## The problem the cache solves

Every integer in Python is an object. Making one means allocating memory; dropping it means freeing that memory. Programs produce the same small values again and again: loop counters, flags, indices. CPython avoids most of that work for a fixed range of values. It keeps one ready-made object per value in that range and returns that same object every time the value is needed at run time.

## Intuition: a shelf of shared objects

![A number line from -10 to 299: the band from -5 to 256 is shared at run time, values outside it are new objects each time](diagrams/3.5-number-line.svg "The cache covers -5 to 256. Rose values are not cached.")

The shaded band is the cache. It holds 262 values: $-5$ to $256$ inclusive. Count by hand: $256 - (-5) + 1 = 262$. The window $[-10, 300)$ holds $310$ values, so $310 - 262 = 48$ values lie outside the band: $-10$ to $-6$ (five values) and $257$ to $299$ (43 values).

## Run-time values: test the boundary

The function below builds each value twice at run time, so the two objects cannot come from the same constant in the source file.

```python
def same_object(v):
    # int(str(v)) builds a new value at run time, so the compiler cannot share it.
    return int(str(v)) is int(str(v))

for v in [-6, -5, 0, 256, 257, 300]:
    print(v, same_object(v))

shared = sum(same_object(v) for v in range(-10, 300))
print("shared:", shared, "of", 310)
```

```output
-6 False
-5 True
0 True
256 True
257 False
300 False
shared: 262 of 310
```

The output matches the hand count: 262 of the 310 values are shared, and the boundaries are exactly $-5$ and $256$.

## Literal constants follow different rules

A number written in the source, such as `300`, is a *literal*. The compiler stores each literal once in a table of constants for the file it is compiling. Two functions in one file that both return `300` therefore return the same object. Two separate `compile()` calls keep separate tables.

```python
def f():
    return 300

def g():
    return 300

print("one file:", f() is g())

source = "def k():\n    return 300\n"
ns1, ns2 = {}, {}
exec(compile(source, "<first>", "exec"), ns1)
exec(compile(source, "<second>", "exec"), ns2)
print("two compile() calls:", ns1["k"]() is ns2["k"]())
```

```output
one file: True
two compile() calls: False
```

![Two side-by-side panels: one file with two functions that both return 300 share one object; two compile calls of the same text give two objects](diagrams/3.5-same-file.svg "Where the constant 300 lives. The answer depends on the compilation, not only on the values.")

The Python Language Reference says that identical literals "may obtain the same object or a different object with the same value", and it labels the CPython behaviour as an implementation detail (Python Software Foundation, Language Reference, §6.2.3.1). The rule for when CPython shares them is a compiler detail. Do not rely on it.

> [!TRAP]
> Do not predict `is` results from the source text. Two `300` literals in the same file can be the same object; the same text compiled in another call may not be.

## Why the cache matters: memory

Each int object takes 28 bytes on 64-bit CPython 3.12. Larger values take more: 40 bytes for $2^{100}$, which needs more digits.

```python
import sys

print(sys.getsizeof(1), sys.getsizeof(10**9), sys.getsizeof(2**100))
print(1_000_000 * sys.getsizeof(1), "bytes for 1,000,000 int objects of this size")
```

```output
28 28 40
28000000 bytes for 1,000,000 int objects of this size
```

![Two bars: a list of one million cached ints takes 8.4 MB; a list of one million distinct ints takes 36.4 MB, 28 MB more for the objects](diagrams/3.5-memory.svg "The list's own pointer array is 8.4 MB in both cases. The difference is the int objects.")

Building one million-element lists with `tracemalloc` (standard library memory tracer) shows the same gap. The code is in the block below; its values are rounded to megabytes because exact byte counts vary a little between runs.

<details><summary>Run locally: standard library only, output measured on CPython 3.12.13</summary>

```python
import tracemalloc

N = 1_000_000

def build_cached():
    # 256 distinct values, cycled: every value is in the cache (0..255).
    return [int(str(i % 256)) for i in range(N)]

def build_fresh():
    # 1,000,000 distinct values: each one is a new int object.
    return [int(str(1000 + i)) for i in range(N)]

def peak_mb(build):
    tracemalloc.start()
    data = build()
    current, _ = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    del data
    return round(current / 1e6, 1)

print("cached MB:", peak_mb(build_cached), " fresh MB:", peak_mb(build_fresh))
```

Output on CPython 3.12.13: `cached MB: 8.4  fresh MB: 36.4`

</details>

The cached list is about 8.4 megabytes (MB) and the fresh list about 36.4 MB. The 28 MB gap is the one million int objects.

## Speed: a hit is cheaper, but only a little

Returning an existing object saves an allocation (reserving memory for a new object). It does not save the addition. The code below times `a + 1` for a result inside the cache and one outside it.

<details><summary>Run locally: standard library only; timings depend on your machine</summary>

```python
import statistics
import timeit

def ns_per_add(a):
    runs = timeit.repeat("a + 1", globals={"a": a}, number=2_000_000, repeat=7)
    return statistics.median(runs) / 2_000_000 * 1e9  # nanoseconds per operation

print("a = 255 (result 256, cached):", round(ns_per_add(255), 1), "ns")
print("a = 1000 (result 1001, new):", round(ns_per_add(1000), 1), "ns")
```

</details>

On one machine running CPython 3.12.13, the cached case took 9.8 nanoseconds (ns) and the new-object case 17.4 ns (median of seven runs). The ratio, about 1.8 times, is the useful number. Your absolute times will differ.

![Two bars: a plus 1 with a result inside the cache takes 9.8 ns; with a result outside it, 17.4 ns](diagrams/3.5-timing.svg "Time per a + 1 on one machine. Absolute times depend on the hardware.")

## Common traps

> [!TRAP]
> Comparing values with `is` works only by accident for small integers. `x is 300` can be `True` or `False` depending on how `x` was produced and compiled. Use `==` for values.

> [!TRAP]
> CPython 3.12.13 prints a `SyntaxWarning` for `x is 300`. The warning is a hint: the result of `is` with a literal depends on how the code was compiled.

> [!TRAP]
> The -5 to 256 range is a CPython implementation detail. The Language Reference warns that "the boundary between 'small' and 'large' integers has already changed in the past" (§6.2.3.1). Do not hard-code it.

> [!TRAP]
> Caching never changes values. `int(str(v)) == v` for every `v`; only object identity changes, and `is` is the only operator that sees the difference.

> [!TRAP]
> A speed-up measured on one machine says nothing about another. Measure your own code with `timeit` before you optimize.

## Summary

- CPython shares one object for each integer from -5 to 256 when the value is produced at run time.
- Literals in one file share objects through the compiler's constant table. Separate `compile()` calls do not.
- `is` compares identity, not value. Use `==` for integers.
- The cache saves memory: a million distinct int objects cost 28 MB more than a million cached ones.
- The speed gain is small: a cache hit saved about 8 ns per operation on the machine measured here.

## Quiz time

### Question 1: Prediction

Both functions below live in the same file. What does `print(f() is g())` print?

```python
def f():
    return 300

def g():
    return 300
```

<details><summary>Show solution</summary>

It prints `True`. Both literals are stored once in the constant table of the file's compilation, so both functions return the same object. The code earlier in this lesson printed `one file: True`.

</details>

### Question 2: Bug-spotting

A function counts items and checks whether the count is 1000. Find the bug.

```python
def is_full(items):
    count = len(items)
    return count is 1000
```

<details><summary>Show solution</summary>

The bug is `is`. The number 1000 lies outside the cache, so `len(items)` returns a new object each time, and `count is 1000` is usually `False` even when the length is 1000. Python also warns about `is` with a literal. The fix is `return count == 1000`.

</details>

### Question 3: Calculation

You run `values = [int(str(v % 300)) for v in range(10_000)]`. How many distinct objects does `values` contain?

<details><summary>Show solution</summary>

The answer is 1,676. Values 0 to 256 are cached, so they share 257 objects. Values 257 to 299 are new each time they appear. In 10,000 values, there are 33 full cycles of 300 (9,900 values) plus 100 values from 9,900 to 9,999 whose remainders run 0 to 99. Each full cycle gives 43 new objects, so $33 \times 43 = 1{,}419$ new objects. Adding the 257 cached objects gives $1{,}419 + 257 = 1{,}676$. Running the line confirms 1,676 distinct objects.

</details>

### Question 4: Explanation

Question 1 changes if the two functions are in different files, each compiled separately. Explain why.

<details><summary>Show solution</summary>

Each `compile()` call builds its own constant table, so `300` in one compilation is a different object from `300` in another. The code earlier in this lesson printed `two compile() calls: False`. The value is equal either way, so `==` returns `True` in both cases.

</details>
