A list comprehension builds a new list from an iterable in one expression. In this lesson you will read the bytecode (the low-level instructions CPython, the standard Python interpreter, runs) of a comprehension and of an equivalent loop, count what each one executes per element, and check how much the difference is worth.

**You need:** `for` loops and `list.append` (Lesson 4.1 covers the list object).

## The problem

You often want a list in which each item is computed from an input: the squares of 0 to n−1, the even numbers in some data, the first letters of some names. The explicit way creates an empty list and appends one value per pass. The comprehension says the same thing in one expression. Both produce identical lists. The question is what, if anything, changes underneath.

## Anatomy of a comprehension

A comprehension is an expression inside square brackets, followed by a `for` clause and an optional `if` clause.

![Three parts of a list comprehension: an expression, a for clause and an if clause, read left to right](diagrams/4.2-anatomy.svg "One comprehension, three parts. Read left to right.")

For each item the `for` clause produces, the `if` clause decides whether to keep it, and the expression computes the value that goes into the new list. The input is not changed.

The order matters. The expression is evaluated last, and only for the items the `if` clause keeps. So a filter placed in the `if` clause protects the expression from bad inputs: a division by `x` written after `if x != 0` never sees a zero. This follows from the left-to-right reading of the clauses, and it is the reason to put conditions in the `if` clause rather than inside the expression.

## Worked example, by hand

Take `[x * x for x in range(4)]`. `range(4)` produces 0, 1, 2 and 3, so the loop makes four passes. Each pass appends one square, and the list grows by one entry:

![Four passes over range(4): x, x times x, and the list after each pass, ending at [0, 1, 4, 9]](diagrams/4.2-worked-trace.svg "Trace of the comprehension for n = 4. The final list is the last one.")

The explicit loop and the comprehension give the same answer:

```python
def squares(n):
    result = []
    for x in range(n):
        result.append(x * x)
    return result

print(squares(4))
print([x * x for x in range(4)])
```

```output
[0, 1, 4, 9]
[0, 1, 4, 9]
```

## What runs per element

CPython compiles each function to bytecode: a list of instructions for a stack machine, a machine that keeps intermediate values on a stack. The standard library module `dis` (disassembler) prints it. Here is the comprehension:

```python
import dis

def comp(n):
    return [x * x for x in range(n)]

dis.dis(comp)
```

```output
  3           0 RESUME                   0

  4           2 LOAD_GLOBAL              1 (NULL + range)
             12 LOAD_FAST                0 (n)
             14 CALL                     1
             22 GET_ITER
             24 LOAD_FAST_AND_CLEAR      1 (x)
             26 SWAP                     2
             28 BUILD_LIST               0
             30 SWAP                     2
        >>   32 FOR_ITER                 7 (to 50)
             36 STORE_FAST               1 (x)
             38 LOAD_FAST                1 (x)
             40 LOAD_FAST                1 (x)
             42 BINARY_OP                5 (*)
             46 LIST_APPEND              2
             48 JUMP_BACKWARD            9 (to 32)
        >>   50 END_FOR
             52 SWAP                     2
             54 STORE_FAST               1 (x)
             56 RETURN_VALUE
        >>   58 SWAP                     2
             60 POP_TOP
             62 SWAP                     2
             64 STORE_FAST               1 (x)
             66 RERAISE                  0
ExceptionTable:
  28 to 50 -> 58 [2]
```

The lines between `FOR_ITER` and `JUMP_BACKWARD` run once per element. For the comprehension there are five: store `x`, load `x` twice, multiply, and `LIST_APPEND`. The explicit loop, measured the same way with `dis`, runs eight: it also loads `result`, looks up its `append` attribute, and calls it, then discards the return value with `POP_TOP`.

![Operations executed per element: the for loop runs 8, the comprehension runs 5; the method-call instructions of the loop are highlighted](diagrams/4.2-per-element.svg "Per-element bytecode on Python 3.12. Counts come from dis.")

`LIST_APPEND 2` is the key instruction. The number 2 says where the list sits on the stack. The CPython documentation defines it as `item = STACK.pop()` followed by `list.append(STACK[-i], item)`. The list is not on top, because the iterator sits above it. Each element is popped and appended to the list under the iterator, and the list stays in place for the next pass.

![LIST_APPEND 2 on the value stack: the value 4 is popped and appended to the list two slots down; the list stays on the stack](diagrams/4.2-stack.svg "The value stack for one pass (x = 2). The list [0, 1] already holds the first two squares.")

Two points about how the bytecode changed across versions. Until Python 3.11 a comprehension was compiled into its own nested function, so calling it cost a function call. Python 3.12 inlined comprehensions: there is no separate code object and no extra function frame (PEP 709). The PEP reports up to 2× for a microbenchmark of a comprehension alone; that figure is the authors' measurement, and I did not reproduce it, because this machine has no Python 3.11 to compare against.

## Measured timing

Timing depends on the machine and the Python build, so treat these numbers as one data point. On an Apple arm64 machine (ARM 64-bit) with Python 3.12.13, for one million elements (minimum of 7 repeats):

![Time per call for four versions at n = 1,000,000: map with a lambda 56.9 ms, for loop 35.5 ms, for loop with append hoisted 37.9 ms, comprehension 30.9 ms](diagrams/4.2-timing.svg "Time per call. Machine-specific; rerun the experiment script for your own numbers.")

The comprehension is about 15% faster than the plain loop (35.5 / 30.9 ≈ 1.15) and about 23% faster than the loop with `append` looked up once outside the loop (37.9 / 30.9 ≈ 1.23). Hoisting did not help. The adaptive interpreter already specialised the loop's call to `CALL_NO_KW_LIST_APPEND`, so the attribute lookup was cheap to begin with. I did not profile which extra instruction costs the most; that is my inference from the bytecode, not a measurement. The `map` version with a lambda is about 1.8× slower, because each element costs a Python function call.

The gap depends on size. At n = 10 the calls take 0.216 µs (comprehension) and 0.246 µs (loop), so fixed call overhead dominates. At n = 1,000 the times are 26.4 µs and 30.4 µs, a ratio of about 1.15, which is close to the million-element ratio. Small inputs tell you little about the per-element cost.

Memory is a different question. A comprehension builds the whole list. Inside `sum()`, for one million squares, `tracemalloc` (the standard memory tracer) recorded a peak of 40,448,200 bytes for the list version and 464 bytes for a generator expression, which computes one value at a time. Use a generator when you only need to consume the values once.

## Filters, nesting and scope

The `if` clause filters, and a second `for` clause nests:

```python
data = [3, 8, -1, 6]
print([x for x in data if x % 2 == 0])
print([[r * c for c in range(3)] for r in range(2)])
```

```output
[8, 6]
[[0, 0, 0], [0, 1, 2]]
```

The loop variable belongs to the comprehension. It does not leak into the enclosing function (Python 3.0 made this change, as the What's New document records):

```python
def f():
    values = [x for x in range(3)]
    return values, "x" in locals()

print(f())
```

```output
([0, 1, 2], False)
```

Use a comprehension when the body is one expression with an optional filter, because the code reads as one statement. Switch to an explicit loop when you need several statements, an early exit, or side effects. This is a judgment about readability, not something the timing proves: the speed difference here is about 15%, and a loop that is clearer is usually worth more than that.

## Common traps

> [!TRAP]
> A comprehension is not faster because of a hidden optimisation. It is faster because each element runs fewer instructions, and the append is a single opcode.

> [!TRAP]
> Do not use a comprehension for side effects. `[seen.append(x) for x in range(3)]` builds a list of `None` values that you then throw away. Write a `for` loop instead.

> [!TRAP]
> A `map` with a `lambda` is slower here, not faster: each element costs a Python function call.

> [!TRAP]
> Hoisting `append` out of the loop is not a reliable speedup on Python 3.12. In our run it was slower.

> [!TRAP]
> The percentages above come from one machine and one build. Repeat the measurement on yours before you quote a number.

## Summary

- A comprehension is an expression with a `for` clause and an optional `if` clause; it builds a new list.
- Per element, the comprehension runs 5 bytecode operations and the explicit loop runs 8; `LIST_APPEND` appends to the list held lower on the stack.
- Python 3.12 inlined comprehensions (PEP 709), so there is no separate function call for them.
- On one machine the comprehension was about 15% faster than the plain loop and about 1.8× faster than `map` with a lambda.
- A list comprehension keeps every element in memory; a generator keeps one at a time.

## Quiz time

### Question 1: Calculation

How many bytecode operations run per element for `[x * x for x in data]` and for the equivalent `for` loop with `append`? Use the counts from the disassembly above.

<details><summary>Show Solution</summary>
The comprehension runs 5 (STORE_FAST, LOAD_FAST, LOAD_FAST, BINARY_OP, LIST_APPEND). The loop runs 8 (STORE_FAST, LOAD_FAST, LOAD_ATTR, LOAD_FAST, LOAD_FAST, BINARY_OP, CALL, POP_TOP). These counts come from dis on Python 3.12; other versions may differ.
</details>

### Question 2: Prediction

What does this print?

```python
print([y - 1 for y in range(5) if y % 2 == 1])
```

<details><summary>Show Solution</summary>
The values of y from range(5) are 0 to 4. The if clause keeps the odd values, 1 and 3. The expression gives 0 and 2, so the output is `[0, 2]`.
</details>

### Question 3: Find the bug

A student wants to print three numbers and keep the results:

```python
results = [print(x) for x in range(3)]
print(results)
```

<details><summary>Show Solution</summary>
The output is `0`, `1`, `2`, then `[None, None, None]`. `print` returns `None`, so the comprehension builds a list of `None` values. The intent is a side effect, so use a `for` loop: `for x in range(3): print(x)`.
</details>

### Question 4: Explanation

Why does `"x" in locals()` return `False` in the scope example above, even though `x` was used as the loop variable?

<details><summary>Show Solution</summary>
In Python 3 the loop variable of a list comprehension is isolated from the enclosing scope. In Python 3.12, inlined comprehensions keep this isolation with `LOAD_FAST_AND_CLEAR` and a restore after the loop (PEP 709). The name is bound while the comprehension runs, then the outer binding is restored, so no `x` remains in the function's locals.
</details>
