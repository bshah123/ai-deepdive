You will be able to choose between `list` and `collections.deque` for a first-in-first-out (FIFO) queue, explain from CPython's memory layout why `list.pop(0)` gets slower as the queue grows, and measure the gap yourself. CPython is the reference implementation of Python, written in C.

**You need:** how a list stores its items as one contiguous array of pointers (Lesson 4.1), and the difference between `append` and `pop`.

## The problem a queue solves

A FIFO queue hands items out in the order they arrived: print jobs, tasks waiting for a worker, the frontier of a breadth-first search (BFS, which explores a graph layer by layer). Two operations matter: add at the back, and remove from the front. A list handles both, and for a short queue it works fine. The question is what removing from the front costs.

## Lists: removing the front shifts everything

A list is one contiguous array of pointers. Removing the first item leaves a hole at slot 0, and the array must stay contiguous, so every remaining pointer moves one slot left.

![Before and after list.pop(0) on the list 1, 2, 3, 4: the pointers to 2, 3 and 4 each move one slot left, and 1 is returned](diagrams/4.5-list-shift.svg "list.pop(0) on a four-item list: three pointers move, one is returned.")

Worked example by hand: the list `[1, 2, 3, 4]` and `pop(0)`. The item 1 is returned. The pointers to 2, 3 and 4 move one slot left, which is three pointer moves. `pop()` from the back moves nothing, because nothing sits after the last slot.

Draining a queue of n items from the front costs (n−1) + (n−2) + … + 0 = n(n−1)/2 pointer moves. For n = 100,000 that is 4,999,950,000 moves. CPython does each shift with one `memmove` over the tail of the array (`list_pop_impl` in `Objects/listobject.c`, v3.12.0). The Python documentation gives the same verdict: list operations "incur O(n) memory movement costs for pop(0) and insert(0, v)".

## collections.deque: a chain of blocks

A deque does not use one array. According to the CPython source (`Modules/_collectionsmodule.c`, v3.12.0), a deque is a doubly linked list of blocks, and each block holds 64 pointers (`BLOCKLEN` is 64). The deque keeps two indexes, `leftindex` and `rightindex`, that mark the live slots in its two end blocks.

![A deque drawn as three linked blocks of four slots: after popleft, the first slot of block A is empty and the left index points at the next slot; the right index points into block C](diagrams/4.5-deque-blocks.svg "Blocks are drawn with four slots for legibility; CPython uses 64.")

So `popleft` reads `leftblock->data[leftindex]`, increments `leftindex`, and moves no pointers. When a block empties, the deque moves on to the next block and releases the old one. `append` writes into the right block and allocates a new block once every 64 appends. The documentation describes both ends as having "approximately the same O(1) performance". Big-O notation (O) describes how cost grows with the number of items n, so O(1) means roughly constant, and O(n) means roughly proportional to n. The word "approximately" is the documentation's, so treat it as a practical claim, not a worst-case bound.

Each block is a C struct of 64 pointers plus two links. On a 64-bit build that is about 528 bytes (66 pointers of 8 bytes each; this size is my arithmetic from the struct, not a measurement). A list keeps one array that grows by over-allocation (Lesson 4.1). Neither container copies the items themselves: both store pointers to the same objects, so the difference lies entirely in how the pointers are arranged.

`queue.Queue` is built on a deque: in the installed CPython 3.12.13 standard library, `Queue._init` sets `self.queue = deque()`. The thread-safe queue therefore has the same cost model.

## Measured: the same operations, two containers

The worked example below uses only the standard library, so it runs in the browser. It shows that the two containers behave the same; it does not measure speed.

```python
from collections import deque

# A list as a FIFO queue: append at the back, pop(0) from the front
q_list = [1, 2, 3]
q_list.append(4)
print("list before pop:", q_list)
first = q_list.pop(0)
print("list popped:", first, "-> left:", q_list)

# The same operations on a deque
q_dq = deque([1, 2, 3])
q_dq.append(4)
first = q_dq.popleft()
print("deque popped:", first, "-> left:", q_dq)

# maxlen: a bounded deque discards from the opposite end when full
window = deque([1, 2, 3], maxlen=3)
window.append(4)
print("after append(4):", window)
window.appendleft(0)
print("after appendleft(0):", window)
```

```output
list before pop: [1, 2, 3, 4]
list popped: 1 -> left: [2, 3, 4]
deque popped: 1 -> left: deque([2, 3, 4])
after append(4): deque([2, 3, 4], maxlen=3)
after appendleft(0): deque([0, 2, 3], maxlen=3)
```

Both containers return the same items in the same order. The difference is the cost. The timing script below is a condensed copy of the drain functions in `scripts/diagrams/lessons/4.5_data.py`, which drains queues of n items from the front and reports the best of three runs. Building the queue happens outside the timed region, so the numbers reflect only the removals. A timer that included the setup would hide the difference.

<details><summary>Timing script (standard library only; numbers depend on your machine)</summary>

```python
import time
from collections import deque

def drain_list(n):
    q = list(range(n))
    t = time.perf_counter()
    while q:
        q.pop(0)
    return time.perf_counter() - t

def drain_deque(n):
    q = deque(range(n))
    t = time.perf_counter()
    while q:
        q.popleft()
    return time.perf_counter() - t

for n in [1000, 10000, 100000]:
    print(n, min(drain_list(n) for _ in range(3)), min(drain_deque(n) for _ in range(3)))
```

</details>

The table comes from one run of `scripts/diagrams/lessons/4.5_data.py` on CPython 3.12.13, arm64 macOS, best of three. Your digits will differ; the shape should match.

| n items | `list.pop(0)` drain | `deque.popleft()` drain | ratio |
|---:|---:|---:|---:|
| 1,000 | 96 µs | 16 µs | 6× |
| 3,000 | 671 µs | 51 µs | 13× |
| 10,000 | 7.1 ms | 170 µs | 42× |
| 30,000 | 91 ms | 494 µs | 184× |
| 100,000 | 1.12 s | 1.65 ms | 680× |

![Log-scale line chart: list drain time rises from 96 µs to 1.12 s as n goes from 1,000 to 100,000, while the deque drain rises from 16 µs to 1.65 ms](diagrams/4.5-drain-times.svg "Time to drain n items from the front, measured. Both axes are on a log scale.")

Between 10,000 and 100,000 items (ten times more), the list time grows 156 times. The move count alone predicts a factor of 100. The extra factor is my reasoning, not something I measured in isolation: a larger array spills out of the cache, so each shift touches more memory. The deque time grows about ten times, as a constant cost per item should.

A realistic BFS-style queue keeps its length steady: one `pop` and one `append` per step. With 100,000 items in the queue, the list costs 22.5 µs per step and the deque 0.031 µs per step, about 730 times less.

The lesson is not that lists are slow. A list used as a stack, with `append` and `pop()` at the same end, moves no pointers, and each operation costs O(1). The cost appears only when items leave from the front.

## When a list is still the right choice

Use a list when you work at one end only (a stack), when you need slicing or the sorting methods from Lessons 4.3 and 4.4, or when the sequence is small and fixed. Use a deque when items enter at one end and leave at the other, or when you need a bounded window. If you need both fast front removal and fast random access, a deque is the wrong tool for the random access part: measure first, then choose.

## Common traps

> [!TRAP]
> **Small tests hide it.** At 1,000 items the list drain takes 96 µs, which no one notices. The cost is quadratic in n, so the slow version passes every small test and fails at production sizes.

> [!TRAP]
> **A deque is not an array.** Its ends are fast, its middle is not. On a 100,000-item deque, `d[50000]` takes about 4.3 µs, against 30 ns for `list[50000]`. Indexing walks the block chain, costing roughly one hop per 64 items.

![Three bars on a linear scale: list[50000] 30 ns, deque[0] 33 ns, deque[50000] 4,296 ns](diagrams/4.5-index-cost.svg "Index access, measured on a 100,000-item list and deque, one run.")

> [!TRAP]
> **`insert(0, x)` has the same problem.** On a list it shifts everything right, the mirror image of `pop(0)`. `appendleft` on a deque is the fix.

> [!TRAP]
> **`maxlen` drops items silently.** `deque(maxlen=3)` discards from the opposite end when full, as the worked example shows. That is a sliding window, not an error, so a bug that expects every item to survive will not raise.

> [!TRAP]
> **One timing run is noise.** Take the minimum of several repeats, and compare containers on the same machine with the same n. Absolute times depend on hardware and build.

## Summary

- A list is one contiguous pointer array, so `pop(0)` moves every remaining pointer and draining n items costs n(n−1)/2 moves.
- A deque is a chain of 64-slot blocks, so `popleft` moves an index, not pointers.
- Measured on CPython 3.12.13: draining 100,000 items took 1.12 s from a list and 1.65 ms from a deque.
- Use a deque for queues and sliding windows; keep a list when you need fast random access by position.

### Question 1: Predict the output

```python
from collections import deque

d = deque(maxlen=2)
for x in "abc":
    d.append(x)
print(list(d))
```

<details><summary>Show Solution</summary>

The output is `['b', 'c']`. The deque holds at most two items. After `a` and `b`, it is full. Appending `c` discards `a` from the left end.

</details>

### Question 2: Calculate the cost

A queue holds 20,000 items in a list, and you drain it with `pop(0)`. How many pointer moves happen in total?

<details><summary>Show Solution</summary>

The total is n(n−1)/2 with n = 20,000: 20,000 × 19,999 / 2 = **199,990,000** moves. This counts the shifts only. Each move is one pointer, typically 8 bytes on a 64-bit build. The number is an estimate from the array layout, not a measured count.

</details>

### Question 3: Find the bug

This breadth-first search uses a deque, but it does not visit nodes in breadth-first order:

```python
from collections import deque

graph = {"A": ["B", "C"], "B": ["D"], "C": [], "D": []}
queue = deque(["A"])
order = []
while queue:
    node = queue.pop()          # the bug is on this line
    order.append(node)
    queue.extend(graph[node])
print(order)
```

<details><summary>Show Solution</summary>

`pop()` takes from the right, so the queue behaves as a stack. The output is `['A', 'C', 'B', 'D']`, which is last-in-first-out order. Breadth-first order is `['A', 'B', 'C', 'D']`. The fix is `queue.popleft()`, which removes from the front and gives the FIFO order that BFS needs.

</details>

### Question 4: Explain the index cost

Why is `list[50000]` about 140 times faster than `deque[50000]` on a 100,000-item container, while `deque[0]` is as fast as the list?

<details><summary>Show Solution</summary>

A list stores its pointers in one array, so `list[i]` is one address calculation: the base address plus 8 × i bytes. A deque splits its items across 64-slot blocks linked together. `deque[i]` must follow the links from one end until it reaches block i // 64, which costs roughly one hop per 64 items. Index 0 sits in the first block, so it takes no hops.

</details>
