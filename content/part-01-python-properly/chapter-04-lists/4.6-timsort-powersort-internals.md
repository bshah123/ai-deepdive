This lesson shows how CPython's `sorted()` finds the ordered stretches in a list, merges them, and what each step costs. You will find natural runs by hand, count comparisons on seven input shapes, and see why merging two disjoint runs of 50,000 elements costs about 40 comparisons. CPython is the reference implementation of Python, written in C. Its sort, Timsort, now also uses the Powersort rule for choosing which runs to merge.

**You need:** Lesson 4.3 (calling `sorted()` and `list.sort()`, and what "stable" means) and the idea of binary search.

## The problem: real lists are often partly ordered

A log appended in time order, two sorted batches joined end to end, and a list with a few edits all contain long stretches already in order. A sort that ignores this does the same work on a sorted list as on a shuffled one. The Python documentation says the built-in sort "can take advantage of any ordering already present in a dataset" (Python docs, Sorting HOW TO). For example, [1, 2, 3, 10, 4, 5, 6] is two ordered pieces that meet where 10 is followed by 4. Timsort works in two steps: find the ordered stretches, called runs, then merge them.

## Natural runs

A **natural run** is a maximal stretch already in order. An **ascending** run never goes down, and a **descending** run goes strictly down. Reversing a descending run turns it into an ascending one, so the sort reverses it in place.

![The 16-element example split into natural runs, and the same list after the descending runs are reversed](diagrams/4.6-natural-runs.svg "Natural runs of a 16-element list, before and after reversing the descending runs.")

Work the example by hand. Start at 5: it rises through 9 and 12, and 3 breaks the rise, so the first run is [5, 9, 12]. Start at 3: 2 is smaller, so the run is descending, and 8 breaks it, giving [3, 2]. The same procedure gives [8, 14], [10, 1], [4, 7, 11] and [6, 13, 15, 16]. That is six runs, with lengths 3 + 2 + 2 + 2 + 3 + 4 = 16.

The scanner in the code below uses the simple strict rule for descending runs. CPython's rule for equal elements is more careful, because reversing equal elements can break stability (listsort.txt discusses this).

Random data has short runs. The scan finds 4,135 runs in 10,000 random numbers, about 2.4 elements each (measured below). CPython therefore extends short runs to a minimum length, called minrun. `listsort.txt` describes binary insertion sort for short inputs. CPython's minrun rule (Lesson 4.3) pads short runs to a length between 32 and 64 for inputs of 64 or more elements. This lesson does not reproduce the extension step.

## Merging two runs, one comparison at a time

A merge keeps one pointer per run, compares the two elements under the pointers, and moves the smaller one to the output. By hand, merge [3, 8, 14] with [2, 10]. Compare 3 and 2: output 2. Compare 3 and 10: output 3. Compare 8 and 10: output 8. Compare 14 and 10: output 10. The second run is now empty, so [14] is copied without comparisons. The result is [2, 3, 8, 10, 14] after 4 comparisons.

The merge must be stable. On a tie, `merge_count` takes the element from the left run, because the right element moves only when `b[j] < a[i]`. The Sorting HOW TO gives the same guarantee at the top level: sorting `('red', 1), ('blue', 1), ('red', 2), ('blue', 2)` by key puts both blue records first, in their original order.

Each comparison outputs one element, and the last element needs no comparison. So merging runs of lengths p and q takes at most p + q − 1 comparisons. This is reasoning (b) from the procedure.

## Counting comparisons, not seconds

Wall-clock timings are noisy. Comparison counts are exact and repeatable. The Sorting HOW TO says the sort routines "use `<` when making comparisons between two objects", so the code below wraps each value in a class whose `__lt__` method (the method behind `<`) increments a counter. The same block produces the scaling data used below. The output was produced with Python 3.12.13.

```python
import random

class Counted:
    """Wraps a value. Each `<` between two wrapped values is counted."""
    count = 0
    __slots__ = ("v",)

    def __init__(self, v):
        self.v = v

    def __lt__(self, other):
        Counted.count += 1
        return self.v < other.v

def comparisons(values):
    """Number of `<` comparisons that sorted() makes on these values."""
    Counted.count = 0
    sorted(Counted(v) for v in values)
    return Counted.count

def natural_runs(a):
    """Split a into maximal runs: non-decreasing, or strictly decreasing."""
    runs, i, n = [], 0, len(a)
    while i < n:
        j = i + 1
        if j < n and a[j] < a[i]:
            while j + 1 < n and a[j + 1] < a[j]:
                j += 1
            j += 1
            kind = "descending"
        else:
            while j < n and a[j] >= a[j - 1]:
                j += 1
            kind = "ascending"
        runs.append((i, j - i, kind))
        i = j
    return runs

def merge_count(a, b):
    """Merge two sorted lists; return (merged, number of `<` comparisons used)."""
    out, i, j, c = [], 0, 0, 0
    while i < len(a) and j < len(b):
        c += 1
        if b[j] < a[i]:
            out.append(b[j])
            j += 1
        else:
            out.append(a[i])
            i += 1
    out += a[i:] + b[j:]
    return out, c

merged, c = merge_count([3, 8, 14], [2, 10])
print("merge [3, 8, 14] with [2, 10]:", merged, "in", c, "comparisons")

example = [5, 9, 12, 3, 2, 8, 14, 10, 1, 4, 7, 11, 6, 13, 15, 16]
print("example:", example)
for start, length, kind in natural_runs(example):
    print(f"  start {start:2d}  length {length}  {kind}")
print("comparisons:", comparisons(example))

N = 10_000
rng = random.Random(4)
rand = [rng.randrange(10**6) for _ in range(N)]
nearly = list(range(N))
for _ in range(100):
    i, j = rng.randrange(N), rng.randrange(N)
    nearly[i], nearly[j] = nearly[j], nearly[i]
chunks = [sorted(rand[k * N // 8:(k + 1) * N // 8]) for k in range(8)]
inputs = {
    "random": rand,
    "ascending": list(range(N)),
    "descending": list(range(N, 0, -1)),
    "nearly sorted (100 swaps)": nearly,
    "8 ascending runs": [v for c in chunks for v in c],
    "2 interleaved runs": list(range(0, N, 2)) + list(range(1, N, 2)),
    "2 disjoint runs": [N + i for i in range(N // 2)] + list(range(N // 2)),
}
print(f"\n{'input':28s}{'comparisons':>12s}{'per n':>8s}{'runs':>7s}")
for name, data in inputs.items():
    c = comparisons(data)
    print(f"{name:28s}{c:12,d}{c / N:8.2f}{len(natural_runs(data)):7d}")

print()
for n in (1_000, 10_000, 100_000):
    half = n // 2
    disjoint = [half + i for i in range(half)] + list(range(half))
    inter = list(range(0, n, 2)) + list(range(1, n, 2))
    print(f"n={n:>7,d}  disjoint {comparisons(disjoint):>8,d}  interleaved {comparisons(inter):>8,d}")
```

The scan that finds the runs compares each adjacent pair once, so it costs n − 1 comparisons for any input. Everything above that is merge work.

- Ascending and descending input each cost exactly n − 1 = 9,999 comparisons. There is one run, and reversing it costs nothing.
- Two disjoint runs cost the scan plus 32 merge comparisons. Two interleaved runs cost the scan plus 9,999, about one per element.
- Eight runs cost 29,992 merge comparisons, close to $n \log_2 8 = 3n$. This is reasoning (b): a balanced merge has three levels, and each level touches every element about once.
- Nearly sorted input (199 runs) needs 13,447 merge comparisons, against 109,839 for random input.
- Random input costs 119,838 comparisons, which is 0.90 times $n \log_2 n$ = 132,877. That term sets the scale, not an exact formula. Auger, Jugé, Nicaud and Pivoteau prove that Python's Timsort runs in O(n log n) worst-case time, and in O(n + n log r) for r runs (arXiv:1805.08612).

Subtracting n − 1 from the scaling rows gives the merge cost: 26, 32 and 40 comparisons for disjoint runs at n = 1,000, 10,000 and 100,000. For interleaved runs it is 999, 9,999 and 99,999.

## Galloping mode: why disjoint runs are cheap

When one run keeps winning, the merge stops comparing one element at a time. `listsort.txt` describes galloping mode: after `MIN_GALLOP` (7 by default) consecutive wins, the merge probes at exponentially growing offsets (1, 3, 7, 15, and so on), then bisects the bracket it has found. The threshold adapts: it drops when galloping pays off and rises when it does not.

For disjoint runs, the first 7 comparisons take one element at a time, and then galloping finds that the whole run belongs in one block. This is reasoning (b): 7 + 2 log2(block length) gives about 25 comparisons at n = 1,000 and about 38 at n = 100,000, close to the measured 26 and 40. For interleaved runs, the wins alternate, so the 7-win threshold is never reached and the merge pays about one comparison per element.

The block below implements the probing in a simplified form, not CPython's C code, and counts its probes.

```python
def gallop_position(a, key):
    """Exponential probes from the left (offsets 0, 1, 3, 7, ...), then bisect the bracket."""
    probes = []

    def is_less(i):
        probes.append(i)
        return a[i] < key

    lo, k = -1, 0
    while True:
        i = (1 << k) - 1
        if i >= len(a):
            hi = len(a)
            break
        if is_less(i):
            lo, k = i, k + 1
        else:
            hi = i
            break
    while hi - lo > 1:
        mid = (lo + hi) // 2
        if is_less(mid):
            lo = mid
        else:
            hi = mid
    return hi, probes

def bisect_count(n, key):
    """Probes used by plain binary search for key in range(n)."""
    lo, hi, count = 0, n, 0
    while lo < hi:
        mid = (lo + hi) // 2
        count += 1
        if mid < key:
            lo = mid + 1
        else:
            hi = mid
    return count

arr = list(range(1000))
for key in (5, 700):
    index, probes = gallop_position(arr, key)
    print(f"key {key}: index {index}, {len(probes)} probes {probes}")
    print(f"  plain binary search: {bisect_count(1000, key)} probes")
```

```output
  plain binary search: 10 probes
```

![Two rows of probe boxes: for key 5, six probes; for key 700, nineteen probes; green boxes move the search right, amber boxes move it left](diagrams/4.6-gallop-probes.svg "Probe sequences of the exponential search for keys 5 and 700 in the list 0 to 999.")

Exponential search is cheap only when the answer is near the start. Key 5 finishes in 6 probes, against 10 for plain bisection. Key 700 costs 19 probes, because the doubling overshoots and the bisection then has to narrow a wide bracket. This trade-off is why CPython adapts its threshold rather than galloping every time.

## Merge order and Powersort

Timsort's merge order was once driven by a stack of pending runs and length rules. `listsort.txt` says those rules were loosely based on Fibonacci numbers and that "the intended invariants weren't actually preserved". So the "merge invariants" in this lesson's title describe a historical design, not a guarantee the current code keeps.

Merge order matters because a merge costs about the total length of the two runs it joins. For runs of 1,000, 10 and 10, merging the two short runs first costs 20 + 1,020 = 1,040 moves. Merging the long run first costs 1,010 + 1,020 = 2,030 moves. This is reasoning (b) from a cost model, not a measurement.

Powersort (Munro and Wild, 2018) picks the merge order from the run boundaries. Each boundary gets a **power**: the depth it would occupy in an ideal binary merge tree. Deeper boundaries merge first (reasoning (b) from that definition). The authors claim "nearly-optimal merging orders with practically negligible overhead" (arXiv:1805.04154). `listsort.txt` says CPython uses this strategy and that it "isn't always truly optimal". It is always truly optimal for three run lengths.

CPython adopted Powersort in 2021 (bpo-34561). I did not open that commit or check which release shipped it. This lesson measures only the interpreter installed here and does not compare against the old policy, so it claims no Powersort speedup.

## Common traps

> [!TRAP]
> Sorted input is cheap only because the scan finds one run. Random input of the same length costs about 12 times more: 119,838 against 9,999.

> [!TRAP]
> A comparison count is not a running time. A `<` on expensive objects costs far more than one on integers, and the counter says nothing about memory.

> [!TRAP]
> Galloping is not free. Key 700 needs 19 probes, while plain bisection needs 10.

> [!TRAP]
> Stability constrains run detection. Reversing a run with equal elements can swap them. The strict rule used here avoids the problem, at the cost of splitting some runs.

> [!TRAP]
> Powersort is not "always optimal". `listsort.txt` says it is always truly optimal for three run lengths, and the paper claims "nearly-optimal" orders.

## Summary

- Finding natural runs costs n − 1 comparisons. Reversing descending runs costs none.
- Merging runs of lengths p and q costs at most p + q − 1 comparisons. Interleaved runs cost about one comparison per element; disjoint runs cost a few dozen, because galloping skips whole blocks.
- Galloping starts after 7 consecutive wins and adapts its threshold. It helps when the answer is near the start of the search.
- Powersort picks the merge order from run boundaries, and CPython uses it. The CPython notes call it nearly optimal, not always optimal.

### Question 3: Bug-spotting

An early draft of `natural_runs` had this descending branch, with the `j += 1` line removed:

```python
if j < n and a[j] < a[i]:
    while j + 1 < n and a[j + 1] < a[j]:
        j += 1
    kind = "descending"
```

What goes wrong on the input `[3, 2, 8]`?

<details><summary>Show solution</summary>

In the draft, `j` ends on the last element of the descending run, not one past it. The run is recorded with length 1 (only `3`), and the next run starts at index 1, which is the `2`. The last element of each descending run is counted twice, and the lengths are one short. Keeping `j` exclusive, as the ascending branch does, fixes it.

</details>

### Question 4: Explanation

Why does galloping make the disjoint case cheap but leave the interleaved case costing about n comparisons?

<details><summary>Show solution</summary>

In the disjoint case one run wins many times in a row, so the merge reaches the 7-win threshold and gallops through the whole block in logarithmic steps. In the interleaved case the wins alternate between the two runs, so the threshold is never reached and every element is compared one at a time.

</details>
