By the end you will be able to predict how many bytes a tuple and a list take, explain why a tuple can be a dictionary key and a list cannot, and read the bytecode of a literal tuple. Every number here was measured on CPython 3.12.13, 64-bit, or derived from such a measurement. Other versions can change the exact sizes, but not the layout ideas.

**You need:** how a list grows by `append` (Lesson 4.1), and the idea that a variable is a name bound to an object (Chapter 2).

## The problem: a list has to grow

A list must support `append`, so it cannot keep its items inside its own object: the object would have to change size. Instead it keeps a pointer to a separate array of slots, and it reserves a few spare slots at the end. A tuple never changes size, so it can keep its items in the same block as its header.

![Tuple: one block holding the GC header, the object header and three items. List: a header block with a pointer to a separate array of four slots, one of them spare](diagrams/5.1-layout.svg "One block versus a header and an array. Sizes are in bytes on a 64-bit build.")

The CPython 3.12 headers show the same thing. `PyTupleObject` ends with `ob_item[1]`, an array whose length is `ob_size` and that sits inside the object. `PyListObject` has `ob_item`, a pointer to a separate array, and `allocated`, the number of slots reserved. Both start with a 24-byte header holding a reference count, a type pointer and a size. CPython also puts a 16-byte garbage-collector header in front of every container. `sys.getsizeof` counts that header too, so an empty tuple reports 40 bytes, not 24.

## Worked example by hand

Take `t = (1, 2, 3)` and `l = [1, 2, 3]`. Pointers are 8 bytes on a 64-bit build.

- **Tuple:** 40 bytes of header, plus 3 items × 8 bytes = 24, so 40 + 24 = **64 bytes**, in one allocation.
- **List:** an empty list reports 56 bytes. The literal reserves 4 slots, 4 × 8 = 32 bytes, so 56 + 32 = **88 bytes**, in two allocations.

The 4 spare slots are an observed value on this build. The CPython code that chooses the number was not checked, so treat it as a measurement, not a rule. To check your own numbers, use the same recipe: a tuple is header + 8 × items, and a list is header + 8 × reserved slots. The reserved count is the one number you cannot read off the item count, so the code below derives it from `sys.getsizeof` rather than assuming a value. It also measures the empty-list header instead of hard-coding 56, because that size depends on the build.

```python
import sys

# Build each container by appending, as most real code does.
empty_list = sys.getsizeof([])        # size of a list header with no slots
for n in range(0, 11, 2):
    t = tuple(range(n))
    items = []
    for i in range(n):
        items.append(i)
    print(f"n={n:2d}  tuple={sys.getsizeof(t):3d} B  list={sys.getsizeof(items):3d} B")

t3 = (1, 2, 3)
l3 = [1, 2, 3]
print("(1, 2, 3) ->", sys.getsizeof(t3), "bytes")
print("[1, 2, 3] ->", sys.getsizeof(l3), "bytes")
print("slots reserved by the list:", (sys.getsizeof(l3) - empty_list) // 8)
```

```output
n= 0  tuple= 40 B  list= 56 B
n= 2  tuple= 56 B  list= 88 B
n= 4  tuple= 72 B  list= 88 B
n= 6  tuple= 88 B  list=120 B
n= 8  tuple=104 B  list=120 B
n=10  tuple=120 B  list=184 B
(1, 2, 3) -> 64 bytes
[1, 2, 3] -> 88 bytes
slots reserved by the list: 4
```

## Growth: the tuple adds 8 bytes per item, the list in steps

The tuple's size is exactly 40 + 8n for every n from 0 to 10, because it never reserves spare room. The list is different. It reserves room, so its size jumps.

![Grouped bars for n from 0 to 10: tuple bars rise by 8 bytes per item; list bars grown by append rise in steps](diagrams/5.1-size-chart.svg "sys.getsizeof against the number of items. Blue: tuple. Amber: list grown by append.")

When appending one item at a time, the list had 4 slots at length 1, 8 at length 5, 16 at length 9, 24 at length 17, and 32 at length 25 on this build. Over 1000 appends it allocated the slot array 28 times, counting the first allocation. Each reserve matches `n + n // 8 + 6`, rounded down to a multiple of 4, where `n` is the length at that resize. That formula fits every resize I observed, but I did not verify it against the CPython source. The reserve is what makes `append` cheap on average: a single append sometimes copies every pointer, but the copies are spread over many appends (reasoning from the growth rule, not measured).

A tuple has no such option. `t = t + (i,)` creates a new tuple and copies every existing item into it. In one run that built 20,000 items this way in about half a second. The same 20,000 items with `append` took under a millisecond. Timings depend on the machine, so read the gap, not the figures. The copy count is simple arithmetic: step *i* copies *i* pointers, so the total over N steps is N(N − 1)/2 = 199,990,000 pointer copies for N = 20,000 (reasoning from the algorithm, not measured).

Use a tuple when the number of items is fixed and the items belong together, such as an `(x, y)` point or a `(rows, columns)` shape. Use a list when items are added or removed. This is my own design rule, not a benchmark result.

## A literal tuple is a constant

The compiler can store a literal tuple once, in the function's constants. The bytecode for returning a tuple and a list shows the difference.

```python
import dis

def f_tuple():
    return (1, 2, 3)

def f_list():
    return [1, 2, 3]

for f in (f_tuple, f_list):
    print(f.__name__, [(i.opname, i.argrepr) for i in dis.get_instructions(f) if i.opname != "RESUME"])
```

```output
f_tuple [('RETURN_CONST', '(1, 2, 3)')]
f_list [('BUILD_LIST', ''), ('LOAD_CONST', '(1, 2, 3)'), ('LIST_EXTEND', ''), ('RETURN_VALUE', '')]
```

![Two bytecode rows: returning a literal tuple is one RETURN_CONST instruction; returning a literal list is BUILD_LIST, LOAD_CONST, LIST_EXTEND and RETURN_VALUE](diagrams/5.1-bytecode.svg "The tuple is already a constant. The list is built from that constant on every call.")

`RETURN_CONST` returns the constant directly. The list version builds a new empty list with `BUILD_LIST`, then `LIST_EXTEND` adds the items of the constant tuple to it, so a new list object exists on every call. The Python 3.12 documentation for `dis` says bytecode "is an implementation detail" that can change between releases, so these instruction names are specific to this version. The code filters out `RESUME`, which only marks the start of a function and is not part of the comparison.

## Hashing: a tuple is only as hashable as its items

A dictionary key needs a hash value that never changes. The Python glossary says that immutable containers, "such as tuples and frozensets", "are only hashable if their elements are hashable". The language reference explains the rule for dictionaries: if an object's hash value changed, it "will be in the wrong hash bucket", so values containing "lists or dictionaries or other mutable types that are compared by value" are not acceptable as keys.

![Decision tree: a tuple whose items are all hashable works as a dict key; a tuple containing a list raises TypeError](diagrams/5.1-hash.svg "The hash check looks inside the tuple, one item at a time.")

```python
d = {(1, "a"): "ok"}
print(d[(1, "a")])

try:
    hash((1, [2]))
except TypeError as e:
    print("TypeError:", e)

t = ([], 1)
t[0].append(9)
print(t)
try:
    t[0] = []
except TypeError as e:
    print("TypeError:", e)
```

```output
ok
TypeError: unhashable type: 'list'
([9], 1)
TypeError: 'tuple' object does not support item assignment
```

Because the check goes item by item, a tuple of tuples of integers is still hashable, since every level passes the same test (reasoning from the glossary rule, not a separate measurement). The last two lines show that immutability is shallow. The tuple cannot change which objects it refers to, so `t[0] = []` fails. The list it refers to is a separate object, and it can still change. So `t` is immutable at its own level, not all the way down.

> [!TRAP]
> `(42)` is just the integer 42, because parentheses alone do not make a tuple. `(42,)` is a one-item tuple. The comma is what matters.

> [!TRAP]
> `sys.getsizeof` counts only the container, not the objects it refers to. A large integer alone reports 72 bytes, but a tuple holding that integer reports 48 bytes, because the integer's memory is not counted. For the total memory of nested data, use a recursive measurement, as the `sys` documentation suggests.

> [!TRAP]
> Building a tuple with `t = t + (i,)` inside a loop is quadratic. Collect the items in a list with `append`, then call `tuple(items)` once at the end.

> [!TRAP]
> `items += (x,)` inside a function rebinds the local name `items` to a new tuple. The caller's tuple does not change. Return the new tuple and assign it at the call site.

## Summary

- A tuple stores its items inside one block. A list stores a pointer to a separate array with spare slots.
- Measured on CPython 3.12.13 (64-bit): a tuple of n items is 40 + 8n bytes; a list built by `append` grows in steps.
- Concatenating tuples copies every item each time, so building a sequence with `+` in a loop costs far more than `append`.
- A tuple is hashable only if every item is hashable. Its immutability covers only its own references, not the objects inside it.

## Quiz time

### Question 1: Calculation

A tuple holds five small integers. Using the rule 40 + 8n measured on this build, how many bytes does `sys.getsizeof` report? Why are the integers not included?

<details><summary>Show Solution</summary>

40 + 8 × 5 = 80 bytes. The tuple stores five pointers, and `sys.getsizeof` counts only the tuple's own memory, not the integer objects that the pointers refer to.

</details>

### Question 2: Prediction

What does this code print, or does it raise an exception? Explain.

```python
d = {(1, 2): "a", (1, [2]): "b"}
print(d)
```

<details><summary>Show Solution</summary>

It raises `TypeError: unhashable type: 'list'` while the dictionary display is built. The first key is fine, but `(1, [2])` contains a list, so `hash()` fails. Nothing is printed.

</details>

### Question 3: Bug-spotting

What does this print, and how would you fix it?

```python
def add_item(items, x):
    items += (x,)

t = ()
add_item(t, 5)
print(t)
```

<details><summary>Show Solution</summary>

It prints `()`. Inside the function, `items += (x,)` creates a new tuple and rebinds the local name `items`. The caller's `t` is unchanged. The fix is to return the new tuple and assign it: `def add_item(items, x): return items + (x,)`, then `t = add_item(t, 5)`. This prints `(5,)`.

</details>

### Question 4: Explanation

Why does `[1, 2, 3]` take more memory than `(1, 2, 3)` on this build, and which measured numbers show it?

<details><summary>Show Solution</summary>

The list has a separate array of pointers, so it makes two allocations, and it reserves spare slots. The measured sizes are 64 bytes for the tuple (40 + 3 × 8) and 88 bytes for the list (56 + 4 × 8, with 4 slots reserved).

</details>
