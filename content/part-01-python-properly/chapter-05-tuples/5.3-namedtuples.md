This lesson shows how to make a small record with named fields in three ways, and what each one allows. By the end you can predict whether attribute assignment, item assignment, a comparison with a plain tuple, or use as a dictionary key will work for each type.

**You need:** tuple unpacking (Lesson 5.2) and a class with an `__init__` method.

## The problem

A point $(3, 4)$ is two numbers. As a plain tuple, the meaning lives only in position: `p[0]` is x and `p[1]` is y, and Python does not check either fact. A dictionary `{"x": 3, "y": 4}` names its fields, but it accepts any key, has no fixed shape, and is mutable. What you want is a record with a fixed set of named fields that is cheap to create.

The standard library gives three answers. `collections.namedtuple` is a factory that returns a tuple subclass. `typing.NamedTuple` is the same idea written as a class with annotations. `dataclasses.dataclass` is a class decorator that writes `__init__`, `__repr__` and `__eq__` for you. They differ in what they allow, so you need to know the differences, not just the syntax.

## Intuition: three types, four features

The grid below compares the four variants you will meet. Each cell was checked by running the type on Python 3.12.13.

![Grid with five rows of features: tuple behaviour, assignment after creation, hashability, kept type annotations, and defaults, for namedtuple, NamedTuple, dataclass and frozen dataclass](diagrams/5.3-features.svg "What each type gives you. Checked on Python 3.12.13.")

Two things stand out. The two named-tuple types behave like tuples, so they unpack, index and compare equal to plain tuples. The dataclass does none of that, but it lets you assign a field after creation.

## Worked example, by hand

Take $p = (3, 4)$. Its squared distance from the origin is $x^2 + y^2 = 3 \cdot 3 + 4 \cdot 4 = 9 + 16 = 25$. With a plain tuple you write `p[0]**2 + p[1]**2`. With a record you write `p.x**2 + p.y**2`. The arithmetic is the same; only the reader's effort changes.

The code below builds the same point with all three types and computes that number. It uses only the standard library, so it runs in the browser on this page.

```python
from collections import namedtuple
from dataclasses import dataclass
from typing import NamedTuple

# 1. collections.namedtuple: a factory that returns a tuple subclass
Point = namedtuple("Point", ["x", "y"])

# 2. typing.NamedTuple: the same idea with a class body and type annotations
class PointNT(NamedTuple):
    x: int
    y: int

# 3. dataclass: an ordinary class whose __init__, __repr__ and __eq__ are generated
@dataclass
class PointDC:
    x: int
    y: int

for p in (Point(3, 4), PointNT(3, 4), PointDC(3, 4)):
    # x*x + y*y is the squared distance from the origin: 3^2 + 4^2 = 25
    print(f"{type(p).__name__:8s} {p!r:22s} distance^2 = {p.x * p.x + p.y * p.y}")

print("Point(3, 4) == (3, 4):", Point(3, 4) == (3, 4))
print("PointDC(3, 4) == (3, 4):", PointDC(3, 4) == (3, 4))
a, b = Point(3, 4)
print("unpacked:", a, b)
print("annotations are not checked at runtime:", PointNT("three", 4))
```

```output
Point    Point(x=3, y=4)        distance^2 = 25
PointNT  PointNT(x=3, y=4)      distance^2 = 25
PointDC  PointDC(x=3, y=4)      distance^2 = 25
Point(3, 4) == (3, 4): True
PointDC(3, 4) == (3, 4): False
unpacked: 3 4
annotations are not checked at runtime: PointNT(x='three', y=4)
```

All three print 25, which is the hand calculation. The two `True` and `False` lines show that the named tuples are tuples and the dataclass is not.

## Under the hood: what an instance is made of

A `namedtuple` or `NamedTuple` instance is a tuple object. Its two fields sit in fixed slots inside that object, and it has no per-instance dictionary. A plain dataclass instance is an object whose fields live in a separate `__dict__`, which costs extra memory. A dataclass with `slots=True` puts its fields into slots, as the named tuples do.

![Three memory layouts: the named-tuple object holds x and y in slots, the dataclass object points to a separate dictionary with x and y, and the slots dataclass holds x and y in slots like the named tuple](diagrams/5.3-memory-layout.svg "Where the fields live. Sizes are per instance on Python 3.12.13.")

The `collections` documentation says named-tuple instances "do not have per-instance dictionaries, so they are lightweight and require no more memory than regular tuples" (Python Software Foundation, `collections` documentation). The code below measures that claim for the five types in the diagram. On this build the measured gap is about 8 bytes per instance (104.5 against 96.4 for a plain tuple), so the claim holds only approximately here. The lesson does not explain the gap.

<details><summary>Run locally: standard library only, measures bytes per instance</summary>

```python
import tracemalloc
from collections import namedtuple
from dataclasses import dataclass
from typing import NamedTuple

Point = namedtuple("Point", ["x", "y"])

class PointNT(NamedTuple):
    x: int
    y: int

@dataclass
class PointDC:
    x: int
    y: int

@dataclass(slots=True)
class PointSlots:
    x: int
    y: int

def bytes_per_instance(make, n=10000):
    tracemalloc.start()
    keep = [make(1000 + i) for i in range(n)]   # one int object per instance, shared by x and y
    current, _ = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    del keep
    return current / n

for name, make in [("tuple", lambda i: (i, i)), ("namedtuple", lambda i: Point(i, i)),
                   ("NamedTuple", lambda i: PointNT(i, i)), ("dataclass", lambda i: PointDC(i, i)),
                   ("slots dataclass", lambda i: PointSlots(i, i))]:
    print(f"{name:16s} {bytes_per_instance(make):6.1f} bytes")
```

```output
tuple              96.4 bytes
namedtuple        104.5 bytes
NamedTuple        104.5 bytes
dataclass         120.8 bytes
slots dataclass    88.5 bytes
```

Timing needs a separate run, and its numbers change with the machine. Use this script to time construction on yours:

```python
import timeit
from collections import namedtuple
from dataclasses import dataclass

Point = namedtuple("Point", ["x", "y"])

@dataclass
class PointDC:
    x: int
    y: int

@dataclass(frozen=True)
class PointFrozen:
    x: int
    y: int

N = 200_000
for name, stmt in [("namedtuple", "Point(1, 2)"), ("dataclass", "PointDC(1, 2)"),
                   ("frozen dataclass", "PointFrozen(1, 2)")]:
    best = min(timeit.repeat(stmt, globals=globals(), number=N, repeat=5)) / N * 1e9
    print(f"{name:18s} {best:6.1f} ns")
```

On the machine where this lesson was written, a call took about 147 ns for a namedtuple, 99 ns for a plain dataclass and 231 ns for a frozen dataclass. Treat these as one measurement, not a law: the frozen version pays for `object.__setattr__` calls in `__init__`, which the dataclass documentation mentions as a small cost (Python Software Foundation, `dataclasses` documentation).

</details>

## Changing a field

Here the three types differ most. Each row below runs the same kind of assignment and records what Python does.

![Table with four rows: namedtuple attribute assignment raises AttributeError; namedtuple item assignment raises TypeError; plain dataclass assignment succeeds; frozen dataclass assignment raises FrozenInstanceError](diagrams/5.3-mutation.svg "The same attempt to change x, four ways. Exception names are as printed by Python 3.12.13.")

The next block runs each attempt on a fresh object and prints the result.

```python
from collections import namedtuple
from dataclasses import dataclass
from typing import NamedTuple

Point = namedtuple("Point", ["x", "y"])

class PointNT(NamedTuple):
    x: int
    y: int

@dataclass
class PointDC:
    x: int
    y: int

@dataclass(frozen=True)
class PointFrozen:
    x: int
    y: int

def try_it(label, make, action):
    obj = make()
    try:
        action(obj)
        print(f"{label}: ok, now {obj!r}")
    except Exception as e:
        print(f"{label}: {type(e).__name__}: {e}")

def set_x(o):
    o.x = 10

def set_item(o):
    o[0] = 10

try_it("namedtuple  o.x ", lambda: Point(1, 2), set_x)
try_it("namedtuple  o[0]", lambda: Point(1, 2), set_item)
try_it("NamedTuple  o.x ", lambda: PointNT(1, 2), set_x)
try_it("dataclass   o.x ", lambda: PointDC(1, 2), set_x)
try_it("frozen dc   o.x ", lambda: PointFrozen(1, 2), set_x)
```

```output
namedtuple  o.x : AttributeError: can't set attribute
namedtuple  o[0]: TypeError: 'Point' object does not support item assignment
NamedTuple  o.x : AttributeError: can't set attribute
dataclass   o.x : ok, now PointDC(x=10, y=2)
frozen dc   o.x : FrozenInstanceError: cannot assign to field 'x'
```

A frozen dataclass raises `FrozenInstanceError`, which the dataclass documentation says is a subclass of `AttributeError` (Python Software Foundation, `dataclasses` documentation). So `except AttributeError` catches it. Replacing a field on a named tuple or frozen dataclass means building a new object; `_replace()` and `dataclasses.replace()` do that for you.

## Choosing one

Start from the question you need answered first: does the record have to behave like a tuple? Then decide on annotations or immutability. The flow below is a rule of thumb, not a ranking.

![Decision flow: first ask if the record must act like a tuple; if yes, ask about annotations to pick NamedTuple or namedtuple; if no, ask if it must be immutable and hashable to pick frozen dataclass or dataclass](diagrams/5.3-decide.svg "Choose the first leaf that matches your needs.")

The type checkers mentioned in the `typing` documentation read the annotations on a `NamedTuple` or dataclass, but the Python runtime does not (Python Software Foundation, `typing` documentation). That is why the `PointNT("three", 4)` call above succeeds.

## Common traps

> [!TRAP]
> "Immutable" means the fields cannot be reassigned. It does not freeze the objects inside them. A named tuple with a list field, such as `class Bag(NamedTuple)` with fields `name` and `items`, still lets you change the list: `Bag("bag", [1]).items.append(2)` changes the record to `Bag(name='bag', items=[1, 2])`.

> [!TRAP]
> Annotations are documentation for tools, not a check at runtime. `PointNT("three", 4)` runs without error. Run `mypy` or `pyright` to catch the mistake before you run the code.

> [!TRAP]
> A named tuple equals a plain tuple with the same values: `Point(3, 4) == (3, 4)` is `True`. A dataclass does not: `PointDC(3, 4) == (3, 4)` is `False`. Equality across types can hide a bug where a function returns the wrong kind of record.

> [!TRAP]
> A plain dataclass with the default `eq=True` sets `__hash__` to `None`, so it cannot go in a set or be a dictionary key. `frozen=True` makes it hashable again.

> [!TRAP]
> A frozen dataclass is hashable only if every field is hashable. `Tags(["a"])` with a list field raises `TypeError: unhashable type: 'list'` the moment you put it in a set.

## Summary

- `namedtuple` and `typing.NamedTuple` make tuple objects with named fields; they unpack, index and compare equal to plain tuples.
- A plain `dataclass` gives mutable fields and its own equality; `frozen=True` makes fields read-only and the object hashable.
- Immutability is shallow: a list inside any of these types can still change.
- `slots=True` on a dataclass removes the per-instance dictionary; on this machine it cut the size from 120.8 to 88.5 bytes.

### Question 1: Predict the output

```python
from collections import namedtuple
P = namedtuple("P", "x y")
print(P(1, 2) == (1, 2), P(1, 2) == P(1.0, 2.0))
```

<details><summary>Show Solution</summary>

The output is `True True`. A named tuple compares element by element like a plain tuple, and `1 == 1.0` is `True` in Python, so both comparisons succeed.

</details>

### Question 2: Find the bug

```python
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Tags:
    names: list = field(default_factory=list)

seen = {Tags(["a"])}
```

<details><summary>Show Solution</summary>

The set display calls `hash()` on the `Tags` object, and the generated `__hash__` hashes the `names` list. Lists are unhashable, so Python raises `TypeError: unhashable type: 'list'`. A fix is to store an immutable value, such as `names: tuple = ()`, so the generated hash works.

</details>

### Question 3: Predict what happens

```python
from typing import NamedTuple

class Pair(NamedTuple):
    a: int
    b: int = 0

pair = Pair(5)
print(pair)
pair.b = 9
```

<details><summary>Show Solution</summary>

The first line prints `Pair(a=5, b=0)`, because the default fills `b`. The second line raises `AttributeError: can't set attribute`. A `NamedTuple` does not allow assignment to its fields, and the error occurs after the print.

</details>

### Question 4: Explain the choice

A team wants a record that is used as a dictionary key, is checked by `mypy`, is never changed after creation, and should not compare equal to plain tuples. Which type do you choose, and why not `namedtuple`?

<details><summary>Show Solution</summary>

Choose a `frozen=True` dataclass with annotated fields. It is hashable and read-only, and its equality does not match plain tuples. A `namedtuple` also hashes, but it has no annotations for `mypy` to read, and it compares equal to any tuple with the same values, which is the behaviour the team wants to avoid.

</details>
