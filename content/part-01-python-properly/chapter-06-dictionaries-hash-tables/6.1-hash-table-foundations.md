In this lesson you will explain how a dictionary turns a key into a slot in a table, why `__hash__` and `__eq__` must agree, and why a key that changes after insertion becomes unreachable. You will measure lookup cost by counting `__eq__` calls, because counts do not depend on your computer's speed.

**You need:** names and objects (Lesson 2.1) and lists (Lesson 4.1). All code here uses only the standard library.

## The problem a dictionary solves

A list finds a value by comparing the key with its elements one at a time. To look up a key among 1,000 keys, Python may compare it with all 1,000. A dictionary (`dict`) answers the same question in roughly constant time, written O(1): the work does not grow with the number of keys. It does this by computing a number from the key and jumping straight to a slot. That structure is a **hash table**: an array of slots plus a function, `hash()`, that turns each key into an integer. At a million keys, a list scan may make a million comparisons for one absent key, while the dictionary makes one hash computation and, in the measurements below, no comparisons at all.

## Hash, then mask

`hash(key)` returns an integer. A table with 8 slots keeps only the low three bits of that integer, which is the bitwise AND with 7 (binary `111`). CPython's source calls that value the **mask**.

![Key 13 goes through hash(13) = 13, then 13 AND 7 = 5, to slot 5; the bits 1101 AND 0111 give 0101](diagrams/6.1-key-to-slot.svg "The slot is the low bits of the hash. Worked by hand: 1101 AND 0111 = 0101 = 5.")

The worked example is the one in the figure. Key 13 is `1101` in binary; the mask `0111` keeps the low three bits, `101`, which is 5. The code reproduces it:

```python
from collections import Counter

print(hash(13), hash(-1), hash(True), hash(1.0))
print(hash(2**61 - 1))

MASK = 7                                  # 8 slots: slot = hash & 7
for key in [13, 8, -1]:
    print(key, "-> slot", hash(key) & MASK)

print("keys 0, 8, ..., 56 by slot:", dict(Counter(k & MASK for k in range(0, 64, 8))))

d = {1: "int key"}
print(d[True], d[1.0])                    # True and 1.0 compare equal to 1
```

```output
13 -2 1 1
0
13 -> slot 5
8 -> slot 0
-1 -> slot 6
keys 0, 8, ..., 56 by slot: {0: 8}
int key int key
```

Two lines need explaining. `hash(-1)` is `-2`: CPython, the C implementation of Python you most likely run, reserves -1 as an error code in its C hash function, so it never returns -1 for an integer (`Objects/longobject.c`, `long_hash`). `d[True]` and `d[1.0]` both find the key `1`, because equal values must hash equally, and `True == 1` and `1.0 == 1` are both true.

## Collisions are structural

Keys 0 to 7 fill slots 0 to 7, one each. Keys 0, 8, 16, ..., 56 all end in the bits `000`, so all eight map to slot 0. Two keys that want the same slot are a **collision**. Collisions are normal: with more keys than slots they are certain, and even with spare slots some pairs of keys will share one. The table handles them by probing for another slot, which is the subject of Lesson 6.3. A hash function that spreads keys evenly keeps collisions rare.

The mask trick needs a power-of-two size. For a size of $2^k$, `hash & (size - 1)` keeps the low $k$ bits, which equals `hash % size` for every integer. This follows from two's complement arithmetic (reasoning; the examples above agree). The table therefore keeps its size a power of two and grows when it fills; Lesson 6.4 covers resizing.

![Eight keys 0 to 7 fill slots 0 to 7 one each; keys 0, 8, 16, ..., 56 all land in slot 0](diagrams/6.1-slot-collisions.svg "The same mask sends eight keys to one slot when they share their low bits.")

## Measuring cost by counting `__eq__`

Timings depend on the machine, so we count instead. For ordinary keys, CPython stores each entry's full hash next to its key. A lookup compares that hash with the lookup hash, and calls `__eq__` only when they match (`Objects/dictobject.c`, the `ep->me_hash == hash` check in the lookup code). A dict whose keys are all `str` omits the stored hash, because the `str` object carries its own (Lesson 6.2). A list calls `__eq__` for every element it scans, so the count is the cost.

```python
class Key:
    eq_calls = 0                          # counts how often __eq__ runs

    def __init__(self, v):
        self.v = v

    def __hash__(self):
        return hash(self.v)

    def __eq__(self, other):
        Key.eq_calls += 1
        return isinstance(other, Key) and self.v == other.v

n = 1000
lst = [Key(i) for i in range(n)]
dct = {Key(i): i for i in range(n)}

Key.eq_calls = 0
Key(-1) in lst
print("list, absent:", Key.eq_calls)

Key.eq_calls = 0
Key(-1) in dct
print("dict, absent:", Key.eq_calls)

Key.eq_calls = 0
Key(n // 2) in dct
print("dict, present:", Key.eq_calls)


class Constant(Key):
    def __hash__(self):
        return 0                          # every key in one probe chain


bad = {Constant(i): i for i in range(n)}
Key.eq_calls = 0
Constant(-1) in bad
print("all hashes 0, absent:", Key.eq_calls)
```

```output
list, absent: 1000
dict, absent: 0
dict, present: 1
all hashes 0, absent: 1000
```

How the counter works:

- `Key.__eq__` increments the class attribute `eq_calls` each time Python compares two keys.
- Setting `Key.eq_calls = 0` before each lookup isolates that lookup's count.
- A bare `Key(-1) in lst` evaluates the membership test; only the count matters here.

![Bar chart of __eq__ calls per lookup for 1000 keys: list absent 1000, dict absent 0, dict present 1, dict with equal hashes absent 1000](diagrams/6.1-eq-calls.svg "Counts from the code above. The last bar is the failure case shown next.")

The list pays one call per element. The dictionary pays nothing for the absent key, because `Key(-1)` has hash -2 and no stored entry has that hash. It pays one call for the present key, which is the match.

Why this is constant time on average. If keys spread evenly over the slots, a lookup touches about one slot and makes about one hash comparison, so its expected cost does not depend on the number of keys. This is reasoning from the mask arithmetic, not a theorem. It holds while collisions stay rare, and their frequency depends on the ratio of keys to slots (the load factor, covered in Lesson 6.4). When every key collides, as in the next example, the average-case argument fails and the lookup becomes linear.

The last count, from `Constant`, gives every key hash 0. Each stored entry then has the same full hash as the lookup key, so each one is compared, and the dictionary has become a list scan. This is why a bad `__hash__` is a performance bug, and why the hash function matters.

## The `__hash__` contract

The Python data model reference states the rule: "the only required property is that objects which compare equal have the same hash value" (`object.__hash__`, Python documentation). Two consequences follow.

If a class defines `__eq__` and not `__hash__`, Python sets `__hash__` to `None`, and its instances cannot be dictionary keys or set members:

```python
try:
    {[1, 2]: "x"}
except TypeError as e:
    print("TypeError:", e)

class Person:
    def __init__(self, name):
        self.name = name

    def __eq__(self, other):
        return isinstance(other, Person) and self.name == other.name

print(Person.__hash__)
try:
    {Person("a"): 1}
except TypeError as e:
    print("TypeError:", e)
```

```output
TypeError: unhashable type: 'list'
None
TypeError: unhashable type: 'Person'
```

The data model also says that a class with mutable state that implements `__eq__` should not implement `__hash__`, because a key's hash must stay fixed while the key sits in a table. Here is what happens when it does not:

```python
class Pt:
    def __init__(self, name):
        self.name = name

    def __eq__(self, other):
        return isinstance(other, Pt) and self.name == other.name

    def __hash__(self):
        return hash(self.name)

p = Pt("a")
table = {p: "value"}
p.name = "b"                              # the key changes after insertion
print("Pt('b') in table:", Pt("b") in table)
print("len:", len(table))
```

```output
Pt('b') in table: False
len: 1
```

The entry is still in the table, in the slot for `hash("a")`. A new object named `"b"` goes to the slot for `hash("b")`, and the stored entry still carries `hash("a")`, so the lookup never matches it. The table cannot reach the entry it holds. Nothing checks that a key still matches its stored hash, so no error is raised. The test uses a new object on purpose. A dict checks identity (`is`) before it compares hashes, so a lookup with `p` itself can succeed by chance when `hash("a")` and `hash("b")` share a slot, and the result then depends on the hash seed. The figure below shows the layout.

![Three rows: insert key a into its slot; change its name to b, the entry stays put; lookup of b goes to the slot for b, which is empty](diagrams/6.1-stale-key.svg "Slot positions are illustrative. The stored entry does not move when the key changes.")

The last requirement is that equal objects share a hash. A class whose `__hash__` uses identity (the default for plain objects) can compare equal yet hash differently:

```python
class Tag:
    def __init__(self, s):
        self.s = s

    def __eq__(self, other):
        return isinstance(other, Tag) and self.s == other.s

    __hash__ = object.__hash__            # identity-based: breaks the contract

t = {Tag("x"): 1}
print(Tag("x") == Tag("x"), Tag("x") in t)
```

```output
True False
```

The dictionary is right to miss here. It probed from the slot that the lookup key's hash names and found no entry with an equal hash. The fault is in the class, which says two objects are equal but gives them unrelated hashes.

![Left: two equal objects with equal hashes share a slot and are found. Right: equal objects with identity hashes land in different slots and are missed](diagrams/6.1-hash-contract.svg "Equal objects must have equal hashes, or a lookup looks in the wrong slot.")

`hash()` is not a unique identifier. Different objects can share a hash, as the collisions above show, and CPython randomizes string hashes to defend against inputs crafted to make dictionaries slow (the `PYTHONHASHSEED` reference). Do not assume either property holds for your own objects.

## Common traps

> [!TRAP]
> `1`, `True` and `1.0` are one dictionary key. `d[True] = "yes"` overwrites the entry for `1`, and `len(d)` does not change.

> [!TRAP]
> Defining `__eq__` in a class removes `__hash__` unless you define `__hash__` again. The error appears only when you first put an instance in a set or dict.

> [!TRAP]
> A hash that uses mutable fields becomes stale when those fields change. The entry stays in the table, and lookups fail silently; no error is raised.

> [!TRAP]
> The hash of a `str` or `bytes` object changes from one process to the next unless `PYTHONHASHSEED` is fixed. The Python documentation says the values "remain constant within an individual Python process, [but] are not predictable between repeated invocations". Never store hash values in files or compare them across runs.

## Summary

- A dictionary maps a key to a slot: `hash(key)` gives an integer, and the table uses its low bits (`hash & (size - 1)` when the size is a power of two).
- Keys that share a slot collide. The table resolves collisions by probing (Lesson 6.3).
- A lookup calls `__eq__` only when stored and lookup hashes match. A list lookup costs one `__eq__` call per element; a dictionary lookup, usually none.
- Equal objects must have equal hashes. Defining `__eq__` without `__hash__` makes instances unhashable.
- A key must not change while it is in a dictionary, or its entry becomes unreachable.

## Quiz time

### Question 1: Calculation

A table has 16 slots. Which slot does `hash(27)` use? Give the binary steps.

<details><summary>Show Solution</summary>

In CPython, `hash(27)` is 27, the same pattern as `hash(13)` in the output above. In binary, 27 is `11011`. The mask for 16 slots is `01111`. AND gives `01011`, which is 11. Slot 11.

</details>

### Question 2: Prediction

```python
d = {1: "one"}
d[True] = "yes"
print(len(d), d[1])
```

<details><summary>Show Solution</summary>

The output is `1 yes`. `True` hashes and compares like `1`, so the assignment overwrites the value of the existing key. The key object stays `1`, and the length stays 1.

</details>

### Question 3: Bug-spotting

```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __eq__(self, other):
        return (self.x, self.y) == (other.x, other.y)

seen = {Point(0, 0)}
```

<details><summary>Show Solution</summary>

The class defines `__eq__` but not `__hash__`, so Python sets `__hash__` to `None`, and the set construction raises `TypeError: unhashable type: 'Point'`. The fix is to add `def __hash__(self): return hash((self.x, self.y))`. The fix is safe only if `x` and `y` are never changed while the point is in a set. The `other.x` access also fails when `other` is not a `Point`; an `isinstance` check, as in the lesson, fixes that.

</details>

### Question 4: Explanation

A list and a dictionary each hold 10,000 distinct `Key` objects (the class with a Python-level `__eq__` from this lesson). For an absent key whose hash matches no stored key, how many `__eq__` calls does each structure make, and why?

<details><summary>Show Solution</summary>

The list makes 10,000 calls, one per element, because it has no way to skip elements. The dictionary makes 0 calls, because no stored entry has the lookup key's full hash, so CPython never reaches the `__eq__` comparison. Plain `int` keys compare in C and never run Python's `__eq__`, so these counts apply to the `Key` class, not to ints.

</details>
