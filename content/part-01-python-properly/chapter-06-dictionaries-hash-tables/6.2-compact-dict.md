After this lesson you can read the two arrays inside a CPython 3.12 dictionary, trace by hand where a key is stored, and predict when a dictionary's memory changes after inserts and deletes. Since CPython 3.6 a dict keeps a small index table and a dense list of entries, which is why it remembers insertion order and why deleting keys does not shrink it.

**You need:** the idea that a hash table turns a hash into a slot number (Lesson 6.1), and `sys.getsizeof`, which returns the bytes of the object's own allocation and not of the objects it refers to.

## The problem this layout solves

A hash table keeps free slots so that lookups stay short, so most of its slots are empty. Suppose every slot stored a full entry: a hash, a key pointer and a value pointer, 24 bytes on a 64-bit machine. For 1000 entries, CPython uses a 2048-slot table (measured below). That is 2048 × 24 bytes, and 1048 of those slots hold nothing. The iteration order would also follow the hash-determined slots, not the order you inserted the keys.

The compact layout, introduced in CPython 3.6, splits the table in two. The 3.6 release notes say the new implementation gave dictionaries "20% to 25% less memory when compared to Python 3.5" (ref 1). The two parts are:

- an **index table** of small signed integers, one per slot. A value $\geq 0$ names an entry; $-1$ means empty, and $-2$ is a third marker, `DKIX_DUMMY` (ref 2).
- a dense **entries array** in insertion order. Each entry holds a hash, a key and a value.

> [!WARNING]
> An earlier draft of this lesson called the layout "PEP 468". That is wrong: PEP 468 is "Preserving the order of **kwargs in a function" (ref 5). I found no PEP for this layout; the sources here are the release notes and CPython source.

## Intuition: an index and a list

![Index table with eight slots, each holding an entry number or -1, with arrows to four entries stored in insertion order](diagrams/6.2-worked-index.svg "Four keys in a size-8 table. Each filled index slot points to an entry; the entries are never reordered.")

Read the picture from the left. Slot 3 holds 0, so it points to entry 0, which is the key 3. The index is small and sparse; the entries are dense and ordered by when you inserted them. Insertion order therefore comes from the entries list, not from the hash.

## Worked example by hand

For small non-negative integers, `hash(k) = k`. The table has 8 slots, so its mask is 7 and the first slot is `hash & 7`. CPython probes with a `perturb` value that starts as the hash. Each probe does `perturb >>= 5` and then `i = (5*i + perturb + 1) & 7` (ref 3).

| key | hash | first slot (hash & 7) | probes | final slot |
|---|---|---|---|---|
| 3 | 3 | 3, empty | none | 3 |
| 11 | 11 | 3, taken by 3 | perturb = 0, so slot (3·5 + 0 + 1) & 7 = 0, empty | 0 |
| 19 | 19 | 3, taken | slot 0, taken by 11; then slot (0·5 + 0 + 1) & 7 = 1, empty | 1 |
| 5 | 5 | 5, empty | none | 5 |

The index is therefore `[1, 2, -1, 0, -1, 3, -1, -1]`. Slot 0 holds entry 1 (key 11), slot 1 holds entry 2 (key 19), slot 3 holds entry 0 (key 3), and slot 5 holds entry 3 (key 5). The probe recurrence is the same one used in CPython's lookup loop (ref 3). The probe loop below reproduces it with plain integers:

```python
MASK = 7  # table of 8 slots

def probe_slots(h, n=4):
    """First n slots CPython tries for integer hash h (same recurrence as the lookup loop)."""
    perturb, i, slots = h, h & MASK, []
    for _ in range(n):
        slots.append(i)
        perturb >>= 5
        i = (i * 5 + perturb + 1) & MASK
    return slots

for h in [3, 11, 19, 5, 27]:
    print(h, probe_slots(h))
```

```output
3 [3, 0, 1, 6]
11 [3, 0, 1, 6]
19 [3, 0, 1, 6]
5 [5, 2, 3, 0]
27 [3, 0, 1, 6]
```

Key 27 arrives later. It probes 3 (taken by 3), 0 (taken by 11), 1 (taken by 19), and lands in slot 6, which is empty. A measured check puts it there: the index becomes `[1, 2, -1, 0, -1, 3, 4, -1]`.

The output shows something specific to small integers. Every integer below 32 has `perturb` equal to 0 after one shift, so its probe sequence depends only on its first slot: 3, 11, 19 and 27 share the same walk, `i → 5i + 1 (mod 8)`, and the walk is the same whether those slots are full or empty. For larger hashes, the high bits enter the probe sequence. The code prints candidate slots only; it does not touch a real dict.

## Measured internals (CPython 3.12)

The next block reads the dict's internal memory with `ctypes`, the Python foreign-function library. It is CPython 3.12 only, and the field offsets come from `pycore_dict.h` (ref 2).

<details><summary>Run locally: CPython 3.12 only (ctypes, no pip install)</summary>

```python
import ctypes as C
import sys

def dict_internals(d):
    """Read the keys object of a CPython 3.12 dict (layout from Include/internal/pycore_dict.h)."""
    k = C.c_void_p.from_address(id(d) + 32).value        # PyDictObject.ma_keys
    log2_size = C.c_uint8.from_address(k + 8).value      # dk_log2_size
    log2_index = C.c_uint8.from_address(k + 9).value     # dk_log2_index_bytes
    kind = C.c_uint8.from_address(k + 10).value          # dk_kind: 1 = unicode-only keys
    nentries = C.c_ssize_t.from_address(k + 24).value    # dk_nentries: entry slots used, holes included
    return dict(dk_size=2 ** log2_size, index_bytes=2 ** log2_index,
                entry_bytes=16 if kind == 1 else 24, nentries=nentries)

def index_slots(d):
    i = dict_internals(d)
    base = C.c_void_p.from_address(id(d) + 32).value + 32
    width = i["index_bytes"] // i["dk_size"]             # 1, 2 or 4 bytes per index slot
    T = {1: C.c_int8, 2: C.c_int16, 4: C.c_int32}[width]
    return [T.from_address(base + j * width).value for j in range(i["dk_size"])]

d = {}
for k in [3, 11, 19, 5]:
    d[k] = k * 10
print(dict_internals(d))
print(index_slots(d))
print("sys.getsizeof:", sys.getsizeof(d))

big = {n: n for n in range(1000)}
print(dict_internals(big), "sys.getsizeof:", sys.getsizeof(big))
```

```output
{'dk_size': 8, 'index_bytes': 8, 'entry_bytes': 24, 'nentries': 4}
[1, 2, -1, 0, -1, 3, -1, -1]
sys.getsizeof: 224
{'dk_size': 2048, 'index_bytes': 4096, 'entry_bytes': 24, 'nentries': 1000} sys.getsizeof: 36952
```

</details>

The reader returns the same index array we derived by hand. It also gives the measured size of the table for 1000 keys: 2048 slots, a 4096-byte index, and 24-byte entries. The offsets were checked on this machine: the experiment's size formula matches `sys.getsizeof` at all 13 resize points and at nine other sizes. A layout change in a later CPython would break the reader, so it is for study only.

## Sizes grow in steps

A dict resizes when its entries array is full. The table size doubles each time, and the usable capacity is two-thirds of the slots. The experiment recorded every resize while inserting 70,000 integer keys. The first few are below, and the full list is in the data file.

| entries after resize | table slots (`dk_size`) | index width | capacity | `sys.getsizeof` |
|---|---|---|---|---|
| 1 | 8 | 1 byte | 5 | 224 |
| 6 | 16 | 1 byte | 10 | 352 |
| 43 | 128 | 1 byte | 85 | 2264 |
| 86 | 256 | 2 bytes | 170 | 4688 |
| 21846 | 65536 | 4 bytes | 43690 | 1310800 |

The index width steps up at 256 slots and again at 65536. Diagram 2 shows the rule. My reasoning, checked against the measured widths: the index is signed, so it must hold every value from 0 to capacity minus 1, plus the markers -1 and -2. A 1-byte signed integer holds up to 127; a 2-byte one holds up to 32767. The header comment in `pycore_dict.h` says 1 byte for `dk_size` up to 0xff. The measurement says 256 slots already need 2 bytes, so I follow the measurement.

![Table of four table sizes with index width, largest index stored and whether it fits a signed type; rows at 256 and 65536 slots change width](diagrams/6.2-index-width.svg "The index width steps up when the largest index no longer fits in a signed type.")

## Deletion leaves holes

Deleting a key does not remove its entry from the entries array. The entry becomes a hole, and the table stays at its size. The experiment inserted 1000 keys, deleted 999 of them, and then inserted one more key.

![Three strips showing entries before deletes, after 999 deletes as holes, and after copy() as a compact table](diagrams/6.2-deletion-holes.svg "Deleting marks entries as holes; the allocation stays until a copy or a resize.")

Measured after 999 deletes: `len` is 1, but 1000 entry slots are still used, 999 of them holes, and `sys.getsizeof` is still 36952 bytes. The one extra insert takes entry slot 1001. The holes disappear when the dict is copied: `d.copy()` of the two-key dict gives 2 entry slots at a 16-slot table, 352 bytes.

Insertion order is part of the language since Python 3.7 (ref 4). The block below shows it, and shows that deleting and re-inserting a key puts it at the end.

```python
d = {}
for key in ["b", "a", "c"]:
    d[key] = len(d)
print(list(d))
del d["a"]
d["a"] = 9
print(list(d))
```

```output
['b', 'a', 'c']
['b', 'c', 'a']
```

## Where the bytes go

For 1000 integer keys, `sys.getsizeof` returns 36952 bytes. The breakdown is 4096 bytes of index table, 24000 bytes for 1000 used entries, 8760 bytes for 365 allocated but empty entry slots, and a 96-byte header. The header is the dict object plus the keys header. The 32-byte keys header follows from the struct fields in `pycore_dict.h` (ref 2). The 48-byte dict object and the 16 bytes of garbage-collector overhead are my reading, not a quoted source; together they make the formula match `sys.getsizeof` exactly at every size in the experiment.

![Stacked bars for 1000 str keys and 1000 int keys, showing index table, used entries and spare entry slots](diagrams/6.2-bytes-breakdown.svg "Where the bytes go. The 96-byte header is not drawn.")

Str keys are cheaper: 26032 bytes against 36952. Their entries are 16 bytes instead of 24, because a str object carries its own hash, so the entry need not store it (ref 2, `PyDictUnicodeEntry`). A model, not a measurement: if every slot of the 2048-slot table held a full 24-byte entry, the entries alone would need 49,152 bytes, which is more than the 36,952 measured here.

> [!TRAP]
> `sys.getsizeof` counts only the dict's own allocation. The 1000 key and value objects are not included. The formula in this lesson matched the measurement without them, so the key and value objects are not counted.

> [!TRAP]
> Deleting keys does not shrink a dict. Measured: 999 deletes left `sys.getsizeof` at 36952 bytes. To release the space, build a new dict with `d.copy()` or a comprehension. A later resize can also shrink it; Lesson 6.4 shows this.

> [!TRAP]
> Insertion order was an implementation detail in 3.6 and became part of the language in 3.7 (ref 4). Code that needs order on 3.6 or earlier should not rely on it.

> [!TRAP]
> The reader above depends on CPython 3.12 offsets. Other interpreters may lay out dicts differently; I did not verify PyPy or any other implementation.

## Summary

- A CPython dict keeps a small index table of signed integers (-1 empty, -2 dummy) and a dense list of entries in insertion order.
- The index width steps up when the largest index no longer fits a signed type: 1 byte up to 128 slots, 2 bytes up to 32768, 4 bytes above.
- Deleting a key leaves a hole and keeps the allocation; `d.copy()` compacts it.
- `sys.getsizeof` returns the dict's own allocation: the index, the entries and a 96-byte header, not the key and value objects.

## Quiz time

### Question 1: Where does key 27 land?

The table already holds keys 3, 11, 19 and 5 in a size-8 table, with the index `[1, 2, -1, 0, -1, 3, -1, -1]`. Trace the probe sequence for 27, using `perturb = hash`, `perturb >>= 5`, and `i = (5*i + perturb + 1) & 7`.

<details><summary>Show Solution</summary>

The first slot is `27 & 7 = 3`, which is taken. Then `perturb = 27 >> 5 = 0`, so `i = (15 + 0 + 1) & 7 = 0`, which is taken by 11. Next `i = (0 + 0 + 1) & 7 = 1`, taken by 19. Next `i = (5 + 0 + 1) & 7 = 6`, which is empty. Key 27 lands in slot 6, and the index becomes `[1, 2, -1, 0, -1, 3, 4, -1]`. The experiment measured exactly this.

</details>

### Question 2: What does a copy do after deletes?

A dict `d` holds 1000 int keys and then has 999 of them deleted. Then `d[10**6] = 0` is added, so `d` has 2 keys. What are `len(c)` and `sys.getsizeof(c)` for `c = d.copy()`?

<details><summary>Show Solution</summary>

`len(c)` is 2. The copy has 2 entry slots and a 16-slot table, and `sys.getsizeof(c)` is 352 bytes on CPython 3.12, as measured. The original `d` still has 1001 entry slots and `sys.getsizeof` of 36952 bytes, which the copy does not change.

</details>

### Question 3: Spot the wrong claim

A student says: "My dict has 1000 string keys, so `sys.getsizeof(d)` includes the 1000 string objects, which is why it is large." What is wrong?

<details><summary>Show Solution</summary>

`sys.getsizeof` counts the dict's own allocation only. For 1000 str keys it is 26032 bytes, which is the index table (4096), the used entries (16000), the spare entry slots (5840) and the 96-byte header. The key strings are separate objects and are not in that number. The formula in the experiment matched the measurement without them.

</details>

### Question 4: Why 2 bytes at 256 slots?

A table with 256 slots can hold indices up to 169. Why does it not use 1 byte per index slot?

<details><summary>Show Solution</summary>

A signed 1-byte integer holds values from -128 to 127. The largest index 169 does not fit, so the index needs 2 bytes, which hold up to 32767. The measured widths show the step at 256 slots, and the reasoning is in the Sizes section.

</details>
