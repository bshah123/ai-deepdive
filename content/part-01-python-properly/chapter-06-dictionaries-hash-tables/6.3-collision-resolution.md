Open addressing keeps every entry in the table's own slots, so a key whose home slot is taken must probe for another slot, and every later lookup must retrace that path. In this lesson you will trace a probe sequence by hand, see why the obvious way to delete an entry breaks lookups, and measure how probing cost rises as the table fills.

**You need:** a hash table maps `key % size` to a home slot (Lesson 6.1), and a dict keeps its entries in an array of slots (Lesson 6.2).

## The problem

In a 10-slot table, `1 % 10` and `11 % 10` are both 1, so two keys want the same slot. Separate chaining would keep a list in that slot. Open addressing keeps one entry per slot, so the second key must go somewhere else, and every lookup must be able to find that somewhere. The rule that makes this work is the probe sequence.

## Intuition: one collision, three probe orders

![Eight slots and one home slot, slot 5. Three rows show the order in which linear probing, triangular probing and CPython's recurrence visit the slots. Linear goes 5, 6, 7, 0 and onward; triangular goes 5, 6, 0, 3; CPython goes 5, 2, 3, 0.](diagrams/6.3-probe-orders.svg "Same home slot, three probe orders. The number above each slot is its visit order.")

A probe sequence is the list of slots a key visits, starting at its home slot. Three schemes appear in this lesson:

- **Linear probing** steps forward by 1 each time, modulo the table size.
- **Triangular probing** steps by 1, then 2, then 3, and so on. This is the old lesson's code.
- **CPython 3.12** (the C implementation of Python) multiplies by 5, adds 1 and a perturbation taken from the hash, and masks the result. Its details are covered below.

## Worked example by hand: linear probing

Use linear probing in a 10-slot table.

1. `insert(1)`: home slot 1 is free, so key 1 goes in slot 1.
2. `insert(2)`: home slot 2 is free, so key 2 goes in slot 2.
3. `insert(11)`: slot 1 holds key 1, slot 2 holds key 2, and slot 3 is free. Key 11 goes in slot 3, so its probe path is 1, 2, 3.
4. `search(11)` retraces 1, 2, 3 and finds key 11 on the third probe.

Now delete key 2 the obvious way: set its slot to `None`, which means empty. `search(11)` visits slot 1, then slot 2, sees an empty slot, and reports the key missing, although key 11 sits in slot 3. An empty slot means "no entry can lie beyond this point on the path", so emptying a slot in the middle of a chain cuts the chain.

![Two rows of a 10-slot table after inserting keys 1, 2 and 11 and deleting key 2. In the top row a naive delete leaves slot 2 empty, and the search for key 11 stops there. In the bottom row a tombstone marks slot 2 as deleted, and the search continues to slot 3.](diagrams/6.3-delete-bug.svg "The search for key 11 after deleting key 2: naive delete (top), tombstone (bottom).")

The fix is a **tombstone**: a marker meaning "deleted here, keep probing". Insertion may reuse a tombstone, but search never stops at one. CPython marks deleted slots the same way, with `DKIX_DUMMY` in its index table. The code below implements both versions. Its output matches the trace above.

```python
DUMMY = object()   # tombstone: "deleted here, keep probing"


class ProbeTable:
    """Open addressing with linear probing. tombstones=False gives the naive delete."""

    def __init__(self, size, tombstones=True):
        self.size = size
        self.tombstones = tombstones
        self.slots = [None] * size   # None = never used, DUMMY = deleted, (key, value) = live

    def _probe(self, key):
        home = key % self.size
        for step in range(self.size):          # at most one full lap
            yield (home + step) % self.size

    def insert(self, key, value):
        for s in self._probe(key):             # update the key if it is already present
            entry = self.slots[s]
            if entry is None:                  # never-used slot: the key cannot be further on
                break
            if entry is not DUMMY and entry[0] == key:
                self.slots[s] = (key, value)
                return
        for s in self._probe(key):             # otherwise take the first free slot
            if self.slots[s] is None or self.slots[s] is DUMMY:
                self.slots[s] = (key, value)
                return
        raise RuntimeError("table is full")

    def search(self, key):
        for s in self._probe(key):
            entry = self.slots[s]
            if entry is None:                  # a never-used slot ends the chain
                return None
            if entry is not DUMMY and entry[0] == key:
                return entry[1]
        return None

    def delete(self, key):
        for s in self._probe(key):
            entry = self.slots[s]
            if entry is None:
                return
            if entry is not DUMMY and entry[0] == key:
                self.slots[s] = DUMMY if self.tombstones else None
                return


if __name__ == "__main__":
    for tombstones in (False, True):
        t = ProbeTable(10, tombstones=tombstones)
        t.insert(1, "One")
        t.insert(2, "Two")
        t.insert(11, "Eleven")
        t.delete(2)
        label = "tombstones" if tombstones else "naive delete"
        print(f"{label}: search(11) = {t.search(11)}")
```

```output
naive delete: search(11) = None
tombstones: search(11) = Eleven
```

## Under the hood: why the probe order matters

Linear probing forms clusters. A run of occupied slots makes every key whose home falls in the run pay for the whole run, and the run keeps growing. Triangular probing spreads the probes out, but it has a trap. A 10-slot table is not a power of two, and from slot 0 the triangular sequence reaches only six of the ten slots.

![Two rows. Size 10: from home slot 0, triangular probing reaches slots 0, 1, 3, 5, 6 and 8, and never slots 2, 4, 7 and 9. Size 8: all eight slots are reached. Labels give the probe on which each slot is first reached.](diagrams/6.3-reachable-slots.svg "Reachable slots from home slot 0, with the probe on which each is first reached.")

The old lesson's `insert` loops while the probed slot is occupied. After six keys with home slot 0 fill the six reachable slots, a seventh key never finds a free slot on its path, so the loop never ends. The size-8 row reached every slot in the check I ran, but I have not proved that for every power of two. CPython sizes its tables as powers of two; the comment in `Objects/dictobject.c` that works through a table of size $2^i$ describes this design.

CPython's recurrence is `i = (i*5 + perturb + 1) & mask`, with `perturb >>= 5` before each step, starting from the full hash. Without the perturbation term, $j \leftarrow 5j + 1 \pmod{2^i}$ visits every slot exactly once. The perturbation brings the higher bits of the hash into the path, so two keys with the same low bits follow different sequences. The source comment says the probe sequence then "depends (eventually) on every bit in the hash code."

```python
def linear(home, size):
    k = 0
    while True:
        yield (home + k) % size
        k += 1

def triangular(home, size):
    off, step = 0, 0
    while True:
        yield (home + off) % size
        step += 1
        off += step

def cpython(h, mask):
    i = h & mask
    perturb = h
    yield i
    while True:
        perturb >>= 5
        i = (i * 5 + perturb + 1) & mask
        yield i

def take(gen, n):
    return [next(gen) for _ in range(n)]

print("linear     :", take(linear(5, 8), 8))
print("triangular :", take(triangular(5, 8), 8))
print("cpython    :", take(cpython(5, 7), 8))
```

```output
linear     : [5, 6, 7, 0, 1, 2, 3, 4]
triangular : [5, 6, 0, 3, 7, 4, 2, 1]
cpython    : [5, 2, 3, 0, 1, 6, 7, 4]
```

For hash 5 the perturbation is zero after one shift, so the CPython order is the pure $5j+1$ order. Larger hashes change it.

## Cost: how many probes?

Let $\alpha = n/m$ be the load factor: $n$ entries in $m$ slots. Assume uniform hashing, meaning each probe lands on an occupied slot with probability $\alpha$, independently of the others. The expected number of probes $E$ for an unsuccessful search satisfies $E = 1 + \alpha E$, because the first probe either ends the search or lands on an occupied slot and the situation restarts. So

$$
E_{\text{miss}} = \frac{1}{1-\alpha}
$$

A successful search costs the same as the insertion did. Insertion at load $u$ costs $1/(1-u)$, and the entries are spread evenly over loads from 0 to $\alpha$, so the average is

$$
E_{\text{hit}} = \frac{1}{\alpha}\int_0^{\alpha} \frac{du}{1-u} = \frac{1}{\alpha}\ln\frac{1}{1-\alpha}
$$

At $\alpha = 0.5$ these give 2.00 and 1.39 probes. At $\alpha = 0.9$ they give 10.00 and 2.56. The chart below sets these formulas beside the measured costs.

![Bars for unsuccessful-search probes at four loads on a log scale. Linear probing rises from 1.39 to 44.6, triangular probing reaches 12.0 at load 0.9, CPython reaches 10.3, and the uniform formula gives 10.0.](diagrams/6.3-probe-cost.svg "Probes per unsuccessful search, measured (filled bars) and from the uniform-hashing formula (outline).")

The measurement fills a 16,384-slot table with random keys, then probes it, averaging four independent tables. The script is in the first block below.

<details><summary>Run locally: standard library only, about 2 seconds</summary>

```python
import math, random

def linear(home, size):                 # probes home, home+1, home+2, ... (mod size)
    k = 0
    while True:
        yield (home + k) % size
        k += 1

def triangular(home, size):             # probes home, home+1, home+3, home+6, ... (mod size)
    off, step = 0, 0
    while True:
        yield (home + off) % size
        step += 1
        off += step

def cpython(h, mask):                   # CPython 3.12 recurrence, Objects/dictobject.c
    i = h & mask
    perturb = h & (2**64 - 1)
    yield i
    while True:
        perturb >>= 5
        i = (i * 5 + perturb + 1) & mask
        yield i

def seq_linear(h, mask):
    return linear(h & mask, mask + 1)

def seq_triangular(h, mask):
    return triangular(h & mask, mask + 1)

def measure_one(seq_fn, m, alpha, seed, n_unsucc=20000):
    rng = random.Random(seed)
    keys = [rng.getrandbits(64) for _ in range(int(alpha * m))]
    table, mask = [None] * m, m - 1
    for k in keys:                      # insert: first free slot along the probe sequence
        for s in seq_fn(k, mask):
            if table[s] is None:
                table[s] = k
                break
    succ = []
    for k in keys:                      # successful search: probes including the matching slot
        for c, s in enumerate(seq_fn(k, mask), 1):
            if table[s] == k:
                succ.append(c)
                break
    unsucc = []
    for _ in range(n_unsucc):           # unsuccessful search: fresh key, probe until an empty slot
        k = rng.getrandbits(64)
        for c, s in enumerate(seq_fn(k, mask), 1):
            if table[s] is None:
                unsucc.append(c)
                break
    return sum(succ) / len(succ), sum(unsucc) / len(unsucc)

def measure(seq_fn, m, alpha, seed, reps=4):
    runs = [measure_one(seq_fn, m, alpha, seed * 10 + r) for r in range(reps)]
    out = []
    for idx in (0, 1):
        xs = [r[idx] for r in runs]
        mu = sum(xs) / reps
        sd = math.sqrt(sum((x - mu) ** 2 for x in xs) / (reps - 1))
        out.append((mu, sd / math.sqrt(reps)))
    return out

M = 2 ** 14
print("m = 16384 slots, 4 independent tables per cell, 20000 unsuccessful queries per table")
for alpha in (0.25, 0.5, 0.75, 0.9):
    res = {}
    for name, fn in (("linear", seq_linear), ("triangular", seq_triangular), ("cpython", cpython)):
        res[name] = measure(fn, M, alpha, seed=int(alpha * 100) + 1)
    print(f"alpha={alpha:.2f} successful:   " + "  ".join(f"{n} {res[n][0][0]:.2f}" for n in res))
    print(f"           unsuccessful: " + "  ".join(f"{n} {res[n][1][0]:.2f}" for n in res)
          + f"   (linear SE {res['linear'][1][1]:.2f})")
    print(f"           uniform theory: successful {(1/alpha)*math.log(1/(1-alpha)):.2f}, unsuccessful {1/(1-alpha):.2f}")
```

CPython's measured costs match the uniform formulas: 1.33, 2.00, 4.00 and 10.27 against 1.33, 2.00, 4.00 and 10.00. Linear probing is the worst by a wide margin: 2.48, 8.42 and 44.56 misses at loads 0.5, 0.75 and 0.9. The classic belief, which the abstract of Bender, Kuszmaul and Kuszmaul calls "widely believed and taught", is that at load $1-1/x$ insertion with linear probing costs $\Theta(x^2)$, against the ideal $\Theta(x)$ (arXiv:2107.01250, abstract). With $x = 1/(1-\alpha)$, that is the growth in the measured column. The same abstract argues that the cost depends on how deletions are implemented, since tombstones counter the clustering. This experiment has no deletions, so it shows only the no-deletion case. A closed form I recalled, $\tfrac12\left(1 + \tfrac{1}{(1-\alpha)^2}\right)$ for linear-probing misses, gives 2.50 and 8.50 at loads 0.5 and 0.75, close to the measured values. I did not open its source, so I do not cite it; I checked it only against these measurements. At load 0.9 the closed form gives 50.5, against 44.6 ± 3.8 measured (standard error across four tables). The spread is large at that load, so read it as an order of magnitude.

CPython caps usable entries at two thirds of the slots: `USABLE_FRACTION(n)` is `((n) << 1)/3` in `Objects/dictobject.c`, and that line sits beside the comment that calls it "the maximum dictionary load." At $\alpha = 2/3$ the uniform formulas give 3.00 probes for a miss and 1.65 for a hit. Lesson 6.4 covers the resize that enforces this cap.

Tombstones also cost space. The churn test below runs a table with 512 live keys and 1,000 steps of delete and insert, first with naive deletes and then with tombstones.

<details><summary>Run locally: standard library only, under one second</summary>

```python
import random

DUMMY = object()                        # tombstone: "deleted here, keep probing"

def cpython(h, mask):                   # CPython 3.12 recurrence, Objects/dictobject.c
    i = h & mask
    perturb = h & (2**64 - 1)
    yield i
    while True:
        perturb >>= 5
        i = (i * 5 + perturb + 1) & mask
        yield i

def churn(tombstones, seed=7, m=1024, live_n=512, steps=1000, checkpoints=(10, 100, 1000), load_limit=0.75):
    rng = random.Random(seed)
    mask = m - 1
    t = [None] * m

    def find(key):
        for s in cpython(key, mask):
            v = t[s]
            if v is None:
                return None
            if v is not DUMMY and v == key:
                return s

    def place(key):
        for s in cpython(key, mask):
            if t[s] is None or (tombstones and t[s] is DUMMY):
                t[s] = key
                return

    live = []
    for _ in range(live_n):
        key = rng.getrandbits(64)
        live.append(key)
        place(key)
    rebuilds, report = 0, {}
    for step in range(1, steps + 1):
        i = rng.randrange(len(live))
        s = find(live[i])                # delete a random live key
        if s is not None:
            t[s] = DUMMY if tombstones else None
        live[i] = live[-1]
        live.pop()
        new_key = rng.getrandbits(64)    # insert a fresh key
        live.append(new_key)
        if tombstones and sum(1 for x in t if x is not None) >= load_limit * m:
            keep = [x for x in t if x is not None and x is not DUMMY]
            t = [None] * m               # rebuild: drop the tombstones
            for x in keep:
                place(x)
            rebuilds += 1
        place(new_key)
        if step in checkpoints:
            unreachable = sum(1 for key in live if find(key) is None)
            occupied = sum(1 for x in t if x is not None)
            report[step] = (unreachable, occupied, rebuilds)
    return report

for tomb in (False, True):
    r = churn(tomb)
    name = "tombstones" if tomb else "naive delete"
    for step, (unreach, occ, rb) in r.items():
        print(f"{name:>12} after {step:>4} steps: unreachable live keys {unreach:>3}, slots in use {occ:>4}, rebuilds {rb}")
```

```output

naive delete after  100 steps: unreachable live keys  17, slots in use  514, rebuilds 0
naive delete after 1000 steps: unreachable live keys 102, slots in use  630, rebuilds 0
  tombstones after   10 steps: unreachable live keys   0, slots in use  522, rebuilds 0
  tombstones after  100 steps: unreachable live keys   0, slots in use  602, rebuilds 0
  tombstones after 1000 steps: unreachable live keys   0, slots in use  742, rebuilds 2
```

## Common traps

> [!TRAP]
> **Open addressing avoids collisions.** It stops two entries sharing a slot, but two keys can still share a home slot. Probing resolves the collision; it does not prevent it.

> [!TRAP]
> **Deleting by emptying the slot.** Every key further along the chain now stops early. Use a tombstone, and make sure search skips it.

> [!TRAP]
> **Any probe step reaches every slot.** Triangular probing from slot 0 on a 10-slot table reaches six slots. Check reachability before you trust a probe sequence, or use a power-of-two size.

> [!TRAP]
> **Tombstones are free.** After 1,000 steps the churn table had 742 slots in use (live entries plus tombstones) and had rebuilt twice to clear them. Tombstones count against the load limit, so they make the table fill sooner.

> [!TRAP]
> **A big table makes high load safe.** The uniform formulas depend on the load factor alone, not on the number of slots. At load 0.9, linear probing averaged about 45 probes per miss at $m = 16{,}384$.

## Summary

- Open addressing keeps one entry per slot. A collision sends the key along a probe sequence, and every lookup retraces it.
- Deleting by emptying a slot cuts probe chains. A tombstone keeps the chain intact, and rebuilds clear the tombstones.
- Probe order matters. Linear probing clusters, and triangular probing on a 10-slot table reached only 6 of its slots.
- Under uniform hashing a miss costs $1/(1-\alpha)$ probes and a hit costs $\frac{1}{\alpha}\ln\frac{1}{1-\alpha}$. Linear probing does worse, at about 45 probes per miss at load 0.9.

## Quiz time

### Question 1: Calculation

A 5-slot table uses linear probing. You insert key 1, then key 6. Which slot holds key 6?

<details><summary>Show Solution</summary>

Key 1's home is `1 % 5 = 1`, so it takes slot 1. Key 6's home is `6 % 5 = 1`, which is taken, so it moves to slot 2, which is free. Key 6 is in slot 2.

</details>

### Question 2: Predict the output

Using the `ProbeTable` class above, with `tombstones=False`, you insert key 1 and key 6 into a 5-slot table, then call `delete(1)`. What does `search(6)` return? What did the old lesson's solution say?

<details><summary>Show Solution</summary>

It returns `None`. The search for 6 starts at home slot 1, finds it empty, and stops. The old lesson's solution printed `Six`, which is wrong. With `tombstones=True` the search returns `Six`; this is the output the code produces when you run it.

</details>

### Question 3: Bug-spotting

The old lesson's `insert` loops while the probed slot is occupied. A 10-slot table holds keys 0, 10, 20, 30, 40 and 50, which fill the six slots reachable from home slot 0 under triangular probing. You then insert key 60, whose home is slot 0. Why does the loop never end, and what change to the table size is the usual remedy?

<details><summary>Show Solution</summary>

From home slot 0, triangular probing reaches slots 0, 1, 3, 5, 6 and 8. Those six slots are full, and slots 2, 4, 7 and 9 are free but unreachable from home 0. The loop exits only on an empty slot, so it never exits. A power-of-two size such as 8 reached every slot in the check above, and CPython uses power-of-two tables. That check covers one size, not a general proof.

</details>

### Question 4: Calculation

Under uniform hashing at load factor $\alpha = 0.5$, what are the expected probes for a miss and for a hit? Why is the miss more expensive?

<details><summary>Show Solution</summary>

A miss costs $1/(1-0.5) = 2.00$ probes. A hit costs $\frac{1}{0.5}\ln 2 \approx 1.39$ probes. A miss must keep probing until it reaches an empty slot. A hit stops at its own entry, and its cost is the insertion cost averaged over the loads at which entries arrived, which is lower.

</details>

### Question 5: Explanation

CPython's comment says linear probing is "deadly" for consecutive hash codes. Why?

<details><summary>Show Solution</summary>

Consecutive hash codes have consecutive home slots. Linear probing sends each colliding key along a fixed order, and the comment says that order is "the same as the order consecutive keys are likely to arrive." So a collision at one slot pushes its key into the next slot, which the next consecutive key then collides with, and the run grows. The comment is in `Objects/dictobject.c`.

</details>
