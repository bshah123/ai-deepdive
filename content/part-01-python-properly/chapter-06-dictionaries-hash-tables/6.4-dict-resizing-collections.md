A `dict` grows by itself, and every growth step copies its table. In this lesson you will predict when CPython 3.12 resizes a dictionary, check the prediction against measured table sizes, and use `defaultdict` and `Counter` without the two traps that catch most readers: a read that writes, and a subtraction that silently drops keys.

**You need:** how a hash table turns a key into a slot index (Lessons 6.1 and 6.3), and basic `dict` use.

## The problem resizing solves

A hash table with a fixed number of slots works until it fills. Lookups then probe through occupied slots, which is the cost you measured in Lesson 6.3. So a dict grows its slot array before it is full. Growing is not free: each resize allocates a new array and moves every entry into it. The questions are how often that happens and what it costs in total.

Two terms. **Slots** are the cells of the table. **Load factor** is the number of entries divided by the number of slots. CPython never lets the entries fill more than two thirds of the slots: the two-thirds limit is the table's "usable" count, and reaching it triggers a resize.

## Intuition: a sawtooth

Each resize (dashed red) drops it by half.")

The load climbs to two thirds, a resize drops it to about one third, and the climb starts again. The resize points are the insert numbers 6, 11, 22, 43, 86, 171, 342 and 683.

## Worked example by hand

Start with 8 slots, which give 5 usable entries. The sixth insert finds the table full, so CPython does four things:

1. **New size.** The rule is: the smallest power of two that is at least 3 × used, with a minimum of 8. Here used = 5, so 3 × 5 = 15, and the new size is 16.
2. **New usable count.** 2 × 16 / 3 = 10.67, rounded down to 10.
3. **Move.** Allocate the 16-slot table and copy the 5 existing entries into it.
4. **Insert.** Add the sixth key. The load is now 6 / 16 = 0.375.

![Before: an 8-slot table with 5 cells used and no room for a sixth. After a resize: a 16-slot table with 6 cells used](diagrams/6.4-worked-insert.svg "The sixth insert, by hand.")

The rule is in the CPython source. The macro `GROWTH_RATE(d)` is `((d)->ma_used*3)`, the macro `USABLE_FRACTION(n)` is `(((n) << 1)/3)`, and `insertion_resize` passes `calculate_log2_keysize(GROWTH_RATE(mp))` to `dictresize` [1]. That function returns the smallest power of two at least its argument, which gives the rule above. The first block below implements the rule and predicts the resize points. It is a model, and it runs in the browser.

```python
# Model of CPython 3.12 dict growth (Objects/dictobject.c)
def new_slots(used):
    """Smallest power of two >= 3 * used, with a minimum of 8 slots."""
    slots = 8
    while slots < 3 * used:
        slots *= 2
    return slots

slots, used, usable = 8, 0, 5          # an empty dict starts with 8 slots and 5 usable
for n in range(1, 1001):               # insert keys one at a time
    if used == usable:                 # table full: resize before this insert
        old = slots
        slots = new_slots(used)
        usable = 2 * slots // 3        # USABLE_FRACTION: two thirds of the slots
        print(f"insert {n:4d}: {old:4d} -> {slots:4d} slots, "
              f"usable {usable:4d}, load after insert = {n}/{slots} = {n / slots:.3f}")
    used += 1
```

```output

insert   11:   16 ->   32 slots, usable   21, load after insert = 11/32 = 0.344
insert   22:   32 ->   64 slots, usable   42, load after insert = 22/64 = 0.344
insert   43:   64 ->  128 slots, usable   85, load after insert = 43/128 = 0.336
insert   86:  128 ->  256 slots, usable  170, load after insert = 86/256 = 0.336
```

## Resizing does not rehash

When a dict resizes, it does not call `__hash__` again for each key. Each entry keeps its hash (a dict whose keys are all `str` reads the hash from the key object instead, as Lesson 6.2 explains), and the rebuild reads that value [1]. The next block counts calls directly.

```python
class Key:
    calls = 0
    def __init__(self, v):
        self.v = v
    def __hash__(self):
        Key.calls += 1
        return hash(self.v)
    def __eq__(self, other):
        return isinstance(other, Key) and other.v == self.v

table = {}
for i in range(1000):
    table[Key(i)] = i                  # every insert hashes its key once
print("__hash__ calls for 1000 inserts:", Key.calls)
print("len:", len(table))
```

```output
__hash__ calls for 1000 inserts: 1000
len: 1000
```

Eight resizes happened in those 1000 inserts, and none of them called `__hash__`.

## What a resize costs in total

A resize copies every live entry once. The question is how much copying a long run of inserts does in total. The doubling argument gives a bound. After a resize at `u` entries, the new table has at least `3u` slots, so its usable count is at least `2u`. The next resize therefore comes after the table holds at least `2u` entries. The copy counts at successive resizes at least double, so their sum is below twice the final count, which is below twice the number of inserts `N`.

The run below counts the copies for four values of `N`.

<details><summary>Run locally: entries copied per insert (CPython 3.12, 64-bit macOS)</summary>

```python
import sys

def entries_moved(N):
    """Sum of the entry counts at each resize, while inserting N keys."""
    d, last, moved = {}, sys.getsizeof({}), 0
    for n in range(N):
        before = len(d)
        d[n] = n
        size = sys.getsizeof(d)
        if size != last and before > 0:    # size change after the first allocation = resize
            moved += before
        last = size
    return moved

for N in (1000, 10000, 100000, 1000000):
    moved = entries_moved(N)
    print(f"N = {N:>7,}: entries moved = {moved:>7,}, moved / N = {moved / N:.2f}")
```

```output
N =   1,000: entries moved =   1,356, moved / N = 1.36
N =  10,000: entries moved =  10,912, moved / N = 1.09
N = 100,000: entries moved = 174,750, moved / N = 1.75
N = 1,000,000: entries moved = 1,398,087, moved / N = 1.40
```

</details>

The ratio stays between 1.09 and 1.75 for these runs, and the bound is 2. So the copies per insert are bounded by a constant. Amortized over many inserts, each insert costs O(1) copying.

![Bar chart of entries moved by resizes divided by N: 1.36, 1.09, 1.75 and 1.40 for N from one thousand to one million, all under a dashed bound at 2](diagrams/6.4-copy-ratio.svg "Copies per insert, measured. The bound of 2 is derived from the doubling argument above.")

Growing is therefore cheap in aggregate. The expensive part is a single resize of a large table, which causes a latency spike. This lesson does not time it.

## Constructors do not presize

A common tip says to pass pairs to `dict()` to avoid resizing. The next measurement tests that for 1000 keys, built six ways.

<details><summary>Run locally: table size by construction method (CPython 3.12, 64-bit macOS)</summary>

```python
import sys
n = 1000
inc = {}
for i in range(n):
    inc[i] = i
builds = {
    "incremental inserts": inc,
    "dict(list of pairs)": dict([(i, i) for i in range(n)]),
    "dict comprehension": {i: i for i in range(n)},
    "dict(zip(...))": dict(zip(range(n), range(n))),
    "dict(other dict)": dict(inc),
    "dict.fromkeys(list)": dict.fromkeys(range(n)),
}
for name, d in builds.items():
    print(f"{name:22s} {sys.getsizeof(d)} bytes")
```

```output
incremental inserts    36952 bytes
dict(list of pairs)    36952 bytes
dict comprehension     36952 bytes
dict(zip(...))         36952 bytes
dict(other dict)       36952 bytes
dict.fromkeys(list)    36952 bytes
```

</details>

All six give the same table size, so passing pairs to `dict()` gives no table-size advantage over inserting one key at a time. I measured sizes, not time, so any timing difference is untested.

## Deleting does not shrink

Deleting a key does not resize the dict. CPython checks for a resize only when a key is inserted and the table has no usable entries left [2]. A resize can then shrink the table, if few keys are live at that moment. The next block deletes 997 of 1000 keys, re-inserts 400, and then churns (inserts one key and deletes it) until the table shrinks.

<details><summary>Run locally: memory after deleting keys (CPython 3.12, 64-bit macOS)</summary>

```python
import sys
d = {i: i for i in range(1000)}
print("1000 keys:", sys.getsizeof(d), "bytes")
for i in range(997):
    del d[i]
print("delete 997:", len(d), "keys,", sys.getsizeof(d), "bytes")
for j in range(1000, 1400):
    d[j] = j
print("re-insert 400:", len(d), "keys,", sys.getsizeof(d), "bytes")
for k in list(d)[:-3]:
    del d[k]
print("delete to 3 keys:", len(d), "keys,", sys.getsizeof(d), "bytes")
k = 0
last = sys.getsizeof(d)
while sys.getsizeof(d) == last:       # churn: insert one key, delete it
    d[10**6 + k] = 0
    del d[10**6 + k]
    k += 1
print("churn:", k, "insert+delete steps ->", len(d), "keys,", sys.getsizeof(d), "bytes")
```

```output
1000 keys: 36952 bytes
delete 997: 3 keys, 36952 bytes
re-insert 400: 403 keys, 36952 bytes
delete to 3 keys: 3 keys, 36952 bytes
churn: 963 insert+delete steps -> 3 keys, 352 bytes
```

</details>

The table stayed at 36952 bytes through the deletions and the 400 re-inserts. The re-inserts used up the 1365 usable entries of the 2048-slot table, so a resize happened. It computed 3 × 368 = 1104, which rounds up to the same 2048 slots. Only the churn produced a resize with 3 live keys, and it dropped to 352 bytes, the size of a 16-slot table.

![Four bars of getsizeof bytes: 36952 after 1000 keys, 36952 after deleting 997, 36952 after 400 re-inserts, and 352 after churn with 3 keys live](diagrams/6.4-shrink.svg "Memory is released only at a resize, and only if the resize computes a smaller size.")

## defaultdict and Counter

`defaultdict(factory)` is a dict whose `[]` calls `factory()` for a missing key, stores the result, and returns it. The docs state that `get()` does not call the factory, so it returns `None` and inserts nothing [3]. The block below shows both behaviours, then `Counter`.

```python
from collections import Counter, defaultdict

groups = defaultdict(list)
print("'x' in groups:", "x" in groups, "| groups.get('x'):", groups.get("x"), "| len:", len(groups))
groups["x"]                            # a read with [] creates the entry
print("after groups['x']: len", len(groups), groups)

c = Counter("abracadabra")
print("c['z'] =", c["z"], "| len(c) =", len(c), "| 'z' in c:", "z" in c)
print("c - Counter('aaaaaaa') =", c - Counter("aaaaaaa"))
s = Counter("abracadabra")
s.subtract(Counter("aaaaaaa"))
print("after subtract:", s)
fresh = Counter("abracadabra")
print("most_common(3):", fresh.most_common(3), "| total:", sum(fresh.values()))
```

```output
'x' in groups: False | groups.get('x'): None | len: 0
after groups['x']: len 1 defaultdict(<class 'list'>, {'x': []})
c['z'] = 0 | len(c) = 5 | 'z' in c: False
c - Counter('aaaaaaa') = Counter({'b': 2, 'r': 2, 'c': 1, 'd': 1})
after subtract: Counter({'b': 2, 'r': 2, 'c': 1, 'd': 1, 'a': -2})
most_common(3): [('a', 5), ('b', 2), ('r', 2)] | total: 11
```

A `Counter` returns 0 for a missing element, as the docs say [3]. The measured output also shows that the lookup does not store the element. The docs do not state that, so I checked it here. The `-` operator keeps only positive results. `subtract()` keeps zero and negative counts. Both behaviours are in the docs [3], and the output confirms them.

> [!TRAP]
> Reading a `defaultdict` with `[]` inserts the key. A test such as `if groups[key] != []` changes the dict. Use `key in groups` or `groups.get(key)` to check without inserting.

> [!TRAP]
> `dict(pairs)` does not presize the table. The six constructions above all gave 36952 bytes for 1000 keys.

> [!TRAP]
> Deleting does not shrink the dict. Memory is released only at a resize, and only when that resize computes a smaller size.

> [!TRAP]
> `Counter` subtraction with `-` drops zero and negative counts. Use `subtract()` if you need them to stay.

> [!TRAP]
> `sys.getsizeof` is shallow: it counts the table, not the keys and values it points to [4]. Its numbers are specific to the CPython build, so treat them as measurements, not constants.

## Summary

- A dict resizes when its entries reach two thirds of its slots. The new table is the smallest power of two at least 3 × used, with a minimum of 8 slots.
- The resize points for inserts are 6, 11, 22, 43, 86, 171, 342 and 683, measured on CPython 3.12.
- Resizing reuses stored hashes, and the copies over many inserts stay below twice the insert count.
- Passing pairs to `dict()` does not presize, and deleting keys does not shrink the table until a resize.
- `defaultdict` creates keys on read through `[]`, and `Counter` subtraction with `-` drops non-positive counts.

## Quiz time

### Question 1: Calculation

A dict has 8 slots and has just taken its 6th insert, which resized it to 16 slots. At which insert number does the next resize happen, and how many slots does the table have after it?

<details><summary>Show Solution</summary>

The 16-slot table has 10 usable entries, so the resize happens at insert 11, when 10 entries are present. The new size is the smallest power of two at least 3 × 10 = 30, which is 32. The model prints the same line: `insert 11: 16 -> 32 slots`.

</details>

### Question 2: Prediction

After `del` removes 997 of 1000 keys from a dict, does `sys.getsizeof` fall immediately?

<details><summary>Show Solution</summary>

No. The measured size stays at 36952 bytes after the deletions. The table only changes at a resize. The resize then computes its size from the live count (`3 × used`), so the table shrinks only when a resize runs while few keys are live. In the measured run, 963 insert-and-delete steps with 3 live keys caused a resize that dropped the size to 352 bytes.

</details>

### Question 3: Bug-spotting

```python
from collections import defaultdict

groups = defaultdict(list)

def has_group(key):
    return groups[key] != []

has_group("x")
print(len(groups))
```

What does this print, and how do you fix it?

<details><summary>Show Solution</summary>

It prints `1`. The check `groups[key]` is a read through `[]`, which inserts a new empty list for a missing key. The fix is to test membership first, so the read happens only for keys that exist:

```python
def has_group(key):
    return key in groups and groups[key] != []
```

Using `groups.get(key, [])` also avoids the insert.

</details>

### Question 4: Explanation

Why does a resize not call `__hash__` for every key?

<details><summary>Show Solution</summary>

Each entry keeps the hash computed when its key was inserted (for an all-`str` dict, the `str` object holds it), and the rebuild reads that value [1]. The hash-count block shows the effect: 1000 inserts make exactly 1000 `__hash__` calls, although the dict resized eight times.

</details>

### Question 5: Prediction

What do `Counter("aab") - Counter("aaa")` and `Counter("aab").subtract(Counter("aaa"))` produce?

<details><summary>Show Solution</summary>

The subtraction returns `Counter({'b': 1})`, because the count for `a` is 2 − 3 = −1 and the operator drops it. `subtract()` keeps the negative count and returns `Counter({'b': 1, 'a': -1})`. Both results were checked by running the code on CPython 3.12.

</details>
