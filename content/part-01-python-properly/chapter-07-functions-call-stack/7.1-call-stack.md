Every running function call has a record called a **frame**, which holds its local variables and its position in the code. Frames form a stack: a call pushes one, and a return pops it. In this lesson you will walk that stack from inside a running call, read the frame fields Python exposes, and see how CPython 3.12 stores frames internally.

**You need:** variables and references (Lesson 2.1), and the `dis` module for reading bytecode (Lesson 1.5).

## The problem a call stack solves

Suppose `factorial(3)` calls `factorial(2)`. The inner call must not overwrite the outer call's `n`. When the inner call returns, its value must go back to the outer call's multiplication. Both facts need a separate record for each active call, with the newest record on top. That record is the frame, and the stack of records is the call stack. Only the top frame is running; the frames below it are waiting for a call to return.

Consider what breaks with one shared variable `n`. The calls would set it to 3, then 2, then 1, then 0. When the call that started with `n = 3` resumes, it would read 0 and compute `0 * ...` instead of `3 * ...`. With one frame per call, each call reads only the `n` in its own record.

## Intuition: a chain of frames

![Five stacked frames, probe(n=0) at the top down to the module frame at the bottom, with f_back arrows pointing from each frame to its caller](diagrams/7.1-chain.svg "The chain of frames at the innermost call of probe(3).")

Each frame links to its caller through `f_back`. The first block starts at the innermost call and follows those links to the module.

```python
import sys

def probe(n: int) -> int:
    if n == 0:
        frame = sys._getframe()           # the innermost frame: the top of the stack
        names = []
        while frame.f_code.co_name == "probe":
            names.append(f"{frame.f_code.co_name}(n={frame.f_locals.get('n')})")
            frame = frame.f_back          # one step towards the caller
        print(names)
        return 1
    return n * probe(n - 1)

probe(3)
```

```output
['probe(n=0)', 'probe(n=1)', 'probe(n=2)', 'probe(n=3)']
```

`sys._getframe()` returns the frame of the call that is running. `f_code.co_name` is the function's name, and `f_locals` maps each local variable to its value. The Python data model defines `f_back` as "the previous stack frame (towards the caller), or `None` if this is the bottom stack frame". The walk stops at the first frame that is not `probe`. When this file is run as a script, that frame is the module, the fifth and bottom frame in the diagram. The stop condition keeps the printed list the same when another runner adds frames below the module.

## Unwinding: values come back up the stack

Each call waits for the call it made, then returns its own value. The second block prints both legs of the journey.

```python
def fact(n: int, depth: int = 0) -> int:
    print("  " * depth + f"enter fact({n})")
    result = 1 if n == 0 else n * fact(n - 1, depth + 1)
    print("  " * depth + f"return {result}")
    return result

fact(3)
```

```output
enter fact(3)
  enter fact(2)
    enter fact(1)
      enter fact(0)
      return 1
    return 1
  return 2
return 6
```

The innermost call returns first, and each return value feeds the multiplication one frame below it. Working the values by hand: `fact(0)` returns 1; `fact(1)` returns 1 × 1 = 1; `fact(2)` returns 2 × 1 = 2; `fact(3)` returns 3 × 2 = 6, the last line printed. At the deepest point the stack held five frames: four `fact` calls and the module. The recursion itself is limited: on this interpreter `sys.getrecursionlimit()` returns 1000 (measured on Python 3.12.13; the docs describe the limit but do not state the default). Lesson 7.4 covers what happens past it.

## Inside a frame object

![A frame object drawn as five labelled rows: f_code, f_back, f_locals, f_lasti and stack, each with a one-line description](diagrams/7.1-frame-anatomy.svg "The fields a frame object exposes. Names as Python shows them.")

In CPython 3.12, the running state of a call lives in an internal structure, `_PyInterpreterFrame`, on the thread's data stack. Its fields include `f_code`, `previous`, `f_locals`, `frame_obj`, `prev_instr`, and `localsplus`, which stores the locals followed by the value stack (CPython source, `Include/internal/pycore_frame.h`). The field `frame_obj` may be NULL. The header says the Python-visible object, the `PyFrameObject`, is created on demand. That object is what `sys._getframe()` returns. It exposes `f_back`, `f_code`, `f_locals`, and `f_lasti`, which is the index of the current instruction in the bytecode (data model).

The internal frame is the working copy. When `frame_obj` is NULL, no Python-visible object exists for that call, and the interpreter runs on the internal frame alone. The header's comments say that `_PyFrame_GetFrameObject` creates the object on demand, and that the creating function runs only when `frame_obj` is NULL.

Lazy creation is deliberate. The Python 3.11 release notes say: "Old-style frame objects are now created only when requested by debuggers or by Python introspection functions such as `sys._getframe()` and `inspect.currentframe()`. For most user code, no frame objects are created at all." They also say that "Most Python function calls now consume no C stack space" (What's New, 3.11). The release notes report speedups from these changes, but this lesson does not depend on those numbers.

> [!ADVANCED]
> The field names above belong to CPython 3.12. Internal layouts change between versions. Treat them as a map of one release, not a stable interface.

## The value stack and `co_stacksize`

After the locals, each frame has a value stack. Bytecode instructions use it for intermediate results. Each instruction pushes or pops a known number of items, which `dis.stack_effect` reports (documented in the `dis` module). The next block walks the recursive branch of `factorial`, adds up those effects, and compares the peak with `co_stacksize`, the stack size recorded on the code object.

```python
import dis

def factorial(n: int) -> int:
    if n == 0:
        return 1
    return n * factorial(n - 1)

print("co_stacksize:", factorial.__code__.co_stacksize)
instrs = list(dis.get_instructions(factorial))
start = next(k for k, i in enumerate(instrs) if i.opname.startswith("RETURN")) + 1
depth = 0
for ins in instrs[start:]:
    depth += dis.stack_effect(ins.opcode, ins.arg)
    print(f"{ins.offset:>3} {ins.opname:<16} depth after = {depth}")
    if ins.opname == "RETURN_VALUE":
        break
```

```output
co_stacksize: 5
 14 LOAD_FAST        depth after = 1
 16 LOAD_GLOBAL      depth after = 3
 26 LOAD_FAST        depth after = 4
 28 LOAD_CONST       depth after = 5
 30 BINARY_OP        depth after = 4
 34 CALL             depth after = 2
 42 BINARY_OP        depth after = 1
 46 RETURN_VALUE     depth after = 0
```

The stack explains why the bytecode can compute `n * factorial(n - 1)` without a named slot for the value of `n`. The left operand stays on the value stack while the recursive call runs (this is my reading of the trace, and the trace is consistent with it).

Work through the first few lines by hand. `LOAD_FAST n` pushes one value, so the depth is 1. `LOAD_GLOBAL` pushes two items, a NULL marker and the function `factorial`, so the depth becomes 3. `LOAD_FAST n` and `LOAD_CONST 1` bring it to 5. `BINARY_OP -` pops two values and pushes one, giving 4. `CALL 1` consumes the function, the marker and one argument, and pushes the result, giving 2.

![Eight bars for the recursive branch, heights 1, 3, 4, 5, 4, 2, 1, 0, with a dashed line at co_stacksize equal to 5](diagrams/7.1-stack-depth.svg "Value-stack depth after each instruction on the recursive branch of factorial.")

The peak is 5, which equals `co_stacksize`. Both numbers come from the same run. The `dis.stack_effect` values are exact here because this path has no jump instructions. The docs say that for an instruction with a jump target, `stack_effect` takes a `jump` argument: `True` gives the effect of jumping, `False` the effect of not jumping, and the default `None` gives the larger of the two.

## Frames keep their data alive

Frames are not destroyed the moment a function returns, if something still refers to them. The next block returns a frame from a function that has already finished.

```python
import sys

def make_frame():
    secret = 42
    return sys._getframe()

frame = make_frame()
print(frame.f_code.co_name, frame.f_locals["secret"], "| f_back:", frame.f_back.f_code.co_name)
```

```output
make_frame 42 | f_back: <module>
```

![Left: a dashed box for make_frame() that has returned. Right: a solid frame object that still holds f_code.co_name, f_locals secret equal to 42, and f_back to the module](diagrams/7.1-captured-frame.svg "A frame object still holds its locals and its caller after the call has returned.")

The call has returned, yet `secret` is still readable through the frame. The output shows that the locals survive; the mechanism is my reasoning from that output, not a source I opened. The frame object keeps a reference to its data, and the reference to the frame in `frame` keeps that data alive.

## Common traps

> [!TRAP] **`f_back` points to the caller, not the callee.**
> Walking `f_back` from the innermost frame moves outward, ending at the module. The innermost frame is the top of the stack.

> [!TRAP] **A stored frame keeps memory alive.**
> A frame that refers to its caller also keeps the caller's locals reachable. Storing frames in long-lived variables can hold large objects in memory. (Reasoning from the references above; I did not measure it.)

> [!TRAP] **`sys._getframe()` is a CPython detail.**
> The `sys` docs say it "should be used for internal and specialized purposes only" and "is not guaranteed to exist in all implementations of Python".

> [!TRAP] **Recursion depth is bounded.**
> On this interpreter `sys.getrecursionlimit()` returns 1000 (measured). The `sys` docs say the limit exists to stop infinite recursion from overflowing the C stack. Depth limits are the subject of Lesson 7.4.

> [!TRAP] **Bytecode offsets and line numbers are version-specific.**
> The offsets in the stack-depth block (14, 16, 26 and so on) and `f_lasti` values change between Python versions. Do not hard-code them. Read them at run time, as the blocks above do.

## Summary

- Each active call has a frame. Frames form a stack, and each `f_back` link points to the caller.
- In CPython 3.11 and later, frame objects are created only when code asks for them, such as through `sys._getframe()`.
- A function's value stack peaks at `co_stacksize`. For `factorial` the peak is 5, and `dis.stack_effect` reproduces it.
- A frame object keeps its locals and its caller reachable after the call has returned.

### Question 2: Calculation

In the stack-depth block, what is the depth after `BINARY_OP` at offset 30, and why?

<details><summary>Show solution</summary>

It is 4. `LOAD_FAST n` makes the depth 1, `LOAD_GLOBAL` pushes two items for a depth of 3, then `LOAD_FAST n` makes 4 and `LOAD_CONST 1` makes 5. `BINARY_OP -` pops two values and pushes one, so the depth goes from 5 to 4.

### Question 3: Find the bug

This function should return the name of its caller, but it returns `<module>` when called from `outer`.

```python
import sys

def who_called_me():
    frame = sys._getframe()
    while frame.f_back is not None:
        frame = frame.f_back
    return frame.f_code.co_name

def outer():
    return who_called_me()

print(outer())
```

<details><summary>Show solution</summary>

The loop walks all the way down to the bottom of the stack, which is the module frame, so it returns `'<module>'`. The caller is one step up from the current frame. The fix is one `f_back` step, with no loop:

```python
import sys

def who_called_me():
    return sys._getframe().f_back.f_code.co_name

def outer():
    return who_called_me()

print(outer())
```

This prints `outer`. I ran both versions.

</details>

### Question 4: Explain

Block 3 prints `42` after `make_frame()` has returned. Why does the function's local variable still exist?

<details><summary>Show solution</summary>

The local variable does not exist as a live variable any more. The frame object returned by `sys._getframe()` still holds `f_locals`, and that frame is referenced by `frame`. So the value remains reachable. Once no reference to the frame remains, the frame and its locals can be released.

</details>
