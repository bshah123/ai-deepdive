In this lesson you will predict which binding a name refers to, using the LEGB rule (Local, Enclosing, Global, Built-in). You will see why one assignment can break a read that looks harmless, and look inside a closure to find the cell object that keeps its variable alive after the outer function has returned.

**You need:** function calls and local variables (Lesson 7.1, the call stack), and the idea that a `dict` maps names to values.

## The problem scoping solves

The name `x` in a function body can refer to a variable of that function, of a function that contains it, of the module, or to a built-in such as `len`. Python must pick one binding every time it reads a name. Two questions follow. Which binding does a read see? And what happens to a variable that an inner function still reads after the outer function has returned? The first question is answered by the lookup rule. The second is answered by cell objects.

## The lookup rule: LEGB

![Four stacked scope boxes, local to built-in, with a search arrow running down them; the enclosing scope is the first to bind name, so the search stops there](diagrams/8.1-legb-search.svg "The search runs inside out and stops at the first scope that binds the name.")

The Python tutorial describes the scopes in this order. The innermost scope, "which is searched first, contains the local names"; the scopes of enclosing functions come next; then the module's global names; the built-in names are searched last (Python Software Foundation, Tutorial §9.2). LEGB is a mnemonic for those four layers. The Language Reference gives the same rule in its own words, "the nearest enclosing scope", and does not use the acronym (Language Reference §4.2).

Trace one read by hand. Inside `inner()`, the name `name` has no local binding, so the local scope misses. The enclosing scope, `outer()`, binds `name`, so the search stops there. The module also binds `name`, but the global scope is never reached. The first program checks each layer.

The search depends only on where each name is written in the source text, not on the order in which functions are called. That is why you can settle any lookup by reading the code, without running it. The rest of this lesson is about the two places where that reading is easy to get wrong: assignments, and variables that outlive their function.

```python
name = "global"                      # G: module level

def outer():
    name = "enclosing"               # E: outer's local, visible to inner
    def inner():
        return name                  # no local binding here: search outward
    return inner()

def no_enclosing():
    def inner():
        return name                  # no E binding: falls through to G
    return inner()

def uses_builtin():
    return len("abc")                # no L, E or G binding: built-in len

def shadows_builtin():
    len = 5                          # L: a local name shadows the built-in
    return len

print(outer())                       # E wins over G
print(no_enclosing())                # G
print(uses_builtin())                # B
print(shadows_builtin(), len("abc")) # the built-in is untouched outside
```

```output
enclosing
global
3
5 3
```

## The compiler decides, before the code runs

The lookup order above is fixed when the function is compiled, not when it is called. The Language Reference states the consequence: "If a name binding operation occurs anywhere within a code block, all uses of the name within the block are treated as references to the current block" (§4.2.2). A binding is any assignment, including `+=`, `for`, `import` and `def`. The compiler therefore marks `g` as local to the whole function body as soon as it sees `g = 2`, even on a line after the read.

```python
g = 1                                # module-level g

def reads_only():
    return g                         # no assignment to g in this body

def reads_then_assigns():
    print(g)                         # g is already local here
    g = 2

print(reads_only())
try:
    reads_then_assigns()
except UnboundLocalError as e:
    print("UnboundLocalError:", e)
```

```output
1
UnboundLocalError: cannot access local variable 'g' where it is not associated with a value
```

![Left: a function that only reads g prints the global value 1. Right: a function that also assigns g to the same name cannot read the local slot before it is bound, so it raises UnboundLocalError](diagrams/8.1-compile-time.svg "One assignment in the body changes where every read of the name goes.")

To rebind a module-level name inside a function, declare it with `global`. The module name then refers to the module variable everywhere in the body:

```python
g = 1

def bump_global():
    global g
    g += 1                           # refers to the module-level g

bump_global()
print(g)
```

```output
2
```

PEP 3104 explains why `nonlocal` was added. Before it, Python code "can only rebind names in two scopes: the local scope (by simple assignment) or the module-global scope (using a `global` declaration)" (PEP 3104, Abstract). The `nonlocal` statement adds the third option: rebinding a name in the nearest enclosing function. Section 4.2 also says that a `nonlocal` name with no binding in any enclosing function is a compile-time error.

## Closures: the variable moves into a cell

The compiler records which names it had to place in cells. In the next program, `count` is used by the inner function, so it becomes a cell variable of `make_counter`. The code object of each function records the result: `co_cellvars` lists the variables a function owns that inner functions use, and `co_freevars` lists the variables a function borrows from outside.

```python
def make_counter():
    count = 0                        # used by counter, so it lives in a cell
    def counter():
        nonlocal count
        count += 1
        return count
    return counter

c = make_counter()                   # make_counter's frame has returned
cell = c.__closure__[0]              # the cell is still reachable from the closure
print(type(cell).__name__, cell.cell_contents)
print(c(), c())
print(cell.cell_contents)
print(make_counter.__code__.co_cellvars, c.__code__.co_freevars)
```

```output
cell 0
1 2
2
('count',) ('count',)
```

![A dashed frame box for make_counter() drops its slot on return; the cell box holds the variable; the counter closure keeps the cell alive through its __closure__ slot](diagrams/8.1-cell.svg "The frame is freed when the call returns; the cell stays because the closure still points to it.")

The cell is a small object of CPython, the reference implementation of Python written in C. Its header file defines the structure with one field besides the standard object header:

```c
typedef struct {
    PyObject_HEAD
    /* Content of the cell or NULL when empty */
    PyObject *ob_ref;
} PyCellObject;
```

The `cell_contents` attribute is a getter and setter for that pointer (CPython `Objects/cellobject.c`). The standard library exposes the type as `types.CellType`, described as "the type for cell objects: such objects are used as containers for a function's closure variables" (Library Reference, `types`, added in 3.8). Two closures created by the same call share one cell. The next program shows the share and the empty case:

```python
def make_pair():
    x = 10
    def get():
        return x
    def set_to(v):
        nonlocal x
        x = v
    return get, set_to

get, set_to = make_pair()
print(get.__closure__[0] is set_to.__closure__[0])
set_to(99)
print(get())

def outer():
    def inner():
        return x                     # x is free in inner
    cell = inner.__closure__[0]
    try:
        cell.cell_contents
    except ValueError as e:
        print("ValueError:", e)
    x = 1
    print(cell.cell_contents)
outer()
```

```output
True
99
ValueError: Cell is empty
1
```

The `ValueError` appears because the cell exists before `x` is bound. Reading it fails with the message "Cell is empty" (CPython `Objects/cellobject.c`). The cell is created when the outer function's frame starts, before `x` is bound, so an inner function can refer to a variable that has no value yet. The same cell then carries the value once the outer function assigns it.

Think of a cell as a labelled box that both the frame and the closure hold a reference to. The frame needs its slot only while the outer function runs. The closure needs the box for as long as it exists, so the box survives the call.

## Closures capture the cell, not the value

Because a closure holds the cell and not a copy of the value, a closure sees the cell's current contents when it runs. This matters in loops. A `lambda` created in a loop reads `i` from one shared cell, and by the time the lambdas are called, that cell holds the last value of `i`.

```python
fs = [lambda: i for i in range(3)]
print([f() for f in fs])

fs2 = [lambda i=i: i for i in range(3)]      # default argument copies i now
print([f() for f in fs2])

def make_fn(i):
    return lambda: i                 # each call to make_fn creates a new cell

fs3 = [make_fn(i) for i in range(3)]
print([f() for f in fs3])
print(fs[0].__closure__[0] is fs[2].__closure__[0])
```

```output
[2, 2, 2]
[0, 1, 2]
[0, 1, 2]
True
```

![Three panels of three closures each: all three point to one cell holding 2; a default argument gives each closure its own value 0, 1 or 2; a factory function gives each closure its own cell](diagrams/8.1-late-binding.svg "Three ways a loop of lambdas can capture i.")

Because the cell is shared, a closure also sees later changes made by any other function that shares it, such as `set_to` in the earlier example. A default argument is evaluated once, when the `lambda` is created, so `i=i` copies the current value into the function. A factory function gives each call its own frame and therefore its own cell, which is the only thing the closure needs to keep its value.

## Class bodies are not enclosing scopes

A class body is a scope, but methods cannot see names defined in it. The Language Reference says: "The scope of names defined in a class block is limited to the class block; it does not extend to the code blocks of methods. This includes comprehensions and generator expressions" (§4.2.2). Class attributes must be read through `self`, which is a parameter (a local name holding the instance), or through the class name. A comprehension inside a class body has the same problem, because it is a separate code block.

```python
class Config:
    level = 3
    def get(self):
        return level                 # class names are not visible here

try:
    Config().get()
except NameError as e:
    print("NameError:", e)
```

```output
NameError: name 'level' is not defined
```

## Under the hood: which opcode reads which name

CPython compiles each access to a name into one opcode, and the opcode shows the kind of lookup. The `dis` module, the standard disassembler, prints them.

```python
import dis

g = 1

def bytecode_demo():
    loc = 1
    def cell_user():
        return loc
    return loc + g + cell_user()

# opcodes that move a name's value, for bytecode_demo (CPython 3.12)
for ins in dis.get_instructions(bytecode_demo):
    if ins.opname in ("STORE_DEREF", "LOAD_DEREF", "LOAD_GLOBAL", "STORE_FAST", "LOAD_FAST"):
        print(ins.opname, ins.argrepr)
```

```output
STORE_DEREF loc
STORE_FAST cell_user
LOAD_DEREF loc
LOAD_GLOBAL g
LOAD_FAST cell_user
```

The output connects the earlier rules to the bytecode. The compiler made `loc` a cell variable, because `cell_user` uses it, so `loc` is written with `STORE_DEREF` and read with `LOAD_DEREF`. `cell_user` itself is a local of `bytecode_demo`, so it uses `STORE_FAST` and `LOAD_FAST`. `LOAD_FAST` reads a slot in the frame, which is the fast path for a plain local. `LOAD_DEREF` and `STORE_DEREF` go through a cell, which is why `loc` is read and written through `LOAD_DEREF` and `STORE_DEREF` in the outer function. `LOAD_GLOBAL` searches the module namespace and then the built-ins. The opcode names are CPython details and can change between versions, so treat this output as the 3.12 behaviour.

## Common traps

> [!TRAP]
> Augmented assignment counts as a binding. `total += n` inside a function makes `total` local to that function, so the read raises `UnboundLocalError`. Add `global total` or `nonlocal total`, or return a new value instead.

> [!TRAP]
> Closures in a loop share one cell. `[lambda: i for i in range(3)]` returns `[2, 2, 2]`. Use a default argument or a factory function to capture each value.

> [!TRAP]
> Class-level names are invisible inside methods. A bare `level` in a method is looked up in the global and built-in scopes only. Use `self.level` or `Config.level`.

> [!TRAP]
> `nonlocal` needs an existing enclosing binding. `nonlocal zz` in a function with no enclosing `zz` fails at compile time with `SyntaxError: no binding for nonlocal 'zz' found` (checked on Python 3.12.13).

## Summary

- LEGB is the lookup order: local, enclosing, global, built-in. The search stops at the first scope that binds the name.
- Any binding in a function body, including `+=`, makes the name local to the whole body. Use `global` or `nonlocal` to rebind an outer name.
- A closure keeps a cell (`PyCellObject`, one pointer `ob_ref`). The frame can be freed while the cell lives on.
- Closures capture variables, not values. A default argument or a factory function freezes a value for each closure.

## Quiz time

### Question 1: Predict the output

What does this program print?

```python
x = "global"

def outer():
    x = "enclosing"
    def inner():
        print(x)
    x = "changed"
    return inner

outer()()
```

<details><summary>Show solution</summary>

```output
changed
```

The closure reads `x` from the enclosing scope when it runs, not when it is defined. Both assignments to `x` happen in `outer` before `inner()` is called, and both refer to the same cell, so the last value wins. The global `x` is never reached.

</details>

### Question 2: Find the bug

This function should add `n` to a running total. What error does it raise, and how do you fix it?

```python
total = 0

def add(n):
    total += n
    return total

add(5)
```

<details><summary>Show solution</summary>

It raises `UnboundLocalError: cannot access local variable 'total' where it is not associated with a value`. The augmented assignment `total += n` binds `total`, so the compiler makes `total` local to `add`, and the read happens before the local is bound.

Two fixes are correct. Declare the module variable: `def add(n): global total; total += n; return total`. Or avoid rebinding the name: `def add(n): return total + n`, which only reads `total`. The second does not change the module variable.

</details>

### Question 3: Calculate the output

What does this program print?

```python
def make():
    n = 1
    def f():
        return n
    n = 2
    def g():
        nonlocal n
        n *= 10
        return n
    return f, g

f, g = make()
print(f(), g(), f())
```

<details><summary>Show solution</summary>

```output
2 20 20
```

`f` and `g` share one cell for `n`. The final value of `n` before the calls is 2, so `f()` returns 2. Then `g()` multiplies the shared cell by 10 and returns 20. The last `f()` reads the same cell and returns 20. Python evaluates the three arguments from left to right, which is why the order matters.

</details>

### Question 4: Explain the loop result

Why does `[lambda: i for i in range(3)]` give `[2, 2, 2]`? Name the object that changes the answer when you use `lambda i=i: i` instead.

<details><summary>Show solution</summary>

Each `lambda` reads `i` through a closure. All three closures point to one cell, the cell for the loop variable `i`. When the lambdas are called after the loop, the cell holds 2, the last value that `range(3)` produced. The closures capture the cell, not the value.

With `lambda i=i: i`, the default value is evaluated when each `lambda` is created. Each function then stores its own copy of the current `i` as a parameter default, so the loop variable is no longer a free variable of the lambda. The factory function `make_fn(i)` also works, because each call creates a new cell.

</details>
