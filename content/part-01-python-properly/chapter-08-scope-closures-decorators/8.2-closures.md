A closure is a function that keeps access to variables of the function that created it, even after that outer function has returned. In this lesson you will read a closure's cells through `__closure__`, build a counter with `nonlocal`, and avoid the two traps that catch most readers: late binding in loops and objects kept alive by a closure.

**You need:** functions and `def` (Chapter 7), and the LEGB scope rules from Lesson 8.1. All code was run on CPython 3.12.13.

## The problem closures solve

You often want a function that carries one piece of state, such as a counter or a fixed setting. A global variable works, but any other function can change it. A class with one method works, but it is heavy for a single value. A closure bundles the function with the variables it needs.

Normally a function's local variables disappear when the function returns. A closure is the exception: if an inner function uses a variable of its outer function, that variable survives as long as the inner function does.

## Intuition: a function plus cells

A name that a function uses but does not define itself is a **free variable** (Python Language Reference, Execution model). To make the variable survive, the compiler stores it in a **cell**, a small container that holds one variable's current value. The outer function's frame keeps the cell, and the inner function points to it.

![A function object points through __closure__ to a cell that holds the string 'Hello, World!'; the outer frame also owns that cell](diagrams/8.2-cell-structure.svg "A closure is a function object plus a tuple of cells, one cell per free variable.")

The inner function's `__closure__` attribute is a tuple of cells, in the order of `__code__.co_freevars`. The Python data model defines it as "None or a tuple of cells that contain bindings for the names specified in the `co_freevars` attribute of the function's code object" (Python Data Model). A function with no free variables has `__closure__` set to `None`. The cell holds the variable, not a copy of its value, which is the single most important idea in this lesson.

## Worked example by hand: a counter

Trace `make_counter()` step by step:

1. `make_counter()` creates a cell `count` holding 0. It returns `increment` and `read`, and both point to that same cell.
2. `inc()` runs `count += 1`. The cell now holds 1, and the call returns 1.
3. `inc()` again. The cell now holds 2, and the call returns 2.
4. `read()` looks at the same cell and returns 2.

![Two function objects, increment() and read(), both point to one cell that holds the count; the cell holds 0 before any call and 2 after two calls](diagrams/8.2-shared-cell.svg "Two closures from one call share one cell. Calling increment changes what read sees.")

The line `nonlocal count` is what lets `increment` change the cell. Without it, `count += 1` is an assignment, and any assignment makes a name local to the function it appears in. PEP 3104 puts it as "any assignment to a name implicitly declares that name to be local", and `nonlocal` is the declaration that cancels this for an enclosing scope (PEP 3104).

Here is the same trace in code. This block runs alone in the browser:

```python
def make_counter():
    count = 0
    def increment():
        nonlocal count
        count += 1
        return count
    def read():
        return count
    return increment, read

inc, read = make_counter()
print("cell before calls:", inc.__closure__[0].cell_contents)
inc()
inc()
print("read() after 2 calls:", read())
print("same cell:", inc.__closure__[0] is read.__closure__[0])
```

```output
cell before calls: 0
read() after 2 calls: 2
same cell: True
```

The `cell_contents` attribute can be read and also set. The Python data model documents it as "a cell object has the attribute `cell_contents`. This can be used to get the value of the cell, as well as set the value."

The next block shows the basic structure. A closure created by `outer_function` has one free variable, `text`, and the outer function owns the matching cell:

```python
def outer_function(text):
    def inner_function():
        return text
    return inner_function

closure = outer_function("Hello, World!")
print(closure())
print(closure.__code__.co_freevars)
print(outer_function.__code__.co_cellvars)
cell = closure.__closure__[0]
print(type(cell).__name__, repr(cell.cell_contents))
```

```output
Hello, World!
('text',)
('text',)
cell 'Hello, World!'
```

`co_freevars` is the inner function's list of free variables, and `co_cellvars` is the outer function's list of variables that some inner function captures. Both name `text`, which is how you can check that the two functions share it.

## Late binding: the closure reads the cell at call time

A closure does not store the value that a variable had when the closure was created. It stores the cell, and the cell is read when the function is called. The execution model states it directly: "Name resolution of free variables occurs at runtime, not at compile time." Its example prints 42, not 10, because `i` is rebound before the call (Python Language Reference, Execution model).

The effect is most visible in loops, which is the first trap below.

## Common traps

> [!TRAP]
> **Late binding in loops.** `fs = [lambda: i for i in range(3)]` creates three functions, but all three share one cell for `i`. After the loop the cell holds 2, so every call returns 2. Bind the current value as a default argument (`lambda i=i: i`) or build each function inside a factory call (`make_adder(i)`). Both fixes are in the next block.

The diagram shows the trap and the fix side by side.

![Three lambdas in a loop all point to one cell holding 2, so they return 2, 2, 2; default arguments give each lambda its own value and return 0, 1, 2](diagrams/8.2-late-binding.svg "The trap and the fix. The default argument copies the current value into a parameter, which is not a free variable.")

```python
fs = [lambda: i for i in range(3)]
print([f() for f in fs])
print("one shared cell:", all(f.__closure__[0] is fs[0].__closure__[0] for f in fs))

fixed = [lambda i=i: i for i in range(3)]
print([f() for f in fixed])

def make_adder(i):
    return lambda: i
factory = [make_adder(i) for i in range(3)]
print([f() for f in factory])
```

```output
[2, 2, 2]
one shared cell: True
[0, 1, 2]
[0, 1, 2]
```

> [!TRAP]
> **Rebinding needs `nonlocal`; mutating does not.** Inside an inner function, `count += 1` without `nonlocal` raises `UnboundLocalError`. The execution model defines this error for "a name [that] refers to a local variable that has not yet been bound", and it is a subclass of `NameError`. Calling `items.append(x)` on a list captured from the outer scope does not rebind `items`, so it works without `nonlocal`.

```python
def broken_counter():
    count = 0
    def increment():
        count += 1
        return count
    return increment

try:
    broken_counter()()
except UnboundLocalError as e:
    print(type(e).__name__)
```

```output
UnboundLocalError
```

> [!TRAP]
> **A closure keeps its whole cell alive.** `first()` below reads only `blob.data[0]`, but it refers to the name `blob`, so the cell holds the whole `Blob` object. While `first` exists, its cell keeps the `Blob` referenced, so the leaky version keeps the object alive. Copy the one value you need into its own variable, and the object can be freed. A weak reference does not keep an object alive, per the weakref documentation ("A weak reference to an object is not enough to keep the object alive"), which is why the test below uses one.

The diagram shows what each closure keeps alive, before and after the fix.

![A closure reads the first element of blob's data through a cell that refers to a Blob object, so the Blob stays alive; the fixed closure keeps only the value 0 and the Blob is freed](diagrams/8.2-retention.svg "What a closure keeps alive. The fix copies the value out before the closure is created.")

```python
import weakref

class Blob:
    def __init__(self):
        self.data = list(range(10))

def make_first_leaky():
    blob = Blob()
    ref = weakref.ref(blob)
    def first():
        return blob.data[0]
    return first, ref

def make_first_fixed():
    blob = Blob()
    ref = weakref.ref(blob)
    first_value = blob.data[0]
    def first():
        return first_value
    return first, ref

f1, r1 = make_first_leaky()
print("leaky, blob alive:", r1() is not None)
print("leaky, first():", f1())
f2, r2 = make_first_fixed()
print("fixed, blob alive:", r2() is not None)
print("fixed, first():", f2())
```

```output
leaky, blob alive: True
leaky, first(): 0
fixed, blob alive: False
fixed, first(): 0
```

The "alive" result comes from CPython's reference counting, which frees an object when its last strong reference is removed. The weakref page shows the same effect in its example but does not describe the mechanism, so treat the exact timing as CPython behaviour and do not rely on it.

> [!TRAP]
> **The closure sees later rebindings.** A closure reads its cell at call time, so if the variable is rebound after the closure is created, the closure returns the new value. The execution model's example prints 42 for this reason, not the value 10 that the name had when the function was defined.

## Summary

- A closure is a function object whose `__closure__` tuple holds one cell per name in `co_freevars`.
- A cell holds a variable, not a copy of its value, so closures made by the same call share state.
- Use `nonlocal` to rebind an outer variable. Mutating an object you captured needs no `nonlocal`.
- Closures read their cells at call time, so loop lambdas need a default argument or a factory function.
- A closure keeps its cells alive, and so the objects they refer to. Copy only the values you need.

## Quiz time

### Question 1: Prediction

What does this print?

```python
def make_acc(total):
    def add(x):
        nonlocal total
        total += x
        return total
    return add

a = make_acc(10)
a(5)
print(a(3))
```

<details><summary>Show Solution</summary>

It prints `18`. The cell starts at 10. The first call makes it 15, and the second call makes it 18 and returns 18.
</details>

### Question 2: Find the bug

This code is meant to print "save", "load", "quit", but it does not.

```python
handlers = []
for name in ["save", "load", "quit"]:
    handlers.append(lambda: print("running", name))
for h in handlers:
    h()
```

<details><summary>Show Solution</summary>

It prints `running quit` three times. This loop runs at module level, so `name` is a global variable, not a cell: the lambdas have no `__closure__` (it is `None`), and each one reads the global `name` when it is called, by which time the loop has left it holding `"quit"`. Inside a function the same bug appears with a shared cell, as in Lesson 8.1. Fix it with a default argument: `handlers.append(lambda name=name: print("running", name))`.
</details>

### Question 3: Explain the memory behaviour

In `make_first_leaky`, why is the `Blob` still alive after the function returns, even though `first` only reads one element?

<details><summary>Show Solution</summary>

`first` refers to the name `blob`, so it has `blob` as a free variable and holds the cell that refers to the `Blob`. As long as `first` is alive, its cell is alive, and so is the `Blob`. Copying `blob.data[0]` into its own variable first removes the reference to the `Blob`.
</details>

### Question 4: Count the cells

```python
def outer(a, b):
    x = 10
    def inner():
        return a + b + x + len("abc")
    return inner

f = outer(1, 2)
print(len(f.__closure__))
```

<details><summary>Show Solution</summary>

It prints `3`. The free variables are `a`, `b` and `x`. `len` is a built-in name, not a local variable of `outer`, so it is not a free variable, and `"abc"` is a constant.
</details>
