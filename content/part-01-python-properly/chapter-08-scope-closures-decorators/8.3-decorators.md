A decorator is a function that takes a function and returns a replacement for it. In this lesson you will write one, trace a single call through it, and use `functools.wraps` so the replacement still reports the original name, docstring and signature.

**You need:** closures and free variables (Lesson 8.2), and the fact that a function is a value you can pass to another function.

## The problem decorators solve

Suppose every function in a program should print its arguments and its result. Pasting the same `print` lines into each function repeats the code, and every change has to be made in every copy. A decorator holds that code once and applies it to any function by name.

## `@` is one reassignment

Writing `@logged` above `def add` does not change the body of `add`. It adds one step after the function is created. PEP (Python Enhancement Proposal) 318 gives the rule: `@dec2` above `@dec1` above `def func` is equivalent to `func = dec2(dec1(func))` (PEP 318, Current Syntax; source 1).

A decorator is also free to refuse the call. A permission check can return an error without calling the original at all. The wrapper decides whether, when and with which arguments the original runs.

The result is that the name `add` now refers to a new function, the wrapper. The wrapper keeps the original function in a closure cell, which is the mechanism from Lesson 8.2.

![The name add points at a wrapper; the wrapper holds the original add(a, b) in a closure cell and calls it](diagrams/8.3-rewrite.svg "@logged is one reassignment. The wrapper reaches the original through its closure cell.")

## A worked example by hand

The wrapper accepts any positional and keyword arguments (`*args, **kwargs`), so the same decorator works for any signature. Here is a complete example, which runs on its own:

```python
import functools

def logged(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"-> {func.__name__}{args}")
        result = func(*args, **kwargs)
        print(f"<- {func.__name__} returned {result!r}")
        return result
    return wrapper

@logged
def add(a, b):
    """Return a plus b."""
    return a + b

print(add(2, 3))
print([cell.cell_contents.__name__ for cell in add.__closure__])
```

```output
-> add(2, 3)
<- add returned 5
5
['add']
```

Trace one call, `add(2, 3)`:

1. The name `add` is bound to `wrapper`, so Python calls `wrapper(2, 3)`, with `args = (2, 3)`.
2. The wrapper prints `-> add(2, 3)`.
3. It calls `func(2, 3)`. `func` is a free variable, read from the closure cell, and holds the original `add`.
4. The original returns 5. The wrapper prints `<- add returned 5` and returns the same 5 to the caller.

![A caller calls the wrapper, which calls the original add(a, b); the return value 5 travels back through the wrapper](diagrams/8.3-call-path.svg "One call, two functions. The arguments go in, the result comes back, and the wrapper sees both.")

The last line of the output confirms the closure: the wrapper's only free variable is `func`, and its cell holds the function named `add`.

## Without functools.wraps, the function loses its identity

A wrapper is an ordinary function, so after decoration the name `add` refers to the wrapper's metadata, not the original's. Compare two decorators that differ only in one line:

```python
import functools
import inspect

def plain(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

def wrapped(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@plain
def add_plain(a, b):
    """Return a plus b."""
    return a + b

@wrapped
def add_wrapped(a, b):
    """Return a plus b."""
    return a + b

for f in (add_plain, add_wrapped):
    print(f.__name__, repr(f.__doc__), hasattr(f, "__wrapped__"), inspect.signature(f))
```

```output
wrapper None False (*args, **kwargs)
add_wrapped 'Return a plus b.' True (a, b)
```

![Two cards: a plain wrapper reports name wrapper, doc None, no __wrapped__, signature (*args, **kwargs); functools.wraps reports the original name, docstring, __wrapped__ and signature (a, b)](diagrams/8.3-metadata.svg "The same call succeeds either way. Only the reported metadata differs.")

`functools.wraps(func)` copies `__module__`, `__name__`, `__qualname__`, `__annotations__`, `__type_params__` and `__doc__` from `func` onto the wrapper, merges `func.__dict__` into the wrapper's, and sets `wrapper.__wrapped__ = func` (functools documentation; source 2). The `__type_params__` entry is copied from Python 3.12 onward, and the outputs here come from 3.12.13. Because `__wrapped__` is set, `inspect.signature` reports the original `(a, b)` by default. Passing `follow_wrapped=False` stops it from following the chain (inspect documentation; source 3).

`functools.wraps` does not change what the wrapper does. It changes only what the wrapper reports about itself. `add.__wrapped__(2, 3)` calls the original and skips the logging.

The difference shows up when you read documentation. `help(add)` reads `__name__` and `__doc__`, so without `functools.wraps` it describes the wrapper, and with it, the original. Tracebacks are different: a traceback still shows `in wrapper` for the wrapper's frame, because `functools.wraps` changes the function object's attributes, not the code that runs. I confirmed both behaviours with a short script (b, reasoning checked by running).

## Stacking decorators

You can apply several decorators to one function. `@outer` above `@inner` above `def greet` is `greet = outer(inner(greet))`. The bottom decorator wraps the function first, so the top one is the outermost layer. At call time the outermost wrapper runs first and finishes last.

Order changes meaning. If `@timer` sits above `@retry`, the measured time includes every retry. With the two swapped, each attempt is timed separately. The decorators are the same; only the layering differs (b, reasoning from the nesting above).

```python
import functools

def outer(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("outer: in")
        result = func(*args, **kwargs)
        print("outer: out")
        return result
    return wrapper

def inner(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("inner: in")
        result = func(*args, **kwargs)
        print("inner: out")
        return result
    return wrapper

@outer
@inner
def greet():
    print("greet body")
    return "done"

print("stack result:", greet())
```

```output
outer: in
inner: in
greet body
inner: out
outer: out
stack result: done
```

![Three nested boxes: outer contains inner, which contains greet; the printed order runs 1 to 5 from the outside in and back out](diagrams/8.3-stacking.svg "Nested layers. The print order is the onion order: in from the outside, out to the outside.")

## Recursion passes through the decorator

A decorator replaces the object bound to a name. A recursive function calls itself through its name, so the name `fib` refers to the wrapper at every level. Each recursive call is therefore counted. The next block counts the calls made by naive Fibonacci:

```python
import functools

calls = 0

def count_calls(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        global calls
        calls += 1
        return func(*args, **kwargs)
    return wrapper

@count_calls
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

for n in (5, 10, 15):
    calls = 0
    value = fib(n)
    print(f"fib({n}) = {value}, wrapper calls = {calls}")
```

```output
fib(5) = 5, wrapper calls = 15
fib(10) = 55, wrapper calls = 177
fib(15) = 610, wrapper calls = 1973
```

The naive recursion obeys $C(n) = C(n-1) + C(n-2) + 1$ with $C(0) = C(1) = 1$, which gives $C(n) = 2F_{n+1} - 1$, where $F$ is the Fibonacci sequence (b, reasoning from the recurrence). The experiment behind this lesson also measured $n = 20$: 21891 wrapper calls, which equals $2 \cdot 10946 - 1$.

Where you put the counter matters. A wrapper counts calls to the decorated name. A counter placed inside the body of `fib` would count the same calls here, but would miss any call that a decorator answers without entering the body, such as a cached result. Decide which event you are measuring before you choose where the code goes.

![Bar chart of wrapper calls for fib at n = 5, 10 and 15: 15, 177 and 1973](diagrams/8.3-fib-calls.svg "Measured wrapper calls. Growth is exponential in n, and the decorator sees every one of them.")

> [!KEY-INSIGHT]
> The decorator runs on every call to the name it replaced, not on the first call only. In `count_calls`, only `wrapper` runs at call time. The body of `count_calls` ran once, when `def fib` executed.

## Common traps

> [!TRAP]
> **Forgetting `return`.** If the wrapper calls `func` but does not return its result, every decorated call gives `None`. The next block shows it:

```python
import functools

def broken(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        func(*args, **kwargs)          # the result is computed, then discarded
    return wrapper

@broken
def square(x):
    return x * x

print("square(4) =", square(4))
```

```output
square(4) = None
```

> [!TRAP]
> **Mutable decorator state is shared.** `calls` in the example above is one module-level variable. Every function decorated with `count_calls` adds to the same total. Give each decorated function its own counter, for example as an attribute on the wrapper, if you need separate totals.

> [!TRAP]
> **Accept any arguments.** A wrapper written as `def wrapper(a, b)` works for `add` and fails for any function with a different signature. Keep `*args` and `**kwargs`. Accepting arbitrary arguments and forwarding them unchanged keeps the decorator reusable.

> [!TRAP]
> **Decorators only affect the name they are attached to.** Code that kept a reference to the original function before decoration still calls the undecorated version. Decorating a name later in the file does not change earlier references to the original object.

## Summary

- `@deco` above `def f` is one reassignment: `f = deco(f)` (PEP 318).
- A wrapper takes `*args, **kwargs`, reaches the original through a closure cell, and returns its result.
- `functools.wraps` copies the name, qualified name, docstring and other metadata, and sets `__wrapped__`; `inspect.signature` follows that link.
- Stacked decorators nest: the outermost wrapper runs first and finishes last.
- A decorator that drops the return value silently turns every call into `None`.

### Question 2: Prediction

What does this print?

```python
import functools

def tag(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        return "[" + func(*args, **kwargs) + "]"
    return wrapper

@tag
def word():
    return "hi"

print(word(), word.__name__)
```

<details><summary>Show Solution</summary>

It prints `[hi] word`. The wrapper returns the original's result in brackets. `functools.wraps` keeps the name `word`.
</details>

### Question 3: Bug-spotting

A colleague writes this decorator to time a function and reports that every call returns `None`. Find the bug.

```python
import functools

def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        func(*args, **kwargs)
    return wrapper
```

<details><summary>Show Solution</summary>

The wrapper calls `func` but does not `return` its result, so the wrapper returns `None`. Fix it with `return func(*args, **kwargs)` or store the value and return it.
</details>

### Question 4: Explanation

Why does `count_calls` count recursive calls to `fib`, even though the recursion is written inside `fib` itself?

<details><summary>Show Solution</summary>

The decorator replaces the object bound to the global name `fib`. The body of `fib` looks up `fib` by name at each call, so it finds the wrapper, not the original function. Each recursive call therefore passes through the wrapper.
</details>
