By the end of this lesson you will be able to write a decorator that takes arguments, such as `@repeat(3)`, and a decorator that takes a class, and you will be able to tell which of the two a bug report is about. You will trace the evaluation of `@repeat(3)` by hand and check each step against code.

**You need:** how a plain decorator is applied (Lesson 8.3) and closures, meaning an inner function that remembers variables of its outer function (Lesson 8.2).

## The problem

A plain decorator receives exactly one thing: the function it decorates. Suppose you want a `repeat` decorator that runs a function three times, and you want the number to be a setting of the decorator, so that the same decorator can run a function two times or ten times. The decorator needs a second input, and the `@` syntax has no slot for it.

The same gap appears with classes. You may want to apply one change, such as logging every attribute access, to many classes. A class decorator is a function that receives a class and returns a class, and it has to do this without rewriting each class by hand.

## Intuition: `@repeat(3)` is two calls

Python does not have special syntax for parameterized decorators. The line `@repeat(3)` is an expression, and Python evaluates it first. The expression `repeat(3)` must return a decorator, and Python then calls that decorator on the function. The Python Enhancement Proposal (PEP) that defined decorators says it directly: `@decomaker(argA, argB)` above a `def` means `func = decomaker(argA, argB)(func)` (PEP 318). PEP 318 is the source for the stacking order used later in this lesson.

![Three stages: repeat(3) returns decorator_repeat with a cell holding num_times = 3; decorator_repeat(greet) returns wrapper, which holds func and num_times; the name greet is then bound to wrapper](diagrams/8.4-closure-chain.svg "Two calls, two closures. Each inner function keeps its outer variables alive.")

Each stage returns a function that remembers variables from the stage before. This memory is the closure: the variables live in cells attached to the inner function, which you can read through `__closure__`.

## Worked example by hand

Trace `@repeat(3)` on `def greet(name)` in three steps:

1. `repeat(3)` runs. It binds `num_times = 3` and returns `decorator_repeat`.
2. `decorator_repeat(greet)` runs. It binds `func = greet`, creates `wrapper`, and returns it. `wrapper` now holds two cells, `func` and `num_times`.
3. The name `greet` is rebound to `wrapper`.

When you later call `greet("Alice")`, `wrapper` loops three times and calls the original `greet` each time. It returns the result of the last call. The code below checks each step, and its last two lines read the cells back.

```python
from functools import wraps

def repeat(num_times):
    def decorator_repeat(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            for _ in range(num_times):
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator_repeat

@repeat(num_times=3)
def greet(name):
    print(f"Hello, {name}!")
    return f"Hello, {name}!"

print(greet("Alice"))

step1 = repeat(3)
print(step1.__code__.co_freevars, [c.cell_contents for c in step1.__closure__])

def plain(name):
    return name

step2 = step1(plain)
cells = {n: c.cell_contents for n, c in zip(step2.__code__.co_freevars, step2.__closure__)}
print(sorted(cells), cells["num_times"])
```

```output
Hello, Alice!
Hello, Alice!
Hello, Alice!
Hello, Alice!
('num_times',) [3]
['func', 'num_times'] 3
```

The first three lines come from the loop. The fourth comes from `print` of the returned string. `step1` has exactly one free variable, `num_times`, and its single cell holds 3. `step2` has two, `func` and `num_times`.

The outer function runs once, when the decorated `def` is executed, not once per call. Anything you compute in `repeat` before `return decorator_repeat` is fixed for every later call of `greet`.

`functools.wraps` is not part of the parameter mechanism. It copies the name and docstring of the original function onto `wrapper` (the Python `functools` documentation lists the copied attributes and sets `__wrapped__`). Without it, `greet.__name__` would read `"wrapper"`, and logs and introspection would show the wrong name. Lesson 8.3 covers this in detail.

## Stacking decorators

Decorators stack from the bottom up. `@a` above `@b` above `def f` means `f = a(b(f))`. The bottom decorator wraps the function first, and the top one wraps the result. The result is that the top decorator runs first when the function is called.

```python
def tag(label):
    def deco(f):
        def w(*args, **kwargs):
            print("enter", label)
            result = f(*args, **kwargs)
            print("exit", label)
            return result
        return w
    return deco

@tag("outer")
@tag("inner")
def body():
    print("body")

body()
```

```output
enter outer
enter inner
body
exit inner
exit outer
```

The top decorator, `outer`, is the outermost wrapper, so it prints first and prints last.

## The forgotten parentheses

The most common bug in parameterized decorators is a missing call. Without parentheses, Python passes the function as `num_times`.

![Correct @repeat(3): greet is a wrapper and the call prints the message three times. Bug @repeat with no call: greet is decorator_repeat, and greet("Alice") returns a function, prints nothing and raises no error](diagrams/8.4-no-parens.svg "The bug produces no error, only a wrong result.")

```python
def repeat(num_times):
    def decorator_repeat(func):
        def wrapper(*args, **kwargs):
            for _ in range(num_times):
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator_repeat

@repeat                       # BUG: missing (3)
def shout(name):
    print(f"Hello, {name}!")
    return f"Hello, {name}!"

result = shout("Alice")       # raises no error
print(type(shout).__name__)
print(type(result).__name__, result.__name__)
```

```output
function
function wrapper
```

Here `repeat(shout)` returns `decorator_repeat`, so `shout` becomes `decorator_repeat`. Calling `shout("Alice")` runs `decorator_repeat("Alice")`, which returns a `wrapper` and does nothing else. The function `shout` never runs, so nothing is printed.

## Class decorators

A class decorator has the same shape as a function decorator. Its input is a class, and its return value is bound to the class name (PEP 3129). PEP 3129 states that the semantics "are the same as for function decorators", and its equivalence is `A = foo(bar(A))` for stacked class decorators.

A class decorator also runs once, when the `class` statement finishes executing. Whatever it does to the class is in place before the first instance exists, so a bug in the decorator shows up at import time, not at the first call.

The example below is the simplest pattern: the decorator builds a subclass whose `__getattribute__` and `__setattr__` print a message, and returns it.

![Left: PersonRaw, the class you wrote. An arrow labelled debug() leads to Person.__name__ = DebuggedClass, which is a subclass of PersonRaw. A note below lists the fix and the functools.update_wrapper error](diagrams/8.4-class-rebind.svg "The decorated name refers to a subclass, not to the class you wrote.")

```python
def debug(cls):
    class DebuggedClass(cls):
        def __getattribute__(self, name):
            print(f"get {name}")
            return super().__getattribute__(name)

        def __setattr__(self, name, value):
            print(f"set {name}")
            super().__setattr__(name, value)
    return DebuggedClass

@debug
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def greet(self):
        return f"Hello, my name is {self.name} and I am {self.age} years old."

print("name:", Person.__name__, "| bases:", [b.__name__ for b in Person.__bases__])
p = Person("Bob", 30)
print(p.greet())
```

```output
name: DebuggedClass | bases: ['Person']
set name
set age
get greet
get name
get age
Hello, my name is Bob and I am 30 years old.
```

![Hook events: constructing Person("Bob", 30) fires two set events and no get events; calling p.greet() fires three get events, for greet, name and age](diagrams/8.4-hook-trace.svg "Each attribute read or write passes through the hook once.")

Two facts from the output matter. First, `Person` now names `DebuggedClass`, and the class you wrote survives only as its base, `Person`. Second, the hooks fire only for instance attribute access. Constructing `Person("Bob", 30)` causes two set events and no get events, because the assignments in `__init__` go through `__setattr__`. Calling `p.greet()` causes three get events, one for each attribute the method touches: `greet`, `name` and `age`. The Python data model documents `__getattribute__` as "called unconditionally to implement attribute accesses for instances of the class" (Python data model reference).

The alternative pattern does not create a subclass. The decorator changes the class in place and returns the same object. The standard library uses this pattern: `dataclasses.dataclass` "returns the same class it is called on; no new class is created" (dataclasses documentation). The exception is `slots=True`, which creates a new class. Parameterized class decorators use the same closure pattern as function decorators:

```python
REGISTRY = {}

def register(name):
    def deco(cls):
        REGISTRY[name] = cls
        return cls
    return deco

@register("csv")
class CsvReader:
    pass

print(list(REGISTRY))
print(REGISTRY["csv"] is CsvReader)
print(CsvReader.__name__)
```

```output
['csv']
True
CsvReader
```

Use the subclass pattern when you need to change how instances behave. Use the in-place pattern when you need to record, register or annotate the class, because the class you wrote stays the class the rest of the program sees.

## Common traps

> [!TRAP]
> Writing `@repeat` where you meant `@repeat(3)` does not raise an error. The function silently becomes `decorator_repeat`, as the second example above shows. When a decorator takes parameters, check the call parentheses first.

> [!TRAP]
> A decorator without `functools.wraps` replaces the function's name. In the `repeat` example without `wraps`, `greet.__name__` is `"wrapper"`, so logs and introspection report the wrong name.

> [!TRAP]
> A subclass-based class decorator changes the class name. `Person.__name__` reads `"DebuggedClass"` after `@debug`, and `type(p).__name__` does too. Copy the identity back onto the subclass with `DebuggedClass.__name__ = cls.__name__` and `DebuggedClass.__qualname__ = cls.__qualname__`, or change the class in place.

> [!TRAP]
> Decorators stack from the bottom up. In `@outer` above `@inner` above `def f`, `inner` wraps `f` first, but `outer` runs first when `f` is called. Reading the stack top to bottom as the order of execution is the usual mistake.

> [!TRAP]
> A class cannot be the wrapper in `functools.update_wrapper`. Calling `functools.update_wrapper(C, func)` with a class `C` failed on Python 3.12 with `AttributeError: 'mappingproxy' object has no attribute 'update'` (checked by running). The reason is that `update_wrapper` updates the wrapper's `__dict__`, and a class's `__dict__` is a read-only mapping (this explanation is my own reasoning from the error message). Copy the identity attributes by hand.

## Summary

- `@repeat(3)` is two calls: `repeat(3)` returns a decorator, and that decorator wraps the function.
- Each stage remembers its variables through closure cells, readable from `__closure__`.
- Stacked decorators apply bottom-up, and the top one runs first when the function is called.
- A class decorator returns a class: a subclass renames the class, while an in-place change keeps the original name, as `dataclasses.dataclass` does.

## Quiz time

### Question 1: Prediction

In the first example, how many lines does `print(greet("Bob"))` print, and why?

<details><summary>Show Solution</summary>

Four lines. `wrapper` calls the original `greet` three times, and each call prints `Hello, Bob!`. The `print` on the outside then prints the returned string, which is the fourth line.

</details>

### Question 2: Bug-spotting

A colleague writes `@repeat` on a function and says the function "is broken because it does nothing". What is the actual state of the program, and what is the one-line fix?

<details><summary>Show Solution</summary>

The function is not broken in the way they think. Without a call, `repeat(func)` sets `num_times` to the function and returns `decorator_repeat`, so the name is bound to `decorator_repeat`. Calling it returns a `wrapper` and prints nothing, with no error. The fix is `@repeat(3)`, with the number of repetitions in the parentheses.

</details>

### Question 3: Calculation

Given `@tag("a")` above `@tag("b")` above `def body()`, write the lines printed by `body()`.

<details><summary>Show Solution</summary>

`body` is `a(b(body))`. Calling it enters `a` first, then `b`, runs the body, and exits in reverse order:

```
enter a
enter b
body
exit b
exit a
```

</details>

### Question 4: Explanation

After you decorate a class with a subclass-based decorator, a test checks `type(obj).__name__ == "Person"` and fails. Explain why, and give two ways to fix it.

<details><summary>Show Solution</summary>

The decorator returned a subclass, which is a new class with the name `DebuggedClass`, so `type(obj)` is that subclass. Fix it in one of two ways. Either copy `__name__` and `__qualname__` from the original class onto the subclass, or change the class in place and return it, as `dataclasses.dataclass` does by default.

</details>
