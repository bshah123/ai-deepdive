By the end of this lesson you can write a class that a `for` loop accepts, explain why a second loop over some objects prints nothing, and find the one-line bug that makes a loop run forever. The protocol is two methods, `__iter__` and `__next__`, and generators (Lesson 9.2) are built on it.

**You need:** a class with `__init__` and `self`, and `for` loops (Lesson 4.1 covers lists, which you will iterate over here).

## The problem

A `for` loop works on a list, a tuple, a dictionary, a string and a file, and it never needs to know how any of them are stored. The loop only asks the object for one item at a time. If your own class can answer the same questions, it works in the same loop.

The cost of the alternative is memory. A list of a million integers keeps a pointer to every item, and the list must exist before the loop starts. An iterator produces one item when asked and keeps only its position. Section "Memory" below measures the difference.

## Intuition: iterable and iterator are different objects

Two words carry the whole protocol.

- An **iterable** is something you can loop over. It has `__iter__`, which returns an iterator. A list is iterable, and it holds the values.
- An **iterator** is a cursor. It has `__next__`, which returns the next value or raises `StopIteration` ("no more values"). It holds the position.

![A list of three values and two separate cursors, each made by its own call to iter(); the cursors are not the same object](diagrams/9.1-iterable-vs-iterator.svg "The list has no position. Each iter() call makes a new cursor at the first item.")

Lists show the split directly. The list has no `__next__`, and each `iter()` call makes a new `list_iterator` object. Measured on CPython 3.12:

```python
lst = [10, 20, 30]
print(type(iter(lst)).__name__)
print(hasattr(lst, "__next__"), hasattr(iter(lst), "__next__"))
it1, it2 = iter(lst), iter(lst)
print("it1 is it2:", it1 is it2)
print(next(it1), next(it1))
print(next(it2))
print(next(it1, "default"))
print(next(it1, "default"))
```

```output
list_iterator
False True
it1 is it2: False
10 20
10
30
default
```

`next(it1, "default")` returns the value given as the second argument when the iterator is exhausted, instead of raising. Here `it1` had one item left (30), so the fourth call returns `"default"`.

## Worked example by hand: the calls for CountUpTo(3)

Write the class. `__iter__` returns the object itself, and `__next__` returns 1, 2, 3, then raises `StopIteration`:

```python
class CountUpTo:
    """An iterator: __iter__ returns self, __next__ does the work."""

    def __init__(self, max_num):
        self.max_num = max_num
        self.current = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self.current < self.max_num:
            self.current += 1
            return self.current
        raise StopIteration

for n in CountUpTo(3):
    print(n)
```

```output
1
2
3
```

By hand, `for n in CountUpTo(3)` does this. Python calls `iter()` once, which calls `__iter__()`. It then calls `next()` repeatedly, which calls `__next__()`. Three calls return 1, 2 and 3, and the fourth call raises `StopIteration`, which ends the loop. The trace below prints each call to check that order:

![Five boxes in order: iter() returns self, then next() returns 1, 2, 3, and a final next() raises StopIteration](diagrams/9.1-call-trace.svg "One iter() call and four next() calls. The fourth next() call is the one that ends the loop.")

```python
class TracedCountUpTo:
    def __init__(self, max_num):
        self.max_num = max_num
        self.current = 0

    def __iter__(self):
        print("iter() called")
        return self

    def __next__(self):
        if self.current < self.max_num:
            self.current += 1
            print(f"next() -> {self.current}")
            return self.current
        print("next() -> StopIteration")
        raise StopIteration

for n in TracedCountUpTo(3):
    pass
```

```output
iter() called
next() -> 1
next() -> 2
next() -> 3
next() -> StopIteration
```

The `for` statement is the protocol written as a loop. The same steps on a list iterator look like this:

```python
it = iter([1, 2, 3])
while True:
    try:
        n = next(it)
    except StopIteration:
        break
    print(n)
```

```output
1
2
3
```

The loop body never sees `StopIteration`. It is the signal that stops the loop.

## Reusable iterables versus one-shot iterators

`CountUpTo` returns `self` from `__iter__`, so it is also an iterator, and its state lives on the object. Once it is exhausted, it stays exhausted:

```python
class CountUpTo:
    def __init__(self, max_num):
        self.max_num = max_num
        self.current = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self.current < self.max_num:
            self.current += 1
            return self.current
        raise StopIteration

c = CountUpTo(5)
print("one-shot, pass 1:", list(c))
print("one-shot, pass 2:", list(c))

class CountUpToIterable:
    def __init__(self, max_num):
        self.max_num = max_num

    def __iter__(self):
        return CountUpToIterator(self.max_num)

class CountUpToIterator:
    def __init__(self, max_num):
        self.max_num = max_num
        self.current = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self.current < self.max_num:
            self.current += 1
            return self.current
        raise StopIteration

r = CountUpToIterable(5)
print("reusable, pass 1:", list(r))
print("reusable, pass 2:", list(r))
```

```output
one-shot, pass 1: [1, 2, 3, 4, 5]
one-shot, pass 2: []
reusable, pass 1: [1, 2, 3, 4, 5]
reusable, pass 2: [1, 2, 3, 4, 5]
```

![Left: __iter__ returns self, and the second list() call gives an empty list. Right: __iter__ returns a new iterator, and both calls give all five values](diagrams/9.1-one-shot-vs-reusable.svg "Where the position is stored decides whether a second pass is possible.")

The fix is to split the roles. The iterable holds the settings and creates a fresh iterator on each `__iter__` call, so the position is never shared.

## The protocol rules, from the sources

The Python library reference defines the two methods in the same terms. A container needs `__iter__()`, which returns an iterator. An iterator needs `__iter__()`, which returns the iterator object itself so that it can be used in a `for` or `in` statement, and `__next__()`, which returns the next item or raises `StopIteration`. It also states that once `__next__()` has raised `StopIteration`, it must keep doing so on later calls, and that implementations which do not are broken ([Python docs, Iteration-related types](https://docs.python.org/3/library/stdtypes.html)). PEP 234 (Yee and van Rossum, 2001) gives the same contract and explains that `for` asks the object for an iterator once, then calls `next()` until the end ([PEP 234](https://peps.python.org/pep-0234/)).

## Memory: why an iterator is worth having

The iterator in the examples keeps only a position. The list it came from keeps every item. Measured on 64-bit CPython 3.12:

![Two bars drawn to scale: a list of one million ints takes 8,000,056 bytes, and an iterator over it takes 48 bytes, a sliver at this scale](diagrams/9.1-memory-bars.svg "Memory held by the list and by its iterator. The list figure counts only its pointer array.")

```python
import sys

data = list(range(1_000_000))
it = iter(data)
print("list object:", sys.getsizeof(data), "bytes")
print("iterator:   ", sys.getsizeof(it), "bytes")
```

```output
list object: 8000056 bytes
iterator:    48 bytes
```

`sys.getsizeof` counts only the container's own allocation. It excludes the million integer objects the list points to, so the true cost of the list is higher. The numbers are specific to 64-bit CPython 3.12; other builds and the browser runner may print different values. The point is the ratio: the iterator does not grow with the data.

## Common traps

> [!TRAP]
> **Forgetting StopIteration.** If `__next__` falls off the end, Python returns `None` as an ordinary value. A `for` loop treats it as an item, so the loop never stops. The section on the missing StopIteration shows this.

> [!TRAP]
> **Reusing a one-shot iterator.** A second `for` loop over an object whose `__iter__` returns `self` runs zero times and raises no error. Return a new iterator from `__iter__` when the object must be looped more than once.

> [!TRAP]
> **Returning a list from `__iter__`.** A list is iterable, not an iterator. `for x in obj` fails with `TypeError: iter() returned non-iterator of type 'list'`. Return `iter(self.items)` instead.

> [!TRAP]
> **Assigning `__iter__` on an instance.** Python looks up special methods on the type, not on the instance. Setting `b.__iter__` on one object has no effect on `for`. The next block shows the error.

```python
class Bag:
    pass

b = Bag()
b.__iter__ = lambda: iter([1, 2])
try:
    for x in b:
        pass
except TypeError as e:
    print("TypeError:", e)
```

```output
TypeError: 'Bag' object is not iterable
```

The fix is to define `__iter__` in the class body. The Python data model states that implicit special-method calls are only guaranteed to work when the method is defined on the type ([Python data model, Special method lookup](https://docs.python.org/3/reference/datamodel.html)).

> [!TRAP]
> **Calling next() on an iterable.** `next([1, 2])` raises `TypeError: 'list' object is not an iterator`. Call `iter()` first, as `for` does.

## A bug to find: the missing StopIteration

This `__next__` is meant to return even numbers up to `max_num`. It tests the counter before adding 2, so it also returns 8 when `max_num` is 6. It also has no `else` branch. When the condition fails, the function ends without a `return` or a `raise`:

```python
from itertools import islice

class EvenNumbers:
    def __init__(self, max_num):
        self.max_num = max_num
        self.current = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self.current <= self.max_num:
            self.current += 2
            return self.current
        # no else branch: the function falls off the end and returns None

print(list(islice(EvenNumbers(6), 8)))
```

```output
[2, 4, 6, 8, None, None, None, None]
```

![Eight boxes: 2, 4, 6, 8 in green, then four None values in red, with a caption that the loop never sees StopIteration](diagrams/9.1-missing-stopiteration.svg "Calls 1 to 4 return even numbers; every later call returns None, which a for loop accepts as a value.")

Calling `list(EvenNumbers(6))` directly would never return. `islice` stops after eight items so the example finishes. The fix is an `else: raise StopIteration` branch. With it, the class yields `2, 4, 6, 8` and the loop ends.

## Summary

- A `for` loop calls `iter(obj)` once and then `next(it)` until `StopIteration` is raised.
- An iterable's `__iter__` returns an iterator. An iterator's `__iter__` returns itself, and its `__next__` returns the next value or raises `StopIteration`.
- If the position lives on the object, one pass is possible. Return a fresh iterator from `__iter__` for objects that must be looped many times.
- An iterator keeps only its position, so it costs a few dozen bytes however long the data is. A list costs memory for every item.

## Quiz time

### Question 1: Predict the output

```python
it = iter([1, 2, 3])
print(list(it))
print(list(it))
```

<details><summary>Show Solution</summary>

The output is `[1, 2, 3]` and then `[]`. The first `list()` consumes the iterator until it raises `StopIteration`. The second call starts from the exhausted cursor, so it gets no values and returns an empty list. The list object itself was never consumed.

</details>

### Question 2: Find the bug

This class should yield the squares 1, 4, 9, 16 for `Squares(4)`. What does it actually print, and why?

```python
class Squares:
    def __init__(self, n):
        self.n = n
        self.i = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self.i > self.n:
            raise StopIteration
        self.i += 1
        return self.i * self.i

print(list(Squares(4)))
```

<details><summary>Show Solution</summary>

It prints `[1, 4, 9, 16, 25]`. The stop test uses `>` where it needs `>=`. The fifth call sees `self.i == 4`, which is not greater than 4, so it increments to 5 and returns 25. The next call sees 5 > 4 and stops. The fix is `if self.i >= self.n:`.

</details>

### Question 3: Count the calls

A class's `__next__` returns 1, 2, 3, 4 and then raises `StopIteration`. How many times do `__iter__` and `__next__` run during `for x in obj: pass`?

<details><summary>Show Solution</summary>

`__iter__` runs once. `__next__` runs five times: four calls return 1, 2, 3, 4, and the fifth raises `StopIteration`. This is the pattern in the call trace above: one `iter()` and `n + 1` `next()` calls for `n` values.

</details>

### Question 4: Explain the design

A colleague writes `__iter__` as `return self` for a class that wraps a database query. Their function `report()` loops over the object twice and the second loop prints nothing. Explain why, and say what they should change.

<details><summary>Show Solution</summary>

The object is its own iterator, so its position (the number of rows read) is stored on the object. The first loop exhausts that position. The second loop asks for an iterator, gets the same exhausted object, and receives `StopIteration` at once, so it runs zero times without an error. They should either store only the query settings and return a new iterator from `__iter__` (the `CountUpToIterable` pattern above), or, if the rows are already in memory, return `iter(self.rows)`.

</details>
