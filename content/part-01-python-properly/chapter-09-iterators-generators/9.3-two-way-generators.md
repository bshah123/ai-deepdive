A generator can receive data as well as produce it. In this lesson you will use `send()` to push values into a paused generator, `throw()` to raise an error at the exact line where it is paused, and `close()` to stop it so its cleanup code runs. You will also be able to predict what each call returns.

**You need:** generators and the `yield` keyword (Lesson 9.2).

## The problem these methods solve

A plain generator moves data one way: `next()` pulls a value out, and nothing goes in. Two situations need data to flow the other way. First, a consumer feeds readings to a running statistic and wants the updated result after each one. Second, a worker holds a resource such as a file or a network connection, and the caller must be able to tell it to stop, so that its cleanup code runs.

Python's answer is PEP 342 (Python Enhancement Proposal 342, "Coroutines via Enhanced Generators", Python 2.5). It added the three methods in this lesson.

You could build the same thing with a class that stores `total` and `count` as attributes and exposes an `update(v)` method. That is often clearer when the state is complicated. A generator is shorter when the state is a few local variables and the logic reads as a sequence of steps. As in Lesson 9.2, the locals survive between calls because the generator's frame is suspended, not destroyed.

## Intuition: `yield` is an expression

In `value = yield average`, the `yield` is an expression, and an expression has a value. That value is whatever the caller passed to `send()`. `next()` passes `None`.

![Two boxes: the caller and the generator. An arrow carries the sent value in through send(v); a second arrow carries the yielded value back out](diagrams/9.3-two-way-flow.svg "A generator is a two-way channel. The sent value lands in the yield expression.")

Each `send(v)` does three things. It resumes the generator at its paused `yield`. It makes `v` the result of that `yield`. Then it runs the code until the next `yield` and returns the value that `yield` produces.

## Worked example by hand: a running average

Here is a generator that keeps a running mean of the numbers sent to it.

![A table with one row per call: next(), then send(10), send(30), send(5), send(3). Columns show the value sent, the running total, the count, and the returned average 10.0, 20.0, 15.0, 12.0](diagrams/9.3-averager-trace.svg "Each send() adds to the total and returns total divided by count.")

Trace it by hand. The first `next()` runs the body up to the first `yield`, which yields `average = None`. Now the generator is paused at `yield`, ready to receive a value.

- `send(10)`: total $= 10$, count $= 1$, average $= 10/1 = 10.0$.
- `send(30)`: total $= 40$, count $= 2$, average $= 40/2 = 20.0$.
- `send(5)`: total $= 45$, count $= 3$, average $= 45/3 = 15.0$.
- `send(3)`: total $= 48$, count $= 4$, average $= 48/4 = 12.0$.

The code reproduces these numbers exactly:

```python
def averager():
    total, count, average = 0.0, 0, None
    while True:
        value = yield average          # the sent value becomes the result of this yield
        total += value
        count += 1
        average = total / count

avg = averager()
print("next() ->", next(avg))          # runs to the first yield; this is the priming step
for x in [10, 30, 5, 3]:
    print(f"send({x}) ->", avg.send(x))

g = averager()
try:
    g.send(10)                         # not primed yet
except TypeError as e:
    print("TypeError:", e)
```

```output
next() -> None
send(10) -> 10.0
send(30) -> 20.0
send(5) -> 15.0
send(3) -> 12.0
TypeError: can't send non-None value to a just-started generator
```

Each call to `send()` runs exactly one trip around the `while` loop: it assigns the sent value, updates the two counters, and yields the new average. Notice that `average` is not recomputed from the whole list. The state carried between calls is just two numbers and the current average, which is why the method stays cheap for a long stream.

The first `next()` is called priming. Before the first `yield` there is no paused expression that could receive a value, so only `None` is allowed. The last block shows the error you get when you skip this step.

## Under the hood: what each method does

The rules below come from the Python documentation for generator methods, which states that `send()` must be called with `None` to start a generator (see References).

**`send(v)`** resumes the paused generator, makes `v` the value of the paused `yield`, and returns the next value the generator yields. It is the same as `next()` when `v` is `None`.

**`throw(e)`** raises the exception `e` at the paused `yield`, as if that line had failed. The generator's own `try`/`except` decides the outcome, and there are three cases, shown below.

![Three columns below one entry point. Case 1: the handler catches the error and yields again, so throw() returns that value and close() raises RuntimeError. Case 2: the handler catches and returns, so throw() raises StopIteration. Case 3: the error is not caught, so throw() re-raises it and close() returns None](diagrams/9.3-throw-close-outcomes.svg "What happens after throw(e) or close(). The generator's handler decides.")

**`close()`** is equivalent to `throw(GeneratorExit)`. `GeneratorExit` is a special exception meant to end a generator. If it propagates out, `close()` returns `None`. If the generator yields instead, `close()` raises `RuntimeError`.

Here is `throw()` in action on a counter. The reset path shows that a caught error does not end the generator.

```python
def counter():
    n = 0
    while True:
        try:
            delta = yield n
            n += delta
        except ValueError:
            n = 0                      # reset on an injected error

c = counter()
print("next() ->", next(c))
print("send(5) ->", c.send(5))
print("send(2) ->", c.send(2))
print("throw(ValueError) ->", c.throw(ValueError("reset")))
print("send(4) ->", c.send(4))
```

```output
next() -> 0
send(5) -> 5
send(2) -> 7
throw(ValueError) -> 0
send(4) -> 4
```

The `throw()` call returned `0`, the value of the next `yield` after the handler ran. The generator did not stop.

If the handler does not catch the error, the error comes back to the caller. If the handler catches it and returns, the generator is finished, and `throw()` raises `StopIteration`:

```python
def plain():
    yield 1
    yield 2

p = plain()
print(next(p))
try:
    p.throw(ValueError("boom"))
except ValueError as e:
    print("propagated:", repr(e))

def stop_on_error():
    try:
        yield 1
    except ValueError:
        return

f = stop_on_error()
print(next(f))
try:
    f.throw(ValueError("x"))
except StopIteration:
    print("throw() raised StopIteration")
```

```output
1
propagated: ValueError('boom')
1
throw() raised StopIteration
```

Both results match the table in the diagram above: the same error reaches the caller, or the caller sees `StopIteration`. The handler decides which.

Next, `close()` on a resource. The `finally` block is cleanup code that runs whenever the `try` block is left, including when `close()` is called.

```python
def resource(name):
    print(f"open {name}")
    try:
        while True:
            yield
    finally:
        print(f"cleanup {name}")

r = resource("A")
next(r)
print("close() returned", r.close())

r2 = resource("B")
print("close() before start returned", r2.close())
```

```output
open A
cleanup A
close() returned None
close() before start returned None
```

The `finally` block for `A` ran because the generator was paused inside the `try`.

For `B`, `close()` was called before the first `next()`, so the body never started and no `try` was entered. Nothing was printed.

Ending a `for` loop early has the same effect when no other reference to the generator remains. In the next example, `break` drops the loop's only reference, so CPython closes the generator and prints `cleanup` before `after loop`. This is the garbage-collection case discussed below, and it is CPython behaviour.

```python
def resource():
    print("open")
    try:
        for i in range(10):
            yield i
    finally:
        print("cleanup")

for x in resource():
    if x == 1:
        print("breaking")
        break
print("after loop")
```

```output
open
breaking
cleanup
after loop
```

The diagram below puts the three methods together as states. A generator is `created` until its first `next()` or `send(None)`, then it sits `suspended at yield` between calls, and it ends in `finished`.

![Three states: created, suspended at yield, and finished. next() or send(None) moves created to suspended; send(v) or a caught throw() loops back inside suspended; an uncaught throw(), a return, or close() moves to finished. A dashed arrow from created shows that send(10) before next() raises TypeError](diagrams/9.3-generator-states.svg "The states of a generator. Only the first move accepts a non-None send.")

Two behaviours come from the same rules, and I checked both by running them on CPython 3.12.13 (the reference implementation of Python). If a generator yields while handling `GeneratorExit`, `close()` raises `RuntimeError: generator ignored GeneratorExit`. When a suspended generator is garbage-collected (its last reference is deleted), Python calls `close()` for it. In CPython this happens at once, when the reference count drops to zero. Other implementations may run it later, so do not rely on the timing: close resources explicitly, with `try`/`finally` or a `with` block.

## Common traps

> [!TRAP]
> Calling `send(10)` on a new generator raises `TypeError`. Call `next()` once first, or pass `None`.

> [!TRAP]
> `send(v)` does not return an acknowledgement of `v`. It returns the next value the generator yields. In the averager, `send(10)` returns `10.0`, the average including the new sample.

> [!TRAP]
> If a handler catches the error from `throw()` and then yields, `throw()` returns that value. Ignoring the return value silently drops one item from the stream.

> [!TRAP]
> A `finally` block runs only if the generator had started. `close()` on an unstarted generator runs nothing (resource `B` above).

> [!TRAP]
> A generator that yields inside `GeneratorExit` handling makes `close()` raise `RuntimeError`. Clean up in the handler, and return instead of yielding.

## Summary

- The `yield` expression evaluates to the value passed to `send()`. `next()` passes `None`.
- Prime a generator with `next()` before the first `send()`. A non-`None` value sent to a just-started generator raises `TypeError`.
- `throw(e)` raises `e` at the paused `yield`. The handler decides whether `throw()` returns a value, raises `StopIteration`, or re-raises the error.
- `close()` raises `GeneratorExit` at the paused `yield`, which runs `finally` blocks. Yielding during `close()` raises `RuntimeError`.
- A generator dropped early is closed automatically in CPython, so cleanup can run sooner than you expect. Close resources explicitly when the timing matters.

## Quiz time

### Question 1: What does this print?

```python
def echo():
    x = yield 1
    print("got", x)
    yield 2

g = echo()
print(next(g))
print(g.send("a"))
```

<details><summary>Show Solution</summary>

The output is:

```
1
got a
2
```

`next(g)` runs to the first `yield` and returns `1`. `send("a")` makes `"a"` the value of `x`, prints `got a`, and then runs to the second `yield`, which returns `2`.

</details>

### Question 2: Calculation

A fresh `averager()` from this lesson is primed with `next()`. What do the next three `send()` calls return for the values `4`, `8` and `6`?

<details><summary>Show Solution</summary>

They return `4.0`, `6.0` and `6.0`. After `4` the average is $4/1 = 4.0$. After `8` it is $12/2 = 6.0$. After `6` it is $18/3 = 6.0$. The code in this lesson gives the same result: `[4.0, 6.0, 6.0]`.

</details>

### Question 3: Find and fix the bug

```python
def running_total():
    total = 0
    while True:
        delta = yield total
        total += delta

gen = running_total()
print(gen.send(5))
```

<details><summary>Show Solution</summary>

The generator has not been started, so the first `send()` must pass `None`. Passing `5` raises `TypeError: can't send non-None value to a just-started generator`. The fix is to prime it first:

```python
gen = running_total()
print(next(gen))     # 0: runs to the first yield
print(gen.send(5))   # 5
```

The output of the fixed version is `0` and then `5`.

</details>

### Question 4: Explain

You create a generator whose `finally` block prints `cleanup`. You call `close()` without calling `next()` first. Does `cleanup` print? Explain.

<details><summary>Show Solution</summary>

No. The body of the generator has not started, so the `try` block was never entered, and the `finally` clause belongs to that block. `close()` on an unstarted generator simply finishes it. Run the case to check:

```python
def resource():
    print("open")
    try:
        while True:
            yield
    finally:
        print("cleanup")

r = resource()
print("close() returned", r.close())
```

```
close() returned None
```

Neither `open` nor `cleanup` is printed.

</details>
