In this lesson you will use the `itertools` module to produce long or infinite sequences without building them in memory, count the tuples that combinatoric functions yield before you run them, and avoid the three traps that catch most readers: unbounded loops, eager input reading, and `groupby` on unsorted data.

**You need:** the iterator protocol (`iter()`, `next()`, `StopIteration`, Lesson 9.1) and generators (Lesson 9.2).

## The problem: a list must hold everything

A `list` is a finished result. Asking for every 2-tuple of ten items, or for "all odd numbers", means building every element before your code can use the first one. For ten items taken three at a time the result has 720 tuples, and an infinite sequence cannot be built at all. An iterator fixes both problems by producing one value per `next()` call. `itertools` is the standard library's collection of fast iterators for the common patterns.

## Infinite iterators: produce on demand, stop outside

Three functions never run out on their own: `count(start, step)`, `cycle(iterable)` and `repeat(obj, times)` (without `times`, `repeat` is also infinite). You bound them with `islice(iterator, stop)`, which takes the first `stop` values and then stops asking.

![Five values, 1, 3, 5, 7, 9, are pulled from count(1, 2); 11, 13 and 15 are drawn dashed because islice never asks for them](diagrams/9.4-lazy-pulls.svg "islice pulls five values from an infinite source. The rest are never computed.")

The diagram shows the mechanism. `islice` asks `count` for a value five times and then stops. Nothing past 9 is ever computed. `cycle` is different in one respect: it stores a copy of each value it has seen, so after the first pass it replays the copy and never asks the source again.

## Combinatoric iterators: count before you run

`product`, `permutations`, `combinations` and `combinations_with_replacement` yield tuples of a fixed length `r` from `n` items. Each has a closed-form count, which you can check before any loop runs:

| Function | Tuples yielded | Count for $n=10$, $r=3$ |
|---|---|---|
| `product(items, repeat=r)` | ordered, repeats allowed | $n^r = 1000$ |
| `permutations(items, r)` | ordered, no repeats | $n!/(n-r)! = 720$ |
| `combinations_with_replacement(items, r)` | unordered, repeats allowed | $\binom{n+r-1}{r} = 220$ |
| `combinations(items, r)` | unordered, no repeats | $\binom{n}{r} = 120$ |

![Bars for the four counts: product 1000, permutations 720, combinations with replacement 220, combinations 120, each with its formula underneath](diagrams/9.4-counts.svg "Tuples yielded for ten items and picks of three. The counts are measured and match the formulas.")

The formulas follow from counting (first-principles reasoning, not a quoted result). An ordered pick of $r$ items from $n$ fills $r$ slots with $n, n-1, \ldots$ choices, which gives $n!/(n-r)!$; allowing repeats gives $n^r$. Dropping the order divides each set of $r$ distinct items by its $r!$ orderings, which gives $\binom{n}{r}$. Allowing repeats in unordered picks gives $\binom{n+r-1}{r}$ (the "stars and bars" count).

The code below computes each count by running the iterator and compares it with the formula.

```python
import itertools
import math

n, r = 10, 3
items = range(n)
iterators = {
    "product(repeat=3)": itertools.product(items, repeat=r),
    "permutations": itertools.permutations(items, r),
    "combinations_with_replacement": itertools.combinations_with_replacement(items, r),
    "combinations": itertools.combinations(items, r),
}
expected = {
    "product(repeat=3)": n ** r,
    "permutations": math.perm(n, r),
    "combinations_with_replacement": math.comb(n + r - 1, r),
    "combinations": math.comb(n, r),
}
for name, it in iterators.items():
    count = sum(1 for _ in it)
    print(f"{name:32} {count:5}  expected {expected[name]}")

print(math.factorial(20))
```

```output
product(repeat=3)                 1000  expected 1000
permutations                       720  expected 720
combinations_with_replacement      220  expected 220
combinations                       120  expected 120
2432902008176640000
```

The last line is $20!$, the number of tuples in `permutations(range(20))`. The counts grow fast, so the real question is not how to store the result but whether to iterate it at all.

## Terminating iterators: finite outputs, combined

`accumulate` running-totals or reduces an input, `chain` joins several iterables end to end, `zip_longest` pads short inputs, and `groupby` merges runs of equal keys. `batched` (Python 3.12+) and `pairwise` (3.10+) are the newest members.

## Worked example by hand

Take `[1, 2, 3]` and pick two.

- **Combinations** keep only pairs whose first index is smaller than the second: (1,2), (1,3), (2,3). That is $\binom{3}{2} = 3$.
- **Permutations** keep order, so each pair appears twice, once in each order: (1,2), (1,3), (2,1), (2,3), (3,1), (3,2). That is $3 \cdot 2 = 6$.

For `groupby` on the string `AAABBCAA`, scan left to right and start a new group each time the key changes. The key changes three times (A to B, B to C, C to A), so there are four groups: (A, 3), (B, 2), (C, 1), (A, 2). Note the last A group: it is a second group, not a continuation of the first.

The code below checks the hand counts.

```python
import itertools

counter = itertools.count(1, 2)
print(list(itertools.islice(counter, 5)))

cyc = itertools.cycle("ab")
print(list(itertools.islice(cyc, 5)))

print(list(itertools.repeat("x", 3)))
print(list(itertools.combinations([1, 2, 3], 2)))
print(len(list(itertools.permutations([1, 2, 3], 2))))
```

```output
[1, 3, 5, 7, 9]
['a', 'b', 'a', 'b', 'a']
['x', 'x', 'x']
[(1, 2), (1, 3), (2, 3)]
6
```

## Watching the pulls: when does the source get read?

The fastest way to understand these iterators is to count what they ask their input for. The helper below passes values through and logs each one.

```python
import itertools

def counted(iterable, log):
    """Pass values through, recording each one the consumer pulls."""
    for x in iterable:
        log.append(x)
        yield x

log = []
print(list(itertools.islice(counted(itertools.count(1, 2), log), 5)), "source pulls:", len(log))

log = []
perms = itertools.permutations(counted(range(10), log), 3)
print("pulls before the first next():", len(log))
print("first tuple:", next(perms))

log = []
cyc = itertools.cycle(counted(range(3), log))
print([next(cyc) for _ in range(7)], "source pulls:", len(log))
```

```output
[1, 3, 5, 7, 9] source pulls: 5
pulls before the first next(): 10
first tuple: (0, 1, 2)
[0, 1, 2, 0, 1, 2, 0] source pulls: 3
```

Two results matter. First, `islice` pulled exactly five values and stopped. Second, `permutations` read all ten input values when it was *called*, before the first `next()`. The Python documentation says the same: `product` "completely consumes the input iterables", and the equivalent code for `permutations` and `combinations` starts with `pool = tuple(iterable)`. The output is lazy; the input is not.

![Ten input values are read at the call to permutations and held in a pool; each next() call then returns one tuple](diagrams/9.4-eager-input.svg "permutations reads its whole input when called. The tuples come out one at a time.")

Memory is therefore O(n) for the pool, not O(n^r) for the output. The measured peak memory for the 720 tuples, traced with the standard `tracemalloc` module, is 52,208 bytes when they are collected into a list and 248 bytes when they are streamed through a `for` loop (CPython 3.12.13; exact byte counts depend on the Python version). The code is in the run-locally block at the end of this section.

![Two bars to scale: list() of the 720 tuples takes 52,208 bytes; the streaming loop takes 248 bytes](diagrams/9.4-memory.svg "Peak traced memory for permutations(range(10), 3), measured on CPython 3.12.13.")

## Terminating iterators: combine and group

Each of these produces a finite result from finite inputs. The outputs below were produced by the code shown.

```python
import itertools
from operator import mul

print(list(itertools.accumulate([1, 2, 3], initial=100)))
print(list(itertools.accumulate([1, 2, 3, 4], mul)))
print(list(itertools.chain.from_iterable([[1, 2], [3], []])))
print(list(itertools.zip_longest("AB", "CDE")))
print(list(itertools.zip_longest("AB", "CDE", fillvalue="-")))
print(list(zip("AB", "CDE")))
```

```output
[100, 101, 103, 106]
[1, 2, 6, 24]
[1, 2, 3]
[('A', 'C'), ('B', 'D'), (None, 'E')]
[('A', 'C'), ('B', 'D'), ('-', 'E')]
[('A', 'C'), ('B', 'D')]
```

`zip` stops at the shorter input and drops the extra value; `zip_longest` keeps going to the longest and fills gaps with `fillvalue`. The `initial` argument of `accumulate` has been available since Python 3.8. `chain.from_iterable` takes one iterable of iterables, so you do not have to unpack the list of lists into arguments with `*`.

`groupby` is the function most often used wrongly. It merges only neighbouring equal keys, and the sorted-input rule is stated in the Python documentation.

```python
import itertools

s = "AAABBCAA"
print([(k, len(list(g))) for k, g in itertools.groupby(s)])
print([(k, len(list(g))) for k, g in itertools.groupby(sorted(s))])

words = ["apple", "banana", "avocado"]
for letter, group in itertools.groupby(words, key=lambda w: w[0]):
    print(letter, list(group))
print("--- fixed ---")
for letter, group in itertools.groupby(sorted(words, key=lambda w: w[0]), key=lambda w: w[0]):
    print(letter, list(group))
```

```output
[('A', 3), ('B', 2), ('C', 1), ('A', 2)]
[('A', 5), ('B', 2), ('C', 1)]
a ['apple']
b ['banana']
a ['avocado']
--- fixed ---
a ['apple', 'avocado']
b ['banana']
```

![Unsorted AAABBCAA gives four groups with A appearing twice; sorted AAAAABBC gives three groups](diagrams/9.4-groupby.svg "groupby merges only neighbouring equal keys. Sort first to group by value.")

The Python documentation states that the iterable "needs to already be sorted on the same key function", and that a group is no longer visible once the `groupby` object advances. If you need a group later, store it as a list.

import tracemalloc

def peak(fn):
    tracemalloc.start()
    fn()
    _, pk = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return pk

def as_list():
    return list(itertools.permutations(range(10), 3))

def stream():
    total = 0
    for t in itertools.permutations(range(10), 3):
        total += t[0]
    return total

print("list:", peak(as_list), "bytes; streaming loop:", peak(stream), "bytes")

## Common traps

> [!TRAP]
> `list(itertools.count())` never returns. Bound every infinite iterator with `islice`, or with `zip` against a finite iterable.

> [!TRAP]
> An iterator is one-shot. `chain` and the others keep a position, not a copy, so `list(it)` followed by `list(it)` gives `[1, 2]` and then `[]`. Create a new iterator for each pass.

> [!TRAP]
> `groupby` groups only adjacent equal keys. Sort by the same key first, or use `collections.Counter` if you only need totals.

> [!TRAP]
> `product`, `permutations` and `combinations` read their input when called. A generator with side effects runs to completion at that point, and a large input is held in memory.

> [!TRAP]
> `cycle` keeps a copy of every item it has seen, so its memory grows with the length of the input, not with the number of loops. The documentation warns that it "may require significant auxiliary storage".

## Summary

- `count`, `cycle` and `repeat` are infinite; `islice` bounds them and stops pulling from the source.
- Combinatoric functions have closed-form counts: $n^r$, $n!/(n-r)!$, $\binom{n+r-1}{r}$ and $\binom{n}{r}$. For $n=10$, $r=3$ these are 1000, 720, 220 and 120.
- Their output is lazy, but their input is read in full at the call, so memory is O(n) for the pool, not for the output.
- `groupby` merges only adjacent equal keys; sort by the key first.
- Iterators are one-shot: create a new one for each pass.

### Question 1: How many tuples?

How many tuples do `combinations(range(6), 2)` and `permutations(range(6), 2)` yield?

<details><summary>Show Solution</summary>

Combinations yield 15 and permutations yield 30.

$\binom{6}{2} = 15$ unordered pairs. Each pair appears twice in permutations, once in each order, so $6 \cdot 5 = 30$.

```output

```

### Question 3: Find the bug

This code is meant to print each first letter once, with its words. What is wrong, and how do you fix it?

```python
import itertools
words = ["apple", "banana", "avocado"]
for letter, group in itertools.groupby(words, key=lambda w: w[0]):
    print(letter, list(group))
```

<details><summary>Show Solution</summary>

The output is `a ['apple']`, `b ['banana']`, `a ['avocado']`: the letter `a` appears twice. `groupby` merges only adjacent equal keys, and `avocado` is not adjacent to `apple`. Sort by the same key first:

```python
import itertools
words = ["apple", "banana", "avocado"]
for letter, group in itertools.groupby(sorted(words, key=lambda w: w[0]), key=lambda w: w[0]):
    print(letter, list(group))
```

```output
a ['apple', 'avocado']
b ['banana']
```

</details>

### Question 4: Explain the second empty list

Why does the second `list(it)` print `[]`?

```python
import itertools
it = itertools.chain([1], [2])
print(list(it), list(it))
```

<details><summary>Show Solution</summary>

The first `list(it)` consumes every value, and `it` keeps its position. The second call starts from the end and gets nothing. The output is `[1, 2] []`. An iterator holds a position, not a copy of the data, so you need a new iterator for each pass.

</details>
