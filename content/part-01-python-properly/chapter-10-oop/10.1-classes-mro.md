In this lesson you will define a class, say where Python keeps an instance's attributes, and decide when `__slots__` (a class declaration that fixes the attribute names) is worth its restrictions.

**You need:** dictionaries and their hash-table behaviour (Lesson 6.2).

## The problem: one object per record

A simulation holds one million particles, each with a position and a velocity. If every particle is an instance of a class, each instance pays a fixed memory cost on top of its data, and that cost is multiplied by the number of objects. At 48 bytes of overhead per particle, one million particles carry 48 MB of bookkeeping before a single coordinate is stored; at 96 bytes, the figure is 96 MB. This lesson asks where an instance keeps its attributes, and what that choice costs.

## Classes and instances

A **class** is a blueprint: it holds methods, and class attributes that all instances share. An **instance** is one object made from the blueprint, with its own attributes. When you call `p.introduce()`, Python finds the function on the class and passes the instance in as `self`; the instance itself stores only its data. Here are two classes that differ in one line. The first declares `__slots__`; the second does not.

```python
class Person:
    __slots__ = ["name", "age"]

    def __init__(self, name, age):
        self.name = name
        self.age = age

class DynamicPerson:
    def __init__(self, name, age):
        self.name = name
        self.age = age

p = Person("Alice", 30)
d = DynamicPerson("Bob", 25)

print("p has __dict__:", hasattr(p, "__dict__"))
print("d has __dict__:", hasattr(d, "__dict__"))
print("vars(d):", vars(d))
print("hasattr(p, '__slots__'):", hasattr(p, "__slots__"))
print("Person.__dict__['name']:", type(Person.__dict__["name"]).__name__)

try:
    p.adress = "123 Main St"        # typo for "address"
except AttributeError as e:
    print("slotted:", e)

d.adress = "123 Main St"            # the same typo: no error
print("dict instance now has:", sorted(vars(d)))
```

```output
p has __dict__: False
d has __dict__: True
vars(d): {'name': 'Bob', 'age': 25}
hasattr(p, '__slots__'): True
Person.__dict__['name']: member_descriptor
slotted: 'Person' object has no attribute 'adress'
dict instance now has: ['adress', 'age', 'name']
```

Two details in that output matter. `hasattr(p, '__slots__')` is `True` because the lookup finds the class attribute, so it does not tell you whether an instance has a dictionary. Test `'__dict__'` instead.

## Where a plain instance keeps its attributes

By default, an instance stores its attributes in a dictionary attached to the object and reached through `__dict__`. The Python Language Reference describes `object.__dict__` as the mapping "used to store an object's (writable) attributes" and notes that not every instance has one (Python Software Foundation, Language Reference, §3.2.11.1 and §3.3.2.4).

![A plain instance points through __dict__ to a separate dictionary holding name and age; a slotted instance is one object whose header is followed by fixed name and age cells](diagrams/10.1-layout.svg "Two layouts: a separate dict versus fixed cells in the object.")

The left side of the figure is why a plain instance costs more: the attribute table is a second object. CPython also shares the key names among instances of one class and stores only the values per instance (PEP 412, Key-Sharing Dictionary), so the dictionary cost is mainly its values and table, not repeated names. The right side is what `__slots__` changes. Python creates one descriptor per name on the class, and the value lives in a fixed cell of the instance itself (Python Software Foundation, Language Reference, §3.3.2.4).

## What `__slots__` takes away

Because the instance has no dictionary, it cannot grow new attributes. The typo above fails at the moment of assignment, which is the feature: a misspelled name is caught early. A plain instance accepts the same typo silently, and the bug appears later, when code reads `d.address` and finds nothing.

![Two rows: a typo on a slotted instance raises AttributeError immediately; the same typo on a dict instance is stored without error](diagrams/10.1-typo.svg "The same misspelled assignment in both classes.")

Slots are also not inherited as a cage. A subclass that declares no `__slots__` gets a `__dict__` back, so the saving disappears unless every class in the hierarchy declares slots. I checked this with a `Sub` class that inherits from `Person` and declares nothing: `hasattr(s, '__dict__')` is `True`, and `s.extra = 1` succeeds.

![Sub instance: two inherited slot cells for name and age, plus a new __dict__ cell that holds an extra attribute](diagrams/10.1-subclass.svg "A subclass without __slots__ adds a __dict__.")

The Language Reference states this rule directly: instances of a child subclass "will get a `__dict__` and `__weakref__` unless the subclass also defines `__slots__`" (Python Software Foundation, Language Reference, §3.3.2.4).

## Measuring the memory cost

The reason to use slots is memory. The method below creates 100,000 instances of a class with 2, 4 or 8 attributes, and measures the bytes allocated with `tracemalloc`, the standard-library allocation tracker. Every attribute holds the same shared integer, so the measurement counts only the containers. The numbers come from CPython 3.12.13 on macOS; other builds will differ in the absolute values, though the pattern should hold.

<details><summary>Run locally (CPython, no installs): measures bytes per instance</summary>

```python
import gc, tracemalloc

N = 100_000

def make(names, slots):
    src = "def __init__(self, " + ", ".join(names) + "):\n" + "".join(f"    self.{n} = {n}\n" for n in names)
    ns = {}
    exec(src, ns)
    attrs = {"__init__": ns["__init__"]}
    if slots:
        attrs["__slots__"] = names
    return type("Slotted" if slots else "Plain", (), attrs)

def bytes_per_instance(cls, nargs):
    gc.collect()
    tracemalloc.start()
    objs = [None] * N               # baseline: the list that holds the instances
    base, _ = tracemalloc.get_traced_memory()
    args = [7] * nargs              # one shared int, so only containers are measured
    for i in range(N):
        objs[i] = cls(*args)
    cur, _ = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return (cur - base) / N

for k in (2, 4, 8):
    names = [f"f{i}" for i in range(k)]
    plain = bytes_per_instance(make(names, slots=False), k)
    slotted = bytes_per_instance(make(names, slots=True), k)
    print(f"{k} attributes: __dict__ {plain:.0f} B, __slots__ {slotted:.0f} B")
```

```output
2 attributes: __dict__ 80 B, __slots__ 48 B
4 attributes: __dict__ 96 B, __slots__ 64 B
8 attributes: __dict__ 136 B, __slots__ 96 B
```

</details>

![Grouped bars: a plain instance uses 80, 96 and 136 bytes for 2, 4 and 8 attributes; a slotted instance uses 48, 64 and 96 bytes](diagrams/10.1-size-chart.svg "Bytes per instance, measured on CPython 3.12.")

**Worked example, by hand.** Start with the slotted column, which has a closed form. Assume a 64-bit CPython build with a 16-byte garbage-collector header, a 16-byte object header (reference count and type pointer), and one 8-byte pointer per slot. Then a two-slot instance is 16 + 16 + 2 × 8 = 48 bytes, a four-slot instance is 16 + 16 + 4 × 8 = 64 bytes, and an eight-slot instance is 16 + 16 + 8 × 8 = 96 bytes. The three slotted numbers in the output match. This accounting is my own reasoning that fits the measurements; I did not measure the header sizes directly. The dictionary column has no such closed form in this lesson, and the plain instances grow less regularly (80, 96, 136), which I did not trace to the allocator.

Do not use `sys.getsizeof` for this comparison. It reports the size of the object itself, not of what the object refers to. In this run it returned 48 bytes for both the plain and the slotted two-attribute instance, which hides the dictionary entirely.

Speed is the second claim often made for slots. The Language Reference says slots can "significantly" improve attribute lookup speed. I did not reproduce a gap. Over three runs, reads took 8.3 to 10.1 ns and writes 8.8 to 9.5 ns for both classes, and which class was faster changed from run to run. These timings depend on the machine and build, and a single run can flip the order, so measure on your own, with repeats, before you rely on them.

## When slots are worth it

Use `__slots__` when you will create many instances of one shape, you know the attribute names in advance, and you do not need weak references or ad hoc attributes. The saving scales with the number of objects: at the measured 32 bytes per two-attribute instance, 1,000 objects save 32 KB, and 1,000,000 objects save about 32 MB. For a handful of configuration objects, the restriction costs more than the bytes save. If you cannot name the attributes before the first instance exists, slots are the wrong tool. Measure your own object count before you decide.

## Common traps

> [!TRAP]
> A subclass without `__slots__` gets a `__dict__` again. Declare `__slots__` in every class in the hierarchy, or accept the dictionary cost.

> [!TRAP]
> A class attribute with the same name as a slot is rejected when the class is defined. With `__slots__ = ['x']` and a class-level `x = 1`, Python raises `ValueError: 'x' in __slots__ conflicts with class variable`. Set defaults in `__init__` instead.

> [!TRAP]
> Slotted instances cannot be weakly referenced unless `'__weakref__'` is listed in `__slots__`. Without it, `weakref.ref(p)` raises `TypeError: cannot create weak reference to 'Person' object`.

> [!TRAP]
> A mutable class attribute is one object shared by every instance. In `class Shared: items = []`, `a.items.append(1)` also changes `b.items`, because both read the same list.

> [!TRAP]
> `sys.getsizeof` on an instance does not count its attribute storage. Measure with `tracemalloc`, as above, when comparing layouts.

## Summary

- A plain instance keeps its attributes in a separate `__dict__`; a slotted instance keeps them in fixed cells inside the object.
- `__slots__` makes a misspelled attribute name fail at assignment, and it removes the per-instance dictionary.
- On CPython 3.12 the measured saving was 32 to 40 bytes per instance for 2 to 8 attributes, with 100,000 instances.
- Slots are lost in subclasses that declare no `__slots__`, and the speed gain the docs mention did not appear in my runs.

## Quiz time

### Question 1: Predict the outcome

```python
class Point:
    __slots__ = ["x", "y"]

    def __init__(self, x, y):
        self.x = x
        self.y = y

pt = Point(1, 2)
pt.z = 3
print("reached the print")
```

<details><summary>Show Solution</summary>

The program stops with `AttributeError: 'Point' object has no attribute 'z'`. The assignment `pt.z = 3` fails because `z` is not in `__slots__` and the instance has no `__dict__`, so `print` never runs and nothing is printed.

</details>

### Question 2: Find the bug

```python
class Counter:
    __slots__ = ["count"]
    count = 0

    def increment(self):
        self.count += 1
```

<details><summary>Show Solution</summary>

The class body is rejected when Python creates it, with `ValueError: 'count' in __slots__ conflicts with class variable`. The class attribute `count = 0` would overwrite the descriptor that `__slots__` creates for `count`. Remove the class attribute and set the default in `__init__`:

```python
class Counter:
    __slots__ = ["count"]

    def __init__(self):
        self.count = 0

    def increment(self):
        self.count += 1
```

</details>

### Question 3: Estimate the memory

A simulation holds 1,000,000 instances of a class with 4 attributes. Using the measured container costs above (96 bytes with `__dict__`, 64 bytes with `__slots__`), estimate the total container memory each way and the saving. Say what the estimate leaves out.

<details><summary>Show Solution</summary>

With `__dict__`: 1,000,000 × 96 B = 96,000,000 B, about 96 MB. With `__slots__`: 1,000,000 × 64 B = 64,000,000 B, about 64 MB. The saving is about 32 MB. The estimate leaves out the attribute values themselves (here they were one shared integer, but real particles hold distinct floats, which cost memory of their own) and any list that holds the instances.

</details>

### Question 4: Explain the subclass result

Why does a subclass with no `__slots__` of its own reintroduce a `__dict__`, even when its parent declares slots?

<details><summary>Show Solution</summary>

A class that declares no `__slots__` does not restrict its instances, so Python gives those instances a `__dict__` and a `__weakref__` slot. The subclass's own attributes go into that dictionary, which is what the `Sub` check in the section above showed (`hasattr(s, '__dict__')` is `True`). To keep the savings, the subclass must declare `__slots__` listing only its new names.

</details>
