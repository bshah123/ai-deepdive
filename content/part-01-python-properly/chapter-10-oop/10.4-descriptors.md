In this lesson you will write a **descriptor**, an object that controls what happens when an attribute is read, assigned or deleted, and you will predict which of two values `obj.attr` returns when both could apply. You will also see why Python's built-in `property` is just a descriptor, and why the storage has to live on the instance, not on the descriptor.

**You need:** classes and each instance's `__dict__` (Lesson 10.1), and the method resolution order (MRO) that Python searches for attributes (Lesson 10.2).

## The problem a descriptor solves

Suppose an `Account` must never hold a negative balance. A plain attribute cannot enforce that: `acct.balance = -5` simply stores -5. You could add a method `set_balance()` and hope every caller uses it, or you could make the assignment itself check the value. Descriptors do the second: the class attribute `balance` becomes an object that intercepts every read, write and delete of `acct.balance`.

Python maps each statement to one method. `obj.attr` calls `__get__`, `obj.attr = value` calls `__set__`, and `del obj.attr` calls `__delete__`. Those three methods are the only hooks you need, and each receives the instance, so it can act on that object's own data.

## Intuition: two places, one answers

A descriptor is stored on the class. The value is stored on the instance. When you write `acct.balance`, Python looks at the class first.

![A class holds a Positive descriptor under the name balance; the instance holds the value in its own dict. The read goes to the descriptor on the class first, and the instance dict is skipped.](diagrams/10.4-where.svg "The descriptor answers for the attribute; the instance dict only stores the value.")

If the object found on the class defines `__set__` or `__delete__`, it is a **data descriptor**, and it takes over reads too. If it defines only `__get__`, it is a **non-data descriptor**. The Python documentation states this split directly: a descriptor that defines `__set__()` or `__delete__()` is a data descriptor, and one that only defines `__get__()` is a non-data descriptor ([Python docs, Descriptor HowTo Guide](https://docs.python.org/3/howto/descriptor.html)).

## Worked example, by hand

Trace `acct.balance = -5`, where `acct` already holds 10:

1. Python looks up `balance` on `type(acct)`. It finds a `Positive` object, and that object defines `__set__`. So it is a data descriptor, and Python calls its `__set__` instead of writing to `acct.__dict__`.
2. `__set__(acct, -5)` runs. The check `value < 0` is true, so it raises `ValueError`.
3. The line that writes `obj.__dict__[self.name] = value` is never reached. The dict still holds `{'balance': 10}`.

The same check guards construction. `Account.__init__` assigns `self.balance = balance`, which goes through `__set__`, so `Account(-1)` raises `ValueError` before any caller can use a bad object. Enforcing the rule in the descriptor means every assignment is checked, in every method, without repeating the check at each call site.

![Three steps for acct.balance = -5: find the data descriptor on the type, call __set__ with -5, raise ValueError. Below, the instance dict is 10 before and after, and reading acct.balance still gives 10.](diagrams/10.4-trace.svg "Worked trace of a rejected assignment, with the numbers the code printed.")

## The code

Here is the full descriptor. `Account` uses it for `balance`:

```python
class Positive:
    """A data descriptor: an int that must be >= 0."""

    def __set_name__(self, owner, name):
        self.name = name                       # called once, when the class is created

    def __get__(self, obj, objtype=None):
        if obj is None:                        # Account.balance: return the descriptor itself
            return self
        try:
            return obj.__dict__[self.name]
        except KeyError:
            raise AttributeError(self.name) from None

    def __set__(self, obj, value):
        if not isinstance(value, int):
            raise TypeError(f"{self.name} must be an int")
        if value < 0:
            raise ValueError(f"{self.name} must be >= 0")
        obj.__dict__[self.name] = value

    def __delete__(self, obj):
        del obj.__dict__[self.name]


class Account:
    balance = Positive()

    def __init__(self, balance):
        self.balance = balance                 # goes through Positive.__set__


acct = Account(10)
print("balance:", acct.balance)
print("type(acct).__dict__ holds:", type(Account.__dict__["balance"]).__name__)
print("acct.__dict__ holds the value:", acct.__dict__)
try:
    acct.balance = -5
except ValueError as e:
    print("ValueError:", e)
print("after the failed set:", acct.__dict__)
del acct.balance
print("getattr after delete:", getattr(acct, "balance", "missing"))
```

```output
balance: 10
type(acct).__dict__ holds: Positive
acct.__dict__ holds the value: {'balance': 10}
ValueError: balance must be >= 0
after the failed set: {'balance': 10}
getattr after delete: missing
```

Three details matter:

- `__get__` receives `obj=None` when the attribute is read on the class (`Account.balance`). Returning `self` lets you inspect the descriptor itself.
- `__get__` raises `AttributeError` for an unset value. That is what lets `hasattr()` and `getattr(obj, name, default)` behave as they do for a plain attribute.
- `__delete__` is the only method that handles `del`. It removes the key from the dict, so a later read raises `AttributeError`. That is why the last line of the output prints `missing`.
- `__set_name__` (added by PEP 487, Python 3.6) is called by `type.__new__` when the class body is executed, and it receives the attribute name. You no longer repeat the string `'balance'`, so the name cannot drift out of sync with the attribute ([PEP 487](https://peps.python.org/pep-0487/)).

`property` is the same mechanism with the functions written for you. The Descriptor HowTo says that calling `property()` builds a data descriptor that runs a function on access ([Descriptor HowTo](https://docs.python.org/3/howto/descriptor.html)). A property without a setter still defines `__set__`, which raises `AttributeError`, so it stays a data descriptor.

## Under the hood: who wins

When the instance dict also has an entry with the same name, the kind of descriptor decides the result. For a read, `obj.attr` is resolved in this order, as the Descriptor HowTo states it ([Descriptor HowTo](https://docs.python.org/3/howto/descriptor.html)):

1. If the class, or any base class found through the MRO (Lesson 10.2), has a data descriptor for `attr`, call its `__get__`.
2. Otherwise, if `obj.__dict__` has `attr`, return that value.
3. Otherwise, if the class has a non-data descriptor, call its `__get__`. Functions are non-data descriptors, and that is how a method becomes a bound method.
4. Otherwise, if the class has a plain attribute, return it.
5. Otherwise, call `__getattr__` if the class defines it, or raise `AttributeError`.

Assignment and deletion use only step 1. If a data descriptor is on the class, its `__set__` or `__delete__` runs. Otherwise Python writes to, or removes from, the instance dict.

```python
class DataDescriptor:
    def __get__(self, obj, objtype=None):
        return "descriptor"
    def __set__(self, obj, value):
        pass

class NonDataDescriptor:
    def __get__(self, obj, objtype=None):
        return "descriptor"

class Demo:
    data = DataDescriptor()
    nondata = NonDataDescriptor()
    plain = "class"

o = Demo()
o.__dict__.update(data="instance", nondata="instance", plain="instance")
print("data:    ", o.data)
print("nondata: ", o.nondata)
print("plain:   ", o.plain)
```

```output
data:     descriptor
nondata:  instance
plain:    instance
```

![A table: a data descriptor is listed first and its result is descriptor, while a non-data descriptor and a plain class attribute both return instance when the instance dict has the same name.](diagrams/10.4-precedence.svg "Which value obj.attr returns when the instance dict also has attr.")

This is why a `__get__`-only descriptor cannot make an attribute read-only. Assigning `o.nondata = 5` writes into the instance dict, and from then on the instance value shadows the descriptor.

## The storage trap: per-instance state belongs on the instance

Descriptor objects are shared by every instance of the class. If you store the value on the descriptor, every instance shares it:

```python
class BadStore:
    def __init__(self):
        self.value = None                      # one slot for the whole class
    def __get__(self, obj, objtype=None):
        return self.value
    def __set__(self, obj, value):
        self.value = value

class Good:
    def __set_name__(self, owner, name):
        self.name = name
    def __get__(self, obj, objtype=None):
        return obj.__dict__[self.name]
    def __set__(self, obj, value):
        obj.__dict__[self.name] = value

class Shared:
    x = BadStore()

class Separate:
    x = Good()

a, b = Shared(), Shared()
a.x, b.x = 1, 2
print("bad:  a.x, b.x =", a.x, b.x)

c, d = Separate(), Separate()
c.x, d.x = 1, 2
print("good: c.x, d.x =", c.x, d.x)
```

```output
bad:  a.x, b.x = 2 2
good: c.x, d.x = 1 2
```

The bad version lost the value of `a` the moment `b` was written. The fix is the one the lesson's `Positive` uses: keep the value in `obj.__dict__`, keyed by the attribute name. Each `__set__` call receives the instance it is writing to, so the value lands on that instance alone.

## What it costs

Each access to a descriptor runs a Python function, and in `Positive` that function also does a dict lookup and, on writes, two checks. A plain attribute read is a single dict-like lookup done in C. So a descriptor is slower than a plain attribute, which is the price of intercepting the access (this explanation is my own reasoning, not a measured breakdown). The timings below come from one run on a Mac with Python 3.12.13. Each figure is the minimum of five runs of one million accesses. Your numbers will differ, but the ratios show the pattern. A plain read took 8.6 ns, a `property` read 24.8 ns, and a data descriptor read 71.4 ns. That is about 8.3 times a plain read and about 2.9 times a property read. Writes followed the same pattern: 9.0 ns plain and 86.4 ns through the descriptor.

![Horizontal bars of nanoseconds per access: plain read 8.6, property read 24.8, data descriptor read 71.4, plain write 9.0, data descriptor write 86.4.](diagrams/10.4-timing.svg "Measured cost per access. Use descriptors for enforcement, not for hot inner loops.")

## Common traps

> [!TRAP]
> **Storing values on the descriptor.** As the `BadStore` example shows, one descriptor serves every instance. Store per-instance values in `obj.__dict__`.

> [!TRAP]
> **Calling `getattr(obj, self.name)` inside `__get__`.** That call goes through the same descriptor again, and Python recurses until it raises `RecursionError`. Read `obj.__dict__[self.name]` instead. (I checked this with a minimal class; it is not in the lesson's main code.)

> [!TRAP]
> **Raising `KeyError` for an unset value.** `getattr(obj, name, default)` returns the default only when `AttributeError` is raised. When I raised `KeyError` in a test, it escaped `getattr` with a default. Raise `AttributeError` instead.

> [!TRAP]
> **Expecting a `__get__`-only descriptor to block assignment.** It does not: assignment writes to the instance dict and shadows the descriptor (see the precedence section).

> [!TRAP]
> **Trusting one timing run.** The table of costs changes with the machine and the Python build. Compare ratios, and measure before you optimise.

## Summary

- A descriptor is an object on the class that defines `__get__`, `__set__` or `__delete__`. Defining `__set__` or `__delete__` makes it a data descriptor.
- A data descriptor on the class takes precedence over the instance dict. A non-data descriptor or a plain class value does not.
- Keep per-instance values in `obj.__dict__`, keyed by the name that `__set_name__` gives you.
- `property` is a built-in data descriptor. Custom descriptors cost a Python call per access.

## Quiz time

### Question 1: Prediction

A class has a non-data descriptor `d` (defines `__get__` only). Then `o = Demo(); o.d = 5; print(o.d)`. What is printed?

<details><summary>Show Solution</summary>

`5`. The descriptor has no `__set__`, so the assignment writes `5` into `o.__dict__`. On lookup, the instance dict beats a non-data descriptor, so `o.d` returns 5, not the descriptor's result.

</details>

### Question 2: Find the bug

```python
class Limit:
    def __init__(self):
        self.max = 100
    def __get__(self, obj, objtype=None):
        return self.max
    def __set__(self, obj, value):
        self.max = value

class Quota:
    cap = Limit()

q1, q2 = Quota(), Quota()
q1.cap = 10
print(q2.cap)
```

<details><summary>Show Solution</summary>

It prints `10`, not `100`. `cap` is stored on the single `Limit` object, which lives on the class, so every `Quota` instance shares it. Fix it by storing the value in `obj.__dict__[self.name]`, as in `Good` above.

</details>

### Question 3: Explain

Why does `property()` define `__set__` even when you give it no setter?

<details><summary>Show Solution</summary>

Because a descriptor is a data descriptor only if it defines `__set__` or `__delete__`. Without `__set__`, an instance dict entry with the same name would shadow the property. The HowTo's pure-Python emulation defines `__set__` and `__delete__` unconditionally and raises `AttributeError` when there is no setter or deleter. The class therefore keeps priority over the instance dict.

</details>

### Question 4: Calculation

Using `Account` from the code above, `acct = Account(25)` and then `acct.balance -= 30`. What is `acct.balance` afterwards, and which exception does the statement raise?

<details><summary>Show Solution</summary>

`-=` reads the balance (25), computes `25 - 30 = -5`, and assigns it. `__set__` rejects -5 with `ValueError: balance must be >= 0`. The dict is unchanged, so `acct.balance` is still `25`.

</details>
