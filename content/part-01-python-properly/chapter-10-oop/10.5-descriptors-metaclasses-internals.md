By the end you will be able to predict which of several same-named attributes Python returns, explain why an instance attribute cannot shadow a property, and write a metaclass that runs when a class is created.

**You need:** the instance `__dict__` (Lesson 10.1) and the property descriptor from Lesson 10.4, meaning a class with `__get__` and `__set__` methods.

## The problem: one name, several possible sources

Suppose `obj.x` could come from a class attribute, from the instance's own `__dict__`, from a descriptor on the class, or from a `__getattr__` method. If two of these exist at once, Python must choose one. The choice is not made by which one you wrote last, and it is not always the instance. This lesson gives the exact rule, then the metaclass machinery that runs one level up, when the class itself is created.

## Intuition: a funnel of five checks

![Flowchart of obj.x: Python checks, in order, for a data descriptor on the class, a key in the instance dict, a non-data descriptor, a plain class attribute, and a __getattr__ method, and raises AttributeError only when all five fail](diagrams/10.5-lookup-funnel.svg "The lookup order. Each yes exits the funnel; the first match wins.")

Two kinds of descriptor matter. A **descriptor** is an object stored as a class attribute whose class defines `__get__`, `__set__` or `__delete__`. A **data descriptor** defines `__set__` or `__delete__`. A **non-data descriptor** defines only `__get__`. Functions are non-data descriptors, which is why `obj.method` returns a bound method.

The Python Descriptor HowTo states the rule as: "Data descriptors always override instance dictionaries", and "Non-data descriptors may be overridden by instance dictionaries". The five-step order in the funnel is the documented emulation of `object.__getattribute__`, and `__getattr__` is only a fallback after it fails.

## Worked example, by hand

Build a class with three kinds of name: `dd` (a data descriptor), `nd` (a non-data descriptor), and `plain` (a class attribute). Then ask what `obj.nd` returns in two cases.

1. No instance entry. Step 1 finds `NonDataDesc` for `nd`. It has no `__set__`, so it is not a data descriptor and the search continues. Step 2 finds no `nd` key in `obj.__dict__`. Step 3 applies: the descriptor has `__get__`, so the result is `"non-data descriptor"`.
2. With `obj.__dict__['nd'] = "instance dict"`. Step 1 is again skipped. Step 2 now finds the key, so the result is `"instance dict"`. The descriptor is never called.

The table below was produced by running that exact setup, not by reasoning alone.

![Matrix of four names by two cases, showing which source answers: a data descriptor always wins; a non-data descriptor, a class attribute or the fallback each lose to an instance dict entry](diagrams/10.5-precedence-matrix.svg "Who answers obj.x. Measured on CPython 3.12.13; the code below reproduces it.")

The code implements the documented order in a few lines and checks it against the real `getattr` in all eight cases:

```python
class DataDesc:
    """Data descriptor: defines __get__ and __set__."""
    def __get__(self, obj, owner=None):
        if obj is None:
            return self
        return "data descriptor"

    def __set__(self, obj, value):
        pass  # value is not stored; reads always go through __get__


class NonDataDesc:
    """Non-data descriptor: defines __get__ only."""
    def __get__(self, obj, owner=None):
        if obj is None:
            return self
        return "non-data descriptor"


class Demo:
    dd = DataDesc()
    nd = NonDataDesc()
    plain = "class attribute"

    def __getattr__(self, name):
        return "__getattr__ fallback"


def reference_lookup(obj, name):
    """Pure-Python model of the documented order."""
    cls = type(obj)
    attr = None
    for klass in cls.__mro__:
        if name in klass.__dict__:
            attr = klass.__dict__[name]
            break
    if attr is not None and (hasattr(type(attr), "__set__") or hasattr(type(attr), "__delete__")):
        return attr.__get__(obj, cls)          # 1. data descriptor
    if name in obj.__dict__:
        return obj.__dict__[name]              # 2. instance dict
    if attr is not None:
        if hasattr(type(attr), "__get__"):
            return attr.__get__(obj, cls)      # 3. non-data descriptor
        return attr                            # 4. class attribute
    if hasattr(cls, "__getattr__"):
        return cls.__getattr__(obj, name)      # 5. fallback
    raise AttributeError(name)


names = ["dd", "nd", "plain", "absent"]
for in_dict in (False, True):
    for n in names:
        obj = Demo()
        if in_dict:
            obj.__dict__[n] = "instance dict"  # write __dict__ directly, bypassing __set__
        real = getattr(obj, n)
        model = reference_lookup(obj, n)
        print(f"{n:7} in __dict__={in_dict!s:5}  ->  {real:24} model agrees: {real == model}")
```

```output
dd      in __dict__=False  ->  data descriptor          model agrees: True
nd      in __dict__=False  ->  non-data descriptor      model agrees: True
plain   in __dict__=False  ->  class attribute          model agrees: True
absent  in __dict__=False  ->  __getattr__ fallback     model agrees: True
dd      in __dict__=True   ->  data descriptor          model agrees: True
nd      in __dict__=True   ->  instance dict            model agrees: True
plain   in __dict__=True   ->  instance dict            model agrees: True
absent  in __dict__=True   ->  instance dict            model agrees: True
```

Read the `dd` row with an instance entry: the instance dict holds `"instance dict"`, but the result is `"data descriptor"`. This is why a property cannot be shadowed by writing to `__dict__`. A `property` defines `__set__`, so it is a data descriptor (Python Descriptor HowTo, which describes `property` as a descriptor).

## Under the hood

The model above follows the documented order. The Descriptor HowTo presents it as an emulation of `object.__getattribute__` for ordinary instances and `type.__getattribute__` for classes. I did not read the CPython C source, so the claim that the C code matches it rests on the documentation and on the tests above. Three details matter in practice.

First, `__getattr__` is not part of `__getattribute__`. The Python data model says it is called when "the default attribute access fails with an `AttributeError`", which happens in two ways: `__getattribute__` raises `AttributeError`, or the `__get__` of a property raises `AttributeError` (Python Data Model, §Customizing attribute access). The second case is a trap, shown below.

Second, class-level access `A.x` calls `desc.__get__(None, A)` on a descriptor found on the class. The instance dict is not searched at all, because there is no instance.

Third, a descriptor can store its value per instance only if it puts that value somewhere keyed by the instance. The descriptor object itself is shared by every instance of the class, as the next example shows.

## Common traps

> [!TRAP]
> An instance attribute does not override a property. Writing `obj.__dict__['v'] = 99` leaves `obj.v` unchanged, because a data descriptor is checked first (the `dd` row above). Writing through `obj.v = 99` calls `__set__` instead.

> [!TRAP]
> A property getter that raises `AttributeError` triggers `__getattr__`, which hides the real error. The output below shows the fallback replacing the message; the original message is lost at that point.

```python
class Masked:
    @property
    def value(self):
        raise AttributeError("real bug: self._missing was never set")

    def __getattr__(self, name):
        return f"fallback for {name}"


print(Masked().value)
```

```output
fallback for value
```

> [!TRAP]
> A descriptor that keeps its value on itself shares it across all instances. The next example stores `1` on one instance and `2` on another, then reads the first one back.

```python
class SharedSlot:
    """BUG: the value lives on the descriptor, so every instance shares it."""
    value = None

    def __get__(self, obj, owner=None):
        return self.value if obj is not None else self

    def __set__(self, obj, value):
        self.value = value


class Holder:
    x = SharedSlot()


a, b = Holder(), Holder()
a.x, b.x = 1, 2
print(a.x)  # prints 2, not 1
```

```output
2
```

The fix is to store the value under a per-instance key, for example `setattr(obj, "_x", value)`. Question 2 below works through it.

> [!TRAP]
> `__set_name__` runs only when the class statement runs. The data model says `type.__new__` collects the attributes that define `__set_name__` from the class namespace when the class is created (Python Data Model, §Creating the class object). A descriptor assigned to a class later never gets its name, so store the name explicitly in that case.

> [!TRAP]
> Many metaclass uses are now unnecessary. PEP 487 added `__set_name__` and `__init_subclass__` so that many class-customization tasks no longer need a metaclass (PEP 487). Try a class decorator or `__init_subclass__` first.

## Metaclasses: who creates the class

A metaclass is the class of a class. `type` is the default metaclass, so `type(int)` is `type`. When you write `class Child(Base, metaclass=Meta):`, the interpreter runs four stages. It calls `Meta.__prepare__` to make a namespace. It executes the class body into that namespace. It calls `Meta(name, bases, namespace)` to create the class object. The data model specifies that last call as `metaclass(name, bases, namespace, **kwds)` (Python Data Model, §Creating the class object; PEP 3115).

Inside that call, `type.__new__` does two more things, in this order. It calls `__set_name__(owner, name)` on every descriptor in the namespace. Then it calls `__init_subclass__` on the immediate parent in the method resolution order (PEP 487). After `__new__` returns, Python calls `Meta.__init__`, which is the normal call protocol for a class instance.

![Six numbered steps in the order Python runs them for a class statement: __prepare__, body, metaclass __new__, __set_name__, __init_subclass__, metaclass __init__; steps four and five run inside type.__new__](diagrams/10.5-class-trace.svg "Order of calls for class Child(Base, metaclass=Meta). The order below is recorded by running the code.")

Every step below runs as the figure shows:

```python
trace = []


class Tracked:
    def __set_name__(self, owner, name):
        trace.append(f"__set_name__({owner.__name__}, {name!r})")

    def __get__(self, obj, owner=None):
        return self


class Base:
    def __init_subclass__(cls, **kw):
        trace.append(f"Base.__init_subclass__({cls.__name__})")
        super().__init_subclass__(**kw)


class Meta(type):
    @classmethod
    def __prepare__(mcls, name, bases, **kw):
        trace.append(f"Meta.__prepare__({name})")
        return {}

    def __new__(mcls, name, bases, ns, **kw):
        trace.append(f"Meta.__new__({name})")
        return super().__new__(mcls, name, bases, ns, **kw)

    def __init__(cls, name, bases, ns, **kw):
        trace.append(f"Meta.__init__({cls.__name__})")
        super().__init__(name, bases, ns, **kw)


class Child(Base, metaclass=Meta):
    x = Tracked()
    trace.append("class body executed")


for line in trace:
    print(line)
```

```output
Meta.__prepare__(Child)
class body executed
Meta.__new__(Child)
__set_name__(Child, 'x')
Base.__init_subclass__(Child)
Meta.__init__(Child)
```

Metaclass attributes follow the same precedence rules, but on the class side. A property defined on the metaclass is visible when you access the class, while instances never consult the metaclass:

```python
class KindMeta(type):
    @property
    def kind(cls):
        return f"class {cls.__name__}"


class Thing(metaclass=KindMeta):
    kind = "class attribute"


print(Thing.kind)    # the metaclass property wins for class access
print(Thing().kind)  # instance lookup never consults the metaclass
```

```output
class Thing
class attribute
```

The first line is the surprise. `Thing.kind` finds the property on `KindMeta`, which is a data descriptor, before the class's own `kind` entry. I checked this on CPython 3.12.13 but did not open the CPython source for this rule. Treat it as observed behaviour that the Python reference describes only indirectly.

## Cost of the lookup path

Access paths that run Python code are several times slower than a plain instance attribute. The measurements below were taken with `timeit` (best of five runs) on one machine and one Python version.

![Horizontal bars of nanoseconds per access: instance attribute 8.5 ns, class attribute 23.1 ns, property 51.2 ns, non-data descriptor 61.9 ns, __getattr__ fallback 49.1 ns](diagrams/10.5-access-cost.svg "Measured cost per access, CPython 3.12.13 on one Mac. Ratios are the useful part; absolute values change with hardware and version.")

The ratios, not the nanoseconds, are what to take from this. The three slower paths sit close together in this run, and their order may change with version or hardware. This run is separate from the one in Lesson 10.4, which measured a property read at 24.8 ns against 51.2 ns here, so compare figures only within one lesson. The gap to the instance attribute is the part this measurement supports.

## Summary

- Lookup checks a data descriptor on the class first, then the instance dict, then a non-data descriptor, then a plain class attribute, then `__getattr__`.
- A property is a data descriptor, so writing to the instance dict cannot shadow it.
- A property getter that raises `AttributeError` silently triggers `__getattr__`.
- A class statement calls the metaclass after the body runs; `__set_name__` runs before `__init_subclass__`.

## Quiz time

### Question 1: Prediction

What does this print?

```python
class A:
    @property
    def v(self):
        return 1

a = A()
a.__dict__["v"] = 99
print(a.v)
```

<details><summary>Show Solution</summary>

It prints `1`. `property` defines `__set__`, so it is a data descriptor, and the lookup returns its `__get__` result before it reaches the instance dict. The value 99 is stored but never read through `a.v`.

</details>

### Question 2: Find the bug

A logging descriptor is meant to give each instance its own counter, but the output is wrong:

```python
class Counter:
    count = 0

    def __get__(self, obj, owner=None):
        return self.count

    def __set__(self, obj, value):
        self.count = value


class Widget:
    hits = Counter()


w1, w2 = Widget(), Widget()
w1.hits = 5
print(w2.hits)  # expected 0, prints 5
```

<details><summary>Show Solution</summary>

The bug is that `self.count` is stored on the descriptor, which exists once per class, so `w1` and `w2` share one value. A fix stores the value on the instance:

```python
class Counter:
    def __set_name__(self, owner, name):
        self.key = "_" + name

    def __get__(self, obj, owner=None):
        if obj is None:
            return self
        return getattr(obj, self.key, 0)

    def __set__(self, obj, value):
        setattr(obj, self.key, value)
```

Running the buggy version prints `5`. The fixed version prints `5 0`, because `w1` stores `_hits` and `w2` falls back to the default `0`.

</details>

### Question 3: Calculation

A class defines `attr` as a data descriptor whose `__get__` increments a counter and returns 0. The loop `for _ in range(1000): _ = o.attr` runs once. How many times is `__get__` called, and how many times would it be called if `attr` were a plain class attribute?

<details><summary>Show Solution</summary>

It is called 1000 times, once per access, because a data descriptor is always consulted. A plain class attribute involves no `__get__` call at all, so the count would be 0. Running the loop with a counting descriptor gives 1000.

</details>

### Question 4: Explain the output

Why does this print `fallback for value` instead of an error message about `_missing`?

```python
class Masked:
    @property
    def value(self):
        raise AttributeError("self._missing was never set")

    def __getattr__(self, name):
        return f"fallback for {name}"

print(Masked().value)
```

<details><summary>Show Solution</summary>

The property getter raises `AttributeError`. The data model says `__getattr__` is called when the default access fails with an `AttributeError`, and this includes an `AttributeError` raised by a property's `__get__`. Python therefore calls `__getattr__("value")`, and the original message is discarded. To expose it, do not define `__getattr__` on this class, or raise a different exception type from the getter.

</details>
