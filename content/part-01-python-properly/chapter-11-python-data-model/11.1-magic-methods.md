Your class can support `obj[i]`, `len(obj)`, `obj(x)` and `for item in obj` by defining **special methods**, also called **dunder methods** because their names begin and end with a double underscore. In this lesson you will build a `Vector` class with `__getitem__`, `__len__` and `__call__`, predict what Python does with each syntax, and check each claim against the Python reference.

**You need:** classes and instance methods (Lesson 10.1), and the iteration protocol (Lesson 9.1).

## The problem this solves

An ordinary object supports none of these syntaxes. This class defines nothing, and each attempt fails:

```python
class Plain:
    pass

p = Plain()
for label, attempt in [("p[0]", lambda: p[0]), ("len(p)", lambda: len(p)), ("p()", lambda: p())]:
    try:
        attempt()
    except TypeError as error:
        print(label, "->", error)
```

```output
p[0] -> 'Plain' object is not subscriptable
len(p) -> object of type 'Plain' has no len()
p() -> 'Plain' object is not callable
```

Each message names a missing special method. Python does not ask the object to do the work. It asks the object's type for a method, and a class that defines that method answers the question.

This matters beyond error messages. Once a class defines the right methods, code written for lists, dictionaries or functions accepts it too: a function that loops over its argument, or calls `len()` on it, works with your object. The lookup happens when the operation runs, so a missing method fails only on the line that needs it. That is my reading of the lookup rule, not a separate claim from the reference.

## Intuition: a syntax is a call on the type

![Three rows: a slice of v, len of v, and v called with 2.0 each point to a method of the Vector type, __getitem__, __len__ and __call__, and produce a result](diagrams/11.1-dispatch.svg "Each syntax becomes a call on a method of the type, with the instance passed as the first argument.")

The Python reference (`object.__call__`) gives the rule for calls: "`x(arg1, arg2, ...)` roughly translates to `type(x).__call__(x, arg1, ...)`". The "Special method lookup" section says the same lookup applies to implicit invocations in general: such methods "are only guaranteed to work correctly if defined on an object's type, not in the object's instance dictionary." So `x[i]` calls `type(x).__getitem__(x, i)`, and `len(x)` calls `type(x).__len__(x)`. The instance is the first argument, which is why each method takes `self`.

## Worked example, by hand

Let `v = Vector([1.0, 2.0, 3.0])`, using the class in the next block. Trace each syntax:

- `v[0]` calls `__getitem__(v, 0)`, which returns `self.components[0]`, which is `1.0`.
- `v[1:]` calls `__getitem__(v, slice(1, None))`. The slice passes through to the list, so the result is the plain list `[2.0, 3.0]`.
- `len(v)` calls `__len__(v)`, which returns `len([1.0, 2.0, 3.0])`, which is `3`.
- `v(2.0)` calls `__call__(v, 2.0)`, which builds a new `Vector` with every component multiplied by 2.0: `Vector([2.0, 4.0, 6.0])`.

The slice result is a list, not a `Vector`. Our `__getitem__` delegates to the list, and the list returns a list. If you want a `Vector`, you must wrap the result yourself.

The same delegation predicts failures. `v[5]` passes the index 5 unchanged to the three-element list, so it raises the list's own `IndexError`. A class that rewrites the index before passing it on has to handle that case itself, and every method in this class inherits the list's rules.

## Code: a Vector with four syntaxes

```python
class Vector:
    def __init__(self, components):
        self.components = components

    def __getitem__(self, index):
        return self.components[index]     # an int or a slice: the list handles both

    def __len__(self):
        return len(self.components)

    def __call__(self, scalar):
        return Vector([x * scalar for x in self.components])

    def __repr__(self):
        return f"Vector({self.components})"


v = Vector([1.0, 2.0, 3.0])
print("v[0] =", v[0])
print("v[1:] =", v[1:])
print("len(v) =", len(v))
print("v(2.0) =", v(2.0))
print("callable(v) =", callable(v))
```

```output
v[0] = 1.0
v[1:] = [2.0, 3.0]
len(v) = 3
v(2.0) = Vector([2.0, 4.0, 6.0])
callable(v) = True
```

`callable(v)` is `True` because the class defines `__call__`. The `callable()` entry in the built-in functions reference says that "instances are callable if their class has a `__call__()` method". The `Plain` class above has no `__call__`, so `callable(p)` would be `False`.

## Under the hood: __getitem__ also gives you iteration

![Four boxes for calls __getitem__(0) to __getitem__(3): the first three return 0, 10 and 20, and the fourth raises IndexError, which ends the loop](diagrams/11.1-iter-fallback.svg "Without __iter__, for and list() call __getitem__ with 0, 1, 2, ... until IndexError.")

The `Trace` class below defines `__getitem__` and no `__iter__`, and a `for` loop still works. The `iter()` entry in the built-in functions reference says an object is iterable if it has `__iter__()`, or if it supports "the sequence protocol (the `__getitem__()` method with integer arguments starting at `0`)". The `__getitem__` note in the data model adds: "for loops expect that an IndexError will be raised for illegal indexes to allow proper detection of the end of the sequence."

```python
class Trace:
    def __init__(self, n):
        self.n = n

    def __getitem__(self, i):
        print(f"  __getitem__({i})")
        if i >= self.n:
            raise IndexError(i)
        return i * 10


print("for loop:")
for x in Trace(3):
    print("  got", x)
print("list:", list(Trace(3)))
```

```output
for loop:
  __getitem__(0)
  got 0
  __getitem__(1)
  got 10
  __getitem__(2)
  got 20
  __getitem__(3)
  __getitem__(0)
  __getitem__(1)
  __getitem__(2)
  __getitem__(3)
list: [0, 10, 20]
```

Read the trace. The loop asks for indices 0, 1 and 2, then 3. Index 3 raises `IndexError`, and that is the signal that ends the loop. The `list()` call runs the same protocol again, which is why its four calls print after the loop's.

## Under the hood: __len__ must return a non-negative integer

![A table of __len__ return values: 3, 0 and True are accepted, with True giving 1; 3.0, -1, None and '3' are rejected with TypeError or ValueError](diagrams/11.1-len-returns.svg "What len() does with the value __len__ returns, CPython 3.12.")

The data model says `__len__` "should return the length of the object, an integer `>= 0`". It does not say what happens otherwise. CPython, the reference implementation of Python written in C, rejects other values. We ran the cases below on CPython 3.12:

```python
class Reports:
    def __init__(self, value):
        self.value = value

    def __len__(self):
        return self.value


for value in [3, 0, True, 3.0, -1, None, "3"]:
    try:
        print(f"{value!r:>5} -> len() = {len(Reports(value))}")
    except Exception as error:
        print(f"{value!r:>5} -> {type(error).__name__}: {error}")
```

```output
    3 -> len() = 3
    0 -> len() = 0
 True -> len() = 1
  3.0 -> TypeError: 'float' object cannot be interpreted as an integer
   -1 -> ValueError: __len__() should return >= 0
 None -> TypeError: 'NoneType' object cannot be interpreted as an integer
  '3' -> TypeError: 'str' object cannot be interpreted as an integer
```

Three things follow. Only integers are accepted, and `True` counts as 1 because `bool` is a subclass of `int`. The float `3.0` is rejected even though it equals 3. The `ValueError` for a negative value is observed CPython 3.12 behaviour. It is not in the reference text we read, so do not depend on its exact wording.

Why does this strictness matter? `len()` is how loops and conditions decide how much work to do, so a wrong length does not just print a wrong number. A float from a division such as `n / 2` could travel into code that expects an integer and fail there, far from the line that produced it. Rejecting it at the `len()` call keeps the error close to its cause. This is my reasoning, not something the reference states.

## Under the hood: special-method lookup skips the instance

![Two boxes: the instance dictionary of b holds __len__ = lambda: 99, and the class Box holds __len__ returning 3. b.__len__() reads 99 from the instance, and len(b) reads 3 from the class](diagrams/11.1-instance-shadow.svg "Explicit attribute access sees the instance; len() looks up the type.")

The reference's "Special method lookup" section says that implicit invocations of special methods "are only guaranteed to work correctly if defined on an object's type, not in the object's instance dictionary." Explicit attribute access, such as `b.__len__`, does see the instance. The syntax `len(b)` does not.

```python
class Box:
    def __len__(self):
        return 3


b = Box()
b.__len__ = lambda: 99          # an instance attribute, not a method on the type
print("b.__len__() =", b.__len__())
print("len(b) =", len(b))
```

```output
b.__len__() = 99
len(b) = 3
```

The lookup starts at the type every time, so a change to the class does reach every instance. Assigning `Box.__len__ = lambda self: 7` changes `len()` for all `Box` objects, while an instance attribute changes only that one object. This is why patching behaviour on a class is a class-wide change, and why patching one instance is a surprise to anyone who expects the type to be the source of truth.

## Common traps

> [!TRAP]
> **Raising KeyError ends the loop with an error, not with a stop.** The loop expects IndexError. A dict-backed class that raises KeyError for a missing key crashes the `for` loop at the first missing key. Raise IndexError for an out-of-range position, or define `__iter__`.

> [!TRAP]
> **Negative indices follow the storage, not list rules.** A class that forwards `key` to a dict passes `-1` straight to the dict, and looks for the key `-1`. Only a list-backed class gets `-1` to mean "last element", and only because the list does that work.

> [!TRAP]
> **Returning a float from __len__.** `len(self.items) / 2` produces a float, and `len()` raises `TypeError`. Use `//` to get an integer.

> [!TRAP]
> **An object with a zero __len__ is false.** The data model says an object without `__bool__()` whose `__len__()` returns zero "is considered to be false in a Boolean context". So `if bag:` skips an empty `Bag`, and the test runs without any error.

Each trap below looks correct when you read the method alone. The failure appears only in a loop, a condition or a negative index, so check the method in the context where Python calls it. The next block shows the first, second and fourth traps in code, plus a `__call__` argument error:

```python
class DictBacked:
    def __init__(self, d):
        self.d = d

    def __getitem__(self, key):
        return self.d[key]


try:
    print(list(DictBacked({0: "a", 1: "b"})))
except KeyError as error:
    print("KeyError:", error)

k = DictBacked({0: "zero", 1: "one", 2: "two"})
try:
    print(k[-1])
except KeyError as error:
    print("KeyError:", error)


class Bag:
    def __init__(self, items):
        self.items = items

    def __len__(self):
        return len(self.items)


print(bool(Bag([])), bool(Bag([0])))


class Scale:
    def __call__(self, x):
        return x * 2


try:
    Scale()(1, 2)
except TypeError as error:
    print("TypeError:", error)
```

```output
KeyError: 2
KeyError: -1
False True
TypeError: Scale.__call__() takes 2 positional arguments but 3 were given
```

## When to implement each method

These are design rules I derived from the behaviour above. They are my reasoning, not requirements from the reference.

- Implement `__getitem__` when callers should index or slice your object. If your data is ordered, also give the caller a predictable result type for slices.
- Implement `__len__` when the object has a natural size. Make it match what iteration produces, so `len(obj)` and `list(obj)` agree.
- Implement `__call__` when the object carries state and behaves like one function, as in a configured scaler or a decorator. A plain function is simpler when there is no state.
- When you define `__iter__`, it takes precedence over the `__getitem__` fallback. In a quick test, a class with both returned only the value from `__iter__`. So you can avoid the IndexError contract entirely by defining `__iter__` and keeping `__getitem__` for indexing.

## Summary

- A syntax such as `x[i]`, `len(x)`, `x(...)` or `for item in x` is a call on a special method of the object's type, with the instance passed first.
- `__getitem__` also gives iteration: Python calls it with 0, 1, 2, ... until it raises IndexError.
- `__len__` must return an integer of at least 0. CPython 3.12 rejects a float or a string, and raises ValueError for a negative value.
- Special methods are looked up on the type, so an attribute set on one instance does not change `len(instance)`.

### Question 2: Find the bug

This class should report the number of pairs in `items`. Running `print(len(Half([1, 2, 3, 4])))` fails.

```python
class Half:
    def __init__(self, items):
        self.items = items

    def __len__(self):
        return len(self.items) / 2

print(len(Half([1, 2, 3, 4])))
```

<details><summary>Show solution</summary>

The bug is the `/`. Division always returns a float, here `2.0`, and `len()` requires an integer, so it raises `TypeError: 'float' object cannot be interpreted as an integer`. Change the line to `return len(self.items) // 2`. Then `len(Half([1, 2, 3, 4]))` returns the integer 2.

</details>

### Question 3: Explain the failure

```python
class Table:
    def __init__(self, d):
        self.d = d

    def __getitem__(self, k):
        return self.d[k]

for row in Table({0: "a", 1: "b", 2: "c"}):
    print(row)
```

<details><summary>Show solution</summary>

The output begins with `a`, `b` and `c`. Then the loop asks for `__getitem__(3)`, the dict raises `KeyError: 3`, and the error reaches the top level. The for loop stops only on IndexError, so a KeyError is not caught. Either raise IndexError inside `__getitem__` when the key is missing, or define `__iter__`, which takes precedence over the fallback.

```text
a
b
c
KeyError: 3
```

</details>

### Question 4: Explain the result

Which of these prints `True`? The class `Bag` has `__len__` returning `len(self.items)` and no `__bool__`.

- (a) `bool(Bag([]))`
- (b) `bool(Bag([0]))`
- (c) `bool(Bag([None]))`

<details><summary>Show solution</summary>

Only (b) and (c) print `True`. Python has no `__bool__` to call, so `bool()` falls back to `__len__`. `Bag([])` has length 0, so it is false, which is option (a). `Bag([0])` and `Bag([None])` each have length 1, so they are true. Stored values do not matter, only the count. The earlier trap block prints `False True` for (a) and (b), matching this reasoning.

</details>
