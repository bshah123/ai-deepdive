By the end of this lesson you will write a class with `__enter__` and `__exit__`, predict the order in which a `with` statement calls them, and decide whether an exception should propagate or be suppressed. You will also see the most common mistake: cleanup code that is skipped when the body raises.

**You need:** the idea from Lesson 11.1 that Python calls methods named `__like_this__` for you, and `try`/`finally`.

## The problem: cleanup must run even when the code fails

A file, lock or database connection must be released even when the code that uses it fails. With `try`/`finally` you can do that, but you repeat the pattern for every resource:

```python
def use_resource(fail):
    print("open")
    try:
        if fail:
            raise ValueError("boom")
        print("work")
    finally:
        print("close")    # runs whether or not the body raised

use_resource(fail=False)
try:
    use_resource(fail=True)
except ValueError as e:
    print("caught:", e)
```

```output
open
work
close
open
close
caught: boom
```

The `with` statement moves that pattern into the object itself, so the caller writes it once. A forgotten `finally` leaks the resource silently, and nested cases become hard to read. Cleanup written inside the object is easier to check.

The built-in file object is the standard example: its `__exit__` closes the file. In the experiment behind this lesson, the file was closed after a normal exit and after an exception (`closed_after_normal` and `closed_after_exception` were both `True`).

## The protocol: `__enter__` and `__exit__`

An object works with `with` if its class defines two methods. For `with EXPR as NAME:`, Python does the following, in this order (Python Language Reference, "The with statement"):

1. Evaluates `EXPR` to get a context manager.
2. Calls `__enter__()` and binds its return value to `NAME`.
3. Runs the body.
4. Calls `__exit__(exc_type, exc_value, traceback)`. On normal completion all three arguments are `None`. If the body raised, they describe the exception.

![Flow of a with statement: evaluate the expression, call __enter__, run the body, then call __exit__; on an exception, the return value of __exit__ decides whether the exception is re-raised or suppressed](diagrams/11.2-desugar.svg "Enter once, run the body, always call __exit__. The return value only matters when the body raised.")

PEP (Python Enhancement Proposal) 343, which added the statement in Python 2.5, gives the same rule as a `try` block: the body runs inside `try`, and `__exit__` receives the exception information. If `__exit__` returns a false value, the exception is re-raised.

Two details of that translation matter later. It looks `__enter__` and `__exit__` up on the object's type (`exit = type(mgr).__exit__`), not by calling them on the instance first. And `__enter__` runs before the `try` starts. The language reference states the consequence as a guarantee: if `__enter__` returns without error, `__exit__` will always be called. An error inside `__enter__` therefore never reaches `__exit__` (see the traps below).

## Worked example: nested managers, by hand

Take `with Tracked("A"), Tracked("B"), Tracked("C"): body`. Each `__enter__` runs in the order written. The body runs once all three are entered. The `__exit__` calls then run in the reverse order, so the innermost resource is released first. The sequence is: enter A, enter B, enter C, body, exit C, exit B, exit A. The diagram below shows this order, and the code reproduces it. The reverse order is the right one for resources that depend on each other. A database connection opened after a lock must close before the lock is released, and stack-order exit gives you that for free.

![Three nested rectangles labelled with their enter and exit steps: enter runs outside in (steps 1 to 3), body is step 4, exit runs inside out (steps 5 to 7)](diagrams/11.2-nested-order.svg "Nested managers: enter outside in, exit inside out, like a stack.")

```python
class Tracked:
    def __init__(self, name):
        self.name = name
    def __enter__(self):
        print(f"enter {self.name}")
        return self                 # bound to the name after "as"
    def __exit__(self, exc_type, exc_value, traceback):
        print(f"exit {self.name}")
        return False                # False: do not suppress exceptions

with Tracked("A"), Tracked("B"), Tracked("C"):
    print("body")
```

```output
enter A
enter B
enter C
body
exit C
exit B
exit A
```

## What __exit__ returns decides the exception

When the body raises, `__exit__` gets the exception and returns a value. The three arguments are the same values `sys.exc_info()` returns, and the language reference writes the decision as `if not exit(*sys.exc_info()): raise` (Python Language Reference, "The with statement"). Python tests the return value for truth. A false value (including `None`, which is what you get if you return nothing) re-raises the exception. A true value suppresses it, and execution continues after the `with` block. A function with no `return` statement returns `None`, so forgetting the return is the same as returning `False`.

If the body raises inside the three-manager block from the worked example, each `__exit__` receives the exception and returns `False`. Every manager still logs its exit, in the same inside-out order, and the exception then leaves the block (checked by running this code):

```python
class Tracked:
    def __init__(self, name):
        self.name = name
    def __enter__(self):
        print(f"enter {self.name}")
        return self
    def __exit__(self, exc_type, exc_value, traceback):
        print(f"exit {self.name} {exc_type.__name__ if exc_type else None}")
        return False

try:
    with Tracked("A"), Tracked("B"), Tracked("C"):
        raise ValueError("boom")
except ValueError as e:
    print("caught", e)
```

```output
enter A
enter B
enter C
exit C ValueError
exit B ValueError
exit A ValueError
caught boom
```

```python
class Quiet:
    def __init__(self, swallow):
        self.swallow = swallow
    def __enter__(self):
        return self
    def __exit__(self, exc_type, exc_value, traceback):
        print("__exit__ got:", exc_type.__name__ if exc_type else None)
        return self.swallow

with Quiet(swallow=True):
    raise ValueError("boom")
print("after the swallowing with")

try:
    with Quiet(swallow=False):
        raise ValueError("boom")
except ValueError:
    print("ValueError reached the caller")
```

```output
__exit__ got: ValueError
after the swallowing with
__exit__ got: ValueError
ValueError reached the caller
```

![Three rows: no exception gives __exit__ None and the flow continues; an exception with a False return is re-raised; an exception with a True return is suppressed and the flow continues](diagrams/11.2-exception-paths.svg "The same with block, three return values. Outcomes come from the experiment script.")

## Generators: the @contextmanager decorator

Writing a class for every resource is verbose. `contextlib.contextmanager` turns a generator into a context manager. Everything before `yield` plays the role of `__enter__`, the value yielded is what `as` binds, and everything after `yield` plays the role of `__exit__`. The `as NAME` part is optional, as in the examples below:

```python
from contextlib import contextmanager

@contextmanager
def logged(name):
    print("open", name)
    yield
    print("close", name)

with logged("R"):
    print("body")
```

```output
open R
body
close R
```

You never write `__exit__` yourself. If the body raises, the exception is thrown into the generator at the `yield` line (Python `contextlib` documentation). Unless you catch it there, the code after `yield` is skipped. A `try`/`finally` around the `yield` makes the cleanup run anyway. The next block shows both versions:

```python
from contextlib import contextmanager

@contextmanager
def no_finally(name):
    print("open", name)
    yield
    print("close", name)      # skipped when the body raises

@contextmanager
def with_finally(name):
    print("open", name)
    try:
        yield
    finally:
        print("close", name)  # always runs

for cm in (no_finally, with_finally):
    try:
        with cm("R"):
            raise ValueError("boom")
    except ValueError:
        print("caught ValueError")
```

```output
open R
caught ValueError
open R
close R
caught ValueError
```

![Two lanes: without try/finally the close step is marked skipped after the body raises; with try/finally the close step runs after the exception](diagrams/11.2-generator-cleanup.svg "Same body, same exception. Only the placement of the cleanup line differs.")

In both versions the caller sees the same `ValueError`. The only difference is whether the `close R` line appears in the log, which is the difference that matters for files and locks.

A class is the better choice when the manager needs state that outlives one `with` block, several methods (for example, a `commit` and a `rollback`), or an object that can be entered more than once. A decorated generator suits setup and teardown that fit in a few lines, because its local variables hold the state. This rule of thumb is my own reasoning, not a published guideline.

## Managing a variable number of resources

Sometimes you do not know in advance how many resources to open, for example one file per line of an input list. A fixed `with` statement cannot be written for an unknown count. `contextlib.ExitStack` registers them one at a time and closes them in reverse order when the `with` block ends (Python `contextlib` documentation):

```python
from contextlib import ExitStack, contextmanager

@contextmanager
def opened(name):
    print("open", name)
    try:
        yield name
    finally:
        print("close", name)

names = ["one", "two", "three"]
with ExitStack() as stack:
    handles = [stack.enter_context(opened(n)) for n in names]
    print("body sees", handles)
```

```output
open one
open two
open three
body sees ['one', 'two', 'three']
close three
close two
close one
```

## Suppressing one expected error

`contextlib.suppress` is a ready-made context manager whose `__exit__` returns true for the exception types you list. The Python documentation says it should be used only for very specific errors where silently continuing is known to be right (contextlib documentation). A broad `suppress(Exception)` hides bugs along with the error you expected.

```python
import contextlib

settings = {"debug": True}
with contextlib.suppress(KeyError):
    print(settings["verbose"])   # raises KeyError
print("continued")
```

```output
continued
```

## Common traps

> [!TRAP]
> A generator without `try`/`finally` skips its cleanup when the body raises. The log in the diagram above shows `close R` missing. Put the cleanup in `finally`.

> [!TRAP]
> `__exit__` returns a true value to suppress an exception, so a truthy return by accident hides errors. A class that ends with `return self.errors` hides every error as soon as `self.errors` holds one item. Return `False` explicitly unless you mean to suppress.

> [!TRAP]
> If `__enter__` raises, `__exit__` is not called. In the experiment, `__enter__` logged `enter E`, then raised, and no exit line appeared. If `__enter__` acquires two resources and the second fails, the first must be released inside `__enter__`.

> [!TRAP]
> An exception raised inside `__exit__` replaces the body's exception. In the experiment, `__exit__` raised `KeyError` while the body had raised `ValueError`. The caller saw `KeyError`, with `ValueError` stored as its `__context__`.

> [!TRAP]
> A one-shot `@contextmanager` object cannot be reused. In the experiment, a second `with` on the same object failed. Call the decorated function again for each new `with` block.

## Summary

- `with` calls `__enter__` once, runs the body, and calls `__exit__` on every exit path.
- On a normal exit, `__exit__` receives three `None` arguments. On an exception, it receives the exception's type, value and traceback.
- A true return value from `__exit__` suppresses the exception. A false or `None` return re-raises it.
- In a `@contextmanager` generator, cleanup must be in `try`/`finally`, because the exception is raised at the `yield`.
- `ExitStack` manages a number of resources that is only known at run time, and releases them in reverse order.
- Lesson 11.3 uses the same idea for containers: Python's built-in syntax works with any object that defines the right special methods.

class Quiet:
    def __init__(self, swallow):

        print("__exit__ got:", exc_type.__name__ if exc_type else None)

The inner manager receives `ValueError` and returns `True`, so it suppresses the exception. The outer manager's body therefore finishes normally, and its `__exit__` receives `None`. It returns `False`, and since there is no exception to re-raise, `end` prints.

### Question 2: Find the bug

A colleague wrote this and reports that `disconnect` is never printed after an error. Explain why, and fix it.

```python
from contextlib import contextmanager

@contextmanager
def connection(name):
    print("connect", name)
    yield name
    print("disconnect", name)

with connection("db"):
    raise RuntimeError("query failed")
```

<details><summary>Show Solution</summary>

The exception is thrown into the generator at the `yield` line. The statement after `yield` never runs, so `disconnect` is skipped, and the `RuntimeError` propagates. Put the cleanup in `finally`:

```python
from contextlib import contextmanager

@contextmanager
def connection(name):
    print("connect", name)
    try:
        yield name
    finally:
        print("disconnect", name)

try:
    with connection("db"):
        raise RuntimeError("query failed")
except RuntimeError:
    print("caught RuntimeError")
```

Output:

```text
connect db
disconnect db
caught RuntimeError
```

</details>

### Question 3: Explain the rule

A class's `__enter__` opens two files, `a.txt` and then `b.txt`. Opening `b.txt` raises `OSError`. Does `__exit__` run, and who closes `a.txt`?

<details><summary>Show Solution</summary>

No. If `__enter__` raises, the body never starts, and Python does not call `__exit__` (the experiment's `enter_fails` case logged the `enter` line and no `exit` line). So `a.txt` must be closed inside `__enter__`, before the error is re-raised. A common pattern is to wrap the second open in `try`, close the first file, and re-raise.

</details>

### Question 4: Find the bug

This class is meant to log errors and let them propagate. Why does it hide them?

```python
class Collect:
    def __init__(self):
        self.errors = []
    def __enter__(self):
        return self
    def __exit__(self, exc_type, exc_value, traceback):
        if exc_type is not None:
            self.errors.append(str(exc_value))
        return self.errors
```

<details><summary>Show Solution</summary>

The method returns `self.errors`, which is a list. Python tests the return value for truth. The append runs before the return, so the list is already non-empty when it is tested, and the exception that was just logged is suppressed too. Return `False` to propagate the error after logging it:

```python
    def __exit__(self, exc_type, exc_value, traceback):
        if exc_type is not None:
            self.errors.append(str(exc_value))
        return False
```

</details>
