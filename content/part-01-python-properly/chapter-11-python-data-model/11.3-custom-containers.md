In this lesson you will write a class that behaves like a built-in list: `len()`, indexing, slicing, `in`, `for` and `reversed()` all work on it. You will also predict how many times Python calls your code for each operation, then check the prediction.

**You need:** magic methods such as `__len__` and `__getitem__` (Lesson 11.1), and the iterator protocol (Lesson 9.1).

## The problem

Container syntax is a method call in disguise. `len(s)` calls `s.__len__()`, `s[2]` calls `s.__getitem__(2)`, and `for x in s` asks `s` for an iterator. Python does not know that your object wraps a list. It only looks at the methods your class defines.

So a class that stores its items in `self._data` gets none of these operations for free. You must define the methods, and you must know which ones Python can work out from the rest. Mistakes here are often silent. A class with no `__iter__` can still be looped over, through a slower fallback. A `__getitem__` that never raises `IndexError` makes a loop run forever.

The payoff is large. Once a class defines these methods, built-ins such as `list()`, `sorted()`, `sum()` and `zip()` accept it unchanged, because they all work through the same protocols. You write the rules once, and the rest of the language follows.

## Intuition: one operation, one method

![A table: each Python operation maps to one special method; when that method is missing, the fallback is listed](diagrams/11.3-dispatch.svg "Each operation becomes one call on your object. Amber marks operations that have a fallback.")

Each operation becomes one call. Some operations have a fallback: if the main method is missing, Python tries a weaker one. For `in` and `for`, the fallback is `__getitem__` alone. Python calls it with 0, 1, 2 and so on until it raises `IndexError`. This is the old sequence protocol, and it is why a class with only `__getitem__` is already iterable.

Read the diagram as three layers. The left column is the syntax you write. The middle column is what your class must define to support that syntax. The right column is what Python does when the method is missing. An absent method is not always an error, because the right column may cover it.

## Worked example by hand

Take `s = [10, 20, 30, 40, 50]` in a class that defines only `__len__` and `__getitem__`. There is no `__contains__` and no `__iter__`, so `x in s` runs the fallback:

- `10 in s`: index 0 matches. One call.
- `30 in s`: indices 0 and 1 do not match, index 2 does. Three calls.
- `99 in s`: indices 0 to 4 do not match. Index 5 is out of range, the list raises `IndexError`, and the scan ends with `False`. Six calls.

So a hit at position $k$ costs $k + 1$ calls, and a miss on $n$ items costs $n + 1$. Make the prediction before you run anything.

![Index trace: for six operations on a five-item sequence, the indices that __getitem__ receives, with the match or the IndexError highlighted](diagrams/11.3-index-trace.svg "Predicted and measured traces are identical. Green is a match, rose is the IndexError that ends the scan.")

Run it:

```python
class Counted:
    """Defines only __len__ and __getitem__, so Python falls back to the sequence protocol."""
    def __init__(self, data):
        self._data = list(data)
        self.calls = []                    # every index Python asks for

    def __len__(self):
        return len(self._data)

    def __getitem__(self, i):
        self.calls.append(i)
        return self._data[i]               # a list raises IndexError past the end

def traced(seq, action):
    seq.calls.clear()
    result = action()
    return result, list(seq.calls)

s = Counted([10, 20, 30, 40, 50])
print("len(s) =", len(s), "| bool(s) =", bool(s), "| bool(Counted([])) =", bool(Counted([])))

_, trace = traced(s, lambda: list(s))
print("list(s)            trace:", trace)
for target in (10, 30, 50, 99):
    found, trace = traced(s, lambda: target in s)
    print(f"{target:>3} in s             ->", found, "trace:", trace)
_, trace = traced(s, lambda: list(reversed(s)))
print("list(reversed(s))  trace:", trace)

big = Counted(range(1000))
_, trace = traced(big, lambda: 999 in big)
print("999 in a 1000-item sequence:", len(trace), "calls")
_, trace = traced(big, lambda: 5000 in big)
print("5000 in a 1000-item sequence:", len(trace), "calls")
```

```output
len(s) = 5 | bool(s) = True | bool(Counted([])) = False
list(s)            trace: [0, 1, 2, 3, 4, 5]
 10 in s             -> True trace: [0]
 30 in s             -> True trace: [0, 1, 2]
 50 in s             -> True trace: [0, 1, 2, 3, 4]
 99 in s             -> False trace: [0, 1, 2, 3, 4, 5]
list(reversed(s))  trace: [4, 3, 2, 1, 0]
999 in a 1000-item sequence: 1000 calls
5000 in a 1000-item sequence: 1001 calls
```

The traces match the hand count. `list(s)` uses the same fallback, and its sixth call raises the `IndexError` that ends the loop. `reversed(s)` needs no `IndexError`: without `__reversed__`, Python uses `__len__` and walks the indices from $n - 1$ down to 0.

The Python data model states the rule. For the membership test, Python first tries `__iter__()`, then "the old sequence iteration protocol via `__getitem__()`". `for` loops expect an `IndexError` for illegal indexes, which is how they find the end of the sequence (Python data model, in References).

Each probe is a Python-level call, so the cost of `in` grows with $n$. If you define `__contains__` yourself, Python calls that one method instead, and it can delegate to the list's own `in`, which runs in C. That turns $n$ calls into one.

## Slices arrive as slice objects

![Flow: s[1:4] becomes one slice object passed to __getitem__, which returns a plain list](diagrams/11.3-slice-path.svg "The method receives one slice object. Delegating to a list returns a list.")

`w[1:4]` does not call a separate slice method. Python builds one `slice` object and passes it as the argument to `__getitem__`. Your method decides what to do with it. Delegating to a list gives you the list's rules, including negative steps, but the result is a plain list, not your class. Wrap the result yourself if callers need your class back.

Negative indices are not special for your class either. `slice.indices(length)` turns any slice into normalized `(start, stop, step)` values for a sequence of that length. The next block shows both behaviours:

```python
class Wrap:
    def __init__(self, data):
        self._data = list(data)

    def __len__(self):
        return len(self._data)

    def __getitem__(self, key):
        print("  __getitem__ received", key)
        return self._data[key]

w = Wrap([10, 20, 30, 40, 50])
part = w[1:4]
print("w[1:4] is a", type(part).__name__, part)
print("w[::-2] is", w[::-2])
print("slice(-2, None).indices(5) =", slice(-2, None).indices(5))
print("slice(None, None, -1).indices(5) =", slice(None, None, -1).indices(5))
```

```output
  __getitem__ received slice(1, 4, None)
w[1:4] is a list [20, 30, 40]
  __getitem__ received slice(None, None, -2)
w[::-2] is [50, 30, 10]
slice(-2, None).indices(5) = (3, 5, 1)
slice(None, None, -1).indices(5) = (4, -1, -1)
```

Negative indices follow the same split of work. In `w[-1]`, Python passes `-1` through unchanged. A list understands it, but your own storage would have to handle it if you did not delegate. The step in `w[::-2]` works the same way: Python passes the whole slice, and whoever owns the data decides what it means.

## Let the abstract base classes fill in the rest

Writing `__contains__`, `__iter__`, `__reversed__`, `index` and `count` by hand is repetitive. The abstract base classes (ABCs) in `collections.abc` write them for you. `Sequence` needs only `__getitem__` and `__len__`. `MutableSequence` adds `append`, `extend`, `pop`, `remove`, `reverse` and `+=` once you supply `__setitem__`, `__delitem__` and `insert`.

![Three columns: a plain class with two methods, a Sequence subclass that gains five mixins, and a MutableSequence subclass that gains more; each column shows its isinstance result](diagrams/11.3-abc-levels.svg "Each column keeps everything from the column before it.")

```python
from collections.abc import Iterable, MutableSequence, Sequence

class Plain:
    def __init__(self, data):
        self._data = list(data)

    def __len__(self):
        return len(self._data)

    def __getitem__(self, i):
        return self._data[i]

class SeqABC(Sequence):
    def __init__(self, data):
        self._data = list(data)

    def __len__(self):
        return len(self._data)

    def __getitem__(self, i):
        return self._data[i]

class MutABC(MutableSequence):
    def __init__(self, data):
        self._data = list(data)

    def __len__(self):
        return len(self._data)

    def __getitem__(self, i):
        return self._data[i]

    def __setitem__(self, i, v):
        self._data[i] = v

    def __delitem__(self, i):
        del self._data[i]

    def insert(self, i, v):
        self._data.insert(i, v)

p = Plain([1, 2, 3])
print("Plain: list(p) =", list(p), "| isinstance(p, Sequence) =", isinstance(p, Sequence))
print("Plain: isinstance(p, Iterable) =", isinstance(p, Iterable), "| has index()?", hasattr(p, "index"))
sq = SeqABC([3, 1, 4, 1, 5])
print("SeqABC: index(4) =", sq.index(4), "| count(1) =", sq.count(1), "| reversed =", list(reversed(sq)))
m = MutABC([1, 2])
m.append(3)
m += [4]
popped = m.pop()
m.reverse()
print("MutABC: popped", popped, "| data", m._data)
```

```output
Plain: list(p) = [1, 2, 3] | isinstance(p, Sequence) = False
Plain: isinstance(p, Iterable) = False | has index()? False
SeqABC: index(4) = 2 | count(1) = 2 | reversed = [5, 1, 4, 1, 3]
MutABC: popped 4 | data [3, 2, 1]
```

The mixins call `__getitem__` repeatedly. The documentation notes that if `__getitem__` takes constant time, the mixins are linear in $n$; if it takes linear time, as in a linked list, the mixins become quadratic and you should override them.

The `isinstance` results show a limit of structural checks. `Plain` is iterable in practice, because `list(p)` works through the fallback, yet `isinstance(p, Iterable)` is False, because `Iterable` checks only for `__iter__`. The ABC `Sequence` does no structural check at all, so only inheritance or `Sequence.register(Plain)` makes `isinstance` return True. To test iterability in practice, call `iter(obj)` and catch `TypeError`.

Choose the base class by the contract you promise. Subclass `Sequence` when callers only read, and `MutableSequence` when they may assign or delete. The base class then documents the contract, and `isinstance(x, MutableSequence)` tells a caller whether changing `x` is supported.

## Where the protocol breaks

Errors in these methods surface as exceptions in unexpected places. The next block shows two of them:

```python
class BadLen:
    def __len__(self):
        return 2.0

class DictLike:
    def __init__(self):
        self._d = {0: "a", 1: "b"}

    def __len__(self):
        return 2

    def __getitem__(self, k):
        return self._d[k]

try:
    len(BadLen())
except TypeError as e:
    print("TypeError:", e)

try:
    list(DictLike())
except KeyError as e:
    print("KeyError escaped the iteration, key =", e)
```

```output
TypeError: 'float' object cannot be interpreted as an integer
KeyError escaped the iteration, key = 2
```

`DictLike` fails because the fallback expects `IndexError` at the end. Its lookup raises `KeyError` for key 2, and nothing catches it. The fix is to translate the error: `raise IndexError(k)` when the key is missing.

Defining `__iter__` explicitly is usually the cleaner fix. With an explicit iterator, `for` never reaches the fallback, so iteration no longer depends on the `IndexError` rule, and `__getitem__` only has to answer the indices that callers ask for. This is a design choice, not something the protocol forces.

## Common traps

> [!TRAP]
> `__getitem__` must raise `IndexError` past the end. Returning `None` makes a `for` loop run forever, and raising `KeyError` escapes the loop, as the last block showed.

> [!TRAP]
> `__len__` must return an integer of at least 0. A float raises `TypeError` and a negative number raises `ValueError`. Because `bool()` falls back to `__len__`, an empty container is also false.

> [!TRAP]
> Setting `__iter__` to `None` makes an object non-iterable. Python does not fall back to `__getitem__` in that case, according to the data model.

> [!TRAP]
> Mixins are not free in time. `index()` and `count()` call `__getitem__` many times; on a linked list they become quadratic, so override them.

## Summary

- Each operation calls one special method. `in` and `for` fall back to `__getitem__` from index 0 until `IndexError`.
- On an $n$-item sequence, a miss costs $n + 1$ `__getitem__` calls, and a hit at position $k$ costs $k + 1$.
- A slice arrives as one `slice` object; `slice.indices(length)` normalizes it. Returning a list from a slice is your choice, not Python's.
- Subclass `collections.abc.Sequence` or `MutableSequence` to get the mixin methods, and make `isinstance` checks work by inheritance, not by duck typing.

### Question 1: Calculation

`s` is `Counted([10, 20, 30, 40, 50])` from the first code block. How many `__getitem__` calls does `40 in s` make, and with which indices?

Four calls, with indices 0, 1, 2 and 3. The value 40 sits at index 3, so the scan stops there. This is $k + 1$ with $k = 3$.

### Question 3: Find the bug

```text
class Ring:
    def __init__(self, items):
        self._items = items

    def __len__(self):
        return len(self._items)

    def __getitem__(self, i):
        if i >= len(self._items):
            return None
        return self._items[i]

for x in Ring([1, 2]):
    print(x)
```

<details><summary>Show Solution</summary>
The loop prints 1, then 2, then `None` forever. The scan asks for index 2, receives `None` instead of `IndexError`, and asks for index 3, 4 and so on without end. Checked by running `list(itertools.islice(Ring([1, 2]), 6))`, which returns `[1, 2, None, None, None, None]`; the unbounded loop never stops. The fix is to replace `return None` with `raise IndexError(i)`.
</details>

### Question 4: Explain

`list(Plain([1, 2, 3]))` works, but `isinstance(Plain([1, 2, 3]), Sequence)` is False. Why, and how do you make the check pass?

<details><summary>Show Solution</summary>
Iteration through the fallback needs only `__getitem__`, so it works without any declared type. (A class without `__len__` still iterates; I checked this.) `Sequence` has no structural check, so `isinstance` only returns True for a class that inherits from it or is registered with it. Fix it with `class Plain(Sequence):` or `Sequence.register(Plain)`.
</details>
