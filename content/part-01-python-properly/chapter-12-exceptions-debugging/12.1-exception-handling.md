When a line of Python fails, the interpreter raises an exception, and that exception travels up the chain of function calls until a `try` block catches it or the program stops. In this lesson you will read the tree of built-in exception classes, predict which `except` clause runs, trace what happens to each function the exception leaves, and spot the handlers that hide bugs.

**You need:** functions and the call stack (Lesson 7.1).

## The problem

Suppose `1 / 0` runs five function calls deep. The function that divides cannot return a value, because there is none to return. Something has to stop the normal return path and pass control to a handler, which may be several frames up. A frame is one active function call on the call stack. Python's answer is an exception: an object whose class says what went wrong, plus `try` / `except` blocks that catch it. Two questions follow. Which handler runs? And what happens to each frame the exception leaves behind?

## The class tree

Every exception is an instance of a class, and every class has a parent. The built-in classes form one tree. Its root is `BaseException`, the base of all built-in exceptions. `Exception` is one of its children, and nearly every ordinary error is a descendant of `Exception`. `SystemExit`, `KeyboardInterrupt` and `GeneratorExit` inherit directly from `BaseException`, not from `Exception`. The Python documentation says `KeyboardInterrupt` does this "so as to not be accidentally caught by code that catches `Exception`" (Python documentation, built-in exceptions).

![A tree with BaseException at the top; Exception has ArithmeticError and LookupError below it, and ZeroDivisionError, KeyError and IndexError at the bottom](diagrams/12.1-hierarchy.svg "The built-in exception tree, with the branches this lesson uses.")

Read the tree from the bottom up. `ZeroDivisionError` is a child of `ArithmeticError`, which is a child of `Exception`, which is a child of `BaseException`. Python searches exactly this chain of parents when it matches an `except` clause. In Python 3.12.13, `BaseException` has five direct subclasses (including `BaseExceptionGroup`), and `Exception` has 21. The exact counts change between Python versions, so treat them as a snapshot.

The tree lets you choose how wide a clause is. Catching `LookupError` handles a missing key and an out-of-range index in one clause, which suits code where both mean "this data is not there". Catching `ZeroDivisionError` alone suits code where only the division should be handled, and other arithmetic failures should still surface. Pick the parent class that matches the meaning you want, not the one that is shortest to write.

## Which handler runs: the first match

A `try` statement can have several `except` clauses. The Python reference says the search "inspects the `except` clauses in turn until one is found that matches the exception" (Python reference, the try statement). Each clause matches a class and every subclass of it. The first matching clause runs, and the rest are skipped.

The next block shows this for the three exception types used in the diagram below.

```python
def first_handler(fn):
    try:
        fn()
    except ArithmeticError:
        return "ArithmeticError"
    except LookupError:
        return "LookupError"
    except Exception:
        return "Exception"
    except BaseException:
        return "BaseException"

print(first_handler(lambda: 1 / 0))
print(first_handler(lambda: {}["k"]))
print(first_handler(lambda: undefined_name))
```

```output
ArithmeticError
LookupError
Exception
```

`KeyError` and `IndexError` both have `LookupError` as a parent, so one clause covers both. `NameError` has no branch of its own above `Exception`, so the `Exception` clause catches it. The diagram shows the full matrix: every clause that matches, and the one that actually runs.

Read the grid row by row. Each row is one raised exception. The green cell is the clause that runs. Grey cells to its right match too, but are skipped, because an earlier clause already handled the exception. Blank cells are clauses that do not match at all. A `ZeroDivisionError` matches three of the four clauses, yet only `ArithmeticError` runs. Python gives no warning about skipped clauses, so the clause order is part of the program's logic and should be read as carefully as the code inside each clause.

![A grid of four raised exceptions against four except clauses; each row has one green cell marked runs, cells to its right marked skipped, and cells to its left blank](diagrams/12.1-catch-matrix.svg "Which except clause handles each exception. Clauses are tried top to bottom, left to right.")

Order matters. If a broad clause comes first, it takes every match, and the specific clause below it never runs.

![Two rows: with except Exception first, the ZeroDivisionError goes to the broad clause and returns Exception clause; with the specific clause first, it returns ZeroDivisionError clause](diagrams/12.1-clause-order.svg "The same error with two orders of clauses. Only the order changes the result.")

## Stack unwinding: frames are left, finally blocks run

When an exception is raised, Python first looks for a handler in the current frame. If the frame has no matching `except`, Python leaves the frame, and the exception continues in the caller. The `finally` clause of each frame it leaves runs on the way out. The Python reference states the rule: "The exception is propagated to the invocation stack unless there is a `finally` clause which happens to raise another exception" (Python reference, the try statement).

Trace the example by hand. Five frames are active: `main_chain`, then `a`, `b`, `c` and `d`, where `d` divides by zero. `d` has no `except`, so its `finally` runs first, and `d` is left. Then `c`, `b` and `a` each run their `finally` and are left in turn. `main_chain` has an `except ZeroDivisionError`, so it catches the exception. The count of traceback entries is the number of frames the exception passed through, including the catching frame.

![Five stacked frames, main_chain at the top and d at the bottom; d raises; numbered finally boxes run from d up to a; the top frame has the except clause](diagrams/12.1-unwinding.svg "One exception passes five frames. Each finally runs before its frame is left.")

The code below reproduces the trace. It is the same logic as the hand trace, with a log of each step.

```python
import traceback

events = []

def d(x):
    try:
        events.append("enter d")
        return 1 / x                      # raises when x is 0
    finally:
        events.append("finally d")

def c(x):
    try:
        events.append("enter c")
        return d(x)
    finally:
        events.append("finally c")

def b(x):
    try:
        events.append("enter b")
        return c(x)
    finally:
        events.append("finally b")

def a(x):
    try:
        events.append("enter a")
        return b(x)
    finally:
        events.append("finally a")

def main_chain(x):
    try:
        return a(x)
    except ZeroDivisionError as exc:
        events.append("caught in main_chain")
        return len(traceback.extract_tb(exc.__traceback__))

entries = main_chain(0)
for i, event in enumerate(events, 1):
    print(f"{i:2d}. {event}")
print("traceback entries at the catch:", entries)
```

```output
 1. enter a
 2. enter b
 3. enter c
 4. enter d
 5. finally d
 6. finally c
 7. finally b
 8. finally a
 9. caught in main_chain
traceback entries at the catch: 5
```

The four `enter` lines run on the way down the stack. The four `finally` lines run on the way up, deepest frame first. The traceback at the catch has 5 entries: one per frame, including `main_chain`. The count is observed, not a rule stated in the docs. The docs say what happens to each frame, and the count follows from that.

The `finally` clause is for cleanup that must run whether or not an exception happened, such as closing a file or releasing a lock. The `else` clause is the opposite case: it runs only when the `try` block raised nothing, so it is the place for work that should happen only on success. Keep `try` blocks short, so that an unexpected exception cannot slip through code that was never meant to be covered.

## Common traps

> [!TRAP] A broad clause above a specific one hides the specific one.
> Python accepts `except Exception:` followed by `except ValueError:` without a `SyntaxError` (checked with `compile()`), and the second clause is never reached. Put the most specific clause first and the broadest last.

> [!TRAP] Bare `except:` and `except BaseException:` catch Ctrl+C.
> `KeyboardInterrupt` and `SystemExit` inherit from `BaseException`, not `Exception`. In the experiment, a `KeyboardInterrupt` got past `except Exception` and was caught only by `except BaseException`. Catch these at the top of a program, and re-raise them everywhere else.

> [!TRAP] A broad handler can hide a typo.
> In `total(xs)`, a misspelled name such as `len(xss)` raises `NameError`. `NameError` is a subclass of `Exception`, so `except Exception: return None` makes `total([1, 2, 3])` return `None` with no message. Catch the exceptions you expect, and log the rest.

> [!TRAP] `raise exc` adds a traceback entry; a bare `raise` does not.
> In the experiment, a function that caught `ZeroDivisionError` and used a bare `raise` left 3 traceback entries at the outer catch. The one that used `raise exc` left 4. The extra entry is a second line for the same function, the `raise exc` line. The Python reference says a bare `raise` "re-raises the exception that is currently being handled" (Python reference, the raise statement). Use a bare `raise` to keep the original traceback.

## Summary

- Built-in exceptions form a tree with `BaseException` at the root. `Exception` is the branch that ordinary errors use.
- `KeyboardInterrupt`, `SystemExit` and `GeneratorExit` sit outside `Exception`, so `except Exception` does not catch them.
- `except` clauses are tried top to bottom, and the first one whose class matches (including its subclasses) runs.
- An exception leaves each frame it passes through, and each frame's `finally` runs on the way out.
- A broad clause above a specific one, or a bare `raise` swapped for `raise exc`, changes the behaviour. Check the order and use bare `raise`.

## Quiz time

### Question 1: Prediction

What does this print?

```python
try:
    [][0]
except LookupError:
    print("lookup")
except IndexError:
    print("index")
```

<details><summary>Show Solution</summary>

It prints `lookup`. `IndexError` is a subclass of `LookupError`, so the first clause matches and runs. The second clause is never reached. Reversing the two clauses would print `index`.

</details>

### Question 2: Find the bug

```python
def average(xs):
    try:
        return sum(xs) / len(xs)
    except ZeroDivisionError:
        return 0
    except Exception:
        print("bad input")
    except ValueError:
        print("never printed")
```

<details><summary>Show Solution</summary>

`ValueError` is a subclass of `Exception`, so the broad `except Exception` clause catches it first, and the last clause is unreachable. Move `except ValueError` above `except Exception`. The code still runs with the bug, which is why it is easy to miss. The fix is the order of the clauses, not their content.

</details>

### Question 3: Calculation

`main` calls `a`, `a` calls `b`, and `b` calls `c`. `c` raises an exception that no function between them catches, and `main` has an `except` clause for it. How many traceback entries does `main`'s handler see?

<details><summary>Show Solution</summary>

Four: `main`, `a`, `b` and `c`. Each frame the exception passes through adds one entry, and the catching frame counts as well. The experiment has five frames (`main_chain` plus four calls) and reports 5.

</details>

### Question 4: Explanation

Why does `except Exception:` not catch `KeyboardInterrupt`, even though `KeyboardInterrupt` is a built-in exception?

<details><summary>Show Solution</summary>

`KeyboardInterrupt` inherits from `BaseException` directly, not from `Exception`. A clause that names `Exception` matches only that class and its subclasses. The Python documentation gives this reason: the class is placed outside `Exception` "so as to not be accidentally caught by code that catches `Exception`." Catch it with `except KeyboardInterrupt` or `except BaseException`, and only at the top level of a program.

</details>
