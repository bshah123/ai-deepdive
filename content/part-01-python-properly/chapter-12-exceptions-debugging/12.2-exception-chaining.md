A `raise` inside an `except` block does not erase the first error. Python links the two exception objects, and the traceback prints both. In this lesson you will use `raise ... from ...` to record which error caused which, predict the printed traceback for each form of re-raise, and walk a chain of exceptions in code.

**You need:** `try`/`except` and the exception hierarchy (Lesson 12.1).

## The problem chaining solves

A training script reads `learning_rate` from a configuration dictionary. When the key is missing, Python raises a `KeyError` whose message is only `'learning_rate'`. That is accurate, but it does not tell the person running the script that their configuration file is incomplete. The usual fix is to catch the low-level error and raise a domain error, `ConfigError`, that callers can handle without knowing about dictionaries.

That fix throws information away: the new exception does not carry the key name. Chaining keeps the original error attached to the new one.

The two readers need different things. The caller of `read_learning_rate` should catch `ConfigError` and report a problem with the configuration. The developer debugging the file needs to know which lookup failed. Chaining serves both: the caller catches one type, and the developer follows `__cause__` back to the original error.

![Two panels: with raise from e, the ConfigError has a __cause__ link and a __context__ link to the KeyError; a bare raise inside except has only the __context__ link](diagrams/12.2-two-links.svg "Two links from the new exception to the old one.")

## Worked example by hand

Trace `read_learning_rate({})` with the code below.

1. `config["learning_rate"]` raises `KeyError('learning_rate')`. Python enters the `except KeyError as e` clause, so this exception is now being handled.
2. `raise ConfigError(...) from e` runs. It sets `ConfigError.__cause__` to the `KeyError` and sets `__suppress_context__` to `True`.
3. Python also sets `__context__` to the `KeyError`, because a new exception was raised while one was being handled. Both links point to the same object.
4. Nothing in this script catches `ConfigError`, so the traceback shows the chain.

```python
class ConfigError(Exception):
    """A configuration value is missing or malformed."""

def read_learning_rate(config: dict) -> float:
    try:
        raw = config["learning_rate"]
        return float(raw)
    except KeyError as e:
        raise ConfigError("missing key: learning_rate") from e
    except ValueError as e:
        raise ConfigError(f"learning_rate is not a number: {raw!r}") from e

for config in [{"learning_rate": "0.01"}, {}, {"learning_rate": "fast"}]:
    try:
        print("lr =", read_learning_rate(config))
    except ConfigError as err:
        print(f"ConfigError: {err}")
        print(f"  __cause__: {type(err.__cause__).__name__}: {err.__cause__}")
```

```output
lr = 0.01
ConfigError: missing key: learning_rate
  __cause__: KeyError: 'learning_rate'
ConfigError: learning_rate is not a number: 'fast'
  __cause__: ValueError: could not convert string to float: 'fast'
```

Note that `str(err)` shows only the new message. The key name lives in `__cause__`, not in the text of `ConfigError`. The third config, `"fast"`, takes the `ValueError` branch instead: `float()` fails, and the message uses `repr` so the bad value appears in quotes.

## What the printout shows

When nothing catches the error, the interpreter prints every link. This traceback comes from a script with the same function plus a `main()` wrapper. The file paths are shortened to `chain_demo.py`; everything else is verbatim, from Python 3.12.

```text
Traceback (most recent call last):
  File "chain_demo.py", line 7, in read_learning_rate
    return float(raw)
           ^^^^^^^^^^
ValueError: could not convert string to float: 'fast'

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File "chain_demo.py", line 23, in <module>
    main()
  File "chain_demo.py", line 20, in main
    read_learning_rate({"learning_rate": "fast"})
  File "chain_demo.py", line 11, in read_learning_rate
    raise ConfigError(f"learning_rate is not a number: {raw!r}") from e
ConfigError: learning_rate is not a number: 'fast'
```

Read a chained traceback in two passes. Start at the bottom to find the exception your code finally raised, then go up through the cause links to find the first failure. Here the first failure is the `float()` call on line 7, and the final raise is on line 11 of the same function.

## Under the hood: which attributes are set

The four forms in the table differ in three attributes. Each value below was measured by running the code, not copied from the old lesson.

![Table with four rows, the forms from e, bare raise, from None and no handler, and columns for __cause__, __context__, suppress and the printed message](diagrams/12.2-attribute-grid.svg "Attributes of the new exception, by form. Values from the experiment in this lesson.")

- `raise X from Y` sets `X.__cause__ = Y`. The expression after `from` must be an exception class or instance, as the Python reference states. Setting `__cause__` also sets `__suppress_context__` to `True` (PEP 415).
- A `raise` inside a handler sets `__context__` automatically, and leaves `__cause__` as `None` (PEP 3134).
- `raise X from None` sets `__cause__` to `None` and `__suppress_context__` to `True`, so the printer does not show the context.

The suppress flag controls display, not the link. After `from None`, `__context__` still refers to the original exception, as the output of the next example shows. Only the printed traceback hides it.

The printer follows `__cause__` first. If there is no cause, it follows `__context__` unless the suppress flag is set. The standard `traceback` module does exactly this. In CPython 3.12, the logic sits in `traceback.py` near lines 786 to 836.

![Flowchart: follow __cause__ if it is set; otherwise follow __context__ unless __suppress_context__ is True; stop when there is nothing left](diagrams/12.2-chain-walk.svg "How the traceback printer picks the next link.")

Three functions give a three-link chain. The root cause is the file error, and the top-level error is the one the program finally reports.

![Three stacked boxes: RuntimeError, ConfigError and OSError, each linked to the one below by a __cause__ arrow, with the function that raised each one](diagrams/12.2-three-level.svg "Each function raises from the exception it caught.")

The same shape appears in training code around files. A checkpoint loader that calls `open()` receives an `OSError`. It should raise a project error such as `CheckpointError` from that exception, so the training loop catches one type while the traceback still points to the file that failed.

The standard printer also keeps a set of exceptions it has already seen (`_seen` in `traceback.py`), so a cyclic chain cannot make it loop. The walk below has no such guard, so it assumes the chain has no cycles. Your code can walk the chain with the same rule:

```python
class ConfigError(Exception):
    pass

def open_file():
    raise OSError("config.toml not found")

def load_config():
    try:
        open_file()
    except OSError as e:
        raise ConfigError("cannot load config") from e

def start_training():
    try:
        load_config()
    except ConfigError as e:
        raise RuntimeError("training did not start") from e

def walk(exc):
    """Follow the links the traceback printer follows, top to bottom."""
    chain = []
    while exc is not None:
        chain.append(f"{type(exc).__name__}({exc})")
        if exc.__cause__ is not None:
            exc = exc.__cause__
        elif exc.__suppress_context__:
            exc = None
        else:
            exc = exc.__context__
    return chain

try:
    start_training()
except RuntimeError as top:
    for link in walk(top):
        print(link)
```

```output
RuntimeError(training did not start)
ConfigError(cannot load config)
OSError(config.toml not found)
```

Compare the bare `raise` with `from None`, using the same missing key. Both leave `__cause__` empty, but only the bare `raise` keeps the context visible in the printed traceback:

```python
class ConfigError(Exception):
    pass

def read_implicit(config):
    try:
        return config["learning_rate"]
    except KeyError:
        raise ConfigError("missing key: learning_rate")

def read_from_none(config):
    try:
        return config["learning_rate"]
    except KeyError:
        raise ConfigError("missing key: learning_rate") from None

for fn in (read_implicit, read_from_none):
    try:
        fn({})
    except ConfigError as err:
        print(fn.__name__, "cause:", err.__cause__, "context:", type(err.__context__).__name__, "suppress:", err.__suppress_context__)
```

```output
read_implicit cause: None context: KeyError suppress: False
read_from_none cause: None context: KeyError suppress: True
```

## Common traps

> [!TRAP]
> **`from` takes an exception, not a message.** Writing `raise ConfigError("missing key") from "KeyError: learning_rate"` raises `TypeError: exception causes must derive from BaseException` instead. Pass the caught object with `from e`.

> [!TRAP]
> **A bare `raise` still chains.** Its `__cause__` is `None`, so code that reads only `err.__cause__`, such as a logger, sees nothing. The `KeyError` is still in `err.__context__`, and the traceback prints it under "During handling of the above exception, another exception occurred:".

> [!TRAP]
> **`from None` hides the middle of a chain.** If a `raise ... from None` sits in the middle of a three-level chain, the walk stops there and the deepest exception is never printed. Use it only when the original error is noise.

> [!TRAP]
> **Chaining does not copy messages.** `str(err)` shows `missing key: learning_rate`, not the `KeyError`'s text. A caller that logs only `str(err)` loses the cause. Put the important detail in your own message, or log the full traceback.

## Summary

- `raise X from Y` sets `X.__cause__ = Y` and `__suppress_context__ = True`. The traceback prints `Y` first, then `X`.
- A `raise` inside an `except` sets only `__context__`, and the traceback prints it under "During handling of the above exception, another exception occurred".
- `raise X from None` clears `__cause__` and hides the context.
- The printer follows `__cause__` first, then `__context__` unless it is suppressed. Your code can walk the chain the same way.
- A rule of thumb follows from the table: default to `from e`, and reach for `from None` only when the low-level error is noise.

## Quiz time

### Question 1: Prediction

Inside an `except KeyError:` block, the code runs `raise ConfigError("missing")` with no `from`. What are `err.__cause__`, `type(err.__context__).__name__` and `err.__suppress_context__`?

<details><summary>Show Solution</summary>

They are `None`, `KeyError` and `False`. A bare `raise` inside a handler sets only `__context__`, and it does not suppress it.

</details>

### Question 2: Bug-spotting

What does this code print, and why?

```python
class ConfigError(Exception):
    pass

try:
    try:
        {}["learning_rate"]
    except KeyError:
        raise ConfigError("missing key") from "KeyError: learning_rate"
except TypeError as err:
    print(err)
```

<details><summary>Show Solution</summary>

It prints `exception causes must derive from BaseException`. The expression after `from` is a string, so the interpreter raises `TypeError` while handling the `KeyError`. The fix is to bind the caught exception and pass it: `except KeyError as e:` followed by `raise ConfigError("missing key") from e`.

</details>

### Question 3: Explanation

Why does the printed traceback for a `raise ... from e` chain show the `ValueError` before the `ConfigError`?

<details><summary>Show Solution</summary>

The `ValueError` happened first, and it is the cause. The printer shows the cause, then the message "The above exception was the direct cause of the following exception:", then the exception raised by your code. Reading top to bottom follows the order in which the errors happened.

</details>

### Question 4: Calculation

Suppose `A.__cause__ = B`, and `B` was raised with `from None` while handling `C`. What does `walk(A)` return, using the function from this lesson?

<details><summary>Show Solution</summary>

It returns two entries, one for `A` and one for `B`, each in the `Type(message)` form that `walk` builds. `walk` follows `A.__cause__` to `B`. `B.__cause__` is `None` and `B.__suppress_context__` is `True`, so the walk stops. `C` is never visited, because `from None` suppressed it.

</details>
