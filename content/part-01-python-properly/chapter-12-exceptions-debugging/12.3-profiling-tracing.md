# 12.3 — Profiling & Tracing with cProfile and sys.settrace

## Motivation & Context

Performance matters—especially in AI, HPC, and production systems where milliseconds translate to dollars or user churn. Profiling reveals *where* your code spends time, while tracing shows *how* it executes. Together, they’re the difference between guessing and knowing.

In this lesson, you’ll master Python’s built-in tools:
- **cProfile**: a deterministic profiler that records function calls, time, and cumulative time.
- **sys.settrace**: a low-level hook to intercept every line, call, and return—ideal for custom tracing, debugging, or even security auditing.

These tools are indispensable when optimizing ML pipelines, web servers, or embedded systems where latency is critical.

---

## Core Concepts Breakdown

> [!KEY-INSIGHT]
> **Profiling** measures *what* your code does; **tracing** measures *how* it does it.
> Profiling answers: “Which function is slow?”
> Tracing answers: “Which line caused the slowdown?”

> [!BEST-PRACTICE]
> Always profile before optimizing. Use `cProfile` first to identify hotspots, then use `sys.settrace` for fine-grained inspection of suspicious functions.

> [!WARNING]
> Avoid `sys.settrace` in production—it adds massive overhead (up to 100x slowdown). Use only in development or controlled environments.

## ## Code Demonstration & Runtime Output

```python
# demo_profiling_tracing.py
import cProfile
import sys
import time
from typing import List, Callable

def fibonacci_recursive(n: int) -> int:
    """Naive recursive Fibonacci—intentionally slow for demo."""
    if n <= 1:
        return n
    return fibonacci_recursive(n - 1) + fibonacci_recursive(n - 2)

def fibonacci_iterative(n: int) -> int:
    """Fast iterative Fibonacci."""
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

def heavy_computation(n: int) -> float:
    """Simulate a CPU-heavy task."""
    total = 0.0
    for i in range(n):
        total += (i ** 0.5) * (i % 7)
    return total

def trace_calls(frame, event: str, arg):
    """Custom tracer: logs every call, line, and return."""
    if event == "call":
        func_name = frame.f_code.co_name
        file_name = frame.f_code.co_filename
        line_no = frame.f_lineno
        print(f"[CALL] {file_name}:{line_no} -> {func_name}")
    elif event == "line":
        print(f"[LINE] {frame.f_code.co_name}:{frame.f_lineno}")
    elif event == "return":
        print(f"[RETURN] {frame.f_code.co_name} -> {arg}")
    return trace_calls  # Must return tracer for continuation

def run_profiling_and_tracing():
    """Run both profiling and tracing on a mixed workload."""
    # Profiling
    profiler = cProfile.Profile()
    profiler.enable()

    # Simulate a workload
    fib_rec = fibonacci_recursive(5)
    fib_iter = fibonacci_iterative(20)
    heavy = heavy_computation(10_000)

    profiler.disable()
    profiler.print_stats(sort="cumulative")

    # Tracing
    print("\n--- Tracing Execution ---")
    sys.settrace(trace_calls)
    fib_rec = fibonacci_recursive(3)  # Smaller to avoid spam
    sys.settrace(None)  # Disable tracing

if __name__ == "__main__":
    run_profiling_and_tracing()
```

## > [!ADVANCED]

Under the hood, `cProfile` uses the `sys.setprofile` hook, which taps into CPython’s call stack machinery. It records:
- `call`, `return`, `c_call`, `c_return`, `exception` events.
- Timestamps via `time.perf_counter()`.
- Function names via `frame.f_code.co_name`.

`sys.settrace` is even lower-level: it hooks into the interpreter’s **line-by-line execution loop**, governed by the **frame object** and **bytecode evaluation**. You can inspect:
- `frame.f_lasti`: index of last executed bytecode.
- `frame.f_code.co_code`: raw bytecode array.
- `dis` module reveals opcodes like `LOAD_FAST`, `CALL_FUNCTION`, `RETURN_VALUE`.

Memory layout: each `frame` object is a C struct (`PyFrameObject`) containing:
```c
typedef struct {
    PyObject_HEAD
    PyObject *f_back;        // previous frame
    PyCodeObject *f_code;    // code object
    PyObject *f_globals;     // globals dict
    PyObject *f_locals;      // locals dict
    ...
    int f_lasti;             // last instruction index
} PyFrameObject;
```

## > [!QA]

**Q: When should I prefer `cProfile` over `sys.settrace`?**
A: Use `cProfile` for **performance profiling**—it’s fast, deterministic, and gives you call counts and cumulative time. Use `sys.settrace` only when you need **semantic insight**—e.g., tracking data flow, logging every variable change, or debugging complex control flow. `sys.settrace` is 10–100x slower and should never run in production.

## ## Summary & Key Takeaways

- **Profiling** (`cProfile`) measures *time spent* in functions.
- **Tracing** (`sys.settrace`) measures *execution flow* line-by-line.
- Always profile first to find hotspots.
- Use `sys.settrace` sparingly—it’s a debugging tool, not a profiler.
- Disable tracing immediately after use to avoid performance degradation.
- Understand the frame object and bytecode to write advanced tracers.

### Question #3: Find and fix the bug

```python
import sys

def tracer(frame, event, arg):
    if event == "call":
        print(f"Called: {frame.f_code.co_name}")
    return tracer

def slow():
    total = 0
    for i in range(1000000):
        total += i
    return total

sys.settrace(tracer)
slow()
sys.settrace(None)
```

<details>
<summary>Show Solution</summary>

The bug: the tracer is never disabled, so it remains active even after `slow()` returns. This can interfere with subsequent code. Fix: disable tracing immediately after use.

**Fixed code:**
```python
import sys

def tracer(frame, event, arg):
    if event == "call":
        print(f"Called: {frame.f_code.co_name}")
    return tracer

def slow():
    total = 0
    for i in range(1000000):
        total += i
    return total

sys.settrace(tracer)
result = slow()
sys.settrace(None)  # <-- Added
print(result)
```
</details>
