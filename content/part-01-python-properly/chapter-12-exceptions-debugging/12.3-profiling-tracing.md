By the end of this lesson you will count the calls a function makes with `cProfile`, read the event stream that `sys.settrace` produces, and know what each costs. Profiling tells you where a program spends its effort. Tracing tells you what the program does, one event at a time.

**You need:** recursion and the call stack (Lesson 7.4).

## The problem

A program is slow. Which function is responsible? Guessing is unreliable, and the answer is often not what you expect. Consider the naive recursive Fibonacci function `fib(n)`, which returns the $n$-th Fibonacci number $F(n)$, defined by $F(0)=0$, $F(1)=1$, $F(n)=F(n-1)+F(n-2)$. It makes 242,785 calls for `fib(25)`. Nothing in the source code shows that number. You have to measure it.

Profiling answers "how many times did each function run, and how long did it take in total?" Tracing answers "what happened, in what order, line by line?"

## Intuition: one event stream, two hooks

When CPython (the standard Python interpreter) runs code, it emits events: a function is `call`ed, a line is about to run, a function `return`s, an exception is raised. A hook is a function the interpreter calls for each event. Both tools are hooks on the same stream. They differ in which events they receive and what they do with them.

![The interpreter emits call, line, return and exception events; cProfile receives only call and return and keeps counts and times, while sys.settrace receives every event and runs your own function](diagrams/12.3-hooks.svg "Two hooks on one event stream. Only sys.settrace sees individual lines.")

## Worked example by hand: fib(3)

`fib(3)` calls `fib(2)` and `fib(1)`. `fib(2)` calls `fib(1)` and `fib(0)`. Count the calls in start order: `fib(3)`, `fib(2)`, `fib(1)`, `fib(0)`, `fib(1)`. That is five calls, and `fib(1)` appears twice.

![A call tree: fib(3) at the top with fib(2) and fib(1) below; fib(2) has fib(1) and fib(0) below it. The numbers give the start order and the returned value.](diagrams/12.3-fib3-tree.svg "Each node is one call, numbered in the order it starts. The right-hand fib(1) repeats work the left one already did.")

The formula confirms the count. Let $C(n)$ be the number of calls made by `fib(n)`. Then $C(0)=C(1)=1$ and $C(n)=C(n-1)+C(n-2)+1$ for $n\ge 2$. Assume $C(n)=2F(n+1)-1$ holds for $n-1$ and $n-2$. Then $C(n)=2F(n)-1+2F(n-1)-1+1=2F(n+1)-1$, so the formula holds for every $n \ge 0$ by induction. For $n=3$: $2F(4)-1=2\cdot 3-1=5$.

## Measure the calls with cProfile

`cProfile` is a deterministic profiler: it sees every call and return, so its call counts are exact. Its timing columns are not reproducible from run to run, but its call counts are. This block counts calls, not time, so its output is the same every run.

```python
import cProfile
import pstats

def fib(n):
    """Naive recursion: each call makes two more calls."""
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

def fib_loop(n):
    """Iterative version: one call, n loop steps."""
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

def count_calls(fn, n):
    """Return (total calls, primitive calls) of fn(n), as cProfile counts them."""
    profiler = cProfile.Profile()
    profiler.enable()
    fn(n)
    profiler.disable()
    for (filename, line, name), (cc, nc, tt, ct, callers) in pstats.Stats(profiler).stats.items():
        if name == fn.__name__:
            return nc, cc
    raise RuntimeError(f"{fn.__name__} not in profile")

for n in (5, 10, 15, 20):
    total, primitive = count_calls(fib, n)
    expected = 2 * fib_loop(n + 1) - 1          # closed form: 2*F(n+1) - 1
    loop_total, _ = count_calls(fib_loop, n)
    print(f"n={n:2d}  fib calls={total:6d} (primitive {primitive})  formula={expected:6d}  fib_loop calls={loop_total}")
    assert total == expected
```

```output
n= 5  fib calls=    15 (primitive 1)  formula=    15  fib_loop calls=1
n=10  fib calls=   177 (primitive 1)  formula=   177  fib_loop calls=1
n=15  fib calls=  1973 (primitive 1)  formula=  1973  fib_loop calls=1
n=20  fib calls= 21891 (primitive 1)  formula= 21891  fib_loop calls=1
```

The "primitive" count is the number of calls that were not made by the function itself recursing. The full `pstats` report writes the same quantity as `ncalls = 15/1`: 15 total calls, 1 primitive. The loop version makes one call however large $n$ is. The cost moves into the loop body, where the profiler cannot see it.

![Bars of naive fib call counts for n = 5, 10, 15, 20, 25: 15, 177, 1,973, 21,891 and 242,785 calls. Each step of n multiplies the count by about 1.618.](diagrams/12.3-call-counts.svg "Naive recursion grows like the golden ratio, about 1.618 per step of n. The loop version stays at one call.")

## Trace every event with sys.settrace

`sys.settrace(f)` installs a global trace function `f`. The interpreter calls `f` with the event `'call'` whenever a new function starts. What `f` returns decides what happens next. The Python documentation puts it this way: the trace function "should return a reference to a local trace function to be used for the new scope, or `None` if the scope shouldn't be traced." So `f` must return itself, or a function, to receive `'line'`, `'return'` and `'exception'` events for that frame. Returning `None` skips the frame's line events.

```python
import sys

def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

log = []

def tracer(frame, event, arg):
    n = frame.f_locals.get("n")
    if event == "call":
        log.append(f"call   fib({n})")
        return tracer                     # ask for 'line' and 'return' events in this frame
    if event == "line":
        log.append(f"  line {frame.f_lineno}")
    elif event == "return":
        log.append(f"return {arg}")
    return tracer

sys.settrace(tracer)
result = fib(3)
sys.settrace(None)
print("\n".join(log))
print("result:", result)
```

```output
call   fib(3)
  line 4
  line 6
call   fib(2)
  line 4
  line 6
call   fib(1)
  line 4
  line 5
return 1
call   fib(0)
  line 4
  line 5
return 0
return 1
call   fib(1)
  line 4
  line 5
return 1
return 2
result: 2
```

Read the log against the call tree. Five `call` lines, five `return` lines, and two `line` events for each call that reaches the `return` (line 4 is the `if`, line 5 is `return n`, line 6 is the recursive `return`). That makes 10 line events for `fib(3)`, and 20 events in all with the calls and returns. `fib(1)` appears twice because the program calls it twice. The tracer records what the interpreter did, not what you intended.

## What it costs

Both hooks add work to every event. The cost depends on how many events each hook receives and how much work the hook does per event. We measured `fib(22)`, which makes 57,313 calls, with the same function under four conditions. The table gives the multiplier over the run with no hook. Timings come from one machine (Python 3.12.13, best of 5 runs), and the ratios moved by a few tenths between runs. The event counts do not move.

![Horizontal bars: no hook 1x, cProfile 3.8x, settrace with call events only 4.1x, settrace with call, line and return 11.8x, on fib(22)](diagrams/12.3-overhead.svg "Overhead on a call-heavy workload. The tracer that receives every line costs about three times more than the profiler.")

The Python documentation describes `cProfile`'s C implementation as having low overhead in typical applications. A function as small as `fib` is the worst case: almost all the time is the call itself, so the hook dominates. That is why the measured ratio here is larger than the documentation's typical figure.

<details>
<summary>Run locally: timing code (standard library only; timings vary by machine)</summary>

```python
import sys, time

def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

N = 22
def best(fn, reps=5):
    times = []
    for _ in range(reps):
        t0 = time.perf_counter(); fn(); times.append(time.perf_counter() - t0)
    return min(times)

def run_none():
    fib(N)

def run_calls_only():
    sys.settrace(lambda frame, event, arg: None)   # global trace only: 'call' events
    fib(N)
    sys.settrace(None)

def run_all_events():
    def t(frame, event, arg):
        return t                                     # local trace: call, line, return
    sys.settrace(t)
    fib(N)
    sys.settrace(None)

base = best(run_none)
print(f"no hook: {base*1000:.2f} ms")
print(f"settrace, call events only: x{best(run_calls_only)/base:.1f}")
print(f"settrace, call+line+return: x{best(run_all_events)/base:.1f}")
```

```text
Output on one run (this machine, Python 3.12.13); your numbers will differ:
no hook: 2.02 ms
settrace, call events only: x4.1
settrace, call+line+return: x11.8
```

</details>

## Under the hood

`cProfile` installs its own C-level profile hook. Two checks on Python 3.12 show this. While a `cProfile.Profile` is enabled, `sys.getprofile()` returns `None`, so the hook is not visible through the public Python-level API. The Python documentation for `sys.setprofile` lists the events a profile function receives: `call`, `return`, `c_call`, `c_return` and `c_exception`. The `c_` events report calls into C functions. In a probe run, the `cProfile` stats also listed built-ins such as `print`, so the profiler sees calls into C as well as Python functions.

`sys.settrace` is not per process. It is per thread. The documentation says the trace function "is thread-specific". In our run, a tracer set in the main thread saw zero events from a worker thread. To trace new threads, use `threading.settrace`.

Python 3.12 added `sys.monitoring` (Python Enhancement Proposal 669, PEP 669). It lets a tool subscribe only to the events it needs, and the proposal reports much lower overhead than `sys.settrace` when few events are enabled. We do not use it here. Treat it as the modern option for new tooling, not as a replacement you need to learn for this chapter.

## Common traps

> [!TRAP]
> A tracer that returns `None` on `'call'` receives no `'line'` events for that frame. Our bug probe in the quiz gives zero line events for `fib(3)`. Return the tracer itself from `'call'`.

> [!TRAP]
> `sys.settrace` affects only the thread that calls it. A worker thread started afterwards runs untraced. We measured zero worker-thread events. Use `threading.settrace` for threads you create.

> [!TRAP]
> If you do not call `sys.settrace(None)`, the trace function stays active and slows every later call. Wrap the traced region in `try`/`finally` so the reset always runs.

> [!TRAP]
> Do not compare two versions of a function by one `cProfile` timing run. The profiler slows the code by several times, and the timing columns move between runs. Compare call counts, or time the code with no profiler attached.

> [!TRAP]
> The overhead of a tracer depends on what the tracer does. Our tracer only increments a counter. A tracer that formats strings or prints each line costs more. We did not measure that case, so treat any single multiplier as specific to the tracer that produced it.

## Summary

- `cProfile` counts calls and time per function. Its call counts are exact, and its timings are not reproducible.
- `sys.settrace` receives `call`, `line`, `return` and `exception` events. Your tracer decides what to record, and returning the tracer itself from `'call'` enables line events.
- Naive recursive `fib(n)` makes $2F(n+1)-1$ calls. The loop version makes one.
- Both tools slow the program down. The tracer that receives every line costs about 12 times on `fib(22)` in our run, and the profiler about 4 times.
- Trace per thread, and reset the trace function in a `finally` block.

### Question 2: Prediction
A tracer records only `'call'` events and returns `None` for every other event. What does the following code print?

```python
import sys

def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

calls = []

def tracer(frame, event, arg):
    if event == "call":
        calls.append(frame.f_code.co_name)
        return tracer
    return None

sys.settrace(tracer)
fib(2)
sys.settrace(None)
print("call events:", len(calls), calls)
```

<details>
<summary>Show solution</summary>

```text
call events: 3 ['fib', 'fib', 'fib']
```

`fib(2)` makes three calls: `fib(2)`, `fib(1)` and `fib(0)`. This tracer returns `tracer` on `'call'`, so the global trace receives every call. It returns `None` for the other events, and the `'line'` and `'return'` branches never run.
</details>

### Question 3: Find the bug
A student wants to count the line events raised while `fib(3)` runs:

```python
import sys

def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

seen = []

def tracer(frame, event, arg):
    if event == "call":
        return None
    if event == "line":
        seen.append(frame.f_lineno)
    return tracer

sys.settrace(tracer)
fib(3)
sys.settrace(None)
print("line events:", len(seen))
```

The output is `line events: 0`. Why, and what is the fix?

<details>
<summary>Show solution</summary>

On `'call'`, the tracer returns `None`. That tells the interpreter not to trace the new frame locally, so no `'line'` events arrive for it. The `'line'` branch is never reached for any `fib` frame. The fix is to return `tracer` from the `'call'` branch. With that change the program prints `line events: 10`, which matches the trace of `fib(3)` above: 5 calls, each with two line events.
</details>

### Question 4: Explain
Two versions of a function take 1.8 s and 2.1 s under `cProfile`. Give one reason the timing difference may not mean the second version is slower, and one measurement that would settle it.

<details>
<summary>Show solution</summary>

The profiler adds its own overhead to each call, and the overhead is larger for functions with many small calls. A version with more calls can therefore look slower under the profiler than it is without it. The timing columns also vary from run to run. A settling measurement is the call counts for both versions, followed by repeated timings with no profiler attached (best of several runs).
</details>
