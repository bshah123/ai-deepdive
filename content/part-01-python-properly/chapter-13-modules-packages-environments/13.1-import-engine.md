When you write `import x`, Python does not read and run a file every time. It first looks in `sys.modules`, a dictionary that caches modules by name, and does the expensive work only when the name is missing. In this lesson you will trace that path step by step, predict how many times a module's code runs, and check each prediction with code.

**You need:** how a Python file runs top to bottom (Lesson 1.2) and what `sys.path` is (Lesson 1.4).

## The problem: one module, many importers

A real program imports the same module from many files. Running a module means executing its body, the top-to-bottom code that defines functions and may also open a file, connect to a database or register a plugin. If every `import` re-ran the body, a program that imports `os` in 200 files would run the `os` setup 200 times.

Python keeps one rule instead: the body runs once per process, and every importer gets the same **module object**, the Python object that holds the names the file defines.

## The fast path: the cache

![Flowchart: import x checks sys.modules first; on a hit it returns the cached object; on a miss it finds, creates, stores and runs the module](diagrams/13.1-import-flow.svg "What import x does, in order. Steps 1 to 4 run only on a cache miss.")

The lookup key is the fully qualified name: for a submodule, the full dotted path such as `pkgdemo.sub`. The Python import reference calls `sys.modules` "the first place checked during import search", and says that when the name is present, "the associated value is the module satisfying the import, and the process completes" (Python Software Foundation, import reference, section 5.3.1). On a hit, nothing is searched and no code runs.

The `import` statement reaches this check through `__import__`, which calls `_gcd_import`. The `_gcd_import` docstring says it is shared with `importlib.import_module`, and it calls `_find_and_load`, where the cache check happens (CPython 3.12.13 source, `Lib/importlib/_bootstrap.py`). So the statement and the function take the same path, and the cost of a hit is one dictionary lookup plus a few Python function calls.

## Worked example: three imports by hand

Suppose `greeter.py` has a body that adds 1 to a counter and sets `VALUE = 42`. The counter lives in `builtins`, a module that is always loaded, so it survives whatever happens to `greeter`. Trace three statements, `import greeter` each time:

- **Import 1.** `'greeter'` is not in `sys.modules`. The engine searches (1 search), creates the module object, stores it under `'greeter'`, runs the body (counter 1), and returns the object.
- **Import 2.** The key is present. No search, no body run, and the same object comes back.
- **Import 3.** Same as import 2.

The prediction is 1 search, 1 body run, and one object. The code below checks it. The `SpyFinder` is an object placed first in `sys.meta_path`, the list of finders the engine consults on a miss. It counts calls for one name and returns `None`, which means "not mine", so the normal search goes on.

```python
import builtins
import importlib
import sys
import tempfile
from pathlib import Path

workdir = Path(tempfile.mkdtemp())            # scratch folder for demo modules
sys.path.insert(0, str(workdir))
(workdir / "greeter.py").write_text(
    "import builtins\n"
    "builtins.GREET_RUNS = getattr(builtins, 'GREET_RUNS', 0) + 1\n"
    "VALUE = 42\n"
)

class SpyFinder:
    """Counts searches for 'greeter'; declines every name so the real search continues."""
    calls = 0
    def find_spec(self, fullname, path=None, target=None):
        if fullname == "greeter":
            SpyFinder.calls += 1
        return None                            # None means "not mine"

sys.meta_path.insert(0, SpyFinder())
importlib.invalidate_caches()

for i in range(1, 4):
    before = SpyFinder.calls
    mod = importlib.import_module("greeter")
    print(f"import #{i}: searches={SpyFinder.calls - before}, body runs so far={builtins.GREET_RUNS}")
print("VALUE =", mod.VALUE)
print("'greeter' in sys.modules:", "greeter" in sys.modules)
print("same object as sys.modules['greeter']:", sys.modules["greeter"] is mod)
```

```output
import #1: searches=1, body runs so far=1
import #2: searches=0, body runs so far=1
import #3: searches=0, body runs so far=1
VALUE = 42
'greeter' in sys.modules: True
same object as sys.modules['greeter']: True
```

Read the output line by line. Line 1 is the only search: the spy counted one call, and the body counter moved from 0 to 1 in the same import. Lines 2 and 3 show zero searches and the counter still at 1, so the body did not run again. The last line confirms that the name maps to the object the first import created.

![Table of three imports: one finder search and one body run on import 1, none on imports 2 and 3; the same object every time](diagrams/13.1-trace.svg "The counts from the code above: all the work happens on the first import.")

## Store first, then run

On a miss, the engine stores the new module in `sys.modules` before it runs the body. The reference explains why: "The module will exist in sys.modules before the loader executes the module code. This is crucial because the module code may (directly or indirectly) import itself" (import reference, section 5.4). If module A imports B and B imports A, the second import finds A in the cache, half-built, and returns it rather than starting the load again. The code below shows the entry existing while the body runs.

If the body raises an exception, the engine deletes that module's entry and re-raises. The reference says that "the failing module – and only the failing module – gets removed" (section 5.4), and the CPython source does exactly this in `_load_unlocked` (CPython 3.12.13, `Lib/importlib/_bootstrap.py`). The second block shows a failed import being retried, and a `None` entry blocking an import.

```python
import importlib
import sys
import tempfile
from pathlib import Path

workdir = Path(tempfile.mkdtemp())            # scratch folder for demo modules
sys.path.insert(0, str(workdir))
(workdir / "selfaware.py").write_text(
    "import sys\n"
    "print('  in sys.modules during its own body:', 'selfaware' in sys.modules)\n"
)
(workdir / "broken.py").write_text(
    "print('  broken.py body runs')\n"
    "raise RuntimeError('boom')\n"
)

importlib.import_module("selfaware")

for attempt in (1, 2):
    try:
        importlib.import_module("broken")
    except RuntimeError as err:
        print(f"attempt {attempt}: RuntimeError({err})")
print("'broken' in sys.modules:", "broken" in sys.modules)

sys.modules["ghost"] = None                   # plant a None entry by hand
try:
    importlib.import_module("ghost")
except ModuleNotFoundError as err:
    print("ghost:", err)
```

```output
  in sys.modules during its own body: True
  broken.py body runs
attempt 1: RuntimeError(boom)
  broken.py body runs
attempt 2: RuntimeError(boom)
'broken' in sys.modules: False
ghost: import of ghost halted; None in sys.modules
```

The second attempt runs the body again because the failed entry was removed. A `None` entry works differently. The CPython source checks for `None` on a cache hit and raises `ModuleNotFoundError` with the message shown (`_find_and_load`, same file).

## Cache miss: where the search goes

On a miss, the engine walks `sys.meta_path` in order and asks each finder's `find_spec()` method whether it can locate the name. Each one returns a module spec, which describes where the code lives, or `None`. The default list has three finders: one for built-in modules, one for frozen modules, and `PathFinder`, the path-based finder that searches `sys.path` (import reference, section 5.3.4).

`PathFinder` walks `sys.path` from the first entry to the last. For each directory it gets a path-entry finder from `sys.path_hooks` and caches the result in `sys.path_importer_cache`, so the hooks run once per directory (section 5.5; `sys` module reference). The first directory with a match wins, even when a later one has a file with the same name.

![Three sys.path entries stacked top to bottom: the first holds helper_mod.py and stops the search; the two below it are never reached](diagrams/13.1-search-order.svg "The search stops at the first match, so list order decides which file you get.")

The next block sets that up with two folders that both hold `helper_mod.py`, and shows a dotted name importing its parent package first.

```python
import importlib
import sys
import tempfile
from pathlib import Path

root = Path(tempfile.mkdtemp())
dir_a, dir_b = root / "dir_a", root / "dir_b"
for folder, tag in ((dir_a, "dir_a"), (dir_b, "dir_b")):
    folder.mkdir()
    (folder / "helper_mod.py").write_text(f"WHERE = '{tag}'\n")
(root / "pkgdemo").mkdir()
(root / "pkgdemo" / "__init__.py").write_text("")
(root / "pkgdemo" / "sub.py").write_text("NAME = 'sub'\n")

# dir_a comes first on sys.path, so its helper_mod.py wins
sys.path[0:0] = [str(dir_a), str(dir_b), str(root)]
importlib.invalidate_caches()
print("helper_mod comes from:", importlib.import_module("helper_mod").WHERE)

importlib.import_module("pkgdemo.sub")
print("cache keys:", sorted(k for k in sys.modules if k.startswith("pkgdemo")))
```

```output
helper_mod comes from: dir_a
cache keys: ['pkgdemo', 'pkgdemo.sub']
```

The second output shows that the cache holds the intermediate path too. The reference says the mapping caches "all modules that have been previously imported, including the intermediate paths" (section 5.3.1). Importing `pkgdemo.sub` imports `pkgdemo` first, because the child cannot be located without its parent's `__path__` (CPython source, `_find_and_load_unlocked`).

## What a cache hit saves

I measured both paths once with the experiment script in the course repository (`scripts/diagrams/lessons/13.1_experiment.py`). The machine was an Apple-silicon Mac running Python 3.12.13. The median first import of a fresh one-line module, over 200 different modules, took 240 µs (microseconds). The median cache hit, taken over seven batches of 100,000 calls, took 321 ns (nanoseconds). That is about 750 times less.

![Log-scale bars: a first import takes 240 microseconds; a cache hit takes 321 nanoseconds](diagrams/13.1-timing.svg "One run on one machine. Read the gap, not the exact values.")

These are one run's numbers. Hardware, load and the file system all change them. The claim you can rely on is that a cache hit is orders of magnitude cheaper than a first import, because the hit skips the search, the file read and the body.

## Common traps

> [!TRAP]
> Setting `sys.modules[name] = None` does not "unload" a module. Every later `import name` raises `ModuleNotFoundError`, as the second block shows. The `sys.modules` documentation warns that replacing the dictionary "will not necessarily work as expected" and that deleting essential items "may cause Python to fail" (`sys` module reference).

> [!TRAP]
> Deleting a cache entry does not reload code in place. In the experiment, after `del sys.modules['greeter']` the next import returned a new object. Anything still holding the old object keeps the old state.

> [!TRAP]
> A file named like a standard-library module can hide the real one. If your folder comes earlier on `sys.path` and the real module is not already in `sys.modules`, `import statistics` loads your file. The first-match rule from the search block is the cause.

> [!TRAP]
> Each Python process has its own `sys.modules`. A cache built in one process does nothing for another, so a benchmark that imports in one process and times in another measures the wrong thing.

## Summary

- `import x` checks `sys.modules` first. On a hit, it returns the stored object without searching or running code.
- On a miss, the `sys.meta_path` finders run in order. `PathFinder` searches `sys.path`, and the first match wins.
- The engine stores the module before running its body, which lets circular imports see a half-built module. A failed body removes only its own entry.
- A `None` entry in `sys.modules` makes every import of that name raise `ModuleNotFoundError`.

## Quiz time

### Question 1: Prediction

After `import greeter` has run once in a process, another file runs `import greeter`. What happens?

<details><summary>Show Solution</summary>

The engine finds `'greeter'` in `sys.modules` and returns the stored object. No finder runs, the body does not run again, and the result is the same object as the first import. This is the cache hit from the first block (import #2 and #3).

</details>

### Question 2: Calculation

`sys.path` is `[A, B, C]`. Folder A has no `util.py`. Folders B and C both contain a `util.py`. Which file is imported?

<details><summary>Show Solution</summary>

The one in B. `PathFinder` searches `sys.path` in order and stops at the first directory with a match, so C's copy is never read. This is the same rule as `dir_a` winning in the search block.

</details>

### Question 3: Bug-spotting

```python
import sys
sys.modules["json"] = None
import json
```

What does this raise, and why?

<details><summary>Show Solution</summary>

It raises `ModuleNotFoundError: import of json halted; None in sys.modules`. The `json` entry in the cache is `None`. The engine's cache check sees `None` and raises before any search. The fix is to delete the assignment line.

</details>

### Question 4: Explanation

Why does the engine store a module in `sys.modules` before running its body, rather than after?

<details><summary>Show Solution</summary>

If the entry were added only after the body finished, a module that imports itself, directly or through another module, would start loading again and recurse without end. With the entry in place first, the nested import returns the half-built module. The import reference states this reason in section 5.4.

</details>
