In this lesson you will turn a folder of files into a package, predict from which folder each `import` works, and fix the error that a relative import raises when its file is run as a script. The outputs below were measured on Python 3.12.

**You need:** Lesson 13.1, which covers how `import` searches `sys.path` (the list of folders Python searches for modules) and caches modules. The browser examples need nothing else. The longer demo needs a terminal and Python 3.

## The problem: the same file works from one folder and fails from another

Suppose `module2.py` needs a function from `module1.py`, which sits in a sibling folder. You write `from ..module1 import greet`. Run `python my_package/sub_package1/module2.py` and Python stops with `ImportError: attempted relative import with no known parent package`. Run `python -m my_package.sub_package1.module2` instead and nothing fails. The file did not change. What changed is how Python names the file and which folders it searches. The rest of this lesson makes both rules explicit.

## Packages are folders, and module names are paths

A module is a `.py` file. A package is a folder that Python imports as a module, and its name is the dotted path from a folder on `sys.path`. A folder that contains an `__init__.py` file is a regular package. The four files below have four dotted names.

![Four file paths, each mapped to a dotted module name: a package folder with __init__.py, a module file, a sub-package __init__.py and a module file inside it](diagrams/13.2-file-to-module-name.svg "Each file path, read from the folder on sys.path, is one dotted name.")

## What `__init__.py` does

The Python Language Reference says: "When a regular package is imported, this `__init__.py` file is implicitly executed, and the objects it defines are bound to names in the package's namespace." The file runs the first time anything under the package is imported. It may be empty.

Importing a submodule also imports its parents first. The reference gives the order for `foo.bar.baz`: Python "first tries to import `foo`, then `foo.bar`, and finally `foo.bar.baz`." The sketch shows the order measured on a copy of the tree with one `print` per file.

![Five steps for import my_package.sub_package1.module2: two __init__.py files run first, then module2 starts, then module1 runs inside module2's first line, then module2 finishes](diagrams/13.2-import-order.svg "Measured order. Step 4 happens in the middle of step 3.")

Two consequences follow. An `__init__.py` with slow code slows every import below it. And importing one leaf module always runs the package's `__init__.py` files, even if you wanted only the leaf.

## Absolute and relative imports

An absolute import gives the full dotted name: `from my_package.module1 import greet`. A relative import starts from the current package. Each leading dot means one level: one dot is the current package, two dots is its parent. Python works out the start point from the module's `__package__` attribute. For `module2` imported as `my_package.sub_package1.module2`, that attribute is `my_package.sub_package1` (checked in a one-line run, not in the demo).

Take `from ..module1 import greet`. Two dots start at `my_package.sub_package1` and climb one level, leaving `my_package`. Then `.module1` is appended, giving `my_package.module1`.

![Two package parts, my_package and sub_package1; two dots drop sub_package1, then .module1 is appended to give my_package.module1](diagrams/13.2-relative-resolve.svg "The dotted name is computed from __package__ before the module is found.")

You can check the rule with the standard library's resolver. This block runs in the browser as it is.

```python
import importlib.util

cases = [
    ("..module1", "my_package.sub_package1"),
    (".", "my_package.sub_package1"),
    ("..", "my_package.sub_package1"),
    ("..module1", "my_package"),
]
for name, package in cases:
    try:
        print(f"{name!r:12} in {package!r:26} -> {importlib.util.resolve_name(name, package)}")
    except ImportError as err:
        print(f"{name!r:12} in {package!r:26} -> ImportError: {err}")
```

```output
'..module1'  in 'my_package.sub_package1'  -> my_package.module1
'.'          in 'my_package.sub_package1'  -> my_package.sub_package1
'..'         in 'my_package.sub_package1'  -> my_package
'..module1'  in 'my_package'               -> ImportError: attempted relative import beyond top-level package
```

Two limits follow from this. The dots cannot climb above the top package: the last row fails because `my_package` has only one part. And a relative import needs a package at all. A file run as a script has no `__package__`, so its first line fails, which is the error from the opening section.

PEP 8, the style guide, says: "Absolute imports are recommended" and "explicit relative imports are an acceptable alternative to absolute imports." So the choice between the two forms is a matter of style. The failure comes from how the file is started, not from the form of the import.

## Which folder is searched depends on how Python starts

The sys.path documentation says that `python script.py` puts the script's own folder first in `sys.path`, while `python -m module` puts the current working directory first. The table below shows five launches of the same files.

![Five rows, each showing a command and its result: test_package.py from the root runs; running module2.py by path fails with a relative import error; -m for module2 runs silently; running module3.py by path fails with ModuleNotFoundError; -m for module3 runs silently](diagrams/13.2-run-modes.svg "Green runs. Rose fails. The same files, started differently.")

Running `module3.py` by path puts `sub_package2/` first on the search path, so `my_package` cannot be found. Running with `-m` from the project root puts the root first, and the import works. The two `-m` runs print nothing, because those files only define functions.

Two fixes work. Run with `-m` from the project root. Or set the `PYTHONPATH` environment variable (a list of extra search folders) to the project root. I checked the second with the working directory at `/`, and it prints `Hello, Dana!`. The fix to avoid is `sys.path.append("/your/path")`. It hardcodes one machine's path and hides the real cause.

## Namespace packages: `__init__.py` is optional

Older advice says every package needs `__init__.py`. That is not true for import. PEP 420 defines namespace packages, and says that they "cannot contain an `__init__.py`." A folder without one still imports, but it has no single file behind it: `__file__` is `None` and `__path__` is a `_NamespacePath` object instead of a list.

The next sketch compares the two kinds. A namespace package can also be split across folders. If `shared/` appears in two folders on the path, Python merges them. A regular package changes this: PEP 420 says that if `<directory>/foo/__init__.py` is found, "a regular package is imported and returned," so a regular package found first hides the other folders.

![Table comparing a regular package with a namespace package: __init__.py present or absent, the type of __path__, and what happens when one name appears in two folders](diagrams/13.2-regular-vs-namespace.svg "Measured. The regular package is the one with __init__.py.")

My recommendation, which is reasoning from these measurements and not a rule from the docs: give your own packages an `__init__.py`. Then each package has one location, and no other folder can join it by accident.

## Run it locally

The block below builds the package from this lesson on disk, runs it the five ways from the table, and checks the import order and the namespace cases. It needs only the standard library. Its output is the real output of the run.

<details><summary>Run locally: demo_packages.py (standard library only, no pip install)</summary>

```python
"""Build the package on disk and run it five ways (standard library only)."""
import shutil
import subprocess
import sys
from pathlib import Path

# Start clean, so the script can be run twice with the same output.
for folder in ("demo", "trace", "ns", "portA", "portB"):
    shutil.rmtree(folder, ignore_errors=True)

root = Path("demo")
files = {
    "my_package/__init__.py": "",
    "my_package/module1.py": (
        'def greet(name: str) -> str:\n    return f"Hello, {name}!"\n\n'
        'def farewell(name: str) -> str:\n    return f"Goodbye, {name}!"\n'),
    "my_package/sub_package1/__init__.py": "",
    "my_package/sub_package1/module2.py": (
        "from ..module1 import greet\n\n"
        "def greet_from_module2(name: str) -> str:\n    return greet(name)\n"),
    "my_package/sub_package2/__init__.py": "",
    "my_package/sub_package2/module3.py": (
        "from my_package.module1 import farewell\n\n"
        "def farewell_from_module3(name: str) -> str:\n    return farewell(name)\n"),
    "test_package.py": (
        "from my_package.sub_package1.module2 import greet_from_module2\n"
        "from my_package.sub_package2.module3 import farewell_from_module3\n\n"
        "def main() -> None:\n    name = \"Alice\"\n"
        "    print(greet_from_module2(name))\n"
        "    print(farewell_from_module3(name))\n\n"
        "if __name__ == \"__main__\":\n    main()\n"),
}
for path, text in files.items():
    (root / path).parent.mkdir(parents=True, exist_ok=True)
    (root / path).write_text(text)


def run(label, args, cwd=root, env=None):
    r = subprocess.run([sys.executable, *args], cwd=cwd, capture_output=True, text=True, env=env)
    last_err = r.stderr.strip().splitlines()[-1] if r.stderr.strip() else ""
    print(f"$ {label}")
    print(f"  exit {r.returncode}: {r.stdout.strip() or '(no output)'}" + (f"  | {last_err}" if last_err else ""))


run("python test_package.py", ["test_package.py"])
run("python my_package/sub_package1/module2.py", ["my_package/sub_package1/module2.py"])
run("python -m my_package.sub_package1.module2", ["-m", "my_package.sub_package1.module2"])
run("python my_package/sub_package2/module3.py", ["my_package/sub_package2/module3.py"])
run("python -m my_package.sub_package2.module3", ["-m", "my_package.sub_package2.module3"])

# Import order: a copy of the tree with one print per file.
trace = Path("trace")
prints = {
    "my_package/__init__.py": 'print("1 my_package/__init__.py")\n',
    "my_package/module1.py": (
        'print("3 my_package/module1.py")\n'
        "def greet(name):\n    return f\"Hello, {name}!\"\n"),
    "my_package/sub_package1/__init__.py": 'print("2 my_package/sub_package1/__init__.py")\n',
    "my_package/sub_package1/module2.py": (
        'print("2b module2.py starts")\n'
        "from ..module1 import greet\n"
        'print("4 module2.py finishes")\n'),
}
for path, text in prints.items():
    (trace / path).parent.mkdir(parents=True, exist_ok=True)
    (trace / path).write_text(text)
run("python -c 'import my_package.sub_package1.module2' (trace copy)",
    ["-c", "import my_package.sub_package1.module2"], cwd=trace)

# Namespace packages: no __init__.py is needed (PEP 420).
ns = Path("ns")
(ns / "reg").mkdir(parents=True, exist_ok=True); (ns / "reg/__init__.py").write_text("")
(ns / "nsd").mkdir(parents=True, exist_ok=True); (ns / "nsd/leaf.py").write_text("Y = 'leaf'\n")
run("import reg; type(reg.__path__)", ["-c", "import reg; print(type(reg.__path__).__name__)"], cwd=ns)
run("import nsd; nsd.__file__", ["-c", "import nsd; print(nsd.__file__, type(nsd.__path__).__name__)"], cwd=ns)

# Split namespace package: two folders contribute to one name "shared".
import os
port_a, port_b = Path("portA"), Path("portB")
for path, text in {"portA/shared/a.py": "A = 1\n", "portB/shared/b.py": "B = 2\n"}.items():
    (Path(path).parent).mkdir(parents=True, exist_ok=True)
    Path(path).write_text(text)
env = dict(os.environ, PYTHONPATH=os.pathsep.join([str(port_a), str(port_b)]))
run("PYTHONPATH=portA:portB python -c 'import shared.a, shared.b'",
    ["-c", "import shared.a, shared.b; print(shared.a.A + shared.b.B)"], cwd=Path("."), env=env)
# A regular package in portA (an __init__.py) hides portB's contents.
Path("portA/shared/__init__.py").write_text("")
run("same, after adding portA/shared/__init__.py",
    ["-c", "import shared.a, shared.b"], cwd=Path("."), env=env)
```

## Common traps

> [!TRAP]
> Running a file inside a package by its path leaves Python with no package name, so relative imports fail. Use `python -m my_package.sub_package1.module2` from the project root.

> [!TRAP]
> `sys.path.append("/your/path")` works only on the machine where it was written. Use `-m` or `PYTHONPATH`.

> [!TRAP]
> Too many dots raise an error that names the top package, not the module. From `my_package.sub_package1`, `...top` fails with "attempted relative import beyond top-level package."

> [!TRAP]
> A folder without `__init__.py` still imports. If a folder meant to be a regular package lacks `__init__.py`, the import succeeds as a namespace package with `__file__` set to `None`. Check `__file__` when an import behaves strangely.

> [!TRAP]
> Code in `__init__.py` runs once, the first time anything below that package is imported, so slow code there delays every program that imports the package. Keep it light.

## Summary

- A regular package is a folder with `__init__.py`. Its dotted name is its path from a folder on `sys.path`.
- Importing a submodule runs each parent's `__init__.py` first.
- Relative imports resolve against `__package__`. They fail when the file runs as a script or when the dots climb above the top package.
- Launch package modules with `python -m` from the project root, or set `PYTHONPATH`. Do not hardcode `sys.path`.
- A folder without `__init__.py` is a namespace package. It can merge across folders, and a regular package found first hides the rest.

## Quiz time

### Question 1: Predict the result

From the project root, which of these run without an ImportError? (a) `python my_package/sub_package2/module3.py` (b) `python -m my_package.sub_package2.module3`

<details><summary>Show Solution</summary>

Only (b). In (a), Python puts `my_package/sub_package2/` first on `sys.path`, so `my_package` is not found. In (b), `-m` puts the current working directory first, so the root is searched. The measured results are "ModuleNotFoundError: No module named 'my_package'" for (a) and a silent exit 0 for (b).

</details>

### Question 2: Calculation

The file `my_package/sub_package1/module2.py` contains `from ...module1 import greet`. What happens when it is imported as `my_package.sub_package1.module2`?

<details><summary>Show Solution</summary>

Python raises `ImportError: attempted relative import beyond top-level package`. The package is `my_package.sub_package1`, which has two parts. Three dots remove two parts, leaving nothing to build the name from. The measured case `...top` in `my_package.sub_package1` gives this same error. The example is calculated from the rule and I did not run this exact line.

### Question 3: Bug-spotting

A student fixes a failing test by adding `sys.path.append("/Users/me/project")` at the top of the script. What is wrong with this, and what would you do instead?

<details><summary>Show Solution</summary>

The path is hardcoded, so the script works on one machine only. It also hides the cause: when the script is run by path, its own folder is first on `sys.path`. Run the script with `-m` from the project root, as in the table above, or set `PYTHONPATH` to the project root. Neither depends on where the project lives.

</details>

### Question 4: Explain

A teammate says, "Python 3.12 imports folders without `__init__.py`, so we can delete them all." What is right and what is wrong about this?

<details><summary>Show Solution</summary>

The first part is right: such a folder imports as a namespace package (PEP 420). The result has `__file__` set to `None` and a `_NamespacePath` for `__path__`. The mistake is treating this as equivalent. A namespace package has no single location, and can merge with other folders of the same name. A regular package found first on the path hides them. Keep `__init__.py` in your own packages.

</details>
