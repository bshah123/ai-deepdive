After this lesson you can explain why two projects need two environments, predict which file `import` loads when two candidates exist, and say why a moved virtual environment breaks `pip` but not `python`. The measurements below were run on CPython 3.12.13 on macOS (arm64). Where a claim comes from the documentation, the source is named.

**You need:** how `import` finds a file (Lessons 13.1 and 13.2).

## The problem a venv solves

Project A was tested with library `lib` version 1.0. Project B needs `lib` 2.0. A plain `pip install` writes into the **site-packages** directory of the interpreter that runs pip. Site-packages is the folder where a Python installation keeps third-party packages, and it holds one copy of each name. The second install replaces the first, and project A breaks without an error at install time.

![Left: one site-packages holding lib 1.0, with project A and project B both pointing at it; B's install overwrites it. Right: two venvs, each with its own library, and each project points at its own venv](diagrams/13.3-two-projects.svg "One shared site-packages has one slot per name. A venv gives each project its own slot.")

A **virtual environment** (venv) fixes this by giving each project its own site-packages directory. The interpreter binary can stay shared. What changes is the list of places where it looks for packages.

## What `python -m venv` creates

![A folder tree: venv_a contains pyvenv.cfg, bin with python and pip, and lib/python3.12/site-packages containing pip. A note says pyvenv.cfg sits beside the python binary and holds the home key.](diagrams/13.3-venv-anatomy.svg "A fresh venv: one configuration file, a bin folder, and a site-packages folder.")

The command does three things in order. It creates the target folder and writes `pyvenv.cfg`. It creates the `bin` folder and the `lib/.../site-packages` folder. Then, unless you pass `--without-pip`, it runs `ensurepip` to put pip into site-packages.
On a fresh venv the measured tree has 862 files and takes about 62 MiB. The only installed package is pip (version 25.0.1). setuptools is not installed, because the Python documentation says that since version 3.12 "setuptools is no longer a core venv dependency" (Python docs, `venv`).

The file `pyvenv.cfg` is the key piece. Its `home` line names the installation that built the venv. Its `include-system-site-packages` line says whether the system's packages stay visible. PEP 405 defines the rule: the interpreter looks for `pyvenv.cfg` next to the executable or one directory above it. If it finds one with a `home` key, `sys.prefix` becomes the folder containing the file, and `sys.base_prefix` becomes the base installation. The documentation gives the test in one line: `sys.prefix != sys.base_prefix` means the interpreter is inside a venv.

Activation is optional. The `activate` script only puts the venv's `bin` folder first on `PATH`, so that a bare `python` or `pip` resolves to the venv. The venv documentation says scripts in an environment "should be runnable without activating it." The block below runs the venv's interpreter with a `PATH` that contains no venv folder, and it still reports itself as inside the venv.

<details><summary>Run locally: creates real venvs with the standard library (not runnable in the browser)</summary>

```python
import json, os, subprocess, sys, tempfile, venv

work = tempfile.mkdtemp()
vdir = os.path.join(work, "venv_a")
venv.create(vdir, with_pip=True)                    # same as: python -m venv venv_a
py = os.path.join(vdir, "bin", "python")
PROBE = "import json, sys; print(json.dumps({'prefix': sys.prefix, 'base': sys.base_prefix, 'path': sys.path}))"

def probe(env=None):
    p = subprocess.run([py, "-c", PROBE], cwd=work, capture_output=True, text=True, env=env, check=True)
    return json.loads(p.stdout)

def show(entry, info):
    if entry == "":
        return "(cwd)"
    if entry.startswith(info["prefix"]):
        return "<venv>" + entry[len(info["prefix"]):]
    if "/lib/" in entry:
        return "<base>/lib/" + entry.split("/lib/", 1)[1]
    return entry

info = probe()
print("in a venv:", info["prefix"] != info["base"])
print("sys.path inside the venv:")
for i, entry in enumerate(info["path"], 1):
    print(f"  {i}. {show(entry, info)}")

bare = probe(env={"PATH": "/usr/bin:/bin"})           # no activation, no venv on PATH
print("in a venv without activation:", bare["prefix"] == info["prefix"])

# a .pth file in the venv's site-packages appends a directory to sys.path
site_dir = next(p for p in info["path"] if p.startswith(info["prefix"]))
extra = os.path.realpath(os.path.join(work, "extra_dir"))
os.makedirs(extra)
with open(os.path.join(site_dir, "demo.pth"), "w") as f:
    f.write(extra + "\n")
paths = probe()["path"]
print("pth entry follows site-packages:", paths.index(extra) == paths.index(site_dir) + 1)
```

```output
in a venv: True
sys.path inside the venv:
  1. (cwd)
  2. <base>/lib/python312.zip
  3. <base>/lib/python3.12
  4. <base>/lib/python3.12/lib-dynload
  5. <venv>/lib/python3.12/site-packages
in a venv without activation: True
pth entry follows site-packages: True
```

</details>

## How `import` searches: `sys.path`

`sys.path` is a list of directories. The Python documentation says it starts with the folder of the input script (or the current directory when there is no script), then the entries of the `PYTHONPATH` variable, then installation defaults, which by convention include `site-packages` (Python docs, "The Module Search Path"). The import system walks this list from the first entry to the last. When a directory holds a file with the requested name, that file is loaded and the search stops.

`sys.path` is an ordinary list, so a program can change it at run time. The documentation warns that the script's folder is placed ahead of the standard library, so a same-named script there "will be loaded instead of modules of the same name in the library directory. This is an error unless the replacement is intended" (Python docs, "The Module Search Path"). Nothing reports the replacement when it happens.

![Five entries of a venv's sys.path stacked top to bottom: the current directory, the zipped standard library slot, the standard library, the compiled extensions folder, and the venv's site-packages highlighted as the only place pip installs. A note says a .pth file adds entries after site-packages.](diagrams/13.3-sys-path.svg "The venv's sys.path as measured. import widget scans from the top and takes the first match.")

Here is the search done by hand, then by the import system. The list has two folders, and each holds a file called `widget.py`. The code asks the import machinery where `widget` would come from, for the list in its given order and for the reversed list.

```python
import importlib.machinery, os, tempfile

root = tempfile.mkdtemp()
for folder, body in [("project", "SOURCE = 'project copy'\n"), ("site-packages", "SOURCE = 'installed copy'\n")]:
    os.makedirs(os.path.join(root, folder))
    with open(os.path.join(root, folder, "widget.py"), "w") as f:
        f.write(body)

def where(name, search_path):
    """Return the file that import would load, relative to root, or None."""
    spec = importlib.machinery.PathFinder.find_spec(name, search_path)
    return None if spec is None else os.path.relpath(spec.origin, root)

search = [os.path.join(root, "project"), os.path.join(root, "site-packages")]
print("first hit:", where("widget", search))
print("after reversing the path:", where("widget", search[::-1]))
print("missing name:", where("gadget", search))
```

```output
first hit: project/widget.py
after reversing the path: site-packages/widget.py
missing name: None
```

By hand: the first folder holds `widget.py`, so the search stops there and returns `project/widget.py`. The reversed list stops at `site-packages`. The order of `sys.path` decides which copy you get, and nothing warns you that a second copy exists.

## Shadowing: a local file hides a library

The most common `sys.path` bug is a file in your own folder that has the same name as a module you need. Because the current directory is searched first, `random.py` in your folder replaces the standard library's `random`. The next block creates that situation and runs it in three ways.

<details><summary>Run locally: starts subprocesses with the standard library (not runnable in the browser)</summary>

```python
import os, subprocess, sys, tempfile

work = tempfile.mkdtemp()
with open(os.path.join(work, "random.py"), "w") as f:
    f.write("print('loaded local random.py')\nvalue = 4\n")

def run(*args):
    return subprocess.run([sys.executable, *args], cwd=work, capture_output=True, text=True)

r = run("-c", "import random; print('randint' in dir(random))")
print(r.stdout.strip().replace("\n", " | "))
r = run("-c", "import random; random.randint(1, 6)")
print("exit status:", r.returncode)
print(r.stderr.strip().splitlines()[-1])
r = run("-I", "-c", "import random, os; print(os.path.realpath(random.__file__) == os.path.realpath(os.path.join(os.getcwd(), 'random.py')))")
print("python -I loads the local file:", r.stdout.strip())
```

```output
loaded local random.py | False
exit status: 1
AttributeError: module 'random' has no attribute 'randint'
python -I loads the local file: False
```

</details>

The failure appears later than the cause. The `import` line succeeds, because a module named `random` exists, and the error shows up only at the first call to a function that the local file does not define. The first run shows the shadow: the local file loads, so `randint` is missing. The `-I` flag (isolated mode) leaves the current directory out of `sys.path`, so the standard library file loads again.

## Moving a venv breaks its scripts, not its Python

A venv's `pip` script starts with a **shebang** line, the `#!` line that names the interpreter to run the script with. Python writes that line when the venv is created, and it is an absolute path. The venv documentation says this directly: "their shebang lines contain the absolute paths to their environment's interpreters. Because of this, environments are inherently non-portable, in the general case" (Python docs, `venv`).

![Left: a venv built at the old path, its bin/pip shebang pointing at old/venv/bin/python3.12. An arrow labelled mv leads to the right: bin/python works and reports the new prefix; bin/pip fails with FileNotFoundError because the old shebang path no longer exists.](diagrams/13.3-moved-venv.svg "Moving a venv: python finds pyvenv.cfg next to itself, but the pip script still names the old interpreter.")

The `python` binary finds `pyvenv.cfg` next to itself, so it keeps working after a move. The `pip` script does not, because its shebang names a path that no longer exists. The error message says only "No such file or directory". The block below moves a venv and shows both results.

<details><summary>Run locally: creates and moves a real venv (not runnable in the browser)</summary>

```python
import os, shutil, subprocess, tempfile, venv

work = tempfile.mkdtemp()
old = os.path.join(work, "old", "venv_a")
new = os.path.join(work, "new_place", "venv_a")
os.makedirs(os.path.dirname(old))
os.makedirs(os.path.dirname(new))
venv.create(old, with_pip=True)
shutil.move(old, new)

r = subprocess.run([os.path.join(new, "bin", "python"), "-c", "import sys; print(sys.prefix.endswith('new_place/venv_a'))"],
                   capture_output=True, text=True)
print("moved python reports the new prefix:", r.stdout.strip(), "| exit", r.returncode)
with open(os.path.join(new, "bin", "pip")) as f:
    shebang = f.readline().strip()
print("pip shebang still names the old folder:", "/old/" in shebang)
try:
    subprocess.run([os.path.join(new, "bin", "pip"), "--version"], capture_output=True)
except OSError as e:
    print(type(e).__name__ + ":", e.strerror)
```

```output
moved python reports the new prefix: True | exit 0
pip shebang still names the old folder: True
FileNotFoundError: No such file or directory
```

</details>

The venv documentation's advice is to recreate the environment at the new location and delete the old one.

## Common traps

> [!TRAP]
> A file named after a standard-library module shadows it. A `random.py`, `json.py` or `email.py` in the folder where you run Python will be imported instead of the library, and the error often appears far from the cause. Rename the file and delete any stale `__pycache__` folder.

> [!TRAP]
> `pip` and `python` can belong to different interpreters. Running `pip install` takes whichever `pip` comes first on `PATH`. Running `python -m pip install` uses the pip module of the exact interpreter you named, so the target is unambiguous. This follows from how `-m` works (my own reasoning from the module-running rules; no source checked).

> [!TRAP]
> Do not move or copy a venv. Its scripts hold absolute paths. Delete it and recreate it in the new place (Python docs, `venv`).

> [!TRAP]
> A `.pth` line that starts with `import` runs code at every interpreter start. The `site` documentation says these lines are "executed with `exec()`" for backward compatibility, and that the directory lines are added only if the directory exists. The 3.15 site documentation marks `import` lines as deprecated from Python 3.15, so this trap applies to 3.12 and earlier, and to later versions until the removal date the docs give.

> [!TRAP]
> Do not commit a venv to version control. It holds absolute paths, tens of megabytes and machine-specific binaries. Record the dependency list in a file such as `requirements.txt` or `pyproject.toml` instead (my own reasoning from the non-portability warning above).

## Summary

- A venv gives one project its own site-packages directory; a shared site-packages holds one version of each name.
- `pyvenv.cfg` next to the interpreter makes `sys.prefix` differ from `sys.base_prefix`. Activation only edits `PATH`.
- `import` walks `sys.path` in order and loads the first match, so a local `random.py` hides the standard library.
- A `.pth` file appends directories to `sys.path` after the site-packages folder it lives in.
- A moved venv keeps a working `python`, but its scripts, such as `pip`, keep the old absolute path in their shebang.

## Quiz time

### Question 1: Predict the output

A folder `work/` contains one file, `json.py`, whose only line is `print('mine')`. You run `cd work` and then `python -c "import json"`. What is printed?

<details><summary>Show Solution</summary>

It prints `mine`. With `-c`, the first entry of `sys.path` is the current directory, which is `work/`. The import system finds `json.py` there before it reaches the standard library, so the local file runs.

</details>

### Question 2: Find the bug

A student runs `pip install requests` in a terminal, then runs a notebook kernel that starts `import requests` and fails with `ModuleNotFoundError`. What is the most likely cause, and how would you check it?

<details><summary>Show Solution</summary>

The `pip` on `PATH` and the notebook's interpreter are probably different installations, so the package went into one site-packages folder and the notebook reads another. Check with `python -c "import sys; print(sys.executable)"` in both places, then install with `python -m pip install requests` using the interpreter the notebook uses. Using `-m` removes the ambiguity about which pip runs.

</details>

### Question 3: Explain the behaviour

After you move a venv folder, `venv/bin/python -c "import sys; print(sys.prefix)"` prints the new location, but `venv/bin/pip --version` raises `FileNotFoundError`. Why do the two commands behave differently?

<details><summary>Show Solution</summary>

The interpreter finds `pyvenv.cfg` relative to its own location, so `sys.prefix` follows the folder it is moved to. The `pip` script is a text file whose shebang line holds the absolute path of the old interpreter. The kernel cannot start that path, and the error gives only "No such file or directory".

</details>

### Question 4: Calculate an index

In the measured venv `sys.path` above, at what zero-based index is the venv's site-packages folder? Where does a `.pth` line that adds a directory land?

<details><summary>Show Solution</summary>

The venv's site-packages is at index 4, the fifth entry, because the list is `(cwd)`, the zip slot, the standard library, the compiled extensions folder, then site-packages. The `.pth` directory lands at index 5 directly after it, as the block above checked.

</details>
