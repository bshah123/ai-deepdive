In this lesson you will add type annotations to Python functions, run the mypy static type checker on them, and read its errors. You will also see what annotations do not do: the interpreter stores them and never checks them.

**You need:** variables and values (Lesson 2.1), and the idea that a value has a type such as `int`, `str` or `None`.

## The problem: a bad value is found only when its line runs

Python checks types when the code runs. Suppose `add_numbers(5, "7")` is in a branch that runs once a month. The `TypeError` appears on that month's run, in production, and the traceback points at the addition, not at the bad call. A type checker reads the code without running it, so it can report the bad call on the line where it is written. Tests help too, but they only cover the paths someone wrote a test for.

Type annotations are the notes a checker needs. They say what each parameter and return value should be.

## Annotations are stored, not enforced

An annotation is a label after a colon (`a: int`) or after an arrow (`-> int`). CPython, the reference implementation of Python, stores these labels in the function's `__annotations__` dictionary and otherwise ignores them.

```python
def double(x: int) -> int:
    return x * 2

print(double.__annotations__)
print(double(21))
print(double("ab"))
```

```output
{'x': <class 'int'>, 'return': <class 'int'>}
42
abab
```

The `double("ab")` call passes a `str` where an `int` is annotated, and nothing stops it. The Python `typing` documentation states it directly: "The Python runtime does not enforce function and variable type annotations. They can be used by third party tools such as type checkers, IDEs, linters, etc." (Python docs, `typing` module). Python Enhancement Proposal (PEP) 484 calls the checker "a very powerful linter" (PEP 484, Type Hints).

![Two paths for one bad call: at run time the call fails on its line only if that line executes; mypy reports the bad argument before the program starts](diagrams/14.1-run-vs-check.svg "One bad call, two checkers.")

## Mypy reads the labels before the run

Mypy is a static type checker: it analyses source code without executing it and reports places where the annotations disagree with the code. Here is the same call, wrapped so the program keeps running after the error.

```python
def add_numbers(a: int, b: int) -> int:
    return a + b

try:
    print(add_numbers(5, "7"))
except TypeError as err:
    print("TypeError:", err)
```

```output
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

Save the same file as `bug.py` and run both tools (mypy 2.4.1, Python 3.12.13, the versions we used):

```bash
python3 bug.py
mypy bug.py
```

```output
TypeError: unsupported operand type(s) for +: 'int' and 'str'
bug.py:5: error: Argument 2 to "add_numbers" has incompatible type "str"; expected "int"  [arg-type]
Found 1 error in 1 file (checked 1 source file)
```

Mypy points at line 5, the call, and names the argument. It infers the type of every expression, then checks each call and each return against the declared types. It does this without running the code, so it also covers branches that no test reaches. The run fails inside `add_numbers` (line 2), not at the call. Mypy points at the call (line 5) and names the bad argument, and it reports the error without running the code.

## Optional values: `str | None`

A value that can be missing is annotated as a union. `str | None` means "a `str`, or `None`". Python Enhancement Proposal (PEP) 604 defines `X | Y` as the spelling of `Union[X, Y]`, and the syntax needs Python 3.10 or later (PEP 604).

```python
def shout(name: str | None) -> str:
    return name.upper()

try:
    print(shout(None))
except AttributeError as err:
    print("AttributeError:", err)
```

```output
AttributeError: 'NoneType' object has no attribute 'upper'
```

```bash
mypy optional_bug.py
```

```output
optional_bug.py:2: error: Item "None" of "str | None" has no attribute "upper"  [union-attr]
Found 1 error in 1 file (checked 1 source file)
```

A guard fixes it. Inside the `if name is None` branch, mypy knows the value is `None`; after the branch it narrows `name` to `str`, so `.upper()` is allowed.

```python
def shout(name: str | None) -> str:
    if name is None:
        return ""
    return name.upper()

print(shout(None) == "")
print(shout("ada"))
```

```output
True
ADA
```

```bash
mypy optional_fixed.py
```

```output
Success: no issues found in 1 source file
```

![Narrowing: name starts as str or None; the yes branch returns; on the no branch mypy knows name is str, so name.upper() passes](diagrams/14.1-optional-narrowing.svg "Narrowing removes None on the path that reaches .upper().")

## Unannotated functions are skipped by default

A function with no annotations has no types to check against. Mypy's documentation states that functions without any annotations "are not type-checked" unless you ask for it (mypy docs, Common issues). The next example puts an error inside such a body.

```python
def total(prices):
    x: int = "3"
    return sum(prices) + x

try:
    print(total([1, 2]))
except TypeError as err:
    print("TypeError:", err)
```

```output
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

```bash
mypy unann.py
mypy --check-untyped-defs unann.py
```

```output
unann.py:2: note: By default the bodies of untyped functions are not checked, consider using --check-untyped-defs  [annotation-unchecked]
Success: no issues found in 1 source file
unann.py:2: error: Incompatible types in assignment (expression has type "str", variable has type "int")  [assignment]
Found 1 error in 1 file (checked 1 source file)
```

The flag `--strict` turns on a group of stricter checks. On the same file it also reports the missing annotation and the call that depends on it:

```bash
mypy --strict unann.py
```

```output
unann.py:1: error: Function is missing a type annotation  [no-untyped-def]
unann.py:2: error: Incompatible types in assignment (expression has type "str", variable has type "int")  [assignment]
unann.py:6: error: Call to untyped function "total" in typed context  [no-untyped-call]
Found 3 errors in 1 file (checked 1 source file)
```

Unannotated parameters are also treated as `Any`. PEP 484 says the default annotation for arguments and return types of a checked function is `Any`, and `Any` is consistent with every type. So a caller passing a `str` into an unannotated parameter is never flagged.

![Default mypy notes the unannotated body and reports success; with --check-untyped-defs the same line is reported as an error](diagrams/14.1-unannotated-body.svg "The same two lines under two mypy settings.")

## Measured: nine toy bugs, two checkers

To see which checker finds what, I wrote nine small snippets (A to I), each with one bug, and ran each under mypy and under CPython on the input shown. The experiment script is `scripts/diagrams/lessons/14.1_experiment.py` in the course repository. These snippets are my own toy set, not a benchmark, so treat the counts as an illustration of the two failure modes.

Four bugs are caught by both: the argument type (A), the `None` value (C), the misspelled attribute (D) and the missing argument (E). Three are caught only by mypy: a wrong return type (B), a bug on a branch the input never takes (G), and a missing `else` return (H), where the run prints `None` and does not crash. Two are caught only by the run: the unannotated call (F) and the unannotated body (I), which mypy skips by default.

In practice, run mypy before each commit or inside your editor, and keep tests for values a checker cannot see. Mypy checks the shape of your calls and returns; tests check the values your code produces. Neither replaces the other.

## Common traps

> [!TRAP]
> Annotations are not checks at run time. `double("ab")` returns `abab`. Only a checker, or your own `isinstance` test, will object.

> [!TRAP]
> A function with no annotations is not checked by default. Add `--check-untyped-defs` or annotate the body.

> [!TRAP]
> A missing annotation means `Any`, which passes every check. `Any` also silences errors downstream of the value it touches.

> [!TRAP]
> A clean mypy run means no error was found, not that the code is right. Each run answers one question: does the code agree with its annotations? `def average(xs: list[float]) -> float: return sum(xs) / len(xs)` passes mypy, yet `average([])` raises `ZeroDivisionError`. The checker does not know that the list may be empty.

> [!TRAP]
> `X | Y` in an annotation needs Python 3.10 or later (PEP 604). Check the interpreter version before you run code on an older machine.

## Summary

- Annotations are labels that CPython stores in `__annotations__` and does not enforce.
- Mypy is a static type checker: it reads annotations and code and reports disagreements without running the program.
- `str | None` marks a value that can be missing; a guard such as `if name is None` narrows the type on each branch.
- Unannotated bodies are skipped by default; `--check-untyped-defs` checks them, but unannotated parameters remain `Any`.
- Mypy and the run each miss bugs the other finds, so use both.

## Quiz time

### Question 1: Prediction

What does this program print, and does mypy report an error for it?

```python
def double(x: int) -> int:
    return x * 2

print(double("ab"))
```

<details><summary>Show Solution</summary>

It prints `abab`. The `str` argument makes `x * 2` a string repetition, so no exception occurs. Mypy reports `error: Argument 1 to "double" has incompatible type "str"; expected "int"`, because `"ab"` is not an `int`. The run prints the value anyway, which is the point of the first trap.

</details>

### Question 2: Bug-spotting

Mypy reports an error for this file. What is it, and how would you fix it?

```python
def half(n: int) -> int:
    return n / 2

print(half(7))
```

<details><summary>Show Solution</summary>

Mypy reports `error: Incompatible return value type (got "float", expected "int")`. The `/` operator always returns a `float`, while the annotation promises `int`. Fix it with `return n // 2` if you want an integer result, or change the annotation to `-> float`. The program itself prints `3.5`.

</details>

### Question 3: Explanation

The function below is `str | None` and calls `len(name)`. Why does mypy report an error, and what guard removes it?

```python
def find(name: str | None) -> int:
    return len(name)
```

<details><summary>Show Solution</summary>

Mypy reports `Argument 1 to "len" has incompatible type "str | None"; expected "Sized"`, because `None` has no length. A guard narrows the type before the call: `if name is None: return 0` followed by `return len(name)` leaves `name` as `str` on the second line, and mypy accepts that version (checked with mypy 2.4.1).

</details>

### Question 4: Explanation

Mypy says "Success: no issues found" for `def average(xs: list[float]) -> float`. Why can `average([])` still crash, and what would you change?

<details><summary>Show Solution</summary>

The annotations do not say the list must be non-empty, and mypy checks types, not values. `sum([]) / len([])` divides by zero at run time, giving `ZeroDivisionError`. Add a guard that raises a clear error or returns a documented default, and add a test for the empty list.

</details>
