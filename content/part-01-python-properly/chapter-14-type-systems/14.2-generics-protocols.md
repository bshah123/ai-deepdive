In this lesson you will write one function that works on many types while keeping the input and output types linked (a `TypeVar`), and an interface that any class can satisfy without inheriting from it (a `Protocol`). You will also see exactly which of these checks Python performs at runtime and which only a static checker such as mypy performs.

**You need:** Lesson 14.1 (type annotations and running mypy) and classes with methods.

## The problem these tools solve

Suppose you want `larger(x, y)` to return the bigger of two values, and it should work for ints, floats and strings. Without generics you have two bad options. You can write one function per type, or you can annotate everything as `Any`. `Any` silences the checker: if `larger(x: Any, y: Any) -> Any` returns `Any`, the checker can no longer tell that an int goes in and an int comes out.

Interfaces have a similar problem. A function that needs "anything with a `close()` method" cannot simply name a base class, because a file object, a socket wrapper and your own class may share the method without sharing a parent. A Protocol describes the method shape and lets any matching class pass.

## Intuition: one definition, a binding per call

![Three boxes in a column for each call: identity(3) binds T to int and returns int; identity('a') binds T to str and returns str. One def line sits above both.](diagrams/14.2-typevar.svg "One definition of identity; T is bound separately at each call.")

A `TypeVar` is a named placeholder for a type. In `def identity(x: T) -> T`, the signature says: for some type `T`, given a `T`, return a `T`. At each call the checker binds `T` to the type of the argument. The body is written once. Nothing is copied at runtime.

## Two checkers, two jobs

Two different programs read your annotations. Python reads them only in a few places, such as `typing.get_type_hints`, `dataclasses`, and `isinstance` on a runtime-checkable Protocol. Mypy reads all of them, but it never runs your code. So a bug can pass Python and fail mypy (an unbounded `T` used with `>`), or pass mypy and fail at runtime (a function annotated `-> int` that raises `ZeroDivisionError`). The rest of this lesson keeps the two views apart. The table in the static checking section shows the split on five concrete cases.

## Worked example: binding T by hand

Take `identity(3)`.

1. The argument `3` has type `int`, so the checker sets `T = int`.
2. The return type `T` becomes `int`.
3. `identity("a")` sets `T = str` and returns `str`.

Python itself never does this binding. It only returns the object it was given. The binding exists in the checker's view of the program. The first code block shows the runtime side:

```python
from typing import Generic, TypeVar, get_args

T = TypeVar("T")

def identity(x: T) -> T:
    return x

class Box(Generic[T]):
    def __init__(self, value: T) -> None:
        self.value = value

print("identity(3)   ->", repr(identity(3)))
print("identity('a') ->", repr(identity("a")))
print("Box.__parameters__ =", Box.__parameters__)
print("get_args(Box[int]) =", get_args(Box[int]))
print("Box[str](1).value =", Box[str](1).value)
```

```output
identity(3)   -> 3
identity('a') -> 'a'
Box.__parameters__ = (~T,)
get_args(Box[int]) = (<class 'int'>,)
Box[str](1).value = 1
```

The last line matters. `Box[str]` is a real runtime object that records its parameter, but Python does not check that the value `1` is a `str`. Only a static checker can object. Since Python 3.12 the same function can be written with the shorter syntax of Python Enhancement Proposal (PEP) 695, `def identity[T](x: T) -> T`; we checked that it runs on 3.12.13. This lesson keeps the `TypeVar` form because most existing code uses it.

## Bounds: what T is allowed to do

An unconstrained `T` can stand for anything, so the checker allows only operations that every object supports. The comparison `x > y` is not one of them.

![Left panel: unbounded T, mypy reports that the left operand of > is unsupported. Right panel: T bound to a protocol with __gt__; mypy accepts x > y and rejects a plain class.](diagrams/14.2-bound.svg "An unbounded T allows no comparison; a bound gives the checker a promise to use.")

The fix is a bound: a protocol that says which methods `T` must have. Here `Orderable` requires `__gt__`, the method behind `>`. Ints, floats and strings all have `__gt__`, so the bounded function runs for each of them (mypy was run on the int case and on a class without `__gt__`).

```python
from typing import Any, Protocol, TypeVar

class Orderable(Protocol):
    def __gt__(self, other: Any, /) -> bool: ...

O = TypeVar("O", bound=Orderable)

def larger(x: O, y: O) -> O:
    return x if x > y else y

print("larger(1, 2)     ->", larger(1, 2))
print("larger('a', 'b') ->", larger("a", "b"))
print("larger(2.5, 1)   ->", larger(2.5, 1))
```

```output
larger(1, 2)     -> 2
larger('a', 'b') -> b
larger(2.5, 1)   -> 2.5
```

Under the hood, the bound is used only by the checker. At runtime `larger` is the same two-line function as before, and the `Orderable` annotation is never consulted.

A cheaper-looking fix is to annotate the parameters as `Any`. The checker then accepts `x > y`, but it accepts every other operation on `x` too, and the return type becomes `Any`, so the link between input and output is lost. A bound is narrower: the checker allows only what the protocol declares. This is reasoning about the typing rules, not a result from our run.

## Protocols: shape, not inheritance

A Protocol lists members. A class conforms if it has those members with compatible types, and it never has to inherit from the Protocol. Python Enhancement Proposal (PEP) 544 calls this structural subtyping, or "static duck typing". The usual object-oriented rule is nominal: a class is accepted only if it names the base class explicitly.

![Two panels for the interface Closable. Nominal: class Good(Closable) inherits and is accepted, class Other has close() but no parent and is rejected. Structural: class Good has close() and is accepted, class Missing has no close() and is rejected.](diagrams/14.2-nominal-vs-structural.svg "Nominal versus structural matching of one interface.")

Here is a hand check of the structural rule for two classes. `Closable` requires one member, `close`, with no arguments besides `self` and a return type of `None`. `Good` has a member named `close` with exactly that shape, so it conforms, and no inheritance is needed. `Missing` has only `clsoe`, which matches no required member, so it does not conform, even though it has the right number of methods.

The second block declares `Closable` as a runtime-checkable Protocol and tests five classes. Each class is a different kind of mistake.

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Closable(Protocol):
    def close(self) -> None: ...

class Good:
    def close(self) -> None:
        pass

class Missing:
    def clsoe(self) -> None:          # typo in the method name
        pass

class WrongReturn:
    def close(self) -> str:           # returns str; the protocol says None
        return "closed"

class WrongParams:
    def close(self, force: bool) -> None:   # needs an argument that close() lacks
        pass

class NotCallable:
    close = None                      # the attribute exists but is not a method

for cls in (Good, Missing, WrongReturn, WrongParams, NotCallable):
    print(f"isinstance({cls.__name__}(), Closable) = {isinstance(cls(), Closable)}")
```

```output
isinstance(Good(), Closable) = True
isinstance(Missing(), Closable) = False
isinstance(WrongReturn(), Closable) = True
isinstance(WrongParams(), Closable) = True
isinstance(NotCallable(), Closable) = False
```

Read the output carefully. `@runtime_checkable` makes `isinstance` check that the named attributes exist. It ignores their signatures, as the typing documentation says for runtime-checkable protocols. So `WrongReturn` and `WrongParams` pass, and only a static checker can reject them. `NotCallable` fails because CPython (the reference implementation of Python) 3.12.13 treats a method member set to `None` as missing (in `typing.py`, near line 1930). That is an implementation detail; the reliable lesson is that the runtime test looks at names.

Mypy compares signatures as well. The notes in its output print the expected and the actual member side by side. For `WrongParams`, the protocol's `close(self)` takes no argument, but the class's `close(self, force: bool)` requires one, so a caller holding a `Closable` could not legally call it. For `WrongReturn`, the protocol promises a `None` return and the class returns `str`. For `NotCallable`, mypy reports that `close` is expected to be `Callable[[], None]` but is `None`. Each of the three is a conflict in the shape the protocol describes, and `isinstance` cannot see it.

## Common traps

> [!TRAP] **isinstance is not a signature check.** A runtime-checkable Protocol confirms that names exist. `WrongReturn` and `WrongParams` both passed `isinstance` above. Run mypy to check signatures.

> [!TRAP] **An unbounded T supports no operators.** `larger` with a plain `T` runs fine on ints, yet mypy rejects `x > y`. Add a bound that declares the method.

> [!TRAP] **list is invariant.** A `list[int]` is not a `list[float]`, even though every int is a float. Mypy rejects the call in the details block below. Annotate read-only parameters as `Sequence[float]`, which is covariant, so a `list[int]` is accepted. Mypy's documentation says that most mutable generic collections are invariant and recommends immutable annotations where possible.

> [!TRAP] **issubclass() refuses data members.** A runtime-checkable Protocol that declares an attribute, such as `name: str`, cannot be used with `issubclass()`. Python raised `TypeError: Protocols with non-method members don't support issubclass()` in our run. `isinstance()` works for such protocols.

> [!TRAP] **Generics are erased at runtime.** `Box[str](1)` ran without error and returned `1`. The parameter is a hint for the checker, not a guard in the running program.

## Summary

- A `TypeVar` is a placeholder that the checker binds at each call; Python itself does not perform the binding.
- An unbounded `T` supports only operations every object has. A bound, written as a Protocol, declares the methods the checker may use.
- A Protocol matches by shape. A class satisfies it without inheriting from it.
- `isinstance` on a runtime-checkable Protocol checks attribute names only. Signature errors need mypy.

## Quiz time

### Question 1: Prediction

A class `WrongParams` defines `close(self, force: bool) -> None`. What does `isinstance(WrongParams(), Closable)` print, and what does mypy report about it?

<details><summary>Show Solution</summary>

It prints `True`, because `runtime_checkable` checks only that a `close` attribute exists. Mypy reports `Incompatible types in assignment`, with the note that `close` has the wrong signature, because `close()` requires an argument the protocol does not pass.

</details>

### Question 2: Prediction

What does this print?

```python
from typing import Generic, TypeVar

T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, value: T) -> None:
        self.value = value

print(Box[str](1).value)
```

<details><summary>Show Solution</summary>

It prints `1`. Python does not check generic parameters at runtime, so `Box[str]` accepts an int without complaint. Only a static checker would flag the mismatch.

</details>

### Question 3: Find and fix the bug

```python
from typing import TypeVar

T = TypeVar("T")

def larger(x: T, y: T) -> T:
    return x if x > y else y

print(larger(1, 2))
```

<details><summary>Show Solution</summary>

The program prints `2`, but mypy reports `Unsupported left operand type for > ("T")`, because an unbounded `T` promises nothing about `>`. Fix it by bounding `T` to a Protocol that declares `__gt__`, as in the `Orderable` example above: `O = TypeVar("O", bound=Orderable)`.

</details>

### Question 4: Explanation

Why does mypy reject `total(ints)` when `total` takes `xs: list[float]` and `ints: list[int]`, and what annotation fixes it without changing the function body?

<details><summary>Show Solution</summary>

`list` is invariant: a `list[int]` is not a `list[float]`, because the function could append a float to a list that the caller still sees as ints. Annotating the parameter as `Sequence[float]` fixes it. `Sequence` is read-only and covariant, so a `list[int]` is accepted, and the body (`sum(xs)`) is unchanged. We ran mypy --strict on the fixed signature and it reported no issues.

</details>
