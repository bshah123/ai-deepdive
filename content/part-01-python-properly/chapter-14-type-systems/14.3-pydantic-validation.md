In this lesson you will declare a data model once, have Pydantic V2 check and convert raw input against it, and read the errors it returns. You will see what "lax" and "strict" mean for the same field, and why the checking code runs in a compiled Rust library.

**You need:** Python type annotations (Lesson 14.1) and the idea of a `dict` that came from JavaScript Object Notation (JSON).

## The problem validation solves

A web request or a JSON file gives you text, not Python objects. A sensor might send `"temperature_c": "21.5"` and `"count": "3"`. Plain Python will happily accept whatever you do with those strings, and it fails only when the bad value reaches a line that cannot handle it.

Run the built-in `int` on a few inputs. Every line below uses only the standard library, so it runs in the page itself:

```python
# Plain Python: int() converts, but it does not check what it converts
print(int(1.5))      # a float with a fractional part is silently truncated
print(int(" 7 "))    # surrounding spaces are ignored
print(int(True))     # bool is a subclass of int, so True becomes 1
try:
    print(int("abc"))
except ValueError as e:
    print("ValueError:", e)
```

```output
1
7
1
ValueError: invalid literal for int() with base 10: 'abc'
```

Nothing stops `1.5` from becoming `1`. You would have to write a check for every field, every type and every range, and remember to call it on every path. Pydantic moves those checks into a model declaration.

## Intuition: compile the schema once, run it on every record

A Pydantic model is a class that inherits from `BaseModel`. When Python executes the `class` statement, Pydantic reads the annotations and defaults, builds a schema, and hands it to a validator object. Each later call to `model_validate` runs that compiled validator on the input. The schema is built once; the validation runs many times.

![A class definition compiles a SchemaValidator once; each input dict goes through that validator and comes out as a Reading object or a ValidationError](diagrams/14.3-pipeline.svg "Compile once, validate many. The validator is compiled Rust code from pydantic-core, called from Python.")

Pydantic 2 does the core validation in `pydantic-core`, a library whose core validation logic is written in Rust (its repository's About section says so; the README notes the code now lives in the main `pydantic` repository) (Pydantic, `pydantic-core` repository). In the code below, `Reading.__pydantic_validator__` is an instance of `pydantic_core._pydantic_core.SchemaValidator`, a compiled extension module. Python owns the objects you see; the Rust side does the parsing and checking.

The one-off compile is cheap. In the experiment, defining the `Reading` class took a median of 0.17 ms over 21 runs (0.000169 s). That cost is paid once per class, not once per record.

## Worked example: one valid record

Here is the model. Its three fields carry the checks: a pattern for the sensor ID, a lower bound for the temperature, and a positive integer count. This block needs Pydantic, so it sits in a local-run section below.

<details><summary>Run locally: needs pip install pydantic</summary>

```python
from pydantic import BaseModel, Field, ValidationError

class Reading(BaseModel):
    sensor_id: str = Field(pattern=r"^S-\d{3}$")
    temperature_c: float = Field(ge=-273.15)
    count: int = Field(gt=0)

ok = Reading.model_validate({"sensor_id": "S-042", "temperature_c": "21.5", "count": "3"})
print(ok)
print({k: type(v).__name__ for k, v in ok.model_dump().items()})
```

```output
sensor_id='S-042' temperature_c=21.5 count=3
{'sensor_id': 'str', 'temperature_c': 'float', 'count': 'int'}
```

Output above is from pydantic 2.14.4 on CPython, the reference implementation of Python, version 3.12.13.

</details>

The strings `"21.5"` and `"3"` became a `float` and an `int`. That conversion is the lax mode described next.

## Lax and strict: two rules for the same input

Pydantic has two modes. In **lax** mode (the default), it converts input when the conversion is well defined. In **strict** mode, it accepts only the exact Python type you declared. The table shows what happens for an `int` field. Each row is one input, and the results come from running the model in both modes.

![Table of six inputs to an int field: lax accepts 1, '1', 1.0, ' 7 ' and rejects 1.5 and 'abc'; strict accepts only the int 1 and rejects every other input with int_type](diagrams/14.3-coercion.svg "Lax versus strict for an int field. Results are from the measured run.")

The rules in the table match the Pydantic conversion table (Pydantic docs, Conversion Table): a string `"1"` becomes `1` in lax mode, a float `1.0` with no fractional part becomes `1`, and a string with surrounding whitespace is accepted in lax mode. A float `1.5` is rejected for an `int` field in both modes, because converting it would lose information. Strict mode rejects every string outright.

Lax mode is the right default for data from JSON and HyperText Transfer Protocol (HTTP) requests, because every value arrives as text. Strict mode is useful when a value should already have the right type, for example data passed between two of your own functions.

## Collect every error, not just the first

Validation reports all bad fields in one pass. The next block uses one record with three bad fields.

![One input dict with three bad fields maps to three ValidationError entries, each with a field name, an error type and a message](diagrams/14.3-errors.svg "One record, three errors, one pass. Messages are copied from the run.")

<details><summary>Run locally: needs pip install pydantic</summary>

```python
from pydantic import BaseModel, Field, ValidationError

class Reading(BaseModel):
    sensor_id: str = Field(pattern=r"^S-\d{3}$")
    temperature_c: float = Field(ge=-273.15)
    count: int = Field(gt=0)

bad = {"sensor_id": "X-1", "temperature_c": "hot", "count": 0}
try:
    Reading.model_validate(bad)
except ValidationError as e:
    print(e.error_count(), "errors")
    for err in e.errors():
        print(err["loc"], err["type"])
```

```output
3 errors
('sensor_id',) string_pattern_mismatch
('temperature_c',) float_parsing
('count',) greater_than
```

</details>

Each entry in `e.errors()` has a `loc` (the field path), a `type` (a stable machine-readable code such as `float_parsing`), and a human-readable `msg`. Your code can branch on `type` without parsing message text. A plain `if`-chain that stops at the first failure would need extra work to report all three.

## Speed: measured, not assumed

Rust does not make every validation faster. To check, the experiment timed three paths over 100,000 valid records. The hand-written version performs the same conversions and checks as the model (`float()`, `int()`, a regular expression (regex), two range checks), but it raises on the first failure and returns a plain `dict`.

![Bar chart of microseconds per valid record: hand-written Python 0.33, Pydantic from a dict 0.71, Pydantic from a JSON string 0.87](diagrams/14.3-bench.svg "Cost per valid record, median of 5 runs. Measured on one arm64 Mac; your numbers will differ.")

On this machine the hand-written code was about twice as fast per record. Pydantic does more work per call: it builds a model object, collects errors and handles the JSON path. The advantage of Pydantic here is correctness and declared structure, not raw speed on flat records. I did not measure nested models or large documents, so I make no claim about them.

> [!TRAP]
> `Optional[int]` with no default is required, not optional. In Pydantic V2 the field must be present; it may hold `None`, but it does not default to `None`. The Pydantic migration guide states this explicitly (Pydantic docs, Migration guide). The run below confirms it.

<details><summary>Run locally: needs pip install pydantic</summary>

```python
from typing import Optional
from pydantic import BaseModel, ValidationError

class NoDefault(BaseModel):
    age: Optional[int]

class WithDefault(BaseModel):
    age: Optional[int] = None

try:
    NoDefault()
except ValidationError as e:
    print(e.errors()[0]["type"], e.errors()[0]["loc"])
print(WithDefault().age)
```

```output
missing ('age',)
None
```

</details>

> [!TRAP]
> Plain `int()` truncates `1.5` to `1` without an error. Pydantic in lax mode rejects the same value with `int_from_float`. If you convert with `int()` before validating, the check has already been lost.

> [!TRAP]
> Lax mode accepts `"nan"` for a `float` field. In the run, `'nan'` converted to a `float` with no error. If NaN (not a number) is not valid in your data, add a check of your own; the default does not catch it.

> [!TRAP]
> The timing above is one machine, one Python build and one micro-benchmark. Do not generalise it to "Pydantic is slow" or "Rust is fast"; measure your own workload.

## Where validation belongs

The title says "Rust backend", so to be precise: this lesson does not start or call a separate Rust service. The Rust code is the compiled core inside `pydantic-core`, which Pydantic installs as a package. You do not write any Rust to use it.

Python does not check annotations while a function runs. A function declared as `def f(n: int)` accepts `"3"` and fails later, wherever the string is used as an integer. Static checkers such as mypy (Lesson 14.1) check annotations before the program runs. Pydantic checks the values at run time. The two complement each other: a static checker verifies your code's internal consistency, and a runtime validator verifies data from outside.

A design rule follows (reasoning from first principles, not a measured result): validate at the boundary, where untrusted data enters your program, such as a request handler or a file reader. Convert the input into a model there, and pass the model object, not the raw `dict`, to the rest of the code. The rest of the code can then rely on the types without re-checking. This holds only if every entry point goes through the model; one path that skips it reopens the problem.

## Summary

- A Pydantic model's schema is compiled once, at class definition; `model_validate` runs the compiled validator on each input.
- Lax mode converts well-defined inputs (`"3"` to `3`, `"21.5"` to `21.5`); strict mode accepts only the declared type.
- Validation collects all errors in one pass; each error has a `loc`, a `type` code and a message.
- `Optional[int]` without a default is required in V2.
- Pydantic's checks are written in Rust, but on this benchmark plain Python with the same checks was faster per record.

## Quiz time

### Question 1: Predict the result

For the `Reading` model above, what does `Reading.model_validate({"sensor_id": "S-042", "temperature_c": "hot", "count": "3"})` raise?

<details><summary>Show Solution</summary>

It raises one `ValidationError` with one entry: `temperature_c` with type `float_parsing`. The sensor ID matches the pattern, and `count` is `"3"`, which lax mode converts to `3` and accepts. Only the float conversion of `"hot"` fails.

</details>

### Question 2: Bug-spotting

A colleague writes `class Sample(BaseModel): note: Optional[str]` and then calls `Sample()` to create a default object. What happens, and why?

<details><summary>Show Solution</summary>

It raises a `ValidationError` with type `missing`, because `Optional[str]` with no default makes the field required (it may hold `None`, but it must be supplied). The fix is `note: Optional[str] = None`, which the run above confirmed behaves as intended.

</details>

### Question 3: Lax versus strict

Given `int(1.5)` in plain Python and `TypeAdapter(int).validate_python(1.5)` in Pydantic, which one fails, and why does the other not?

<details><summary>Show Solution</summary>

Plain `int(1.5)` returns `1` silently, because `int()` truncates toward zero. Pydantic's lax-mode `int` rejects `1.5` with `int_from_float`, because it accepts a float for an `int` field only when the value has no fractional part. Pydantic makes the information loss an explicit error.

</details>

### Question 4: Explain the mechanism

Why does constructing a model with a bad input not re-build the schema, and what object does the work?

<details><summary>Show Solution</summary>

The schema is built when the `class` statement runs and stored as `Reading.__pydantic_validator__`, an instance of `pydantic_core._pydantic_core.SchemaValidator`. Each call to `model_validate` runs that compiled validator on the input; it does not re-read the annotations. Only the validator object does the parsing, and it is implemented in Rust inside `pydantic-core`.

</details>
