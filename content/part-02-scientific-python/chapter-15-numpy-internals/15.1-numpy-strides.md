In this lesson you will find where any element of a NumPy array sits in memory from its shape, data type and strides. You will also say whether an array is C-order or Fortran-order, and predict whether an operation returns a view (same bytes) or a copy (new bytes).

**You need:** Python lists, and the idea that a variable names an object (Lesson 2.1). NumPy itself is introduced in the text as we go.

## The problem layout solves

A NumPy array is a description (shape and data type) sitting on top of one flat block of bytes. Two arrays can show the same numbers and still store them in different orders. The order decides which operations are free. Transposing with `a.T` is instant and copies nothing. Converting to Fortran order with `np.asfortranarray(a)` has to rearrange every value. The order also affects how quickly a loop walks the data, because the processor fetches memory in fixed-size chunks (see the performance section below).

An array is **contiguous** when its elements, taken in index order, sit next to each other in memory with no gaps. NumPy records this in two flags, `C_CONTIGUOUS` and `F_CONTIGUOUS`, which you can read from `arr.flags`. The strides carry the same information in more detail. For a C-contiguous array, the last stride equals `itemsize`, and each earlier stride equals the next stride times the length of the next axis. For a Fortran-contiguous array the rule runs the other way, starting from the first axis. These rules assume no axis has length 1, which is why the traps section warns about such axes.

## Intuition: a grid is flattened into a line

Memory is one-dimensional, so a 2-by-3 grid must be laid out as six slots in a row. There are two conventions. **C order** (row-major, NumPy's default) stores each row in turn, so the last index changes fastest. **Fortran order** (column-major) stores each column in turn, so the first index changes fastest. The figure shows the same six values under both rules.

![Two 2-by-3 grids holding 1 to 6. In C order the buffer reads 1 2 3 4 5 6; in Fortran order it reads 1 4 2 5 3 6. Each buffer slot is labelled with its byte offset.](diagrams/15.1-c-vs-fortran-order.svg "Same grid, two byte orders. The number under each slot is its byte offset from the start of the buffer.")

## Worked example by hand

Take `arr = [[1, 2, 3], [4, 5, 6]]` stored as `int32`. Each value occupies 4 bytes, which NumPy reports as `itemsize`. The **strides** are the number of bytes to step along each axis:

- One step along axis 0 (down a row) skips 3 values: $3 \times 4 = 12$ bytes.
- One step along axis 1 (along a row) skips 1 value: 4 bytes.

So `arr.strides` is $(12, 4)$. The byte offset of element $[i, j]$ is the dot product of its index with the strides:

$$
\text{offset}(i, j) = i \cdot s_0 + j \cdot s_1
$$

For $[1, 2]$ this gives $1 \cdot 12 + 2 \cdot 4 = 20$. Byte 20 is the sixth slot in the figure, and it holds 6.

Now transpose it. `t = arr.T` has shape $(3, 2)$ and strides $(4, 12)$. The same byte 20 is reached by the index $[2, 1]$, because $2 \cdot 4 + 1 \cdot 12 = 20$. The figure shows both index maps on one buffer. Transposing swaps the strides and leaves the six values where they are.

![One buffer of six values with byte offsets 0 to 20. Box one: arr has strides (12, 4), element [1, 2], 1 times 12 plus 2 times 4 equals 20, value 6. Box two: arr.T has strides (4, 12), element [2, 1], 2 times 4 plus 1 times 12 equals 20, value 6.](diagrams/15.1-strides-offset.svg "One buffer, two index maps. Transposing swaps the strides; the six values stay where they are.")

Check every number in NumPy:

```python
import numpy as np

arr = np.array([[1, 2, 3], [4, 5, 6]], dtype=np.int32)

print("shape:", arr.shape)
print("itemsize (bytes per value):", arr.itemsize)
print("strides (bytes per step):", arr.strides)
print("C-contiguous:", arr.flags['C_CONTIGUOUS'], " F-contiguous:", arr.flags['F_CONTIGUOUS'])

# byte offset of element [i, j] = i*stride0 + j*stride1
i, j = 1, 2
offset = i * arr.strides[0] + j * arr.strides[1]
print(f"element [{i}, {j}] is at byte {offset}")
print("value there:", arr.ravel()[offset // arr.itemsize])

t = arr.T
print("transposed shape:", t.shape, "strides:", t.strides)
print("t[2, 1] =", t[2, 1], "| same byte as arr[1, 2]:", 2 * t.strides[0] + 1 * t.strides[1] == offset)
print("share memory:", np.shares_memory(arr, t))
```

```output
shape: (2, 3)
itemsize (bytes per value): 4
strides (bytes per step): (12, 4)
C-contiguous: True  F-contiguous: False
element [1, 2] is at byte 20
value there: 6
transposed shape: (3, 2) strides: (4, 12)
t[2, 1] = 6 | same byte as arr[1, 2]: True
share memory: True
```

The offset rule reproduces the value 6. The transpose has its own strides but the same bytes, which is why `np.shares_memory` returns `True`.

The same contiguity rule gives the strides for any C-order array. For shape $(d_0, d_1, d_2)$ and `itemsize` $b$, the stride of axis $k$ is $b \prod_{m > k} d_m$. The NumPy documentation's own example, shape $(2, 3, 4)$ of `int32`, gives $(48, 16, 4)$: $4 \cdot 3 \cdot 4 = 48$, $4 \cdot 4 = 16$, and $4$ (Reference 1).

## Fortran order: the same idea with other strides

`np.asfortranarray(arr)` stores the columns one after another, so its buffer reads 1, 4, 2, 5, 3, 6 (bottom row of the first figure). Its strides are $(4, 8)$: one step down a column is 4 bytes, and one step along a row skips the 2 values of a column. The values are equal to `arr`, but the bytes are a different sequence, so NumPy must allocate a new buffer.

```python
import numpy as np

a = np.array([[1, 2, 3], [4, 5, 6]], dtype=np.int32)

f = np.asfortranarray(a)
print("Fortran copy strides:", f.strides, " same values:", np.array_equal(f, a))
print("bytes in Fortran order:", f.ravel(order="K").tolist())
print("share memory with a:", np.shares_memory(a, f))

tests = {
    "a.T": a.T,
    "a.reshape(-1)": a.reshape(-1),
    "a.T.ravel(order='A')": a.T.ravel(order="A"),
    "a.T.reshape(-1)": a.T.reshape(-1),
    "a.T.copy()": a.T.copy(),
    "np.asfortranarray(a)": f,
}
for name, result in tests.items():
    print(f"{name:24s} view={np.shares_memory(a, result)}")

# the transposed-then-flattened result really is independent
b = a.T.reshape(-1)
b[0] = 99
print("after writing b[0], a[0, 0] =", a[0, 0])
```

```output
Fortran copy strides: (4, 8)  same values: True
bytes in Fortran order: [1, 4, 2, 5, 3, 6]
share memory with a: False
a.T                      view=True
a.reshape(-1)            view=True
a.T.ravel(order='A')     view=True
a.T.reshape(-1)          view=False
a.T.copy()               view=False
np.asfortranarray(a)     view=False
after writing b[0], a[0, 0] = 1
```

A view keeps the bytes and only changes how they are read. A transpose or a basic slice can do that. A flattened transpose cannot, because its element order is not expressible with the existing bytes and new strides. Basic slicing (`x[1:3]`) always returns a view, while advanced indexing with an array of positions (`x[[0, 1]]`) always returns a copy (Reference 2). Lesson 15.4 covers views and indexing in depth. Here the point is narrower: a view is a second way of reading the same bytes, which is why it costs nothing and why writing through it changes the original. The figure below summarises which results share memory.

![Six operations on the 2-by-3 array a, each with a verdict: a.T, a.reshape(-1) and a.T.ravel(order A) are views; a.T.reshape(-1), a.T.copy() and np.asfortranarray(a) are copies.](diagrams/15.1-view-or-copy.svg "Whether each result shares memory with a. A view needs strides that can describe the result.")

## Performance: why layout matters

Here the layout matters for speed, not just for bookkeeping. In a 1000-by-1000 `float64` matrix in C order, one step along a row moves 8 bytes, but one step down a column moves 8000 bytes. A processor does not fetch single values. It fetches whole **cache lines**, which are typically 64 bytes, or eight `float64` values.

Walking a row uses all eight values in each line it fetches. Walking a column uses one value per line. The next block counts the lines for each walk. It assumes that the array starts on a 64-byte boundary.

```python
import numpy as np

z = np.zeros((3, 1))
print("zeros((3, 1)) strides:", z.strides, "C:", z.flags['C_CONTIGUOUS'], "F:", z.flags['F_CONTIGUOUS'])

col = np.arange(12, dtype=np.int32).reshape(3, 4)[:, ::2]
print("column slice [:, ::2] strides:", col.strides, "C:", col.flags['C_CONTIGUOUS'], "F:", col.flags['F_CONTIGUOUS'])

big = np.zeros((1000, 1000), dtype=np.float64)
print("1000x1000 float64 strides:", big.strides)
print("values per 64-byte cache line:", 64 // big.itemsize)

LINE = 64
row0 = [j * big.strides[1] for j in range(1000)]
col0 = [i * big.strides[0] for i in range(1000)]
lines = lambda offs: len({o // LINE for o in offs})
print("row walk: cache lines", lines(row0), "bytes loaded/useful", lines(row0) * LINE / (1000 * 8))
print("column walk: cache lines", lines(col0), "bytes loaded/useful", lines(col0) * LINE / (1000 * 8))
```

```output
zeros((3, 1)) strides: (8, 8) C: True F: True
column slice [:, ::2] strides: (16, 8) C: False F: False
1000x1000 float64 strides: (8000, 8)
values per 64-byte cache line: 8
row walk: cache lines 125 bytes loaded/useful 1.0
column walk: cache lines 1000 bytes loaded/useful 8.0
```

The row walk needs 125 lines for its 1000 values, so the bytes loaded match the bytes used. The column walk needs 1000 lines, so it loads eight times the bytes it uses. This is a model built from first principles, not a measurement. It assumes 64-byte cache lines, and real speed depends on the cache hierarchy of your machine and on whether a library reorders the loop for you. A Fortran-order matrix reverses the roles: the column walk becomes the cheap one. To see the effect on your hardware, time both walks with `%timeit` before you draw conclusions.

The figure shows the two walks.

![Left: a row walk of a C-order matrix uses all eight values of one 64-byte cache line. Right: a column walk touches one value in each of many lines, shown here as three of the 1000 lines. Counts: 125 lines versus 1000 lines, with 1.0x versus 8.0x bytes loaded per useful byte.](diagrams/15.1-cache-lines.svg "Row walk versus column walk. ## Common traps

> [!TRAP]
> Strides are in bytes, not elements. `(12, 4)` for `int32` means 3 values and 1 value. Divide by `itemsize` to get element steps.

> [!TRAP]
> `a.T` is a view. Writing `t[0, 0] = 10` changes `a` as well. Call `.copy()` when you need an independent array.

> [!TRAP]
> `reshape` and `ravel` copy when the strides cannot describe the result. After a transpose, `a.T.reshape(-1)` is a copy: writing to it leaves `a` unchanged (the second code block shows this).

> [!TRAP]
> Both contiguity flags can be `True` at once. `zeros((3, 1))` is C- and Fortran-contiguous, and its stride along the length-1 axis (8 here) carries no meaning. Read the layout from the flags, not from the length-1 strides.

> [!TRAP]
> Equal values do not mean equal layout. `np.asfortranarray(a)` equals `a` element by element but has its own buffer and different strides.

## Summary

- Strides are the bytes to step along each axis. An element's byte offset is the dot product of its index with the strides.
- C order (NumPy's default) varies the last index fastest. Fortran order varies the first index fastest.
- Transposing and basic slicing return views: same bytes, new strides.
- `reshape` and `ravel` return copies when the strides cannot describe the result. A Fortran-order conversion of a C-order array is a copy.
- Walking a C-order matrix down a column touches many cache lines. Measure before you optimise.

## Quiz time

### Question 1: Calculation

Let `x = np.arange(12, dtype=np.int64).reshape(3, 4)`. What are `x.strides`?

<details><summary>Show solution</summary>

`(32, 8)`. Each row holds 4 values of 8 bytes, so one step down a row skips $4 \times 8 = 32$ bytes. One step along a row skips one 8-byte value.

</details>

### Question 2: Prediction

Let `c = np.arange(6, dtype=np.int32).reshape(2, 3)` and `t = c.T`. What are `t.strides`, and is `t` C-contiguous?

<details><summary>Show solution</summary>

`t.strides` is `(4, 12)`, and `t` is not C-contiguous (`False`). The transpose swaps the two strides of `c`, which are `(12, 4)`. Walking along the first axis of `t` now moves by 4 bytes, the layout of a Fortran-order array.

</details>

### Question 3: Bug-spotting

```python
import numpy as np

a = np.zeros((2, 3))
b = a.T.reshape(-1)
b[0] = 5
print(a[0, 0])
```

What is printed, and why?

<details><summary>Show solution</summary>

It prints `0.0`. `a.T` is not C-contiguous, so `reshape` cannot flatten it by changing strides and returns a copy. Writing to `b` changes only that copy. If you need the write to reach `a`, index `a` (or `a.T`) directly.

</details>

### Question 4: Explanation

Why must `np.asfortranarray(a)` allocate a new buffer for the 2-by-3 array in this lesson, rather than return a view?

<details><summary>Show solution</summary>

A view keeps the same bytes and changes only how they are read. The C-order buffer holds `1, 2, 3, 4, 5, 6`. The Fortran-order array needs the bytes `1, 4, 2, 5, 3, 6`, which is a different byte sequence (the second code block printed it). No change of strides can turn one sequence into the other, so NumPy has to write new bytes.

</details>
