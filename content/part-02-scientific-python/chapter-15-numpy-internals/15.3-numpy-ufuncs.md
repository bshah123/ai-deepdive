In this lesson you will learn what one NumPy ufunc call does, how NumPy picks the inner loop and the result dtype from the input dtypes, and why the same operator can return a float or wrap around silently. You will also measure what the vectorized call saves.

**You need:** broadcasting (Lesson 15.2) and the idea of a dtype, the element type of an array such as `int32` (32-bit integer) or `float64` (64-bit floating point).

## The problem ufuncs solve

Add two lists of a million numbers in pure Python and the interpreter runs one step per element: fetch `i`, fetch two values, add, store, repeat. Each step costs interpreter time, and that time is spent on bookkeeping rather than arithmetic.

NumPy's answer is the **universal function**, or **ufunc**: one Python call, `np.add(a, b)`, that hands the whole buffer to a compiled C loop.

![A Python loop repeats one interpreter step per element; np.add makes one Python call and one compiled C loop runs over the buffer](diagrams/15.3-loop-vs-ufunc.svg "Who runs the loop. Same result, same dtype; the difference is how many times Python runs.")

## What a ufunc is

NumPy's reference defines a ufunc as "a function that operates on ndarrays in an element-by-element fashion, supporting array broadcasting, type casting, and several other standard features" (NumPy, *Universal functions (ufunc) basics*). Every ufunc has an inner loop: "a one-dimensional strided loop that implements the actual function for a specific type combination" (same source). Two things follow from that sentence. The loop is written once for one-dimensional data, so higher-dimensional arrays are handled by stepping through them with strides (Lesson 15.1). And there is one loop per dtype combination, so the dtypes decide which code runs.

When you call `np.add(a, b)`, four things happen in order.

![Five steps of a ufunc call: inputs, type lookup, broadcast, allocate output, inner loop](diagrams/15.3-dispatch.svg "What np.add(a, b) does, in order, for two int32 arrays of length 5.")

1. **Type lookup.** NumPy searches the ufunc's list of supported signatures. `np.add.types` in NumPy 2.5.5 lists 22 of them. The list starts with `'??->?'` and `'bb->b'`, and includes `'ii->i'`, which means two `int32` inputs and one `int32` output.
2. **Broadcast.** The input shapes are aligned by the rules of Lesson 15.2.
3. **Allocate.** A new output array is created, unless you pass `out=`.
4. **Inner loop.** The compiled loop walks the elements.

## Worked example by hand

Take `a = [1, 2, 3, 4, 5]` and `b = [6, 7, 8, 9, 10]`, both `int32`. Element by element:

- Sum: $1+6=7$, $2+7=9$, …, $5+10=15$, giving $[7, 9, 11, 13, 15]$.
- Product: $1\cdot 6=6$, …, $5\cdot 10=50$, giving $[6, 14, 24, 36, 50]$.
- Difference: $1-6=-5$ for every position, giving $[-5, -5, -5, -5, -5]$.
- Power: $1^6=1$, $2^7=128$, $3^8=6561$, $4^9=262144$, $5^{10}=9765625$.

The code reproduces each line:

```python
import numpy as np

a = np.array([1, 2, 3, 4, 5], dtype=np.int32)
b = np.array([6, 7, 8, 9, 10], dtype=np.int32)
print("add     :", np.add(a, b))
print("multiply:", np.multiply(a, b))
print("subtract:", np.subtract(a, b))
print("power   :", np.power(a, b))
print("dtype   :", np.add(a, b).dtype)
```

```output
add     : [ 7  9 11 13 15]
multiply: [ 6 14 24 36 50]
subtract: [-5 -5 -5 -5 -5]
power   : [      1     128    6561  262144 9765625]
dtype   : int32
```

## Which loop runs: type resolution

The rule is in NumPy's basics page: if no loop matches the input dtypes exactly, NumPy looks for a signature to which all inputs can be cast "safely", and "the first one it finds in its internal list of loops is selected" (NumPy, *Universal functions (ufunc) basics*). Values never enter the decision. Only dtypes do.

![Four calls: int32 with int32 gives int32; int32 divided by int32 gives float64; int32 with float64 gives float64; an int8 array with the Python int 1000 raises OverflowError](diagrams/15.3-type-resolution.svg "The result dtype follows from the input dtypes. The highlighted row looks like a bug and is not.")

Division is the case that surprises people. Dividing two `int32` arrays does not give an integer array. The `divide` ufunc uses true division and has no integer loops. For `int8`, `int16`, `int32`, `int64` and `uint8` inputs, NumPy's result is `float64` (the `dd->d` loop). The ufunc page does not document the rule that picks that loop, so check the result dtype rather than assume it. Run on this machine, `np.divide` of two `int64` arrays gives `[3.5]` with dtype `float64`.

Python scalars follow a different rule. Under NEP 50 (NumPy Enhancement Proposal 50, "Promotion rules for Python scalars"), a Python `int` is "weakly typed": it takes the dtype of the array it meets, and its value is used only to convert it. If the value does not fit, NumPy raises an error. That is why `np.add(np.array([100], dtype=np.int8), 1000)` raises `OverflowError`, while the same array plus `27` gives `127`.

## Silent overflow

Integer arithmetic in a ufunc wraps around at the limits of the dtype and raises nothing. The product $100000 \times 100000 = 10^{10}$ does not fit in `int32`, whose range is $-2^{31}$ to $2^{31}-1$.

![A number line for int32 with the stored value 1,410,065,408 marked; the exact product 10,000,000,000 lies outside the range](diagrams/15.3-overflow.svg "int32 keeps only the low 32 bits of the exact product.")

The stored result is $10^{10} - 2\cdot 2^{32} = 1{,}410{,}065{,}408$, which lies inside the `int32` range, so nothing signals the error. NumPy's ufunc reference says the same about reductions: a data type whose range is "too small" to handle the result "will silently wrap" (NumPy, *Universal functions (ufunc)*).

## Methods, out= and where=

A ufunc has five methods. `reduce` collapses an axis, `accumulate` keeps the running results, `reduceat` reduces over the index ranges you give, `outer` applies the operator to every pair, and `at` performs an unbuffered in-place update. This lesson uses the first four and `at`. Two keyword arguments control memory. `out=` writes into an array you supply, so no new array is allocated. `where=` computes only at positions where the mask is `True`; elsewhere the output keeps its previous value.

```python
import numpy as np

a = np.array([1, 2, 3, 4, 5])
print("reduce     :", np.add.reduce(a))
print("accumulate :", np.add.accumulate(a))
print("outer      :")
print(np.multiply.outer(np.array([1, 2, 3]), np.array([10, 20])))

x = np.array([1.0, 2.0, 3.0])
y = np.array([10.0, 20.0, 30.0])
np.add(x, y, out=x)                       # result goes into x; no new array
print("in place   :", x)

num = np.array([4.0, 0.0, 9.0])
den = np.array([2.0, 0.0, 3.0])
print("guarded    :", np.divide(num, den, out=np.zeros_like(num), where=den != 0))

idx = np.array([0, 0, 2])
plain = np.zeros(3, dtype=np.int64)
plain[idx] += 1                           # buffered: index 0 counted once
unbuf = np.zeros(3, dtype=np.int64)
np.add.at(unbuf, idx, 1)                  # unbuffered: index 0 counted twice
print("plus-equal :", plain)
print("ufunc.at   :", unbuf)
```

```output
reduce     : 15
accumulate : [ 1  3  6 10 15]
outer      :
[[10 20]
 [20 40]
 [30 60]]
in place   : [11. 22. 33.]
guarded    : [2. 0. 3.]
plus-equal : [1 0 1]
ufunc.at   : [2 0 1]
```

The last two lines show the difference between `a[idx] += 1` and `np.add.at`. The NumPy reference gives the same example: `a[[0,0]] += 1` increments the first element once "because of buffering", whereas `add.at(a, [0,0], 1)` increments it twice (NumPy, *numpy.ufunc.at*).

## Measured cost: loop versus ufunc

The timing numbers below come from one machine, an arm64 Mac running Python 3.12.13 and NumPy 2.5.5. Each value is the median of five repeats. The Python loop builds a list of floats, and the ufunc returns an array. Your numbers will differ, but the shape of the result should not.

![Log-scale bars: at 10 elements the loop and ufunc take about the same time; at 1,000 elements the ufunc is 67 times faster; at 1,000,000 elements it is 117 times faster](diagrams/15.3-timing.svg "Measured time per call, log scale. The ratio is loop time divided by ufunc time.")

At 10 elements the two are within a factor of about 1.3. I did not profile that case, so I cannot say where the time goes. At a million elements the ufunc is more than 100 times faster on this machine. My reading, not a profiled result, is that most of the gap is the per-element interpreter work that the C loop avoids. The script that produced these numbers is `scripts/diagrams/lessons/15.3_experiment.py` in the course repository. It is not a checked code block here, because its output depends on hardware.

> [!TRAP]
> Do not expect a ufunc to beat a loop on tiny arrays. The advantage grows with the number of elements, and a call that touches 10 numbers pays the same dispatch cost as one that touches a million.

Why the C loop is fast is partly the compiled code and partly SIMD (single instruction, multiple data), where one instruction works on several values at once. NumPy's SIMD page describes kernels compiled for several CPU feature sets at build time, with the one matching the CPU chosen when NumPy is imported (NumPy, *CPU/SIMD optimizations*). That page does not name ufunc inner loops, so I have not confirmed that every ufunc uses those kernels. Treat SIMD as the likely reason for the speed, not as a verified one.

## Common traps

> [!TRAP]
> `np.divide` on integer arrays returns `float64`. This is true division, not a bug. Use `//` on the arrays if you want floor division with an integer result.

> [!TRAP]
> Integer overflow is silent. `np.multiply` on `int32` values whose product is too large wraps around with no warning, and the same happens to `np.add` on `int8` values when the sum exceeds 127.

> [!TRAP]
> `a[idx] += 1` counts each repeated index once. Use `np.add.at(a, idx, 1)` when repeats must accumulate.

> [!TRAP]
> A Python `int` does not change the result dtype of an array operation. If its value does not fit the array's dtype, NumPy raises `OverflowError`.

## Summary

- A ufunc is a vectorized wrapper around a compiled inner loop, and one call replaces a Python loop over the elements.
- The loop is chosen from the input dtypes by NumPy's casting search over its loop list; values are not inspected.
- Integer results wrap silently at the limits of the dtype, and integer division with `/` returns `float64`.
- `out=` and `where=` control memory and masking, and `np.add.at` is the unbuffered way to accumulate repeated indices.
- The speed advantage appears with many elements; on the 10-element case used here it is only about 1.3 times.

## Quiz time

### Question 1: Calculation

What does `np.multiply(np.array([2**30], dtype=np.int32), 4)` return? Show the exact product first.

<details><summary>Show Solution</summary>

The exact product is $2^{30} \cdot 4 = 2^{32}$. An `int32` keeps only the low 32 bits, and $2^{32} \bmod 2^{32} = 0$. The result is `[0]`, with no error. The Python `4` fits in `int32`, so NEP 50 raises no error either.

</details>

### Question 2: Prediction

What are the values and dtype of `np.divide(np.array([7], dtype=np.int64), np.array([2], dtype=np.int64))`?

<details><summary>Show Solution</summary>

The result is `[3.5]` with dtype `float64`. Division uses the true-division loop, which produces floating-point output for integer inputs, as the type-resolution section explains. Floor division would be `//` and would give `[3]`.

</details>

### Question 3: Find the bug

A student counts hits per bin:

```python
import numpy as np

counts = np.zeros(4, dtype=np.int64)
counts[[1, 1, 3]] += 1
print(counts)
```

The student expects `[0 2 0 1]`. What is printed, and what change fixes it?

<details><summary>Show Solution</summary>

It prints `[0 1 0 1]`. The fancy-index `+=` reads each index once and writes back, so the repeated index 1 is incremented only once. The fix is `np.add.at(counts, [1, 1, 3], 1)`, which is unbuffered and applies the increment for every occurrence.

</details>

### Question 4: Explanation

Explain why `np.add(np.array([100], dtype=np.int8), 27)` returns `[127]`, while `np.add(np.array([100], dtype=np.int8), 100)` returns `[-56]` with no error.

<details><summary>Show Solution</summary>

Under NEP 50 the Python int takes the array's dtype `int8`. Both values fit in `int8`, so no conversion error occurs. The sum $100 + 27 = 127$ is the largest `int8` value and is representable. The sum $100 + 100 = 200$ is not, and it wraps modulo 256 to $200 - 256 = -56$. Overflow in the arithmetic is silent; only a value that cannot be converted to the dtype raises an error.

</details>
