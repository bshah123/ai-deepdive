In this lesson you will predict whether a NumPy operation returns a **view** (a new array object that shares memory with the original) or a **copy** (a new array with its own memory), confirm the answer with `np.may_share_memory`, and avoid the in-place update that silently changes data you meant to keep.

**You need:** NumPy arrays, their shape and dtype. Lesson 15.1 covers strides and memory layout, which this lesson uses.

## The problem

A float64 array of 1,000,000 elements takes 8,000,000 bytes, or 8 MB. Taking a slice to read a few values should not cost 8 MB, but sometimes a copy is genuinely needed. The indexing you choose also decides whether writing to the slice changes the original. Getting this wrong causes two bugs: data changes you did not expect, and memory use that grows because a copy was made where a view would have done.

## Intuition: an array is a header plus a buffer

A NumPy array is a small **header** (dtype, shape, strides and an offset into the memory) that points to a **buffer** of bytes. A view is a new header that points into an existing buffer. A copy is a new header with a new buffer. Nothing is moved when you make a view; only the header is written.

![Left: a view is a new header with an offset of 8 bytes and the same buffer as a, covering cells 1 to 3. Right: a copy is a header with a new buffer holding the same values](diagrams/15.4-view-vs-copy.svg "A view adds a header; a copy adds a header and a buffer.")

A step slice keeps the same buffer and changes only the stride, the number of bytes to move between consecutive elements:

![Every other cell of the buffer is selected; the stride doubles from 8 to 16 bytes, so the view reads bytes 0, 16 and 32](diagrams/15.4-step-slice.svg "a[::2] reads the same buffer with a doubled stride.")

## Worked example by hand

Take `a = [1, 2, 3, 4, 5]` with dtype int64. Each element is 8 bytes, so the buffer is 40 bytes long.

- `a[1:4]` starts 1 × 8 = 8 bytes into the buffer, keeps stride 8, and has three elements: 2, 3, 4.
- `a[::2]` starts at byte 0 and has stride 2 × 8 = 16 bytes, so it reads bytes 0, 16 and 32: the values 1, 3, 5.
- `a[[0, 2, 4]]` uses an integer array as the index. These elements are not at one regular stride, so NumPy must gather them into a new buffer.

The code below reproduces these numbers. The memory addresses are not printed; only their difference is meaningful.

```python
import numpy as np

a = np.array([1, 2, 3, 4, 5])
v = a[1:4]        # basic slice: view
s = a[::2]        # basic slice with a step: view
f = a[[0, 2, 4]]  # integer-array index: copy
m = a[a > 2]      # boolean mask: copy

def addr(x):      # address of the first element; only differences matter
    return x.__array_interface__["data"][0]

print("v shares memory with a:", np.shares_memory(v, a))
print("v starts", addr(v) - addr(a), "bytes after a[0]; strides:", v.strides)
print("s strides:", s.strides, " values:", s)
print("f shares memory with a:", np.may_share_memory(f, a), " f.base is None:", f.base is None)
print("m values:", m)
print("even and odd slices: may share", np.may_share_memory(a[::2], a[1::2]),
      " share", np.shares_memory(a[::2], a[1::2]))

v[0] = 20          # writes into the buffer that a also uses
print("a after v[0] = 20:", a)
```

```output
v shares memory with a: True
v starts 8 bytes after a[0]; strides: (8,)
s strides: (16,)  values: [1 3 5]
f shares memory with a: False  f.base is None: True
m values: [3 4 5]
even and odd slices: may share True  share False
a after v[0] = 20: [ 1 20  3  4  5]
```

## Which indexing returns a view?

The NumPy indexing documentation states the rule. Basic indexing (integers, slices, ellipsis and newaxis) returns a view. Advanced indexing returns a copy: "Advanced indexing always returns a *copy* of the data (contrast with basic slicing that returns a view)" (NumPy, Indexing on ndarrays). Advanced indexing has two forms, integer arrays and boolean arrays, and both copy.

![A table of expressions and their results: slices, step slices and one integer index on a 2-D array return views; a scalar from a 1-D integer index is a NumPy scalar; integer arrays, boolean masks, and copy() or flatten() return copies; reshape returns a view only when possible](diagrams/15.4-indexing-rules.svg "Basic indexing gives views; advanced indexing gives copies; reshape depends on layout.")

Single-element access is a separate case. `a[2]` on a 1-D array returns a NumPy scalar (`numpy.int64`), not an array, so it holds one value, not a window onto the buffer.

## Reshape, ravel and transpose depend on memory layout

`reshape` is documented as returning "a new view object if possible; otherwise, it will be a copy" (NumPy, `numpy.reshape`). Whether it is possible depends on the strides. A transpose just reverses the axes and strides, so it is always a view. Flattening a transposed array is the case that fails. Take `x` with shape (3, 4). Its transpose has shape (4, 3) and strides (8, 32) bytes, measured in the experiment. Reading `x.T` in row-major order visits byte offsets 0, 32, 64, 8, 40, 72, and so on. These offsets do not form one constant stride, so no 1-D view can express them, and NumPy copies (this explanation is my reasoning from the strides; NumPy's documentation states the outcome, not the mechanism).

The figure below measures the cost on a 1,000,000-element float64 array (8 MB). Each bar is the peak number of bytes that the operation allocated.

![Bar chart: views allocate 96 to 192 bytes; integer-array and boolean-mask copies allocate about 4 MB; copy(), flatten() and reshape of a transposed array allocate about 8 MB](diagrams/15.4-memory-bars.svg "Peak bytes allocated per operation on 1,000,000 float64 values, measured with tracemalloc.")

> [!TIP]
> Do not test for a copy with `arr.flags.owndata`. The result of `t.reshape(-1)` on a transposed array is a copy, yet its `owndata` is `False` (see the next code block). Compare the result with the original using `np.may_share_memory` instead.

```python
import numpy as np

big = np.arange(1_000_000, dtype=np.float64)   # 8,000,000 bytes
t = big.reshape(1000, 1000).T                  # transpose: view
print("transpose shares memory:", np.may_share_memory(t, big))
flat = t.reshape(-1)                           # flattening a transposed array: copy
print("flat shares memory:", np.may_share_memory(flat, big))
print("flat.flags.owndata:", flat.flags.owndata)
```

```output
transpose shares memory: True
flat shares memory: False
flat.flags.owndata: False
```

## In-place updates: the trap

Python evaluates `target[key] += value` in three steps: it gets `target[key]`, applies the operator, and then sets `target[key]` to the result (Python Reference, Augmented assignment). The get returns a view for basic indexing and a copy for advanced indexing. A view is written through directly. A copy changes the original only in the final set step, which runs when the subscript is on the original array. Rebinding a name with `=` never writes to the original.

```python
import numpy as np

a = np.array([1, 2, 3, 4, 5])
mask = a > 2

b = a[mask]          # boolean mask: copy
b += 10
print("a after b += 10:", a)     # unchanged
print("b:", b)

c = np.array([1, 2, 3, 4, 5])
c[c > 2] += 10       # get a copy, add, then set back into c
print("c after c[c > 2] += 10:", c)

d = np.array([1, 2, 3, 4, 5])
v = d[1:4]           # view
v = v * 2            # rebinding: v names a new array
print("d after v = v * 2:", d)

e = np.array([1, 2, 3, 4, 5])
w = e[1:4]           # view
w *= 2               # in place: writes through the view
print("e after w *= 2:", e)
```

```output
a after b += 10: [1 2 3 4 5]
b: [13 14 15]
c after c[c > 2] += 10: [ 1  2 13 14 15]
d after v = v * 2: [1 2 3 4 5]
e after w *= 2: [1 4 6 8 5]
```

![Four statements applied to the array 1 to 5: copy-then-add leaves the array unchanged; a subscript write-back changes cells 3 to 5 to 13, 14, 15; an in-place multiply on a view changes cells 2 to 4; rebinding leaves the original unchanged](diagrams/15.4-trap.svg "Only writes through the original array's memory, or a set on the original, change it.")

## Measuring instead of guessing

The byte counts above come from `tracemalloc`, the standard-library tracer for Python memory allocations. It reports the current and peak traced size. NumPy's data buffers are traced, which is why a copy shows up as megabytes while a view costs a few hundred bytes (observed here; the internal reason is not documented on the pages I opened). Timing is not shown in this lesson, because it depends on the machine.

<details><summary>Run locally: measures peak allocation with tracemalloc</summary>

```python
import tracemalloc
import numpy as np

big = np.arange(1_000_000, dtype=np.float64)   # 8,000,000 bytes
idx = np.arange(0, 1_000_000, 2)               # built outside the measurement
measure = {
    "basic slice big[1:-1]": lambda: big[1:-1],
    "integer array big[idx]": lambda: big[idx],
    "big.copy()": lambda: big.copy(),
}
for label, fn in measure.items():
    tracemalloc.start()
    fn()
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    print(f"{label:<26}{peak:>12,d} B")
```

```output
basic slice big[1:-1]               96 B
integer array big[idx]       4,000,096 B
big.copy()                   8,000,096 B
```

</details>

## Common traps

> [!TRAP]
> A slice is not a copy. `sub = big[:10]; sub[:] = 0` sets the first ten elements of `big` to zero.

> [!TRAP]
> `b = a[mask]; b += 1` leaves `a` unchanged, but `a[mask] += 1` changes it. The difference is whether the final write goes back into `a`.

> [!TRAP]
> `reshape` can copy without warning. Writing to `x.T.reshape(-1)` does not change `x` when the reshape had to copy.

> [!TRAP]
> `np.may_share_memory` answers "might share". For `a[::2]` and `a[1::2]` it returns `True` while `np.shares_memory` returns `False`, because the two address ranges interleave. `np.shares_memory` is exact but can be very slow on complicated layouts.

> [!TRAP]
> `flags.owndata` is not a reliable copy test (see the code block above). Compare against the original array instead.

## Summary

- Basic indexing (integers and slices) returns a view; advanced indexing (integer arrays and boolean masks) returns a copy.
- `reshape` returns a view when the memory layout allows it, and a copy otherwise; `transpose` is always a view; `flatten` always copies.
- Writes through a view, or an assignment back into the original with a subscript, change the original; rebinding a name does not.
- Use `np.may_share_memory` to check, and remember that `True` means "might".
- Measure peak allocations with `tracemalloc` before deciding that a copy is a problem.

## Quiz time

### Question 1: Prediction

```python
import numpy as np
x = np.arange(6)
y = x[::3]
y[1] = 99
print(x)
```

<details><summary>Show Solution</summary>

`x` is `[0 1 2 3 4 5]` and `y = x[::3]` is a view on elements 0 and 3. `y[1]` is `x[3]`, so the output is `[ 0  1  2 99  4  5]`.

</details>

### Question 2: Calculation

A float64 array `big` has 1,000,000 elements. How many bytes does `big[idx]` allocate for an integer index array `idx` with 250,000 entries?

<details><summary>Show Solution</summary>

The result is a copy with 250,000 float64 values: 250,000 × 8 = 2,000,000 bytes (2 MB). The index array `idx` has its own memory and is not counted in that figure.

</details>

### Question 3: Find the bug

```python
import numpy as np

def clip_negatives(x):
    y = x[x < 0]     # boolean mask
    y[:] = 0
    return x

print(clip_negatives(np.array([-1, 2, -3])))
```

<details><summary>Show Solution</summary>

`x[x < 0]` is advanced indexing, so `y` is a copy. Zeroing `y` leaves `x` unchanged, and the function returns `[-1  2 -3]`. The fix writes into `x` with a subscript: `x[x < 0] = 0`, which returns `[0 2 0]`.

</details>

### Question 4: Explanation

Why does `big.reshape(1000, 1000).T` allocate about 192 bytes while `big.reshape(1000, 1000).T.reshape(-1)` allocates about 8 MB?

<details><summary>Show Solution</summary>

The transpose only reorders axes and strides, so it is a view. Flattening the transpose in row-major order reads elements whose byte offsets do not form one constant stride, so no 1-D view can express the order, and NumPy copies. The copy is 1,000,000 × 8 bytes, about 8 MB.

</details>

### Question 5: Explanation

`np.may_share_memory(a[::2], a[1::2])` returns `True` but `np.shares_memory` returns `False`. Why?

<details><summary>Show Solution</summary>

`may_share_memory` checks only whether the address ranges of the two arrays overlap. The even and odd slices interleave across the same range, so the ranges overlap. `shares_memory` checks whether any element is actually shared, and none is.

</details>
