In this lesson you will learn how pandas stores a DataFrame as a few NumPy arrays called blocks. You will read a frame's block layout, predict when a write reaches the parent frame, and recognise when repeated column inserts fragment the storage.

**You need:** NumPy strides (Lesson 15.1) and views versus copies (Lesson 15.4). The pandas code is in "Run locally" blocks; it was run with pandas 3.1.1 and NumPy 2.5.5.

## The problem this solves

A DataFrame is a table whose columns can have different types: integers, floats, text. A NumPy array has exactly one dtype, so one array cannot hold the whole table. Two simple layouts fail:

- **One array per column.** Simple, but a whole-table operation then touches many small objects.
- **One array for everything.** It forces one dtype on every column, so the integers would become floats or the text would become objects.

pandas takes a middle path. Columns with the same dtype are stacked into one two-dimensional NumPy array, called a **block**. The blocks, plus the lookup tables that say which block holds each column, form the **BlockManager**. You can reach it as `df._mgr`. The leading underscore marks it as private: useful for learning, not a stable interface.

## Intuition: columns grouped by dtype

![Five columns a to s are grouped into three blocks: block 0 holds the int64 columns a and c, block 1 the float64 columns b and d, and block 2 the str column s; blknos and blklocs map each column to its block and row](diagrams/16.1-blocks.svg "Five columns, three blocks. blknos gives the block of each column, blklocs its row inside that block.")

Find column `c` by hand. Its position is 2, so `blknos[2] = 0` (block 0) and `blklocs[2] = 1` (row 1 of that block). Block 0 holds `[10, 20, 30]`, which is column `c`.

The convention to remember is that **a block's rows are DataFrame columns**. Block 0 has shape `(2, 3)`: two columns by three frame rows. The NumPy-only example below shows why this choice matters.

Grouping by dtype also means a column-wise operation can run on a whole block with one NumPy call instead of one call per column. That is reasoning (b) from the layout, not a measurement: I did not time it, and the gain depends on the number of columns and the hardware.

The code below reads the block layout directly.

<details><summary>Run locally: needs pip install pandas</summary>

```python
import numpy as np
import pandas as pd

df = pd.DataFrame({
    "a": np.array([1, 2, 3], dtype="int64"),
    "b": np.array([1.5, 2.5, 3.5]),
    "c": np.array([10, 20, 30], dtype="int64"),
    "d": np.array([0.1, 0.2, 0.3]),
    "s": ["x", "yy", "zzz"],
})
mgr = df._mgr  # private attribute: fine for inspection, not for production code
print("nblocks:", mgr.nblocks)
for i, blk in enumerate(mgr.blocks):
    print(i, type(blk).__name__, blk.dtype, blk.shape, blk.mgr_locs.as_array.tolist())
print("blknos :", mgr.blknos.tolist())
print("blklocs:", mgr.blklocs.tolist())

N = 100_000
big = pd.DataFrame({
    "a": np.arange(N, dtype="int64"),
    "b": np.linspace(0.0, 1.0, N),
    "c": np.arange(N, dtype="int64") * 2,
})
print("big blocks:", [blk.shape for blk in big._mgr.blocks])
print("bytes per column:", big.memory_usage(index=False).to_dict())
```

```output
nblocks: 3
0 NumpyBlock int64 (2, 3) [0, 2]
1 NumpyBlock float64 (2, 3) [1, 3]
2 ExtensionBlock str (1, 3) [4]
blknos : [0, 1, 0, 1, 2]
blklocs: [0, 0, 1, 1, 0]
big blocks: [(2, 100000), (1, 100000)]
bytes per column: {'a': 800000, 'b': 800000, 'c': 800000}
```

</details>

The class names (`NumpyBlock`, `ExtensionBlock`) are those of pandas 3.1.1. The `str` column is an `ExtensionBlock` because pandas' string dtype is an extension type rather than a plain NumPy dtype.

## Inside a block: one flat run of bytes

A block is an ordinary C-contiguous NumPy array. The NumPy strides rule from Lesson 15.1 says that the byte offset of element `(i, j)` is `i × stride[0] + j × stride[1]`. Run the NumPy-only check below. It runs in the browser.

```python
import numpy as np

block = np.array([[1, 2, 3],
                  [10, 20, 30]], dtype=np.int64)   # one row per DataFrame column
print("shape:", block.shape, "strides:", block.strides, "nbytes:", block.nbytes)
col_a = block[0]
print("column a:", col_a, "strides:", col_a.strides)
print("column a shares memory with block:", np.shares_memory(col_a, block))
```

```output
shape: (2, 3) strides: (24, 8) nbytes: 48
column a: [1 2 3] strides: (8,)
column a shares memory with block: True
```

The strides are `(24, 8)`. Stepping along a column of the frame (the next row) moves 8 bytes. Stepping to the next column of the block moves 24 bytes, because a row of three int64 values takes 3 × 8 = 24 bytes. Column `c` starts at byte 24, as the sketch shows.

The general rule is the offset formula from Lesson 15.1. For an element at block index $(i, j)$ with strides $(s_0, s_1)$, the byte offset from the start of the block is $i\,s_0 + j\,s_1$. Worked by hand for the last cell, column `c`, row 2 (value 30): $i = 1$, $j = 2$, so the offset is $1 \times 24 + 2 \times 8 = 40$ bytes. That is the last cell of the sketch, and the NumPy check confirms the strides that produce it.

![Block 0 as a flat run of six 8-byte cells at byte offsets 0 to 40: a0, a1, a2 then c0, c1, c2; a column is a contiguous run and the block stride from a0 to c0 is 24 bytes](diagrams/16.1-layout.svg "Block 0 is one 2 × 3 int64 array: 48 bytes. A column is one contiguous run of 8-byte steps.")

Contiguity is why a column is cheap to hand out. `df["a"]` can return a view, a window onto the same bytes, with no copy. Column-wise NumPy operations stream through memory. The cost of that layout appears when you go across dtypes, shown in the section on row access below.

With 100,000 rows, one int64 column takes 100,000 × 8 = 800,000 bytes. The `memory_usage` output above confirms that figure.

## Views and copy-on-write

Because `df["a"]` shares memory with the block, a write through a derived object could change the parent. pandas 3.0 closed that path. According to the pandas migration guide, Copy-on-Write (CoW) is "the default and only mode in pandas 3.0", and a derived DataFrame or Series behaves as a copy for writes. Setting the old `mode.copy_on_write` option now only prints a deprecation message. The run below shows both outcomes.

<details><summary>Run locally: needs pip install pandas</summary>

```python
import numpy as np
import pandas as pd

df = pd.DataFrame({
    "a": np.array([1, 2, 3], dtype="int64"),
    "b": np.array([1.5, 2.5, 3.5]),
    "c": np.array([10, 20, 30], dtype="int64"),
    "d": np.array([0.1, 0.2, 0.3]),
    "s": ["x", "yy", "zzz"],
})
x = df["a"]
x.iloc[0] = 99
print("after x.iloc[0] = 99, df['a'][0] =", df["a"].iloc[0])
df._mgr.blocks[0].values[0, 0] = 98   # writes the NumPy array under the frame
print("after the direct block write, df['a'][0] =", df["a"].iloc[0])
print("df.iloc[0].dtype:", df.iloc[0].dtype)
sub = df[["a", "c"]].to_numpy()
print("df[['a','c']].to_numpy():", sub.dtype, sub.shape)
```

```output
after x.iloc[0] = 99, df['a'][0] = 1
after the direct block write, df['a'][0] = 98
df.iloc[0].dtype: object
df[['a','c']].to_numpy(): int64 (3, 2)
```

</details>

![Two writes to column a. A write through a variable x taken from the frame leaves the frame value at 1, because x behaves as a copy. A write to the private block array under the frame changes the frame value to 98](diagrams/16.1-cow.svg "The public API is protected by copy-on-write. The private block array is not.")

The view is not copied up front. The migration guide describes the rule as: "CoW triggers a copy when `df` is changed to avoid mutating `view` as well". The copy happens at the first write to the parent, so reads stay cheap and writes stay safe.

The first write in the run is safe. The second is not: `_mgr` is outside the public API, so copy-on-write never sees it. Code that writes to `_mgr` changes data silently in every place that shares the block.

## Row access across dtypes

A block holds one dtype, so a single row that spans three dtypes has no NumPy dtype that fits it all. `df.iloc[0]` therefore returns an `object` Series, and `df.to_numpy()` on the full mixed frame does the same. Each value is stored as a Python object, which costs memory and speed (my reasoning; I did not time it, and timings depend on hardware). A column subset with one dtype stays `int64`, as the `(3, 2)` result shows.

## Fragmentation: many inserts, many blocks

Inserting a new column with `df[name] = value` appends a block for it, so a loop of inserts leaves one block per column. The sketch below counts the blocks. pandas warns once the frame is "highly fragmented". The condition in the pandas 3.1.1 source (`pandas/core/internals/managers.py`) is that the total number of blocks **and** the number of NumPy blocks both exceed 100.

<details><summary>Run locally: needs pip install pandas</summary>

```python
import warnings
import pandas as pd
from pandas.errors import PerformanceWarning

for n in (10, 50, 100, 101, 150):
    f = pd.DataFrame(index=range(3))
    with warnings.catch_warnings(record=True) as w:
        warnings.simplefilter("always")
        for i in range(n):
            f[f"f{i}"] = float(i)
    warned = any(issubclass(x.category, PerformanceWarning) for x in w)
    print(f"{n:>4} inserts -> {f._mgr.nblocks:>4} blocks, PerformanceWarning: {warned}")
g = f.copy()
print("after copy():", g._mgr.nblocks, "block, shape", g._mgr.blocks[0].shape)
```

```output
  10 inserts ->   10 blocks, PerformanceWarning: False
  50 inserts ->   50 blocks, PerformanceWarning: False
 100 inserts ->  100 blocks, PerformanceWarning: False
 101 inserts ->  101 blocks, PerformanceWarning: True
 150 inserts ->  150 blocks, PerformanceWarning: True
after copy(): 1 block, shape (150, 3)
```

</details>

![Bar chart of block counts: 10, 50 and 100 inserts give 10, 50 and 100 blocks; 101 and 150 inserts give 101 and 150 blocks, above the warning line at 100; copy() merges them into 1 block](diagrams/16.1-fragmentation.svg "Each column insert adds a block. Above 100 blocks the warning fires; copy() merges the frame into one block.")

`copy()` consolidates the frame: the 150 one-row blocks become one `(150, 3)` block. I measured block counts, not the time taken by consolidation.

## Common traps

> [!TRAP]
> Writing to `df._mgr` bypasses copy-on-write and any bookkeeping pandas does. The attribute is private and can change between releases. Use `df.loc`, `df.iloc` or column assignment.

> [!TRAP]
> Chained assignment such as `df["a"][0] = 5` does not work under copy-on-write. The migration guide says it "will consistently never work" and raises a `ChainedAssignmentError` warning. Use `df.loc[0, "a"] = 5`.

> [!TRAP]
> A loop of `df[name] = ...` produces one block per column and triggers the fragmentation warning past 100 NumPy blocks. Build the new columns once, for example with `pd.concat(new_columns, axis=1)`, or call `copy()` at the end.

> [!TRAP]
> A row loop over a mixed-dtype frame creates object values, one Python object per cell. Keep the work column-wise so each block is processed as one NumPy array.

> [!TRAP]
> A block's `values` array is transposed relative to the frame: it has shape `(columns, rows)`. For the three-row frame above, `df._mgr.blocks[0].values` has shape `(2, 3)`, not `(3, 2)`. Transpose it, or index by column first, before reading it as a table.

## Summary

- A DataFrame stores its columns in blocks. Each block is one two-dimensional NumPy array holding columns of one dtype, and its rows are DataFrame columns.
- `df._mgr` exposes the blocks and the `blknos` and `blklocs` lookup arrays. It is private.
- A numeric column is a contiguous run of bytes in its block, so `df["a"]` is a view with no copy.
- Since pandas 3.0, copy-on-write is always on: a write through a derived object does not reach the parent. Writes to `_mgr` still reach the data.
- Repeated column inserts create one block each. Past 100 NumPy blocks pandas warns, and `copy()` merges the blocks.

## Quiz time

### Question 1: Calculation
A frame has four columns: `p` (int64), `q` (float64), `r` (int64) and `t` (int64). It also has a `str` column `u`, so five columns in all. How many blocks does pandas create, and what is the shape of the block that holds `p`, `r` and `t`? Assume `n` rows.

<details><summary>Show Solution</summary>

There are three blocks. The int64 block holds `p`, `r` and `t`, so its shape is `(3, n)`: three columns by `n` rows. `q` is alone in a float64 block of shape `(1, n)`, and the `str` column `u` is an `ExtensionBlock` of shape `(1, n)`. The pattern follows the measured layout: each block's first axis counts columns and its second counts rows.

</details>

### Question 2: Prediction
Starting from the frame in the code above, you run `x = df["a"]` and then `x.iloc[0] = 99`. What is `df["a"].iloc[0]` in pandas 3.1.1?

<details><summary>Show Solution</summary>

It is `1`. Under copy-on-write, `x` behaves as a copy for writes, so the parent frame is unchanged. The run above shows this.

</details>

### Question 3: Bug-spotting
A script inserts 180 new columns into a frame with one `df[name] = ...` statement per column. It runs, but emits a `PerformanceWarning` and the frame gets slow to modify. What is the cause, and how would you fix it?

<details><summary>Show Solution</summary>

Cause: each insert appends a block, and the total passes 100 NumPy blocks, which triggers the fragmentation warning. Fix: compute the new columns into a list or dict first, then join them once with `pd.concat(new_columns, axis=1)`. A `copy()` at the end also merges existing blocks, but it does not stop the growth while inserting.

</details>

### Question 4: Explanation
Why is `df[["a", "c"]].to_numpy()` an `int64` array, while `df.iloc[0]` on the mixed frame is an `object` Series? Explain using the block layout.

<details><summary>Show Solution</summary>

Columns `a` and `c` both live in the int64 block, so pandas can return one int64 array of shape `(3, 2)`. The row `df.iloc[0]` spans the int64, float64 and `str` blocks. No single NumPy dtype holds all three, so pandas builds an object array, which stores each value as a Python object.

</details>
