In this lesson you will read an Apache Arrow string column byte by byte, predict when pandas copies memory and when it does not, and choose between CSV, Parquet and Arrow IPC (inter-process communication) files for a job. Every number comes from one experiment script, run with pandas 3.1.1 and pyarrow 26.0.1.

**You need:** how pandas stores a column (Lesson 16.1) and what a pointer is.

## The problem

A pandas numeric column is one contiguous NumPy array, so another library can read it in place. A string column is different. In object dtype each entry is a pointer to a separate Python object, so 200,000 short strings are 200,000 heap objects plus a pointer array. Another process cannot read those pointers, and a Parquet writer cannot use them without a conversion. Apache Arrow defines one columnar memory layout that every implementation reads the same way, so data can move between processes and libraries without being re-encoded.

## Intuition: a column is a few flat buffers

![Object dtype stores a pointer per value, each pointing to a scattered Python object. An Arrow string array stores three flat buffers: validity bits, offsets and data bytes.](diagrams/16.2-layout.svg "The same four values, as pandas objects and as an Arrow string array.")

An Arrow string array has three buffers. The validity bitmap holds one bit per slot: 1 for a value, 0 for null, numbered least-significant-bit first. The offsets buffer holds length + 1 integers, and slot j is the bytes from offsets[j] up to offsets[j+1]. The data buffer holds every string's bytes back to back. Nothing in the layout is a pointer, which is what lets C++, Rust and Python read the same bytes without translating them [1].

## Worked example by hand

Take four values: "ann", "bob", None and "cy".

1. **Validity.** Slots 0 to 3 are valid, valid, null, valid. Written least-significant-bit first, the bits are 1, 1, 0, 1, which is 1 + 2 + 8 = 11.
2. **Offsets.** The lengths are 3, 3, 0 and 2. A null has length 0 in this array. The running totals are 0, 3, 6, 6, 8: five int32 values, 20 bytes.
3. **Data.** Concatenate the valid strings to get "annbobcy", 8 bytes.

The payload is 1 + 20 + 8 = 29 bytes. The block below rebuilds the three buffers with the standard library only, so it runs in the browser.

```python
from itertools import accumulate

values = ["ann", "bob", None, "cy"]
valid = [v is not None for v in values]
bits = sum(1 << i for i, ok in enumerate(valid) if ok)
lengths = [len(v) if v is not None else 0 for v in values]
offsets = [0] + list(accumulate(lengths))
data = "".join(v for v in values if v is not None).encode()
print("validity byte:", bits, format(bits, "04b")[::-1], "(LSB first)")
print("offsets:", offsets)
print("data:", data)
print("payload bytes:", 1 + 4 * len(offsets) + len(data))
```

```output
validity byte: 11 1101 (LSB first)
offsets: [0, 3, 6, 6, 8]
data: b'annbobcy'
payload bytes: 29
```

## Zero-copy: measured, not assumed

Zero-copy means the consumer reads the producer's bytes without a second copy. Whether pandas does this depends on the direction of conversion and on the default arguments, so the block below tests each case. It also reads the worked example back from pyarrow to confirm the same buffers.

<details><summary>Run locally: needs pip install pandas pyarrow</summary>

Run with pandas 3.1.1 and pyarrow 26.0.1.

```python
import numpy as np
import pandas as pd
import pyarrow as pa

# 1. pa.array() wraps the NumPy buffer when there are no nulls
a = np.arange(5, dtype=np.int64)
t = pa.array(a)
a[0] = 99
print("arrow sees the change:", t[0].as_py())

# 2. the pandas constructor copies by default; copy=False keeps the buffer
x = np.arange(8, dtype=np.float64)
tab = pa.Table.from_pandas(pd.DataFrame({"x": x}, copy=False), preserve_index=False)
x[0] = -1.0
print("copy=False, arrow[0] after mutation:", tab.column("x")[0].as_py())
y = np.arange(8, dtype=np.float64)
tab2 = pa.Table.from_pandas(pd.DataFrame({"x": y}), preserve_index=False)
y[0] = -1.0
print("default, arrow[0] after mutation:", tab2.column("x")[0].as_py())

# 3. Arrow -> pandas: does the float column reuse the Arrow buffer?
tab3 = pa.Table.from_pandas(pd.DataFrame({"x": np.arange(8, dtype=np.float64)}), preserve_index=False)
addr = tab3.column("x").chunk(0).buffers()[1].address
print("split_blocks=True reuses buffer:", tab3.to_pandas(split_blocks=True)["x"].to_numpy().ctypes.data == addr)
print("default reuses buffer:", tab3.to_pandas()["x"].to_numpy().ctypes.data == addr)

# 4. the worked example, read back from pyarrow
w = pa.array(["ann", "bob", None, "cy"], type=pa.string())
print("validity byte:", w.buffers()[0].to_pybytes()[0])
print("offsets:", np.frombuffer(w.buffers()[1], dtype=np.int32).tolist())
print("data:", w.buffers()[2].to_pybytes())
```

```output
arrow sees the change: 99
copy=False, arrow[0] after mutation: -1.0
default, arrow[0] after mutation: 0.0
split_blocks=True reuses buffer: True
default reuses buffer: False
validity byte: 11
offsets: [0, 3, 6, 6, 8]
data: b'annbobcy'
```

</details>

So the first conversion into Arrow can share memory, but the default pandas constructor makes a copy before that happens. Converting back, the plain `to_pandas()` call copied the float column, while `split_blocks=True` reused the Arrow buffer. Reuse is therefore a property of the call you make, not of the format.

## Nulls change the type in pandas

A pandas integer column has no null value, so a column that contains a missing entry is stored as float64 (64-bit floating point). The block below uses 2^53 + 1, the first integer a float64 cannot represent exactly.

<details><summary>Run locally: needs pip install pandas pyarrow</summary>

```python
import pandas as pd
import pyarrow as pa

big = 2**53 + 1  # 9007199254740993
s_pd = pd.Series([big, None])
print("pandas:", s_pd.dtype, int(s_pd.iloc[0]), int(s_pd.iloc[0]) == big)
ta = pa.array([big, None], type=pa.int64())
print("arrow:", ta.type, ta[0].as_py(), ta.null_count)
q = pd.Series([big, None], dtype="Int64")
print("pandas Int64:", q.dtype, int(q.iloc[0]), int(q.iloc[0]) == big)
q2 = pd.Series([big, None], dtype="int64[pyarrow]")
print("pandas int64[pyarrow]:", q2.dtype, int(q2.iloc[0]) == big)
```

```output
pandas: float64 9007199254740992 False
arrow: int64 9007199254740993 1
pandas Int64: Int64 9007199254740993 True
pandas int64[pyarrow]: int64[pyarrow] True
```

</details>

Arrow keeps the int64 values and stores the null in the validity bitmap, so the value is exact. The nullable `Int64` type also kept the value exact in this test.

## Memory: the layout decides the bytes

![Four horizontal bars for a 200,000-value string column: pandas object 11.6 MB, pandas 3 default str 3.4 MB, Arrow large_string 3.4 MB, Arrow string 2.6 MB.](diagrams/16.2-string-memory.svg "Memory for 200,000 string values, by layout.")

The experiment compares four layouts of the same 200,000 strings, each nine characters long with 1,000 distinct values. pandas' deep memory count for the object column is 11.6 MB, which is about 58 bytes per value. The Arrow `string` array is 2.6 MB, which is 13 bytes per value: 4 bytes of offset and 9 bytes of data, with no validity buffer because nothing is null. A `large_string` uses 64-bit offsets, so it is 3.4 MB. The pandas 3 default `str` dtype is backed by Arrow storage when pyarrow is installed, and its deep count is also 3.4 MB [3].

The tracemalloc module, which counts Python heap allocations directly, reports 11.62 MB for a list of 200,000 freshly created strings, and 13.23 MB once the pandas object Series is added on top of it. The Arrow string array takes 2.60 MB from Arrow's own memory pool. The two methods agree to within about 15 percent for the object column, so the lesson uses pandas' count for the comparison.

The 1,000 distinct labels do not reduce any of these numbers. Neither layout deduplicates strings. Categorical dtypes do, and Lesson 16.3 covers them.

## Files: Parquet is smaller, uncompressed IPC is not

![Four bars for a one-million-row table: CSV 36.16 MB, Parquet 13.81 MB, Arrow IPC file 33.00 MB, in memory 33.00 MB.](diagrams/16.2-file-size.svg "One million rows, written four ways.")

The IPC file here stores the same buffers as memory, so its size equals the in-memory size, 33.00 MB. Parquet is 13.81 MB because it stores each column with an encoding and compresses it. We did not open the Parquet specification, so why this particular data compresses so well is my own reasoning, not a cited result. The cost of that size is decoding on read. We did not time reads, because timings depend on the hardware.

Reading Parquet with `dtype_backend="pyarrow"` keeps Arrow types in pandas: the experiment shows `int64[pyarrow]`, `double[pyarrow]` and `large_string[pyarrow]`, with a deep size of 33.25 MB [2].

## Memory-mapped files: reads without copies

![Two rows. A copying read copies the file on disk into Arrow pool buffers, 33,000,320 bytes. A memory-mapped read maps the same file and allocates 0 bytes.](diagrams/16.2-mmap.svg "Copying read versus memory-mapped read of the same Arrow IPC file.")

A copying read of the one-million-row file allocates 33,000,320 bytes from Arrow's memory pool. The memory-mapped read allocates 0 bytes from the pool, and its result sums the `id` column to 499,999,500,000, which is the correct value for 0 to 999,999. The arrays point into the mapped pages of the file. Two processes that map the same file would share those pages through the operating system: that is my reasoning, not something the experiment tested.

> [!TRAP]
> `to_pandas()` is not zero-copy by default. In the test above, the default call copied the float column and `split_blocks=True` did not. Check the buffer address when the copy matters.

> [!TRAP]
> A missing value turns an integer column into float64 in pandas, and integers above 2^53 then lose precision. Use `dtype="Int64"` or an Arrow type, and check the result.

> [!TRAP]
> Object dtype is the expensive layout. It costs about 58 bytes per value here, against 13 for an Arrow string array. Converting a whole table to object dtype undoes the saving.

> [!TRAP]
> A memory map is only as stable as its file. The pyarrow documentation says the size of the memory map cannot change [4], so do not rewrite a file while it is mapped.

## Summary

- An Arrow string array is three flat buffers: validity bits, offsets and data bytes. Each buffer is contiguous, so other libraries read it without translation.
- pandas can share an Arrow buffer, but only in some calls: the constructor copies by default, and `to_pandas()` copies unless you pass `split_blocks=True`.
- Object dtype costs about 58 bytes per string here, and Arrow costs 13, for the same values.
- Memory-mapped reads allocate 0 bytes from Arrow's pool, while copying reads allocate the full 33 MB.

### Question 4: Explanation

Why does the memory-mapped read report 0 bytes from Arrow's pool while the copying read reports 33,000,320?

<details><summary>Show solution</summary>

The memory-mapped arrays point into the mapped pages of the file, so Arrow does not allocate memory for the column data. The copying read reads the bytes into new buffers in the pool, so the pool records their full size.

</details>
