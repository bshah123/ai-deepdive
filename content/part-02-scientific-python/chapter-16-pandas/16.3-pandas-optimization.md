In this lesson you will measure what a pandas column really costs, then shrink it with three tools: categorical dtypes, numeric downcasting and chunked reading. You will also see where each tool silently costs you accuracy, memory or correctness.

**You need:** the idea from Lesson 16.1 that each DataFrame column is a typed array, and `pd.read_csv`. All outputs come from pandas 3.1.1 and NumPy 2.5.5. The NumPy-only blocks also run in the browser.

## The problem

A table with one million rows, a city name and an amount, is 20.8 MB as a CSV file. Loaded with pandas defaults, its in-memory frame takes 30.3 MB. Memory grows with the number of rows, so a 50-million-row file of the same shape would need about 1.5 GB. That figure is a linear extrapolation from the measured 30.3 MB per million rows. Measure before you optimize.

Use `memory_usage(deep=True)`:

<details><summary>Run locally: needs pip install pandas (tested with pandas 3.1.1)</summary>

```python
import numpy as np
import pandas as pd

rng = np.random.default_rng(16)
cities = pd.Series(rng.choice(["Mumbai", "Delhi", "Chennai", "Kolkata"], size=1_000_000), dtype=object)
print("shallow:", cities.memory_usage())
print("deep:   ", cities.memory_usage(deep=True))
```

```output
shallow: 8000132
deep:    55251604
```

</details>

Without `deep=True`, pandas counts only the 8-byte pointer stored in each object cell. The strings those pointers reach are left out, so this column looks about seven times smaller than it is.

## Categoricals: store each label once

A categorical column keeps one `categories` table of the distinct values. Each row stores only an integer code that points into that table. NumPy's `np.unique` returns exactly this split:

```python
import numpy as np

values = np.array(["Chennai", "Chennai", "Kolkata", "Delhi", "Kolkata", "Mumbai", "Chennai", "Delhi"])
categories, codes = np.unique(values, return_inverse=True)
print("categories:", categories.tolist())
print("codes:     ", codes.tolist())
print("rebuilt:   ", categories[codes].tolist() == values.tolist())
```

```output
categories: ['Chennai', 'Delhi', 'Kolkata', 'Mumbai']
codes:      [0, 0, 2, 1, 2, 3, 0, 1]
rebuilt:    True
```

![Layout of a categorical column: a one-byte code per row points into a four-entry categories table](diagrams/16.3-category-layout.svg "A categorical stores each label once, plus one small code per row")

Now the same idea on one million city names in pandas:

<details><summary>Run locally: needs pip install pandas (tested with pandas 3.1.1)</summary>

```python
import numpy as np
import pandas as pd

rng = np.random.default_rng(16)
city = rng.choice(["Mumbai", "Delhi", "Chennai", "Kolkata"], size=1_000_000)
columns = [
    ("object", pd.Series(city, dtype=object)),
    ("str (pandas 3 default)", pd.Series(city)),
    ("category", pd.Series(city, dtype="category")),
]
for name, s in columns:
    print(f"{name:24s} {s.memory_usage(deep=True):>12,d} bytes")
cat = pd.Series(city, dtype="category")
print("codes dtype:", cat.cat.codes.dtype, "| categories:", list(cat.cat.categories))
```

```output
object                     55,251,604 bytes
str (pandas 3 default)     14,251,604 bytes
category                    1,000,190 bytes
codes dtype: int8 | categories: ['Chennai', 'Delhi', 'Kolkata', 'Mumbai']
```

</details>

![Bar chart: one million city names take 55.3 MB as object, 14.3 MB as str and 1.0 MB as category](diagrams/16.3-city-memory.svg "The same million city names, by column dtype")

The categorical is about 55 times smaller than the object column and 14 times smaller than the default `str` column. Its codes are `int8`, because four categories fit in one byte. The remaining 190 bytes are the row index (132 bytes) and the categories table (58 bytes). pandas 3 uses `str` by default; `object` is the older representation that much existing code still produces.

Categoricals help only when distinct values are few compared with rows. Here every name is unique:

<details><summary>Run locally: needs pip install pandas (tested with pandas 3.1.1)</summary>

```python
import pandas as pd

ids = pd.Series([f"user_{i:07d}" for i in range(1_000_000)])
print("str:     ", ids.memory_usage(deep=True))
print("category:", ids.astype("category").memory_usage(deep=True))
```

```output
str:      20000132
category: 24125132
```

</details>

The categories table now holds all one million strings, and the `int32` codes add about 4 MB on top. The categorical is about 20% larger. Compare `nunique()` with the row count before you convert a column.

A categorical also brings things a plain string column does not have. It can carry an order (so `min`, `max` and sorting follow the declared order rather than the alphabet), and it tells other libraries that the column is a set of labels, not free text. The categories are fixed when the column is built, so a new label has to be added to the table before rows can use it. These properties are the reason to choose a categorical even when memory is not the bottleneck.

## Downcasting: the smallest type that holds the values

An `int64` takes 8 bytes per value, whether the value is 3 or 999,999. NumPy shows what each type holds and costs:

```python
import numpy as np

n = 1_000_000
ids = np.arange(n, dtype=np.int64)
print("int64:", ids.nbytes, "bytes, max value", ids.max())
print("int32:", ids.astype(np.int32).nbytes, "bytes, max value", ids.astype(np.int32).max())
print("int8 max:", np.iinfo(np.int8).max, "| int16 max:", np.iinfo(np.int16).max)
print("float32 holds 16777216 exactly:", np.float32(16777216) == 16777216)
print("float32 value of 16777217:", float(np.float32(16777217.0)))
print("float32 value of 0.1:", float(np.float32(0.1)))
```

```output
int64: 8000000 bytes, max value 999999
int32: 4000000 bytes, max value 999999
int8 max: 127 | int16 max: 32767
float32 holds 16777216 exactly: True
float32 value of 16777217: 16777216.0
float32 value of 0.1: 0.10000000149011612
```

A float32 has a 24-bit significand (23 stored mantissa bits plus an implicit leading 1), so it represents every integer up to 16,777,216 exactly, but not 16,777,217. It also stores 0.1 as a nearby binary fraction, not exactly. NumPy's type table gives the single-precision layout as a sign bit, 8 exponent bits and 23 mantissa bits, "typically" on a given platform. The IEEE 754 binary32 format behind it is general knowledge, not something that page states.

`pd.to_numeric(..., downcast=...)` picks the smallest type that holds the values:

<details><summary>Run locally: needs pip install pandas (tested with pandas 3.1.1)</summary>

```python
import numpy as np
import pandas as pd

rng = np.random.default_rng(16)
n = 1_000_000
frame = pd.DataFrame({
    "order_id": np.arange(n),
    "items": rng.integers(0, 100, size=n),
    "price": rng.random(n) * 1000.0,
})
for col, kind in [("order_id", "integer"), ("items", "integer"), ("price", "float")]:
    before = frame[col]
    after = pd.to_numeric(before, downcast=kind)
    print(f"{col:9s} {str(before.dtype):8s} -> {str(after.dtype):8s} "
          f"{before.memory_usage():>10,d} -> {after.memory_usage():>10,d} bytes")
err = (pd.to_numeric(frame["price"], downcast="float").astype("float64") - frame["price"]).abs().max()
print("max abs error on price:", err)
```

```output
order_id  int64    -> int32     8,000,132 ->  4,000,132 bytes
items     int64    -> int8      8,000,132 ->  1,000,132 bytes
price     float64  -> float32   8,000,132 ->  4,000,132 bytes
max abs error on price: 3.051754663374595e-05
```

</details>

![Bar chart comparing bytes per column before and after downcasting one million rows: int64 to int32, int64 to int8, float64 to float32](diagrams/16.3-downcast.svg "Bytes for one million rows, before and after pd.to_numeric")

`to_numeric` does not demand exact equality. For float32 it accepts the downcast when every value changes by less than an absolute 5e-4 (pandas 3.1.1, `maybe_downcast_numeric` in `pandas/core/dtypes/cast.py`). The pandas `to_numeric` reference confirms the basic rule: the downcast goes to the smallest dtype that qualifies, and the target must be strictly smaller than the original. The next two results show both sides of that tolerance:

<details><summary>Run locally: needs pip install pandas (tested with pandas 3.1.1)</summary>

```python
import numpy as np
import pandas as pd

big = pd.Series([100000.123456789])
print("100000.12 ->", pd.to_numeric(big, downcast="float").dtype,
      "| float32 error:", abs(float(np.float32(100000.123456789)) - 100000.123456789))
near = pd.Series([8001.123456789])
out = pd.to_numeric(near, downcast="float")
print("8001.12 ->", out.dtype, "| error:", abs(float(out.iloc[0]) - 8001.123456789))
```

```output
100000.12 -> float64 | float32 error: 0.0015432109939865768
8001.12 -> float32 | error: 7.836725035303971e-05
```

</details>

The check protects large values, but a value near 8,000 passes with an error of 8e-5 and no warning. That is about seven significant digits, the most float32 can hold. Do not store money in float32. Use integer cents in `int64`, or float64.

Missing values have their own trap:

<details><summary>Run locally: needs pip install pandas (tested with pandas 3.1.1)</summary>

```python
import pandas as pd

s = pd.Series([1, 2, None, 4])
print(s.dtype, "->", pd.to_numeric(s, downcast="integer").dtype)
print(pd.Series([1, 2, None, 4], dtype="Int8").dtype)
```

```output
float64 -> float64
Int8
```

</details>

A missing value turns an integer column into float64, and `downcast="integer"` cannot undo that. The nullable integer dtypes such as `Int8` and `Int32` keep integers and use `pd.NA` as the missing marker, so the column stays an integer type. The pandas guide on nullable integers confirms the `pd.NA` marker; it does not describe the internal storage, so we do not claim a layout here.

## Chunking: never hold the whole file

`pd.read_csv(path, chunksize=n)` returns an iterator. Each item is a DataFrame of up to `n` rows. You can process one chunk, keep a small result and let the chunk go. The same 1,000,000-row CSV is read four ways below:

<details><summary>Run locally: needs pip install pandas (tested with pandas 3.1.1)</summary>

```python
import os
import tempfile
import tracemalloc

import numpy as np
import pandas as pd

def traced_peak_mb(fn):
    """Run fn; return (result, peak MB allocated by Python and NumPy while fn ran)."""
    tracemalloc.start()
    result = fn()
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return result, round(peak / 1e6, 1)

rng = np.random.default_rng(16)
n = 1_000_000
df = pd.DataFrame({
    "order_id": np.arange(n),
    "city": rng.choice(["Mumbai", "Delhi", "Chennai", "Kolkata"], size=n),
    "amount": np.round(rng.random(n) * 500, 2),
})

with tempfile.TemporaryDirectory() as d:
    path = os.path.join(d, "sales.csv")
    df.to_csv(path, index=False)

    full, peak = traced_peak_mb(lambda: pd.read_csv(path))
    print("plain read:", round(full.memory_usage(deep=True).sum() / 1e6, 1), "MB frame, peak", peak, "MB")

    typed_cols = {"city": "category", "order_id": "int32", "amount": "float32"}
    typed, peak = traced_peak_mb(lambda: pd.read_csv(path, dtype=typed_cols))
    print("typed read:", round(typed.memory_usage(deep=True).sum() / 1e6, 1), "MB frame, peak", peak, "MB")

    _, peak = traced_peak_mb(lambda: pd.concat(list(pd.read_csv(path, chunksize=100_000)), ignore_index=True))
    print("chunks then concat: peak", peak, "MB")

    def running_sum():
        totals = None
        for chunk in pd.read_csv(path, chunksize=100_000):
            part = chunk.groupby("city")["amount"].sum()
            totals = part if totals is None else totals.add(part, fill_value=0)
        return totals.sort_index()

    sums, peak = traced_peak_mb(running_sum)
    exact = full.groupby("city")["amount"].sum().sort_index()
    print("chunked running sum: peak", peak, "MB, max difference from full sum", float((sums - exact).abs().max()))
```

```output
plain read: 30.3 MB frame, peak 32.3 MB
typed read: 9.0 MB frame, peak 13.2 MB
chunks then concat: peak 32.1 MB
chunked running sum: peak 3.5 MB, max difference from full sum 7.450580596923828e-09
```

</details>

![Bar chart of traced peak memory for four ways to read the same CSV: plain read 32.3 MB, typed read 13.2 MB, chunks then concat 34.1 MB, chunked running sum 3.5 MB](diagrams/16.3-chunk-peak.svg "Peak memory while reading the same 1,000,000-row file")

The fastest place to downcast is at read time. `pd.read_csv(path, dtype={...})` builds the small types directly, so the large type never sits in memory. The typed read above does exactly that.

Chunking cut the peak from 32.3 MB to 3.5 MB. The sums agree to floating-point rounding, because the two paths add the numbers in a different order. The typed read is the cheapest full read: the category, `int32` and `float32` choices from the previous sections cut the frame to 9.0 MB.

Two caveats. `tracemalloc` counts memory allocated through Python and NumPy, and only part of the pyarrow buffers behind pandas' default `str` columns, so read the peaks as approximate. It is not the process's resident memory. We did not time the runs, so this lesson makes no speed claim.

The third bar is the common mistake. Collecting the chunks into a list and calling `pd.concat` holds the chunks and the joined frame at the same time. The peak (32.1 MB) is no lower than a plain read (32.3 MB), so the chunking saved nothing. Keep only the small per-chunk results.

Chunks also have their own categories. Each chunk builds categories from the values it contains:

<details><summary>Run locally: needs pip install pandas (tested with pandas 3.1.1)</summary>

```python
import io

import pandas as pd

text = "city\nMumbai\nMumbai\nDelhi\nChennai\n"
parts = list(pd.read_csv(io.StringIO(text), chunksize=2, dtype={"city": "category"}))
print([list(p["city"].cat.categories) for p in parts])
print(pd.concat(parts, ignore_index=True)["city"].dtype)

fixed = pd.CategoricalDtype(["Chennai", "Delhi", "Mumbai"])
parts = list(pd.read_csv(io.StringIO(text), chunksize=2, dtype={"city": fixed}))
print(pd.concat(parts, ignore_index=True)["city"].dtype)
```

```output
[['Mumbai'], ['Chennai', 'Delhi']]
str
category
```

</details>

The first chunk sees only Mumbai and the second sees Chennai and Delhi. Their categories disagree, so `pd.concat` falls back to `str` and the categorical saving disappears without an error. Passing the full category list up front, as in the second read, avoids this.

Choosing `chunksize` trades peak memory against per-chunk overhead. The examples use 100,000 rows, which keeps each chunk far below the plain read's frame. Pick a size so that one chunk plus your running results fits in free RAM with headroom. The last chunk can be smaller than `chunksize`: the pandas IO guide shows a 10-row file read with `chunksize=4` producing chunks of 4, 4 and 2 rows. Never assume equal chunk sizes.

Chunked processing also has a limit. Sums, counts and group means can be combined chunk by chunk. Operations that need the whole data at once, such as a global median, a sort or a join, do not split this way. In that case a typed frame, or a library built for out-of-core work, is the better tool (our reasoning, not a measured claim).

## Choosing a strategy

In practice, work through the tools in this order. First measure with `memory_usage(deep=True)`. Second, convert low-cardinality string columns to `category`. Third, give numeric columns their smallest safe dtype at read time with `dtype=`, keeping float64 for money-like values. Fourth, chunk only when the typed frame still does not fit, because chunked code is harder to write and check. Each step is a trade of effort for memory, and the traps below mark where each one can go wrong.

## Common traps

> [!TRAP]
> `memory_usage()` without `deep=True` counts 8 bytes per object cell and leaves out the strings, so it understates a string column about seven times.

> [!TRAP]
> A categorical on mostly unique values is larger than the plain column, because the table holds every value and the codes are extra.

> [!TRAP]
> float32 keeps about seven significant digits, and the 5e-4 check in `to_numeric` is a tolerance, not exactness. Keep money out of float32.

> [!TRAP]
> An integer column with a missing value becomes float64. Use `Int8` or `Int32` instead.

> [!TRAP]
> Concatenating chunks rebuilds the whole frame, so the chunking saves nothing. Each chunk's categories can also differ. Aggregate per chunk, and give the categories explicitly.

## Summary

- Measure with `memory_usage(deep=True)`. The default undercounts string columns.
- A categorical stores each distinct value once and one small integer code per row. It pays off when distinct values are few compared with rows.
- Downcast to the smallest type that holds the values. float32 keeps about seven significant digits, and missing values need nullable integer types.
- Chunked reading bounds peak memory. Keep the per-chunk results, and do not concatenate the chunks back.

## Quiz time

### Question 1: Calculation

Using the measurement in the categorical section, how many bytes do the codes of a 1,000,000-row categorical with four categories take, and why is the whole column only 1.0 MB?

<details><summary>Show Solution</summary>

The codes are `int8`, so each row takes 1 byte: 1,000,000 bytes. The total adds the 132-byte row index and the 58-byte categories table, which gives 1,000,190 bytes.

</details>

### Question 2: Prediction

What does this print?

```python
import pandas as pd

print(pd.to_numeric(pd.Series([1, 2, None]), downcast="integer").dtype)
```

<details><summary>Show Solution</summary>

It prints `float64`. The missing value makes the column float64, and `downcast="integer"` cannot turn float64 into an integer type that holds NaN. Use `dtype="Int8"` to keep an integer type with missing values.

</details>

### Question 3: Bug-spotting

A student reads a large file like this:

```python
import pandas as pd

parts = []
for chunk in pd.read_csv("sales.csv", chunksize=100_000):
    parts.append(chunk)
df = pd.concat(parts, ignore_index=True)
```

What is wrong, and how would you fix it?

<details><summary>Show Solution</summary>

The loop keeps every chunk, and `pd.concat` builds the full frame while they are still alive. The peak memory is no lower than a plain read: in our run it was 32.1 MB against 32.3 MB, so the chunking saved nothing. Fix it by aggregating each chunk into a small result, for example a running sum by group, and keeping only that result.

</details>

### Question 4: Explanation

Why does a categorical column of one million unique user names use more memory than the plain `str` column?

<details><summary>Show Solution</summary>

The categories table stores each distinct value once, so it holds the same strings as the plain column. The categorical then adds one `int32` code per row, about 4 MB for one million rows. Every value is unique, so nothing is saved on the strings.

</details>
