This lesson explains why CPython, the standard Python interpreter, has a Global Interpreter Lock (GIL), and what PEP 703 (Python Enhancement Proposal 703, the formal design document for the change) does about it. You will be able to predict when threads speed up CPU-bound code, explain biased reference counting, and recognise the race condition that appears once the GIL is gone.

**You need:** the basics of threads and `threading.Thread`, and the idea that CPython keeps a reference count on every object. Lesson 16.1 is related but not required.

## The problem: one thread runs Python bytecode at a time

A CPU-bound task is limited by computation, not by waiting for a disk or a network. Give four such tasks to four threads on four free cores, and you would expect close to four times the speed. Standard CPython does not give you that. A single lock, the GIL, must be held while a thread executes Python bytecode, so the threads take turns. Four threads still interleave, but no two of them run Python bytecode at the same instant.

The lock protects memory. Every time a reference to an object is copied or deleted, CPython changes that object's reference count. If two threads changed the same count at once without coordination, a count could be lost. The object would then be freed while still in use, or never freed. One global lock prevents this at the cost of parallelism.

## What PEP 703 changes

PEP 703, by Sam Gross, was accepted on 24 October 2023 ([PEP 703](https://peps.python.org/pep-0703/)). It makes the GIL optional in a separate build. The free-threaded build is a different executable, usually called `python3.13t`, and it has to be built with the `--disable-gil` option or installed from a free-threaded binary ([Python 3.13 What's New](https://docs.python.org/3.13/whatsnew/3.13.html)).

Removing the lock means every object needs its own protection. PEP 703 uses two mechanisms: biased reference counting, described below, and a per-object lock. The PEP reports that the largest slowdown comes from the reference counting, followed by the per-object locking.

The rollout is gradual by design. The Steering Council accepted the PEP on the condition that the rollout breaks as little as possible and that it can be rolled back. The follow-up, [PEP 779](https://peps.python.org/pep-0779/), says the free-threaded build is still "explicitly experimental" in its current phase and targets an officially supported but optional build for Python 3.14. It leaves the question of making the GIL-free build the default to a future PEP.

![A timeline of the PEP 703 rollout: accepted October 2023, experimental in 3.13, PEP 779 in June 2025 targeting an optional supported build in 3.14, and default status not yet decided](diagrams/16.4-rollout.svg "Status as the two PEPs and the 3.13 documentation state it. Check the release notes for your version.")

## Biased reference counting

An atomic operation is a read-modify-write that no other core can interleave with. Atomics are correct but slow when many cores update the same memory location, because that location's cache line keeps moving between cores. Biased reference counting avoids atomics in the common case by assuming that most objects are used mostly by the thread that created them.

Each object records its owner thread in the `ob_tid` field. The owner updates a local count, `ob_ref_local`, with plain instructions. Every other thread updates a separate count, `ob_ref_shared`, with atomic instructions. When the shared count goes negative, the object is queued so its owner can merge the two counts. The PEP's pseudocode and merge states are more detailed than this lesson needs ([PEP 703](https://peps.python.org/pep-0703/)).

![An object header with ob_tid, ob_ref_local and ob_ref_shared. The owner thread updates the local count without atomics; every other thread updates the shared count atomically](diagrams/16.4-biased-refcount.svg "Biased reference counting. The bias is toward the creating thread.")

The scheme pays off only when the assumption holds. A worker that makes its own temporary objects takes the cheap path every time. A shared object that every worker reads takes the atomic path, and the cost shows up. The measurements below test exactly that.

## Worked example by hand: a lost update

The statement `Shared.n += 1` is three steps: read `n`, add 1, and write the result back. Two threads that interleave those steps can lose an increment. Here the interleaving is traced by hand:

```python
# Two "threads" each run: read n, add 1, write n.
# The steps are interleaved by hand to show one bad order.
n = 0
a = n        # thread A reads 0
b = n        # thread B reads 0, before A has written
n = a + 1    # thread A writes 1
n = b + 1    # thread B writes 1, so A's update is lost
print(n)
```

```output
1
```

Two increments should give 2, and the program prints 1. Nothing in the code is wrong; the order of the steps is. Whether the GIL build can produce this order depends on when thread switches happen. In our five GIL-on runs the bad order never reached the final count. The GIL makes the bad order rare, not impossible (my own reasoning from the three-step structure, not measured).

## Measuring it

The demo below runs three things: a CPU-bound loop in 1, 2 and 4 threads; four threads doing 200,000 increments each on one shared counter; and four threads doing 3 million reference updates each, on objects they own versus one object owned by the main thread. Run it once per interpreter.

<details><summary>Run locally: needs a free-threaded build (python3.13t)</summary>

```python3.13t
import sys, time, threading

def cpu_task(n):
    s = 0
    for i in range(n):
        s += i * i % 7
    return s

def run_threads(k, n):
    ts = [threading.Thread(target=cpu_task, args=(n,)) for _ in range(k)]
    t0 = time.perf_counter()
    for t in ts:
        t.start()
    for t in ts:
        t.join()
    return time.perf_counter() - t0

class Shared:
    n = 0

def bump(m):
    for _ in range(m):
        Shared.n += 1          # read, add, write: three bytecodes, not one atomic step

def race(k=4, m=200_000):
    Shared.n = 0
    ts = [threading.Thread(target=bump, args=(m,)) for _ in range(k)]
    for t in ts:
        t.start()
    for t in ts:
        t.join()
    return Shared.n

def touch(o, m):
    for _ in range(m):
        x = o
        del x

def refcount_time(mode, m=3_000_000):
    shared = object()                      # created by the main thread
    times = []
    def worker():
        o = object() if mode == "owned" else shared   # "owned": this thread made it
        t0 = time.perf_counter()
        touch(o, m)
        times.append(time.perf_counter() - t0)
    ts = [threading.Thread(target=worker) for _ in range(4)]
    for t in ts:
        t.start()
    for t in ts:
        t.join()
    return max(times)

if __name__ == "__main__":
    gil = sys._is_gil_enabled() if hasattr(sys, "_is_gil_enabled") else True
    print(f"python {sys.version.split()[0]}, GIL enabled: {gil}")
    t1 = min(run_threads(1, 2_000_000) for _ in range(3))
    print(f"1 task, serial: {t1:.3f} s")
    for k in (2, 4):
        tk = min(run_threads(k, 2_000_000) for _ in range(3))
        print(f"{k} tasks in threads: {tk:.3f} s, speedup {k * t1 / tk:.2f}x")
    print("race, expected 800000, 5 runs:", [race() for _ in range(5)])
    own = min(refcount_time("owned") for _ in range(3))
    shr = min(refcount_time("shared") for _ in range(3))
    print(f"4 threads, 3M ref ops each: owned {own:.3f} s, shared {shr:.3f} s, ratio {shr / own:.1f}x")
```

Run on the free-threaded build (`python3.13t lesson_demo.py`), the output was:


These runs are one machine (10-core Apple silicon Mac, 4 performance cores) and one interpreter build per row. Timings and race counts vary from run to run, so treat the numbers as an example of the pattern, not as a benchmark.

**Scaling.** The free-threaded build reached 2.01x with two tasks and 3.07x with four (3.48x in an earlier run on the same machine; see the figure). With the GIL on, the same binary stayed at 1.00x.

![Bar chart of speed-up for 1, 2 and 4 threads: the GIL-on build stays at 1.00x, while the free-threaded build reaches 2.01x and 3.07x](diagrams/16.4-scaling.svg "Same work per thread. Speed-up is one task's serial time times the number of tasks, divided by the wall-clock time.")

**Single-thread cost.** Even with one task, the free-threaded binary took 0.113 s against 0.108 s for the standard build, about 5%. An earlier run gave about 9%. The PEP reports 5% (AMD Zen 3) and 6% (Intel Skylake) single-thread overhead on pyperformance, measured against a different baseline. Our figure comes from one loop on one machine, so it is a rough check, not a confirmation.

**Lost updates.** On the free-threaded build, five runs of four threads counted between 348,362 and 360,927 out of 800,000, so 55 to 56 percent of the increments were lost. The GIL-on run counted 800,000 in all five runs. Five correct runs do not make the GIL build safe; they show only that the bad order is rare in this loop.

![Bar comparison: the free-threaded build counted 348,362 to 360,927 of 800,000 increments, losing about 55 percent; the GIL-on build counted 800,000 in every run](diagrams/16.4-lost-updates.svg "A shared counter with four threads, each adding 200,000. Same binary in both rows.")

**Reference counting.** Touching an object owned by the main thread from four workers took 1.038 s on the free-threaded build, against 0.042 s for objects each worker owned: a ratio of 24.6x (about 23x in an earlier run). With the GIL on, the ratio was 1.8x in the free-threaded binary and 0.8x in the standard build. Neither is a consistent gap, as expected: the GIL serialises the threads, so the atomic path is never contended.

![Bar chart comparing owned and shared objects: on the free-threaded build the shared case takes 1.038 s against 0.042 s owned; with the GIL on the two are close](diagrams/16.4-refcount-cost.svg "The contention cost appears only when the GIL is off.")

## Common traps

> [!TRAP]
> **It passes on the GIL build and fails on `python3.13t`.** The GIL makes the bad order rare, so a test that increments a shared counter can look correct for a long time. Run concurrency tests on the free-threaded build as well.

> [!TRAP]
> **Check-then-act is not atomic.** `if key not in cache: cache[key] = make(key)` can call `make` twice when two threads race through the check. Each dictionary operation may be safe on its own while the sequence is not (my reasoning from the lost-update example).

> [!TRAP]
> **One extension module can turn the GIL back on.** The Python 3.13 What's New says that importing a C extension that does not declare free-threaded support re-enables the GIL, unless `PYTHON_GIL=0` or `-X gil=0` was set explicitly. Check `sys._is_gil_enabled()` after your imports.

> [!TRAP]
> **Four threads will not give four times the speed.** We measured 3.07x and 3.48x on four threads. The cause on this machine is not isolated. Apple silicon mixes performance and efficiency cores, so measured speed-up depends on the machine and the run.

> [!TRAP]
> **A free-threaded interpreter needs compatible packages.** Extension modules must be built for the free-threaded build, so check that each dependency has a free-threaded build before you switch interpreters ([Python 3.13 What's New](https://docs.python.org/3.13/whatsnew/3.13.html)).

## Summary

- The GIL lets one thread run Python bytecode at a time, so CPU-bound threads do not scale on standard CPython.
- PEP 703 adds a free-threaded build (`python3.13t`) that removes the GIL, using biased reference counting and per-object locks.
- Biased reference counting: the owning thread updates a local count without atomics, and other threads update a shared count atomically.
- `counter += 1` is three steps. Without the GIL, threads lose updates; protect the counter with a lock.
- Measured on one machine: 3.07x on four tasks with the GIL off, 1.00x with it on, and about 5% single-thread cost for the free-threaded binary.

### Question 1: Calculation

In the free-threaded run, one task took 0.113 s and four tasks took 0.148 s. Compute the speed-up and the parallel efficiency (speed-up divided by the number of tasks).

<details><summary>Show Solution</summary>

The speed-up from the rounded times is $4 \times 0.113 / 0.148 \approx 3.05$. The demo printed 3.07 because it divides unrounded times. The efficiency is $3.07 / 4 \approx 0.77$, or about 77%.

</details>

### Question 2: Prediction

Four threads each run `Shared.n += 1` 200,000 times. Which statement is true?

a) The total is always 800,000 on any CPython build.
b) On the GIL build, the total was 800,000 in five runs, but the code is still not guaranteed correct.
c) On the free-threaded build, the total is always 800,000 with four threads.

<details><summary>Show Solution</summary>

Answer: b. The GIL build counted correctly in all five runs we made, but the three-step increment is not protected by a lock, so correctness is not guaranteed. Option c is contradicted by the measured 348,362 to 360,927 range.

</details>

### Question 3: Bug-spotting

```python
import threading
results = {}

def get(key):
    if key not in results:
        results[key] = expensive(key)
    return results[key]
```

Two threads call `get` with the same key. What can go wrong, and how do you fix it?

<details><summary>Show Solution</summary>

Both threads can see the key missing and both call `expensive(key)`. The result is duplicated work and possibly two different objects stored in turn, not a crash. The fix is a `threading.Lock` held around the check and the store:

```python
import threading
results = {}
lock = threading.Lock()

def get(key):
    with lock:
        if key not in results:
            results[key] = expensive(key)
        return results[key]
```

This reasoning is mine; the code was not run.

</details>

### Question 4: Explanation

Why does touching an object created by the main thread cost more on the free-threaded build than touching an object each worker created?

<details><summary>Show Solution</summary>

A worker that created its object is the owner, so it updates the local count with plain instructions and no atomics. The workers that touch the main thread's object are not the owner, so they update the shared count atomically. Four cores doing atomic updates to one location contend for its cache line, which is the slowdown measured (1.038 s against 0.042 s).

</details>
