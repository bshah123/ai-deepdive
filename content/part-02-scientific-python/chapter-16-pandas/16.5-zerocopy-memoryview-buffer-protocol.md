A `memoryview` lets Python code read and write another object's bytes without copying them. In this lesson you will see which operations copy memory and which only create a view, count the allocated bytes with `tracemalloc`, and learn the traps that turn a view into a silent copy.

**You need:** mutable and immutable objects (Lesson 2.2), and strides, the byte step between neighbouring elements of an array (Lesson 15.1).

## The problem

Take a 16 MiB (mebibyte: 16 × 1,048,576 bytes) buffer, such as a binary file read into memory or a block of sensor data. The expression `data[1024:]` looks the same whether it copies or not, but its cost is not: for a `bytes` or `bytearray` object it allocates a new 16 MiB block, and for a `memoryview` it allocates only a small header that points at the original bytes. A loop that slices a buffer on every iteration can therefore either allocate gigabytes or allocate almost nothing, depending on the type of the object.

![Left: bytes(src) allocates a new 16 MiB block. Right: memoryview(src) allocates a small header that points at the original 16 MiB.](diagrams/16.5-copy-vs-view.svg "Copy versus view. The memoryview header is the only new allocation.")

## The buffer protocol

Objects that expose their raw memory implement the buffer protocol. The built-in examples are `bytes`, `bytearray`, `array.array`, `mmap` and NumPy arrays. The protocol has two sides. The exporter (the object that owns the memory) fills in a C structure, `Py_buffer`, that describes the block. The consumer (the code that wants the bytes) requests that structure and must release it afterwards. The C-API documentation says it plainly: "Successful calls to `PyObject_GetBuffer()` must be paired with calls to `PyBuffer_Release()`, similar to `malloc()` and `free()`" (CPython documentation, buffer protocol; reference 1).

The `Py_buffer` fields are `buf` (the start address), `obj` (a new reference to the exporter), `len`, `itemsize`, `readonly`, `ndim`, `format` (a `struct`-style type code such as `'i'` for C int), `shape`, `strides` (bytes to step per dimension), `suboffsets` and `internal`. Nothing in the protocol copies data. Every consumer reads the exporter's memory in place.

![One 8-byte bytearray is the exporter. A Py_buffer structure describes it; memoryview and NumPy read the same bytes.](diagrams/16.5-one-buffer.svg "The exporter owns the bytes; the struct describes them; every reader points at the same block.")

> [!NOTE]
> The `Py_buffer` struct is C code, and we have not compiled any C in this lesson. The Python attributes in the next section (`format`, `itemsize`, `shape`, `strides`, `readonly`) are the same fields, exposed to Python.

## memoryview from Python

A `memoryview` is the Python-level handle on a buffer. Creating one calls the protocol and stores the result; it copies nothing. Each attribute below mirrors a field of `Py_buffer`:

```python
import array
import numpy as np

a = array.array('i', [1, 2, 3, 4, 5])
mv = memoryview(a)                        # no copy: mv describes a's memory
for name in ['format', 'itemsize', 'ndim', 'shape', 'strides', 'readonly', 'c_contiguous', 'nbytes']:
    print(f"{name:12s} {getattr(mv, name)}")

f = np.arange(12, dtype=np.float64).reshape(3, 4)
mf = memoryview(f)
print("float64 3x4 :", "format", mf.format, "itemsize", mf.itemsize,
      "shape", mf.shape, "strides", mf.strides, "c_contiguous", mf.c_contiguous)
```

```output
format       i
itemsize     4
ndim         1
shape        (5,)
strides      (4,)
readonly     False
c_contiguous True
nbytes       20
float64 3x4 : format d itemsize 8 shape (3, 4) strides (32, 8) c_contiguous True
```

Read the strides. For the 3 × 4 float64 array, moving one column advances 8 bytes (one `float64`), and moving one row advances 32 bytes (4 × 8). `format` `'i'` is the C `int`; its `itemsize` of 4 bytes holds on the platform used here, but the C `int` size is platform-dependent, so check `itemsize` rather than assuming it.

## Views share memory; copies do not

This is the behaviour that makes zero-copy useful, and also the one that surprises people:

```python
import numpy as np

buf = bytearray(b'abcdefgh')
mv = memoryview(buf)
sl = mv[2:5]                              # slicing a memoryview gives another view
print("slice.obj is buf:", sl.obj is buf)
sl[0] = ord('X')
print("after sl[0] = 'X':", buf)

npv = np.frombuffer(buf, dtype=np.uint8)  # NumPy wraps the same bytes
npv[7] = ord('Z')
print("after frombuffer[7] = 'Z':", buf)
print("asarray(mv) shares:", np.shares_memory(np.asarray(mv), npv))

cp = np.array(mv)                         # np.array copies by default
print("np.array(mv) shares:", np.shares_memory(cp, npv))
cp[0] = 0
print("buf[0] after changing the copy:", buf[0], "== ord('a') =", ord('a'))
```

```output
slice.obj is buf: True
after sl[0] = 'X': bytearray(b'abXdefgh')
after frombuffer[7] = 'Z': bytearray(b'abXdefgZ')
asarray(mv) shares: True
np.array(mv) shares: False
buf[0] after changing the copy: 97 == ord('a') = 97
```

Three writes went through three handles to one block: the `memoryview` slice, the NumPy array made by `np.frombuffer`, and the `np.asarray` of the view. `np.array(mv)` made a copy, so writing to it left `buf` unchanged. The rule to remember is that `np.asarray` and `np.frombuffer` wrap the buffer, while `np.array` copies unless you ask it not to.

## Read-only views, reinterpretation and strides

A `bytes` object is immutable, so a view of it is read-only. `cast()` changes how the same bytes are read (the byte order is the native order, little-endian on this machine) without copying them. A slice with a step produces a view whose elements are not adjacent in memory:

```python
ro = memoryview(b'\x01\x00\x00\x00\x02\x00\x00\x00')
print("bytes view readonly:", ro.readonly)
try:
    ro[0] = 9
except TypeError as e:
    print("TypeError:", e)

ints = memoryview(bytearray(b'\x01\x00\x00\x00\x02\x00\x00\x00')).cast('I')
print("cast('I') ->", ints.tolist(), "format", ints.format, "itemsize", ints.itemsize)

m = memoryview(bytearray(range(10)))
ev = m[::2]                               # stride 2: every second byte
print("m[::2] tolist:", ev.tolist(), "| strides", ev.strides, "| c_contiguous", ev.c_contiguous)
print("tobytes() of strided view:", ev.tobytes())
```

```output
bytes view readonly: True
TypeError: cannot modify read-only memory
cast('I') -> [1, 2] format I itemsize 4
m[::2] tolist: [0, 2, 4, 6, 8] | strides (2,) | c_contiguous False
tobytes() of strided view: b'\x00\x02\x04\x06\x08'
```

![Ten source bytes, 0 to 9. The stride-2 view reads the even ones, one step of two bytes apart, and needs no copy.](diagrams/16.5-strided.svg "m[::2] reads every second byte. The view's strides are (2,), so it is not c_contiguous.")

A strided view is not contiguous, so some consumers must copy it first. `tobytes()` always returns a new `bytes` object, and the example above shows that it packs the selected bytes together.

## A view locks its owner

While a view is alive, the exporter must not change its memory layout. A `bytearray` therefore refuses to resize, and `release()` lifts the restriction. The `memoryview` documentation says this directly: "Many objects take special actions when a view is held on them (for example, a `bytearray` would temporarily forbid resizing); therefore, calling `release()` is handy to remove these restrictions" (CPython documentation, memoryview; reference 2).

```python
ba = bytearray(b'hello')
view = memoryview(ba)
try:
    ba.append(33)
except BufferError as e:
    print("BufferError:", e)
view.release()
ba.append(33)
print("after release:", ba)

try:
    memoryview([1, 2, 3])                 # a list has no buffer
except TypeError as e:
    print("TypeError:", e)
```

```output
BufferError: Existing exports of data: object cannot be re-sized
after release: bytearray(b'hello!')
TypeError: memoryview: a bytes-like object is required, not 'list'
```

A `list` stores pointers to separate Python objects, not one contiguous block of numbers, so it has no buffer. To get zero-copy access to numbers, use `array.array` or a NumPy array.

## Measuring the copies

The next block counts allocations with `tracemalloc`, the standard-library tracer for Python memory. It reports the peak allocation during each call and the memory still held after it returns. It needs CPython and does not run in the browser.

<details><summary>Run locally: tracemalloc, standard library (not run in the browser)</summary>

```python
import gc
import tracemalloc
import numpy as np

MiB = 1024 * 1024
src = bytearray(16 * MiB)                 # allocated before tracing starts

def measure(label, fn):
    gc.collect()
    tracemalloc.start()
    out = fn()
    cur, pk = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    print(f"{label:34s} peak {pk / MiB:7.2f} MiB   retained {cur / MiB:7.2f} MiB")
    return out

keep = []
keep.append(measure("memoryview(src)", lambda: memoryview(src)))
keep.append(measure("memoryview(src)[1024:]", lambda: memoryview(src)[1024:]))
keep.append(measure("np.frombuffer(src, uint8)", lambda: np.frombuffer(src, dtype=np.uint8)))
keep.append(measure("bytes(src)  (copy)", lambda: bytes(src)))
keep.append(measure("src[:]  (bytearray slice copy)", lambda: src[:]))
keep.append(measure("np.array(memoryview(src))  (copy)", lambda: np.array(memoryview(src))))
```

```output
memoryview(src)                    peak    0.00 MiB   retained    0.00 MiB
memoryview(src)[1024:]             peak    0.00 MiB   retained    0.00 MiB
np.frombuffer(src, uint8)          peak    0.00 MiB   retained    0.00 MiB
bytes(src)  (copy)                 peak   16.00 MiB   retained   16.00 MiB
src[:]  (bytearray slice copy)     peak   16.00 MiB   retained   16.00 MiB
np.array(memoryview(src))  (copy)  peak   16.00 MiB   retained   16.00 MiB
```

</details>

![Bar chart of peak allocation: the three view operations bars are zero; the three copy operations each reach 16.00 MiB.](diagrams/16.5-allocation.svg "Peak allocation for a 16 MiB source. Views allocate nothing measurable; copies allocate the whole block.")

The copies cost the same memory in every case, and the views cost nothing measurable. Time follows the same split. In one run on macOS with CPython 3.12, `memoryview(src)` took about 0.08 µs and `bytes(src)` took about 0.4 ms, a ratio near 5,000. Timing depends on the machine, so treat the ratio as the lesson, not the absolute values.

## Common traps

> [!TRAP]
> `np.array(mv)` copies. `np.asarray(mv)` and `np.frombuffer(mv)` share the memory. Read the function name and the `np.shares_memory` check before assuming a view.

> [!TRAP]
> `bytes(view)` and `view.tobytes()` copy the whole selection, even when the view is strided. Put them inside a loop and the copies add up.

> [!TRAP]
> A write through a view changes the owner, silently. A function that receives a `memoryview` can change the caller's `bytearray`. Pass a copy, or a read-only view with `toreadonly()`, when the callee should not write.

> [!TRAP]
> A live view blocks resizing. `ba.append()` raises `BufferError` while the view exists. Use `with memoryview(ba) as v:` so that the view is released at the end of the block.

> [!TRAP]
> After `release()`, any operation on the view raises `ValueError`. Keep the view in scope only as long as the owner is safe to use.

## Summary

- The buffer protocol lets an object expose its memory through a `Py_buffer` structure; consumers read the memory in place and must release the buffer.
- A `memoryview` is a Python handle on that buffer. Slicing it creates another view, and writes through any view change the owner.
- `bytes(x)`, `x.tobytes()`, `np.array(mv)` and `bytearray` slices copy; `np.asarray(mv)` and `np.frombuffer(mv)` do not.
- A live view prevents a `bytearray` from resizing, and `release()` (or a `with` block) lifts that restriction.

## Quiz time

### Question 1: Predict the output

```python
buf = bytearray(b'abcdef')
mv = memoryview(buf)
s = mv[1:4]
s[0] = ord('X')
print(buf)
```

<details><summary>Show solution</summary>

The output is `bytearray(b'aXcdef')`. The slice `mv[1:4]` is a view of positions 1 to 3. Writing `s[0]` writes position 1 of the shared block, which is the `'b'`.

</details>

### Question 2: Find the bug

```python
data = bytes(16)
view = memoryview(data)
view[0] = 1
```

<details><summary>Show solution</summary>

This raises `TypeError: cannot modify read-only memory`. `bytes` is immutable, so its buffer is exported as read-only. The fix is to start from a mutable buffer: `data = bytearray(16)`.

</details>

### Question 3: Calculate the copy size

An `array.array('d', range(1000))` holds 1000 float64 values of 8 bytes each. How many bytes does `memoryview(a)[::10].tobytes()` allocate, and how many does `memoryview(a)[::10]` allocate?

<details><summary>Show solution</summary>

The slice `[::10]` selects 100 elements, so `tobytes()` builds a `bytes` object of 100 × 8 = 800 bytes. The `memoryview` slice allocates only its small header, because it is a view. This follows from the stride of 80 bytes (10 × 8) and the element count, not from a measurement.

</details>

### Question 4: Explain the design

A function `normalize(view)` is meant to scale a sensor frame in place, but the caller wrote `frame = np.array(raw)` and then `normalize(memoryview(frame))`. Why does the caller's `raw` buffer stay unchanged, and what change makes the function write to the original?

<details><summary>Show solution</summary>

`np.array(raw)` copies the buffer by default, so `frame` owns new memory and `normalize` scales that copy. The raw buffer is never touched. To write to the original, wrap the original buffer with `np.asarray(raw)` or `np.frombuffer(raw)`, which share memory, and check the change with `np.shares_memory`.

</details>
