By the end you will be able to explain why a copy from CPU memory to GPU memory can stall the Python thread, when pinned memory lets the copy run in the background, and how two CUDA streams with two buffers overlap copies with computation. You will predict the total time of a copy-and-compute loop from three numbers.

**You need:** lesson 17.1 (how a tensor points to its storage), and the idea that a GPU (graphics processing unit) kernel (a function that runs on the GPU) is queued work that the CPU (central processing unit) does not wait for.

## The problem: copy and compute take turns

A training step often starts by copying a batch from host memory (CPU random-access memory, RAM) to device memory (GPU memory), then runs a kernel on it. Call the copy time $c$ and the kernel time $k$, both per batch. If the two run one after the other, $n$ batches take $n(c+k)$. While the copy runs, the compute units idle. While the kernel runs, the copy engine idles. The goal is to keep both busy at once.

## Intuition: what a copy travels through

The copy engine is the GPU's hardware unit that moves bytes over the PCI Express bus (PCIe). Ordinary memory from `malloc` is called pageable memory. Pinned memory, also called page-locked memory, is memory the operating system will not move. The 2012 NVIDIA article describes the pageable path: "the CUDA driver must first allocate a temporary page-locked, or 'pinned', host array," then "copy the host data to the pinned array, and then transfer the data from the pinned array to device memory" (NVIDIA Developer Blog, 2012). The reason the driver needs a pinned buffer for the transfer is my own reasoning (b): the transfer hardware needs memory whose physical location stays fixed. The article does not state it.

![Pageable data is copied by the CPU into a driver-made pinned buffer before the DMA; pinned data goes straight to the DMA](diagrams/17.2-staging.svg "Pageable copies take an extra CPU copy; pinned copies do not.")

## Worked example by hand

Take eight batches of 256 MB each (256 × 10⁶ bytes), a kernel of $k = 15$ ms, and two assumed bandwidths: 12 GB/s from pinned memory and 6 GB/s from pageable memory. These numbers are illustrative. They are not measured on any GPU. The 2012 NVIDIA article measured pinned-to-pageable ratios of about 2.5× on a laptop and about 1.15× on a desktop, so the ratio depends strongly on the machine.

The copy times are

$$
c_{\text{pinned}} = \frac{256 \times 10^{6}\ \text{B}}{12 \times 10^{9}\ \text{B/s}} = 21.33\ \text{ms}, \qquad c_{\text{pageable}} = \frac{256 \times 10^{6}}{6 \times 10^{9}} = 42.67\ \text{ms}.
$$

Four configurations follow, with $N = 8$:

- **A:** pageable copies, one stream. $N(c_{\text{pageable}} + k) = 8 \times 57.67 = 461.33$ ms.
- **B:** pinned copies, still one stream. $N(c_{\text{pinned}} + k) = 8 \times 36.33 = 290.67$ ms.
- **C:** pinned copies, two streams, two buffers. Copy $i+1$ runs while kernel $i$ runs. Here the copy is the longer stage ($21.33 > 15$), so the copy engine is busy from 0 to $8 \times 21.33 = 170.67$ ms, and the last kernel adds 15 ms. Total $= 185.67$ ms.
- **D:** pinned copies, two streams, one buffer. Copy $i$ must wait for kernel $i-1$ to free the buffer, so the stages serialise again: 290.67 ms.

For configuration C, $T = N\,c + k$ when $c \ge k$. The formula assumes uniform batches, one copy engine, one compute engine, two buffers, and no host overhead.

## Runnable model: a timeline simulator

No NVIDIA GPU was available when this lesson was written, so the numbers come from a small model. The model is a list scheduler: each operation starts when its stream, its engine and its dependencies are all free. It is a model of the scheduling rules, not a benchmark.

```python
# Timeline model of one GPU training loop: N batches, each = one host-to-device copy then one kernel.
# Times in ms. Each op runs when its stream, its engine and its dependencies are all free.
# Assumptions: one copy engine, one compute engine, the kernel fills the compute engine,
# and the host issues ops at zero cost. Bandwidths are illustrative, not measured here.

def simulate(ops):
    stream_free, engine_free, finish = {}, {}, {}
    timeline = []
    for op in ops:
        start = max([stream_free.get(op["stream"], 0.0), engine_free.get(op["engine"], 0.0)]
                    + [finish[d] for d in op["deps"]])
        finish[op["name"]] = start + op["ms"]
        stream_free[op["stream"]] = engine_free[op["engine"]] = finish[op["name"]]
        timeline.append((op["name"], op["engine"], start, finish[op["name"]]))
    return timeline, max(finish.values())

def pipeline(n, copy_ms, kernel_ms, streams, buffers):
    # Batch i is copied into buffer i % buffers. A copy must wait for the kernel
    # that last read that buffer, which is batch i - buffers.
    ops = []
    for i in range(n):
        ops.append({"name": f"c{i}", "engine": "copy", "ms": copy_ms,
                    "stream": "copy" if streams == 2 else "s0",
                    "deps": [f"k{i - buffers}"] if i >= buffers else []})
        ops.append({"name": f"k{i}", "engine": "sm", "ms": kernel_ms,
                    "stream": "compute" if streams == 2 else "s0",
                    "deps": [f"c{i}"]})
    return ops

BYTES = 256e6          # one batch: 256 MB
PINNED_GBS = 12.0      # assumed host-to-device bandwidth from pinned memory
PAGEABLE_GBS = 6.0     # assumed bandwidth from pageable memory
KERNEL_MS = 15.0
N = 8

copy_pinned = BYTES / (PINNED_GBS * 1e9) * 1e3
copy_pageable = BYTES / (PAGEABLE_GBS * 1e9) * 1e3
print(f"copy: pinned {copy_pinned:.2f} ms, pageable {copy_pageable:.2f} ms, kernel {KERNEL_MS} ms")

cases = [
    ("A pageable, 1 stream", pipeline(N, copy_pageable, KERNEL_MS, streams=1, buffers=2)),
    ("B pinned, 1 stream", pipeline(N, copy_pinned, KERNEL_MS, streams=1, buffers=2)),
    ("C pinned, 2 streams, 2 buffers", pipeline(N, copy_pinned, KERNEL_MS, streams=2, buffers=2)),
    ("D pinned, 2 streams, 1 buffer", pipeline(N, copy_pinned, KERNEL_MS, streams=2, buffers=1)),
]
for label, ops in cases:
    _, total = simulate(ops)
    print(f"{label:32s} total {total:8.2f} ms")

c, k = copy_pinned, KERNEL_MS
print(f"formula N*max(c,k)+min(c,k) for C: {N * max(c, k) + min(c, k):.2f} ms")

tl, _ = simulate(cases[2][1])
for name, engine, s, f in tl[:6]:
    print(f"{name:3s} {engine:5s} {s:7.2f} -> {f:7.2f}")

for ratio in (1.15, 2.5):
    t_page = BYTES / (PINNED_GBS / ratio * 1e9) * 1e3
    _, a = simulate(pipeline(N, t_page, KERNEL_MS, streams=1, buffers=2))
    print(f"pageable {ratio}x slower: A total {a:.2f} ms")
```

```output
copy: pinned 21.33 ms, pageable 42.67 ms, kernel 15.0 ms
A pageable, 1 stream             total   461.33 ms
B pinned, 1 stream               total   290.67 ms
C pinned, 2 streams, 2 buffers   total   185.67 ms
D pinned, 2 streams, 1 buffer    total   290.67 ms
formula N*max(c,k)+min(c,k) for C: 185.67 ms
c0  copy     0.00 ->   21.33
k0  sm      21.33 ->   36.33
c1  copy    21.33 ->   42.67
k1  sm      42.67 ->   57.67
c2  copy    42.67 ->   64.00
k2  sm      64.00 ->   79.00
pageable 1.15x slower: A total 316.27 ms
pageable 2.5x slower: A total 546.67 ms
```

The timeline makes the overlap visible. In configuration A, the copy and kernel alternate. In configuration C, the copy engine starts batch 1 the moment batch 0's copy ends, without waiting for kernel 0.

![Gantt-style timeline: in the serial pageable case the copy and kernel take turns; in the two-stream pinned case copy i+1 overlaps kernel i](diagrams/17.2-timeline.svg "Three batches. The lower panel ends at 79 ms; the upper panel ends at 173 ms.")

Read the four totals side by side. Pinned memory alone (A to B) removes 170.67 ms. Overlap (B to C) removes another 105 ms. Two streams with one buffer (D) gain nothing over B.

![Bar chart of total time for eight batches: A 461.3 ms, B 290.7 ms, C 185.7 ms, D 290.7 ms](diagrams/17.2-totals.svg "Model totals for eight batches. Same batch and kernel in every bar.")

## Streams, buffers and the reuse rule

A CUDA stream is an ordered queue of GPU work. Operations in one stream run in the order they were issued. Operations in different streams may run at the same time (NVIDIA CUDA Programming Guide, §2.5). A copy can overlap a kernel only when the two sit in different streams and the host buffer is pinned. The guide says the host buffers "must be pinned and page-locked" for asynchronous copies, and without pinning "it will revert to a synchronous behavior which will not overlap with other work" (same section, note on host-device copies).

Streams are not enough on their own. Copy $i$ writes into a buffer, and that buffer may still be read by kernel $i-2$. With two buffers the copy into slot 0 for batch 2 waits for kernel 0 to finish; the copy into slot 1 for batch 3 waits for kernel 1. That is why the simulator adds the dependency on `k{i - buffers}`.

![Two buffer slots: copy batch 2 reuses slot 0 and must wait for kernel 0, so two slots are needed for overlap](diagrams/17.2-buffers.svg "Double buffering. One slot forces each copy to wait for the previous kernel.")

## Running it with PyTorch

The lines below use PyTorch's pinned-memory and `non_blocking` options. They need an NVIDIA GPU and PyTorch, which this lesson's sandbox did not have, so the code was not run. I checked the calls against the PyTorch CUDA notes (version 2.15 pages) and the NVIDIA guide. The code produces no output here.

<details><summary>Run locally: needs pip install torch and an NVIDIA GPU (not run for this lesson)</summary>

```python
import torch

x_cpu = torch.randn(4096, 4096).pin_memory()   # page-locked copy of a 64 MiB (67 MB) float32 tensor
x_gpu = x_cpu.to("cuda", non_blocking=True)    # asynchronous with respect to the host
```

</details>

Without `non_blocking=True`, PyTorch waits for the copy to finish. The PyTorch notes say that "PyTorch automatically performs necessary synchronization when copying data between CPU and GPU," and that the flag "lets the caller bypass synchronization when it is unnecessary." The notes also say host-to-GPU copies "are much faster when they originate from pinned (page-locked) memory," and that the flag "can be used to overlap data transfers with computation."

## Common traps

> [!TRAP]
> **`non_blocking=True` on pageable memory gives no overlap.** The CUDA guide says that without pinned host buffers the copy becomes synchronous and "will not overlap with other work." The flag is accepted, but the copy stays synchronous, so the code looks asynchronous and is not.

> [!TRAP]
> **Reusing a pinned source buffer too early.** The runtime documentation says `cudaMemcpyAsync` is "asynchronous with respect to the host, so the call may return before the copy is complete." Writing into the source before the copy finishes can corrupt the batch with no error. Keep the buffer until the copy is done, or use one slot per batch in flight.

> [!TRAP]
> **Timing an asynchronous copy with a Python timer.** A timer around a non-blocking call measures how long the call took to queue, not how long the transfer took. Wait for the copy to finish before reading the clock. This follows from the asynchrony quoted above (reasoning from first principles).

> [!TRAP]
> **Adding streams without a second buffer.** Configuration D has two streams and 290.67 ms, the same as B. Overlap needs a buffer the copy can fill while the kernel reads the other one.

> [!TRAP]
> **Pinning too much memory.** Pinned memory is a fixed resource. The PyTorch notes warn that overusing it "can cause serious problems when running low on RAM." Pin only the batches that are copied repeatedly.

## Summary

- A copy from pageable memory goes through a driver-made pinned buffer, so it is slower and blocks the caller.
- Pinned memory lets `non_blocking=True` copies run asynchronously; without it the copy becomes synchronous.
- A copy and a kernel overlap only when they sit in different streams and each batch has its own buffer.
- For a copy-bound loop with two buffers, the total is about $N\,c + k$; a single buffer removes the overlap.
- Time transfers only after waiting for them to finish, or the clock measures how long the call took to queue.

## Quiz time

### Question 1: Calculation

A batch is 256 MB, pinned bandwidth is 12 GB/s, the kernel takes 10 ms, there are 4 batches, and there are two buffers and two streams. What is the total time?

<details><summary>Show Solution</summary>

The copy takes $256 \times 10^6 / 12 \times 10^9 = 21.33$ ms, which is longer than the 10 ms kernel, so the copy-bound formula applies: $4 \times 21.33 + 10 = 95.33$ ms.

</details>

### Question 2: Prediction

Same as Question 1, but with one buffer. What changes?

<details><summary>Show Solution</summary>

Each copy waits for the previous kernel to finish reading the single buffer, so the stages serialise: $4 \times (21.33 + 10) = 125.33$ ms. This is the same reasoning as configuration D in the model.

</details>

### Question 3: Bug-spotting

```text
x = torch.randn(4096, 4096).pin_memory()
y = x.to("cuda", non_blocking=True)
x.zero_()   # reuse the host buffer for the next batch
```

What is wrong, and how would you fix it?

<details><summary>Show Solution</summary>

`zero_()` may run before the asynchronous copy has read `x`, so `y` can contain zeros where it should contain the data. The bug is silent. Fix it by waiting for the copy to finish before reusing `x`, or by giving each batch in flight its own pinned buffer. The runtime documentation's statement that the call "may return before the copy is complete" is the reason.

</details>

### Question 4: Explanation

Why does `non_blocking=True` not help when the source tensor is pageable?

<details><summary>Show Solution</summary>

Without pinned host buffers the copy reverts to synchronous behaviour, which the CUDA guide says "will not overlap with other work." The flag only changes behaviour for pinned memory.

</details>
