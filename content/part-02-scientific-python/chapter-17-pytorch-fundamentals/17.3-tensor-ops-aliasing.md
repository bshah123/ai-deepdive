A PyTorch tensor is a name attached to a block of memory, so two names can refer to the same numbers. In this lesson you will tell in-place operations (which overwrite a tensor's existing memory) from out-of-place ones (which allocate a new result), predict when a change made through one name shows up under another, and read the errors PyTorch raises when an in-place write would corrupt a backward pass.

**You need:** what a tensor and its storage buffer are (lesson 17.1), and how Python assignment works.

## The problem this solves

A training step creates many large tensors. Whether an update writes into an existing buffer or allocates a new one decides peak memory use. Whether another variable sees the update decides correctness. Get either wrong and the program runs out of memory, or it trains on values you did not intend. Both failures are quiet until something breaks.

## Intuition: names point at buffers

![Out-of-place makes a second buffer; in-place rewrites the first one, and the name x still points at it](diagrams/17.3-storage-before-after.svg "Out-of-place allocates; in-place overwrites. Blue is x's buffer, green is y's.")

`y = x + 1` computes its result into a new buffer and binds the name `y` to it. `x.add_(1)` writes into the buffer that `x` already owns. PyTorch marks in-place methods with a trailing underscore. Nothing is rebound, so every other name that points at that buffer sees the new values.

## Worked example, by hand

Start with x = [1, 2, 3].

- Out-of-place: `y = x + 1` gives y = [2, 3, 4]. x is still [1, 2, 3].
- In-place: `x.add_(1)` gives x = [2, 3, 4]. No other name changes.

The same two rules hold in NumPy, which runs on this page:

```python
import numpy as np

x = np.array([1.0, 2.0, 3.0])
z = x                  # z is a second name for the same array
x += 1                 # in-place: writes into x's buffer
print("z after x += 1:", z)

x = np.array([1.0, 2.0, 3.0])
z = x
x = x + 1              # rebinds x to a new array; z keeps the old one
print("z after x = x + 1:", z)
```

```output
z after x += 1: [2. 3. 4.]
z after x = x + 1: [1. 2. 3.]
```

The first result depends only on which buffer `x` points at after each line. Keep that question in mind for everything below.

## Aliasing: several names, one buffer

Assignment copies the name, not the data. `z = x` makes two names for one object, so `z is x` is true. Slicing makes a **view**: `v = base[2:5]` is a tensor that points into `base`'s buffer, starting at offset 2. Writes through either name land in the same memory. `clone()` is the one operation here that copies.

![Buffer S holds the base tensor; the view v covers elements 2 to 4 of it; x and z name the whole buffer; clone makes buffer W with its own copy](diagrams/17.3-aliases.svg "Names, views and clones. The bracket is the view; the values are those after base.mul_(10).")

Python's augmented assignment `x += 1` calls the method `__iadd__`. The Python data model says these methods "should attempt to do the operation in-place (modifying self) and return the result" (Python Software Foundation, Language Reference §3.3.8). For a tensor, `c += 1` therefore writes into c's buffer, while `a = a + 1` allocates a new one. This difference is the most common way aliasing bugs enter PyTorch code.

<details><summary>Run locally: needs pip install torch (output from torch 2.15.0, CPU)</summary>

Part 1: out-of-place and in-place.

```python
import torch

x = torch.tensor([1.0, 2.0, 3.0])
y = x + 1                                   # out-of-place: y gets its own buffer
print("y shares x's buffer:", y.untyped_storage().data_ptr() == x.untyped_storage().data_ptr())
x.mul_(10)                                  # in-place: x keeps its buffer
print("x after mul_:", x.tolist())
print("y unchanged:", y.tolist())
```

```output
y shares x's buffer: False
x after mul_: [10.0, 20.0, 30.0]
y unchanged: [2.0, 3.0, 4.0]
```

Part 2: names, views and clones.

```python
import torch

x = torch.tensor([1.0, 2.0, 3.0])
z = x                                       # a second name for the same object
x.add_(1)
print("z:", z.tolist())

a = torch.tensor([1.0, 2.0, 3.0]); b = a
a = a + 1                                   # rebinds a; b keeps the old tensor
print("b:", b.tolist(), "a:", a.tolist())

c = torch.tensor([1.0, 2.0, 3.0]); d = c
c += 1                                      # __iadd__: in place, same object
print("d:", d.tolist(), "same object:", c is d)

base = torch.arange(6, dtype=torch.float32)
v = base[2:5]                               # slicing returns a view
base.mul_(10)
print("v after base.mul_(10):", v.tolist())
w = base.clone()                            # clone copies into a new buffer
base.add_(1)
print("w:", w.tolist())
print("base:", base.tolist())
```

```output
z: [2.0, 3.0, 4.0]
b: [1.0, 2.0, 3.0] a: [2.0, 3.0, 4.0]
d: [2.0, 3.0, 4.0] same object: True
v after base.mul_(10): [20.0, 30.0, 40.0]
w: [0.0, 10.0, 20.0, 30.0, 40.0, 50.0]
base: [1.0, 11.0, 21.0, 31.0, 41.0, 51.0]
```

</details>

## The version counter

PyTorch keeps a **version counter** on each tensor. The autograd notes state: "Every tensor keeps a version counter, that is incremented every time it is marked dirty in any operation" (PyTorch, Autograd mechanics). The counter is how PyTorch later notices that a tensor changed after its value was saved.

![Four steps: t starts at version 0, add_ gives 1, mul_ gives 2; a write through the view v makes both t and v read 3](diagrams/17.3-version-counter.svg "Each in-place write adds one. The view and its base share one counter. An out-of-place result starts at 0.")

The counter is a private attribute (`_version`), so use it only to observe behaviour. The run below shows that a write through a view bumps the base's counter, which matches the PyTorch tensor-view page: "if you edit the data in the view, it will be reflected in the base tensor as well" (PyTorch, Tensor views).

<details><summary>Run locally: needs pip install torch (output from torch 2.15.0, CPU)</summary>

```python
import torch

t = torch.tensor([1.0, 2.0, 3.0])
print("start:", t._version)
t.add_(1)
t.mul_(2)
print("after add_ and mul_:", t._version)
v = t[1:]
v.add_(1)
print("after write through view, t:", t._version, "v:", v._version)
print("out-of-place result:", (t + 1)._version)
```

```output
start: 0
after add_ and mul_: 2
after write through view, t: 3 v: 3
out-of-place result: 0
```

</details>

## Where autograd gets involved

Autograd is PyTorch's automatic differentiation. During the forward pass it records each operation and keeps the tensors that the operation's backward formula needs. The derivative of sigmoid is $s(1-s)$ where $s$ is the sigmoid output, so autograd keeps the output. If you overwrite that output in place, the value the backward formula would read is no longer the one the forward pass produced.

![Left: x, then y = sigmoid(x), which saves y; y.mul_(2) changes it from version 0 to 1 and backward raises an error. Right: y = x * 2 then y.mul_(3) needs only constants, so backward gives grad [6, 6]](diagrams/17.3-autograd-saved.svg "What the backward pass needs decides whether an in-place write is allowed.")

Multiplying by a constant saves nothing from the input, so writing into the result afterwards is safe. PyTorch also refuses in-place writes to a **leaf** tensor, which is a tensor you created with `requires_grad=True` and which holds the gradient.

<details><summary>Run locally: needs pip install torch (output from torch 2.15.0, CPU)</summary>

```python
import torch

w = torch.tensor([1.0, 2.0], requires_grad=True)
try:
    w.add_(1)
except RuntimeError as e:
    print("leaf:", str(e).splitlines()[0])

x = torch.tensor([0.5, -1.0], requires_grad=True)
y = x.sigmoid()
y.mul_(2)
try:
    y.sum().backward()
except RuntimeError as e:
    print("sigmoid then mul_:", str(e).splitlines()[0])

x = torch.tensor([0.5, -1.0], requires_grad=True)
y = x * 2
y.mul_(3)
y.sum().backward()
print("x * 2, then mul_(3): grad", x.grad.tolist())
```

```output
leaf: a leaf Variable that requires grad is being used in an in-place operation.
sigmoid then mul_: one of the variables needed for gradient computation has been modified by an inplace operation: [torch.FloatTensor [2]], which is output 0 of Sigmoid, is at version 1; expected version 0 instead. Hint: enable anomaly detection to find the operation that failed to compute its gradient, with torch.autograd.set_detect_anomaly(True, check_nan=False).
x * 2, then mul_(3): grad [6.0, 6.0]
```

</details>

PyTorch raises an error in the first two cases, but the `.data` attribute gets around the check. The next block writes into `y.data`, and autograd does not notice:

<details><summary>Run locally: needs pip install torch (output from torch 2.15.0, CPU)</summary>

```python
import torch

x = torch.tensor([0.5, -1.0], requires_grad=True)
y = x.sigmoid()
y.data.mul_(2)                              # .data hides the write from autograd
y.sum().backward()
s = torch.sigmoid(x.detach())
print("forward y:", [round(v, 4) for v in y.tolist()])
print("grad:", [round(v, 4) for v in x.grad.tolist()])
print("grad of 2*sigmoid(x):", [round(v, 4) for v in (2 * s * (1 - s)).tolist()])
```

```output
forward y: [1.2449, 0.5379]
grad: [-0.3049, 0.2486]
grad of 2*sigmoid(x): [0.47, 0.3932]
```

</details>

The gradient that comes out is the derivative at the overwritten value, not the derivative of the function the forward pass computed. Nothing raises an error.

## Memory: when in-place saves memory

Out-of-place code is not automatically expensive. When a name is rebound, the old buffer is freed once nothing refers to it. I measured resident memory (what the Unix `ps` command reports for the process) on a 2^23-element float32 tensor, which is 32 MiB (mebibytes, 2^20 bytes each) per buffer. The script ran each case in its own process and sampled memory after each of ten sigmoid steps. This was macOS with torch 2.15.0 on the CPU (central processing unit). The numbers depend on the allocator and the machine, and they are noisy by about one buffer.

![Growth after ten steps: no_grad out-of-place +32 MiB; no_grad in-place +0 MiB; autograd on, out-of-place +288 MiB](diagrams/17.3-rss-bars.svg "Measured on one macOS machine, one run. Each step is 32 MiB.")

- **No gradients, out-of-place:** one extra buffer (+32 MiB). The old buffer is freed when its name is rebound, so peak memory stays near two buffers.
- **No gradients, in-place:** no extra memory (+0 MiB).
- **Gradients on, out-of-place:** about one buffer per step is kept alive (+288 MiB after ten steps), because the graph holds each step's output for backward.

So in-place writes save memory only when nothing still needs the old value. With autograd on, the saved outputs are exactly what you cannot overwrite.

<details><summary>Run locally: needs pip install torch (condensed from the measurement script; no output block because results depend on the machine)</summary>

```python
import os, subprocess, sys
import torch

def rss_mib():                              # resident memory of this process, from ps
    kb = int(subprocess.run(["ps", "-o", "rss=", "-p", str(os.getpid())],
                            capture_output=True, text=True).stdout)
    return kb / 1024

mode = sys.argv[1]                          # run each mode in its own process
x = torch.linspace(-3, 3, 2 ** 23)          # 2**23 float32 values = 32 MiB
x.requires_grad_(mode == "autograd")
y = x.clone()
base = rss_mib()
for _ in range(10):
    if mode == "in-place":
        with torch.no_grad():
            y.sigmoid_()
    elif mode == "no_grad":
        with torch.no_grad():
            y = torch.sigmoid(y)
    else:
        y = torch.sigmoid(y)
print(mode, round(rss_mib() - base), "MiB")
```

</details>

## Common traps

> [!TRAP]
> **`x = x + 1` breaks an alias; `x += 1` does not.** Rebinding gives the name a new buffer, and every other name keeps the old one. Check with `is` and `data_ptr` before assuming two names still match.

> [!TRAP]
> **A view is not a copy.** Writing through `v = base[2:5]` changes `base`, even if you only meant to use `v` for a moment. Call `.clone()` when you need an independent tensor.

> [!TRAP]
> **`.data` turns off autograd's check.** The run above gave a gradient of [-0.3049, 0.2486] where the function the forward pass printed implies [0.47, 0.3932]. Avoid `.data` in code that has gradients, and check gradients with a finite-difference test when you suspect a write.

> [!TRAP]
> **In-place cannot change shape or dtype.** `torch.zeros(3).add_(torch.ones(3, 1))` fails because the result has shape [3, 3], which does not fit the output. An integer tensor cannot hold 1.5, so `i.add_(1.5)` fails and leaves `i` unchanged. Broadcasting works only when the result has the shape of the tensor being written.

## Summary

- Out-of-place operations allocate a new buffer; in-place operations write into the buffer the tensor already owns, and nothing is rebound.
- Assignment, slicing and `+=` on a tensor create aliases. Slicing makes a view that shares memory; `clone()` is the only copy here.
- PyTorch counts in-place writes with a version counter; autograd compares saved versions with current ones and raises an error on a mismatch.
- In-place writes save memory only when no saved value is needed. With gradients on, saved outputs are kept, and `.data` bypasses the check, so avoid it.

## Quiz time

### Question 1: Prediction

With NumPy, `a = np.array([1.0, 2.0])`, then `b = a`, then `a = a * 2`. What does `b` hold?

<details><summary>Show Solution</summary>

`b` holds `[1.0, 2.0]`. The line `a = a * 2` computes a new array and rebinds `a` to it. `b` still points at the original buffer, which was never written.

</details>

### Question 2: Bug-spotting

A loss is computed as `h = torch.sigmoid(z)`, then `h.mul_(0.5)`, then `h.sum().backward()`. What happens, and how do you fix it?

<details><summary>Show Solution</summary>

`backward()` raises a RuntimeError. Sigmoid saves its output for the backward pass. `h.mul_(0.5)` overwrites that output and bumps its version from 0 to 1, so autograd detects the mismatch. The fix is out-of-place: `h = torch.sigmoid(z) * 0.5`. The multiplication allocates a new tensor, so the saved output is left alone.

</details>

### Question 3: Calculation

`base = torch.arange(6.0)`, then `v = base[1:4]`, then `v.mul_(2)`. What is `base.sum()`?

<details><summary>Show Solution</summary>

21. The view covers elements 1 to 3, which hold 1, 2, 3. Multiplying them by 2 gives 2, 4, 6. So `base` becomes [0, 2, 4, 6, 4, 5], and its sum is 21.

</details>

### Question 4: Explanation

Why does `x + 1` need memory that `x.add_(1)` does not?

<details><summary>Show Solution</summary>

The result of `x + 1` must exist while `x` still exists, because `x` is read while the result is computed. It needs its own buffer. `x.add_(1)` writes each result back into the element it came from, so it can reuse `x`'s buffer. The one-buffer write works only when nothing else still needs the old values.

</details>

### Question 5: Bug-spotting

Why does `v = t[1:]` followed by `v.add_(1)` change `t`, but `v = t[1:].clone()` followed by `v.add_(1)` does not?

<details><summary>Show Solution</summary>

Slicing returns a view that points into `t`'s buffer, so writes through `v` land in `t`. `clone()` copies the selected values into a new buffer, so `v` no longer shares memory with `t`.

</details>
