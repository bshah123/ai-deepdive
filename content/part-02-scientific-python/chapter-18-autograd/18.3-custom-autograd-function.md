In this lesson you will write a custom `torch.autograd.Function` with your own backward pass, check that backward with `torch.autograd.gradcheck`, and use tensor hooks to read or edit a gradient as it flows back. You will also meet the two traps that catch most people: gradients add up in `.grad`, and `gradcheck` rejects a backward that is correct for its purpose.

**You need:** reverse-mode automatic differentiation and the chain rule (Lesson 18.1), and the idea of a computational graph (Lesson 18.2). The NumPy block runs in the browser. The PyTorch blocks need `pip install torch`; they were run with torch 2.15.0.

## The problem this solves

Autograd differentiates a program by applying the derivative of each primitive operation it knows, then chaining them. Some operations have a derivative that is useless for learning. Rounding is one. `round(x)` is flat between the half-integers and jumps at each of them, so its derivative is 0 almost everywhere. The finite-difference check below shows both behaviours.

```python
import numpy as np

h = 1e-6
for v in [0.4, 1.6, -0.7, 2.5]:
    d = (np.round(v + h) - np.round(v - h)) / (2 * h)
    print(f"x={v:5.2f}  central difference={d:.1f}")
```

```output
x= 0.40  central difference=0.0
x= 1.60  central difference=0.0
x=-0.70  central difference=0.0
x= 2.50  central difference=500000.0
```

At $x = 2.5$ the function jumps from 2 to 3 within $10^{-6}$, so the quotient explodes; at a jump the derivative does not exist. Everywhere else the derivative is 0, and that is what autograd returns for `torch.round`. My own reasoning: a network that rounds its weights or activations therefore sends no learning signal through the rounding step.

Bengio, Léonard and Courville (2013) studied this kind of hard threshold and proposed a heuristic, the **straight-through estimator** (STE): in the backward pass, copy the gradient arriving at the rounded output to the input unchanged, as if rounding were the identity. The paper calls it a heuristic and its abstract gives no derivation [1]. A second reason to write a custom `Function` is speed or reach: the forward may call a C++ or CUDA kernel that autograd cannot see into, or the backward may have a cheaper closed form than the one autograd builds.

## Intuition: a custom Function is one node

Autograd records each call to `Function.apply` as one node in the graph. Forward computes the output and may store tensors on `ctx`, a small object that carries information from forward to backward. Backward receives the gradient of the loss with respect to the output (`grad_out`) and returns the gradient with respect to each input. Autograd does not look inside the node. It only calls your backward.

![A custom Function is one node: forward runs left to right from leaf x through RoundSTE to y and the loss; backward runs right to left and returns the gradient for x](diagrams/18.3-custom-node.svg "One custom node. Forward runs left to right; backward runs right to left and returns the gradient for x.")

## Worked example by hand

Take four inputs, $x = [0.4,\ 1.6,\ 2.5,\ -0.7]$. The forward pass is $y = \mathrm{round}(x)$ with half-to-even rounding, as `torch.round` and NumPy both use. So $y = [0,\ 2,\ 2,\ -1]$. Take the loss $L = \sum_i y_i$, so $\partial L / \partial y_i = 1$ for every $i$. The chain rule gives

$$
\frac{\partial L}{\partial x_i} = \frac{\partial L}{\partial y_i}\cdot\frac{\partial y_i}{\partial x_i}.
$$

The three rules differ only in the local factor $\partial y_i / \partial x_i$:

- **True derivative** (what autograd uses for `torch.round`): 0 at every point, so $\partial L / \partial x = [0,\ 0,\ 0,\ 0]$.
- **Straight-through** (identity): factor 1, so $[1,\ 1,\ 1,\ 1]$.
- **Clipped straight-through**: factor $\mathbb{1}[\,|x_i| \le 1\,]$. Here $|0.4|$ and $|-0.7|$ pass and $1.6$ and $2.5$ are blocked, so $[1,\ 0,\ 0,\ 1]$.

![Staircase plot of round(x) with flat steps and a dashed ramp of slope 1; the four worked-example inputs are marked on the staircase](diagrams/18.3-ste-staircase.svg "Flat steps have slope 0. The straight-through backward uses the dashed ramp, slope 1, instead.")

![Grouped bars of x.grad for the four inputs under the three rules: true derivative is 0 everywhere, straight-through is 1 everywhere, clipped straight-through is 1 only for 0.4 and -0.7](diagrams/18.3-gradient-rules.svg "Gradient for each input under three backward rules. Values are measured by the code in the next section.")

The straight-through rule is not the derivative of anything. The clipped version adds a cut-off at $|x| \le 1$, which is a design choice that the chain rule does not force. The abstract calls the estimator a heuristic [1]; I did not check the paper body for guarantees, so treat any claim that it converges as unverified.

## Code: a custom Function

Every rule in the figure is one class. The forward is the same in each; only `backward` differs.

<details><summary>Run locally: needs pip install torch (run with torch 2.15.0)</summary>

```python
import torch
from torch.autograd import Function

class RoundSTE(Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return torch.round(x)

    @staticmethod
    def backward(ctx, grad_out):
        return grad_out.clone()  # straight-through: pass the gradient unchanged

class RoundClippedSTE(Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return torch.round(x)

    @staticmethod
    def backward(ctx, grad_out):
        (x,) = ctx.saved_tensors
        return grad_out * (x.abs() <= 1).to(grad_out.dtype)

xs = [0.4, 1.6, 2.5, -0.7]

x = torch.tensor(xs, requires_grad=True)
y = RoundSTE.apply(x)
print("forward:", y.tolist())
y.sum().backward()
print("STE grad:", x.grad.tolist())

x = torch.tensor(xs, requires_grad=True)
torch.round(x).sum().backward()
print("torch.round grad:", x.grad.tolist())

x = torch.tensor(xs, requires_grad=True)
RoundClippedSTE.apply(x).sum().backward()
print("clipped STE grad:", x.grad.tolist())
```

```output
forward: [0.0, 2.0, 2.0, -1.0]
STE grad: [1.0, 1.0, 1.0, 1.0]
torch.round grad: [0.0, 0.0, 0.0, 0.0]
clipped STE grad: [1.0, 0.0, 0.0, 1.0]
```

</details>

Three API points carry the whole pattern:

- `forward` and `backward` are `@staticmethod`s. You never call them directly; `RoundSTE.apply(x)` runs forward and records the node.
- `ctx.save_for_backward(x)` is the documented place for tensors that backward needs. The PyTorch notes say it "should be used to save any tensors needed for the backward pass (as opposed to directly on ctx)" [2].
- `backward` returns one gradient per forward input. The notes say it "should return as many tensors as there were inputs" [2]. These classes have one input, so they return one tensor.

Backward multiplies the incoming gradient by the local derivative, which is the chain rule of the last section applied at one node. For the cube function below, the local derivative is $3x^2$, so backward returns `grad_out * 3 * x ** 2`.

## Checking a backward: gradcheck

`torch.autograd.gradcheck` perturbs each input by a small step, computes finite-difference derivatives, and compares them with your analytic backward. It is designed for double precision, and the default tolerances assume it [3]. The next block checks three cases: a correct backward, a backward with a missing factor, and the straight-through estimator.

<details><summary>Run locally: needs pip install torch (run with torch 2.15.0)</summary>

```python
import torch
from torch.autograd import Function, gradcheck
from torch.autograd.gradcheck import GradcheckError

class CubeFn(Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return x ** 3

    @staticmethod
    def backward(ctx, grad_out):
        (x,) = ctx.saved_tensors
        return grad_out * 3 * x ** 2

class CubeBuggy(Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return x ** 3

    @staticmethod
    def backward(ctx, grad_out):
        (x,) = ctx.saved_tensors
        return grad_out * x ** 2  # bug: the factor 3 is missing

class RoundSTE(Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return torch.round(x)

    @staticmethod
    def backward(ctx, grad_out):
        return grad_out.clone()

xd = torch.tensor([0.5, -1.2, 2.0], dtype=torch.float64, requires_grad=True)
print("CubeFn passes:", gradcheck(CubeFn.apply, (xd,)))
try:
    gradcheck(CubeBuggy.apply, (xd,))
except GradcheckError as e:
    print("CubeBuggy fails:", str(e).splitlines()[0])

xs = torch.tensor([0.4, 1.6, 2.5, -0.7], dtype=torch.float64, requires_grad=True)
try:
    gradcheck(RoundSTE.apply, (xs,))
except GradcheckError as e:
    print("RoundSTE fails:", str(e).splitlines()[0])
```

```output
CubeFn passes: True
CubeBuggy fails: Jacobian mismatch for output 0 with respect to input 0,
RoundSTE fails: Jacobian mismatch for output 0 with respect to input 0,
```

</details>

The straight-through failure is correct behaviour, not a bug in `gradcheck`. The check compares your backward with the true derivative of the forward, which is 0 here, and the straight-through backward deliberately returns 1. So for an estimator, test the backward against the formula you intended, for example the three values in the worked example, and keep `gradcheck` for smooth operations.

## Hooks: reading and editing gradients

`tensor.register_hook(fn)` calls `fn` with the gradient that reaches that tensor during backward. If `fn` returns a tensor, that tensor replaces the gradient; if it returns `None`, the gradient is unchanged. The PyTorch notes list the order of execution: tensor hooks run before a leaf tensor's gradient is accumulated into `.grad`, and a later hook can see the changes made by an earlier one [4]. A hook that returns `None` leaves the gradient unchanged; I checked this in the same environment.

![Pipeline: the graph gives g = 1, the hook returns g times 0.5, and x.grad receives 0.5 by addition; below, three states show x.grad after two backward calls and after a zero_() plus a third backward](diagrams/18.3-hook-accumulation.svg "Hook order and accumulation. The values come from the run in the next block.")

The next block registers a hook that halves the gradient, then runs three backward passes.

<details><summary>Run locally: needs pip install torch (run with torch 2.15.0)</summary>

```python
import torch
from torch.autograd import Function

class RoundSTE(Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return torch.round(x)

    @staticmethod
    def backward(ctx, grad_out):
        return grad_out.clone()

def halve(g):
    print("hook sees:", g.tolist())
    return g * 0.5

x = torch.tensor([0.4, 1.6, 2.5, -0.7], requires_grad=True)
handle = x.register_hook(halve)

RoundSTE.apply(x).sum().backward()
print("x.grad after backward 1:", x.grad.tolist())
RoundSTE.apply(x).sum().backward()
print("x.grad after backward 2:", x.grad.tolist())
x.grad.zero_()
RoundSTE.apply(x).sum().backward()
print("x.grad after zero_() and backward 3:", x.grad.tolist())
handle.remove()
```

```output
hook sees: [1.0, 1.0, 1.0, 1.0]
x.grad after backward 1: [0.5, 0.5, 0.5, 0.5]
hook sees: [1.0, 1.0, 1.0, 1.0]
x.grad after backward 2: [1.0, 1.0, 1.0, 1.0]
hook sees: [1.0, 1.0, 1.0, 1.0]
x.grad after zero_() and backward 3: [0.5, 0.5, 0.5, 0.5]
```

</details>

The hook saw 1.0 each time, because the graph passes $\partial L / \partial x = 1$ for this loss. It returned 0.5, and autograd added that to `.grad`. The second backward did not replace the first value; it added to it, which gives 1.0. Clearing `.grad` with `zero_()` restores the single-pass value. A training loop does this for you through `optimizer.zero_grad()`.

## Common traps

> [!TRAP]
> `.grad` accumulates. Each `backward()` adds to what is already there, so a second backward without clearing gives 1.0, not 0.5. The run above shows it.

> [!TRAP]
> A hook's returned tensor becomes the new gradient. Returning `g * 0.5` halves what the graph computed. Returning `None` leaves it alone, so a logging hook must not return a value by accident.

> [!TRAP]
> Save backward's inputs with `ctx.save_for_backward`, not directly on `ctx` such as `ctx.x = x`. The notes say `save_for_backward` should be used for tensors needed in the backward pass, "as opposed to directly on ctx" [2].

> [!TRAP]
> A failing `gradcheck` on a straight-through estimator is expected. Do not loosen the tolerance to make it pass; the check measures the true derivative, and the estimator is a different object.

> [!TRAP]
> A wrong constant factor raises no error at run time. Only a check like `gradcheck` catches it, as the `CubeBuggy` case above shows. Run it on every custom backward, on float64 inputs.

## Summary

- A custom `autograd.Function` is one graph node. `forward` computes the output, `ctx.save_for_backward` keeps what backward needs, and `backward` returns one gradient per input.
- Autograd gives 0 for `torch.round`; the straight-through estimator replaces it with the identity, which is a heuristic [1].
- `gradcheck` compares a backward with finite differences. It passes for a correct derivative and fails for a straight-through estimator, by design.
- Tensor hooks can read or replace a gradient before it reaches `.grad`. Gradients accumulate across backward calls until you clear them.

## Quiz time

### Question 1: Calculation

Your clipped straight-through function computes $y = \mathrm{round}(x)$ with the backward rule of the lesson. The loss is $L = \sum_i w_i y_i$ with $w = [2,\ 3,\ -1]$, and $x = [0.9,\ -1.4,\ 0.2]$. What is $\partial L / \partial x$?

<details><summary>Show Solution</summary>

The upstream gradient is $\partial L / \partial y = w = [2,\ 3,\ -1]$. The clip factor is $\mathbb{1}[|x_i| \le 1]$, which is $[1,\ 0,\ 1]$, because $|0.9| \le 1$, $|-1.4| > 1$ and $|0.2| \le 1$. So $\partial L / \partial x = [2,\ 0,\ -1]$.

</details>

### Question 2: Prediction

A leaf tensor `x` has a hook that returns `0.5 * g`. You run three backward passes, each producing an incoming gradient of 1 for every element, and you never call `zero_()`. What is `x.grad` after the third pass?

<details><summary>Show Solution</summary>

Each pass adds $0.5$, so after three passes `x.grad` is $1.5$ in every element.

</details>

### Question 3: Bug-spotting

A colleague writes `y = x ** 3` as a custom `Function` and returns `grad_out * x ** 2` from backward. `gradcheck` reports a Jacobian mismatch. What is wrong, and what should the backward return?

<details><summary>Show Solution</summary>

The derivative of $x^3$ is $3x^2$, and the backward is missing the factor 3. The correct return value is `grad_out * 3 * x ** 2`. The mismatch is the reason `gradcheck` exists: it reports the disagreement between the backward and finite differences.

</details>

### Question 4: Explanation

Why does `gradcheck` fail for the straight-through estimator even though the estimator is deliberately chosen? Say what it compares and what the failure means.

<details><summary>Show Solution</summary>

`gradcheck` compares the analytic backward with finite differences of the forward function. For `round`, the finite-difference derivative is 0 away from the jumps, while the straight-through backward returns 1. The mismatch is real: the estimator is not the derivative of the forward. It is a training heuristic, so the failure is expected and does not mean the code is wrong.

</details>
