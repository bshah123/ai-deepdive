Lessons 23.1 and 23.2 built tokenizers by hand. This lesson shows the production library behind `tokenizer.json` files and the "fast" tokenizers in `transformers`: Hugging Face `tokenizers`. You will build a tokenizer from its four stages, trace offsets back to the original text, see exactly how **byte fallback** and **byte-level BPE** (byte-pair encoding) make sure no character is ever lost, and measure where the "Rust core" speed really comes from.

**You need:** BPE merges and byte-level BPE (Lesson 23.1), SentencePiece and the idea of an unknown token (Lesson 23.2), and how text becomes UTF-8 (Unicode Transformation Format, 8-bit) bytes (Lesson 3.3).

## The problem the library solves

A notebook tokenizer is not yet shippable. Production needs four more things:

- **One portable file.** Training and serving must use *exactly* the same normalization, splitting rules, merges and special tokens. A mismatch does not crash; it silently feeds the model ids it never saw.
- **No silent loss.** Users type emoji, accents and scripts your training data barely had; every input must become *some* valid ids.
- **Alignment.** Named-entity recognition and question answering need each token mapped back to a span of the *original* string, even after lowercasing.
- **Speed.** Pre-training corpora are huge (LLaMA's was about 1.4 trillion tokens; Touvron et al., 2023), so tokenizing is a real cost.

`tokenizers` is a Rust library with Python bindings that packs all four into a single `tokenizer.json` file. The `transformers` library's "fast" tokenizers are this library underneath; its documentation says they give a speed-up "in particular when doing batched tokenization" and methods "to map between the original string ... and the token space" (Hugging Face, *Tokenizer* docs).

> [!NOTE]
> Everything here was run with `tokenizers` **0.23.3**, the current stable release on PyPI as of November 2026. A v1.0 release candidate (1.0.0rc4) is out, and its README's roadmap lists training, editing pipeline components, saving and offset output as features still to be brought back to the Python bindings, so the code below needs 0.23.x.

## A tokenizer is a four-stage pipeline

When you call `encode`, the text passes through four swappable components, in this order (Hugging Face, *The tokenization pipeline*):

1. **Normalizer:** cleans the string, for example Unicode normalization (NFD, Normalization Form D, splits `é` into `e` plus a combining accent), accent stripping, lowercasing.
2. **Pre-tokenizer:** splits it into "words". Tokens never cross a word boundary.
3. **Model:** the learned part (BPE from Sennrich, Haddow and Birch, 2016; WordPiece; Unigram; or WordLevel) that splits each word into vocabulary tokens and looks up their ids.
4. **Post-processor:** adds the special tokens a model expects, such as BERT's `[CLS]` and `[SEP]`.

A fifth component, the **decoder**, runs in the opposite direction, from ids back to text. Here is all of it on one sentence, using a tiny BPE trained on four sentences about cats:

![The text The Café cat! flows down four stages: the normalizer gives the cafe cat!, the pre-tokenizer splits it into the, cafe, cat and !, the BPE model gives the, c, a, UNK, e, cat, UNK, and the post-processor wraps it in CLS and SEP; below are the ids and offsets](diagrams/23.3-pipeline.svg "One string through the four stages. Every value here is printed by the code below.")

> [!WARNING]
> The code blocks that import `tokenizers` need a local install (`pip install tokenizers==0.23.3`). The in-browser Python runner on this page has NumPy only. The pure-Python blocks run anywhere.

```python
import tokenizers
from tokenizers import Tokenizer, models, normalizers, pre_tokenizers, processors, trainers

corpus = ["The cat sat on the mat.", "The cat ate the rat.",
          "A rat sat on a hat.", "The hat is on the cat."] * 50

tok = Tokenizer(models.BPE(unk_token="[UNK]"))                     # 3. model
tok.normalizer = normalizers.Sequence(                             # 1. normalizer
    [normalizers.NFD(), normalizers.StripAccents(), normalizers.Lowercase()])
tok.pre_tokenizer = pre_tokenizers.Whitespace()                    # 2. pre-tokenizer
trainer = trainers.BpeTrainer(vocab_size=40, show_progress=False,
                              special_tokens=["[UNK]", "[CLS]", "[SEP]", "[PAD]"])
tok.train_from_iterator(corpus, trainer)                           # learns merges
tok.post_processor = processors.TemplateProcessing(                # 4. post-processor
    single="[CLS] $A [SEP]", special_tokens=[("[CLS]", 1), ("[SEP]", 2)])

text = "The Café cat!"
norm = tok.normalizer.normalize_str(text)
print("tokenizers", tokenizers.__version__, "| vocab size", tok.get_vocab_size())
print("1 normalized   :", repr(norm))
print("2 pre-tokenized:", [w for w, _ in tok.pre_tokenizer.pre_tokenize_str(norm)])
enc = tok.encode(text)
print("3+4 tokens     :", enc.tokens)
print("    ids        :", enc.ids)
print("    offsets    :", enc.offsets)
print("    original   :", [text[a:b] for a, b in enc.offsets])
print("decode         :", repr(tok.decode(enc.ids)))
```

```output
    original   : ['', 'The', 'C', 'a', 'f', 'é', 'cat', '!', '']
decode         : 'the c a e cat'
```

Three things to read off this output:

- **The vocabulary stopped at 27, not 40.** Training ends early once every word in this tiny corpus is a single token, so there is nothing left to merge.
- **Offsets point into the original string.** The token `e` came from the normalized text, yet its offsets `(7, 8)` select `é` in `"The Café cat!"`: the library tracks alignment through every normalization step. (In Python, offsets are character positions.)
- **`'f'` and `'!'` never appeared in training, so they became `[UNK]`.** Worse, `decode` dropped them: `decode` removes special tokens by default (`skip_special_tokens=True`), and `[UNK]` is registered as one. The spaces between `c a e` appear because this pipeline has no decoder, so tokens are joined with spaces (Hugging Face, *The tokenization pipeline*).

The whole pipeline, merges included, is one JSON (JavaScript Object Notation) document. Save it, reload it anywhere, and batch-encode with padding (continuing from the block above):

```python
import json
from tokenizers import Tokenizer

spec = tok.to_str()                                 # the whole pipeline as JSON text
print(list(json.loads(spec).keys()))
tok.save("tiny-tokenizer.json")                     # same JSON, written to a file
again = Tokenizer.from_file("tiny-tokenizer.json")
print("same ids after reload:", again.encode("The Café cat!").ids == tok.encode("The Café cat!").ids)

again.enable_padding(pad_id=again.token_to_id("[PAD]"), pad_token="[PAD]")
batch = again.encode_batch(["the cat", "a rat sat on the mat"])
for e in batch:
    print(e.tokens, e.attention_mask)
```

```output

same ids after reload: True
```

The `attention_mask` marks real tokens with 1 and padding with 0, so the model can ignore the padding.

> [!KEY-INSIGHT]
> `tokenizer.json` *is* the tokenizer. If two systems load the same file, they produce the same ids; if they rebuild the pipeline "the same way" in code, they often do not.

## Worked example: three answers to an unseen character

The `[UNK]` above is the core problem. Take the string `café🤗` and a vocabulary that only knows `c`, `a` and `f`. Every character has a Unicode **code point**, written U+ and a hex number, and is stored as 1 to 4 **UTF-8 bytes**: `é` (U+00E9) is the two bytes `C3 A9`, and the emoji 🤗 (U+1F917) is the four bytes `F0 9F A4 97`. There are three ways to handle the two unknown characters:

![The input café plus emoji, with UTF-8 bytes under each character, tokenized three ways: unknown-token gives c a f unk unk; byte fallback gives c a f followed by six byte tokens 0xC3 0xA9 0xF0 0x9F 0xA4 0x97; byte-level BPE gives c a f followed by six byte characters](diagrams/23.3-unseen-chars.svg "Same input, three strategies. Only the first loses information.")

- **Unknown token:** replace each one with `<unk>`. Five tokens, but you can never get the text back. (WordPiece, Lesson 23.2, is harsher: `models.WordPiece` with this vocabulary turns the whole word `café🤗` into one `[UNK]`.)
- **Byte fallback:** keep the character-level vocabulary, add the 256 byte tokens `<0x00>` to `<0xFF>`, and spell *only the unknown characters* as their bytes. Nine tokens, fully reversible.
- **Byte-level BPE:** turn *every* character into bytes before the model ever sees it, so the base vocabulary is the 256 bytes and nothing can be unknown, provided all 256 are in the vocabulary (Lesson 23.1; see the trap below).

Do the first two by hand in plain Python:

```python
text = "café🤗"
for ch in text:
    b = ch.encode("utf-8")                     # the raw bytes a computer stores
    print(f"{ch!r} = U+{ord(ch):04X} = {len(b)} byte(s): {b.hex(' ').upper()}")

vocab = {"c", "a", "f"}                         # a toy vocabulary of characters

def with_unk(text):
    return [ch if ch in vocab else "<unk>" for ch in text]

def with_byte_fallback(text):
    out = []
    for ch in text:
        if ch in vocab:
            out.append(ch)
        else:                                   # spell the character as its UTF-8 bytes
            out += [f"<0x{b:02X}>" for b in ch.encode("utf-8")]
    return out

def undo_byte_fallback(tokens):
    raw = b"".join(bytes([int(t[3:5], 16)]) if t.startswith("<0x") else t.encode()
                   for t in tokens)
    return raw.decode("utf-8")

print(with_unk(text))
toks = with_byte_fallback(text)
print(toks, len(toks), "tokens")
print(undo_byte_fallback(toks))
```

```output

'a' = U+0061 = 1 byte(s): 61
'f' = U+0066 = 1 byte(s): 66
'é' = U+00E9 = 2 byte(s): C3 A9
'🤗' = U+1F917 = 4 byte(s): F0 9F A4 97
['c', 'a', 'f', '<unk>', '<unk>']
['c', 'a', 'f', '<0xC3>', '<0xA9>', '<0xF0>', '<0x9F>', '<0xA4>', '<0x97>'] 9 tokens
café🤗
```

Byte fallback is an option of SentencePiece (Kudo and Richardson, 2018; Lesson 23.2), `--byte_fallback`, documented as "decomposes out-of-vocabulary characters into UTF-8 byte tokens (e.g., `<0xE3>`)" in its options documentation. LLaMA used it: its tokenizer is SentencePiece BPE, and the authors "fallback to bytes to decompose unknown UTF-8 characters" (Touvron et al., 2023, Section 2.1).

### The same thing in the library

`models.BPE(byte_fallback=True)` does exactly what `with_byte_fallback` does. In the 0.23.3 Rust source (`models/bpe/model.rs`), when a symbol is not in the vocabulary, the model looks up `<0xNN>` for each of its bytes, and uses `unk_token` only if one of those byte tokens is missing. The `ByteFallback` decoder turns the byte tokens back into UTF-8, and `Fuse` joins the pieces into one string.

```python
from tokenizers import Tokenizer, models, decoders

def build(byte_fallback):
    vocab = {"<unk>": 0}
    if byte_fallback:                                   # 256 byte tokens <0x00> ... <0xFF>
        vocab.update({f"<0x{b:02X}>": 1 + b for b in range(256)})
    for t in ["c", "a", "f", "t", "ca", "cat"]:
        vocab[t] = len(vocab)
    model = models.BPE(vocab=vocab, merges=[("c", "a"), ("ca", "t")],
                       unk_token="<unk>", byte_fallback=byte_fallback)
    tok = Tokenizer(model)
    tok.decoder = decoders.Sequence([decoders.ByteFallback(), decoders.Fuse()])
    return tok

for bf in (False, True):
    tok = build(bf)
    enc = tok.encode("café🤗cat")
    print(f"byte_fallback={bf}  vocab={tok.get_vocab_size()}")
    print("  tokens:", enc.tokens)
    print("  decode:", repr(tok.decode(enc.ids)))
```

```output
byte_fallback=False  vocab=7
  tokens: ['ca', 'f', '<unk>', '<unk>', 'cat']
  decode: 'caf<unk><unk>cat'
byte_fallback=True  vocab=263
  tokens: ['ca', 'f', '<0xC3>', '<0xA9>', '<0xF0>', '<0x9F>', '<0xA4>', '<0x97>', 'cat']
  decode: 'café🤗cat'
```

The cost is 256 extra vocabulary entries, and more tokens for every rare character: 🤗 alone takes four.

## Byte-level BPE and the strange `Ġ`

If you have ever printed GPT-2 or RoBERTa tokens you have seen `Ġthe` and `Ã©`. That is the byte-level BPE of Lesson 23.1 (Radford et al., 2019; RoBERTa adopted the same scheme with a 50K vocabulary, Liu et al., 2019). Bytes such as space (`0x20`) or newline (`0x0A`) are awkward inside a vocabulary file of strings, so GPT-2's `bytes_to_unicode` gives every byte a *printable* stand-in character:

![A 16 by 16 grid of all byte values: 188 printable bytes keep their own character, 68 bytes, mostly control characters, space and 0x7F to 0xA0, are shown as letters from U+0100 to U+0143; newline becomes Ċ and space becomes Ġ](diagrams/23.3-byte-map.svg "GPT-2's byte-to-character table. Blue cells map to themselves; amber cells were moved.")

```python
def bytes_to_unicode():
    """GPT-2's byte -> printable-character table (openai/gpt-2, src/encoder.py)."""
    bs = (list(range(ord("!"), ord("~") + 1)) + list(range(ord("¡"), ord("¬") + 1))
          + list(range(ord("®"), ord("ÿ") + 1)))      # bytes that already look fine
    cs = bs[:]
    n = 0
    for b in range(256):
        if b not in bs:                               # control chars, space, etc.
            bs.append(b)
            cs.append(256 + n)                        # move them past U+00FF
            n += 1
    return dict(zip(bs, map(chr, cs)))

table = bytes_to_unicode()
kept = sum(table[b] == chr(b) for b in range(256))
print("bytes kept as themselves:", kept, "| bytes shifted:", 256 - kept)
print("one-to-one:", len(set(table.values())) == 256)
for b in [0x41, 0x20, 0x0A, 0xC3, 0xA9]:
    print(f"byte 0x{b:02X} -> {table[b]!r} (U+{ord(table[b]):04X})")

def byte_level(text):
    return "".join(table[b] for b in text.encode("utf-8"))
print(byte_level("café🤗"), "|", byte_level(" the\n"))

inverse = {c: b for b, c in table.items()}
print(bytes(inverse[c] for c in byte_level("café🤗")).decode("utf-8"))
```

```output

one-to-one: True

byte 0x0A -> 'Ċ' (U+010A)
```

So `Ġ` just means "this token starts with a space" (the leading space GPT-2's pre-tokenizer keeps on each word, Lesson 23.1), and `Ã©` is the two bytes of `é` shown one character per byte. The library's `pre_tokenizers.ByteLevel` uses the same table (it is `bytes_char` in the 0.23.3 source; `set(table.values()) == set(pre_tokenizers.ByteLevel.alphabet())` is `True`). Now train a byte-level BPE in the library, once with all 256 byte characters in the starting alphabet and once without:

```python
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers

corpus = ["The cat sat on the mat.", "The cat ate the rat.",
          "A rat sat on a hat.", "The hat is on the cat."] * 50

def byte_level_bpe(initial_alphabet):
    tok = Tokenizer(models.BPE())
    tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False)
    tok.decoder = decoders.ByteLevel()
    trainer = trainers.BpeTrainer(vocab_size=300, show_progress=False,
                                  initial_alphabet=initial_alphabet)
    tok.train_from_iterator(corpus, trainer)
    return tok

alphabet = pre_tokenizers.ByteLevel.alphabet()          # the 256 byte characters
print("alphabet size:", len(alphabet), "| contains 'Ġ':", "Ġ" in alphabet)

text = "The café 🤗"
for name, alpha in [("all 256 bytes", alphabet), ("corpus bytes only", [])]:
    tok = byte_level_bpe(alpha)
    enc = tok.encode(text)
    print(f"{name}: vocab={tok.get_vocab_size()}")
    print("  tokens:", enc.tokens)
    print("  decode:", repr(tok.decode(enc.ids)))
    if alpha:
        print("  offsets:", enc.offsets)
```

```output
alphabet size: 256 | contains 'Ġ': True
all 256 bytes: vocab=278
  tokens: ['The', 'Ġ', 'c', 'a', 'f', 'Ã', '©', 'Ġ', 'ð', 'Ł', '¤', 'Ĺ']
  decode: 'The café 🤗'
  offsets: [(0, 3), (3, 4), (4, 5), (5, 6), (6, 7), (7, 8), (7, 8), (8, 9), (9, 10), (9, 10), (9, 10), (9, 10)]
corpus bytes only: vocab=37
  tokens: ['The', 'Ġ', 'c', 'a', 'Ġ']
  decode: 'The ca '
```

With the full alphabet, the text round-trips exactly. Without it, the trainer only knows bytes that occurred in the corpus, the model has no `unk_token`, and `f`, `é` and 🤗 **disappear without any error**. Note also that several tokens can share one character span: `Ã` and `©` both have offsets `(7, 8)`, because a token is a byte sequence, not a character.

| | byte fallback | byte-level BPE |
|---|---|---|
| Base vocabulary | characters + 256 byte tokens | exactly 256 byte characters |
| Common characters | one token each | spelled as bytes, then merged by BPE |
| Rare characters | spelled as `<0xNN>` tokens | spelled as bytes |
| Used by (cited above) | SentencePiece option; LLaMA | GPT-2, RoBERTa |

## Under the hood: where the Rust speed comes from

The Python package is a thin layer over a Rust crate (package), with bindings built by PyO3 (`bindings/python/Cargo.toml`). Batch calls are split across CPU cores by the Rayon library unless the environment variable `TOKENIZERS_PARALLELISM` is false (`utils/parallelism.rs`). Those worker threads run pure Rust, so Python's global interpreter lock (GIL), which lets only one thread run Python code at a time, does not hold them back; batch calls also release the GIL (`py.detach` in `bindings/python/src/tokenizer.rs`) so your other Python threads keep running. The repository README claims it "takes less than 20 seconds to tokenize a GB of text on a server's CPU".

"Rust is fast" is a claim, so test it. I trained a 4,000-token BPE with the library, re-implemented its encoding in pure Python (apply the lowest-ranked merge first, as GPT-2's `bpe()` does), confirmed that all variants give **identical ids** on 2,000 documents (2.86 MB), and timed each one:

```python
import json, os, random, re, time
import tokenizers
from tokenizers import Tokenizer, models, pre_tokenizers, trainers

# --- a synthetic corpus: 100k made-up word types with Zipf-like frequencies
rng = random.Random(0)
syll = ["ka", "to", "ri", "sen", "mo", "la", "pe", "dun", "vi", "ar",
        "es", "qu", "il", "tha", "no", "b", "x", "u"]
words = ["".join(rng.choices(syll, k=rng.randint(1, 5))) for _ in range(100_000)]
freq = [1 / (r + 1) for r in range(len(words))]
def doc():
    return " ".join(rng.choices(words, freq, k=200)) + "."
train_docs = [doc() for _ in range(2000)]
test_docs = [doc() for _ in range(2000)]

# --- train a BPE tokenizer with the library (Rust)
tok = Tokenizer(models.BPE())
tok.pre_tokenizer = pre_tokenizers.Whitespace()            # regex \w+|[^\w\s]+
tok.train_from_iterator(train_docs, trainers.BpeTrainer(vocab_size=4000, show_progress=False))

# --- the same model in pure Python: apply merges in rank order (as in GPT-2's bpe())
state = json.loads(tok.to_str())
vocab = state["model"]["vocab"]
rank = {tuple(m): i for i, m in enumerate(state["model"]["merges"])}
NO_MERGE = 1 << 30

def bpe_word(word):
    parts = list(word)
    while len(parts) > 1:
        r, i = min((rank.get(p, NO_MERGE), i) for i, p in enumerate(zip(parts, parts[1:])))
        if r == NO_MERGE:
            break
        parts[i:i + 2] = [parts[i] + parts[i + 1]]          # apply the best-ranked merge
    return parts

def py_encode(text, cache=None):
    ids = []
    for w in re.findall(r"\w+|[^\w\s]+", text):
        if cache is None:
            ids += [vocab[p] for p in bpe_word(w)]
        else:
            if w not in cache:
                cache[w] = [vocab[p] for p in bpe_word(w)]
            ids += cache[w]
    return ids

rust_ids = [e.ids for e in tok.encode_batch(test_docs)]
assert rust_ids == [e.ids for e in tok.encode_batch_fast(test_docs)]
assert rust_ids == [py_encode(t) for t in test_docs] == [py_encode(t, {}) for t in test_docs]
print("Python and Rust give identical ids on all", len(test_docs), "documents")

def best_of_3(f):
    times = []
    for _ in range(3):
        t0 = time.perf_counter(); f(); times.append(time.perf_counter() - t0)
    return min(times)

mb = sum(len(t.encode()) for t in test_docs) / 1e6
results = {}
results["Python, no cache"] = best_of_3(lambda: [py_encode(t) for t in test_docs])
results["Python + cache, cold"] = best_of_3(lambda: (lambda c: [py_encode(t, c) for t in test_docs])({}))
CACHE = {}                                       # shared across runs, like the Rust word cache
results["Python + cache, warm"] = best_of_3(lambda: [py_encode(t, CACHE) for t in test_docs])
results["Rust, encode() loop"] = best_of_3(lambda: [tok.encode(t) for t in test_docs])
os.environ["TOKENIZERS_PARALLELISM"] = "false"
results["Rust, encode_batch, 1 thread"] = best_of_3(lambda: tok.encode_batch(test_docs))
results["Rust, batch_fast, 1 thread"] = best_of_3(lambda: tok.encode_batch_fast(test_docs))
os.environ["TOKENIZERS_PARALLELISM"] = "true"
results["Rust, encode_batch, all cores"] = best_of_3(lambda: tok.encode_batch(test_docs))
results["Rust, batch_fast, all cores"] = best_of_3(lambda: tok.encode_batch_fast(test_docs))

print(f"tokenizers {tokenizers.__version__}, {os.cpu_count()} CPU cores, {mb:.2f} MB of text")
for k, v in results.items():
    print(f"{k:31s} {v:6.3f} s  {mb / v:6.1f} MB/s")
```

A follow-up, appended to the same script and run separately. (Re-running the whole script on the same machine moved individual timings by up to about 25 percent, most for the multi-core rows.)

```python
# Continuing from the script above: does the Rust word cache explain the gap?
os.environ["TOKENIZERS_PARALLELISM"] = "false"
n_types = len({w for t in test_docs for w in re.findall(r"\w+|[^\w\s]+", t)})
print("distinct words in the test text:", n_types)
merges = [tuple(m) for m in state["model"]["merges"]]
for cap in [10_000, 200_000]:                     # 10,000 is the library default
    t2 = Tokenizer(models.BPE(vocab=vocab, merges=merges, cache_capacity=cap))
    t2.pre_tokenizer = pre_tokenizers.Whitespace()
    assert [e.ids for e in t2.encode_batch(test_docs)] == rust_ids
    speed = mb / best_of_3(lambda: t2.encode_batch(test_docs))
    print(f"cache_capacity={cap:>7,}: {speed:.1f} MB/s, 1 thread")
```

```output
distinct words in the test text: 27131
cache_capacity= 10,000: 8.5 MB/s, 1 thread
cache_capacity=200,000: 9.0 MB/s, 1 thread
```

</details>

What the numbers say (one run, one machine, synthetic ASCII text, so treat them as a sketch, not a benchmark):

- **The algorithm matters first.** A **word cache** (remember each word's tokens the first time you see it, as GPT-2's encoder does) makes pure Python 6.7× faster, because word frequencies are skewed and most words repeat.
- **One Rust thread is not magic.** A single-threaded `encode_batch` (8.5 MB/s) ran no faster than cached Python on its first pass (8.7 MB/s), and a warm-cache Python loop was faster still. That loop only returns ids, while the library also tracks offsets and builds full `Encoding` objects: `encode_batch_fast`, which skips offsets, nearly doubled single-thread speed (15.5 MB/s). Rust's own word cache holds only 10,000 words by default (`utils/cache.rs`), against 27,131 distinct test words, but raising `cache_capacity` to 200,000 only moved 8.5 to 9.0 MB/s (follow-up in the details block), so that is not the explanation.
- **The big win is parallelism.** Rayon spread `encode_batch` over all 10 cores: 6.1× faster than one thread. A Python loop over `tok.encode` stays at one-thread speed (8.4 MB/s), so always batch.

68 MB/s is about 15 seconds per GB, consistent with the README's claim (different text, different CPU). My conclusion, from these measurements rather than any published benchmark: you use the library less for single-thread speed than for **one exact file, alignment, no silent loss, and painless parallelism**.

## Common traps

> [!TRAP]
> **`decode` drops special tokens by default.** If `[UNK]` is registered as a special token, unknown text vanishes from the decoded string without warning. Pass `skip_special_tokens=False` while debugging.

> [!TRAP]
> **Both byte schemes need all 256 bytes in the vocabulary.** Byte-level BPE trained without `initial_alphabet=ByteLevel.alphabet()` silently deletes unseen bytes (`"The café 🤗"` decoded to `"The ca "`), and byte fallback with even one `<0xNN>` missing turns a whole character into `<unk>` (Quiz question 2).

> [!TRAP]
> **Offsets are not one per character.** With byte-level tokens several tokens can share a span, and special tokens get `(0, 0)`. Code that assumes one token per character will mis-highlight.

> [!TRAP]
> **Forking after parallel use turns parallelism off.** If a process encoded in parallel and then forks (for example `multiprocessing` or PyTorch `DataLoader` workers using the `fork` start method), the child silently disables parallelism to avoid deadlocks, unless `TOKENIZERS_PARALLELISM` was set explicitly (`bindings/python/src/lib.rs`). Set it yourself.

> [!TRAP]
> **Changing the normalizer or pre-tokenizer after training invalidates the merges.** Nothing errors, but the merges were learned on the old splits; the docs say to retrain. The post-processor can change freely (Hugging Face, *The tokenization pipeline*).

## Summary

- A Hugging Face tokenizer is normalizer → pre-tokenizer → model → post-processor, plus a decoder, and all of it is saved in one `tokenizer.json`.
- `Encoding.offsets` maps every token back to the original string, through lowercasing and accent stripping.
- Byte fallback keeps a character vocabulary and spells only unknown characters as `<0xNN>` byte tokens; byte-level BPE (GPT-2's `Ġ` table) turns everything into bytes first. Both are lossless if set up right.
- The library's speed comes mostly from parallel batches spread over all cores, and from skipping work you don't need (`encode_batch_fast`); a single Rust thread is not dramatically faster than a well-cached Python BPE.

### Question 2: Predict the output

This vocabulary has byte fallback switched on but contains only *one* byte token. What does it print?

```python
from tokenizers import Tokenizer, models
vocab = {"<unk>": 0, "c": 1, "a": 2, "f": 3, "<0xC3>": 4}     # only ONE byte token
tok = Tokenizer(models.BPE(vocab=vocab, merges=[], unk_token="<unk>", byte_fallback=True))
```

### Question 3: Find the bug

A colleague's GPT-2-style tokenizer decodes `"The café 🤗"` as `"The ca "`. Which line causes it, and how do you fix it?

```python
tok = Tokenizer(models.BPE())
tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False)
tok.decoder = decoders.ByteLevel()
trainer = trainers.BpeTrainer(vocab_size=300)
tok.train_from_iterator(corpus, trainer)
```

<details><summary>Show Solution</summary>

The trainer line. Without `initial_alphabet`, the trainer adds only the bytes that occur in `corpus`. The bytes of `f`, `é` and 🤗 are missing from the vocabulary, and with no `unk_token` they are dropped. Fix: `trainers.BpeTrainer(vocab_size=300, initial_alphabet=pre_tokenizers.ByteLevel.alphabet())`. The lesson's run with this fix decodes `'The café 🤗'` exactly.

</details>

### Question 4: Read the table

Using GPT-2's `bytes_to_unicode` table, what character does byte `0x21` (`!`) become? And byte `0x7F` (the DEL control character)?

<details><summary>Show Solution</summary>

`0x21` is in the first kept range (`!` to `~`), so it stays `'!'`. `0x7F` is not kept. The moved bytes are numbered in order: `0x00` to `0x20` take the 33 slots U+0100 to U+0120, so `0x7F` is next and becomes U+0121, `'ġ'`. Checking with the lesson's function: `table[0x21]` is `'!'` and `table[0x7F]` is `'ġ'` (U+0121). You can find it in the diagram at row `7_`, column `_F`.

</details>

### Question 5: Explain the benchmark

In the benchmark, a warm-cache pure-Python loop (29.3 MB/s) beat the library's single-threaded `encode_batch` (8.5 MB/s). Give two reasons this does not mean Python is "faster than Rust", and say how you would make the library win.

<details><summary>Show Solution</summary>

(1) The two do different amounts of work: the Python loop returns only ids, while `encode_batch` also tracks offsets through normalization and builds `Encoding` objects with tokens, masks and offsets; `encode_batch_fast` skipping offsets alone nearly doubled the speed. (2) The warm cache means the Python loop does almost no BPE at all, only a regex and dictionary lookups; on its first pass it ran at 8.7 MB/s, the same as one Rust thread. To make the library win, call `encode_batch` (or `encode_batch_fast` when offsets are not needed) on large batches with parallelism on, which used all 10 cores for about 52 to 68 MB/s.

</details>

## Exercise: the cost of byte fallback across scripts

A byte-fallback vocabulary that only knows lowercase ASCII letters and space must spell every other character as bytes. Write `byte_fallback_tokens(text)` that returns the token count without building the tokens, and print tokens per character for English, French, Hindi and Japanese text.

<details><summary>Show Solution</summary>

A known character costs 1 token; any other character costs its UTF-8 length.

```python
samples = {
    "English": "the cat sat on the mat",
    "French": "le cœur a ses raisons",
    "Hindi": "नमस्ते दुनिया",
    "Japanese": "こんにちは世界",
}
vocab = set("abcdefghijklmnopqrstuvwxyz ")          # ASCII letters and space only

def byte_fallback_tokens(text):
    n = 0
    for ch in text:
        n += 1 if ch in vocab else len(ch.encode("utf-8"))
    return n

for lang, text in samples.items():
    n = byte_fallback_tokens(text)
    print(f"{lang:9s} {len(text):3d} chars -> {n:3d} tokens  ({n / len(text):.2f} per char)")
```

```output
English    22 chars ->  22 tokens  (1.00 per char)
French     21 chars ->  22 tokens  (1.05 per char)
Hindi      13 chars ->  37 tokens  (2.85 per char)
Japanese    7 chars ->  21 tokens  (3.00 per char)
```

"Chars" here are Unicode code points: the Hindi vowel signs count as separate code points. Devanagari and Japanese characters take 3 bytes each in UTF-8, so text in those scripts costs about three times as many tokens per character. A real tokenizer reduces this by learning those characters (and merges of them) when they are common in training data, which is why the training mix matters for non-English users.

</details>
