FlashAttention computes exactly the same attention output as Lesson 25.1, but never stores the $N \times N$ matrix of scores. In this lesson you will compute a softmax in pieces by hand, build the whole tiled algorithm in NumPy, check that it matches ordinary attention, and learn what versions 2 and 3 changed.

**You need:** scaled dot-product attention and the softmax max-subtraction trick (Lesson 25.1), and the causal mask (Lesson 25.3). No GPU programming is assumed.

## The problem: attention is slowed by memory traffic, not arithmetic

For a sequence of $N$ tokens, attention builds a score matrix $S = QK^\top/\sqrt{d}$ (here $d$ is the head width, called $d_k$ in Lesson 25.1 and $d_{\text{head}}$ in Lesson 25.2) and a weight matrix $P = \mathrm{softmax}(S)$, each with $N^2$ numbers. At $N = 16{,}384$ that is 512 MiB per matrix, per head, per sequence, in 16-bit floats (the table further down computes this).

A GPU (graphics processing unit) has two kinds of memory that matter here:

- **HBM** (high-bandwidth memory): the main GPU memory. Large, but comparatively slow to reach.
- **SRAM** (static random-access memory): small memory on the chip itself, next to the arithmetic units. Fast, but tiny. An NVIDIA A100 has 192 KB of it per *streaming multiprocessor* (SM, one of the GPU's 108 independent compute units).

The sketch uses the A100 figures quoted by Dao et al. (2022, Section 2.1). Arithmetic can only happen on data that has been brought on-chip, and a matrix with $N^2$ numbers does not fit there. So a standard implementation runs three separate steps, and each one pushes an $N \times N$ matrix through the slow link:

![Standard attention: Q and K are read from HBM, S is written back, S is read again, P is written back, P and V are read, O is written. Four of the six transfers carry an N by N matrix.](diagrams/25.4-three-round-trips.svg "Red arrows carry N × N numbers. The arithmetic is cheap; the transfers are not.")

> [!KEY-INSIGHT]
> Counting floating-point operations does not predict the running time of attention. Counting how many numbers cross between slow and fast memory does. FlashAttention is designed around the second count.

## The idea: one tile at a time

Cut the queries into blocks of rows and the keys and values into blocks of columns. A **tile** is the small piece of $S$ where one query block meets one key block. Load the three small blocks, compute the tile, use it, and throw it away:

![The score matrix as an 8 by 8 grid of tiles that is never stored. One row block is highlighted, one tile in it is being computed. In SRAM: a Q block, a K block, a V block, the 128 by 128 score tile, and per-row running state m, l and acc.](diagrams/25.4-tiling.svg "For N = 1,024, d = 64 and 128 × 128 tiles, everything a tile needs is about 96.5 KiB.")

There is one obstacle. Softmax divides each score's exponential by the sum over the **whole row**, and a tile only sees part of the row. The fix is to carry a small running state per row and correct it as each tile arrives. This is called **online softmax**. The single-pass way of computing the softmax normaliser is due to Milakov and Gimelshein (2018); FlashAttention applies it block by block.

## Worked example: softmax in two pieces

Take the query from Lesson 25.1 with a fourth key added. Its scaled scores are $[2, 0, 1, 3]$ and the values are $v_1 = [10, 0]$, $v_2 = [0, 10]$, $v_3 = [5, 5]$, $v_4 = [10, 10]$. Process the keys two at a time, keeping three things:

- $m$: the largest score seen so far.
- $\ell$: the sum of $e^{s_j - m}$ over the keys seen so far.
- $\mathrm{acc}$: the sum of $e^{s_j - m}\, v_j$ over the keys seen so far (an output that is not yet normalised).

![Scores 2, 0 form block 1 and scores 1, 3 form block 2. After block 1: m = 2, l = 1.135, acc = (10, 1.353). Multiply by 0.368 and add block 2: m = 3, l = 1.553, acc = (14.355, 11.175). Divide by l to get the output (9.244, 7.195).](diagrams/25.4-online-softmax.svg "The state after block 1 is corrected by one multiplication when a larger score shows up.")

1. **Block 1**, scores $[2, 0]$. The max is $m = 2$. Unnormalised weights: $[e^{0}, e^{-2}] = [1, 0.135]$. So $\ell = 1.135$ and $\mathrm{acc} = 1 \cdot v_1 + 0.135 \cdot v_2 = [10, 1.353]$.
2. **Block 2**, scores $[1, 3]$. The max rises to $m = 3$. Everything stored so far was measured against the old max, so shrink it by $e^{2-3} = 0.368$. New weights: $[e^{-2}, e^{0}] = [0.135, 1]$. So $\ell = 0.368 \cdot 1.135 + 1.135 = 1.553$ and $\mathrm{acc} = 0.368 \cdot [10, 1.353] + 0.135 \cdot v_3 + 1 \cdot v_4 = [14.355, 11.175]$.
3. **Finish.** Output $= \mathrm{acc} / \ell = [9.244, 7.195]$.

```python
import numpy as np

s = np.array([2.0, 0.0, 1.0, 3.0])            # scaled scores of one query against 4 keys
V = np.array([[10.0,  0.0],                   # value 1
              [ 0.0, 10.0],                   # value 2
              [ 5.0,  5.0],                   # value 3
              [10.0, 10.0]])                  # value 4

m, l, o = -np.inf, 0.0, np.zeros(2)           # running max, running sum, running (unnormalised) output
for start in (0, 2):                          # two blocks of two keys each
    sb, Vb = s[start:start + 2], V[start:start + 2]
    m_new = max(m, sb.max())
    shrink = np.exp(m - m_new)                # rescales everything accumulated so far
    p = np.exp(sb - m_new)                    # this block's unnormalised weights
    l = shrink * l + p.sum()
    o = shrink * o + p @ Vb
    m = m_new
    print(f"after keys {start + 1}-{start + 2}: shrink={shrink:.3f}  p={np.round(p, 3)}  m={m:.0f}  l={l:.3f}  o={np.round(o, 3)}")

print("online :", np.round(o / l, 3))         # normalise once, at the very end
w = np.exp(s) / np.exp(s).sum()               # ordinary softmax over all four scores
print("weights:", np.round(w, 3))
print("direct :", np.round(w @ V, 3))
```

```output
after keys 1-2: shrink=0.000  p=[1.    0.135]  m=2  l=1.135  o=[10.     1.353]
after keys 3-4: shrink=0.368  p=[0.135 1.   ]  m=3  l=1.553  o=[14.355 11.175]
online : [9.244 7.195]
weights: [0.237 0.032 0.087 0.644]
direct : [9.244 7.195]
```

The first `shrink` is 0 only because nothing has been accumulated yet ($e^{-\infty} = 0$).

## Why it is exact

Claim: after any number of blocks, $\ell = \sum_j e^{s_j - m}$ and $\mathrm{acc} = \sum_j e^{s_j - m} v_j$, where the sums run over the keys seen so far and $m$ is their max.

Suppose this holds and a new block arrives that raises the max to $m'$. Multiplying the old sums by $e^{m - m'}$ turns every old term $e^{s_j - m}$ into $e^{s_j - m'}$, because $e^{s_j - m} \cdot e^{m - m'} = e^{s_j - m'}$. Adding the new block's terms $e^{s_j - m'}$ makes the claim true again. At the end,

$$
\frac{\mathrm{acc}}{\ell} = \frac{\sum_j e^{s_j - m}\, v_j}{\sum_j e^{s_j - m}} = \frac{\sum_j e^{s_j}\, v_j}{\sum_j e^{s_j}}
$$

because the common factor $e^{-m}$ cancels. The right-hand side is ordinary attention. Nothing was approximated. On a computer the two differ only by rounding, since the additions happen in a different order.

The running max is not optional. Without it the exponentials overflow:

```python
import numpy as np

s = np.array([1000.0, 999.0, 998.0])
with np.errstate(over="ignore", invalid="ignore"):
    print("no max subtracted:", np.exp(s) / np.exp(s).sum())
print("max subtracted   :", np.round(np.exp(s - s.max()) / np.exp(s - s.max()).sum(), 3))
print("largest float64  :", np.finfo(np.float64).max, " exp overflows above", round(float(np.log(np.finfo(np.float64).max)), 1))
print("largest float16  :", np.finfo(np.float16).max, " exp overflows above", round(float(np.log(np.finfo(np.float16).max)), 1))
```

```output
no max subtracted: [nan nan nan]
max subtracted   : [0.665 0.245 0.09 ]
largest float64  : 1.7976931348623157e+308  exp overflows above 709.8
largest float16  : 6.55e+04  exp overflows above 11.1
```

In 16-bit floats, a common choice on GPUs, a score above about 11 is already too large to exponentiate.

## The full algorithm in NumPy

Now do the same for a block of queries at once: $m$ and $\ell$ become one number per row, and `acc` one vector per row. The loop order below (query blocks outside, key blocks inside) is the one FlashAttention-2 uses. NumPy runs on the CPU, so this shows the algorithm, not the speed-up.

```python
import numpy as np

def naive_attention(Q, K, V, causal=False):
    S = Q @ K.T / np.sqrt(Q.shape[1])                     # the full N x N score matrix
    if causal:
        S = np.where(np.triu(np.ones(S.shape, dtype=bool), k=1), -np.inf, S)
    P = np.exp(S - S.max(axis=1, keepdims=True))
    return (P / P.sum(axis=1, keepdims=True)) @ V, S.size

def flash_attention(Q, K, V, Bq=128, Bk=128, causal=False):
    N, d = Q.shape
    O = np.empty((N, V.shape[1]))
    tiles = peak = 0
    for i in range(0, N, Bq):                             # outer loop: a block of queries (rows)
        Qi = Q[i:i + Bq]
        m = np.full((len(Qi), 1), -np.inf)                # running max, one per row
        l = np.zeros((len(Qi), 1))                        # running sum, one per row
        acc = np.zeros((len(Qi), V.shape[1]))             # running unnormalised output
        for j in range(0, N, Bk):                         # inner loop: a block of keys and values
            if causal and j > i + len(Qi) - 1:
                break                                     # tile is entirely in the future: skip it
            S = Qi @ K[j:j + Bk].T / np.sqrt(d)           # one small tile of scores
            if causal and j + Bk - 1 > i:                 # tile touches the diagonal: mask inside it
                rows = np.arange(i, i + len(Qi))[:, None]
                cols = np.arange(j, j + S.shape[1])[None, :]
                S = np.where(cols > rows, -np.inf, S)
            m_new = np.maximum(m, S.max(axis=1, keepdims=True))
            shrink = np.exp(m - m_new)
            P = np.exp(S - m_new)
            l = shrink * l + P.sum(axis=1, keepdims=True)
            acc = shrink * acc + P @ V[j:j + Bk]
            m = m_new
            tiles += 1
            peak = max(peak, S.size)
        O[i:i + Bq] = acc / l                             # normalise once per row block
    return O, tiles, peak

rng = np.random.default_rng(0)
N, d = 1024, 64
Q, K, V = (rng.standard_normal((N, d)) for _ in range(3))

for causal in (False, True):
    ref, full = naive_attention(Q, K, V, causal)
    out, tiles, peak = flash_attention(Q, K, V, causal=causal)
    print(f"causal={causal!s:5}  same result: {np.allclose(out, ref, rtol=0, atol=1e-12)}"
          f"  tiles computed: {tiles:2d} of 64  largest score array: {peak:,} vs {full:,} numbers")
```

```output
causal=False  same result: True  tiles computed: 64 of 64  largest score array: 16,384 vs 1,048,576 numbers
causal=True   same result: True  tiles computed: 36 of 64  largest score array: 16,384 vs 1,048,576 numbers
```

The outputs agree to 12 decimal places, and the largest score array that ever exists is 64 times smaller than the full matrix. The causal run shows a bonus. With the mask of Lesson 25.3, a tile whose keys all lie after its queries would be entirely $-\infty$, so it is never computed:

![An 8 by 8 grid of tiles. The 28 tiles below the diagonal are computed without a mask, the 8 diagonal tiles are masked inside, the 28 tiles above the diagonal are skipped. 36 of 64 are computed.](diagrams/25.4-causal-tiles.svg "Only the diagonal tiles need the mask at all.")

FlashAttention-2 does exactly this and reports a speed-up of about 1.7 to 1.8 times over attention without the mask (Dao, 2023).

## Counting the memory traffic

How much does tiling save? The model below is my own simplified count, not a measurement: it counts every number moved between HBM and SRAM in the forward pass. The standard version follows the first sketch; the tiled version follows the code above.

```python
def standard_io(N, d):
    # read Q, K; write S; read S; write P; read P, V; write O
    return 2*N*d + N*N + N*N + N*N + (N*N + N*d) + N*d

def tiled_io(N, d, Bq):
    q_blocks = N // Bq
    # read each Q block once; for each Q block read all of K and V; write each O block once
    return N*d + q_blocks * 2*N*d + N*d

d, Bq, Bk = 64, 128, 128
print(f"{'N':>6} {'standard':>15} {'tiled':>15} {'ratio':>6}   N x N matrix in float16")
for N in (1024, 4096, 16384, 65536):
    a, b = standard_io(N, d), tiled_io(N, d, Bq)
    print(f"{N:>6} {a:>15,} {b:>15,} {a / b:>6.2f}   {N * N * 2 / 2**20:>8,.0f} MiB")

work = Bq*d + 2*Bk*d + Bq*Bk + Bq*(2 + d)     # Q block; K and V blocks; score tile; m, l, acc
print(f"working set of one tile: {work:,} numbers = {work * 2 / 1024:.1f} KiB in float16")
```

```output
     N        standard           tiled  ratio   N x N matrix in float16
  1024       4,456,448       1,179,648   3.78          2 MiB
  4096      68,157,440      17,301,504   3.94         32 MiB
 16384   1,077,936,128     270,532,608   3.98        512 MiB
 65536  17,196,646,400   4,303,355,904   4.00      8,192 MiB
working set of one tile: 49,408 numbers = 96.5 KiB in float16
```

In symbols, the standard count is $4N^2 + 4Nd$ and the tiled count is $2Nd + 2N^2 d / B_q$, so for large $N$ the ratio approaches $2B_q/d$: bigger query blocks mean fewer re-reads of $K$ and $V$. The block size is limited by the SRAM size $M$, roughly $B_q \propto M/d$, which turns the tiled count into something proportional to $N^2 d^2 / M$. That is the bound Dao et al. (2022, Theorem 2) prove, against $N^2 + Nd$ for standard attention. The same paper proves the extra memory needed beyond inputs and output is proportional to $N$, not $N^2$ (Theorem 1).

The paper's own measurement, which includes the backward pass, shows a larger gap:

![Three pairs of bars for GPT-2 medium on an A100: 66.6 versus 75.2 GFLOPs, 40.3 versus 4.4 GB of HBM reads and writes, 41.7 versus 7.3 milliseconds.](diagrams/25.4-reported-numbers.svg "FlashAttention does more floating-point operations and still finishes sooner. Numbers reported by Dao et al. (2022), not measured here.")

## The backward pass: recompute instead of store

Training needs gradients, and the usual way to get them is to keep $P$ from the forward pass, which is $N^2$ numbers again. FlashAttention keeps only the output and the per-row softmax statistics, and **recomputes** each tile from $Q$, $K$ and $V$ during the backward pass (Dao et al., 2022). That is why the FLOP count goes up in the chart above. FlashAttention-2 stores a single number per row for this, $L = m + \log \ell$, the logarithm of the row's softmax denominator.

## What versions 2 and 3 changed

The algorithm you just built is version 1. The later versions keep the mathematics and change how the work is laid out on the GPU:

![Three columns. FlashAttention 2022: tiling, online softmax, recomputation in the backward pass; 25 to 40 percent of peak FLOPs per second. FlashAttention-2 2023: fewer non-matmul operations, parallel row blocks, work split between warps; about 2 times faster, 50 to 73 percent of peak. FlashAttention-3 2024: for Hopper GPUs, overlapping data movement and compute, interleaved matmul and softmax, optional FP8; 1.5 to 2.0 times speedup on H100.](diagrams/25.4-versions.svg "Reported figures are from the abstracts of the FlashAttention-2 and FlashAttention-3 papers (the 2022 percentage is quoted in the former); percentages are of the GPU's theoretical maximum FLOPs per second. Version 3 is measured on H100, versions 1 and 2 on A100.")

- **FlashAttention-2** (Dao, 2023). Version 1 looped over key blocks on the outside and ran one GPU *thread block* per attention head. Version 2 swaps the loops, as in the code above. Each query block then depends on no other, so many of them run in parallel even for a single head. It also normalises once at the end instead of after every tile (the `acc / l` line), which removes divisions, and divides the work inside a thread block among *warps* (small groups of threads that execute together).
- **FlashAttention-3** (Shah et al., 2024) targets NVIDIA's Hopper generation (the H100), on which version 2 reached only about 35% utilisation. It lets data loading and arithmetic run at the same time in specialised warps, interleaves block-wise matrix multiplication and softmax operations, and adds an optional 8-bit floating-point (FP8) mode. The FP8 mode is the only variant here that is not exact; the paper reports its error as 2.6 times lower than a baseline FP8 attention.

In practice you rarely call any of this yourself. PyTorch's `torch.nn.functional.scaled_dot_product_attention` lists FlashAttention-2 as one of three implementations it may select on the CUDA backend; on other backends it uses its plain C++ implementation.

<details><summary>Run locally: needs pip install torch</summary>

Run with torch 2.15.0 on a CPU, where PyTorch uses its plain implementation. The check is only that the tiled NumPy version computes the same function. The statement about FlashAttention-2 on CUDA is from the docstring shipped with this torch version; I did not run it on a GPU.

```python
import numpy as np, torch, torch.nn.functional as F

def flash_attention(Q, K, V, Bq=128, Bk=128):
    N, d = Q.shape
    O = np.empty((N, V.shape[1]))
    for i in range(0, N, Bq):
        Qi = Q[i:i + Bq]
        m = np.full((len(Qi), 1), -np.inf); l = np.zeros((len(Qi), 1)); acc = np.zeros((len(Qi), V.shape[1]))
        for j in range(0, N, Bk):
            S = Qi @ K[j:j + Bk].T / np.sqrt(d)
            m_new = np.maximum(m, S.max(axis=1, keepdims=True))
            shrink, P = np.exp(m - m_new), np.exp(S - m_new)
            l, acc, m = shrink * l + P.sum(axis=1, keepdims=True), shrink * acc + P @ V[j:j + Bk], m_new
        O[i:i + Bq] = acc / l
    return O

rng = np.random.default_rng(0)
Q, K, V = (rng.standard_normal((1024, 64)) for _ in range(3))
ref = F.scaled_dot_product_attention(*(torch.from_numpy(x) for x in (Q, K, V))).numpy()
print("torch", torch.__version__.split("+")[0])
print("matches F.scaled_dot_product_attention:", np.allclose(flash_attention(Q, K, V), ref, rtol=0, atol=1e-12))
```

## Common traps

> [!TRAP]
> **"FlashAttention is an approximation."** It is not. Versions 1 and 2, and version 3 in 16-bit mode, return the same output as ordinary attention up to rounding. Methods that drop or compress attention entries are a different family.

> [!TRAP]
> **Applying softmax inside each tile and adding the results.** Each tile would then be normalised by its own sum, not the row's sum, and the output is wrong. The row is only normalised correctly through the running $m$ and $\ell$.

> [!TRAP]
> **Rescaling $\ell$ but forgetting `acc`.** Both were measured against the old max, so both must be multiplied by `shrink`. The bug is silent whenever the first block happens to contain the row's largest score.

> [!TRAP]
> **"It makes attention linear."** The extra *memory* becomes proportional to $N$. The *time* is still proportional to $N^2$: every query still meets every key. Only the constant shrinks.

## Summary

- Standard attention moves $N \times N$ matrices between slow and fast GPU memory several times; that traffic, not the arithmetic, dominates its running time.
- FlashAttention computes the score matrix one tile at a time in fast on-chip memory and never stores it, so extra memory grows with $N$ instead of $N^2$.
- Online softmax makes this possible: keep a running max $m$, running sum $\ell$ and unnormalised output per row, rescale by $e^{m_{\text{old}} - m_{\text{new}}}$ when the max rises, divide once at the end.
- The result is exact. The backward pass recomputes tiles instead of storing weights, and a causal mask lets whole tiles be skipped.
- Versions 2 and 3 keep the algorithm and improve parallelism and hardware use.

## Quiz time

### Question 1: Online softmax by hand

One query has scaled scores $[1, 1, 2]$ against three keys whose values are the single numbers $4$, $8$ and $10$. Process the first two keys as block 1 and the third as block 2. Give $m$, $\ell$ and $\mathrm{acc}$ after each block, and the output.

<details><summary>Show solution</summary>

Block 1: $m = 1$, weights $[e^0, e^0] = [1, 1]$, so $\ell = 2$ and $\mathrm{acc} = 4 + 8 = 12$.

Block 2: the max rises to $m = 2$, so shrink by $e^{1-2} = 0.368$. The new weight is $e^0 = 1$. Then $\ell = 0.368 \cdot 2 + 1 = 1.736$ and $\mathrm{acc} = 0.368 \cdot 12 + 10 = 14.415$.

Output $= 14.415 / 1.736 = 8.304$. An ordinary softmax over $[1, 1, 2]$ gives weights $[0.212, 0.212, 0.576]$ and the same $8.304$.

</details>

### Question 2: Predict the tile count

You run `flash_attention` with `causal=True`, $N = 1{,}024$ and `Bq = Bk = 256`. How many tiles are computed, and how many are skipped?

<details><summary>Show solution</summary>

There are $1024 / 256 = 4$ blocks each way, so $16$ tiles. Row block 0 computes 1 tile, row block 1 computes 2, then 3, then 4: $1 + 2 + 3 + 4 = 10$ computed, $6$ skipped. Of the 10, the 4 on the diagonal need the mask applied inside them.

</details>

### Question 3: Spot the bug

A student's inner loop contains these lines. On the example from Question 1 it returns $12.675$. What is wrong, and how can you tell from the number alone that something is wrong?

```text
m_new = np.maximum(m, S.max(axis=1, keepdims=True))
shrink = np.exp(m - m_new)
P = np.exp(S - m_new)
l = shrink * l + P.sum(axis=1, keepdims=True)
acc = acc + P @ V[j:j + Bk]
m = m_new
```

<details><summary>Show solution</summary>

`acc` is not multiplied by `shrink`, so the contributions of earlier blocks stay measured against the old, smaller max and are too large. Here $\mathrm{acc} = 12 + 10 = 22$ while $\ell = 1.736$, giving $22 / 1.736 = 12.675$.

The tell: an attention output is a weighted average of the values, so it must lie between the smallest and largest value, $4$ and $10$. A result of $12.675$ is impossible. The fix is `acc = shrink * acc + P @ V[j:j + Bk]`.

</details>

### Question 4: More work, less time

In the paper's GPT-2 measurement, FlashAttention performs 75.2 GFLOPs against 66.6 for standard attention, yet takes 7.3 ms against 41.7 ms. Explain both halves.

<details><summary>Show solution</summary>

More FLOPs: the backward pass recomputes the score and weight tiles from $Q$, $K$ and $V$ instead of reading stored weights, so some arithmetic is done twice.

Less time: the running time is dominated by moving data between HBM and on-chip SRAM, and FlashAttention never writes or reads an $N \times N$ matrix there. The paper reports 4.4 GB of HBM reads and writes against 40.3 GB. Saving that traffic outweighs the extra arithmetic.

</details>
