A Mixture-of-Experts (MoE) layer stores many feed-forward networks but runs only a few of them for each token. In this lesson you will route one token through a top-2 gate by hand, measure how an unbalanced router overflows expert capacity, compute the auxiliary loss that discourages it, and count the cross-device traffic that expert parallelism creates.

**You need:** the feed-forward network (FFN) from Lesson 26.3, softmax (Lesson 25.1), and the idea that each accelerator chip has its own memory. No deep-learning framework is needed: every code block below is NumPy and runs in the browser.

## The problem MoE solves

In a dense Transformer block, one FFN runs on every token. Its size sets both the model's capacity (how many parameters it stores) and its cost (how many multiply-adds each token pays). MoE separates the two. The layer holds $E$ expert FFNs. A learned router sends each token to only $k$ of them, and the output is a weighted sum of those $k$ outputs. Parameters grow with $E$; compute per token grows with $k$.

Mixtral 8x7B is a public example. Each layer has 8 experts, and the router selects 2 of them for each token (Jiang et al., 2024). With $E = 8$ and $k = 2$, a token uses 25% of the expert weights. With $E = 64$ and the same $k$, it uses about 3.1%.

![One MoE layer: a router sends the token to two of eight experts, and their outputs are combined with the gate weights](diagrams/26.4-moe-layer.svg "One MoE layer. Only the two highlighted experts run for this token.")

## Worked example by hand

Take one token $x = [1, 2]$ and four experts. The gate has one row $g_i$ per expert, and the gate score is $s_i = g_i \cdot x$:

$$
g_0 = [1, 0], \quad g_1 = [0.5, 1], \quad g_2 = [0.3, 0], \quad g_3 = [0, 1]
\quad\Rightarrow\quad s = [1.0,\ 2.5,\ 0.3,\ 2.0]
$$

1. **Top-2.** The two largest scores are $s_1 = 2.5$ and $s_3 = 2.0$.
2. **Softmax over all four.** $p_i = e^{s_i} / \sum_j e^{s_j}$ gives $p_1 \approx 0.515$ and $p_3 \approx 0.313$. The two selected experts hold only $0.828$ of the probability.
3. **Renormalise over the two.** $w_i = p_i / (p_1 + p_3)$ gives $w_1 \approx 0.6225$ and $w_3 \approx 0.3775$. Dividing by $p_1 + p_3$ is the same as a softmax over the two selected scores alone. The common denominator cancels, so $w_1 = e^{2.5} / (e^{2.5} + e^{2.0}) = 1 / (1 + e^{-0.5})$. This is reasoning from first principles.
4. **Run only experts 1 and 3.** Expert $i$ is a matrix $W_i$ here. $W_1 x = [2, 2]$ and $W_3 x = [3, 2]$, so $y = 0.6225\,[2, 2] + 0.3775\,[3, 2] = [2.378,\ 2.000]$.

![Worked top-2 example: gate scores 1.0, 2.5, 0.3 and 2.0; top-2 weights 0.622 and 0.378; output [2.378, 2.000]](diagrams/26.4-worked-top2.svg "Scores, top-2 softmax and weighted sum for the worked token.")

```python
import numpy as np

def softmax(z):
    z = z - z.max()                          # subtract the max for numerical stability
    e = np.exp(z)
    return e / e.sum()

x = np.array([1.0, 2.0])                     # one token, d = 2
G = np.array([[1.0, 0.0],                    # gate: one row per expert (4 experts)
              [0.5, 1.0],
              [0.3, 0.0],
              [0.0, 1.0]])
W = np.array([[[1, 0], [0, 1]],              # expert 0: a 2x2 linear map
              [[2, 0], [0, 1]],              # expert 1
              [[0, 1], [1, 0]],              # expert 2
              [[1, 1], [0, 1]]], dtype=float)  # expert 3

logits = G @ x                               # gate score for each expert
top2 = np.argsort(-logits)[:2]               # ids of the two largest scores
mass = softmax(logits)[top2].sum()           # probability mass the top-2 experts hold
w = softmax(logits[top2])                    # weights over the two selected experts only
y = sum(wj * (W[e] @ x) for wj, e in zip(w, top2))   # run only the selected experts

print("logits  :", logits)
print("top-2   :", top2)
print(f"mass top-2 before renormalising: {mass:.4f}")
print("weights :", np.round(w, 4), f"sum = {w.sum():.1f}")
print("output  :", np.round(y, 4))
```

```output
logits  : [1.  2.5 0.3 2. ]
top-2   : [1 3]
mass top-2 before renormalising: 0.8279
weights : [0.6225 0.3775] sum = 1.0
output  : [2.3775 2.    ]
```

The code computes only the two selected experts. A production layer groups tokens by expert and runs each expert once on its batch, but the arithmetic per token is identical.

## Routing at scale: loads and capacity

The worked example has one token, so it cannot show imbalance. Next we route $T = 4096$ random tokens with $d = 16$ input features through $E = 8$ experts, with $k = 2$. A balanced gate gives each expert $Tk/E = 1024$ assignments on average. The skewed gate adds a fixed bias that favours low-numbered experts. This is a toy stand-in for the imbalance that real training produces. The numbers describe this toy, not any real model.

Each expert has a capacity $C = \lceil c\,kT/E \rceil$, where $c$ is the capacity factor. Assignments beyond $C$ are dropped. That expert's contribution for that token is lost, and the token continues only through the residual connection. GShard describes this overflow behaviour in Section 2.2 (Lepikhin et al., 2020). A larger $c$ reduces drops but wastes memory and compute on empty slots, so $c$ is a trade-off. This last point is reasoning from first principles.

![Bar chart of expert loads under a skewed router: expert 0 receives 2157 assignments against a capacity of 1024](diagrams/26.4-skew-loads.svg "Expert loads, skewed router, capacity factor 1.0. Rose marks the dropped part.")

![Grouped bars: dropped share of assignments for balanced and skewed routers at four capacity factors](diagrams/26.4-drop-vs-capacity.svg "Dropped share against capacity factor, measured on the toy routers.")

```python
import math
import numpy as np

rng = np.random.default_rng(26)
T, d, E, k = 4096, 16, 8, 2                  # tokens, input dim, experts, experts per token
X = rng.standard_normal((T, d))
Wg = rng.standard_normal((d, E)) / np.sqrt(d)   # gate weights
skew = np.array([0.8, 0.5, 0.3, 0.1, -0.1, -0.3, -0.5, -0.8])  # toy bias towards low ids

def top_k_route(bias):
    logits = X @ Wg + bias
    return np.argsort(-logits, axis=1)[:, :k]   # (T, k) expert ids per token

def dispatch(idx, cap):
    """Each expert accepts its first `cap` assignments in token order; the rest are dropped."""
    counts = np.zeros(E, dtype=int)
    kept = np.zeros(idx.shape, dtype=bool)
    for t in range(idx.shape[0]):
        for j in range(k):
            e = idx[t, j]
            if counts[e] < cap:
                counts[e] += 1
                kept[t, j] = True
    return kept

for name, bias in [("balanced", np.zeros(E)), ("skewed", skew)]:
    idx = top_k_route(bias)
    loads = np.bincount(idx.ravel(), minlength=E)
    print(name, "loads:", loads, f" max/mean = {loads.max() / loads.mean():.3f}")
    for cf in [1.0, 1.25, 1.5, 2.0]:
        cap = math.ceil(cf * k * T / E)          # expert capacity
        dropped = int((~dispatch(idx, cap)).sum())
        print(f"  cf={cf:<4} cap={cap:<5} dropped={dropped:<5} ({dropped / (T * k):.4f})")
```

```output
balanced loads: [ 847 1041  988 1012  986 1170 1190  958]  max/mean = 1.162
  cf=1.0  cap=1024  dropped=329   (0.0402)
  cf=1.25 cap=1280  dropped=0     (0.0000)
  cf=1.5  cap=1536  dropped=0     (0.0000)
  cf=2.0  cap=2048  dropped=0     (0.0000)
skewed loads: [2157 1591 1202  990  726  710  625  191]  max/mean = 2.106
  cf=1.0  cap=1024  dropped=1878  (0.2292)
  cf=1.25 cap=1280  dropped=1188  (0.1450)
  cf=1.5  cap=1536  dropped=676   (0.0825)
  cf=2.0  cap=2048  dropped=109   (0.0133)
```

Read the skewed rows. At $c = 1.0$ the capacity is 1024, and expert 0 receives 2157 assignments. Of the $8192 = Tk$ assignments, 1878 (22.9%) are dropped. With this first-come, first-served rule, the dropped count is $\sum_e \max(0, \text{load}_e - C)$: $(2157 - 1024) + (1591 - 1024) + (1202 - 1024) = 1878$. The balanced router drops 4.0% at $c = 1.0$ and nothing at $c = 1.25$.

## Balancing the router: the auxiliary loss

Switch Transformers (Fedus et al., 2021) adds this term to the training loss:

$$
L_{\text{aux}} = \alpha\, N \sum_{i=1}^{N} f_i P_i, \qquad \alpha = 10^{-2}
$$

Here $N$ is the number of experts, $f_i$ is the fraction of tokens dispatched to expert $i$ (Switch uses each token's top-1 choice), and $P_i$ is the mean router probability for expert $i$ over the batch.

$f_i$ is a count, so it has no gradient. $P_i$ is a smooth function of the gate, so the gradient pushes probability away from overloaded experts. This is reasoning from first principles. If routing is uniform, $f_i = P_i = 1/N$ and the loss equals $\alpha$ exactly. If every token goes to one expert with probability 1, the loss reaches $N\alpha$. The code below computes the loss for both routers and also counts cross-device pairs, which the next section needs.

![Four devices each holding two experts; a token on device 0 sends its state to experts on devices 1 and 2](diagrams/26.4-expert-parallel.svg "Expert parallelism. The arrows are the all-to-all traffic for one token.")

```python
import numpy as np

rng = np.random.default_rng(26)
T, d, E, k, D = 4096, 16, 8, 2, 4            # tokens, dim, experts, top-k, devices
X = rng.standard_normal((T, d))
Wg = rng.standard_normal((d, E)) / np.sqrt(d)
skew = np.array([0.8, 0.5, 0.3, 0.1, -0.1, -0.3, -0.5, -0.8])

def softmax(z):
    z = z - z.max(axis=1, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=1, keepdims=True)

alpha = 0.01
token_dev = np.arange(T) // (T // D)         # tokens are sharded across the devices
dev_of_expert = np.arange(E) // (E // D)     # experts 0-1 on device 0, 2-3 on device 1, ...
for name, bias in [("balanced", np.zeros(E)), ("skewed", skew)]:
    logits = X @ Wg + bias
    p = softmax(logits)
    f = np.bincount(p.argmax(axis=1), minlength=E) / T   # share of tokens whose top-1 is expert i
    P = p.mean(axis=0)                                  # mean router probability of expert i
    aux = alpha * E * np.sum(f * P)                     # Switch-style load-balancing loss
    print(f"{name}: aux loss = {aux:.5f} = {aux / alpha:.3f} x alpha")

    idx = np.argsort(-logits, axis=1)[:, :k]
    dest = dev_of_expert[idx]                           # device that computes each assignment
    cross = dest != token_dev[:, None]
    print(f"  cross-device pairs: {cross.mean():.4f}   per-device assignments: {np.bincount(dest.ravel(), minlength=D)}")
    mb = cross.sum() * 4096 * 2 / 1e6                   # d_model = 4096, bf16 = 2 bytes (assumed)
    print(f"  one-way traffic for this layer: {mb:.1f} MB")
```

```output
balanced: aux loss = 0.01014 = 1.014 x alpha
  cross-device pairs: 0.7551   per-device assignments: [1888 2000 2156 2148]
  one-way traffic for this layer: 50.7 MB
skewed: aux loss = 0.01245 = 1.245 x alpha
  cross-device pairs: 0.7446   per-device assignments: [3748 2192 1436  816]
  one-way traffic for this layer: 50.0 MB
```

The loss values are close to $\alpha$ in both cases. Because $\alpha$ is small, compare the ratio to $\alpha$ rather than the absolute value. A batch-averaged loss can look acceptable while a single batch still overflows, so check the loads and the dropped share as well.

## Expert parallelism: where the tokens go

With expert parallelism, each device holds a slice of the experts and a slice of the tokens. A token whose experts live on other devices sends its hidden state to them in an all-to-all exchange, in which every device sends a piece of its data to every other device. The results return in a second exchange. This is reasoning from the standard data-flow pattern; the figure shows one token.

With 4 devices, an expert is on the token's own device with probability 1/4 if the router ignores the token's position and the experts are spread evenly over the devices. So about 3/4 of the token-expert pairs must cross the network. The balanced router gives 75.5%, close to that expectation. The skewed router gives 74.5%, but it concentrates work: device 0 computes 3748 assignments, 1.83 times the mean. A synchronous step waits for the busiest device, so imbalance costs time even when the total traffic is unchanged.

The traffic figure is my own arithmetic under stated assumptions: 6186 cross-device pairs, each carrying a 4096-value vector in bf16 (a 16-bit floating-point format), gives 50.7 MB one way for one layer and 4096 tokens. Returning the outputs roughly doubles it.

## Common traps

> [!TRAP]
> The top-2 weights sum to 1 only after renormalising. In the worked example the two experts hold 0.828 of the probability before renormalising. Using the raw probabilities shrinks the output by about 17%.

> [!TRAP]
> MoE does not make compute free. With $k = 2$, each token runs two expert FFNs, which is twice the cost of one dense FFN of the same size. The saving is that the model holds more parameters than a dense model with the same per-token cost.

> [!TRAP]
> Overflow is silent. The layer still returns a tensor of the right shape. Log the dropped share and the max/mean load. The skewed router dropped 22.9% of assignments at $c = 1.0$ and had a max/mean load of 2.11, and nothing in the output shape shows it.

> [!TRAP]
> A small auxiliary loss does not prove balance. With $\alpha = 0.01$ the skewed loss is only 1.245 times $\alpha$, so the number barely moves. Judge balance from loads and drops.

> [!TRAP]
> Top-2 overflow has an edge case. The GShard text (Section 2.2) says a token overflows when both its experts are full, but its Algorithm 1 checks capacity per expert. I read both in the arXiv version I fetched. Check the released code before relying on the edge case.

## Summary

- MoE separates parameters from compute: $E$ experts are stored, and each token runs $k$ of them, a fraction $k/E$ of the expert weights.
- Softmax over the two selected scores equals the renormalised full softmax, so top-2 weights sum to 1.
- Capacity $C = \lceil c\,kT/E \rceil$ limits each expert. Overflow is dropped, and the dropped share falls as $c$ rises, at a memory cost.
- Switch's loss $\alpha N \sum_i f_i P_i$ equals $\alpha$ under uniform routing and $N\alpha$ when one expert takes everything.
- With 4 devices and a router that ignores token position, about 3/4 of token-expert pairs cross devices, and the busiest device sets the step time.

## Quiz time

### Question 1: Calculation

In the worked example, $p_3 \approx 0.313$. Why is the weight $w_3 \approx 0.3775$ rather than 0.313?

<details><summary>Show Solution</summary>

The weight is renormalised over the two selected experts: $w_3 = p_3 / (p_1 + p_3) = 0.313 / 0.828 \approx 0.378$. The raw probability includes the mass on experts 0 and 2, which the top-2 router does not use.

</details>

### Question 2: Prediction

A layer has $T = 8192$ tokens, $E = 16$ experts, $k = 2$ and capacity factor $c = 1.5$. What is the per-expert capacity $C$, and how many token-expert assignments are there in total?

<details><summary>Show Solution</summary>

$C = \lceil 1.5 \times 2 \times 8192 / 16 \rceil = \lceil 1536 \rceil = 1536$. The total is $Tk = 16384$ assignments.

</details>

### Question 3: Bug-spotting

```python
import numpy as np

logits = np.array([1.0, 2.5, 0.3, 2.0])
top2 = np.argsort(-logits)[:2]
p = np.exp(logits) / np.exp(logits).sum()
w = p[top2]                       # weights for the two selected experts
print(w.sum())
```

What does this print, and what is the bug?

<details><summary>Show Solution</summary>

It prints about 0.828, not 1. The code uses the raw probabilities and never renormalises over the selected experts. The fix is `w = w / w.sum()`. Without it, the layer's output is about 17% too small for this token.

</details>

### Question 4: Explanation

Why does the Switch loss multiply $f_i$ by $P_i$ instead of penalising $f_i$ alone?

<details><summary>Show Solution</summary>

$f_i$ alone is a count from an argmax, so it has no gradient and cannot be trained directly. $P_i$ is differentiable. The product makes the loss large only when an expert both receives many tokens and has high router probability, and the gradient flows through $P_i$. This is reasoning from first principles; the exact formulation is Switch's Equations 4 to 6.

</details>
