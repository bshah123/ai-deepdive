By the end of this lesson you will be able to compute the size of the key-value (KV) cache for any decoder configuration, and to bound a model's decoding speed from memory bandwidth alone. Serving a large language model is usually limited by memory traffic, not arithmetic, and this lesson shows why.

**You need:** the attention formula (Lesson 25.1) and the generation loop with its KV cache (Lesson 27.2). Binary units: 1 KiB = 1,024 bytes, 1 GiB = $2^{30}$ bytes.

## The problem the cache solves

A decoder produces one token per forward pass. To produce token $t$, every layer attends to the keys and values of all $t-1$ earlier tokens. Without storage, each step would recompute those keys and values from scratch, so the projection work for a sequence of length $T$ grows quadratically. The KV cache stores each token's keys and values once. Each new step computes only the new token's keys and values, appends them, and reads the whole stored history.

The cache trades compute for memory. The history grows with every token and every sequence in the batch, and every decode step must read it. Shazeer (2019) names the cost directly: incremental decoding is slow because of "the memory-bandwidth cost of repeatedly loading the large keys and values tensors."

## What the cache stores

![Four factors multiply to give 512 KiB per token for a 7B-class configuration: 2 for K and V, 32 layers, 32 KV heads, head dimension 128, and 2 bytes per fp16 value](diagrams/29.1-per-token-factors.svg "Per-token cache size is a product of factors. The numbers are an illustrative configuration.")

The cache size is

$$
M_{\text{KV}} = 2 \cdot L \cdot H_{\text{kv}} \cdot d \cdot T \cdot B \cdot b \qquad \text{bytes}
$$

- $2$: one tensor for keys and one for values.
- $L$: decoder layers. Each layer keeps its own cache.
- $H_{\text{kv}}$: key-value heads. In standard multi-head attention (MHA) this equals the number of query heads $H$. Grouped-query attention (GQA) uses fewer KV heads, each shared by a group of query heads (Ainslie et al., 2023).
- $d$: head dimension. $T$: tokens in context. $B$: sequences in the batch.
- $b$: bytes per stored value. 2 for fp16 or bf16, 4 for fp32, 1 for int8.

A head is a separate set of projection matrices in the attention formula of Lesson 25.1. Each head produces its own key and its own value for every token. A layer with 32 KV heads therefore stores 32 keys and 32 values per token, and the model has $L$ such layers.

Dimension check: every factor except $b$ is a count, and $b$ is bytes per value, so the product is bytes.

## Worked example by hand

Take a toy model with $L=2$, $H=2$, $d=4$, $T=3$, stored in fp16. One token stores $2 \times 2 \times 2 \times 4 = 32$ values, which is $32 \times 2 = 64$ bytes. Three tokens store $3 \times 64 = 192$ bytes, or 96 values.

![Three token boxes of 64 bytes each add up to 192 bytes for the toy model](diagrams/29.1-toy-example.svg "The toy model. Each token costs the same, so the total is linear in T.")

The code reproduces these numbers and the realistic ones in the next section.

```python
def kv_cache_bytes(n_layers, n_kv_heads, head_dim, n_tokens, batch, bytes_per_value):
    """Bytes for K and V over all layers, KV heads, tokens and sequences."""
    return 2 * n_layers * n_kv_heads * head_dim * n_tokens * batch * bytes_per_value

# Toy model from the worked example: L=2, H=2, d=4, T=3, fp16
toy = kv_cache_bytes(2, 2, 4, 3, 1, 2)
print("toy bytes:", toy, "per token:", toy // 3)

# Illustrative 7B-class configuration: 32 layers, 32 KV heads, d=128, fp16
mha = kv_cache_bytes(32, 32, 128, 1, 1, 2)
print("MHA bytes per token:", mha, "=", mha / 1024, "KiB")
print("MHA per 4096-token sequence:", kv_cache_bytes(32, 32, 128, 4096, 1, 2) / 2**30, "GiB")
print("GQA (8 KV heads) per sequence:", kv_cache_bytes(32, 8, 128, 4096, 1, 2) / 2**30, "GiB")
```

```output
toy bytes: 192 per token: 64
MHA bytes per token: 524288 = 512.0 KiB
MHA per 4096-token sequence: 2.0 GiB
GQA (8 KV heads) per sequence: 0.5 GiB
```

## A realistic configuration

I could not retrieve the architecture of a specific released model in this session, so the 7B-class configuration above is illustrative. Its arithmetic is what matters. Each token costs 512 KiB, and a 4,096-token sequence needs 2 GiB. Using 8 KV heads instead of 32 cuts that fourfold, to 0.5 GiB. Pope et al. (2022) make the same point at scale: the lower memory of multi-query attention allows contexts up to 32 times longer in their setting.

![Per-sequence cache in GiB against context length from 512 to 32,768 tokens: MHA reaches 16 GiB, 8 KV heads reach 4 GiB, and a dashed line marks 12.5 GiB of fp16 weights](diagrams/29.1-growth-chart.svg "The cache grows linearly in T. The weights are a fixed cost, shown for scale.")

Batch size counts as much as length. The weights of a 6.7-billion-parameter model take 12.5 GiB in fp16. At batch 32 and 4,096 tokens, the cache alone needs 64 GiB, so the total is 76.5 GiB. An 80 GB card provides only 74.5 GiB in binary units, before activations or framework overhead. The batch does not fit.

The next block is a small cache of the same layout. It shows the bytes the formula predicts, and a trap in how the cache is grown.

```python
import numpy as np

class KVCache:
    """One sequence's cache, allocated once: K and V are (layers, kv_heads, max_tokens, head_dim)."""
    def __init__(self, n_layers, n_kv_heads, max_tokens, head_dim, dtype=np.float16):
        shape = (n_layers, n_kv_heads, max_tokens, head_dim)
        self.k = np.zeros(shape, dtype=dtype)
        self.v = np.zeros(shape, dtype=dtype)
        self.length = 0

    def append(self, layer, k_new, v_new):
        # k_new, v_new: (kv_heads, head_dim) for one token in one layer
        self.k[layer, :, self.length] = k_new
        self.v[layer, :, self.length] = v_new
        if layer == self.k.shape[0] - 1:          # the last layer completes the token
            self.length += 1

L, H, d, T = 4, 4, 8, 10
cache = KVCache(L, H, 16, d)
rng = np.random.default_rng(0)
for t in range(T):
    for layer in range(L):
        cache.append(layer, rng.standard_normal((H, d)), rng.standard_normal((H, d)))

b = cache.k.itemsize                                     # 2 bytes for fp16
print("tokens stored:", cache.length)
print("bytes used (2*L*H*d*T*b):", 2 * L * H * d * cache.length * b)
print("bytes allocated:", cache.k.nbytes + cache.v.nbytes)

# The trap: growing the history with concatenate copies everything at every step.
per_token = 2 * L * H * d * b
buf, copied = np.zeros(0, dtype=np.uint8), 0
for t in range(T):
    copied += buf.nbytes
    buf = np.concatenate([buf, np.zeros(per_token, dtype=np.uint8)])
print("naive bytes copied:", copied)
print("preallocated bytes written:", per_token * T)
```

```output
tokens stored: 10
bytes used (2*L*H*d*T*b): 5120
bytes allocated: 8192
naive bytes copied: 23040
preallocated bytes written: 5120
```

The preallocated cache writes each token's bytes once. The concatenating version copies the whole history at every step, so its copy traffic grows with $T^2$.

## The memory-bandwidth bound

Each decode step must read every weight once and every sequence's cache once. If memory bandwidth is $BW$ bytes per second, a step cannot finish faster than

$$
t_{\text{step}} \ge \frac{2P + B \cdot M_{\text{seq}}}{BW}
$$

where $P$ is the parameter count, so $2P$ is the fp16 weight traffic, and $M_{\text{seq}}$ is the cache of one sequence. For hardware I use the NVIDIA A100 80GB SXM figures: 2,039 GB/s memory bandwidth and 312 TFLOP/s dense fp16 tensor-core throughput (NVIDIA A100 product page).

Is the step limited by memory or by compute? Compare each operation's arithmetic intensity, meaning floating-point operations (FLOPs) per byte read, with the hardware ratio $312\ \text{TFLOP/s} \div 2{,}039\ \text{GB/s} \approx 153$ FLOP/byte. This comparison is my own reasoning from two spec numbers, not a cited result.

- **Weights.** Each weight byte serves one multiply-add (2 FLOPs) per sequence in the batch. At fp16 the intensity is about $B$ FLOP/byte, so the weights stop being bandwidth-bound only near batch 153.
- **Cache.** Per layer, the scores $QK^\top$ and the mix $AV$ cost $4 H d T$ FLOPs, while reading K and V costs $2 H_{\text{kv}} d T b$ bytes. The intensity is $(2/b)(H/H_{\text{kv}})$. For fp16 MHA this is 1 FLOP/byte. For 32 query heads sharing 8 KV heads it is 4. Both are far below 153, so cache reads stay bandwidth-bound at any batch size.

Batch therefore amortises the weight reads but not the cache reads. The table below uses the 7B-class MHA configuration at 4,096 tokens.

![Stacked bars for batch 1, 8 and 32: weights are a fixed 13.4 GB, the cache grows with the batch, reaching 82.1 GB at batch 32, and the note gives a ceiling of 949 tokens per second](diagrams/29.1-bytes-per-step.svg "Bytes read per decode step. Throughput is the batch divided by the step time.")

```python
BW = 2.039e12            # A100 80GB SXM memory bandwidth, bytes/s (NVIDIA)
FLOPS = 312e12           # A100 fp16 tensor-core peak, FLOP/s (dense)
P = 6.7e9                # parameters, illustrative 7B-class model
weights = 2 * P          # fp16 weight bytes read per step
kv_seq = 2 * 32 * 32 * 128 * 4096 * 2   # one 4,096-token MHA sequence, bytes

print("ridge point (FLOP/byte):", round(FLOPS / BW))
for B in (1, 8, 32):
    step = weights + B * kv_seq          # weights once, cache once per sequence
    t = step / BW
    print(f"batch {B:2d}: {step/1e9:5.1f} GB per step, {t*1e3:5.1f} ms, {B/t:4.0f} tokens/s")
print("ceiling, MHA:", round(BW / kv_seq), "tokens/s")
print("ceiling, 8 KV heads:", round(BW / (kv_seq / 4)), "tokens/s")
```

```output
ridge point (FLOP/byte): 153
batch  1:  15.5 GB per step,   7.6 ms,  131 tokens/s
batch  8:  30.6 GB per step,  15.0 ms,  533 tokens/s
batch 32:  82.1 GB per step,  40.3 ms,  795 tokens/s
ceiling, MHA: 949 tokens/s
ceiling, 8 KV heads: 3798 tokens/s
```

As the batch grows, throughput approaches $BW / M_{\text{seq}}$, which is 949 tokens per second here, and no batch size exceeds it. Fewer KV heads raise this ceiling in proportion: 3,798 tokens per second with 8 KV heads.

These numbers are upper bounds. They assume every byte is read at full bandwidth, no cache is reused across sequences, and compute time is negligible. Real kernels achieve less. Lesson 29.2 covers how the cache is laid out in memory, which determines how much of the bandwidth is usable.

## Common traps

> [!TRAP] **Forgetting the factor of 2.**
> The cache holds keys and values. Leaving out the 2 undercounts memory by half.

> [!TRAP] **Counting query heads instead of KV heads.**
> With GQA or multi-query attention, $H_{\text{kv}} < H$. Using $H$ overstates the cache by $H/H_{\text{kv}}$, which is 4 for 32 query heads and 8 KV heads.

> [!TRAP] **Mixing GB and GiB.**
> Hardware is sold in decimal GB ($10^9$ bytes). The formulas here use GiB ($2^{30}$ bytes). An 80 GB card is 74.5 GiB, a 7 % difference that decides whether a batch fits.

> [!TRAP] **Growing the cache with `np.concatenate`.**
> Each append copies the whole history. For 4,096 tokens of the 7B-class model, the naive loop copies about 4.0 TiB in total, while a preallocated cache writes 2 GiB.

> [!TRAP] **Reading the bandwidth ceiling as a prediction.**
> The ceiling is a bound on what is physically possible. Measured throughput is lower, and the gap depends on the kernel, the batch and the memory layout.

## Summary

- Cache bytes = $2 \cdot L \cdot H_{\text{kv}} \cdot d \cdot T \cdot B \cdot b$. Every factor is a count except the bytes per value.
- The 7B-class MHA example costs 512 KiB per token and 2 GiB per 4,096-token sequence. Eight KV heads cut this fourfold.
- A decode step reads all weights and every sequence's cache, so its time is at least bytes divided by bandwidth.
- Batch amortises the weight reads, not the cache reads. The cache ceiling is $BW / M_{\text{seq}}$ tokens per second.
- Attention reads have an arithmetic intensity of 1 to 4 FLOP/byte, far below the roughly 153 FLOP/byte ratio of an A100.

## Quiz time

### Question 1: Calculation

A model has $L = 48$ layers, $H_{\text{kv}} = 8$ KV heads, $d = 128$, and stores fp16 values. It serves a batch of 4 sequences of 8,192 tokens each. How many GiB does the KV cache occupy?

<details>
<summary>Solution</summary>

Per token and sequence: $2 \cdot 48 \cdot 8 \cdot 128 \cdot 2 = 196{,}608$ bytes. Per sequence: $196{,}608 \times 8{,}192 = 1.5 \times 2^{30}$ bytes, which is 1.5 GiB. Four sequences: 6 GiB.

</details>

### Question 2: Prediction

In the bandwidth-bound regime, a 7B-class MHA model at 4,096 tokens has a ceiling of 949 tokens per second. You raise the batch from 16 to 32. Does the ceiling change? What happens to the achieved throughput?

<details>
<summary>Solution</summary>

The ceiling does not change. It is $BW / M_{\text{seq}}$, which does not depend on $B$. Achieved throughput rises toward 949 tokens per second, because the fixed weight reads are spread over more sequences. It never exceeds the ceiling.

</details>

### Question 3: Bug-spotting

A decoder appends each new key with `k_cache = np.concatenate([k_cache, k_new], axis=1)` at every step. What is the problem, and how would you fix it?

<details>
<summary>Solution</summary>

Each step copies the entire existing cache, so the total copy traffic over $T$ steps grows as $T^2$. Preallocate a buffer of shape (layers, KV heads, max tokens, head dimension) and write each token at the current position, as the `KVCache` class above does.

</details>

### Question 4: Explanation

Grouped-query attention cuts the cache by $H/H_{\text{kv}}$. Why does it barely change the weight term $2P$?

<details>
<summary>Solution</summary>

Only the key and value projection matrices shrink, because they now produce $H_{\text{kv}}$ heads instead of $H$. The query, output and feed-forward weights, which make up most of $P$, are unchanged, so the weight term changes only slightly.

</details>
