In this lesson you will build a block-based (paged) key-value (KV) cache in NumPy (Python's numerical array library), check that it returns exactly the same attention output as a contiguous cache, and measure how many requests fit into a fixed memory budget under each layout. You will also see how parallel sampling shares prompt pages. This is the idea behind vLLM, the large language model (LLM) serving system that introduced PagedAttention.

**You need:** the KV cache idea and its memory cost (Lesson 29.1) and scaled dot-product attention (Lesson 25.1).

## The problem: memory for a sequence whose length is unknown

During generation, each request keeps one key vector and one value vector per token, per layer and per head. These are the KV cache. A serving system must reserve graphics processing unit (GPU) memory for this cache before it knows how long the answer will be.

The simplest design reserves one contiguous block sized for the longest allowed sequence. A request that ends up using 300 of 2,048 reserved slots leaves 1,748 slots empty for its whole lifetime, and no other request can use them. Kwon et al. (2023) profiled existing serving systems and found that only 20.4% to 38.2% of KV cache memory held actual token states. The rest was reserved in advance, lost to internal fragmentation (slots over-provisioned inside a request's slab) or lost to external fragmentation (gaps between slabs). In the paper's Fig. 1, the dynamic request state is close to 30% of the memory of a 13B-parameter model on a 40 GB A100 GPU, and this waste limits how many requests can share one batch.

![A 300-token request in one 2,048-slot slab, with 1,748 slots reserved and empty, versus 19 pages of 16 slots where only 4 slots are empty](diagrams/29.2-reserve-vs-pages.svg "Same request, two layouts. The slab wastes most of its memory; the pages waste 4 slots.")

## The idea: pages and a block table

Operating systems (OS) solved the same problem for programs. A program sees one contiguous range of virtual addresses, while the physical memory behind it is scattered in fixed-size pages, and a page table maps one to the other. PagedAttention (Kwon et al., 2023) does this for the KV cache. The cache is a pool of fixed-size **blocks** (we call them pages), each holding $B$ token slots. Here $B$ is the page size, not the batch size $B$ of Lesson 29.1. Each sequence has a **block table** that lists the physical pages holding its tokens, in logical order. A new page is taken from a free list only when the current one is full.

For token position $t$, the logical page is $\lfloor t / B \rfloor$ and the slot inside it is $t \bmod B$. Here is the calculation by hand for $B = 4$ and a 10-token sequence whose block table is $[0, 2, 4]$:

- Pages 0, 1 and 2 hold tokens 0–3, 4–7 and 8–9. Page 2 is half empty.
- Token 9 is in logical page $\lfloor 9/4 \rfloor = 2$, slot $9 \bmod 4 = 1$.
- The block table maps logical page 2 to physical page 4, so token 9 is at physical page 4, slot 1.

![Two sequences, A and B, with logical pages placed above the physical pages they map to; A uses blocks 0, 2 and 4, B uses 1 and 3, and blocks 5 to 7 are free](diagrams/29.2-block-table.svg "Logical pages of two requests are interleaved in one pool because pages are taken as they are needed.")

## Code: a paged cache, checked against the contiguous answer

The code below implements the cache for one attention head. It stores keys and values in a pool of pages, keeps a block table per sequence, and gathers the used slots back in order before attending. It also implements fork (sharing) with copy-on-write, which is the mechanism behind shared prompts. Copy-on-write (CoW) means a shared page is copied before anyone writes to it. The last part compares the paged result with a contiguous reference and with a version that does not mask unused slots.

```python
import math
import numpy as np

class PagedKVCache:
    """One attention head's KV cache, stored as fixed-size pages (blocks) of B token slots."""

    def __init__(self, num_blocks, block_size, dim):
        self.B, self.D = block_size, dim
        self.k = np.zeros((num_blocks, block_size, dim))   # physical key pool
        self.v = np.zeros((num_blocks, block_size, dim))   # physical value pool
        self.free = list(range(num_blocks))[::-1]          # pop() hands out 0, 1, 2, ...
        self.ref = [0] * num_blocks                        # how many sequences map each block
        self.table = {}                                    # seq id -> block table (logical -> physical)
        self.length = {}                                   # seq id -> tokens stored

    def _take(self):
        if not self.free:
            raise MemoryError("no free blocks")
        b = self.free.pop()
        self.ref[b] = 1
        return b

    def _release(self, b):
        self.ref[b] -= 1
        if self.ref[b] == 0:
            self.free.append(b)

    def new_seq(self, sid):
        self.table[sid], self.length[sid] = [], 0

    def append(self, sid, k_vec, v_vec):
        t, blocks = self.length[sid], self.table[sid]
        if t % self.B == 0:                       # no page yet, or the last one is full
            blocks.append(self._take())
        elif self.ref[blocks[-1]] > 1:            # shared partial page: copy before writing
            new = self._take()
            self.k[new], self.v[new] = self.k[blocks[-1]], self.v[blocks[-1]]
            self._release(blocks[-1])
            blocks[-1] = new
        b, slot = blocks[-1], t % self.B
        self.k[b, slot], self.v[b, slot] = k_vec, v_vec
        self.length[sid] = t + 1

    def fork(self, parent, child):
        """Child shares every page of the parent: no data is copied."""
        self.table[child] = list(self.table[parent])
        self.length[child] = self.length[parent]
        for b in self.table[child]:
            self.ref[b] += 1

    def free_seq(self, sid):
        for b in self.table.pop(sid):
            self._release(b)
        del self.length[sid]

    def gather(self, sid):
        """Walk the block table; return keys and values in logical token order."""
        blocks, n = self.table[sid], self.length[sid]
        K = self.k[blocks].reshape(-1, self.D)[:n]
        V = self.v[blocks].reshape(-1, self.D)[:n]
        return K, V


def attend(q, K, V):
    """Scaled dot-product attention for one query over the given keys and values."""
    s = K @ q / math.sqrt(q.shape[0])
    w = np.exp(s - s.max())
    return (w / w.sum()) @ V


def kv(seq, pos, D=4):
    """Deterministic fake key and value for token `pos` of sequence `seq`."""
    base = np.arange(1, D + 1)
    return np.cos(0.1 * (pos + 1) * base + seq), np.sin(0.3 * (pos + 1) * base - seq)


D, B = 4, 4
cache = PagedKVCache(num_blocks=8, block_size=B, dim=D)
cache.new_seq("A")
cache.new_seq("B")
ref = {"A": [], "B": []}
# Interleave two requests, so their pages end up scattered through the pool
for i in range(10):
    for sid, n in (("A", 10), ("B", 6)):
        if i < n:
            k, v = kv(ord(sid), i)
            cache.append(sid, k, v)
            ref[sid].append((k, v))
print("block tables:", {s: cache.table[s] for s in "AB"})
print("free blocks:", sorted(cache.free))

q = np.array([0.5, -1.0, 0.25, 0.8])
K, V = cache.gather("A")
K_ref = np.stack([k for k, _ in ref["A"]])
V_ref = np.stack([v for _, v in ref["A"]])
out_contig = attend(q, K_ref, V_ref)
print("max |paged - contiguous| =", np.abs(attend(q, K, V) - out_contig).max())
pad_K = cache.k[cache.table["A"]].reshape(-1, D)       # all 3 pages, including 2 empty slots
pad_V = cache.v[cache.table["A"]].reshape(-1, D)
print("max error if empty slots are not masked =", np.abs(attend(q, pad_K, pad_V) - out_contig).max())

# Parallel sampling: 4 outputs share a 100-token prompt (page size 16), 50 output tokens each
def run(share):
    c = PagedKVCache(num_blocks=64, block_size=16, dim=D)
    c.new_seq("p")
    for i in range(100):
        c.append("p", *kv(0, i))
    for s in range(4):
        if share:
            c.fork("p", f"c{s}")
        else:
            c.new_seq(f"c{s}")
            for i in range(100):
                c.append(f"c{s}", *kv(0, i))
    c.free_seq("p")
    for s in range(4):
        for j in range(50):
            c.append(f"c{s}", *kv(10 + s, 100 + j))
    return c

shared, separate = run(share=True), run(share=False)
print("pages in use, shared prompt:", 64 - len(shared.free))
print("pages in use, separate copies:", 64 - len(separate.free))
ok = True
for s in range(4):
    expect = [kv(0, i) for i in range(100)] + [kv(10 + s, 100 + j) for j in range(50)]
    K_s, V_s = shared.gather(f"c{s}")
    ok &= np.array_equal(K_s, np.stack([k for k, _ in expect]))
    ok &= np.array_equal(V_s, np.stack([v for _, v in expect]))
print("every child reads back its own tokens:", ok)
print("child 0 block table:", shared.table["c0"])
print("child 3 block table:", shared.table["c3"])
```

```output
block tables: {'A': [0, 2, 4], 'B': [1, 3]}
free blocks: [5, 6, 7]
max |paged - contiguous| = 0.0
max error if empty slots are not masked = 0.023570046687576063
pages in use, shared prompt: 22
pages in use, separate copies: 40
every child reads back its own tokens: True
child 0 block table: [0, 1, 2, 3, 4, 5, 7, 8, 9, 10]
child 3 block table: [0, 1, 2, 3, 4, 5, 6, 19, 20, 21]
```

The block tables show the interleaving from the diagram: A's tokens sit in pages 0, 2 and 4, and B's in pages 1 and 3. The paged output equals the contiguous output exactly, because `gather` returns the same keys and values in the same order, and the arithmetic is unchanged. Paging changes where the numbers live, not the attention formula.

The unmasked version is different. Its two empty slots have zero keys, so their score is 0 rather than $-\infty$, and they take part in the softmax. The error is 0.0236, which is small but not zero, and it would be silent in a real system.

Parallel sampling is where sharing pays off. Four outputs that start from the same 100-token prompt need 7 pages for the prompt. Without sharing, each output stores its own copy, for 40 pages in total. With fork, the prompt pages are shared, and the partly filled page 6 is copied by three of the four outputs as they write. The fourth output is then the only owner of page 6 and writes into it directly. The total is 22 pages (a saving of 45%). Every output still reads back exactly its own tokens. The diagram shows the physical page ids each output uses.

![Four rows of physical page ids for four outputs; pages 0 to 5 are shared by all four rows, and pages 6 to 9 are private copies or new pages](diagrams/29.2-copy-on-write.svg "After forking, the prompt pages are shared. Each output then writes to private pages.")

## Code: how many requests fit?

The second block uses the same page-size logic, but for many requests at once. It uses a fixed deterministic workload of 1,000 requests with lengths from 32 to 2,048 tokens, and a memory budget of 65,536 token slots. A static scheme reserves 2,048 slots per request. A paged scheme takes ceil(length / B) pages, with B = 16 in the main case. The numbers below are a snapshot: every admitted request is counted at its full final length, which is a conservative assumption for the paged scheme.

```python
import numpy as np

CAPACITY = 65_536                          # token slots of KV memory
MAX_LEN = 2048                             # per-request reservation of a static scheme
idx = np.arange(1000)
lengths = 32 + (idx * 7919) % 2017         # deterministic workload: 1000 requests, 32..2048 tokens

# Static: reserve MAX_LEN slots per request, whatever its real length
static_admit = CAPACITY // MAX_LEN
static_util = lengths[:static_admit].sum() / CAPACITY

def paged(B):
    blocks_total = CAPACITY // B
    need = -(-lengths // B)                # ceil(L / B) pages per request
    admit = int(np.searchsorted(np.cumsum(need), blocks_total, side="right"))
    util = lengths[:admit].sum() / CAPACITY
    waste = (need[:admit] * B - lengths[:admit]).mean()
    return admit, util, waste

admit16, util16, waste16 = paged(16)
print(f"static: {static_admit} requests admitted, {static_util:.1%} of capacity holds tokens")
print(f"paged B=16: {admit16} requests admitted, {util16:.1%} of capacity holds tokens")
print(f"paged B=16: mean wasted slots per request = {waste16:.2f}")
print("mean request length:", lengths.mean())
for Bs in [1, 4, 16, 64, 256, 2048]:
    a, u, w = paged(Bs)
    print(f"page size {Bs:4d}: {a:2d} admitted, {u:.1%} of capacity holds tokens, {w:7.2f} wasted slots per request")
```

```output
paged B=16: 61 requests admitted, 97.8% of capacity holds tokens
paged B=16: mean wasted slots per request = 6.95
mean request length: 1040.283
page size    1: 62 admitted, 99.4% of capacity holds tokens,    0.00 wasted slots per request
page size    4: 62 admitted, 99.4% of capacity holds tokens,    1.42 wasted slots per request
page size   16: 61 admitted, 97.8% of capacity holds tokens,    6.95 wasted slots per request
page size   64: 60 admitted, 96.0% of capacity holds tokens,   30.68 wasted slots per request
page size  256: 56 admitted, 86.6% of capacity holds tokens,  129.84 wasted slots per request
page size 2048: 32 admitted, 51.9% of capacity holds tokens,  984.84 wasted slots per request
```

With pages, 61 requests fit instead of 32, and 97.8% of the budget holds real tokens instead of 51.9%. The larger batch is the source of the throughput gain, not any speedup of a single request.

![Bar charts: 32 requests admitted with a static slab against 61 with 16-token pages, and 51.9% of capacity holding tokens against 97.8%](diagrams/29.2-admission.svg "Same budget, same workload: the paged layout admits almost twice as many requests.")

The page-size sweep shows the trade-off. Smaller pages waste less memory per request, but they mean more table entries and more, smaller copies. The paper reports that its default block size of 16 is "large enough to efficiently utilize the GPU and small enough to avoid significant internal fragmentation in most workloads" (Kwon et al., 2023). The sweep above measures only memory, not GPU efficiency, so it cannot test that claim.

## What the 2–4× does and does not mean

The paper's headline result is that vLLM improves the throughput of popular LLMs by 2 to 4 times over FasterTransformer and Orca at the same latency, measured on the authors' GPU serving setup (Kwon et al., 2023, abstract). This lesson does not reproduce that benchmark. Our numbers show the memory mechanism only: the number of requests that can be admitted. Paging does not reduce the arithmetic in attention. The gather step adds an indirection, and on a real GPU it needs an attention kernel that reads pages through the block table.

> [!TRAP]
> **Unmasked empty slots**
> The last page of a sequence is usually partly empty. If you pass the whole page to softmax, empty slots take part in the attention weights. In our run this changed the output by 0.0236 with no error raised. Gather only the used slots, or mask the rest.

> [!TRAP]
> **Freeing a shared page**
> If a page is still mapped by another sequence, freeing it corrupts that sequence's data once the page is reused. Free a page only when its reference count drops to 0, as `_release` does.

> [!TRAP]
> **Writing into a shared partial page**
> Without the copy-on-write check, two outputs write their next tokens to the same slot, and each reads the other's token. The output then depends on another sample, and the error is silent.

> [!TRAP]
> **Reading the 2–4× as a per-request speedup**
> The gain comes from admitting larger batches under a memory budget. A single request decodes no faster because its cache is paged.

> [!TRAP]
> **Taking the block size as free**
> Block size 1 wastes no memory but needs a table entry for every token. Block size 2048 is just a contiguous slab again. The sweep above shows the memory side only.

## Summary

- A static KV cache reserves the maximum length per request, and in the paper's profiling only 20.4% to 38.2% of that memory held token states.
- PagedAttention maps logical token positions to physical pages through a block table, in the same way as OS virtual memory.
- Paging keeps attention output identical, provided that the gather step returns only the used slots in logical order.
- Copy-on-write lets parallel samples share prompt pages; in our run 4 outputs of a 100-token prompt used 22 pages instead of 40.
- The paper's motivation is that memory waste limits batch size, and the 2–4× throughput result is measured on its own GPU setup; our measured admission gain, from 32 to 61 requests, is a memory result only.

### Question 1: Calculation

A request has 1,000 tokens and the page size is 16. How many pages does it need, and how many of its slots are empty? A static slab of 2,048 slots holds the same request. What fraction of the slab holds tokens?

<details>
<summary>Solution</summary>

$\lceil 1000 / 16 \rceil = 63$ pages, which is $63 \times 16 = 1008$ slots, so 8 slots are empty. The slab holds $1000 / 2048 \approx 48.8\%$ of its slots as tokens.

</details>

### Question 2: Prediction

Using the block table from the first code block ($B = 4$, sequence A has table $[0, 2, 4]$), which index of the flat pool array `cache.k.reshape(-1, 4)` holds token 9 of sequence A? Use the formula physical page × B + slot.

<details>
<summary>Solution</summary>

Token 9 is in logical page 2 and slot 1. Physical page 4, so the flat index is $4 \times 4 + 1 = 17$.

</details>

### Question 3: Bug-spotting

Someone forks a sequence for parallel sampling, but removes the `elif self.ref[blocks[-1]] > 1` branch from `append`. What goes wrong, and how would you detect it?

<details>
<summary>Solution</summary>

After the fork, both outputs share the partial last page. Without the copy, both write their next token into the same slot, so the second write overwrites the first and each output reads the other's token. Detection: compare each child's `gather` output with the per-output reference, as the code does with `np.array_equal`.

</details>

### Question 4: Explanation

Why is the paged output exactly equal to the contiguous output in the first code block, and what changed in the output when the unused slots were not masked?

<details>
<summary>Solution</summary>

The gather step returns the same key and value arrays in the same logical order, so attention computes the same numbers. Without masking, the two empty slots have zero keys, which give score 0 and take part in the softmax, which changes the weights and the output by about 0.0236.

</details>
