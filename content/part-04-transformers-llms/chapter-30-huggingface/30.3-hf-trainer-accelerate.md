Training with the Hugging Face libraries takes little loop code, but three layers do the work underneath: the `datasets` library streams data lazily, `Accelerator` moves batches and shards them across processes, and `Trainer` runs the whole loop. In this lesson you will rebuild each mechanism in NumPy and check its numbers.

**You need:** minibatch gradient descent and the learning rate (Lesson 21.3), and loading a pretrained model with `AutoModel` (Lesson 30.1). Lesson 30.2 covers text generation and is not used here.

## The problem: the data does not fit, and the loop repeats

A pretraining corpus can be far larger than a disk. The English split of the FineWeb dataset is 45 terabytes, and the `datasets` documentation says streaming lets you use it without downloading it first (Hugging Face, datasets streaming guide). Every training run also repeats the same chores: fetch a batch, run the forward pass, run the backward pass, step the optimizer, then log and save. The three layers take these over in steps:

| Layer | What it removes | What you still write |
|---|---|---|
| `datasets` with `streaming=True` | downloading the whole dataset first | the preprocessing function |
| `Accelerator` | device placement and process sharding | your own loop |
| `Trainer` | the loop, logging and checkpoints | a configuration object |

Each layer is a thin wrapper, so each mechanism fits in a few lines. The rest of the lesson builds them that way.

## Streaming: nothing runs until you pull

A streamed dataset is an iterator. Nothing is read, tokenized or batched until the training loop asks for the next batch. Chaining a map and a batcher builds a pipeline of generators, and each example flows through one stage at a time.

![Three shards feed a lazy tokenize step, which feeds a batcher; the training step pulls one batch at a time](diagrams/30.3-stream-pipeline.svg "A pull-based pipeline. The counts come from the experiment run.")

The code below builds this pipeline on a toy dataset of 15 examples in 3 shards. It counts how many source examples were read and how many times the tokenizer ran.

```python
# Streaming pipeline on a toy dataset: 3 shards x 5 examples.
calls = {"source": 0, "map": 0}

def source():
    for shard in range(3):
        for i in range(5):
            ex_id = shard * 5 + i
            calls["source"] += 1
            text = ("good film" if ex_id % 2 == 0 else "bad plot twist") + f" number {ex_id}"
            yield {"id": ex_id, "text": text, "label": int(ex_id % 2 == 0)}

vocab = {"<pad>": 0}
MAX_LEN = 6

def tokenize(text):
    ids = [vocab.setdefault(w, len(vocab)) for w in text.split()][:MAX_LEN]
    return ids + [0] * (MAX_LEN - len(ids))

def lazy_map(it, fn):
    for ex in it:
        calls["map"] += 1
        yield {"input_ids": fn(ex["text"]), "label": ex["label"]}

def batches(it, n):
    buf = []
    for ex in it:
        buf.append(ex)
        if len(buf) == n:
            yield buf
            buf = []
    if buf:
        yield buf

pipe = batches(lazy_map(source(), tokenize), 2)
first = next(pipe)
print("first batch:", [e["input_ids"] for e in first])
print(f"after first batch: read {calls['source']} examples, {calls['map']} tokenizer calls")
rest = list(pipe)
print(f"batches: {len(rest) + 1}, last batch size: {len(rest[-1])}")
print(f"after full pass: read {calls['source']} examples, {calls['map']} tokenizer calls")
```

```output
first batch: [[1, 2, 3, 4, 0, 0], [5, 6, 7, 3, 8, 0]]
after first batch: read 2 examples, 2 tokenizer calls
batches: 8, last batch size: 1
after full pass: read 15 examples, 15 tokenizer calls
```

The first batch of 2 needed 2 source reads and 2 tokenizer calls. The full pass read 15 examples and produced 8 batches. Memory use therefore depends on the shuffle buffer and one batch, not on the size of the corpus. `IterableDataset.map` works the same way: the docs say it "applies processing on-the-fly when examples are streamed" (datasets guide).

A streamed dataset cannot be shuffled the way an in-memory array can, because the library does not know the full order in advance. `IterableDataset.shuffle` uses a shuffle buffer instead. It fills a buffer with `buffer_size` examples. For each new example, it emits a random buffered one and puts the new example in that slot. The default buffer size is 1,000 (datasets guide, "Shuffle").

```python
import numpy as np

def shuffle_buffer(it, buffer_size, rng):
    buf = []
    for ex in it:
        if len(buf) < buffer_size:
            buf.append(ex)
            continue
        j = int(rng.integers(len(buf)))   # pick a random buffered example
        yield buf[j]
        buf[j] = ex                       # put the newly read example in its slot
    for k in rng.permutation(len(buf)):   # source exhausted: flush the buffer in random order
        yield buf[k]

N = 1000
for b in [1, 10, 100, 1000]:
    order = list(shuffle_buffer(iter(range(N)), b, np.random.default_rng(0)))
    disp = np.abs(np.arange(N) - np.array(order))
    print(f"buffer={b:4d}  mean displacement={disp.mean():7.1f}  max={disp.max():4d}")
print(f"uniform random permutation of {N} items: mean displacement about {N / 3:.1f}")
```

```output
buffer=   1  mean displacement=    0.0  max=   0
buffer=  10  mean displacement=    6.9  max=  56
buffer= 100  mean displacement=   71.1  max= 779
buffer=1000  mean displacement=  332.9  max= 974
uniform random permutation of 1000 items: mean displacement about 333.3
```

![Bar chart: mean displacement is 0.0 for buffer 1, 6.9 for 10, 71.1 for 100 and 332.9 for 1000, which sits at the uniform-shuffle level N/3](diagrams/30.3-shuffle-buffer.svg "A buffer of 1 keeps the source order. A buffer as large as the dataset gives a full shuffle.")

Buffer size is a dial. The code also checks a guarantee: output position $k$ (counting from 0) holds a source example with index at most $k + \text{buffer\_size} - 1$, because an example enters the buffer only after it is read. Small buffers keep examples near their original place, so a dataset stored in topic order stays partly in topic order.

## Gradient accumulation: batch size is a product

Each optimizer step in `Trainer` uses the effective batch size

$$
B_{\text{eff}} = b_{\text{device}} \times N_{\text{devices}} \times k
$$

where $b_{\text{device}}$ is `per_device_train_batch_size` (default 8), $N_{\text{devices}}$ is the number of devices, and $k$ is `gradient_accumulation_steps` (Trainer docs). Accumulation runs $k$ forward and backward passes and adds their gradients before one update. The memory cost is that of one micro-batch, and the update uses $k$ times as many examples.

When is this the same update as one large batch? Take mean squared error (MSE), $L = \frac{1}{m}\sum_{i=1}^{m} (x_i^\top w - y_i)^2$. Its gradient is $g = \frac{2}{m} X^\top (Xw - y)$ on $m$ examples. Split $M = km$ examples into $k$ micro-batches of size $m$. Each example's term has weight $2/M$ in the full gradient. In its micro-batch it has weight $2/m$, and the averaging step multiplies that by $1/k$. Since $(2/m)(1/k) = 2/M$, the average of the $k$ micro-gradients equals the full gradient. This holds only if the micro-batches have equal size and the loss is a mean over examples.

```python
import numpy as np

rng = np.random.default_rng(1)
n, d = 32, 3
X = rng.normal(size=(n, d))
w_true = np.array([1.0, -2.0, 0.5])
y = X @ w_true + 0.1 * rng.normal(size=n)
w = np.zeros(d)

def grad_mse(Xb, yb, w):
    # L = mean((Xb w - yb)^2), so dL/dw = (2/m) Xb^T (Xb w - yb)
    return 2.0 / len(yb) * Xb.T @ (Xb @ w - yb)

g_full = grad_mse(X, y, w)                                           # one batch of 32
micro = [grad_mse(X[i:i + 8], y[i:i + 8], w) for i in range(0, 32, 8)]  # 4 micro-batches of 8

g_acc = sum(micro) / len(micro)    # accumulate, then divide by k = 4
g_naive = sum(micro)               # bug: forgot the division

print("g_full =", [round(float(x), 3) for x in g_full])
print(f"max |g_acc - g_full| = {np.max(np.abs(g_acc - g_full)):.1e}")
print(f"naive / full norm = {np.linalg.norm(g_naive) / np.linalg.norm(g_full):.1f}")

# Trap: micro-batches of unequal size, averaged as a mean of means
g_uneven = (grad_mse(X[:20], y[:20], w) + grad_mse(X[20:], y[20:], w)) / 2
print(f"unequal split relative error = {np.linalg.norm(g_uneven - g_full) / np.linalg.norm(g_full):.3f}")
```

```output
g_full = [-1.303, 3.027, -0.406]
max |g_acc - g_full| = 4.4e-16
naive / full norm = 4.0
unequal split relative error = 0.083
```

![Four micro-batches of 8 produce gradients that are summed and divided by 4, giving the gradient of one batch of 32](diagrams/30.3-grad-accum.svg "The division by k is what makes accumulation equal to one large batch.")

The 4.4e-16 difference is floating-point rounding. The naive sum is exactly $k = 4$ times too large, so it acts like a learning rate four times bigger. The unequal split is wrong by 8.3 percent: examples in the smaller micro-batch get more weight. For language models, where micro-batches hold different numbers of non-padding tokens, the same issue arises. I did not check how `Trainer` normalizes loss across accumulation steps, so treat that case as my own reasoning.

## Accelerate: prepare the loader, not the dataset

`Accelerator.prepare(*args)` prepares PyTorch DataLoaders, modules, optimizers and learning-rate schedulers for distributed training and mixed precision, and returns them in the same order (Accelerate docs, `Accelerator` reference). It passes a raw dataset through unchanged without an error, so wrap your data in a DataLoader first.

With the default `split_batches=False`, the batch size per process is the one you set, and the global batch is that size times the number of processes (Accelerate docs, `DataLoaderConfiguration`). The default `even_batches=True` says that when the total batch does not divide the dataset, "samples at the start of the dataset will be duplicated so the batch can be divided equally among all workers." The model below applies that rule to 9 samples, 2 processes and batches of 5. It is my NumPy model of the documented behaviour, not Accelerate's source code.

```python
import itertools

def assign(n_samples, bs, world):
    seq = list(range(n_samples))
    bl = [seq[i:i + bs] for i in range(0, n_samples, bs)]
    cyc = itertools.cycle(seq)                # duplicates come from the start of the data
    while len(bl[-1]) < bs:
        bl[-1].append(next(cyc))
    while len(bl) % world:
        bl.append([next(cyc) for _ in range(bs)])
    return {p: [bl[i] for i in range(p, len(bl), world)] for p in range(world)}

plan = assign(9, 5, 2)
print("process 0:", plan[0])
print("process 1:", plan[1])
gathered = [x for p in plan for step in plan[p] for x in step]
print(f"gathered: {len(gathered)} items; unique: {len(set(gathered))}")
```

```output
process 0: [[0, 1, 2, 3, 4]]
process 1: [[5, 6, 7, 8, 0]]
gathered: 10 items; unique: 9
```

![Two process rows of batch slots: process 0 holds samples 0 to 4, process 1 holds 5, 6, 7, 8 and a duplicate 0, and the gathered metric drops the duplicate](diagrams/30.3-sharding.svg "Ten slots hold nine samples. Use gather_for_metrics to drop the duplicate before computing metrics.")

The docs example for `gather_for_metrics` shows the same count: 9 samples, 2 processes, batch 5, and 9 items after gathering (Accelerate docs).

## Trainer: the same pieces, with the loop written for you

`Trainer` builds the data loader, creates an Accelerator internally (the Trainer docs say it does "the accelerator and perform post-creation setup"), and runs the loop. You configure it with `TrainingArguments`. The call shape below was checked against the Trainer docs. It was not run here, because this environment has no PyTorch.

```text
args = TrainingArguments(
    output_dir="out",
    per_device_train_batch_size=8,    # default is 8
    gradient_accumulation_steps=4,    # effective batch = 8 x devices x 4
    max_steps=10_000,                 # required when train_dataset has no length
)
trainer = Trainer(model=model, args=args, train_dataset=streamed)
trainer.train()
```

A streamed dataset has no length, so `Trainer` cannot infer how many steps an epoch takes. The docs therefore require `max_steps` for an `IterableDataset`.

## Common traps

> [!TRAP]
> **Preparing the dataset instead of the loader.** `accelerator.prepare` returns an object of a type it does not handle unchanged, and it raises no error, so a raw dataset is neither sharded nor placed on the device, and nothing warns you. Wrap the dataset in a DataLoader and prepare that.

> [!TRAP]
> **Streaming without `max_steps`.** `Trainer` needs `max_steps` when the training set has no `__len__`, because it cannot compute the total number of steps.

> [!TRAP]
> **Splitting before shuffling.** `take` and `skip` lock in the order of the shards, so the docs say to shuffle first and split second.

> [!TRAP]
> **Resuming a shuffled stream.** The docs say examples that were in a shuffle buffer are lost on resume, and the buffer refills with new data.

> [!TRAP]
> **Averaging unequal micro-batches.** A mean of means gives examples in small micro-batches more weight. Equalize the micro-batch sizes, or normalize by the true count.

## Summary

- A streamed dataset is a chain of generators: nothing is read or tokenized until the loop pulls a batch.
- A shuffle buffer of size $b$ bounds how far an example can move, so its size sets how well the data is mixed.
- Gradient accumulation averages $k$ micro-batch gradients; with equal micro-batches and a mean loss, the result equals one large batch.
- `Accelerator.prepare` takes loaders, modules, optimizers and schedulers, not raw datasets. A streamed training set needs `max_steps` in `Trainer`.

## Quiz time

### Question 1: Calculation

A run uses `per_device_train_batch_size=8`, `gradient_accumulation_steps=4` and 2 devices. What is the effective batch size per optimizer step?

<details><summary>Show solution</summary>

$8 \times 2 \times 4 = 64$. The formula above, with $k$ included, is the one that applies here.

</details>

### Question 2: Prediction

A shuffle buffer has size 10. Which source ids can be the first example emitted (output position 0)?

<details><summary>Show solution</summary>

Ids 0 to 9. The buffer holds ids 0 to 9 when id 10 is read. The emitted example is chosen from the buffer before id 10 is stored, so id 10 cannot be emitted first. The general bound is that output position $k$ holds a source index of at most $k + \text{buffer\_size} - 1$, which the experiment asserts for every output.

</details>

### Question 3: Bug spotting

The snippet below trains on a streamed dataset. What goes wrong, and how do you fix it?

```text
accelerator = Accelerator()
model, dataset = accelerator.prepare(model, streamed_dataset)
for batch in dataset:
    ...
```

<details><summary>Show solution</summary>

`prepare` handles DataLoaders, modules, optimizers and schedulers. A raw dataset passes through unchanged with no error, so the loop runs unsharded. Wrap the streamed dataset in a DataLoader, then prepare the loader: `loader = accelerator.prepare(DataLoader(streamed_dataset, batch_size=8))`. If you use `Trainer`, skip this step, because `Trainer` builds the loader itself.

</details>

### Question 4: Explanation

Two micro-batches of sizes 20 and 12 are averaged as a mean of means. Why does the gradient differ from the full-batch gradient, and which examples count more?

<details><summary>Show solution</summary>

With $k = 2$, the full-batch gradient gives each of the 32 examples weight $1/32$. The mean of means gives weight $1/(k m_i)$: $1/40$ for the 20 examples in the first micro-batch and $1/24$ for the 12 in the second. The examples in the smaller micro-batch count more. On the data in the experiment, the relative error is 0.083.

</details>
