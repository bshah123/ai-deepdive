You will be able to read the byte layout of a GGUF file, compute the storage cost of a block-quantized tensor, and explain why llama.cpp stores 4-bit weights in blocks of 32, each with one 16-bit scale. You will also see which parts of inference run on the CPU and which can run on the Metal GPU of a Mac.

**You need:** block quantization and scale factors (Lesson 32.1), and comfort reading hexadecimal bytes.

## The problem: a model has to fit, load and run on the machine you have

A 7-billion-parameter model stored in FP16 (16-bit floating point, 2 bytes per weight) needs about 14 GB for its weights alone (7e9 × 2 bytes). Quantization (Lesson 32.1) shrinks that. Two engineering questions remain. First, where do the bytes live? The weights, their scales, the tokenizer and the hyperparameters must sit in one file that a runtime can load without a training stack. Second, which kernel reads them? A CPU needs vectorized integer code, and a GPU needs its own kernels, and both must read the packed bytes directly.

GGUF answers the first question. GGML, the C tensor library inside the llama.cpp repository, and llama.cpp answer the second. Secondary sources read the name GGUF as "GGML Universal File". Do not trust blog expansions such as "GPT-Generated": the name comes from GGML.

## A GGUF file: a header, a table, then aligned bytes

![Byte map of a 768-byte GGUF file: a 24-byte header, 261 bytes of metadata, 113 bytes of tensor infos, 18 bytes of padding, then the F32 norm tensor (256 bytes) and the Q4_0 tensor (72 bytes) with 24 bytes of final padding](diagrams/32.3-gguf-layout.svg "Byte map of the two-tensor file from the experiment. Bar widths are proportional to bytes.")

The file has four parts, in this order:

- **Header, 24 bytes.** The ASCII bytes `GGUF`, a 4-byte version (3 in the spec), an 8-byte tensor count and an 8-byte metadata count.
- **Metadata.** Typed key-value pairs such as `general.architecture = "llama"`. Each key is a length-prefixed UTF-8 string, and each value has a type code (8 for STRING, 4 for UINT32).
- **Tensor infos.** One record per tensor: name, dimensions, a ggml type code (0 for F32, 2 for Q4_0) and an offset.
- **Tensor data.** Starts at the first multiple of `general.alignment` (default 32) after the tensor infos. Each offset is relative to this start, not to the start of the file.

The first code block builds a tiny file in memory with these rules and parses it back. It runs in the browser.

```python
import io
import struct
import numpy as np

def gstr(s):                                   # GGUF string: uint64 length, then UTF-8 bytes, no terminator
    b = s.encode("utf-8")
    return struct.pack("<Q", len(b)) + b

def align_up(offset, alignment=32):
    return offset + (alignment - offset % alignment) % alignment

# Write: magic, version, counts, metadata, tensor info, padding, data
kv = [gstr("general.architecture") + struct.pack("<I", 8) + gstr("llama"),          # value type 8 = STRING
      gstr("general.alignment") + struct.pack("<I", 4) + struct.pack("<I", 32)]     # value type 4 = UINT32
norm = np.linspace(0.5, 1.5, 64, dtype=np.float32)                                  # 64 x 4 bytes = 256 bytes
info = (gstr("blk.0.attn_norm.weight") + struct.pack("<I", 1)                      # one dimension
        + struct.pack("<Q", 64) + struct.pack("<IQ", 0, 0))                         # ggml type 0 = F32, offset 0
header = b"GGUF" + struct.pack("<IQQ", 3, 1, len(kv))                               # version 3, 1 tensor, 2 kv
prefix = header + b"".join(kv) + info
data_start = align_up(len(prefix))
blob = prefix + b"\x00" * (data_start - len(prefix)) + norm.tobytes()
print("header + metadata + tensor info:", len(prefix), "bytes; data starts at", data_start)
print("file size:", len(blob), "bytes")

# Read it back
buf = io.BytesIO(blob)
magic = buf.read(4)
version, n_tensors, n_kv = struct.unpack("<IQQ", buf.read(20))
def read_str():
    (n,) = struct.unpack("<Q", buf.read(8))
    return buf.read(n).decode("utf-8")
print("magic:", magic, "version:", version, "tensors:", n_tensors, "kv pairs:", n_kv)
for _ in range(n_kv):
    key = read_str()
    (vtype,) = struct.unpack("<I", buf.read(4))
    value = read_str() if vtype == 8 else struct.unpack("<I", buf.read(4))[0]
    print(f"  {key} = {value!r}")
name = read_str()
(ndim,) = struct.unpack("<I", buf.read(4))
dims = struct.unpack(f"<{ndim}Q", buf.read(8 * ndim))
ggml_type, offset = struct.unpack("<IQ", buf.read(12))
print("tensor:", name, "dims:", dims, "type:", ggml_type, "offset:", offset)
w = np.frombuffer(blob, dtype=np.float32, count=dims[0], offset=data_start + offset)
print("first 3 values:", w[:3].tolist(), " last value:", float(w[-1]))
```

```output
header + metadata + tensor info: 156 bytes; data starts at 160
file size: 416 bytes
magic: b'GGUF' version: 3 tensors: 1 kv pairs: 2
  general.architecture = 'llama'
  general.alignment = 32
tensor: blk.0.attn_norm.weight dims: (64,) type: 0 offset: 0
first 3 values: [0.5, 0.5158730149269104, 0.5317460298538208]  last value: 1.5
```

Because the offsets sit in a table, a runtime reads only the table, then maps each tensor's bytes where they are. That is why llama.cpp can load a large file lazily (see the CPU and Metal section).

## Block quantization: 32 weights share one scale

The basic 4-bit format in GGML is `Q4_0`. Its weights are split into blocks of 32. Each block stores one FP16 scale `d` and 32 four-bit levels packed two per byte: 2 + 16 = 18 bytes. This lesson writes the scale as $d$ and calls each 32-weight unit a block; Lessons 32.1 and 32.2 wrote the scale as $s$ and called the unit a group. That is 18 × 8 / 32 = 4.5 bits per weight. The extra half bit is the scale, spread over 32 weights.

![Bars for bits per weight: F32 32, F16 16, Q8_0 8.5, Q4_0 4.5, with the storage for 7 billion weights: 28.00, 14.00, 7.44 and 3.94 GB](diagrams/32.3-bits-per-weight.svg "Bits per weight, and the size of a 7-billion-weight model computed as parameters times bits divided by 8.")

The storage layout is the C struct `block_q4_0` (a 2-byte scale followed by 16 bytes of quants) in `ggml/src/ggml-common.h`. The quantizer, `quantize_row_q4_0_ref` in `ggml/src/ggml-quants.c`, works like this:

1. Find the element with the largest magnitude, and keep its sign.
2. Set $d = w_{\max} / -8$, so the largest weight maps to level 0.
3. Compute each level as $q = \min(15, \operatorname{trunc}(w/d + 8.5))$, which lies in 0 to 15.
4. Reconstruct with $w' = (q - 8)\,d$. The offset of 8 centres the levels on zero.

The second code block works one block by hand. The 32 values were chosen for this lesson, and the scale comes from the largest one, 0.91.

![One Q4_0 block: the first eight weights, their levels from 0 to 15, and the rebuilt values, with the scale d equal to -0.11375](diagrams/32.3-worked-block.svg "First eight values of the block. The full block has 32 values; the scale comes from element 14 (0.91).")

```python
import numpy as np

# One block of 32 weights (values chosen for the lesson)
x = np.array([0.12, -0.80, 0.33, 0.05, -0.41, 0.60, -0.02, 0.27,
              0.00, 0.19, -0.66, 0.08, 0.44, -0.11, 0.91, -0.25,
              0.37, -0.53, 0.14, 0.02, -0.07, 0.29, -0.38, 0.50,
              -0.19, 0.61, 0.03, -0.46, 0.22, -0.09, 0.75, -0.31], dtype=np.float32)

i = int(np.argmax(np.abs(x)))                       # element of largest magnitude (keeps its sign)
d = np.float32(x[i] / np.float32(-8))               # scale: the largest weight maps to level 0
inv_d = np.float32(1) / d
d16 = d.astype(np.float16)                          # the file stores the scale as FP16 (2 bytes)
q = np.minimum(15, np.trunc(x * inv_d + np.float32(8.5))).astype(np.int32)   # 4-bit levels 0..15
rebuilt = (q - 8).astype(np.float32) * d16.astype(np.float32)                # w' = (q - 8) * d

packed = (q[:16] | (q[16:] << 4)).astype(np.uint8)  # element j -> low nibble of byte j; j+16 -> high nibble
print("largest |w|:", float(x[i]), "at element", i)
print("scale d:", float(d), " stored as FP16:", float(d16))
print("levels:", q.tolist())
print("rebuilt first 8:", [round(float(v), 3) for v in rebuilt[:8]])
print("bytes per block:", 2 + packed.size, "-> bits per weight:", (2 + packed.size) * 8 / 32)
print("RMSE:", round(float(np.sqrt(np.mean((rebuilt - x) ** 2))), 3),
      " max error:", round(float(np.max(np.abs(rebuilt - x))), 3))
```

```output
largest |w|: 0.9100000262260437 at element 14
scale d: -0.11375000327825546  stored as FP16: -0.11376953125
levels: [7, 15, 5, 8, 12, 3, 8, 6, 8, 6, 14, 7, 4, 9, 0, 10, 5, 13, 7, 8, 9, 5, 11, 4, 10, 3, 8, 12, 6, 9, 1, 11]
rebuilt first 8: [0.114, -0.796, 0.341, -0.0, -0.455, 0.569, -0.0, 0.228]
bytes per block: 18 -> bits per weight: 4.5
RMSE: 0.031  max error: 0.051
```

Check the output against the rules. The weight 0.12 gives $0.12 / -0.11375 + 8.5 = 7.45$, which truncates to level 7 and rebuilds to $(7 - 8)(-0.11377) = 0.114$. The weight 0.91 gets level 0 and rebuilds to 0.910. The weight 0.05 gets level 8, which rebuilds to zero, so a value that small is lost. (`-0.0` is a signed zero.)

Two details of the C code matter for correctness. The inverse scale is computed from the FP32 value of $d$, but dequantization uses the FP16 value, a mismatch of about $2^{-11}$ relative. And the range is asymmetric: the lowest level rebuilds to $-8d$ and the highest to $+7d$.

`Q8_0` uses the same block size with 8-bit signed values and $d = \max|w| / 127$. It costs 8.5 bits per weight. llama.cpp's formats are symmetric, so they have no zero point. Lesson 32.1 covers the general scale and zero-point maths.

> [!KEY-INSIGHT]
> The block is the unit of error. Each scale fits only the 32 values in its block, so one outlier spoils only its own block.

## How much error does block size buy?

The experiment script `scripts/diagrams/lessons/32.3_experiment.py` quantizes 65,536 seeded Gaussian weights, then the same weights with 0.1% of entries multiplied by 20. It reports RMSE divided by the weights' standard deviation. Two rows use one scale per 256 weights and one scale for the whole tensor. Those are not llama.cpp formats; they show block size alone.

![Grouped bars of relative RMSE for four quantizers. Gaussian weights: Q8_0 0.005, Q4_0 0.086, 4-bit block 256 0.111, 4-bit whole tensor 0.171. Weights with outliers: 0.007, 0.114, 0.252, 0.878](diagrams/32.3-error-bars.svg "Relative RMSE (root-mean-square error divided by the weight standard deviation). Lower is better.")

With outliers, the whole-tensor scale is set by the largest value, so most weights get levels far too coarse. Q4_0 rises from 0.086 to 0.114 when outliers appear. The whole-tensor scheme rises from 0.171 to 0.878. These are synthetic weights and one seed. They measure weight error, not model quality, so do not read them as a perplexity result.

## Dot products stay in integers

Each output of a linear layer is a dot product, $\sum_i w_i x_i$. llama.cpp's generic reference kernel `ggml_vec_dot_q4_0_q8_0_generic` (`ggml/src/ggml-cpu/quants.c`) takes the weights as `Q4_0` blocks and the activations as `Q8_0` blocks. For each block it forms an integer sum of products of levels, then multiplies by the two FP16 scales once: `sumi * d_w * d_a`. The third code block checks this path against dequantizing first.

![Weight block (Q4_0) and activation block (Q8_0) combine into an exact integer sum sumi = 379; multiplied by both scales this gives a block contribution of 0.0609; 128 blocks summed give 0.765178](diagrams/32.3-dot-kernel.svg "Block 0 of the experiment's 4,096-element dot product. The integer sum is exact; only the scale multiplications round.")

```python
import numpy as np

def q4_0(x):                                        # per block of 32: FP16 scales and 4-bit levels (0..15)
    x = x.reshape(-1, 32)
    i = np.argmax(np.abs(x), axis=1)
    d = (x[np.arange(len(x)), i] / np.float32(-8)).astype(np.float32)
    inv = np.where(d != 0, np.float32(1) / np.where(d != 0, d, 1), 0).astype(np.float32)
    q = np.minimum(15, np.trunc(x * inv[:, None] + np.float32(8.5))).astype(np.int32)
    return d.astype(np.float16), q

def q8_0(x):                                        # per block of 32: FP16 scale and int8 values
    x = x.reshape(-1, 32)
    d = (np.max(np.abs(x), axis=1) / np.float32(127)).astype(np.float32)
    inv = np.where(d != 0, np.float32(1) / np.where(d != 0, d, 1), 0).astype(np.float32)
    v = x * inv[:, None]
    return d.astype(np.float16), (np.sign(v) * np.floor(np.abs(v) + 0.5)).astype(np.int32)

rng = np.random.default_rng(0)
n = 128                                             # 4 blocks
w = (rng.standard_normal(n) * 0.02).astype(np.float32)
a = rng.standard_normal(n).astype(np.float32)

dw, qw = q4_0(w)
da, qa = q8_0(a)
signed = qw - 8                                     # llama.cpp's -8 offset, per element
sumi = (signed * qa).sum(axis=1)                    # exact integer sum inside each block
blockwise = np.sum(sumi * dw.astype(np.float32) * da.astype(np.float32))

rebuilt_w = (signed.astype(np.float32) * dw.astype(np.float32)[:, None]).reshape(-1)
rebuilt_a = (qa.astype(np.float32) * da.astype(np.float32)[:, None]).reshape(-1)
print("integer sums per block:", sumi.tolist())
print("blockwise dot:", round(float(blockwise), 6))
print("dequantize, then float dot:", round(float(rebuilt_w @ rebuilt_a), 6))
print("exact dot of the original floats:", round(float(w.astype(np.float64) @ a.astype(np.float64)), 6))
```

```output
integer sums per block: [197, 2162, 66, 1103]
blockwise dot: 0.019937
dequantize, then float dot: 0.019937
exact dot of the original floats: 0.006927
```

The first two lines agree to six decimal places. That is the check that matters: the integer path computes what dequantizing and multiplying would compute. The third line is the quantization error. Both the exact dot and its error scale with $\sqrt{n}$, and the error's spread is about 0.086 of the exact dot's spread. The reason: the error per weight is about 0.086 of the weight spread, and the activations are independent of the errors. The experiment's 300-row check on 4,096-element vectors bears this out: error standard deviation 0.111 against a predicted 0.110.

The benefit is memory traffic: the weights are read once in 4-bit form, and the inner loop works on bytes and small integers. This lesson has no speed benchmark, so it does not claim a speed-up.

## CPU and Metal: where the kernels run

llama.cpp has several backends. The CPU path uses SIMD (single instruction, multiple data) versions of the kernels above. The Metal backend runs the same operations on the GPU. The llama.cpp build documentation says: "On MacOS, Metal is enabled by default. Using Metal makes the computation run on the GPU." Metal can be turned off at build time with `-DGGML_METAL=OFF`, and `--n-gpu-layers 0` keeps inference on the CPU at run time.

The flag `-ngl` (`--n-gpu-layers`) sets how many layers go to the GPU. The CLI README describes it as "max. number of layers to store in VRAM, either an exact number, 'auto', or 'all' (default: auto)". Its load-mode `auto` means mmap (memory mapping) "unless a device does not support it". With mmap, the file is not copied into RAM up front, and the operating system pages tensor bytes in when they are touched. This is why the offset table matters.

On an Apple Silicon Mac, CPU and GPU share one memory pool. This is my reasoning, not something the sources say: it avoids copying weights across a bus, but it does not remove the need for the weights to fit in memory. Test speed on your own machine before you rely on any setting.

> Flag names change between llama.cpp releases. The flags here come from the README read for this lesson. Check `--help` on the build you run.

## Common traps

> [!TRAP]
> `Q4_0` is 4.5 bits per weight, not 4. The FP16 scale costs 16 bits per 32 weights.

> [!TRAP]
> Tensor offsets are relative to the start of tensor data. Reading `np.frombuffer(blob, offset=offset)` without adding `data_start` may silently read the wrong bytes.

> [!TRAP]
> GGUF is a container, not a compression scheme. All the information loss comes from the quantizer.

> [!TRAP]
> A small value in a block can round to zero. In the worked block, 0.05 rebuilds to 0. That is a property of the 4-bit grid, not a loader bug.

## Summary

- A GGUF file is a 24-byte header, typed metadata, a tensor table of names, shapes, types and offsets, and tensor data aligned to 32 bytes by default.
- `Q4_0` stores 32 weights as one FP16 scale and 16 bytes of packed 4-bit levels: 18 bytes, or 4.5 bits per weight.
- The scale is $d = w_{\max} / -8$, and reconstruction is $(q - 8)\,d$, which is asymmetric in range.
- Block size limits the damage from outliers: on synthetic weights, a whole-tensor scale raised relative RMSE from 0.114 to 0.878 compared with Q4_0 blocks.
- The dot product is an exact integer sum per block, scaled by two FP16 values. On macOS, the llama.cpp build enables Metal by default.

## Quiz time

### Question 1: Storage arithmetic

A `Q4_0` tensor has 4,096 × 4,096 weights. How many bytes does the quantized data take, excluding the header and metadata? What is the cost in bits per weight?

<details><summary>Show solution</summary>

There are 4,096 × 4,096 / 32 = 524,288 blocks. Each block is 18 bytes, so 524,288 × 18 = 9,437,184 bytes, about 9.4 MB. Bits per weight: 18 × 8 / 32 = 4.5.

</details>

### Question 2: Prediction

In the worked block, the weight 0.05 rebuilds to 0. Why? If the block contained only that value, what would it rebuild to?

<details><summary>Show solution</summary>

The level is trunc(0.05 / -0.11375 + 8.5) = trunc(8.06) = 8, and (8 − 8) × d = 0. If 0.05 were the only value, it would be the largest magnitude, so it would map to level 0 with d = 0.05 / −8 = −0.00625. It would rebuild to 0.05 (within FP16 rounding of the scale).

</details>

### Question 3: Bug spotting

A loader reads a tensor with this line. What is wrong, and how would you find it?

```python
w = np.frombuffer(blob, dtype=np.float32, count=n, offset=t["offset"])
```

<details><summary>Show solution</summary>

The offset is relative to the start of tensor data, not the file. The line omits `data_start`, the first multiple of `general.alignment` after the tensor infos. The fix is `offset=data_start + t["offset"]`. To find it, check that `data_start` is a multiple of 32, then compare the first values with a file whose contents you wrote yourself.

</details>

### Question 4: Explanation

Why does one 4-bit scale for a whole tensor fare so badly with 0.1% outliers of size 20, while Q4_0 blocks of 32 do not? Answer in terms of the scale.

<details><summary>Show solution</summary>

The scale is set by the largest magnitude in its group. With one scale for the whole tensor, a single outlier of size about 20 sets the step for every weight, so the typical weights fall into a handful of levels. With blocks of 32, only the blocks that contain an outlier get a large scale, and the rest keep a fine step. The measured relative RMSE rose from 0.171 to 0.878 for the whole-tensor scheme, against 0.086 to 0.114 for Q4_0.

</details>
