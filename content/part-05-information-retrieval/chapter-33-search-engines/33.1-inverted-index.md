A search engine answers a query by looking up each word in an **inverted index**, a table that maps every word to the list of documents containing it. In this lesson you will build one in plain Python, answer AND queries by intersecting its lists, and measure how much space the lists take once they are stored as compressed differences.

**You need:** Python strings and `split()` (Lesson 3.3), and dictionaries (Lesson 6.1).

## The problem the index solves

Suppose a query asks for the documents that contain "cat". Without an index, the engine must read every document. With $N$ documents of average length $L$ tokens, one query costs about $N \times L$ token reads. The work grows with the corpus even when the answer is one document. This is reasoning from the definition, not a measurement.

An inverted index changes the access path. For every term it stores a **postings list**: the sorted document identifiers (docIDs) that contain the term. A query reads only the lists of its own terms.

![Four short documents read forward, document to terms, and then inverted, term to postings](diagrams/33.1-forward-vs-inverted.svg "The same four documents, read forward and then inverted.")

Two definitions are used below. A **posting** is one entry in a list: a docID plus the **term frequency** (tf), the number of times the term occurs in that document. The **document frequency** (df) of a term is the length of its postings list.

## Building the index and intersecting lists

The corpus has four short documents. The tokenizer splits on whitespace, which is enough for this example; real engines also lowercase, stem and remove stop words. The code builds the index, prints every postings list, and answers three AND queries. An AND query keeps only the documents that appear in both lists.

```python
docs = {
    0: "the cat sat",
    1: "the dog sat down",
    2: "a cat and a dog",
    3: "the bird flew",
}

def build_index(docs):
    """Map each term to a sorted list of (doc_id, term_frequency) pairs."""
    index = {}
    for doc_id in sorted(docs):
        counts = {}
        for term in docs[doc_id].split():
            counts[term] = counts.get(term, 0) + 1
        for term, tf in counts.items():
            index.setdefault(term, []).append((doc_id, tf))
    return index

def intersect(p, q):
    """Two-pointer AND of two sorted doc-id lists. Returns (result, comparisons)."""
    i = j = comparisons = 0
    out = []
    while i < len(p) and j < len(q):
        comparisons += 1
        if p[i] == q[j]:
            out.append(p[i]); i += 1; j += 1
        elif p[i] < q[j]:
            i += 1
        else:
            j += 1
    return out, comparisons

index = build_index(docs)
for term in sorted(index):
    print(f"{term:5s} df={len(index[term])} postings={index[term]}")

def doc_ids(term):
    return [d for d, _ in index.get(term, [])]

for a, b in [("cat", "dog"), ("the", "sat"), ("the", "bird")]:
    result, cmp_ = intersect(doc_ids(a), doc_ids(b))
    print(f"{a} AND {b}: docs {result}  ({cmp_} comparisons)")
```

```output
a     df=1 postings=[(2, 2)]
and   df=1 postings=[(2, 1)]
bird  df=1 postings=[(3, 1)]
cat   df=2 postings=[(0, 1), (2, 1)]
dog   df=2 postings=[(1, 1), (2, 1)]
down  df=1 postings=[(1, 1)]
flew  df=1 postings=[(3, 1)]
sat   df=2 postings=[(0, 1), (1, 1)]
the   df=3 postings=[(0, 1), (1, 1), (3, 1)]
cat AND dog: docs [2]  (3 comparisons)
the AND sat: docs [0, 1]  (2 comparisons)
the AND bird: docs [3]  (3 comparisons)
```

Each posting is a pair. The word "a" occurs twice in document 2, so its posting is `(2, 2)`.

Answering "cat AND dog" means intersecting two sorted lists. Walk both lists with one pointer each. If the two heads are equal, output the docID and advance both pointers. If not, advance the pointer at the smaller head. The figure traces the first query.

![Three steps of a two-pointer walk over the lists cat [0, 2] and dog [1, 2]; the amber cells are the current pointers](diagrams/33.1-and-trace.svg "Two-pointer AND of cat and dog, one step per panel.")

The lists must be sorted for this walk to be correct (Trap 1 below). The cost is at most $|p| + |q|$ comparisons, where $|p|$ and $|q|$ are the two list lengths. That is linear in the list lengths, not in the corpus size. This bound follows from the algorithm: each comparison advances one pointer, and the pointers never move backwards.

## Compressing postings: d-gaps and VByte

Sorted docIDs in a dense list sit close together, so storing the differences is cheaper. These differences are called **d-gaps**. The docIDs [1000, 1004, 1010] become the d-gaps [1000, 4, 6]. A small number needs fewer bytes than the 4 bytes of a 32-bit integer.

**VByte** (variable-byte encoding) stores each integer in groups of 7 data bits, and each byte spends its top bit as a flag. The survey by Pibiri and Venturini defines the convention as follows: the continuation bit is 1 on every byte except the last, which is 0 (their Section 2.9). This lesson uses that convention. Other byte layouts exist, so check a file format's specification before reading files written by another program.

The worked example by hand:

- 4 is below 128, so it fits in 7 bits. It takes one byte, with flag 0 and data 0000100: `00000100`.
- 1000 = 7 × 128 + 104. The high group 7 = 0000111 gets flag 1: `10000111`. The low group 104 = 1101000 gets flag 0: `01101000`. That is two bytes.

![Byte layouts of 4 and 1000 in VByte: each byte is eight cells, with the amber flag bit first and seven data bits after it](diagrams/33.1-vbyte-bits.svg "VByte bytes for 4 and 1000. The amber cells are the flag bits.")

```python
import random

def vbyte_encode(n):
    """Encode one non-negative integer: 7 data bits per byte, high bit 1 = more bytes follow."""
    groups = [n & 0x7F]
    n >>= 7
    while n:
        groups.append(n & 0x7F)
        n >>= 7
    groups.reverse()
    out = bytearray()
    for k, g in enumerate(groups):
        more = 0x80 if k < len(groups) - 1 else 0x00
        out.append(more | g)
    return bytes(out)

def vbyte_decode(data):
    """Decode a byte string back into a list of integers."""
    nums, n = [], 0
    for b in data:
        n = (n << 7) | (b & 0x7F)
        if b & 0x80 == 0:
            nums.append(n)
            n = 0
    return nums

for x in [4, 127, 128, 824, 1000]:
    enc = vbyte_encode(x)
    print(f"{x:5d} -> {[format(b, '08b') for b in enc]}  {len(enc)} byte(s)  decodes to {vbyte_decode(enc)[0]}")

rng_check = random.Random(1)
sample = [rng_check.randrange(0, 2**20) for _ in range(10000)]
assert [v for x in sample for v in vbyte_decode(vbyte_encode(x))] == sample
print("round trip of 10,000 random integers below 2**20: OK")
```

```output
    4 -> ['00000100']  1 byte(s)  decodes to 4
  127 -> ['01111111']  1 byte(s)  decodes to 127
  128 -> ['10000001', '00000000']  2 byte(s)  decodes to 128
  824 -> ['10000110', '00111000']  2 byte(s)  decodes to 824
 1000 -> ['10000111', '01101000']  2 byte(s)  decodes to 1000
round trip of 10,000 random integers below 2**20: OK
```

The decoder reads bytes until it meets one with flag 0, so no separate length field is needed. The round trip is exact for every integer in the test, which is what the assertion checks.

## Measuring space on a synthetic corpus

Real collections are not available here, so the next experiment uses a synthetic corpus of 20,000 documents and 1,000 terms. The assumption is a model, not a fact about any corpus: the term with rank $r$ has df $\approx 0.3 N / r$, a Zipf-like distribution (frequency falls off as a power of rank). Each postings list is a random sample of docIDs. The code measures bytes per posting after VByte on the d-gaps, and compares it with an uncompressed bitmap of one bit per document, which costs 2,500 bytes per term.

```python
import random

def vbyte_encode(n):
    """Encode one non-negative integer: 7 data bits per byte, high bit 1 = more bytes follow."""
    groups = [n & 0x7F]
    n >>= 7
    while n:
        groups.append(n & 0x7F)
        n >>= 7
    groups.reverse()
    out = bytearray()
    for k, g in enumerate(groups):
        more = 0x80 if k < len(groups) - 1 else 0x00
        out.append(more | g)
    return bytes(out)

N_DOCS, N_TERMS = 20_000, 1_000
rng = random.Random(33)
postings = {}
for r in range(1, N_TERMS + 1):
    df = max(1, round(0.3 * N_DOCS / r))
    postings[f"t{r}"] = sorted(rng.sample(range(N_DOCS), df))
print(f"terms={len(postings)} postings={sum(len(p) for p in postings.values())}")

def gaps(doc_ids_):
    """d-gaps: the first id as is, then each id minus the previous one."""
    return [doc_ids_[0]] + [b - a for a, b in zip(doc_ids_, doc_ids_[1:])]

buckets = [("df>=1000", 1000, 10**9), ("100-999", 100, 999), ("10-99", 10, 99), ("1-9", 1, 9)]
bucket_rows = {}
for label, lo, hi in buckets:
    terms = [p for p in postings.values() if lo <= len(p) <= hi]
    n_post = sum(len(p) for p in terms)
    vbytes = sum(len(vbyte_encode(g)) for p in terms for g in gaps(p))
    bitmap = sum(N_DOCS // 8 for _ in terms)
    bucket_rows[label] = {"terms": len(terms), "postings": n_post,
                          "vbyte": vbytes / n_post, "bitmap": bitmap / n_post}
    print(f"{label:9s} terms={len(terms):4d} postings={n_post:6d} "
          f"vbyte={vbytes / n_post:.2f} B/posting  bitmap={bitmap / n_post:.2f} B/posting  raw32=4.00")
```

```output
terms=1000 postings=44907
df>=1000  terms=   6 postings= 14700 vbyte=1.00 B/posting  bitmap=1.02 B/posting  raw32=4.00
100-999   terms=  54 postings= 13379 vbyte=1.19 B/posting  bitmap=10.09 B/posting  raw32=4.00
10-99     terms= 571 postings= 14079 vbyte=1.80 B/posting  bitmap=101.39 B/posting  raw32=4.00
1-9       terms= 369 postings=  2749 vbyte=1.95 B/posting  bitmap=335.58 B/posting  raw32=4.00
```

![Bytes per posting on a log scale, for four df buckets: VByte of d-gaps is about 1 byte for the most common terms and about 2 for rare ones; the uncompressed bitmap is about 1 for the most common terms and hundreds for rare ones; a dashed line marks raw 32-bit IDs at 4 bytes](diagrams/33.1-bytes-per-posting.svg "Bytes per posting on the synthetic corpus, log scale. Raw 32-bit IDs cost 4 bytes.")

On this corpus, VByte costs about 1 byte per posting for terms in at least 1,000 documents, and about 2 bytes for rare terms. That is 2 to 4 times smaller than raw 32-bit IDs. The bitmap is competitive only for the densest bucket, where it costs 1.02 bytes per posting against 1.00 for VByte. For rare terms it costs 100 to 335 bytes per posting. The measurement covers only the docID gaps. Term frequencies, positions and block headers add to the real size.

## Skip pointers for unequal lists

When one list is much shorter than the other, the merge still walks the long list one entry at a time. A **skip pointer** lets the long list jump. Here the long list has a pointer every $\text{step} = \text{round}(\sqrt{\text{length}})$ entries. The search jumps to the next pointer while the pointer's docID is still below the current docID of the short list, and then steps one entry at a time. The square-root step is a heuristic chosen for this lesson, not an optimum. The technique and the numbers below are my own measurement on this synthetic corpus.

```python
import math
import random

rng = random.Random(33)
N_DOCS, N_TERMS = 20_000, 1_000
postings = {}
for r in range(1, N_TERMS + 1):
    df = max(1, round(0.3 * N_DOCS / r))
    postings[f"t{r}"] = sorted(rng.sample(range(N_DOCS), df))

def merge_and(p, q):
    """Two-pointer AND. Returns (result, comparisons)."""
    i = j = comparisons = 0
    out = []
    while i < len(p) and j < len(q):
        comparisons += 1
        if p[i] == q[j]:
            out.append(p[i]); i += 1; j += 1
        elif p[i] < q[j]:
            i += 1
        else:
            j += 1
    return out, comparisons

def skip_and(short, long_, step):
    """Two-pointer AND where long_ has skip pointers at every multiple of `step`."""
    i = j = comparisons = 0
    out = []
    while i < len(short) and j < len(long_):
        x, y = short[i], long_[j]
        comparisons += 1
        if x == y:
            out.append(x); i += 1; j += 1
        elif x < y:
            i += 1
        else:
            while (j // step + 1) * step < len(long_):
                nxt = (j // step + 1) * step
                comparisons += 1
                if long_[nxt] < x:
                    j = nxt
                else:
                    break
            j += 1
    return out, comparisons

skip_rows = []
for a, b in [("t300", "t1"), ("t60", "t1"), ("t300", "t60"), ("t20", "t40")]:
    p, q = sorted([postings[a], postings[b]], key=len)
    truth = sorted(set(p) & set(q))
    m, c_m = merge_and(p, q)
    s, c_s = skip_and(p, q, step=round(math.sqrt(len(q))))
    assert m == truth and s == truth
    skip_rows.append({"pair": f"{a} AND {b}", "short": len(p), "long": len(q),
                      "result": len(truth), "merge": c_m, "skip": c_s})
    print(f"{a} AND {b}: short={len(p)} long={len(q)} result={len(truth)} "
          f"merge={c_m} skip={c_s}")
```

```output
t300 AND t1: short=20 long=6000 result=8 merge=5881 skip=1436
t60 AND t1: short=100 long=6000 result=34 merge=6043 skip=5711
t300 AND t60: short=20 long=100 result=0 merge=118 skip=144
t20 AND t40: short=150 long=300 result=2 merge=446 skip=688
```

![Bar chart of comparisons for merge and skip-pointer AND on four list pairs: 20 against 6000 drops from 5881 to 1436 with skips, while 150 against 300 rises from 446 to 688](diagrams/33.1-skip-comparisons.svg "Comparisons for merge and skip-pointer AND on four list pairs.")

For a 20-entry list against a 6,000-entry list, skip pointers cut the comparisons from 5,881 to 1,436. For two lists of similar length, 150 and 300 entries, they cost more: 688 against 446. The jumps are not repaid when there is no long stretch to skip. These are comparison counts from one seed, not timings.

## Common traps

> [!TRAP]
> **Trap 1: unsorted input fails silently.** The two-pointer walk assumes sorted lists. `intersect([2, 0], [0, 2])` returns `[2]` and drops 0, with no error. By hand: 2 is greater than 0, so the pointer on the second list advances; then 2 equals 2, which is output, and the second list is exhausted. The 0 in the first list is never compared.

> [!TRAP]
> **Trap 2: smaller is not automatically faster.** Each integer must be decoded before use, and decoding speed is a separate engineering target. Lemire, Kurz and Rupp report that their Stream VByte variant decodes up to twice as fast as varint-G8IU on real data sets, which is a different byte-oriented scheme. Measure decode time on your own hardware before choosing a code.

> [!TRAP]
> **Trap 3: mismatched byte conventions decode wrongly without an error.** If the flag bit is read with the opposite meaning, `10000111 01101000` yields 7 and then an unfinished integer, not 1000. Confirm the convention against the format's specification.

> [!TRAP]
> **Trap 4: synthetic numbers are a model's output.** The 2-to-4 times figure and the bucket sizes follow from the Zipf-like assumption and one random seed. A real corpus can differ in both directions. Rerun the measurement on your own postings before quoting it.

## Summary

- An inverted index maps each term to a sorted postings list, so a query reads only the lists of its own terms.
- An AND query is a two-pointer intersection. It costs at most $|p| + |q|$ comparisons, and it is correct only when both lists are sorted.
- D-gaps with VByte shrink the lists. On the synthetic corpus they cost about 1 byte per posting for common terms and about 2 for rare ones, against 4 bytes for raw IDs.
- Skip pointers help when the list lengths differ a lot, and they can cost more when the lengths are similar.

## Quiz time

### Question 1: Encoding (calculation)

Encode 300 with VByte, using this lesson's convention: flag 1 means more bytes follow. Give both bytes in binary.

<details><summary>Solution</summary>

300 = 2 × 128 + 44. The high group 2 = 0000010 gets flag 1, giving `10000010`. The low group 44 = 0101100 gets flag 0, giving `00101100`. The code produces the same two bytes for `vbyte_encode(300)`.

</details>

### Question 2: Prediction

What does the two-pointer intersection return for `[3, 5, 9]` and `[1, 5, 7, 9]`, and how many comparisons does it make?

<details><summary>Solution</summary>

The result is `[5, 9]` after 5 comparisons. The trace is: 3 against 1 advances the second list; 3 against 5 advances the first; 5 equals 5 is output; 9 against 7 advances the second list; 9 equals 9 is output. The code returns `([5, 9], 5)`.

</details>

### Question 3: Bug-spotting

A colleague's AND function returns `[10]` for the inputs `[10, 2, 7]` and `[2, 7, 10]`. What is wrong, and how do you fix it?

<details><summary>Solution</summary>

The first list is not sorted, so the two-pointer walk stops early and misses 2 and 7. The fix is to sort both lists before intersecting. Sorting `[10, 2, 7]` gives `[2, 7, 10]`, and the intersection is then `[2, 7, 10]`. An index builder should keep postings sorted by docID as it writes them, so queries never have to sort.

</details>

### Question 4: Explanation

Why does the bitmap win only for the densest bucket in the measurement?

<details><summary>Solution</summary>

A bitmap costs a fixed $N/8$ bytes per term, here 2,500 bytes, however many documents contain the term. VByte costs about one byte per gap when the gap is below 128, and the gap is about $N/\text{df}$ on average. So the two costs are similar when df is near $N/8$, and the bitmap is much worse for rare terms. The top bucket, with df between 1,000 and 6,000, sits near that crossover, which is why the two costs are nearly equal there. This is reasoning from the sizes; the code measured the buckets only.

</details>
