# Architectural Intuition & Execution Pipeline

An **Inverted Index** is the foundational data structure powering modern full-text search engines (e.g., Elasticsearch, Apache Lucene, Tantivy). While a forward index maps **Documents $\rightarrow$ Words**, an inverted index inverts this relationship to map **Terms $\rightarrow$ Postings Lists** (ordered lists of document IDs containing the term, along with term frequencies, payload metadata, and byte positions).

At production scale, inverted indices achieve sub-millisecond query latency across billions of documents by leveraging **Skip Lists**, **Delta-Encoding (VByte / SIMD-BP128)**, and **Roaring Bitmaps** for intersection operations.

---

# Why Does It Exist?

Without an inverted index, searching for keywords across a corpus of $N$ documents requires a linear full-table scan ($\mathcal{O}(N \times L)$ where $L$ is document length). For a 100-million document corpus, linear scanning takes minutes.

The inverted index reduces search complexity from $\mathcal{O}(N)$ to $\mathcal{O}(|Q| \times \log |V| + k)$ where $|Q|$ is the query length, $|V|$ is vocabulary size, and $k$ is the length of the matching postings lists.

# Low-Level Systems Anatomy & Execution Mechanics

### 1. The Postings List Structure
In C++ engines like Lucene/Tantivy, each term in the dictionary points to a multi-tier structure:

$$\text{PostingsEntry} = \{\text{doc\_id}: \text{uint32}, \text{term\_freq}: \text{uint16}, \text{positions}: [\text{uint32}], \text{offsets}: [(\text{start}, \text{end})]\}$$

### 2. Variable-Byte (VByte) Delta Compression
Storing raw 32-bit unsigned integers for sorted DocIDs ($[1000, 1004, 1010]$) wastes 4 bytes per ID. Inverted indices store **differences (d-gaps)**: $[1000, 4, 6]$. Small delta values are compressed using Variable-Byte (VByte) encoding where the MSB (Most Significant Bit) serves as a continuation flag:

| Integer Value | Binary | VByte Encoded (Hex) | Bytes Consumed |
| :--- | :--- | :--- | :--- |
| `4` | `00000100` | `0x84` (MSB=1: terminal) | **1 Byte** |
| `1000` | `00000111 11010000` | `0x07 0xD0` (MSB=0 then MSB=1) | **2 Bytes** |

# Production Implementation & Interactive Code Lab

Below is the complete, production-grade implementation with type annotations and live execution demonstration:

```python
import time
import sys
from typing import List, Dict, Tuple, Set
from collections import defaultdict
import torch

class InvertedIndex:
    """
    A class to represent an Inverted Index with postings list compression.

    Attributes:
        index (Dict[str, List[int]]): The inverted index mapping terms to document IDs.
        doc_freq (Dict[str, int]): The document frequency for each term.
        total_docs (int): The total number of documents in the corpus.
    """

    def __init__(self):
        self.index: Dict[str, List[int]] = defaultdict(list)
        self.doc_freq: Dict[str, int] = defaultdict(int)
        self.total_docs: int = 0

    def add_document(self, doc_id: int, terms: List[str]) -> None:
        """
        Add a document to the inverted index.

        Args:
            doc_id (int): The ID of the document.
            terms (List[str]): The list of terms in the document.
        """
        unique_terms: Set[str] = set(terms)
        for term in unique_terms:
            self.index[term].append(doc_id)
            self.doc_freq[term] += 1
        self.total_docs += 1

    def compress_postings(self) -> None:
        """
        Compress the postings lists using delta encoding and PyTorch tensors.
        """
        for term in self.index:
            postings = self.index[term]
            postings.sort()
            delta_encoded = [postings[0]]
            for i in range(1, len(postings)):
                delta_encoded.append(postings[i] - postings[i-1])
            self.index[term] = torch.tensor(delta_encoded, dtype=torch.int32)

    def search(self, term: str) -> List[int]:
        """
        Search for a term in the inverted index.

        Args:
            term (str): The term to search for.

        Returns:
            List[int]: The list of document IDs containing the term.
        """
        if term not in self.index:
            return []
        postings = self.index[term]
        if isinstance(postings, torch.Tensor):
            postings = postings.tolist()
            doc_ids = [postings[0]]
            for i in range(1, len(postings)):
                doc_ids.append(doc_ids[i-1] + postings[i])
            return doc_ids
        return postings

    def get_doc_freq(self, term: str) -> int:
        """
        Get the document frequency for a term.

        Args:
            term (str): The term to get the document frequency for.

        Returns:
            int: The document frequency for the term.
        """
        return self.doc_freq.get(term, 0)

    def get_memory_footprint(self) -> int:
        """
        Get the memory footprint of the inverted index in bytes.

        Returns:
            int: The memory footprint of the inverted index in bytes.
        """
        memory_footprint = 0
        for term in self.index:
            memory_footprint += sys.getsizeof(term)
            postings = self.index[term]
            if isinstance(postings, torch.Tensor):
                memory_footprint += postings.element_size() * postings.nelement()
            else:
                memory_footprint += sys.getsizeof(postings)
        memory_footprint += sys.getsizeof(self.doc_freq)
        return memory_footprint

if __name__ == "__main__":
    # Example usage
    documents = [
        ("doc1", ["apple", "banana", "cherry"]),
        ("doc2", ["banana", "date", "fig"]),
        ("doc3", ["apple", "cherry", "date"]),
        ("doc4", ["banana", "fig", "grape"]),
        ("doc5", ["apple", "banana", "cherry", "date", "fig"])
    ]

    inverted_index = InvertedIndex()

    start_time = time.time()
    for doc_id, terms in documents:
        inverted_index.add_document(doc_id, terms)
    print(f"Time to build inverted index: {time.time() - start_time:.4f} seconds")

    start_time = time.time()
    inverted_index.compress_postings()
    print(f"Time to compress postings lists: {time.time() - start_time:.4f} seconds")

    print("\nInverted Index:")
    for term in inverted_index.index:
        print(f"{term}: {inverted_index.search(term)}")

    print("\nDocument Frequencies:")
    for term in inverted_index.index:
        print(f"{term}: {inverted_index.get_doc_freq(term)}")

    print(f"\nMemory footprint: {inverted_index.get_memory_footprint()} bytes")

    # Search for a term
    term_to_search = "banana"
    start_time = time.time()
    doc_ids = inverted_index.search(term_to_search)
    print(f"\nTime to search for '{term_to_search}': {time.time() - start_time:.4f} seconds")
    print(f"Documents containing '{term_to_search}': {doc_ids}")
```

# Hard-Won Production Traps & Antipatterns

> [!TRAP]
> **Trap 1: Intersecting Longest Postings Lists First**
> Always order query terms by ascending postings length before running two-pointer intersection. Intersecting the smallest list first ensures that non-matching candidate sets are pruned in $\mathcal{O}(\min(|L_1|, |L_2|))$ operations instead of scanning millions of document entries.

> [!TRAP]
> **Trap 2: Storing Absolute DocIDs Without D-Gaps**
> Storing raw 32-bit integer arrays on disk causes massive memory bandwidth saturation during high-QPS search spikes. Always use delta compression (VByte, SIMD-BP128, or Roaring Bitmaps).

# Systems Benchmarking & Performance Profile

| Operation | Time Complexity | Space Complexity |
| :--- | :--- | :--- |
| **Dictionary Lookup** | $\mathcal{O}(|T|)$ via FST / Radix Tree | $\mathcal{O}(|V| \times \text{avg\_term\_len})$ |
| **2-List Intersection (Uncompressed)** | $\mathcal{O}(|L_1| + |L_2|)$ | $\mathcal{O}(1)$ working memory |
| **2-List Intersection with Skip Pointers** | $\mathcal{O}(\sqrt{|L_1|} + \sqrt{|L_2|})$ | $\mathcal{O}(1)$ |
| **VByte Compression Ratio** | $\approx 70\% - 85\%$ size reduction vs 32-bit uints | $\approx 1.2\text{ bytes/doc\_id}$ |

# Real-World Frontier AI Connection

> [!AI]
> **Hybrid Search & BM25 in Modern RAG Pipelines**
> Dense vector search (HNSW / FAISS) excels at semantic understanding but frequently fails on exact alphanumeric queries (e.g., error codes `ERR_404_OOM`, part numbers `H100-SXM5-80GB`). Modern production RAG architectures (Cohere, Vespa, Pinecone, Azure AI Search) combine **Inverted Index BM25 search** with **Dense Embedding Search** using Reciprocal Rank Fusion (RRF):
> $$\text{RRF\_Score}(d) = \sum_{m \in \{\text{dense}, \text{lexical}\}} \frac{1}{60 + \text{rank}_m(d)}$$
