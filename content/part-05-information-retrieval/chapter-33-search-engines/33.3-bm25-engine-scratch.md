By the end you will be able to build a BM25 search engine in about 50 lines of standard-library Python, using an inverted index, and check its scores against a brute-force scorer. You will also measure how the work grows with the size of the collection.

**You need:** the BM25 formula and its IDF convention (Lesson 33.2), and the idea of a postings list (Lesson 33.1). Everything here uses only the standard library.

## The problem the index solves

The first search engine most people write is a loop. For each document, count each query term in it, and combine the counts with the BM25 formula. That is correct, and it is slow. Each query term forces a pass over every token of every document. Over 50,000 documents with a median of 100 tokens each, one three-term query compares about 17 million tokens (measured below; the mean document length in that synthetic corpus is about 113).

Most documents contain none of the query terms, so most of that work is wasted. An inverted index stores, for each term, only the documents that contain it. A query then reads only those lists.

![Scanning every document versus walking the postings of the query terms, on the three toy documents](diagrams/33.3-scan-vs-postings.svg "Scanning costs every token; the index costs only the matching postings.")

## The index: a dictionary of postings lists

The index maps each term to a list of `(doc_id, tf)` pairs, one per document that contains the term, in `doc_id` order. The length of that list is the document frequency $n$, which the IDF needs. At query time the engine also needs each document's length, which it stores once.

![The inverted index of the toy corpus: each query term points to its postings list, and the list length is the document frequency](diagrams/33.3-index-layout.svg "Amber rows are the query terms. A query reads only those lists.")

## Worked example by hand

Take the three toy documents, lowercased and split into tokens. Their lengths are 9, 16 and 7, so $N = 3$ and $\mathrm{avgdl} = 32/3 \approx 10.6667$. Use $k_1 = 1.5$ and $b = 0.75$. Lesson 33.2 quotes Lucene's default $k_1 = 1.2$; the $k_1 = 1.5$ used here is a choice for this lesson, not a default.

The query "quick brown fox" has $n = 2$ for each term. The IDF convention from Lesson 33.2 gives

$$
\mathrm{IDF} = \log\!\left(\frac{N - n + 0.5}{n + 0.5} + 1\right) = \log(0.6 + 1) = \log 1.6 \approx 0.4700.
$$

The length factor is $K_d = k_1\,(1 - b + b\,|d|/\mathrm{avgdl})$, which gives $K_0 \approx 1.3242$ and $K_1 \approx 2.0625$. For a term that occurs $tf$ times, the saturated tf part is $tf\,(k_1 + 1)/(tf + K_d)$.

- Doc 0, $tf = 1$: $1 \times 2.5 / (1 + 1.3242) \approx 1.0756$. Each query term adds $0.4700 \times 1.0756 \approx 0.5055$, and three terms give 1.5167.
- Doc 1, $tf = 2$: $2 \times 2.5 / (2 + 2.0625) \approx 1.2308$. Each term adds $0.5785$, and three terms give 1.7354.
- Doc 2 contains no query term, so its score is 0.

Doc 1 scores higher because it repeats each term, but saturation means two occurrences are worth 1.2308 units, not twice the 1.0756 of one occurrence. Its length (16 tokens) pulls the score down, so the gain is modest.

## Code: the engine

The block below is the whole engine and a toy run. It uses only `re`, `math`, `heapq` and `collections`, so it runs unchanged in the browser.

```python
import heapq
import math
import re
from collections import Counter, defaultdict
from operator import itemgetter

TOKEN = re.compile(r"[a-z0-9]+")

def tokenize(text):
    return TOKEN.findall(text.lower())   # lowercase first: "The" and "the" become one token

class BM25Index:
    def __init__(self, k1=1.5, b=0.75):
        self.k1, self.b = k1, b
        self.postings = defaultdict(list)   # term -> [(doc_id, tf), ...] in doc_id order
        self.doc_len = []
        self.built = False

    def add(self, text):
        tokens = tokenize(text)
        doc_id = len(self.doc_len)
        self.doc_len.append(len(tokens))
        for term, tf in Counter(tokens).items():
            self.postings[term].append((doc_id, tf))
        self.built = False

    def build(self):
        """Precompute per-document and per-term values once, after all add() calls."""
        self.N = len(self.doc_len)
        self.avgdl = sum(self.doc_len) / self.N
        # K[d] = k1 * (1 - b + b * |d| / avgdl): the length-normalisation term of document d
        self.K = [self.k1 * (1 - self.b + self.b * n / self.avgdl) for n in self.doc_len]
        # IDF as in Lesson 33.2: log((N - n + 0.5) / (n + 0.5) + 1). Always > 0.
        self.idf = {t: math.log((self.N - len(p) + 0.5) / (len(p) + 0.5) + 1)
                    for t, p in self.postings.items()}
        self.built = True

    def accumulate(self, query):
        """Return {doc_id: score} for documents containing at least one query term."""
        assert self.built, "call build() after the last add()"
        scores = defaultdict(float)
        for term in tokenize(query):
            if term not in self.postings:
                continue
            w = self.idf[term] * (self.k1 + 1)
            for doc_id, tf in self.postings[term]:
                scores[doc_id] += w * tf / (tf + self.K[doc_id])
        return scores

    def search(self, query, k=3):
        return heapq.nlargest(k, self.accumulate(query).items(), key=itemgetter(1))


docs = [
    "The quick brown fox jumps over the lazy dog",
    "The quick brown fox jumps over the lazy dog and the quick brown fox jumps again",
    "The lazy dog sleeps in the sun",
]
index = BM25Index()
for d in docs:
    index.add(d)
index.build()
print("N =", index.N, "avgdl =", round(index.avgdl, 4))
print("postings['fox'] =", index.postings["fox"])
print("idf['fox'] =", round(index.idf["fox"], 4))
for doc_id, score in index.search("quick brown fox"):
    print(f"doc {doc_id}: {score:.4f}")
```

```output
N = 3 avgdl = 10.6667
postings['fox'] = [(0, 1), (1, 2)]
idf['fox'] = 0.47
doc 1: 1.7354
doc 0: 1.5167
```

Three choices make this fast. First, `build()` computes the length factor $K_d$ and the IDF for every term once, so the query loop does not recompute them. Second, `accumulate()` visits only the postings of the query terms, and the accumulator is a dictionary, so documents that match nothing never enter it. Third, `search()` keeps the top $k$ with `heapq.nlargest`. Note that this engine ranks with OR semantics: a document gets a score if it contains any one query term. The AND intersection of Lesson 33.1 is a different operation and is not used here. The Python documentation states that this is equivalent to `sorted(..., reverse=True)[:n]` but does not specify the order of ties, so do not rely on a particular order between documents with exactly equal scores.

## Checking the engine against a brute-force scorer

A fast engine is only useful if it returns the same scores as the slow one. The benchmark below contains a brute-force scorer that rescans every document for every term, and compares it with the index on 1,000 synthetic documents and 30 queries. The two scorers share one IDF dictionary, so this test checks the accumulation, not the IDF formula; the IDF was checked by hand above.

The synthetic corpus draws words from a Zipf distribution, in which the word of rank $r$ has weight $1/(r+1)$. Natural text is roughly Zipf-shaped, which is why common words have long postings lists; that is a standard empirical observation, not one this lesson checks.

<details><summary>Run locally: stdlib only, about 10 s. Save the engine block above as engine.py first</summary>

```python
import math, random, time, platform, sys
from engine import BM25Index, tokenize

V = 20_000
cum, total = [], 0.0
for rank in range(V):                       # Zipf: the word of rank r has weight 1/(r+1)
    total += 1.0 / (rank + 1)
    cum.append(total)
vocab = [f"w{r}" for r in range(V)]

def make_corpus(n, seed):
    rng = random.Random(seed)
    docs = []
    for _ in range(n):
        length = max(5, int(rng.lognormvariate(math.log(100), 0.5)))
        docs.append(" ".join(rng.choices(vocab, cum_weights=cum, k=length)))
    return docs

def make_queries(n, seed):
    rng = random.Random(seed)
    return [" ".join(f"w{rng.randrange(50, 5000)}" for _ in range(3)) for _ in range(n)]

def naive_scores(doc_tokens, query, idf, k1=1.5, b=0.75):
    """First-version approach: rescan every document's tokens for every query term."""
    lens = [len(d) for d in doc_tokens]
    avg = sum(lens) / len(lens)
    terms = tokenize(query)
    out = []
    for d, n in zip(doc_tokens, lens):
        K = k1 * (1 - b + b * n / avg)
        s = 0.0
        for t in terms:
            if t in idf:
                tf = d.count(t)
                s += idf[t] * tf * (k1 + 1) / (tf + K)
        out.append(s)
    return out

print("python", sys.version.split()[0], platform.machine(), platform.system())

# verification: N = 1000, 30 queries
texts = make_corpus(1000, seed=1)
index = BM25Index()
for t in texts:
    index.add(t)
index.build()
doc_tokens = [tokenize(t) for t in texts]
max_err, mismatches = 0.0, 0
for q in make_queries(30, seed=2):
    acc = index.accumulate(q)
    naive = naive_scores(doc_tokens, q, index.idf)
    for i, s in enumerate(naive):
        max_err = max(max_err, abs(acc.get(i, 0.0) - s))
    top_index = [i for i, _ in index.search(q, 10)]
    top_naive = [i for i, _ in sorted([(i, s) for i, s in enumerate(naive) if s > 0],
                                      key=lambda x: -x[1])[:10]]
    mismatches += top_index != top_naive
print(f"verification N=1000, 30 queries: max abs score difference = {max_err:.3g}, top-10 list mismatches = {mismatches}")

# scaling: 200 queries per size (naive: 20 or 5 queries, because it is slow)
print("N, build_s, naive_ms_per_query, index_ms_per_query, postings_per_query, naive_token_comparisons_per_query")
for n in (1_000, 10_000, 50_000):
    texts = make_corpus(n, seed=n)
    t0 = time.perf_counter()
    index = BM25Index()
    for t in texts:
        index.add(t)
    index.build()
    build_s = time.perf_counter() - t0
    doc_tokens = [tokenize(t) for t in texts]
    queries = make_queries(200, seed=99)
    postings = sum(sum(len(index.postings[t]) for t in tokenize(q) if t in index.postings) for q in queries) / len(queries)
    naive_work = sum(len(d) for d in doc_tokens) * 3
    nq = 20 if n <= 1000 else 5
    t0 = time.perf_counter()
    for q in queries[:nq]:
        naive_scores(doc_tokens, q, index.idf)
    naive_ms = (time.perf_counter() - t0) / nq * 1000
    t0 = time.perf_counter()
    for q in queries:
        index.search(q, 10)
    index_ms = (time.perf_counter() - t0) / len(queries) * 1000
    print(f"{n}, {build_s:.3f}, {naive_ms:.2f}, {index_ms:.3f}, {postings:.1f}, {naive_work}")
```

A second run of the same script gave 0.53 ms per query for the index and 186.90 ms for the naive scorer at 50,000 documents, so the timings vary between runs and will differ on your machine. ## Measured scaling

The table summarises the run above. The brute-force scorer does $\sum_d |d| \times 3$ token comparisons per query, because `list.count` scans the whole token list of every document. The index touches only the postings of the three query terms.

| N | naive ms per query | index ms per query | postings touched per query | naive token comparisons per query |
|---|---|---|---|---|
| 1,000 | 3.34 | 0.014 | 29.6 | 329,133 |
| 10,000 | 36.02 | 0.106 | 298.1 | 3,357,519 |
| 50,000 | 186.59 | 0.658 | 1,499.2 | 16,918,815 |

![Log-scale bars of token comparisons for the naive scan and postings entries touched for the index, at three corpus sizes](diagrams/33.3-work-chart.svg "Counts from one run, plotted on a log scale. The gap widens with N.")

At 50,000 documents the naive scorer does about 11,300 times more token comparisons than the index touches postings, and the time ratio was 280 to 350 times across the two runs on this machine. The time gap is smaller because `list.count` runs in C, one token at a time, while the index loop runs Python bytecode once per posting. Comparisons measure how much work each method does; time also includes the cost per unit of work, which depends on the language and the machine.

The postings count grows with $N$ (30, 298, 1,499), because a fixed term's document frequency grows with the collection. So the index is still linear in $N$, with a much smaller constant. The query terms here were drawn from Zipf ranks 50 to 5,000, which are fairly common words with long lists. Production engines reduce this cost further with techniques such as dynamic pruning, which this lesson does not implement.

## Common traps

> [!TRAP]
> The unshifted IDF $\log\bigl((N - n + 0.5)/(n + 0.5)\bigr)$ is negative whenever a term occurs in more than half the documents. For the toy corpus it gives $\log 0.6 \approx -0.5108$ and scores of $-1.6484$ and $-1.8861$. The "+1 inside the log" form used here is always positive, and it is the form Lucene's BM25 implementation documents.

> [!TRAP]
> `str.split()` without lowercasing treats "The" and "the" as different tokens. In doc 0 the term "the" has tf 1 with `split()` and tf 2 after lowercasing, so every score changes silently. Normalise the text before counting.

> [!TRAP]
> Adding documents after `build()` leaves $N$, avgdl, the length factors and the IDF table out of date. The engine avoids this by resetting `built` in `add()` and asserting in `accumulate()`. An engine without that check ranks with stale statistics and gives no error.

> [!TRAP]
> The accumulator contains only documents that match at least one query term. If you sort all $N$ documents by score, the zero-score documents are tied, and their order is arbitrary. Compare engines on the non-zero scores, as the verification above does.

> [!TRAP]
> A 280 to 350-fold speedup on one machine is not a constant. Scaling claims should rest on operation counts, which are the same on every machine, and timings should be measured on your own hardware with the same corpus.

## Summary

- A postings index reads only the lists of the query terms, so the work depends on the matching documents, not on the whole collection.
- Precomputing the length factor and the IDF in `build()` keeps the inner loop to a multiply, a divide and an accumulate per posting.
- Check a fast engine against a brute-force scorer on the same corpus, and compare operation counts as well as time.
- Use the "+1 inside the log" IDF; the unshifted form goes negative for common terms.

## Quiz time

### Question 1: Calculation. In the toy corpus, what is the tf part for doc 1 if the query term occurs once instead of twice?

Use $tf\,(k_1+1)/(tf+K_1)$ with $K_1 \approx 2.0625$ and $tf = 1$.

<details><summary>Show solution</summary>

$1 \times 2.5 / (1 + 2.0625) = 2.5 / 3.0625 \approx 0.8163$. Compare with 1.2308 at $tf = 2$: saturation means doubling the count raises the tf part by about 51 percent, not 100 percent.

</details>

### Question 2: Prediction. A term appears in 90 of 100 documents. What is the sign of its unshifted IDF, and of the "+1" IDF?

<details><summary>Show solution</summary>

Unshifted: $\log\bigl((100 - 90 + 0.5)/(90 + 0.5)\bigr) = \log(10.5/90.5) \approx \log(0.116) \approx -2.15$, which is negative. "+1" form: $\log(0.116 + 1) \approx 0.110$, which is positive. Negative weights would make a very common word reduce a document's score.

</details>

### Question 3: Bug-spotting. A colleague calls `add()` for 1,000 more documents, then calls `search()` without calling `build()`. What happens, and why?

<details><summary>Show solution</summary>

`add()` sets `built = False`, so `accumulate()` raises `AssertionError` with the message "call build() after the last add()". Without that check, the search would use the old $N$, avgdl and K list, and the new documents' lengths would not be in the normalisation, so scores would be wrong without any error.

</details>

### Question 4: Explanation. Why does the index touch 6 postings entries for the toy query, while the naive scan does 96 token comparisons?

<details><summary>Show solution</summary>

The index reads the postings lists of "quick", "brown" and "fox", each with two entries, so $3 \times 2 = 6$. The naive scan reads every token of all three documents, $9 + 16 + 7 = 32$, once per query term, so $32 \times 3 = 96$. The gap comes from skipping documents that do not contain the query terms.

</details>
