A dense embedding turns a whole sentence into one fixed-length vector, so that a search engine can rank documents by a single dot product. In this lesson you will see why retrieval systems encode queries and documents separately (a *bi-encoder*), how mean pooling turns per-token vectors into one sentence vector, and what this design costs and buys compared with a cross-encoder.

**You need:** token embeddings (Lesson 24.1) and the attention block (Lesson 25.1). Dot products and cosine similarity from linear algebra.

## The problem: keyword matching misses synonyms

A search for "a kitten sleeps" should find "the cat sleeps on the sofa". Lexical methods such as BM25 (Best Matching 25, a word-overlap ranking function) score only shared words. "kitten" and "cat" share no letters, so the match is missed. A dense retriever instead represents every text as a vector and ranks by similarity between vectors. Synonyms can end up close together because the encoder learned that they occur in similar contexts.

The catch is cost. A ranking model must score the query against every document. The architecture decides how expensive that is.

## Two architectures

A **cross-encoder** feeds the query and the document into one Transformer together, as `[CLS] query [SEP] doc`, and reads a score from the output. Every token of the query can attend to every token of the document, so it is accurate. But each (query, document) pair needs its own forward pass.

A **bi-encoder** runs the same encoder on the query and on the document separately. The two vectors meet only at the end, through a cosine similarity. The document vectors do not depend on the query, so they are computed once, offline, and stored.

![A cross-encoder reads query and document in one pass and outputs a score; a bi-encoder encodes each text separately with the same weights and compares the two vectors with cosine similarity](diagrams/34.1-two-architectures.svg "Cross-encoder versus bi-encoder. The bi-encoder's document side is cached.")

Sentence-BERT (Reimers and Gurevych, 2019) fine-tuned BERT (Bidirectional Encoder Representations from Transformers) into this siamese form and compared the outputs with cosine similarity. The abstract reports that finding the most similar pair among 10,000 sentences falls from about 65 hours with BERT to about 5 seconds with Sentence-BERT. The full paper gives the hardware and protocol, which I have not checked. Dense Passage Retrieval (Karpukhin et al., 2020) uses the same dual-encoder idea for open-domain question answering. Its abstract reports 9–19 points of absolute top-20 accuracy over a BM25 baseline.

## From token vectors to one sentence vector

An encoder outputs one vector per token: for $L$ tokens of dimension $d$, a matrix $H \in \mathbb{R}^{L \times d}$. Retrieval needs a single vector. **Mean pooling** averages the rows of $H$ that are real tokens, using the attention mask $m_i \in \{0, 1\}$ (1 for a real token, 0 for padding):

$$
v = \frac{\sum_{i=1}^{L} m_i\, h_i}{\sum_{i=1}^{L} m_i}, \qquad \hat{v} = \frac{v}{\lVert v \rVert_2}
$$

Padding exists because a batch of sentences is stored as a rectangle, and the short ones are filled up with `[PAD]` tokens. If the mask is ignored, those pad rows leak into every sentence vector. The sentence-transformers `Pooling` module with `mode="mean"` (its default) multiplies by the mask, sums, and divides by the count of unmasked tokens; I read this in the library source, not by running it.

![A 4-by-2 table of token states with a mask column; the pad row is excluded, giving the masked mean (3, 2), and including it would give (4.5, 3.75)](diagrams/34.1-mean-pooling.svg "Mean pooling. The pad row is excluded by the mask.")

The final division by $\lVert v \rVert_2$ puts every sentence vector on the unit sphere. For unit vectors, cosine similarity equals the dot product, so the whole retrieval step reduces to matrix multiplication.

## Worked example, by hand, with NumPy

Three real token vectors and one pad row, in two dimensions. The mask is $m = (1, 1, 1, 0)$.

- Sum of real rows: $(1+3+5,\ 2+0+4) = (9, 6)$.
- Divide by the 3 real tokens: $v = (3, 2)$.
- Length: $\lVert v \rVert_2 = \sqrt{13} \approx 3.606$, so $\hat{v} \approx (0.832, 0.555)$.

Without the mask, the average is $(18, 15)/4 = (4.5, 3.75)$, which is a different vector. The code below reproduces the numbers and then compares two similarity measures on purpose-chosen vectors.

```python
import numpy as np

# Token states for "cat naps warm [PAD]": 3 real tokens and 1 padding token, 2 dimensions each
H = np.array([[1.0, 2.0],
              [3.0, 0.0],
              [5.0, 4.0],
              [9.0, 9.0]])          # last row is [PAD]
mask = np.array([1.0, 1.0, 1.0, 0.0])

plain = H.mean(axis=0)                                    # average over every row, pad included
masked = (H * mask[:, None]).sum(axis=0) / mask.sum()     # average over real tokens only

print("sum of real rows:", (H * mask[:, None]).sum(axis=0))
print("real tokens     :", mask.sum())
print("masked mean     :", masked)
print("plain mean      :", plain)

# Normalise to length 1, so cosine similarity is a plain dot product
unit = masked / np.linalg.norm(masked)
print("unit vector     :", np.round(unit, 4), " length =", round(float(np.linalg.norm(unit)), 4))

print()
q = np.array([1.0, 0.0])
d1 = np.array([0.6, 0.0])                 # short, same direction as q
d2 = np.array([2.0, 1.0])                 # long, partly off-direction
for name, d in [("d1", d1), ("d2", d2)]:
    dot = q @ d
    cos = dot / (np.linalg.norm(q) * np.linalg.norm(d))
    print(f"{name}: dot = {dot:.2f}  cos = {cos:.4f}")
```

```output
sum of real rows: [9. 6.]
real tokens     : 3.0
masked mean     : [3. 2.]
plain mean      : [4.5  3.75]
unit vector     : [0.8321 0.5547]  length = 1.0

d1: dot = 0.60  cos = 1.0000
d2: dot = 2.00  cos = 0.8944
```

![Dot product of 0.6 for the short vector and 2.0 for the long one, against cosine 1.000 and 0.894: the dot product picks the long vector, cosine picks the aligned one](diagrams/34.1-cosine-dot.svg "Dot product versus cosine. Normalising removes the length term.")

Use cosine (or normalise first) when you want direction, not length. An unnormalised dot product would rank $d_2$ above $d_1$ even though $d_1$ points exactly along the query.

## A complete bi-encoder retriever, in NumPy

The encoder below is a stub, not a Transformer. Each word gets an 8-dimensional vector from a positive-PMI (pointwise mutual information) matrix of sentence co-occurrence, reduced by SVD (singular value decomposition). A sentence vector is the mean of its word vectors, then normalised. The pipeline is the real one: encode the corpus once, encode each query, multiply, take the top results. The corpus has 24 sentences in three topics (pets, cooking, finance), and each query has a topic label.

```python
import re
import numpy as np

np.set_printoptions(precision=3, suppress=True)

DOCS = [
    "the cat sleeps on the sofa", "a kitten naps in the warm sun", "the dog runs in the park",
    "a puppy plays with a ball in the park", "my cat chases a mouse", "the dog barks at the mailman",
    "bake the bread in a hot oven", "boil the pasta in salted water", "add salt and pepper to the soup",
    "roast the vegetables in the oven", "stir the sauce until it thickens", "fresh bread needs flour and yeast",
    "the bank raised the interest rate", "deposit money into a savings account", "the stock price fell after earnings",
    "investors sold shares of the company", "the loan carries a monthly interest charge", "check your account balance online",
    "the cat drinks milk from a bowl", "a small dog wags its tail", "kittens and puppies need vaccines",
    "the vet checked the cat and the dog", "knead the dough and let it rise", "simmer the soup for twenty minutes",
]
TOPIC = ["pets"] * 6 + ["cooking"] * 6 + ["finance"] * 6 + ["pets"] * 4 + ["cooking"] * 2
QUERIES = [
    ("a kitten sleeps", "pets"), ("a puppy runs outside", "pets"),
    ("baking dough in an oven", "cooking"), ("salt for the soup", "cooking"),
    ("where to put money for interest", "finance"), ("stock market shares", "finance"),
]

def tokenize(text):
    return re.findall(r"[a-z]+", text.lower())

# Word vectors from sentence co-occurrence: positive PMI, then truncated SVD to 8 dimensions.
# This is a stand-in for a trained encoder's token states, not a Transformer.
vocab = sorted({t for d in DOCS for t in tokenize(d)})
w2i = {w: i for i, w in enumerate(vocab)}
C = np.zeros((len(vocab), len(vocab)))
for d in DOCS:
    ids = [w2i[t] for t in tokenize(d)]
    for a in ids:
        for b in ids:
            if a != b:
                C[a, b] += 1
total = C.sum()
row = C.sum(axis=1, keepdims=True)
ppmi = np.maximum(np.log((C * total) / (row @ row.T + 1e-12) + 1e-12), 0)
U, S, _ = np.linalg.svd(ppmi)
TOKEN_VEC = U[:, :8] * np.sqrt(S[:8])

def encode(texts):
    """Mean-pool token states over real tokens (the mask), then L2-normalise."""
    out = []
    for s in texts:
        ids = [w2i[t] for t in tokenize(s) if t in w2i]   # unknown words are dropped
        H = TOKEN_VEC[ids]
        v = H.mean(axis=0)
        out.append(v / np.linalg.norm(v))
    return np.array(out)

D = encode(DOCS)                       # encoded once, offline
print("document matrix D:", D.shape)

def lexical(q, docs):
    qs = set(tokenize(q))
    return np.array([len(qs & set(tokenize(d))) for d in docs])

def precision_at_3(scores, topic):
    top = np.argsort(-scores, kind="stable")[:3]
    return float(np.mean([TOPIC[i] == topic for i in top]))

dense_p, lex_p = [], []
for q, topic in QUERIES:
    cos = D @ encode([q])[0]           # one matrix-vector product
    lex = lexical(q, DOCS)
    top = np.argsort(-cos, kind="stable")[:3]
    dense_p.append(precision_at_3(cos, topic))
    lex_p.append(precision_at_3(lex + 1e-6 * cos, topic))
    print(f"{q!r:34s} dense top-3 topics: {[TOPIC[i] for i in top]}  overlap: {[int(lex[i]) for i in top]}")
print("P@3 dense :", round(np.mean(dense_p), 3))
print("P@3 lexical:", round(np.mean(lex_p), 3))
```

```output
document matrix D: (24, 8)
'a kitten sleeps'                  dense top-3 topics: ['pets', 'pets', 'pets']  overlap: [1, 1, 0]
'a puppy runs outside'             dense top-3 topics: ['pets', 'pets', 'pets']  overlap: [2, 1, 1]
'baking dough in an oven'          dense top-3 topics: ['cooking', 'cooking', 'cooking']  overlap: [2, 2, 1]
'salt for the soup'                dense top-3 topics: ['cooking', 'cooking', 'pets']  overlap: [3, 3, 1]
'where to put money for interest'  dense top-3 topics: ['cooking', 'cooking', 'pets']  overlap: [1, 1, 0]
'stock market shares'              dense top-3 topics: ['finance', 'finance', 'finance']  overlap: [1, 1, 0]
P@3 dense : 0.778
P@3 lexical: 0.833
```

The stub gets 14 of 18 top-3 slots right (precision at 3, P@3 = 0.778), and plain word overlap gets 15 of 18 (0.833). This is a negative result, and it is the most important line in the lesson. The architecture decides how comparisons are made and what they cost. It does not decide whether the vectors mean anything. A bi-encoder is only as good as its training. Here the co-occurrence vectors are too crude, and the query "where to put money for interest" retrieves cooking sentences. I have not investigated why. One guess is that mean pooling gives function words such as "the" and "for" as much weight as content words. That guess is untested.

## Cost: where the bi-encoder wins

Count the expensive operations per query over $N$ documents. A cross-encoder runs $N$ encoder passes. A bi-encoder runs one encoder pass for the query, and then $N$ dot products of length $d$, which are cheap and can be batched into one matrix-vector product.

![Work per query at one million documents: the cross-encoder needs 1,000,000 encoder passes; the bi-encoder needs 1 encoder pass and 1,000,000 dot products, about 7.68 × 10^8 multiply-adds at d = 768](diagrams/34.1-cost.svg "Counts per query. The dot-product count assumes d = 768, a common width for base-size encoders.")

The cross-encoder is not wasteful. It sees both texts at once, so it can model interactions between query and document tokens that a bi-encoder's single pooled vector must compress. Use the bi-encoder to shortlist from a large corpus, and a cross-encoder to re-rank the shortlist. Chapter 35 (vector search) covers indexes that avoid scoring every document.

## Common traps

> [!TRAP]
> **Padding leaks into the vector.** `H.mean(axis=0)` over a padded batch averages `[PAD]` rows too. The example above moved the sentence vector from $(3, 2)$ to $(4.5, 3.75)$. Always multiply by the mask before summing.

> [!TRAP]
> **Dot product instead of cosine.** Unnormalised vectors let long documents win. Normalise, or say explicitly which similarity your index uses. The two are equal only for unit vectors.

> [!TRAP]
> **Re-encoding the corpus on every query.** The bi-encoder's advantage exists only if the document vectors are cached. Encoding 1,000,000 documents per query gives back the cross-encoder's cost.

> [!TRAP]
> **Mismatched query and document encoding.** Some trained models expect a prompt or instruction on one side only. Use the model card's recipe for each side. I did not check any specific model's recipe here.

> [!TRAP]
> **Judging an architecture by a weak encoder.** The stub above loses to word overlap. A bad result from a poorly trained encoder says nothing about the bi-encoder design, and a good result from a strong one says nothing about its ceiling.

## Summary

- A bi-encoder encodes query and document separately into vectors and scores them with cosine similarity, so document vectors can be cached.
- A cross-encoder reads the pair together, which is more accurate but costs one encoder pass per document.
- Mean pooling averages real-token vectors under an attention mask, then normalises; without the mask, pad tokens distort the result.
- For unit vectors, cosine similarity equals the dot product, so retrieval is one matrix-vector product.
- The architecture sets the cost. The training sets the quality, and a weak encoder can lose to word overlap.

## Quiz time

### Question 1: Calculation

Two real tokens with vectors $(2, 4)$ and $(4, 0)$, followed by one `[PAD]` row $(9, 9)$, with mask $(1, 1, 0)$. What is the masked mean-pooled vector, and what is the unmasked mean?

<details><summary>Solution</summary>

Masked: $((2+4)/2,\ (4+0)/2) = (3, 2)$. Unmasked: $((2+4+9)/3,\ (4+0+9)/3) = (5,\ 4.33)$. The pad row changes both coordinates.

</details>

### Question 2: Prediction

A system embeds 1,000,000 documents and answers 100 queries per second with a bi-encoder. A colleague proposes switching to a cross-encoder for better accuracy. Roughly how many encoder passes per query does each design need, and what changes in the online cost?

<details><summary>Solution</summary>

The bi-encoder needs 1 encoder pass per query, plus 1,000,000 dot products against cached vectors. The cross-encoder needs 1,000,000 encoder passes per query, one per pair. The online cost grows by about six orders of magnitude in encoder passes, which is why cross-encoders are usually used to re-rank a short list.

</details>

### Question 3: Bug-spotting

A retriever normalises sentence vectors, but the code computes `scores = D @ q` with `q` unnormalised and `D` normalised. A reviewer says the ranking is still correct. Is the reviewer right?

<details><summary>Solution</summary>

Yes, for ranking within one query. Scaling $q$ by a positive constant multiplies every score by the same number, so the order does not change. The reported score values are scaled, though, so any threshold on absolute similarity would break. The cleaner fix is to normalise both sides.

</details>

### Question 4: Explanation

Why does the bi-encoder allow an offline index, while the cross-encoder does not?

<details><summary>Solution</summary>

In a bi-encoder, each document is encoded without reference to any query, so its vector can be computed once and stored. In a cross-encoder, the query and document pass through the network together, so the computation depends on the pair and cannot be precomputed.

</details>
