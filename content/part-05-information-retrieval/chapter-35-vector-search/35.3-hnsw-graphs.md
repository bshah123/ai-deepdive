Hierarchical Navigable Small World (HNSW) graphs answer nearest-neighbour queries by walking a graph instead of comparing the query with every stored vector. You will trace a walk by hand, build a small HNSW in NumPy, and measure how search effort trades against recall.

**You need:** the exact-versus-approximate distinction from Lesson 35.1, and Python's `heapq` module (a binary heap; `heappop` returns the smallest item).

## The problem

Exact nearest-neighbour search computes the distance from the query to all $N$ stored vectors. Our running dataset has $N = 2000$ random vectors in 16 dimensions. Brute force costs 2000 distance calls per query and always returns the true top 10. That cost grows linearly with $N$, which becomes the bottleneck when $N$ is in the millions.

An approximate method accepts a small chance of missing a true neighbour in return for fewer distance calls. We score it with two numbers:

- **recall@10**: the fraction of the true 10 nearest neighbours that the search returns, averaged over queries.
- **distance calls per query**: how many times the search computes a distance. Unlike seconds, this count does not depend on the machine.

## Intuition: walk a graph

Connect each vector to a few of its close vectors. To search, start at some node, look at its neighbours, move to the one nearest the query, and repeat until no neighbour is nearer. Each move is a **greedy hop**.

![A query q at the top right; the search starts at node A and hops along the highlighted path C, E, G, each hop to the neighbour nearest q](diagrams/35.3-greedy-hop.svg "Greedy search on one layer. Positions are illustrative; no numbers are measured here.")

A graph of short links alone is slow to cross and can trap a walk in a locally good node. HNSW stacks coarser graphs on top of the full one.

Each node draws a random top level $l$. Every node lives on layer 0. A node with $l \ge 1$ also lives on layers $1, \dots, l$, and each higher layer holds a random subset of the layer below. Upper layers have fewer nodes, so their links are longer. A search enters at one node on the top layer and descends.

![Five stacked layers with node counts: layers 4 and 3 hold one node each, layer 2 holds 24, layer 1 holds 232, layer 0 holds 2000](diagrams/35.3-layers.svg "Each layer keeps a random subset of the layer below. Counts from one build with N = 2000 and M = 8.")

The level is drawn as $l = \lfloor -\ln(U)\, m_L \rfloor$, with $U$ uniform on $(0, 1]$ and $m_L = 1/\ln M$. Then $\Pr(l \ge j) = M^{-j}$. Derivation: $l \ge j$ exactly when $-\ln U \ge j/m_L$, that is $U \le \exp(-j/m_L) = \exp(-j \ln M) = M^{-j}$. With $M = 8$, one node in eight reaches layer 1 and one in 64 reaches layer 2. The expected counts for $N = 2000$ are $250$, $31$ and $4$. The measured $232$, $24$ and $2$ (layers 3 and 4 hold one node each) are within sampling noise. The constant $m_L = 1/\ln M$ is my implementation choice. The abstract of Malkov and Yashunin says only that levels follow an exponentially decaying distribution (arXiv:1603.09320).

## Worked example by hand

Five nodes sit on a line at positions a = 0, b = 2, c = 5, d = 9 and e = 12. The links are a–b, b–c, c–d and d–e. The query is $q = 11$. From a, the nearest neighbour is b (distance 9 against 11). From b, it is c (distance 6). From c, it is d (distance 2). From d, it is e (distance 1). Node e has no neighbour nearer than itself, so the walk stops after **4 hops**.

Now add one long link, a–d. From a, node d is only 2 away, so the walk reaches d in one hop and e in a second: **2 hops**. The code reproduces both counts.

```python
def greedy_walk(start, q, neighbours, pos):
    """Hop to the neighbour nearest q until no neighbour is nearer."""
    node, path = start, [start]
    while True:
        best = min(neighbours[node], key=lambda n: abs(pos[n] - q), default=None)
        if best is None or abs(pos[best] - q) >= abs(pos[node] - q):
            return path
        node = best
        path.append(node)

pos = {"a": 0, "b": 2, "c": 5, "d": 9, "e": 12}
chain = {"a": ["b"], "b": ["a", "c"], "c": ["b", "d"], "d": ["c", "e"], "e": ["d"]}
path = greedy_walk("a", 11, chain, pos)
print("chain only :", path, "hops =", len(path) - 1)

with_shortcut = {k: list(v) for k, v in chain.items()}
with_shortcut["a"].append("d"); with_shortcut["d"].append("a")
path = greedy_walk("a", 11, with_shortcut, pos)
print("with a-d   :", path, "hops =", len(path) - 1)
```

```output
chain only : ['a', 'b', 'c', 'd', 'e'] hops = 4
with a-d   : ['a', 'd', 'e'] hops = 2
```

A long link lets one hop cover what would take several short ones. The upper layers add about $N/(M-1)$ node entries in expectation, which is $\sum_{j \ge 1} N M^{-j}$. For $M = 8$ that is 14% of layer 0; the measured build has 258 extra entries, 12.9%.

## HNSW in NumPy

The class has four parts: `search_layer` (best-first search on one layer, keeping the `ef` nearest nodes), `select` (chooses which candidates become links), `insert` (adds a node from its top level down to 0), and `search` (descends with `ef = 1`, then searches layer 0 with the requested `ef`). The demo uses only NumPy and the standard library, so it runs in the browser.

```python
import heapq, math
import numpy as np

class HNSW:
    """Minimal HNSW following Malkov & Yashunin (arXiv:1603.09320), Algorithms 1-4."""
    def __init__(self, data, M=8, efC=64, heuristic=True, seed=1):
        self.data = data
        self.M, self.M0, self.efC = M, 2 * M, efC
        self.mL = 1.0 / math.log(M)
        self.heuristic = heuristic
        self.rng = np.random.default_rng(seed)
        self.layers = []          # layers[l] = {node: [neighbours]}
        self.ep, self.top = None, -1
        self.evals = 0            # distance computations (machine-independent cost)

    def dist(self, v, i):
        self.evals += 1
        return float(np.linalg.norm(self.data[i] - v))

    def search_layer(self, q, eps, ef, lc):
        visited = set(eps)
        cand, res = [], []        # cand: min-heap; res: max-heap via negated distance
        for e in eps:
            de = self.dist(q, e)
            heapq.heappush(cand, (de, e)); heapq.heappush(res, (-de, e))
        while cand:
            dc, c = heapq.heappop(cand)
            if dc > -res[0][0]:
                break
            for e in self.layers[lc][c]:
                if e in visited:
                    continue
                visited.add(e)
                de = self.dist(q, e)
                if len(res) < ef or de < -res[0][0]:
                    heapq.heappush(cand, (de, e)); heapq.heappush(res, (-de, e))
                    if len(res) > ef:
                        heapq.heappop(res)
        return sorted((-nd, i) for nd, i in res)

    def select(self, q, cands, m):
        # cands: sorted list of (distance to q, node)
        if not self.heuristic:
            return cands[:m]
        chosen, skipped = [], []
        for dq, e in cands:
            if len(chosen) >= m:
                break
            # keep e only if it is closer to q than to every already-chosen neighbour
            if all(self.dist(self.data[e], s) >= dq for _, s in chosen):
                chosen.append((dq, e))
            else:
                skipped.append((dq, e))
        for item in skipped:                      # keepPrunedConnections: top up to m
            if len(chosen) >= m:
                break
            chosen.append(item)
        return chosen

    def insert(self, idx):
        l = int(-math.log(self.rng.random()) * self.mL)
        while len(self.layers) <= l:
            self.layers.append({})
        for lc in range(l + 1):
            self.layers[lc][idx] = []
        if self.ep is None:
            self.ep, self.top = idx, l
            return
        q = self.data[idx]
        ep = [self.ep]
        for lc in range(self.top, l, -1):          # greedy descent, ef = 1
            ep = [self.search_layer(q, ep, 1, lc)[0][1]]
        for lc in range(min(l, self.top), -1, -1):
            W = self.search_layer(q, ep, self.efC, lc)
            m_max = self.M0 if lc == 0 else self.M
            nbrs = self.select(q, W, self.M)
            self.layers[lc][idx] = [i for _, i in nbrs]
            for _, e in nbrs:
                conn = self.layers[lc][e]
                conn.append(idx)
                if len(conn) > m_max:              # shrink the neighbour's list
                    ev = self.data[e]
                    cands = sorted((self.dist(ev, c), c) for c in conn)
                    self.layers[lc][e] = [i for _, i in self.select(ev, cands, m_max)]
            ep = [i for _, i in W]
        if l > self.top:
            self.ep, self.top = idx, l

    def search(self, q, k, ef, descend=True):
        ep = [self.ep]
        if descend:
            for lc in range(self.top, 0, -1):
                ep = [self.search_layer(q, ep, 1, lc)[0][1]]
        else:
            ep = [int(self.rng.integers(len(self.data)))]   # single-layer ablation: random entry
        W = self.search_layer(q, ep, max(ef, k), 0)
        return [i for _, i in W[:k]]

def build(data, **kw):
    g = HNSW(data, **kw)
    for i in range(len(data)):
        g.insert(i)
    return g

def recall_at_k(found, truth):
    return len(set(found) & set(truth)) / len(truth)

if __name__ == "__main__":
    rng = np.random.default_rng(0)
    X = rng.standard_normal((300, 8))              # 300 points in 8 dimensions
    Q = rng.standard_normal((20, 8))               # 20 queries
    truth = [list(np.argsort(np.linalg.norm(X - q, axis=1))[:10]) for q in Q]

    g = build(X, M=8, efC=64, heuristic=True, seed=1)
    print("nodes per layer:", [len(L) for L in g.layers])
    for ef in [10, 40]:
        g.evals = 0
        rec = np.mean([recall_at_k(g.search(q, 10, ef), t) for q, t in zip(Q, truth)])
        print(f"ef={ef}: recall@10 = {rec:.2f}, distance calls per query = {g.evals / len(Q):.1f} (brute force: 300)")
```

```output

ef=40: recall@10 = 1.00, distance calls per query = 198.9 (brute force: 300)
```

`ef` is the length of the candidate list. A larger `ef` keeps more nodes alive during the walk, which costs more distance calls and raises recall. `search_layer` stops when the closest unexpanded candidate is farther than the worst kept result. That is a stopping heuristic, not a guarantee: the walk can end at a local optimum.

## What we measured

The experiment below builds one graph on $N = 2000$ vectors (16 dimensions, Gaussian, $M = 8$, `efConstruction` = 64) and runs 200 queries. Brute force is 2000 distance calls and recall 1.000.

| ef | recall@10 | distance calls per query |
|---|---|---|
| 10 | 0.802 | 170.3 |
| 20 | 0.913 | 250.3 |
| 40 | 0.980 | 394.9 |
| 80 | 1.000 | 629.6 |
| 160 | 1.000 | 961.2 |

![Recall at 10 against distance calls per query for ef from 10 to 160; the curve rises steeply and flattens near recall 1.0 by ef 80](diagrams/35.3-recall-cost.svg "Measured sweep, N = 2000. Labels show ef, recall and distance calls. Brute force would be 2000 calls.")

The smallest measured `ef` that reaches recall of at least 0.95 is `ef = 40`. It costs 394.9 calls per query, about 20% of brute force. The curve also shows diminishing returns: going from `ef = 80` to `ef = 160` adds about 330 calls and no gain in recall at three decimals.

The same construction on $N = 10000$ (100 queries, a different data seed) gives layer sizes [10000, 1269, 149, 14, 4]. At `ef = 40` it costs 480.3 calls per query, against 394.9 at $N = 2000$. A fivefold larger dataset raised the cost by 22%, while brute force rises fivefold. Two sizes cannot establish the logarithmic scaling that the abstract claims, but they show the cost growing much more slowly than $N$.

## Does the neighbour-selection rule matter?

The simple rule keeps the $M$ nearest candidates. The heuristic visits candidates in order of distance to the query and keeps one only if it is closer to the query than to every neighbour already kept. This spreads links in different directions, so a walk is less likely to circle one cluster. The abstract reports that the heuristic helps at high recall and on clustered data. The rule above is my reading of the paper's heuristic; I did not open the full text.

![Dot plot of recall at ef 40 for three graph seeds: the heuristic sits near 0.98 at 395 to 398 calls, the simple rule near 0.95 at 357 to 361 calls](diagrams/35.3-selection.svg "Same ef for both rules, three graph seeds, N = 2000. The y-axis starts at 0.90.")

At `ef = 40` the heuristic reaches recall 0.979 to 0.980 at 395 to 398 calls. The simple rule reaches 0.952 to 0.953 at 357 to 361 calls. At matched `ef`, the heuristic is better by about 2.7 points and costs about 10% more calls. This is not a cost-matched comparison: I measured only one `ef` for the simple rule. A fair claim needs a full sweep for both rules at equal cost. The data here is uniform, not clustered, which is the case where the paper reports the largest gain.

## Does the hierarchy help?

| Search setting | N | recall@10 | distance calls per query |
|---|---|---|---|
| Descent through upper layers, then layer 0 | 2000 | 0.980 | 394.9 |
| Layer 0 only, random entry node | 2000 | 0.978 | 383.0 |
| Descent through upper layers, then layer 0 | 10000 | 0.945 | 480.3 |
| Layer 0 only, random entry node | 10000 | 0.942 | 469.1 |

On this data the hierarchy does not help. The descent costs 11 to 12 extra distance calls, and recall differs by 0.002 to 0.003, which I treat as no difference: I computed no confidence intervals, and each row uses one graph seed. A single layer with $2M = 16$ links per node already navigates this data well. My reasoning, not tested here, is that the layers matter more for clustered data, much larger $N$, and queries far from the data.

## Common traps

> [!TRAP]
> Recall@10 is an average over queries. A mean of 0.98 can hide queries that miss most true neighbours. Report the spread too.

> [!TRAP]
> Distance calls are not latency. Memory access dominates many real indexes, so halving the calls may not halve the time.

> [!TRAP]
> Equal `ef` is not equal cost. Compare methods at matched cost, as in the selection experiment above, not at matched parameter values.

> [!TRAP]
> Random level draws make small graphs unrepresentative. With $N = 300$ the demo has three layers and the top layer holds two nodes. Do not read a pattern into a few hundred points.

> [!TRAP]
> The data is Gaussian in 16 dimensions. Real embeddings have lower intrinsic dimension and cluster structure, so these curves are not a production forecast.

## Summary

- Brute force costs $N$ distance calls per query. Graph search trades a small recall loss for far fewer calls.
- Each node gets a random top level with $\Pr(l \ge j) = M^{-j}$, so upper layers are sparse and their links are long.
- A search descends from one entry point with `ef = 1`, then runs a wider best-first search on layer 0.
- On 2000 Gaussian vectors, `ef = 40` reaches recall 0.980 at about 20% of brute-force cost; the hierarchy did not reduce cost in our runs.
- Compare index settings at matched cost, not matched parameters. Lesson 35.2 covers the inverted-file alternative, and Lesson 35.4 covers production systems.

## Quiz time

### Question 1: Calculation

With $M = 16$ and $N = 1{,}000{,}000$ nodes, how many nodes do you expect on layer 2 or above?

<details><summary>Show Solution</summary>

$\Pr(l \ge 2) = 16^{-2} = 1/256$. The expected count is $1{,}000{,}000 / 256 \approx 3906$.

</details>

### Question 2: Reading the data

From the sweep table, what is the smallest `ef` that reaches recall@10 of at least 0.95, and what does it cost per query?

<details><summary>Show Solution</summary>

`ef = 40`, with recall 0.980 and 394.9 distance calls per query, about 20% of the 2000 calls of brute force. `ef = 20` gives 0.913, which is below 0.95.

</details>

### Question 3: Bug spotting

In `search_layer`, the condition for admitting a new candidate is changed from `de < -res[0][0]` to `de > -res[0][0]`. What breaks, and why?

<details><summary>Show Solution</summary>

`res` is a max-heap of the `ef` best results, and `-res[0][0]` is the worst kept distance. With `>`, the search admits nodes farther than that and keeps the farthest ones, so recall should fall sharply. This is my reasoning; I did not run the modified code.

</details>

### Question 4: Explanation

One long link cut the hop count from 4 to 2. Why does a layered structure get long links without raising every node's degree?

<details><summary>Show Solution</summary>

Only a small fraction of nodes appear on upper layers, so the long links live in a sparse graph. Layer 0 keeps short links for accuracy, and the upper layers provide long jumps for coarse navigation. Each node still keeps at most $2M$ links on layer 0 and $M$ above it. This is the design intent in the paper's abstract, which describes separate link length scales across layers. Our measurements did not show a cost benefit at the sizes tested.

</details>
