A vector database is an approximate nearest-neighbour index plus what a service needs around it: stored attributes, filters, deletes and distribution across machines. In this lesson you will size the memory for a collection, measure how a metadata filter changes what a search returns, check that sharded search matches a single index, and see why deletes behave like filters.

**You need:** exact and approximate search (Lesson 35.1), inverted-file search (Lesson 35.2), HNSW graphs (Lesson 35.3), and NumPy.

## The problem: a demo index is not a service

A demo loads 10,000 vectors into one process and calls `search`. A service must also answer "only documents from tenant acme", remove a document without rebuilding the index, hold more vectors than one machine's memory, and serve many queries at once. Each requirement changes the results you get, not only the speed.

We do not compare Milvus, Qdrant, Chroma and Pgvector feature by feature. Their APIs and defaults change between releases, and we did not verify a current feature matrix. The section "What to check in any product" lists questions to ask of any of them.

## Experiment setup

The data are 20,000 vectors of 32 dimensions drawn from 50 Gaussian clusters. The 200 queries are noisy copies of stored vectors. Ground truth is exact brute-force search. The approximate index is a small IVF: 64 k-means cells, with the 4 nearest cells probed per query. The seed is fixed, so every number below repeats exactly. Clustered data is easy for IVF, so the recall values describe this setup, not a benchmark. We report counts, not timings, because timings depend on hardware.

```python
import numpy as np

rng = np.random.default_rng(0)
N, D, K, NQ = 20_000, 32, 10, 200   # stored vectors, dimensions, neighbours wanted, queries

# Clustered data: 50 blobs in 32 dimensions. Queries are noisy copies of stored vectors.
centers = rng.normal(0, 3, size=(50, D))
X = centers[rng.integers(0, 50, N)] + rng.normal(0, 1, size=(N, D))
Q = X[rng.choice(N, NQ, replace=False)] + rng.normal(0, 0.5, size=(NQ, D))

def sq_dists(A, B):
    """Squared Euclidean distance between every row of A and every row of B."""
    return (A**2).sum(1)[:, None] - 2 * A @ B.T + (B**2).sum(1)[None, :]

def exact_topk(Q, X, mask=None):
    d = sq_dists(Q, X)
    if mask is not None:
        d[:, ~mask] = np.inf
    return np.argsort(d, axis=1)[:, :K]

def recall(found, true):
    return len(set(found.tolist()) & set(true.tolist())) / K

dist = sq_dists(Q, X)
truth = exact_topk(Q, X)

# A small IVF index: 64 k-means cells, probe the 4 nearest cells.
NLIST, NPROBE = 64, 4

def kmeans(X, k, iters=15):
    C = X[rng.choice(len(X), k, replace=False)].copy()
    for _ in range(iters):
        a = sq_dists(X, C).argmin(1)
        for j in range(k):
            if np.any(a == j):
                C[j] = X[a == j].mean(0)
    return C, sq_dists(X, C).argmin(1)

C, assign = kmeans(X, NLIST)
lists = [np.flatnonzero(assign == j) for j in range(NLIST)]

def candidates(q):
    near = np.argsort(sq_dists(q[None], C)[0])[:NPROBE]
    return np.concatenate([lists[j] for j in near])

print("== 1. Metadata filters: three strategies ==")
print(f"stored={N}  dims={D}  k={K}  queries={NQ}  cells={NLIST}  probes={NPROBE}")
print(f"mean candidates scanned per query (IVF): {np.mean([len(candidates(q)) for q in Q]):.0f} of {N}")
print("selectivity  strategy     results/10  recall@10")
for p in (0.5, 0.1, 0.01):
    mask = rng.random(N) < p
    filt_truth = exact_topk(Q, X, mask)
    for strategy in ("post-filter", "overfetch", "in-scan"):
        cnt, rec = [], []
        for i, q in enumerate(Q):
            cand = candidates(q)
            order = cand[np.argsort(dist[i, cand])]
            if strategy == "post-filter":          # top-K from the index, then drop non-matches
                found = order[:K]
                found = found[mask[found]]
            elif strategy == "overfetch":          # fetch K/p candidates, then drop non-matches
                pool = order[:int(np.ceil(K / mask.mean()))]
                found = pool[mask[pool]][:K]
            else:                                  # rank only matching vectors inside the probed cells
                found = order[mask[order]][:K]
            cnt.append(len(found))
            rec.append(recall(found, filt_truth[i]))
        print(f"{p:<12} {strategy:<12} {np.mean(cnt):>9.2f}  {np.mean(rec):>9.3f}")

print("\n== 2. Sharding: scatter-gather merge ==")
shard = rng.integers(0, 4, N)
ok_k, ok_3 = 0, 0
for i in range(NQ):
    for per_shard, counter in ((K, 'k'), (3, '3')):
        cands = []
        for s in range(4):
            ids = np.flatnonzero(shard == s)
            cands.append(ids[np.argsort(dist[i, ids])[:per_shard]])   # each shard's local top-k
        cands = np.concatenate(cands)
        top = cands[np.argsort(dist[i, cands])][:K]                   # coordinator merge
        if counter == 'k':
            ok_k += set(top.tolist()) == set(truth[i].tolist())
        else:
            ok_3 += set(top.tolist()) == set(truth[i].tolist())
print(f"each shard returns k=10: merged result equals global exact top-10 for {ok_k}/{NQ} queries")
print(f"each shard returns 3:    merged result equals global exact top-10 for {ok_3}/{NQ} queries")

print("\n== 3. Memory and int8 scalar quantization ==")
for name, bytes_per_dim in (("float32", 4), ("float16", 2), ("int8", 1), ("1-bit", 1 / 8)):
    print(f"10M x 768 at {name:<8}: {10_000_000 * 768 * bytes_per_dim / 1e9:6.2f} GB")
scale = np.abs(X).max(0) / 127
codes = np.round(X / scale).astype(np.int8)
Xq = codes.astype(np.float64) * scale
print(f"int8 codes range: [{codes.min()}, {codes.max()}], mean |error| per coordinate: {np.abs(Xq - X).mean():.4f}")
qtop = exact_topk(Q, Xq)
print(f"exact search on int8-decoded vectors, recall@10 vs float: {np.mean([recall(qtop[i], truth[i]) for i in range(NQ)]):.3f}")

print("\n== 4. Deletes as tombstones (index not rebuilt) ==")
print("deleted  live results/10  recall@10 vs exact search over live rows")
for f in (0.0, 0.3, 0.6):
    dead = rng.random(N) < f
    live_truth = exact_topk(Q, X, ~dead)
    cnt, rec = [], []
    for i, q in enumerate(Q):
        cand = candidates(q)
        order = cand[np.argsort(dist[i, cand])][:K]   # index returns K rows, deleted ones included
        found = order[~dead[order]]
        cnt.append(len(found))
        rec.append(recall(found, live_truth[i]))
    print(f"{f:<8.1f} {np.mean(cnt):>15.2f}  {np.mean(rec):>9.3f}")
```

## Memory comes first: raw vectors dominate

Before any index structure, storage is $N \times d \times b$ bytes, where $b$ is bytes per dimension. The chart uses 10 million vectors of 768 dimensions, a common sentence-embedding size.

![Bar chart of raw memory for 10 million 768-dimensional vectors: float32 30.72 GB, float16 15.36 GB, int8 7.68 GB, 1-bit 0.96 GB](diagrams/35.4-memory-precision.svg "Raw vector memory at four precisions. Index overhead is extra.")

Halving the bytes per dimension halves the memory. Scalar int8 quantisation stores each dimension as one byte with a per-dimension scale. On our data it keeps 0.970 of the true top-10 neighbours, with a mean absolute error of 0.0212 per coordinate. That figure belongs to this data; measure it on yours. The 1-bit bar is arithmetic only (768 bits = 96 bytes per vector), and we did not measure its recall. Graph indexes add neighbour lists on top of the raw vectors (Lesson 35.3); we did not count them.

## Filters: the same top-10 can shrink to four rows

A post-filter takes the index's top 10 and then drops rows that fail the filter. The experiment compares three strategies for filters that keep 50%, 10% and 1% of rows.

![Grouped bars of results out of 10 for post-filter, overfetch and in-scan strategies at 50%, 10% and 1% match rates](diagrams/35.4-filter-strategies.svg "Mean results returned out of 10. Recall is in the output above.")

- **Post-filter** returns 0.96 rows on average at a 10% match. If matches were spread evenly, the expected count is $10 \times 0.10 = 1.0$.
- **Overfetch** takes the first $K/p$ candidates, where $p$ is the match fraction, then keeps the first 10 matches. At 10% it returns 8.80 rows, but the candidate pool grows as $1/p$.
- **In-scan** ranks only matching rows inside the probed cells. It returns 10 rows at 10% and 9.53 at 1%. At 1%, however, its recall is 0.767: the matching neighbours that are truly closest often lie in cells the search never probed.

No strategy repairs a search budget that is too small. Probing 4 of 64 cells is the cause at 1%. The remedy is a larger probe budget or an index that understands the filter, which is a product question.

The Pgvector README describes the same mechanism. It says: "With approximate indexes, filtering is applied after the index is scanned." Its example: if a condition matches 10% of rows, with HNSW and the default `hnsw.ef_search` of 40, "only 4 rows will match on average." From version 0.8.0 it offers iterative index scans, which keep scanning until enough rows match, bounded by `hnsw.max_scan_tuples` (20,000 by default).

> [!TRAP]
> The in-scan recall of 1.000 at 50% and 10% looks too good. We checked the code path: the ground truth is exact search over matching rows only, and in-scan draws only from matching rows. The value reflects clustered queries whose matching neighbours fall in the probed cells. To falsify it, widen the noise so clusters overlap, or probe more cells, and watch recall fall.

## Sharding: the merge is exact only if each shard returns k

Split the 20,000 vectors across four shards. Each shard returns its local top 10, and a coordinator merges the 40 candidates and keeps the best 10.

![Diagram: one query fans out to four shards, each returning a local top-10; a merge step keeps the best 10 of 40 candidates](diagrams/35.4-scatter-gather.svg "Scatter-gather. The merge is only as good as the lists each shard sends.")

With exact search on each shard, the merged result equals the global top 10 for 200 of 200 queries. When each shard returns only its local top 3, the merge is correct for 47 of 200 queries. A true neighbour can rank fourth within its own shard and still belong to the global top 10. Each shard must return at least the final k. With approximate per-shard indexes, the merge is exact over the candidates each shard returns, so recall is capped by each shard's own recall.

## Deletes are filters

Many indexes cannot remove a row cheaply. Systems therefore often mark it deleted (a tombstone) and hide it until a rebuild or compaction. Our model is simple: the index returns its top 10 including deleted rows, and then they are removed.

![Horizontal bars showing live results out of 10 after 0%, 30% and 60% of rows are deleted: 10.00, 6.90 and 3.72](diagrams/35.4-tombstone-live.svg "Live results left after tombstone deletes, index not rebuilt.")

After 30% of rows are deleted, the mean result holds 6.90 live rows; at 60%, 3.72. Recall against exact search over the live rows is 0.690 and 0.372, close to the live fractions of 0.70 and 0.40. This is the post-filter problem again. Real graph indexes may route through deleted nodes differently from this model, so read the numbers as the mechanism, not a forecast. Overfetching by about $1/(1-f)$ would compensate in this model; we did not measure that.

## What to check in any product

Put these questions to the documentation, then test each one on your own data.

- Is the filter applied during the index search or after it? Can a query return fewer than k rows? Pgvector's documentation says yes, as quoted above.
- After an insert or delete, how soon is the change visible to search? We did not verify this for any product.
- Does each shard return k, and how are merged results ordered?
- Which distance does the index assume? For cosine similarity, normalise vectors to unit length. Then $\cos(a,b) = a\cdot b / (\lVert a\rVert \lVert b\rVert)$ reduces to a dot product, so the ranking matches inner-product search.
- Does the memory figure include index overhead, or only raw vectors?

Qdrant's filtering documentation advises creating payload indexes on filtered fields, and says: "For best results, create payload indexes before ingesting data." We did not measure that advice.

## Common traps

> [!TRAP]
> **Silent short results.** A broad filter hides the bug: at a 50% match the post-filter still returns 4.95 rows, and at 10% it returns 0.96. Assert the number of returned rows in tests.

> [!TRAP]
> **Shard k below the final k.** Asking each shard for 3 rows when the caller wants 10 loses 153 of 200 query answers in our test. The error does not raise an exception.

> [!TRAP]
> **Recall from clustered synthetic data.** Easy clusters make IVF look good. Build a test set from your real queries and labelled neighbours.

> [!TRAP]
> **Counting stored rows, not live rows.** After deletes, storage can hold far more rows than the collection serves. Track both.

> [!TRAP]
> **Memory equals raw vectors.** Raw vectors are the floor. Graph links, metadata and replicas add to it.

## Summary

- Memory is N × d × bytes per dimension; for 10M × 768, float32 needs 30.72 GB and int8 needs 7.68 GB.
- A post-filter applied after an approximate search can return far fewer than k rows; at a 10% match it returned 0.96 of 10 on average.
- Sharded search is exact only if each shard returns at least k candidates; with 3 per shard, 47 of 200 queries matched the global top 10.
- Tombstoned deletes behave like filters: 30% deleted left 6.90 live results out of 10.
- Product choice matters less than measuring these four behaviours on your own data.

## Quiz time

### Question 1: Calculation

A collection holds 1 million vectors of 1,536 float32 dimensions. How much raw memory do the vectors need, in GB (decimal)? Ignore index overhead.

<details><summary>Show solution</summary>

Bytes = $10^6 \times 1536 \times 4 = 6.144 \times 10^9$ bytes, so 6.144 GB. Index overhead comes on top.

</details>

### Question 2: Prediction

A post-filter keeps 1% of rows. What does the experiment predict for the mean number of results out of 10, and why is it not exactly $10 \times 0.01$?

<details><summary>Show solution</summary>

The expected count is $10 \times 0.01 = 0.1$. Our measured value was 0.12. The estimate assumes matches are spread evenly across the index's top 10; the sample of 200 queries varies around the expectation.

</details>

### Question 3: Bug-spotting

```python
hits = index.search(query, k=10)
hits = [h for h in hits if h.tenant == "acme"]
```

What goes wrong when "acme" owns 5% of rows?

<details><summary>Show solution</summary>

The filter runs after the top 10 are chosen, so the code usually returns fewer than 10 hits, sometimes none. Pass the filter to the search call, or overfetch by about $1/p$ and then truncate to 10.

</details>

### Question 4: Explanation

Why can in-scan search return 9.53 results at a 1% match rate and still have recall of only 0.767?

<details><summary>Show solution</summary>

In-scan ranks only matching rows, so it fills the list. Recall is low because the true filtered neighbours can sit in cells that were never probed. The result list is full but the search covered too little of the space.

</details>
