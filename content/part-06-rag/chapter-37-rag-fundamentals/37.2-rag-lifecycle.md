A retrieval-augmented generation (RAG) system answers a question in three stages: ingestion, retrieval and generation. By the end you will be able to say what each stage does and how often it runs, build all three in NumPy on a small handbook, and find which stage lost an answer when a system fails.

**You need:** the idea that text can be turned into a vector (Lesson 24.1), and that cosine similarity is a normalised dot product. Lesson 37.1 explains why vector search alone is not RAG. Lesson 37.3 builds a complete system without a framework.

## The problem

A language model answers from its training data. Ask it how many days of annual leave a staff member accrues each month at a company whose handbook it has never seen, and it can only guess, with no way for you to check. RAG fetches the relevant text when the question is asked and places it in the prompt, so the answer can be traced to a source. Lewis et al. (2020) introduced this idea by pairing a pretrained generator with a dense index of Wikipedia that a pretrained neural retriever searches [1].

## Three stages, two schedules

![Three rows of boxes: offline ingestion (load, chunk, embed, index), online retrieval (question, embed query, top-k search) and online generation (prompt, LLM call, answer with citations); a dashed arrow shows search reading the index](diagrams/37.2-lifecycle.svg "The lifecycle. The top row runs once per corpus; the other two run once per question.")

- **Ingestion** (offline): load the documents, split them into chunks, embed each chunk as a vector, and store the vectors in an index.
- **Retrieval** (online): embed the question with the same embedder, score every chunk against it, and keep the top $k$ chunks.
- **Generation** (online): put the top-$k$ chunks and the question into a prompt, and ask a language model for an answer that cites the chunks by number.

The embedder must be the same at ingestion and retrieval. Vectors from two different embedders live in different spaces, so their dot products mean nothing.

Gao et al. (2023) survey RAG and name three paradigms: Naive, Advanced and Modular RAG [4]. This lesson covers only the naive pipeline above, with no query rewriting or reranking.

## Worked example by hand: TF-IDF scores

To keep the whole pipeline runnable without model weights, we use TF-IDF (term frequency times inverse document frequency) as the embedder. Each chunk becomes a sparse vector with one dimension per word. It matches only shared words, which is a real limit, and we return to it below.

Take two chunks, $c_1$ = "leave requests approved" and $c_2$ = "leave notify manager", so $N = 2$. Use $\mathrm{idf}(t) = \ln\frac{1+N}{1+\mathrm{df}(t)} + 1$, where $\mathrm{df}(t)$ is the number of chunks that contain $t$.

- "leave" is in both chunks, so $\mathrm{idf} = \ln(3/3) + 1 = 1$.
- "approved", "requests", "notify" and "manager" are each in one chunk, so $\mathrm{idf} = \ln(3/2) + 1 \approx 1.405$.

The query "leave approved" has the vector $(1,\ 1.405)$ over (leave, approved), with norm $\sqrt{1 + 1.405^2} \approx 1.725$. Chunk $c_1$ has the vector $(1,\ 1.405,\ 1.405)$ over (leave, requests, approved), with norm $\approx 2.224$. The shared dimensions give a dot product of $1 + 1.405^2 \approx 2.974$, so the cosine is $2.974 / (1.725 \times 2.224) \approx 0.775$. For $c_2$, only "leave" is shared, so the cosine is $1 / (1.725 \times 2.224) \approx 0.261$. The code below reproduces both numbers.

## Build the pipeline

The corpus is six short documents from a fictional staff handbook, so no outside facts are needed. There are 14 questions. Each has a gold answer string that must appear word for word in the text the model would see. The code uses only the standard library and NumPy, so it can run in the browser; it was run locally, not in the in-browser runner.

```python

import json, re

# ---- Source documents: a fictional staff handbook, so no outside facts are needed
DOCS = {

# ---- Evaluation questions: (question, gold answer string that must appear verbatim in the context)
QUERIES = [
    ("How many days of annual leave do staff accrue each month?", "1.5 days"),
    ("How long can unused leave carry over?", "10 days"),
    ("How far ahead must a leave request be approved?", "5 working days"),
    ("By what time must I tell my manager I am sick?", "9:30 a.m."),

    ("How soon after a trip must a travel claim be submitted?", "30 days"),
    ("Who approves a claim above 500 dollars?", "second approval"),
    ("Is alcohol reimbursable?", "not reimbursable"),
    ("How many days a week can I work remotely?", "2 days per week"),
    ("What are the core hours for remote staff?", "10:00 to 15:00"),
    ("How quickly must a lost device be reported?", "24 hours"),
    ("Can I connect a personal USB drive to a company laptop?", "not permitted"),
    ("How long is probation?", "3 months"),
    ("When is the first performance review?", "week 12"),

# ---- 1. INGESTION: load, chunk, index
def chunk(text, size, overlap=0):
    """Split text into windows of `size` words; consecutive windows share `overlap` words."""
    words = text.split()
    step = size - overlap
    out = []
    for start in range(0, len(words), step):
        out.append(" ".join(words[start:start + size]))
        if start + size >= len(words):
            break
    return out

def ingest(docs, size, overlap=0):
    return [{"doc": d, "text": piece} for d, text in docs.items() for piece in chunk(text, size, overlap)]

STOP = {"a", "an", "the", "of", "to", "is", "are", "be", "do", "does", "i", "my", "it", "on", "in",
        "for", "and", "or", "at", "how", "can", "what", "when", "which", "if", "after", "before", "by"}

def tokens(s):
    return [t for t in re.findall(r"[a-z0-9]+", s.lower()) if t not in STOP]

def build_index(chunks):
    """TF-IDF vectors, one row per chunk, L2-normalised. A toy stand-in for a neural embedding."""
    vocab = sorted({t for c in chunks for t in tokens(c["text"])})
    col = {t: j for j, t in enumerate(vocab)}
    counts = np.zeros((len(chunks), len(vocab)))
    for i, c in enumerate(chunks):
        for t in tokens(c["text"]):
            counts[i, col[t]] += 1
    df = (counts > 0).sum(axis=0)
    idf = np.log((1 + len(chunks)) / (1 + df)) + 1.0
    X = counts * idf
    X = X / (np.linalg.norm(X, axis=1, keepdims=True) + 1e-12)
    return {"chunks": chunks, "vocab": col, "idf": idf, "X": X}

# ---- 2. RETRIEVAL: embed the query, score every chunk, keep top-k
def embed_query(index, text):
    v = np.zeros(len(index["vocab"]))
    for t in tokens(text):
        if t in index["vocab"]:
            v[index["vocab"][t]] += 1
    v = v * index["idf"]
    return v / (np.linalg.norm(v) + 1e-12)

def retrieve(index, query, k=3):
    scores = index["X"] @ embed_query(index, query)
    order = np.argsort(-scores, kind="stable")[:k]
    return [dict(index["chunks"][i], score=float(scores[i])) for i in order]

# ---- 3. GENERATION: assemble the prompt (the LLM call itself is not run here)
def build_prompt(question, hits):
    sources = "\n".join(f"[{i + 1}] {h['text']}" for i, h in enumerate(hits))
    return ("Answer using only the numbered sources and cite them as [n]. "
            "If the sources do not contain the answer, say so.\n\n"
            f"Sources:\n{sources}\n\nQuestion: {question}\nAnswer:")

# ---- Evaluation: does the gold answer reach the prompt?
def evaluate(size, overlap, k=3):
    chunks = ingest(DOCS, size, overlap)
    index = build_index(chunks)
    in_index, at1, at_k = 0, 0, 0
    for q, gold in QUERIES:
        g = gold.lower()
        in_index += any(g in c["text"].lower() for c in chunks)
        top = retrieve(index, q, k)
        at1 += g in top[0]["text"].lower()
        at_k += g in " \n ".join(h["text"] for h in top).lower()
    n = len(QUERIES)
    return {"size": size, "overlap": overlap, "n_chunks": len(chunks),
            "mean_words": round(float(np.mean([len(c["text"].split()) for c in chunks])), 1),
            "answer_in_index": in_index / n, "answer_at_1": at1 / n, "answer_at_k": at_k / n}

CONFIGS = [(4, 0), (4, 2), (8, 0), (8, 4), (16, 0), (16, 8), (32, 0), (32, 16), (64, 0), (10**6, 0)]

if __name__ == "__main__":
    # Walkthrough at the default chunk size
    size, overlap = 16, 0
    chunks = ingest(DOCS, size, overlap)
    index = build_index(chunks)
    print("documents:", len(DOCS), " chunks:", len(chunks), " vocabulary:", len(index["vocab"]))
    print("first chunks of 'leave':")
    for c in chunks[:3]:
        print("  |", c["text"])
    q, gold = QUERIES[2]
    print("\nquery:", q)
    top = retrieve(index, q, 3)
    for h in top:
        print(f"  {h['score']:.3f}  [{h['doc']}] {h['text'][:60]}...")
    print("\nprompt:")
    print(build_prompt(q, top))
    # Hand-check example: two chunks, worked by hand in the lesson
    tiny = [{"doc": "a", "text": "leave requests approved"}, {"doc": "b", "text": "leave notify manager"}]
    tiny_index = build_index(tiny)
    print("\nhand check (N = 2 chunks):")
    print("idf:", {t: round(float(tiny_index["idf"][j]), 3) for t, j in sorted(tiny_index["vocab"].items())})
    for h in retrieve(tiny_index, "leave approved", 2):
        print(f"  {h['score']:.3f}  {h['text']}")
    print("\nsweep over chunk size (words) and overlap, k = 3:")
    print(f"{'size':>8} {'ov':>4} {'chunks':>7} {'words':>6} {'in_index':>9} {'@1':>6} {'@3':>6}")
    rows = []
    for s, o in CONFIGS:
        r = evaluate(s, o)
        rows.append(r)
        label = "doc" if s >= 10**6 else str(s)
        print(f"{label:>8} {o:>4} {r['n_chunks']:>7} {r['mean_words']:>6} "
              f"{r['answer_in_index']:>9.2f} {r['answer_at_1']:>6.2f} {r['answer_at_k']:>6.2f}")

    # Per-query failure attribution at the default configuration
    per_query = []
    for q, gold in QUERIES:
        g = gold.lower()
        top = retrieve(index, q, 3)
        if not any(g in c["text"].lower() for c in chunks):
            status = "lost_at_ingestion"
        elif g in " \n ".join(h["text"] for h in top).lower():
            status = "in_top3"
        else:
            status = "lost_at_retrieval"
        per_query.append({"question": q, "gold": gold, "status": status})
    print("\nper-query status at size 16:")
    for p in per_query:
        print(f"  {p['status']:<20} {p['gold']}")
```

## Ingestion: a fixed-size cut can break the answer

Ingestion cuts each document into windows of a fixed number of words. Consecutive windows can share some words (the overlap), so a sentence cut at one boundary may survive whole in the next window.

![Two consecutive 16-word chunks from the leave policy. Chunk 1 ends with "up to 10" and chunk 2 begins with "days", so the phrase 10 days is split and no chunk contains it](diagrams/37.2-chunk-cut.svg "A fixed-size cut splits the gold answer 10 days across two chunks.")

The leave policy has the sentence "Unused leave up to 10 days carries over". At 16 words, the cut falls between "10" and "days". No chunk in the index contains the phrase, so no retriever can return it. This is an ingestion failure, and it is the only one at size 16 in our 14 questions (the "per-query status" output shows it).

## Retrieval: the answer is not always rank 1

Retrieval embeds the question with the same TF-IDF function, takes the dot product with every chunk vector (the vectors are normalised, so the dot product is the cosine), and sorts.

![Three horizontal bars for the top three chunks of the question "How far ahead must a leave request be approved?" The top bar scores 0.460 but lacks the answer; rank 2 scores 0.253 and contains 5 working days](diagrams/37.2-retrieval-rank.svg "The chunk that holds the answer is rank 2, not rank 1.")

For this question the top-scoring chunk shares the words "leave", "must" and "approved" with the question, but not the answer. The answer chunk ranks second, with 0.253. Taking only the top chunk would miss it.

At size 16, the top chunk contains the answer for 10 of the 14 questions, and the top three contain it for 13 of 14. Retrieving more chunks raises recall but makes the prompt longer, so $k$ is a trade-off, not a free setting.

## Generation: build the prompt, then check what it contains

The generation stage turns the chunks into a prompt. The example prompt in the output has three parts: an instruction to answer only from numbered sources and to say so when they do not contain the answer; the sources, numbered so the answer can cite them; and the question. The instruction to abstain is what lets a model report "not in the handbook" instead of guessing.

This lesson stops before the model call, because a real model would need weights or an API key. What we can measure is whether the evidence reached the prompt. Liu et al. (2023) found that a model's accuracy is often highest when the relevant information sits at the beginning or end of the input, and drops when it sits in the middle of long contexts [3]. So the order of the sources is a generation decision that can lose an answer even when the answer is in the prompt.

## Which stage lost the answer?

The sweep varies the chunk size in words, with no overlap, and reports two numbers for each size: the share of the 14 gold answers that appear in some chunk (the index can return them), and the share that appear in the top three chunks.

![Grouped bars for chunk sizes 4, 8, 16, 32, 64 and whole documents. The answer-in-index bars rise from 0.57 to 1.00; the answer-in-top-3 bars rise from 0.07 to 1.00 and are lower than the index bars at small sizes](diagrams/37.2-sweep.svg "Fraction of 14 questions whose gold answer is in some chunk (blue) and in the top three chunks (green).")

Two regimes show up.

- **At size 4 with no overlap**, the index contains only 57% of the answers, so 43% are lost at ingestion. Only 7% are in the top three. The 73 short chunks are too fragmentary to be found.
- **At size 4 with 2 words of overlap**, the index contains 100% of the answers, but only 21% are in the top three. The answers exist and retrieval does not find them, so the loss is in the retrieval stage. Overlap helped here (the top-three rate rose from 7%), but not enough to close the gap.

Size 16 gives the best balance in this set: 93% in the index and 93% in the top three. Whole documents reach 100% at both steps, but with only six chunks each of which is a full document, so each prompt would carry about 47 words per source.

The practical rule is to check the stages in order. First, is the gold text in any chunk? If not, fix ingestion. Second, is it in the top $k$? If not, fix retrieval. Third, is it in the prompt and does the model use it? That third check needs a real model and is not measured here.

These numbers come from 14 questions over six documents. One question moves a rate by 0.07, so treat them as an illustration of the mechanism, not a benchmark. The embedder is lexical, so it cannot match a paraphrase such as "sick" for "absence", and a neural embedder might behave differently; we did not test that (reasoning). Karpukhin et al. (2020) report that a trained dense retriever beats a strong BM25 baseline by 9 to 19 points on top-20 passage accuracy in their setting [2]; that is a different benchmark and not a result about this toy corpus.

## Common traps

> [!TRAP]
> Embedding the documents with one model and the questions with another. The scores run without error and mean nothing.

> [!TRAP]
> Trusting the top chunk. In the worked question the answer was at rank 2. Check the top $k$, not only rank 1.

> [!TRAP]
> Choosing the chunk size from one number. At size 4, the index contains almost every answer, yet the top three contain few of them. The two metrics point to different fixes.

> [!TRAP]
> Adding overlap without counting the cost. At size 4, overlap 2 raises the chunk count from 73 to 137. In this run it helped the top-three rate, but the index is almost twice as large and retrieval has more near-duplicate candidates.

> [!TRAP]
> Reading a fluent answer as a grounded one. A model can write a confident answer that the sources do not support. Check the cited chunk contains the claim.

## Summary

- RAG has three stages: ingestion (offline), retrieval and generation (per question). The embedder must be the same at ingestion and retrieval.
- A fixed-size chunk cut can split the answer across two chunks, and then no retriever can return it.
- Retrieval ranks by score, so the answer can sit at rank 2 or lower; top-$k$ recall is the number to watch.
- Diagnose by stage: is the answer in the index, in the top $k$, and in the prompt?
- Small samples and lexical embeddings make these numbers illustrations, not benchmarks.

### Question 1: Calculation

With 14 questions, chunk size 8 and no overlap give an index hit rate of 0.86 and a top-3 rate of 0.50. How many questions have their answer in some chunk, and how many have it in the top three?

<details><summary>Show solution</summary>

The counts are $0.86 \times 14 = 12.04$ and $0.50 \times 14 = 7$. So 12 questions have the answer in the index and 7 have it in the top three. The 5 questions with the answer in the index but not the top three are retrieval losses.

</details>

### Question 2: Find the bug

```python
def chunk(text, size, overlap=0):
    words = text.split()
    step = size - overlap
    return [" ".join(words[i:i + size]) for i in range(0, len(words), step)]

print(chunk("a b c d e f", size=4, overlap=4))
```

<details><summary>Show solution</summary>

With `overlap` equal to `size`, `step` is 0, and `range(0, n, 0)` raises `ValueError: range() arg 3 must not be zero`. The fix is to require `0 <= overlap < size` before chunking, for example with an `assert` or a `ValueError` of our own that explains the constraint.

</details>

### Question 3: Prediction

At size 4 with 2 words of overlap, the index contains 100% of the answers but only 21% are in the top three. Why can the answer text be in the index and still not be retrieved?

<details><summary>Show solution</summary>

Each short chunk shares few words with a question, so many chunks score similarly and the answer fragment competes with near-duplicates for the three slots. This is reasoning about this toy scorer, not a measured cause. A longer chunk carries more of the question's words, which is consistent with the size-16 row, but the experiment does not isolate the cause.

</details>

### Question 4: Explanation

Why does retrieval fail silently when the query and documents are embedded by different models, and what check would catch it?

<details><summary>Show solution</summary>

The two models produce vectors in different spaces, so the cosine between them is a number with no meaning. Nothing raises an error. A check is to embed one known chunk with the ingestion code and again with the retrieval code, and confirm the vectors are identical. Logging the embedder's name and version in the index metadata also catches it.

</details>
