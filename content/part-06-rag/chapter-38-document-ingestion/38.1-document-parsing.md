A retrieval system can only answer from the text it has, so a parser that scrambles the text scrambles the answers. In this lesson you will see why a Portable Document Format (PDF) file is not a text file, measure reading-order and table strategies on pages you generate yourself, and write an XY-cut reading-order step in pure Python.

**You need:** Python lists, tuples and `sorted` with a key function (Part 1), and the retrieval-augmented generation (RAG) pipeline from Lesson 37.1.

## The problem parsing solves

RAG splits documents into text, embeds that text, retrieves chunks, and generates an answer. Every later step depends on the first one. Suppose a two-column page is parsed one line at a time across the page: left column line 1, right column line 1, left column line 2, and so on. A chunk built from those lines reads as nonsense, and no embedding model can repair it. Lesson 38.2 cuts parsed text into chunks; a chunk that begins in the middle of a table is a parsing error that chunking cannot undo.

## A PDF is a list of glyphs at coordinates

A PDF page is a content stream of drawing instructions: use this font, place this glyph at (x, y). It has no paragraphs, no reading order and no table objects. A parser rebuilds those from positions in five stages.

![Five parsing stages from PDF bytes to Markdown, with a branch to OCR when a page has no text layer](diagrams/38.1-pipeline.svg "Each stage is a separate failure point. The OCR branch is taken when a page has no glyphs.")

Glyphs are the raw data. Lines group glyphs that share a baseline. Reading order decides which line comes next. Table detection decides which lines form cells. Output is Markdown or JSON (JavaScript Object Notation). A scanned page skips the first stage entirely, because it is an image. Optical character recognition (OCR) is the only route for it.

## Worked example by hand

The test page has a title and 12 lines in each of two columns: 25 lines in total. Its true reading order is TITLE, L01 to L12, then R01 to R12. Lines are 12 points (pt) apart, and the widest left-column line ends at x = 224.3 pt.

Score the simplest strategy by hand: sort every line top to bottom, then left to right. The predicted order is TITLE, L01, R01, L02, R02, and so on. Define the score as **adjacency**: the fraction of the $n-1$ consecutive pairs in the prediction that are also consecutive in the truth.

$$
\text{adjacency} = \frac{\#\{\, i : t(p_{i+1}) = t(p_i) + 1 \,\}}{n - 1}
$$

Here $p_i$ is the $i$-th predicted line and $t(\cdot)$ its true position. Of the 24 consecutive pairs, only TITLE to L01 is correct. The score is $1/24 \approx 0.042$, which is the value the experiment prints.

0.042 is also chance level. For a random order, each line's successor is one specific true successor with probability 1/24, so the expected adjacency is 1/24.

## Stream order versus reading order

The content stream holds glyphs in the order the producer drew them. Whether that order is the reading order depends on the producer. We drew the same page three ways and measured four strategies.

| Producer draws the page in | Stream order | Top-to-bottom sort | pdfminer.six default | XY-cut, min gap 6 pt |
|---|---|---|---|---|
| column-major (left column, then right) | 1.00 | 0.04 | 1.00 | 1.00 |
| row-major (L01, R01, L02, R02, ...) | 0.04 | 0.04 | 1.00 | 1.00 |
| shuffled (boxes in random creation order) | 0.04 | 0.04 | 1.00 | 1.00 |

![Two producers draw the same two-column page; the stream order reads correctly only for the column-major one](diagrams/38.1-stream-order.svg "Numbers are drawing steps. Adjacency is measured on the 25 lines.")

Nothing in the file forces a producer to write columns in reading order, so the stream is not a reliable order by itself. The pdfminer.six default scored 1.00 on all three. Its layout analysis groups glyphs into text boxes and orders the boxes by position. Its documented parameter `boxes_flow` (default 0.5) sets how much horizontal and vertical position matter when ordering boxes (pdfminer.six documentation). This page is clean, so these scores are a best case. They say nothing about pages with figures, sidebars or footnotes, which we did not test.

## XY-cut: cut the page where the whitespace is

The recursive XY-cut is a top-down method from the document-analysis literature: cut the page along blank bands, then recurse. I did not open its original paper, so it is uncited here. Our version works on text-line boxes, with one parameter, the minimum gap `min_gap` (in pt) that counts as a cut.

1. Sort boxes by top edge. Start a new band wherever the vertical gap above a box exceeds `min_gap`. If there is more than one band, recurse into each.
2. Otherwise, sort by left edge and start a new column wherever the horizontal gap exceeds `min_gap`. If there is more than one column, recurse into each.
3. Otherwise, read top to bottom, then left to right.

This code runs in the browser as written:

```python
def xy_cut(boxes, min_gap):
    """boxes: (x0, y0, x1, y1, label) in PDF coordinates, where y grows upward."""
    if len(boxes) <= 1:
        return [b[4] for b in boxes]
    # 1. Horizontal cut: start a new band wherever the vertical gap exceeds min_gap.
    bands, band = [], []
    for b in sorted(boxes, key=lambda b: -b[3]):          # top edge first
        if band and b[3] < min(x[1] for x in band) - min_gap:
            bands.append(band)
            band = []
        band.append(b)
    bands.append(band)
    if len(bands) > 1:
        return [lab for part in bands for lab in xy_cut(part, min_gap)]
    # 2. Vertical cut: start a new column wherever the horizontal gap exceeds min_gap.
    cols, col = [], []
    for b in sorted(boxes, key=lambda b: b[0]):           # left edge first
        if col and b[0] > max(x[2] for x in col) + min_gap:
            cols.append(col)
            col = []
        col.append(b)
    cols.append(col)
    if len(cols) > 1:
        return [lab for part in cols for lab in xy_cut(part, min_gap)]
    # 3. Nothing left to cut: read top to bottom, then left to right.
    return [b[4] for b in sorted(boxes, key=lambda b: (-b[3], b[0]))]

boxes = [
    (72.0, 739.1, 241.6, 753.1, "TITLE"),
    (72.0, 717.9, 224.3, 727.9, "L01"),
    (72.0, 705.9, 224.3, 715.9, "L02"),
    (320.0, 717.9, 473.9, 727.9, "R01"),
    (320.0, 705.9, 473.9, 715.9, "R02"),
]
for gap in (1.0, 6.0, 80.0):
    print(gap, xy_cut(boxes, gap))
```

```output
1.0 ['TITLE', 'L01', 'R01', 'L02', 'R02']
6.0 ['TITLE', 'L01', 'L02', 'R01', 'R02']
80.0 ['TITLE', 'L01', 'R01', 'L02', 'R02']
```

On the full 25-line page, the measured geometry was: line gap 2.0 pt, title-to-body gap 11.2 pt, and column gap 95.7 pt between the widest left line and the start of the right column. The title ends at x = 241.6 pt, which leaves 78.4 pt to the right column. The sweep below shows where the method works.

![Bar chart of XY-cut adjacency against minimum gap: 1.00 from 2 to 60 pt, 0.04 at 0, 1, 80 and 100 pt](diagrams/38.1-xycut-sweep.svg "Adjacency for the column-major page, 25 lines, one run per minimum gap.")

Both edges of the working window have a cause:

- Below 2.0 pt, every line gap counts as a horizontal cut. Each row is then read across both columns, which gives row-major order. A cut needs a gap strictly larger than `min_gap`, so a 2.0 pt gap survives at `min_gap` = 2.
- Above 78.4 pt, the title (which spans x = 72 to 241.6 pt) is still in the same group as the columns when the vertical cut runs. Its right edge leaves only 78.4 pt to the right column, so the title bridges the gap and nothing is cut. The 95.7 pt column gap is not the limiting number. An unrelated element is.

## Tables: the anchor edge decides

Lines are the easy case. Tables need columns, and a column is a set of text fragments that share an edge. We cut the text into 24 fragments, one per cell, from an unruled table: a left-aligned name column and three right-aligned numeric columns. Then we clustered one edge of every fragment (left edge x0, centre xc, or right edge x1) with a 3 pt tolerance. Each cluster is a column.

Scoring needs care. The first version used majority purity (each cluster's most common true column), and every anchor scored 1.00. That is because splitting each fragment into its own cluster is always pure. The score we report is **pairwise**: over all $\binom{24}{2} = 276$ pairs of fragments, a pair from the same column should share a cluster (recall), and a pair from different columns should not (precision). The F1 score is $F_1 = 2PR/(P+R)$, the harmonic mean of precision $P$ and recall $R$.

![Horizontal bars: pairwise F1 is 0.71 for left edge, 0.80 for centre, 0.96 for right edge, and 1.00 for ruled lines](diagrams/38.1-table-anchors.svg "Pairwise F1 over 276 fragment pairs. Ruled lines use the vertical rules in the file.")

Right-aligned numbers share a right edge, so x1 is the best anchor here (pairwise recall 0.92, five clusters). Left-aligned names share a left edge, so x0 suits them, but the numbers have different widths and split apart (pairwise recall 0.55, nine clusters). We did not record which column loses recall under x1; the names are the likely cause, since they have no shared right edge (my reasoning). No single anchor fits mixed alignment. The file itself settles the question when it contains rules: the five vertical rules sit at x = 78, 218, 308, 398 and 488 pt, which gives four columns and F1 = 1.00. Unruled tables need inference, and inference fails where the alignment is mixed.

Real tables have merged cells, spanning headers and multi-line cells. We did not test those. PubTables-1M, a dataset of nearly one million tables from scientific articles with structure annotations, was built for exactly this kind of table extraction (Smock et al., 2021).

## Where learned models fit

Rules fail on pages with no text layer and on tables without a shared edge. Two open tools use learned models for these cases. Nougat converts scientific documents to markup with a visual Transformer and OCR (Blecher et al., 2023). Its design does not rely on an embedded text layer; we checked that only against the abstract. Docling is an MIT-licensed toolkit that uses AI models for layout analysis and table structure recognition (Auer et al., 2024). Likely costs, from my reasoning and not measured: GPU time, and errors that are hard to spot. We did not run either tool, so treat them as the next step, not as tested behaviour.

## Common traps

> [!TRAP]
> `extract_pages(path, laparams=None)` does not turn off layout analysis. In pdfminer.six 20260107, `high_level.py` replaces `None` with `LAParams()` at lines 169 and 210. Our check found `LTTextBoxHorizontal` children. To read glyphs in stream order, use `PDFPageAggregator(rsrc, laparams=None)`, as in the local check below.

> [!TRAP]
> A purity score rewards over-splitting. A table split into one cluster per cell can score perfect purity while recovering no columns. Score pairs (precision and recall) instead.

> [!TRAP]
> A scanned page returns an empty string with no error. Our scanned test page gave 0 characters. Count characters per page, and route empty pages to OCR, or the index will silently lack them.

> [!TRAP]
> A title or banner that reaches into the column gap can disable the column cut for every minimum gap above a threshold. Check a sweep over the parameter, not one value.

> [!TRAP]
> Our pages are clean: equal column lengths, no figures, no footnotes, no hyphenated line breaks. Each of those changes the result, and none is tested here.

## Summary

- A PDF stores glyphs at coordinates; reading order and tables must be rebuilt from positions.
- Stream order is the reading order only when the producer wrote it that way: adjacency 1.00 for column-major, 0.04 for row-major.
- XY-cut worked for minimum gaps from 2 to 60 pt on our page; the lower edge is the 2.0 pt line gap, and the upper edge is set by the title.
- Score table recovery with pairwise precision and recall; purity rewards over-splitting.
- Count characters per page. An empty text layer is a silent failure that needs OCR.

## Quiz time

### Question 1: Calculation

A predicted order of 25 lines has 9 consecutive pairs that are also consecutive in the truth. What is its adjacency?

<details><summary>Solution</summary>

There are $25 - 1 = 24$ consecutive pairs. Adjacency is $9/24 = 0.375$.

</details>

### Question 2: Prediction

A producer writes the right column first (R01 to R12), then the left column (L01 to L12), after the title. Predict the stream-order adjacency before computing it.

<details><summary>Solution</summary>

The 24 consecutive pairs are: TITLE to R01 (wrong), eleven R-to-R pairs (correct), R12 to L01 (wrong), and eleven L-to-L pairs (correct). That gives 22 correct pairs, so adjacency is $22/24 \approx 0.917$. The score is high even though the column order is reversed, because the metric counts within-column pairs. Adjacency does not penalise a block-level swap as much as it penalises an interleaved order.

</details>

### Question 3: Bug-spotting

A student writes this to read glyphs in drawing order:

```python
page = next(extract_pages("report.pdf", laparams=None))
glyphs = [c for c in page if isinstance(c, LTChar)]
```

What goes wrong?

<details><summary>Solution</summary>

The top-level children of `extract_pages` are text boxes (`LTTextBoxHorizontal`), not characters, so `glyphs` is empty. Even a recursive walk gives layout order, because `laparams=None` is replaced by `LAParams()`. Use `PDFPageAggregator(rsrc, laparams=None)` with `PDFPageInterpreter` to get the raw stream.

</details>

### Question 4: Explanation

A table has a left-aligned name column and right-aligned numbers. Why does no single anchor edge recover every column, and what would you do instead?

<details><summary>Solution</summary>

Left-aligned cells share a left edge, and right-aligned cells share a right edge. Clustering on one edge therefore merges one kind of column correctly and splits the other. Options: choose the anchor per column (reasoning, not tested here), use ruled lines if the file has them, or use a learned table-structure model.

</details>

### Question 5: Engineering judgement

A 300-page batch returns empty text for 40 pages, and no exception is raised. What is the most likely cause, and what should the pipeline do?

<details><summary>Solution</summary>

The most likely cause is a scanned page with no text layer. The pipeline should record characters per page, send empty pages to OCR, and keep the page number in the index so the source can be traced. This is reasoning from the scanned-page test, not a measured property of the 40 pages.

</details>

<details><summary>Run locally: needs pip install pdfminer.six reportlab</summary>

The check below builds two pages with reportlab, then reads them with pdfminer.six 20260107 and reportlab 5.1.0. It compares stream order (layout analysis off) with the default layout analysis.

```python
import random
import re
from pdfminer.converter import PDFPageAggregator
from pdfminer.high_level import extract_pages
from pdfminer.layout import LAParams, LTChar, LTTextBox
from pdfminer.pdfinterp import PDFPageInterpreter, PDFResourceManager
from pdfminer.pdfpage import PDFPage
from reportlab.pdfgen import canvas

FILL = "lorem ipsum dolor sit amet elit"
TRUTH = ["TITLE"] + [f"L{i:02d}" for i in range(1, 13)] + [f"R{i:02d}" for i in range(1, 13)]
POS = {"TITLE": (72, 742)}
for i in range(1, 13):
    POS[f"L{i:02d}"] = (72, 720 - 12 * (i - 1))
    POS[f"R{i:02d}"] = (320, 720 - 12 * (i - 1))

def draw(path, order):
    c = canvas.Canvas(path, pagesize=(612, 792))
    for lab in order:
        c.setFont("Helvetica-Bold" if lab == "TITLE" else "Helvetica", 14 if lab == "TITLE" else 10)
        text = "TITLE Two-column report" if lab == "TITLE" else f"{lab} {FILL}"
        c.drawString(POS[lab][0], POS[lab][1], text)
    c.save()

def raw_page(path):
    """Glyphs in content-stream order, with layout analysis switched off."""
    rsrc = PDFResourceManager()
    device = PDFPageAggregator(rsrc, laparams=None)
    interp = PDFPageInterpreter(rsrc, device)
    with open(path, "rb") as f:
        for page in PDFPage.get_pages(f):
            interp.process_page(page)
            return device.get_result()

def iter_chars(obj):
    if isinstance(obj, LTChar):
        yield obj
    elif hasattr(obj, "__iter__"):
        for child in obj:
            yield from iter_chars(child)

def stream_lines(path):
    lines, cur = [], None
    for ch in iter_chars(raw_page(path)):
        if cur is None or abs(ch.y0 - cur[0]) > 0.5 or ch.x0 - cur[1] > 15 or ch.x0 < cur[1] - 0.5:
            cur = [ch.y0, ch.x1, ""]
            lines.append(cur)
        cur[2] += ch.get_text()
        cur[1] = ch.x1
    return [re.match(r"(TITLE|[LR]\d\d)", t.replace(" ", "")).group(1) for _, _, t in lines]

def layout_lines(path):
    page = next(extract_pages(path, laparams=LAParams()))
    out = []
    for box in page:
        if isinstance(box, LTTextBox):
            for line in box:
                out.append(re.match(r"(TITLE|[LR]\d\d)", line.get_text().replace(" ", "")).group(1))
    return out

def adjacency(pred):
    idx = [TRUTH.index(p) for p in pred]
    return round(sum(b == a + 1 for a, b in zip(idx, idx[1:])) / (len(idx) - 1), 3)

orders = {
    "column-major": list(TRUTH),
    "shuffled": random.Random(7).sample(TRUTH, len(TRUTH)),
}
for name, order in orders.items():
    path = f"{name}.pdf"
    draw(path, order)
    print(name)
    print("  stream order     :", adjacency(stream_lines(path)))
    print("  layout (default) :", adjacency(layout_lines(path)))
    print("  boxes after extract_pages(laparams=None):", sorted({type(b).__name__ for b in extract_pages(path, laparams=None).__next__()}))
```

```output
  layout (default) : 1.0
  boxes after extract_pages(laparams=None): ['LTTextBoxHorizontal']
shuffled
  stream order     : 0.042
  layout (default) : 1.0
  boxes after extract_pages(laparams=None): ['LTTextBoxHorizontal']
```
