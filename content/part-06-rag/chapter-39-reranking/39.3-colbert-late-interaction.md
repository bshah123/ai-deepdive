In this lesson you will score a query against a passage token by token, using the MaxSim rule from ColBERT. You will compute one score by hand, measure when a single pooled vector loses information that MaxSim keeps, and count the storage and compute cost of each design.

**You need:** the bi-encoder and cross-encoder tradeoff (Lessons 39.1 and 39.2), and matrix multiplication in NumPy.

## The problem

A bi-encoder compresses a whole passage into one vector. A cross-encoder reads the query and passage together, which is accurate but costs one transformer pass per pair (Lesson 39.2). Late interaction (LI) sits between them. Each passage keeps one vector per token. The query also gets one vector per token. The two sides interact only at scoring time, through cheap dot products, so the passage side can be computed once, offline.

ColBERT (Contextualized Late Interaction over BERT) is the best-known LI system. Khattab and Zaharia (2020) introduced it. Each token is passed through BERT (Bidirectional Encoder Representations from Transformers), projected to 128 dimensions, and scaled to unit Euclidean length (L2 norm 1). The paper sets the embedding dimension $m = 128$; this lesson writes it $d$. Because the vectors have length 1, a dot product is a cosine similarity.

## Intuition: a matrix instead of a vector

![A bi-encoder index stores one 128-number vector per passage. ColBERT stores one 128-number vector for each token, so a 100-token passage is a 100 by 128 matrix.](diagrams/39.3-one-vector-vs-tokens.svg "One vector per passage, or one vector per token.")

The difference is in the shape of what gets stored. Pooling all tokens into one vector throws away which token said what. Keeping one vector per token keeps that information, at the price of a 100-fold larger index for a 100-token passage. The index is the largest cost in this design, and most of the engineering in ColBERT goes into shrinking it.

## Worked example: MaxSim by hand

Each query token asks one question: which document token matches me best? The answer is the largest dot product over the document tokens. The score is the sum of those maxima over the query tokens:

$$
S(Q, D) = \sum_{i=1}^{|E_Q|} \max_{j=1}^{|E_D|} \; E_{Q,i} \cdot E_{D,j}^{\top}
$$

Here $E_{Q,i}$ is the $i$-th query token vector and $E_{D,j}$ is the $j$-th document token vector. Use 2-D unit vectors so the numbers are easy to check: three query tokens and four document tokens.

![A 3 by 4 matrix of dot products. The largest entry in each row is highlighted: 0.80, 1.00 and 0.96. Their sum is 2.76.](diagrams/39.3-maxsim-worked.svg "Rows are query tokens, columns are document tokens. Each row keeps its best match.")

Compute the matrix $S = Q D^\top$ in NumPy. The visible code blocks on this page run in the browser, so each one imports what it needs.

```python
import numpy as np

def maxsim(Q, D):
    """Sum over query tokens of the best dot product with any document token."""
    return float((Q @ D.T).max(axis=1).sum())

Q = np.array([[1.0, 0.0],        # query token q1
              [0.0, 1.0],        # query token q2
              [0.6, 0.8]])       # query token q3
D = np.array([[0.8, 0.6],        # document token d1
              [0.0, 1.0],        # d2
              [-1.0, 0.0],       # d3
              [0.6, -0.8]])      # d4

S = Q @ D.T                      # S[i, j] = q_i . d_j
np.set_printoptions(precision=2, suppress=True)
print(S)
print("best document token per query token:", S.argmax(axis=1))
print("best score per query token:", S.max(axis=1))
print("MaxSim score:", round(maxsim(Q, D), 4))
```

```output
[[ 0.8   0.   -1.    0.6 ]
 [ 0.6   1.    0.   -0.8 ]
 [ 0.96  0.8  -0.6  -0.28]]
best document token per query token: [0 1 0]
best score per query token: [0.8  1.   0.96]
MaxSim score: 2.76
```

Check the first row by hand: $q_1 = (1, 0)$ dotted with $d_1 = (0.8, 0.6)$ gives 0.8. The maximum of $\{0.8, 0, -1, 0.6\}$ is 0.8, so $q_1$ matches $d_1$. The score is $0.80 + 1.00 + 0.96 = 2.76$.

> [!KEY-INSIGHT]
> The three query tokens may match three different document tokens. Nothing forces them to match one passage vector. This is what "late interaction" means: the query and document interact per token, after both have been encoded.

## Why the max matters: a test with known answers

Pooling is the usual way to get a single vector. To see what it costs, build a synthetic test where the answer is known. There are 200 random "concept" directions in 128 dimensions. A token is a noisy copy of one concept (cosine with its concept about 0.89). The query has two concept tokens, $a$ and $b$. The relevant passage contains $a$ and $b$. The distractor contains $a$ and a different concept $c$. Both passages have $L$ tokens in total, and the rest are filler concepts. The test asks: does the relevant passage score higher?

This is a mechanism test, not a retrieval benchmark. The concept vectors are random, and no BERT encoder is run (no model weights are available here). The mean-pooled baseline is the simplest pooling, with no training, so it is a weak bi-encoder.

```python
import numpy as np

def unit(x):
    return x / np.linalg.norm(x, axis=-1, keepdims=True)

def maxsim(Q, D):
    return float((Q @ D.T).max(axis=1).sum())

def cosine(u, v):
    return float(u @ v / (np.linalg.norm(u) * np.linalg.norm(v)))

rng = np.random.default_rng(39)
DIM, N_CONCEPTS = 128, 200
concepts = unit(rng.standard_normal((N_CONCEPTS, DIM)))

def token(i):
    # a noisy copy of concept i; cosine with the concept is about 0.89
    return unit(concepts[i] + 0.5 * rng.standard_normal(DIM) / np.sqrt(DIM))

def trial(L):
    a, b, c = rng.choice(N_CONCEPTS, size=3, replace=False)
    others = np.setdiff1d(np.arange(N_CONCEPTS), [a, b, c])
    Q = np.stack([token(a), token(b)])
    fill1 = rng.choice(others, size=L - 2)
    fill2 = rng.choice(others, size=L - 2)
    rel = np.stack([token(a), token(b)] + [token(k) for k in fill1])
    dis = np.stack([token(a), token(c)] + [token(k) for k in fill2])
    ms = maxsim(Q, rel) > maxsim(Q, dis)
    mp = cosine(Q.mean(0), rel.mean(0)) > cosine(Q.mean(0), dis.mean(0))
    return ms, mp

print("accuracy: relevant passage beats distractor (400 trials per length)")
for L in (4, 16, 64, 256):
    res = np.array([trial(L) for _ in range(400)])
    print(f"L={L:3d}  MaxSim={res[:, 0].mean():.3f}  mean-pool={res[:, 1].mean():.3f}")
```

```output
accuracy: relevant passage beats distractor (400 trials per length)
L=  4  MaxSim=1.000  mean-pool=1.000
L= 16  MaxSim=1.000  mean-pool=0.870
L= 64  MaxSim=1.000  mean-pool=0.728
L=256  MaxSim=1.000  mean-pool=0.637
```

![Grouped bars for passage lengths 4, 16, 64 and 256. MaxSim is 1.00 at every length. Mean-pooled accuracy falls from 1.00 to 0.87, 0.73 and 0.64.](diagrams/39.3-dilution.svg "Accuracy in the synthetic test. The dashed line is chance (0.5).")

Mean pooling dilutes the matched concepts. As $L$ grows, each matched concept makes up a smaller share of the mean, and the filler, which differs between the two passages, becomes the main source of difference. This is a first-principles explanation; the test shows the effect, not its exact scaling. MaxSim does not dilute, because the best match for $a$ is still $a$, however many filler tokens there are. In this test, MaxSim is also monotone: adding a document token can only raise the maximum, so it never lowers the score. The next block checks that on random data, and also measures what float16 storage does to the scores.

```python
import numpy as np

def unit(x):
    return x / np.linalg.norm(x, axis=-1, keepdims=True)

def maxsim(Q, D):
    return float((Q @ D.T).max(axis=1).sum())

rng2 = np.random.default_rng(7)
Q = unit(rng2.standard_normal((32, 128)))      # 32 query tokens, as ColBERT pads queries to 32
D = unit(rng2.standard_normal((100, 128)))     # 100 document tokens
base = maxsim(Q, D)
extra = maxsim(Q, np.vstack([D, unit(rng2.standard_normal((1, 128)))]))
print("before adding one document token:", round(base, 4), " after:", round(extra, 4))
print("non-decreasing:", extra >= base)

violations = 0
for _ in range(500):
    Qt = unit(rng2.standard_normal((8, 128)))
    Dt = unit(rng2.standard_normal((20, 128)))
    more = np.vstack([Dt, unit(rng2.standard_normal((5, 128)))])
    violations += maxsim(Qt, more) < maxsim(Qt, Dt)
print("monotonicity violations in 500 random cases:", violations)

docs = unit(rng2.standard_normal((200, 100, 128)))
s32 = np.array([maxsim(Q, d) for d in docs])
Q16 = Q.astype(np.float16).astype(np.float32)
s16 = np.array([maxsim(Q16, d.astype(np.float16).astype(np.float32)) for d in docs])
print(f"float16 storage: max score error = {np.abs(s32 - s16).max():.2e}")
print("top-1 document unchanged:", bool(s32.argmax() == s16.argmax()))
```

```output
before adding one document token: 7.2099  after: 7.2099
non-decreasing: True
monotonicity violations in 500 random cases: 0
float16 storage: max score error = 3.92e-04
top-1 document unchanged: True
```

The 16-bit float (float16, written fp16) result is a single random test with 200 documents. It shows that the storage error was small here, not that it is always small. A safe habit is to check the top-$k$ order on your own data after compressing.

## Cost: where the work goes

Three quantities matter: compute per query, index size, and how both grow with corpus size $N$. Assume a BERT-base-sized encoder with about $1.1 \times 10^8$ parameters (an assumption, not a measurement), and count one multiply-add as 2 floating-point operations (FLOPs). Use $L_Q = 32$ query tokens, $L_D = 100$ document tokens and $d = 128$.

```python
P = 1.1e8                    # encoder parameters (assumption)
Lq, Ld, d = 32, 100, 128
N = 1_000_000                # documents in the corpus

cross_pair = 2 * P * (Lq + Ld)     # cross-encoder: one full pass per query-document pair
maxsim_doc = 2 * Lq * Ld * d       # MaxSim: one document, after its tokens are precomputed
print(f"cross-encoder, one pair : {cross_pair:.2e} FLOPs")
print(f"MaxSim, one document    : {maxsim_doc:.2e} FLOPs")
print(f"ratio                   : {cross_pair / maxsim_doc:,.0f}x")
print(f"per query, N = {N:,}")
print(f"  cross-encoder on every document : {N * cross_pair:.2e}")
print(f"  MaxSim brute force              : {N * maxsim_doc:.2e}")
print(f"  bi-encoder (query pass + dots)  : {2 * P * Lq + N * 2 * d:.2e}")
print(f"index, {Ld} tokens per document, fp32: {N * Ld * d * 4 / 1e9:.1f} GB")
print(f"index, {Ld} tokens per document, fp16: {N * Ld * d * 2 / 1e9:.1f} GB")
```

```output
cross-encoder, one pair : 2.90e+10 FLOPs
MaxSim, one document    : 8.19e+05 FLOPs
ratio                   : 35,449x
per query, N = 1,000,000
  cross-encoder on every document : 2.90e+16
  MaxSim brute force              : 8.19e+11
  bi-encoder (query pass + dots)  : 7.30e+09
index, 100 tokens per document, fp32: 51.2 GB
index, 100 tokens per document, fp16: 25.6 GB
```

![Log-scale bars of FLOPs per query over one million documents: cross-encoder 2.9e16, MaxSim brute force 8.2e11, bi-encoder 7.3e9.](diagrams/39.3-cost-per-query.svg "Each gridline is 100 times the one before. Bar length is proportional to log10 of the value.")

The cross-encoder is roughly 35,000 times more expensive per document than MaxSim here, so it can only be run over a short list. MaxSim is cheaper per document, but brute force over a million documents still costs $8.2 \times 10^{11}$ FLOPs per query, which is why LI systems add candidate generation. Khattab and Zaharia (2020) report about two orders of magnitude lower latency and four orders of magnitude fewer FLOPs per query than BERT-based re-rankers, but the abstract does not name the baseline, so treat those figures as the paper's claim and not as a number you can reproduce from this page.

## Making the index smaller and the search faster

Santhanam et al. (2022) introduced ColBERTv2, which keeps the late interaction design and compresses the stored token vectors. Their abstract reports a space reduction of "6--10×" for late interaction models. The abstract describes an "aggressive residual compression mechanism" but gives no bit widths or codebook sizes, so check the paper before quoting parameters. The same group's PLAID engine (Santhanam et al., 2022, preprint) prunes candidates with centroids before the full MaxSim, and reports latency reductions of "up to 7×" on a GPU (graphics processing unit) and "45×" on a CPU (central processing unit), relative to ColBERTv2. "Up to" means the best case, and the abstract gives no quality numbers for those settings.

> [!TRAP]
> Scores are not comparable across queries. MaxSim is a sum over query tokens, so a 32-token query gets a larger score than a 4-token query for the same match quality. Rank passages within one query only, or normalise by $|Q|$ if you must compare across queries.

> [!TRAP]
> MaxSim does not normalise by passage length. Adding a token to a document can never lower its score (checked above). This is a reasoned property, not a measured bias, but it means long passages have an advantage that a length penalty would remove. Decide whether your system wants that.

> [!TRAP]
> Do not assume the test above reflects a trained model. The concept vectors are random, the filler is structureless, and no BERT encoder ran. Real accuracy depends on the encoder, the training data and the benchmark, none of which this page measured.

> [!WARNING]
> Brute-force MaxSim over a whole corpus is a FLOP count, not a latency. Measure on your hardware before choosing a design.

## Summary

- ColBERT keeps one normalised vector per token and scores a query by summing, over query tokens, the best dot product with any document token.
- For a 3-by-4 example, the row maxima are 0.80, 1.00 and 0.96, so the score is 2.76.
- In a synthetic test with known answers, pooled vectors lose accuracy as passages grow (1.00 to 0.64 at $L = 256$), while MaxSim stays at 1.00.
- Storage is large: one vector per token gives 51.2 GB at 32-bit precision (fp32) for one million 100-token passages, and 16-bit storage (fp16) halves that.
- Brute-force MaxSim is still about $8 \times 10^{11}$ FLOPs per query over a million documents, so practical systems prune candidates first.

## Quiz time

### Question 1: Calculation

Using the worked example matrix, what is the MaxSim score if query token $q_2$ is replaced by the zero vector $(0, 0)$?

<details><summary>Solution</summary>

The row for $q_2$ becomes all zeros, so its maximum is 0. The other rows still give 0.80 and 0.96. The score is $0.80 + 0 + 0.96 = 1.76$.

</details>

### Question 2: Prediction

You append a copy of the document token that already gives the best match for query token $q_1$. Does the MaxSim score change, and why?

<details><summary>Solution</summary>

It does not change. The copy has the same dot product with $q_1$ as the original token, so the maximum over document tokens is unchanged. The other rows are also unchanged, so the sum is the same.

</details>

### Question 3: Bug-spotting

A colleague writes `score = (Q @ D.T).max(axis=0).sum()` and says it implements MaxSim. What is wrong?

<details><summary>Solution</summary>

`max(axis=0)` takes the maximum down each column, that is, over query tokens for each document token. The sum then runs over document tokens. MaxSim needs `max(axis=1)`, the best document token for each query token, summed over query tokens. The two versions give different numbers in general.

</details>

### Question 4: Explanation

Why can the document side of ColBERT be computed once and reused for many queries, but a cross-encoder cannot?

<details><summary>Solution</summary>

A ColBERT document token vector depends only on the document, so it can be precomputed and stored. A cross-encoder reads the query and document in one forward pass, so its document representation changes with every query, and it must be recomputed for each pair.

</details>

### Question 5: Calculation

An index holds one million passages of 100 tokens, each token a 128-dimensional vector stored in fp16 (2 bytes per number). How many gigabytes is it, ignoring overhead?

<details><summary>Solution</summary>

$10^6 \times 100 \times 128 \times 2 = 2.56 \times 10^{10}$ bytes, which is 25.6 GB.

</details>
