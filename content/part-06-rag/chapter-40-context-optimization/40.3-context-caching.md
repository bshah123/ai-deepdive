In this lesson you will learn why a hosted model application programming interface (API) can bill a repeated prompt at a fraction of its normal price, which rules decide whether a cache hits, and how to compute the break-even point where caching starts to save money. You will simulate the mechanism in NumPy and in plain Python.

**You need:** the key-value (KV) cache from Lesson 29.1, which stores each token's keys and values during generation, and the idea that API providers bill input tokens per token.

## The problem caching solves

A retrieval-augmented generation (RAG) assistant, which answers questions from a document store, sends the same long prefix on every call: about 20,000 tokens of tool definitions, system instructions and a policy document. Each call then adds a 200-token user question. Without caching, every call pays full price for all 20,200 input tokens, and the model runs prefill again over all of them. Storing and reusing these keys and values is a memory-management problem too; Kwon et al. (2023) report that inefficient KV-cache management wastes memory through fragmentation and redundant duplication. Prefill is the pass that computes keys and values for every prompt token before the first output token appears. The prefix never changes, so that work is repeated for nothing.

Provider prompt caching stores the keys and values for a prefix and reuses them when a later request starts with exactly the same tokens. You pay a reduced rate for the reused tokens, and the provider skips their prefill compute.

## A cache matches exact prefixes, not similar questions

Caching is not a semantic cache. Providers do not compare meanings or apply a similarity threshold. A hit requires the same tokens, in the same order, from the start of the prompt up to a marked point. Anthropic's documentation describes the order as `tools`, then `system`, then `messages`, and a change at any level invalidates that level and every level after it.

![Four prompt blocks drawn as boxes: on call 1 all are written; on call 3, after a date is added to the system block, only the tools block is reused and the rest are recomputed](diagrams/40.3-prefix-blocks.svg "Exact-prefix matching. The first changed block ends the reuse.")

Here is a small simulation of that rule. It stores every leading run of blocks it has seen, and a request reuses the longest one that matches.

```python
class PrefixCache:
    """Exact-prefix cache: a request hits on the longest leading run of blocks seen before."""
    def __init__(self):
        self.seen = set()                       # every leading prefix ever written

    def request(self, blocks):
        matched = 0
        for i in range(1, len(blocks) + 1):
            if tuple(blocks[:i]) in self.seen:
                matched = i
        for i in range(1, len(blocks) + 1):
            self.seen.add(tuple(blocks[:i]))
        return f"{matched} of {len(blocks)} blocks reused"

cache = PrefixCache()
tools = "tools: search(query)"
system = "system: You are a helpful assistant."
doc = "doc: 3,000 tokens of refund policy"
user = "user: What is the refund window?"
print("1 first call          :", cache.request([tools, system, doc, user]))
print("2 new user question   :", cache.request([tools, system, doc, "user: How do I log in?"]))
print("3 timestamp in system :", cache.request([tools, system + " Today is 2026-11-23.", doc, user]))
print("4 tool signature edit :", cache.request(["tools: search(query, limit)", system, doc, user]))
```

```output
1 first call          : 0 of 4 blocks reused
2 new user question   : 3 of 4 blocks reused
3 timestamp in system : 1 of 4 blocks reused
4 tool signature edit : 0 of 4 blocks reused
```

Call 2 changes only the last block, so the first three hit. Call 3 adds a date to the system block, which is the common production mistake: the cache keeps the tools block and recomputes everything after it. Anthropic writes entries only at breakpoints you mark (up to four per request), so the hit depth depends on where you place them. OpenAI places breakpoints automatically in its default mode. The invalidation rule is the same.

## Why only a prefix can be reused

The reason prefixes work is causal attention. In a decoder-only model, a token may attend only to itself and earlier tokens. The keys and values at position $p$ therefore depend only on tokens $0 \ldots p$. Two prompts that agree up to position $p$ have identical cached tensors up to $p$, so a provider can store them once.

The following NumPy model is a stand-in for a real large language model (LLM): two layers of causal self-attention with random weights. It is small enough to run in the browser, and it shows the mechanism exactly.

```python
import numpy as np

# A tiny 2-layer causal self-attention model with random weights (a stand-in for an LLM).
rng = np.random.default_rng(0)
D, VOCAB, LAYERS = 8, 100, 2
E = rng.normal(size=(VOCAB, D))                                   # token embeddings
Wq = rng.normal(size=(LAYERS, D, D)) / np.sqrt(D)
Wk = rng.normal(size=(LAYERS, D, D)) / np.sqrt(D)
Wv = rng.normal(size=(LAYERS, D, D)) / np.sqrt(D)

def forward(tokens, cache=None):
    """Process `tokens` after an optional cached prefix.
    cache: per-layer (K, V) arrays for the prefix. Returns (hidden states of the new tokens, updated cache)."""
    start = 0 if cache is None else cache[0][0].shape[0]
    x = E[tokens]
    new_cache = []
    for l in range(LAYERS):
        q, k, v = x @ Wq[l], x @ Wk[l], x @ Wv[l]
        if cache is not None:
            k = np.vstack([cache[l][0], k])
            v = np.vstack([cache[l][1], v])
        new_cache.append((k, v))
        scores = q @ k.T / np.sqrt(D)
        q_pos = np.arange(start, start + len(tokens))[:, None]
        k_pos = np.arange(k.shape[0])[None, :]
        scores = np.where(k_pos <= q_pos, scores, -np.inf)            # causal mask: no looking ahead
        w = np.exp(scores - scores.max(axis=1, keepdims=True))
        w = w / w.sum(axis=1, keepdims=True)
        x = x + w @ v                                                  # residual connection
    return x, new_cache

prefix = [3, 14, 15, 9, 26, 5, 35, 8]     # 8 tokens: tools + system prompt (the cacheable part)
suffix = [7, 9, 32, 38]                   # 4 tokens: the new user message

full, _ = forward(prefix + suffix)        # no cache: all 12 tokens are processed
_, cache = forward(prefix)                # write the prefix cache once: 8 tokens processed
part, _ = forward(suffix, cache)          # later call: only the 4 new tokens are processed
print("tokens processed without cache:", len(prefix) + len(suffix))
print("tokens processed with cache   :", len(suffix))
print("suffix matches full recompute :", np.allclose(full[-len(suffix):], part))

edited = [3, 14, 99, 9, 26, 5, 35, 8]     # one token changed, at position 2
_, c_orig = forward(prefix)
_, c_edit = forward(edited)
for layer in range(LAYERS):
    changed = [p for p in range(len(prefix))
               if not np.allclose(c_orig[layer][0][p], c_edit[layer][0][p])]
    print(f"layer {layer + 1}: cached keys that changed at positions", changed)
```

```output
tokens processed without cache: 12
tokens processed with cache   : 4
suffix matches full recompute : True
layer 1: cached keys that changed at positions [2]
layer 2: cached keys that changed at positions [2, 3, 4, 5, 6, 7]
```

The cached run processes 4 tokens instead of 12, and its suffix matches the full recomputation. The second half shows the invalidation boundary. A layer-1 key depends only on its own token's embedding, so the edit changes one key. A layer-2 key is computed from layer-1 outputs, which mix in earlier positions, so the same edit reaches positions 2 to 7. The edit never reaches positions 0 and 1, so their cache entries stay valid.

![Two rows of twelve token cells: an edit at position 2 changes one layer-1 key and six layer-2 keys (positions 2 to 7); positions 0 and 1 stay valid](diagrams/40.3-causal-reuse.svg "Why an early edit costs the whole suffix. Real models have dozens of layers, so the spread is wider.")

> [!KEY-INSIGHT]
> A cache entry is valid only if every token before it is unchanged. This is a property of causal attention, not a provider policy. Providers enforce this with an exact-match lookup. The property itself comes from the attention mask.

## The price model

Providers bill cached tokens with multipliers on the base input price. TTL means time to live: how long an entry survives after its last use. The rules below were read from each provider's documentation on 2026-11-23. Prices and minimums change, so check the pricing page before you budget.

| Provider | Cache write | Cache read | Lifetime | Notes from the docs |
|---|---|---|---|---|
| Anthropic | 1.25× (5-minute TTL), 2× (1-hour TTL) | 0.1× | 5 minutes by default; each hit refreshes it | Minimum cacheable length depends on the model (512 to 4,096 tokens in the current table) |
| OpenAI | 1.25× on current models (default 30-minute retention); none on earlier models | 0.1× on current models; model-dependent on earlier ones, up to 95% off | Earlier models: about 5 to 10 minutes idle, up to 1 hour, or up to 24 hours with extended retention | Automatic for supported models; cache hits come in 128-token steps on earlier models |
| Google Gemini | Implicit caching on by default for Gemini 2.5 and newer | Discount passed on automatically | Explicit caches have a time-to-live and a storage charge | Implicit minimum 2,048 tokens for the Gemini 2.5 Flash and Pro models listed; explicit rates not checked here |


The simulation below uses the Anthropic multipliers. Ten requests share a 20,000-token prefix, each adds 200 new tokens, and the gaps between requests are fixed in seconds. The cost counts input tokens in base-price units.

```python
# Input-side cost, in units of one uncached base input token.
# Multipliers as quoted in the Anthropic prompt-caching docs: a cache write costs 1.25x (5-minute TTL)
# or 2x (1-hour TTL) the base price; a cache read costs 0.1x. A hit refreshes the entry's lifetime.
PREFIX, NEW = 20_000, 200                 # shared prefix tokens; new uncached tokens per request
POLICIES = {
    "no cache":     {"write": 1.00, "read": 1.00, "ttl": 0},
    "5-minute TTL": {"write": 1.25, "read": 0.10, "ttl": 300},
    "1-hour TTL":   {"write": 2.00, "read": 0.10, "ttl": 3600},
}
GAPS = [60, 120, 240, 400, 100, 2000, 90, 3700, 30]   # seconds between requests; first request at t=0

def run(policy):
    p = POLICIES[policy]
    times = [0]
    for g in GAPS:
        times.append(times[-1] + g)
    last, cost, log = None, 0.0, []
    for t in times:
        alive = last is not None and p["ttl"] > 0 and t - last <= p["ttl"]
        if alive:
            cost += PREFIX * p["read"] + NEW
            log.append("hit")
        else:
            cost += PREFIX * p["write"] + NEW
            log.append("miss" if p["ttl"] else "full")
        last = t
    return cost, log

def ratio(policy, k):
    """Cost of k requests that share one prefix, relative to paying full price every time."""
    p = POLICIES[policy]
    cached = PREFIX * p["write"] + (k - 1) * PREFIX * p["read"] + k * NEW
    return cached / (k * (PREFIX + NEW))

for name in POLICIES:
    cost, log = run(name)
    print(f"{name:13s} total {cost:>10,.0f}   " + " ".join(log))
print()
for name in ("5-minute TTL", "1-hour TTL"):
    print(name, [round(ratio(name, k), 3) for k in (1, 2, 3, 5, 10, 100)])
```

```output
no cache      total    202,000   full full full full full full full full full full
5-minute TTL  total    114,000   miss hit hit hit miss hit miss hit miss hit
1-hour TTL    total     98,000   miss hit hit hit hit hit hit hit miss hit

5-minute TTL [1.248, 0.678, 0.488, 0.337, 0.223, 0.12]
1-hour TTL [1.99, 1.05, 0.736, 0.485, 0.297, 0.128]
```

The ratio list is the key result. A single request under the 5-minute policy costs 1.248 times the uncached price, so caching is a loss if the prefix is never reused. Two requests are enough to win under the 5-minute TTL. The 1-hour TTL needs three, because its write costs 2×. In general, with write multiplier $w$, read multiplier $r$, and $k$ requests within the lifetime, the cached prefix costs less when

$$
w + (k-1)\,r < k \quad\Longleftrightarrow\quad k > \frac{w - r}{1 - r}.
$$

With $w = 1.25$ and $r = 0.1$ the bound is $1.15 / 0.9 \approx 1.28$, so $k \geq 2$. With $w = 2$ it is $1.9 / 0.9 \approx 2.11$, so $k \geq 3$. The new 200 tokens are paid in both cases and cancel out.

The timeline below shows the same ten requests. Hits refresh the clock. The gap of 400 seconds misses the 5-minute cache, which then pays the write premium again. The 1-hour cache survives it. Its cost is still higher per write, so the savings come from fewer writes, not from cheaper ones.

![Ten requests on two lanes: the 5-minute lane misses four times, the 1-hour lane misses twice, with the gap in seconds written between requests](diagrams/40.3-timeline.svg "Hit or miss per request. The gap column shows the time since the previous request.")

![Three horizontal bars: no cache costs 202,000 units, the 5-minute TTL 114,000, the 1-hour TTL 98,000](diagrams/40.3-cost-bars.svg "Total input cost of the ten requests. Lower is cheaper; output tokens are excluded.")

The 1-hour policy is cheapest here only because the gaps are dense enough that it writes twice. Latency also falls when the prefill is skipped, but this lesson does not measure it.

## Common traps

> [!TRAP]
> **Dynamic content before static content.** A timestamp, a user name or a random request identifier (ID) placed in the system block invalidates every later block on every call. Put static content first and dynamic content last.

> [!TRAP]
> **Assuming a hit from a similar question.** Caching matches tokens, not meaning. "What is the refund window?" and "How long is the refund period?" share no cached prefix beyond the static blocks.

> [!TRAP]
> **Paying the write premium without reuse.** A single call with a marked prefix costs more than an uncached call under both Anthropic TTLs (1.248 and 1.99 in the output above).

> [!TRAP]
> **Short prompts that never cache.** Anthropic's documentation says requests below the minimum length are processed without caching and return no error. Check the usage fields for cache reads and writes. Both zero means no cache.

> [!TRAP]
> **Counting the cache lifetime from the end of a response.** The Anthropic documentation measures the lifetime from the start of the request that writes or reads the entry, so a long streamed response can expire the cache before the next call.

## Summary

- Provider caching reuses the keys and values of an exact token prefix, so anything changed early in the prompt invalidates everything after it.
- Causal attention makes this boundary exact: a key at position $p$ depends only on tokens up to $p$.
- Write multipliers of 1.25× (5-minute) or 2× (1-hour) and a read multiplier of 0.1× give a break-even at $k \geq 2$ and $k \geq 3$ requests.
- Put static content first; check the cache usage fields rather than assuming a hit.

## Quiz time

### Question 1: Break-even for a new policy

A provider charges 1.5× to write a cache entry and 0.2× to read one. How many requests must share a prefix before caching is cheaper than paying full price each time?

<details>
<summary>Solution</summary>

Use $k > (w - r) / (1 - r) = (1.5 - 0.2) / (1 - 0.2) = 1.3 / 0.8 = 1.625$. The smallest integer is $k = 2$. Check $k = 2$: $1.5 + 0.2 = 1.7 < 2$, so caching wins. Check $k = 1$: $1.5 > 1$, so it loses.

</details>

### Question 2: Predict the invalidation

A prompt has 8 cached prefix tokens. An edit changes the token at position 5. Using the two-layer model in this lesson, which cached keys change in layer 1, and which in layer 2?

<details>
<summary>Solution</summary>

Layer 1 changes only position 5, because a layer-1 key depends only on its own token's embedding. Layer 2 changes positions 5, 6 and 7, because its keys depend on layer-1 outputs that mix in earlier positions, so the edit reaches every later position. Positions 0 to 4 stay valid in both layers. The output of the lesson's model, with the edit at position 2, shows the same pattern: layer 1 changes [2] and layer 2 changes [2 to 7].

</details>

### Question 3: Bug-spotting

A team puts `f"Today is {datetime.now()}"` at the start of the system prompt and sees a cache hit rate of 0%. What is wrong, and how do you fix it?

<details>
<summary>Solution</summary>

The timestamp changes on every call, so the very first block differs and the exact-prefix match fails at position zero. Every later block is invalidated too. Move the timestamp to the end of the prompt, after the static tools, system instructions and documents. The static prefix then hits on every call.

</details>

### Question 4: Explanation

Why does a cache keyed on cosine similarity of question embeddings not match how provider caching works?

<details>
<summary>Solution</summary>

Provider caching reuses stored keys and values, which were computed from exact tokens. A reused entry is correct only if every earlier token is identical, because attention at each position depends on all earlier positions. A similarity threshold would return keys computed from a different prefix, so the model would attend to tokens it never saw. The cache would be wrong, not just less accurate.

</details>
