A LangChain pipeline is a chain of steps in which each step receives the output of the one before it. In this lesson you will compose such a chain with the `|` operator of LangChain Expression Language (LCEL), call it with `invoke` and `batch`, and recognise the two mistakes that break most chains: a value of the wrong type passed silently along, and a function given its input in the wrong shape.

**You need:** Python dictionaries (Lesson 6.1) and functions (Lesson 7.1). The visible code runs in your browser with no application programming interface (API) key and no model download. The real `langchain-core` package appears only in a collapsed block.

## The problem a runnable solves

LangChain has several kinds of component: prompt templates, chat models, output parsers, retrievers and ordinary Python functions. Each has its own calling convention. Joining two of them by hand means writing glue code that unwraps one result and reshapes it for the next. Every join is a place where a shape can be wrong, and the glue multiplies as components are added.

LangChain 0.3 addresses this with the **Runnable** interface: one base class that every component implements. `invoke` runs one input. `batch` runs a list of inputs. `stream` yields output in chunks (Lesson 43.2 covers it), and each method has an async twin (`ainvoke`, `abatch`, `astream`). In `langchain-core` 0.3.86, the release we ran, all six are defined on `RunnableLambda`, which wraps an ordinary function. **LCEL** is the `|` operator that joins two runnables into a new runnable, so a whole chain is called with one `invoke`. The payoff is that the chain becomes a single object: you can pass it to a web handler, batch it, or inspect its steps without knowing what each one does internally.

## Intuition: a pipeline is one function

![Four pipeline steps in a row, each passing its value to the next; the third step receives a PromptValue rather than a string](diagrams/43.1-data-types.svg "Each step returns a value, and the next step receives exactly that value.")

Read a pipeline as a single function built from smaller ones. Its input is what the first step takes, its output is what the last step returns, and in between each output is the next input. The prompt template takes a dictionary of variables and returns a `StringPromptValue`: a wrapper around the filled-in text. The wrapper is not a `str`. The next step is an ordinary function that formats its argument with an f-string. The f-string does not fail. It formats the wrapper object, so the output looks almost right and is not.

## Worked example by hand

Trace the chain for the input `{"input_text": "Hello, LangChain!"}`:

1. The template substitutes `input_text` into `Process this input: {input_text}`. The result is a `StringPromptValue` whose text is `Process this input: Hello, LangChain!`.
2. The function receives that wrapper. The f-string `f"Model processed: {x}"` formats the wrapper, which prints its field: `Model processed: text='Process this input: Hello, LangChain!'`.
3. One call fixes it. `x.to_string()` returns the plain text, so the result is `Model processed: Process this input: Hello, LangChain!`.

No exception was raised at any step. A check that only tests whether the final output is a non-empty string would pass the broken chain. To catch this kind of error, look at the type that each step returns, which is what the diagram's labels show.

## The `|` operator, under the hood

Python evaluates `a | b` by calling `a.__or__(b)`. If that returns `NotImplemented`, Python calls `b.__ror__(a)` instead. In langchain-core 0.3.86, `Runnable.__or__` returns `RunnableSequence(self, coerce_to_runnable(other))` (`runnables/base.py`, line 636). `coerce_to_runnable` is what lets a plain function or a dict stand on either side of `|`: a callable becomes a `RunnableLambda`, and a dict becomes a `RunnableParallel`.

A dict literal on the left is the subtle case. `dict.__or__` is the merge operator added by Python Enhancement Proposal (PEP) 584, and the PEP's reference sketch returns `NotImplemented` when the right operand is not a dict. The Python language reference says that when a binary method returns `NotImplemented`, the interpreter tries the reflected method of the other operand. So `{"k": f} | b` ends up in `b.__ror__`, which builds a sequence whose first step is the coerced dict. The result is the same kind of object as in the first case, so the rest of the chain behaves identically. The figure shows both cases.

![Two rows: a runnable on the left calls a.__or__ and builds a RunnableSequence; a dict on the left returns NotImplemented, so b.__ror__ builds a RunnableSequence with the coerced dict first](diagrams/43.1-pipe-operator.svg "What the | operator builds, in two cases.")

The `coerce` function is what makes the operator convenient. Without it, every step would have to be wrapped by hand in an object with an `invoke` method, and the chain would be twice as long to write.

The mini-LCEL below reproduces this mechanism in about sixty lines. It is a teaching model, not LangChain's code: it has no types, no config and no callbacks.

```python
from typing import Any, Callable

class Runnable:
    """Anything with invoke() can take part in a pipeline."""

    def __or__(self, other):                  # runnable | other
        return Sequence([self, coerce(other)])

    def __ror__(self, other):                 # dict | runnable, after dict.__or__ gave NotImplemented
        return Sequence([coerce(other), self])

    def batch(self, inputs):
        return [self.invoke(x) for x in inputs]

class Lambda(Runnable):
    def __init__(self, fn: Callable[[Any], Any]):
        self.fn = fn

    def invoke(self, x):
        return self.fn(x)

class Template(Runnable):
    def __init__(self, text: str):
        self.text = text

    def invoke(self, values: dict) -> str:
        return self.text.format(**values)

class Sequence(Runnable):
    def __init__(self, steps):
        self.steps = steps

    def __or__(self, other):                  # flatten: a | b | c is one sequence of three steps
        return Sequence(self.steps + [coerce(other)])

    def invoke(self, x):
        for step in self.steps:
            x = step.invoke(x)                # each step receives the previous output
        return x

class Parallel(Runnable):
    def __init__(self, branches):
        self.branches = branches

    def invoke(self, x):
        return {k: r.invoke(x) for k, r in self.branches.items()}

def coerce(thing):
    if isinstance(thing, Runnable):
        return thing
    if isinstance(thing, dict):               # a dict literal becomes a parallel fan-out
        return Parallel({k: coerce(v) for k, v in thing.items()})
    if callable(thing):
        return Lambda(thing)
    raise TypeError(f"cannot coerce {type(thing).__name__}")

def fake_model(prompt: str) -> str:           # stands in for a chat model: no network
    return f"Model processed: {prompt}"

passthrough = Lambda(lambda x: x)
prompt = Template("Process this input: {input_text}")
pipe = {"input_text": passthrough} | prompt | fake_model

print("steps:", [type(s).__name__ for s in pipe.steps])
print("invoke:", pipe.invoke("Hello, LangChain!"))
print("batch:", pipe.batch(["a", "bb"]))
```

```output
steps: ['Parallel', 'Template', 'Lambda']
invoke: Model processed: Process this input: Hello, LangChain!
batch: ['Model processed: Process this input: a', 'Model processed: Process this input: bb']
```

Three steps, not two: the dict became a `Parallel`, and the flattening in `Sequence.__or__` kept a single sequence. The passthrough receives the string and the `Parallel` wraps it as `{"input_text": ...}` for the template.

## Batch and fan-out

![Three inputs 3, 1 and 2 pass through x times 2 and come out as 6, 2 and 4 in the same order](diagrams/43.1-batch-order.svg "batch returns one output per input, in input order.")

`batch` calls `invoke` once per input. The langchain-core default runs these calls on a thread pool (its docstring says so), and the result list keeps the input order: inputs 3, 1, 2 come back as 6, 2, 4. The mini-LCEL runs them one after another, but the output order is the same. Each input still produces its own call to the step, so `batch` changes how the calls are scheduled, not what each call does.

A dict on the left of `|` is a fan-out. Every branch receives the same input, and the outputs are merged into a dict under the branch keys.

![One input string fans out to two branches, upper and length, and their results merge into one dict](diagrams/43.1-parallel-fanout.svg "RunnableParallel: the same input to every branch, one dict out.")

The same chain with the real library, using `FakeListLLM`, a langchain-core class that returns canned answers in turn so that no network is needed:

<details><summary>Run locally: needs pip install langchain-core==0.3.86</summary>

```python
from langchain_core.runnables import RunnableLambda, RunnablePassthrough
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.language_models import FakeListLLM

prompt = PromptTemplate.from_template("Process this input: {input_text}")

# The dict on the left becomes a RunnableParallel: step 1 of 4
chain = ({"input_text": RunnablePassthrough()} | prompt
         | RunnableLambda(lambda pv: f"Model processed: {pv.to_string()}") | StrOutputParser())
print("steps:", len(chain.steps), [type(s).__name__ for s in chain.steps])
print("invoke:", repr(chain.invoke("Hello, LangChain!")))
print("prompt output:", type(prompt.invoke({"input_text": "x"})).__name__)

llm_chain = prompt | FakeListLLM(responses=["First.", "Second."]) | StrOutputParser()
print("batch:", llm_chain.batch([{"input_text": "a"}, {"input_text": "b"}]))
```

```output
steps: 4 ['RunnableParallel', 'PromptTemplate', 'RunnableLambda', 'StrOutputParser']
invoke: 'Model processed: Process this input: Hello, LangChain!'
prompt output: StringPromptValue
batch: ['First.', 'Second.']
```

</details>

## Common traps

> [!TRAP] **A prompt returns a wrapper, not a string.** `PromptTemplate.invoke` returns a `StringPromptValue`. A plain function that formats it prints `text='...'` instead of failing. Call `.to_string()` first, or pass the value to a component that accepts prompt values, such as a chat model.

> [!TRAP] **`RunnableLambda` passes its whole input as one argument.** `RunnableLambda(add_numbers).invoke({"a": 5, "b": 3})` raises `TypeError: add_numbers() missing 1 required positional argument: 'b'`. Unpack inside the function: `RunnableLambda(lambda d: add_numbers(d["a"], d["b"]))` returns `8`.

> [!TRAP] **A dict on the left of `|` is a fan-out, not a dict value.** `{"k": f} | g` runs `f` on the input and gives `g` a dict of results. If you wanted `g` to receive the dictionary itself, wrap it in a `RunnableLambda`.

> [!TRAP] **A missing template variable fails at the prompt.** `PromptTemplate.from_template("...{input_text}").invoke({"text": "x"})` raises `KeyError` with the message "Input to PromptTemplate is missing variables {'input_text'}". The error names the first step that failed, so start debugging there.

> [!TRAP] **Single-variable templates accept a bare string.** With langchain-core 0.3.86, `PromptTemplate.invoke("Hello")` works for a template with one variable. Do not rely on this once a second variable is added: pass a dict by name.

## Summary

- A runnable exposes `invoke`, `batch`, `stream` and their async twins; LCEL's `|` joins two runnables into one runnable, so a chain has the same interface as its parts.
- `a | b` calls `a.__or__(b)`, which returns a `RunnableSequence`. A dict literal on the left is coerced to a `RunnableParallel` after `dict.__or__` returns `NotImplemented`.
- Each step receives exactly the previous step's output. A prompt template returns a prompt value, not a `str`, so call `.to_string()` where a string is needed.
- `RunnableLambda` passes its whole input as one argument; unpack a dict inside the function.
- `batch` returns outputs in input order, and a dict on the left fans one input out to several branches.

## Quiz time

### Question 1: Prediction

What does `RunnableLambda(lambda x: x * 2).batch([3, 1, 2])` return, with `RunnableLambda` from langchain-core?

<details><summary>Show Solution</summary>

It returns `[6, 2, 4]`. `batch` calls `invoke` on each input and keeps the input order.

</details>

### Question 2: Find the bug

A colleague writes `RunnableLambda(add_numbers).invoke({"a": 5, "b": 3})` for `def add_numbers(a, b): return a + b`. What happens, and how do you fix it?

<details><summary>Show Solution</summary>

It raises `TypeError`: the whole dict arrives as one argument, so `b` is missing. Wrap the call so the function receives two values: `RunnableLambda(lambda d: add_numbers(d["a"], d["b"]))`, which returns `8`.

</details>

### Question 3: Explain the output

A chain `prompt | RunnableLambda(f) | StrOutputParser()` gives `f` a `StringPromptValue`, and `f` builds an f-string from it. Why does adding `StrOutputParser()` at the end not fix `f`'s input?

<details><summary>Show Solution</summary>

A parser transforms the output of the step it follows. It sits after `f`, so it cannot change what `f` received. The fix belongs before `f`: call `.to_string()` on the prompt value inside `f`, or use a component that accepts prompt values.

</details>

### Question 4: Count the steps

How many steps does `({"input_text": RunnablePassthrough()} | prompt | RunnableLambda(g) | StrOutputParser())` have, and which one is the dict?

<details><summary>Show Solution</summary>

Four. Each `|` adds one step to a flat `RunnableSequence`, and the first step is the `RunnableParallel` built from the dict. The real run in the collapsed block above prints `steps: 4`.

</details>
