In this lesson you will predict the wall-clock time of a pipeline whose branches run in parallel, read the chunks that `stream()` yields, and choose between `invoke`, `ainvoke`, `batch` and `abatch`. Every timing here was measured with langchain-core 0.3.86 on one machine. The ratios matter more than the exact seconds.

**You need:** the Runnable interface and the `|` operator from Lesson 43.1, and the basics of `async def` and `await`.

## The problem

A retrieval-augmented generation (RAG) answer usually needs several independent calls: retrieve passages, look up metadata, check a policy. Run one after another, their latencies add up. Users also want the first words of an answer before the last word exists. And a batch job may run the same chain on thousands of questions. LangChain Expression Language (LCEL) covers these three needs with one class, `RunnableParallel`, and four methods that every runnable shares.

| Need | Use | What it does |
|---|---|---|
| Several independent steps on one input | `RunnableParallel` | Each branch gets the same input; results come back under the same keys |
| Output before the end | `stream()`, `astream()` | Yields chunks as the steps produce them |
| Many inputs | `batch()`, `abatch()` | One call per input, run concurrently |
| Waiting without blocking other work | `ainvoke()` | The awaitable form of `invoke()` |

## Fan-out: a dictionary of runnables

A `RunnableParallel` is a dictionary of runnables. It sends the same input to each branch and returns a dictionary with the same keys.

![One input box feeds three branch boxes, which feed one output dictionary with the keys upper, length and words](diagrams/43.2-fan-out.svg "RunnableParallel fans one input out to independent branches and gathers the results under their keys.")

The mechanism first, in plain Python that runs in the browser:

```python
def parallel(steps, x):
    """Give the same input to every step and collect the results under the same keys."""
    return {key: step(x) for key, step in steps.items()}

steps = {
    "upper": lambda s: s.upper(),
    "length": len,
    "words": lambda s: s.split(),
}
print(parallel(steps, "retrieval augmented generation"))
```

```output
{'upper': 'RETRIEVAL AUGMENTED GENERATION', 'length': 30, 'words': ['retrieval', 'augmented', 'generation']}
```

The mini version runs the steps one after another. The real class is next. It needs the package, so it sits in a collapsed block.

<details><summary>Run locally: needs pip install langchain-core==0.3.86</summary>

```python
from langchain_core.runnables import RunnableParallel, RunnableLambda

par = RunnableParallel(
    upper=RunnableLambda(lambda s: s.upper()),
    length=RunnableLambda(len),
    words=RunnableLambda(lambda s: s.split()),
)
print(par.invoke("retrieval augmented generation"))
```

```output
{'upper': 'RETRIEVAL AUGMENTED GENERATION', 'length': 30, 'words': ['retrieval', 'augmented', 'generation']}
```

</details>

Branches are independent. A branch cannot read a sibling's output. If one step needs another's result, chain them with `|` instead.

## Parallel is not fast by itself

Three branches, each waiting 0.3 s to stand in for a network call. Measured wall-clock times:

- Sequential `invoke()` calls, one after another: 0.9 s.
- `RunnableParallel.invoke()` with ordinary functions: 0.3 s.
- `RunnableParallel.ainvoke()` with `async def` branches that `await asyncio.sleep`: 0.3 s.
- `RunnableParallel.ainvoke()` with ordinary functions: 0.3 s.
- `RunnableParallel.ainvoke()` with `async def` branches that call `time.sleep`: 0.9 s.

![Five timeline rows: sequential calls take 0.9 s, the three parallel variants take 0.3 s, and a coroutine that calls time.sleep takes 0.9 s](diagrams/43.2-timeline.svg "Measured wall time for three 0.3 s branches. Bars are drawn at their nominal length; the totals include overhead.")

The source explains the first two rows. In `langchain_core/runnables/base.py`, `RunnableParallel.invoke` submits each step to a `ThreadPoolExecutor`. `ainvoke` schedules every step with `asyncio.gather`. An ordinary function inside `ainvoke` is run in a thread through `run_in_executor`, so it still overlaps with the others.

The last row is the trap. A coroutine that calls a blocking function holds the event loop, so no other branch can run until it returns. The Python asyncio documentation says that blocking code in a coroutine delays "all concurrent asyncio Tasks and IO operations" (asyncio developer guide, "Running Blocking Code").

<details><summary>Run locally: needs pip install langchain-core==0.3.86</summary>

```python
import asyncio, time
from langchain_core.runnables import RunnableParallel, RunnableLambda

def sync_branch(label, d):
    def f(x):
        time.sleep(d)            # blocking wait, like a slow network call
        return label
    return RunnableLambda(f)

def async_branch(label, d):
    async def f(x):
        await asyncio.sleep(d)   # cooperative wait: the loop can run other tasks
        return label
    return RunnableLambda(f)

def async_blocking(label, d):
    async def f(x):
        time.sleep(d)            # blocking call inside a coroutine: the loop stops
        return label
    return RunnableLambda(f)

def timed(fn):
    t = time.perf_counter()
    fn()
    return time.perf_counter() - t

D = 0.3
seq = [sync_branch(f"b{i}", D) for i in range(3)]
print("sequential invoke:", round(timed(lambda: [b.invoke({}) for b in seq]), 1))
par = RunnableParallel({f"b{i}": sync_branch(f"b{i}", D) for i in range(3)})
print("parallel invoke:", round(timed(lambda: par.invoke({})), 1))
pa = RunnableParallel({f"b{i}": async_branch(f"b{i}", D) for i in range(3)})
print("parallel ainvoke, asyncio.sleep:", round(timed(lambda: asyncio.run(pa.ainvoke({}))), 1))
ps = RunnableParallel({f"b{i}": sync_branch(f"b{i}", D) for i in range(3)})
print("parallel ainvoke, ordinary functions:", round(timed(lambda: asyncio.run(ps.ainvoke({}))), 1))
pb = RunnableParallel({f"b{i}": async_blocking(f"b{i}", D) for i in range(3)})
print("parallel ainvoke, blocking coroutine:", round(timed(lambda: asyncio.run(pb.ainvoke({}))), 1))
```

```output
sequential invoke: 0.9
parallel invoke: 0.3
parallel ainvoke, asyncio.sleep: 0.3
parallel ainvoke, ordinary functions: 0.3
parallel ainvoke, blocking coroutine: 0.9
```

</details>

Timings vary by machine. On this machine, the pattern is the lesson: parallel branches take about as long as the slowest branch, and a blocking call inside a coroutine serializes them again. Your numbers should show the same ratios.

Work that is CPU-bound, such as parsing a large file or computing an embedding in plain Python, is a different case. The asyncio guide says blocking code should not run directly on the event loop and suggests an executor (same section of the asyncio guide). An executor helps with waiting. It does not make computation faster, because the threads still share one interpreter.

## Streaming: chunks come from whichever branch produced them

`RunnableParallel.stream()` does not wait for every branch. Each chunk it yields is a dictionary with one key: the branch that just produced output. The source (`RunnableParallel._transform`) asks each branch's generator for its next item in a thread, and yields `{name: chunk}` as soon as one finishes.

![Three lanes on a time axis: fast emits one chunk at 0.05 s, tokens emits five pieces between 0.1 and 0.5 s, slow emits one chunk at 0.36 s](diagrams/43.2-stream-lanes.svg "Chunks from one run, approximate times. The consumer sees them in this order, not in the order the branches were written.")

A consumer that wants the full answer merges the pieces. For text, that means concatenating per key:

```python
chunks = [{"fast": "fast"}, {"tokens": "Retr"}, {"tokens": "ieval"}, {"tokens": " is"},
          {"slow": "slow"}, {"tokens": " fast"}, {"tokens": "."}]
answer = {}
for chunk in chunks:
    for key, piece in chunk.items():
        answer[key] = answer.get(key, "") + piece
print(answer)
```

```output
{'fast': 'fast', 'tokens': 'Retrieval is fast.', 'slow': 'slow'}
```

Streaming matters most for user-facing latency. A web response can forward each chunk as it arrives, so the first words appear long before the last word is ready.

A step only streams if it yields. A `RunnableLambda` wrapping an ordinary function produces one chunk, because nothing is available until the function returns. A generator function produces one chunk per `yield`. The next block measures both, and runs the parallel stream itself.

<details><summary>Run locally: needs pip install langchain-core==0.3.86</summary>

```python
import time
from langchain_core.runnables import RunnableParallel, RunnableLambda

def branch(label, d):
    def f(x):
        time.sleep(d)
        return label
    return RunnableLambda(f)

def gen_tokens(x):
    for tok in ["Retr", "ieval", " is", " fast", "."]:
        time.sleep(0.1)
        yield tok

par = RunnableParallel({"fast": branch("fast", 0.05),
                        "slow": branch("slow", 0.35),
                        "tokens": RunnableLambda(gen_tokens)})
for chunk in par.stream({}):
    print(chunk)

print("ordinary function, chunks:", len(list(RunnableLambda(lambda x: x * 2).stream(3))))
print("generator function, chunks:", len(list(RunnableLambda(gen_tokens).stream(3))))
```

```output
{'fast': 'fast'}
{'tokens': 'Retr'}
{'tokens': 'ieval'}
{'tokens': ' is'}
{'slow': 'slow'}
{'tokens': ' fast'}
{'tokens': '.'}
ordinary function, chunks: 1
generator function, chunks: 5
```

</details>

The order depends on sleep timings, so the `slow` chunk lands between the third and fourth token only because the gap is 50 ms. On a busy machine the order can change. The `astream()` method has the same chunk shape (`RunnableParallel.astream` in `base.py`), but I did not run it here.

## Batching: many inputs, not many branches

`batch()` is defined on the base `Runnable` class, not on `RunnableParallel`. Its default runs `invoke` once per input in a thread pool. `abatch()` runs `ainvoke` once per input under `asyncio.gather`, limited by a semaphore sized from `max_concurrency` (`gather_with_concurrency` in `runnables/utils.py`). So `RunnableParallel(...).batch(xs)` runs every branch for every input.

The two kinds of parallelism multiply. Three branches over 12 inputs make 36 step calls. Count the calls before you choose a concurrency limit, because the limit decides how many of them are in flight at once.

The chart below uses 0.2 s stand-ins for requests and `max_concurrency=4`. The work runs in waves of four, so the expected time is ceil(n/4) × 0.2 s. For 12 inputs that is three waves, about 0.6 s.

![Grouped bars for n equal 1, 2, 4, 8 and 12 inputs: batch and abatch both step up at each wave of four, reaching about 0.6 seconds at n equal 12](diagrams/43.2-batch-chart.svg "Measured wall time, one run, rounded to 0.01 s. Thread-based batch and asyncio-based abatch match here because the stand-in calls only sleep.")

<details><summary>Run locally: needs pip install langchain-core==0.3.86</summary>

```python
import asyncio, time
from langchain_core.runnables import RunnableLambda

def call(x):
    time.sleep(0.2)              # stands in for one 0.2 s request
    return x * 2

async def acall(x):
    await asyncio.sleep(0.2)
    return x * 2

chain, achain = RunnableLambda(call), RunnableLambda(acall)
for n in [1, 2, 4, 8, 12]:
    t = time.perf_counter()
    chain.batch(list(range(n)), config={"max_concurrency": 4})
    t_thread = time.perf_counter() - t
    t = time.perf_counter()
    asyncio.run(achain.abatch(list(range(n)), config={"max_concurrency": 4}))
    t_async = time.perf_counter() - t
    print(f"n={n:2d}  batch {t_thread:.1f} s  abatch {t_async:.1f} s")
```

```output
n= 1  batch 0.2 s  abatch 0.2 s
n= 2  batch 0.2 s  abatch 0.2 s
n= 4  batch 0.2 s  abatch 0.2 s
n= 8  batch 0.4 s  abatch 0.4 s
n=12  batch 0.6 s  abatch 0.6 s
```

</details>

## Concurrency limits, and where they stop

`max_concurrency` in the config caps the thread pool used by `invoke`, because `get_executor_for_config` passes it as `max_workers`. It does not cap `ainvoke`: `RunnableParallel.ainvoke` calls a bare `asyncio.gather` with no limit. Six branches of 0.2 s each, with `max_concurrency=2`, took 0.6 s under `invoke` and 0.2 s under `ainvoke`. If your branches call a rate-limited API, `ainvoke` will not throttle them. Put your own `asyncio.Semaphore` around the call. This behaviour belongs to langchain-core 0.3.86, so check the source of the version you install.

<details><summary>Run locally: needs pip install langchain-core==0.3.86</summary>

```python
import asyncio, time
from langchain_core.runnables import RunnableParallel, RunnableLambda

def slow(label):
    def f(x):
        time.sleep(0.2)
        return label
    return RunnableLambda(f)

def aslow(label):
    async def f(x):
        await asyncio.sleep(0.2)
        return label
    return RunnableLambda(f)

def timed(fn):
    t = time.perf_counter()
    fn()
    return time.perf_counter() - t

cfg = {"max_concurrency": 2}
t_inv = timed(lambda: RunnableParallel({f"b{i}": slow(f"b{i}") for i in range(6)}).invoke({}, config=cfg))
t_ainv = timed(lambda: asyncio.run(RunnableParallel({f"b{i}": aslow(f"b{i}") for i in range(6)}).ainvoke({}, config=cfg)))
print(f"invoke {t_inv:.1f} s, ainvoke {t_ainv:.1f} s")

try:
    aslow("x").invoke(3)
except TypeError as e:
    print("TypeError:", e)

try:
    RunnableParallel(fetch=RunnableLambda(lambda d: {"data": 1}),
                     analyze=RunnableLambda(lambda d: d["processed_data"])).invoke({})
except KeyError as e:
    print("KeyError:", e)
```

```output
invoke 0.6 s, ainvoke 0.2 s
TypeError: Cannot invoke a coroutine function synchronously.Use `ainvoke` instead.
KeyError: 'processed_data'
```

</details>

## Choosing a method

The rules below follow from the mechanisms above. They are my reasoning, not a benchmark.

- In a script or notebook with independent waits, `invoke()` on a `RunnableParallel` is enough.
- In an async web server, use `ainvoke()`, so the event loop can serve other requests while branches wait. A blocking branch stalls all of them.
- For a user-facing answer, use `stream()` (or `astream()`) and forward chunks as they arrive.
- For many inputs, use `batch()` or `abatch()` with `max_concurrency` set to what your model provider allows.

## Common traps

> [!TRAP]
> Branches cannot see each other. In the last block, `analyze` received the original input, not the output of `fetch`, so `d["processed_data"]` raised `KeyError`. Use `|` to pass one step's output to the next.

> [!TRAP]
> A coroutine that calls `time.sleep` freezes every branch. Use `await asyncio.sleep`, or make the function ordinary so that `ainvoke` runs it in a thread.

> [!TRAP]
> `invoke()` on an `async def` runnable raises `TypeError`. Call `ainvoke()` instead.

> [!TRAP]
> A plain function streams nothing: it yields one chunk. Streaming needs a generator.

> [!TRAP]
> `max_concurrency` limits `invoke` but not `ainvoke` for `RunnableParallel`. Rate limits need a semaphore in your own code.

## Summary

- `RunnableParallel` gives each branch the same input and returns a dictionary keyed by branch name. Branches cannot read each other's outputs.
- Parallel branches take about as long as the slowest branch, but only if each waits without blocking the event loop (in `ainvoke`) or in its own thread (in `invoke`).
- `stream()` yields one single-key dictionary per chunk, in arrival order. A step streams only if it is a generator.
- `batch()` and `abatch()` parallelise over inputs, not branches. `max_concurrency` limits `invoke` and `batch` but not `RunnableParallel.ainvoke`.

## Quiz time

### Question 1: Prediction

Three `RunnableParallel` branches each take 0.5 s and are called with `invoke()`. What is the wall-clock time, approximately?

<details><summary>Show solution</summary>

About 0.5 s. The branches run in threads, so the total is roughly the slowest branch, not the sum (1.5 s).
</details>

### Question 2: Prediction

How many chunks does `RunnableLambda(lambda x: x * 2).stream(3)` yield, and how many does `RunnableLambda(gen).stream(3)` yield if `gen` yields three values?

<details><summary>Show solution</summary>

One chunk for the ordinary function, because it has nothing to stream until it returns. Three chunks for the generator, one per `yield`.
</details>

### Question 3: Find the bug

Four branches each call `time.sleep(1)` inside an `async def` and run under `await par.ainvoke({})`. A colleague expects about 1 s. What happens, and how do you fix it?

<details><summary>Show solution</summary>

The coroutines block the event loop, so they run one after another: about 4 s. Replace `time.sleep(1)` with `await asyncio.sleep(1)`, or make each branch an ordinary function so that `ainvoke` runs it in a thread through `run_in_executor`.
</details>

### Question 4: Explain

Why is `batch()` not a feature of `RunnableParallel`, and what would `RunnableParallel(...).batch(xs)` run?

<details><summary>Show solution</summary>

`batch()` belongs to the base `Runnable` class and calls `invoke` once per input, in a thread pool. `RunnableParallel(...).batch(xs)` therefore runs every branch once for each input in `xs`: branches times inputs calls in total.
</details>
