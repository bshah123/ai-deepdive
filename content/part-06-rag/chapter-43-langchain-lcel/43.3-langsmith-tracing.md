A LangChain chain returns one final value, but it runs several steps to get there. In this lesson you will read a **trace** (a record of every step), find the first step whose output went wrong, and find the step that spends the most time.

**You need:** LangChain Expression Language (LCEL, Lesson 43.1), where `|` joins steps and each step has `invoke`; and the idea of a **callback**, a function the framework calls at fixed points during a run.

## The problem tracing solves

Suppose a chain answers questions from a document store. It retrieves passages, builds a prompt, calls a large language model (LLM), and parses the reply. If the answer is wrong, the final string does not say which step failed. If the chain takes 1.2 seconds, the same string does not say whether retrieval or the model is slow.

A trace records every step with its inputs, outputs, timing and token counts. One record answers both questions.

Why bother saving the record? A chain that calls an LLM is not deterministic when sampling is on: the same input can give a different answer on the next run, so a bug may appear once and then vanish. A saved trace keeps the evidence. You can compare what each step received with what it returned, after the run is over.

## Intuition: a trace is a tree

Tracing works through callbacks. Before a step starts, the framework sends a start event that carries the step's name, its inputs and the id of its parent run. When the step ends, it sends an end event that carries the outputs. A handler that stores these events can rebuild the whole tree after the run finishes. The chain's code does not change, which is why turning tracing on is an environment setting.

![A root run named answer_chain has four child runs: retrieve, prompt, ChatModel and parse. The retrieve run's output is an empty list.](diagrams/43.3-run-tree.svg "One run per step. Each run that calls other steps is the parent of those steps.")

Each step becomes a **run**. A run that calls other steps is the parent of those runs, so the runs form a tree. The root run is the whole chain. Each run carries a `run_type` label (for example `chain`, `retriever` or `llm`) that says what kind of step it was.

LangChain emits a start event and an end event for each run to every attached callback handler. LangSmith's tracer is one such handler: `LangChainTracer` is a subclass of `BaseTracer`, which subclasses `BaseCallbackHandler` (the installed `langchain-core` 1.8.4 source; see References).

## Worked example by hand

Each run has two times. Its **total time** runs from its start to its end, including its children. Its **self time** is its total minus the totals of its children: the time spent in its own code.

The simulated run in the next section has these self times in seconds: `answer_chain` 0.004, `retrieve` 0.350, `prompt` 0.003, `ChatModel` 0.812, `parse` 0.001.

- The root total is the sum of all self times: 0.004 + 0.350 + 0.003 + 0.812 + 0.001 = 1.170 s.
- The root's self time is not 1.170 s. Its children account for 0.350 + 0.003 + 0.812 + 0.001 = 1.166 s, so its self time is 1.170 − 1.166 = 0.004 s.
- The model's share is 0.812 / 1.170 ≈ 69.4 %. Most of the wait is in the model call.

A run with no children has a self time equal to its total. A run with children can have a tiny self time even when its total is large, which is why the root shows only 0.004 s. The simulated times here are fixed, so you can check the arithmetic by hand, and they cannot change between runs. Real latency depends on the provider, the load on the server and the length of the output. A real trace is noisy: take the median of several runs before you decide which step is slow.

![Horizontal bars of self time: ChatModel 0.812 s (69.4 %), retrieve 0.350 s (29.9 %), and three runs under 0.5 %.](diagrams/43.3-self-time.svg "Rank by self time, not total time. Total time puts the root first, which tells you nothing.")

## Runnable code: a mini tracer

The code below is a small tracer written with the standard library only. It keeps the same bookkeeping as a real tracer: start and end events, parent links, and token counts. Its times are simulated, so the output is reproducible. Real timings vary with hardware and the network.

```python
from dataclasses import dataclass, field


@dataclass
class Span:
    name: str
    run_type: str
    parent: "Span | None"
    start: float
    end: float = 0.0
    tokens: int = 0
    outputs: object = None
    children: list = field(default_factory=list)

    @property
    def total(self):
        return self.end - self.start

    @property
    def self_time(self):
        return self.total - sum(c.total for c in self.children)


class MiniTracer:
    """Records a run tree the way a callback handler does: start and end events."""

    def __init__(self):
        self.clock = 0.0          # simulated seconds; moves only through work()
        self.roots = []
        self._stack = []

    def start(self, name, run_type):
        parent = self._stack[-1] if self._stack else None
        span = Span(name, run_type, parent, start=self.clock)
        (parent.children if parent else self.roots).append(span)
        self._stack.append(span)
        return span

    def work(self, seconds, tokens=0):
        self.clock += seconds     # time spent inside the current span
        self._stack[-1].tokens += tokens

    def end(self, outputs=None):
        span = self._stack.pop()
        span.end = self.clock
        span.outputs = outputs
        return span


def answer_chain(tracer, docs):
    """Retrieve, build a prompt, call a model, parse. Times are simulated."""
    tracer.start("answer_chain", "chain")
    tracer.work(0.004)                                   # glue code between steps
    tracer.start("retrieve", "retriever")
    tracer.work(0.350)
    tracer.end(outputs=docs)
    prompt = f"Context: {docs}\nQuestion: How do I pipe steps?"
    tracer.start("prompt", "prompt")
    tracer.work(0.003)
    tracer.end(outputs=prompt)
    tracer.start("ChatModel", "llm")
    tracer.work(0.812, tokens=396)                       # prompt + completion tokens
    tracer.end(outputs="Use the | operator.")
    tracer.start("parse", "parser")
    tracer.work(0.001)
    tracer.end(outputs="Use the | operator.")
    return tracer.end(outputs="Use the | operator.")


def print_tree(span, depth=0):
    print(f"{'  ' * depth}{span.name} [{span.run_type}] total={span.total:.3f}s "
          f"self={span.self_time:.3f}s tokens={span.tokens}")
    for child in span.children:
        print_tree(child, depth + 1)


def walk(span):
    yield span
    for child in span.children:
        yield from walk(child)


# Good run: retrieval returns one document.
good = MiniTracer()
answer_chain(good, ["LCEL pipes runnables with |."])
print_tree(good.roots[0])
print("first output at retrieve:", [s for s in walk(good.roots[0]) if s.name == "retrieve"][0].outputs)

# Bad run: retrieval returns nothing, so the prompt has no context.
bad = MiniTracer()
answer_chain(bad, [])
print("first output at retrieve:", [s for s in walk(bad.roots[0]) if s.name == "retrieve"][0].outputs)
print("prompt:", [s for s in walk(bad.roots[0]) if s.name == "prompt"][0].outputs)

# Profile: rank by self time, as a share of the root total.
root = good.roots[0]
print("root total:", round(root.total, 3))
for s in sorted(walk(root), key=lambda s: -s.self_time):
    print(f"{s.name:>12}: self={s.self_time:.3f}s  share={s.self_time / root.total:6.1%}")
```

## Debugging: find the first wrong value

![Two columns, good run and bad run, and three rows: retrieve output, prompt context and final answer. The bad run's retrieve output and prompt context are highlighted; the final answer is the same in both.](diagrams/43.3-good-vs-bad.svg "Compare the runs row by row. The final answer hides the fault; the middle rows show it.")

Read the tree from the top down and stop at the first run whose output is wrong for its input. In the bad run, `retrieve` returns `[]`. The prompt then reads `Context: []`, which is a symptom of that. In the simulated run the model still answers, so the final answer looks normal. The final answer is the same in both runs, so the final answer cannot show the fault.

The fix belongs at the first wrong span, not at the last one. Here that means the retriever, not the prompt or the model.

A short procedure works for most bugs:

1. Reproduce the bad answer with the same input, with tracing on.
2. Open the trace and check each run's inputs and outputs, top-down.
3. Stop at the first run whose output is wrong for its input, and check that run's own code and its inputs.
4. Fix it, run the same input again, and compare the new trace with the saved one.

## The real LangChain version

The next block uses `langchain-core` (not the standard library). It attaches a callback handler that records the same start and end events that the mini tracer simulates. The LLM is a fake model that returns a fixed reply, so the code runs without an API key.

<details><summary>Run locally: needs pip install langchain-core==1.8.4 langsmith==0.16.0</summary>

```python
import importlib.metadata as md
from langchain_core.callbacks import BaseCallbackHandler
from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda

print("langchain-core", md.version("langchain-core"), "| langsmith", md.version("langsmith"))

class RunRecorder(BaseCallbackHandler):
    def __init__(self):
        self.rows = {}   # run_id -> dict
        self.order = []
    def _open(self, run_id, parent_run_id, name, run_type, inputs):
        self.rows[run_id] = dict(name=name, run_type=run_type, parent=parent_run_id, inputs=inputs, outputs=None)
        self.order.append(run_id)
    def on_chain_start(self, serialized, inputs, *, run_id, parent_run_id=None, tags=None, metadata=None, run_type=None, name=None, **kw):
        self._open(run_id, parent_run_id, name or "?", run_type or "chain", inputs)
    def on_chain_end(self, outputs, *, run_id, **kw):
        self.rows[run_id]["outputs"] = outputs
    def on_llm_start(self, serialized, prompts, *, run_id, parent_run_id=None, tags=None, metadata=None, name=None, **kw):
        self._open(run_id, parent_run_id, name or "llm", "llm", prompts)
    def on_chat_model_start(self, serialized, messages, *, run_id, parent_run_id=None, tags=None, metadata=None, name=None, **kw):
        self._open(run_id, parent_run_id, name or "chat", "llm", messages)
    def on_llm_end(self, response, *, run_id, **kw):
        self.rows[run_id]["outputs"] = response.generations[0][0].text
    def on_retriever_start(self, serialized, query, *, run_id, parent_run_id=None, tags=None, metadata=None, name=None, **kw):
        self._open(run_id, parent_run_id, name or "retriever", "retriever", query)
    def on_retriever_end(self, documents, *, run_id, **kw):
        self.rows[run_id]["outputs"] = [d.page_content for d in documents]

def retrieve(q):
    return ["LCEL pipes runnables with |."]          # stub retriever, always returns one doc

def build(retrieve_fn):
    prompt = ChatPromptTemplate.from_template("Context: {context}\nQuestion: {question}")
    llm = FakeListChatModel(responses=["Use the | operator."])
    return (
        {"context": RunnableLambda(retrieve_fn, name="retrieve"), "question": lambda x: x["question"]}
        | prompt | llm | StrOutputParser()
    ).with_config(run_name="answer_chain")

def show(rec):
    depth = {}
    for rid in rec.order:
        r = rec.rows[rid]
        d = 0 if r["parent"] is None else depth[r["parent"]] + 1
        depth[rid] = d
        print(f'{"  " * d}{r["name"]} [{r["run_type"]}] parent={"none" if r["parent"] is None else "yes"} outputs={r["outputs"]!r}'[:200])

rec = RunRecorder()
out = build(retrieve).invoke({"question": "How do I pipe steps?"}, config={"callbacks": [rec]})
print("final:", repr(out))
show(rec)
print("number of runs:", len(rec.rows), "| roots:", sum(1 for r in rec.rows.values() if r["parent"] is None))

rec2 = RunRecorder()
out2 = build(lambda q: []).invoke({"question": "How do I pipe steps?"}, config={"callbacks": [rec2]})
print("buggy final:", repr(out2))
show(rec2)
```

## Turning on LangSmith

Hosted tracing needs a LangSmith account and network access, which this lesson's environment does not have. The block below is checked against the observability docs and the `langsmith` 0.16.0 source. It is not run. The code above does not change: the environment variables switch tracing on for the same chain.

```bash
export LANGSMITH_TRACING=true        # turns tracing on for LangChain runs
export LANGSMITH_API_KEY="<your key>"
```

With tracing on, the same chain you wrote above sends its run tree to LangSmith. To keep user inputs and outputs out of the trace, set `LANGSMITH_HIDE_INPUTS=true` and `LANGSMITH_HIDE_OUTPUTS=true`, or pass `hide_inputs=True` and `hide_outputs=True` to `Client` (both read in `langsmith/client.py`).

## Common traps

> [!TRAP]
> **Reading the final answer as the result.** The final answer can look correct while an early step is wrong. Always read the tree, not just the last output.

> [!TRAP]
> **Ranking by total time.** The root's total includes every child, so it is always the largest. Rank the runs by self time to find the slow step.

> [!TRAP]
> **Trusting one timing.** Latency in a real trace includes network and queueing. Compare several runs before you optimise anything.

> [!TRAP]
> **Sending personal data.** Traces hold prompts, inputs and outputs. Turn on hiding before you trace real users.

> [!TRAP]
> **Mixing product setups.** Both `LANGSMITH_TRACING` and the older `LANGCHAIN_TRACING_V2` work in `langsmith` 0.16.0, because the library reads both name spaces (`langsmith/utils.py`). The observability quickstart tells its agent setup to remove `LANGSMITH_PROJECT`, so check which product your docs describe before copying names.

## Summary

- A trace is a tree of runs. Each run records its name, `run_type`, inputs, outputs, timing and tokens.
- Total time includes children; self time does not. Rank by self time to find where the time goes.
- For a wrong answer, read the tree top-down and stop at the first run whose output is wrong.
- LangSmith tracing is a callback handler; enable it with `LANGSMITH_TRACING=true` and an API key.
- Hide inputs and outputs before tracing real users, because traces store the text that flows through the chain.

## Quiz time

### Question 1: Using the good run, what is the self time of `answer_chain`, and why is it not 1.170 s?

<details><summary>Show Solution</summary>

The self time is 0.004 s. The total of 1.170 s includes the children's totals: 0.350 + 0.003 + 0.812 + 0.001 = 1.166 s. So the self time is 1.170 − 1.166 = 0.004 s, the glue time that belongs to the root alone.

</details>

### Question 2: Prediction. Suppose the model call takes 0.406 s instead of 0.812 s and nothing else changes. What is the new root total, and what share of it is the model's self time?

<details><summary>Show Solution</summary>

The new total is 1.170 − 0.406 = 0.764 s. The model's share is 0.406 / 0.764 ≈ 53.1 %. The share falls from 69.4 % because the total also falls. The model is still the largest single cost, so it is still the first place to look. The calculation assumes that the other steps keep their times.

</details>

### Question 3: Bug spotting. A trace shows `retrieve` output `[]` and `prompt` text `Context: []`. The final answer reads fluently. Which run do you fix first, and why not the model?

<details><summary>Show Solution</summary>

Fix `retrieve`. It is the first run whose output is wrong. The prompt's empty context is a symptom of that output. The model produces a fluent answer from the question alone, so a fluent answer does not show that the model was given the wrong context. Fix the upstream step first; the downstream steps may then be correct without any change.

</details>

### Question 4: Explanation. Why is the root's total time a poor guide to which step to optimise?

<details><summary>Show Solution</summary>

The root's total is the sum of all the runs beneath it, so it always comes out largest and says nothing about a single step. A run's self time excludes its children, so ranking by self time separates the steps. Here the model has self time 0.812 s, which is the largest of the five.

</details>
