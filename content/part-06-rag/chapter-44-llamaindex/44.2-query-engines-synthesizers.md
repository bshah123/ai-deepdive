In this lesson you will build the three layers that sit on top of a retriever in LlamaIndex, a Python framework for retrieval-augmented generation (RAG): a **query engine**, the **response synthesizers** it calls, and a **chat engine**. You will count how many calls to a large language model (LLM) each design makes, and measure what a follow-up question does to retrieval. The code uses only NumPy and a stub LLM. The stub's answers are meaningless, but its call counts and prompt sizes are exact.

**You need:** Lesson 44.1 (nodes, indices and retrievers), and NumPy vectors with dot products and norms.

## The problem these layers solve

RAG answers a question in two steps: retrieve passages that may contain the answer, then have an LLM write the answer from them (Lewis et al., 2020). Two practical problems follow.

The first is size. A retriever returns k passages, but a prompt holds at most a fixed **context window**, the maximum input length. Six passages may not fit in one prompt, so the system must split them across calls and combine the results.

The second is memory. A chat user asks "How often do its seals need replacing?" The word "its" refers to a pump named in an earlier turn. A retriever that sees only the follow-up cannot find the right passage.

## The three layers

![Question flows into a retriever, then a synthesizer, then an answer; the retriever and synthesizer sit inside a dashed query engine box](diagrams/44.2-query-engine.svg "A query engine is a retriever followed by a response synthesizer.")

- The **retriever** scores every chunk against the question and returns the top k.
- The **response synthesizer** turns the k chunks and the question into one answer. Its *mode* decides how many LLM calls are made and how the chunks are arranged.
- The **query engine** is a retriever followed by a synthesizer. In LlamaIndex, `as_query_engine()` builds one from an index.
- The **chat engine** is a query engine plus a memory of earlier turns and a step that rewrites a follow-up into a standalone question before retrieval.

LlamaIndex's default retriever uses an embedding model. This lesson uses TF-IDF (term frequency times inverse document frequency) instead, because it needs no model weights. The layering is the same; the scores are not.

## Worked example: retrieval by hand

The corpus has ten chunks about a fictional pump (see the code). Take the query "What is the rated flow of the Ferrin P200 pump?" Stop words are dropped, leaving five terms: rated, flow, ferrin, p200, pump.

Each term gets an inverse document frequency, idf(t) = ln((1+N)/(1+df(t))) + 1, where N = 10 is the number of chunks and df(t) is how many chunks contain t:

- df = 1 (rated, ferrin, p200): idf = ln(11/2) + 1 = 2.7047
- df = 2 (flow, in chunks 0 and 7): idf = ln(11/3) + 1 = 2.2993
- df = 4 (pump, in chunks 0, 2, 4 and 5): idf = ln(11/5) + 1 = 1.7885

Chunk 0 has 12 distinct terms: ten with df = 1, plus flow and pump. Each vector is scaled to length 1, so cosine similarity is a dot product of unit vectors. The squared length of chunk 0 is 10 × 2.7047² + 2.2993² + 1.7885² = 81.64, so its length is 9.035. The query has three df = 1 terms, plus flow and pump: 3 × 2.7047² + 2.2993² + 1.7885² = 30.43, so its length is 5.517. Every query term appears in chunk 0 with the same weight, so the dot product of the unnormalised vectors equals the query's squared length, 30.43. The cosine is therefore 5.517 / 9.035 = 0.611, the first score in the output below.

Chunk 7 scores 0.107 because it shares only "flow", and chunk 5 scores 0.075 because it shares only "pump". Matching is exact: "install" does not match "installed", and "replacing" does not match "replaced". Embedding retrievers exist to close that gap, and the chat results below depend on it.

## Runnable code

The whole lesson's code is one file. It runs in the browser, using only the standard library and NumPy.

```python
"""Lesson 44.2: a query engine, three response synthesizers and a chat engine, from scratch.

Pure standard library + NumPy, so it runs in the browser (Pyodide).
The retriever is TF-IDF (term frequency x inverse document frequency), not an embedding model.
The LLM is a deterministic stub: it counts calls and prompt words and returns the first
OUT words of its CONTEXT block. Its answers are NOT meaningful; only call counts and prompt sizes are.
"""
import math
import re
import numpy as np

# Toy manual of 10 chunks (our own text, fictional product).
CHUNKS = [
    "The Ferrin P200 pump is rated for a flow of 40 litres per minute at a head of 25 metres.",
    "Its motor is a sealed induction unit that runs on 230 volts, single phase, and draws 1.2 amps.",
    "Install the pump on a level concrete base, at least 30 centimetres above the highest water level.",
    "The mechanical seals must be replaced every 4000 running hours, or sooner if a leak appears at the shaft.",
    "Before replacing seals, drain the casing and close the isolation valves on both sides of the pump.",
    "Never run the pump dry: without water the seals overheat within minutes.",
    "The warranty covers the motor and casing for 24 months from the date of commercial installation.",
    "Clean the strainer basket every month; a blocked basket reduces flow and can damage the impeller.",
    "The control panel has a dry-run sensor that stops the motor when the suction level drops too low.",
    "Spare parts include a seal kit, a capacitor and a strainer basket; order them with the serial number.",
]
STOP = {"the", "a", "an", "is", "of", "on", "to", "do", "does", "how", "what", "it", "its", "and", "or",
        "be", "at", "we", "i", "me", "my", "can", "for", "that", "by", "this", "with", "should", "must",
        "need", "where", "which", "then", "if", "from", "in", "so", "as", "when", "up", "out", "not",
        "will", "they", "them", "there", "both", "than", "any", "are", "you", "your"}

def tokens(text):
    return [w for w in re.findall(r"[a-z0-9]+", text.lower()) if w not in STOP]

VOCAB = sorted({w for c in CHUNKS for w in tokens(c)})
IDX = {w: i for i, w in enumerate(VOCAB)}
N = len(CHUNKS)
df = np.zeros(len(VOCAB))
for c in CHUNKS:
    for w in set(tokens(c)):
        df[IDX[w]] += 1
IDF = np.log((1 + N) / (1 + df)) + 1          # smoothed idf: log((1+N)/(1+df)) + 1

def vec(toks):
    v = np.zeros(len(VOCAB))
    for w in toks:
        if w in IDX:                           # out-of-vocabulary words are dropped
            v[IDX[w]] += 1
    v = v * IDF
    n = np.linalg.norm(v)
    return v / n if n > 0 else v

X = np.stack([vec(tokens(c)) for c in CHUNKS])  # one unit vector per chunk

def retrieve(query, k):
    """Query engine step 1: the retriever. Returns [(chunk_id, cosine score)], best first."""
    scores = X @ vec(tokens(query))
    order = np.argsort(-scores, kind="stable")[:k]
    return [(int(i), float(scores[i])) for i in order]

# ---- Response synthesis -------------------------------------------------------------
OUT = 12                                       # stub answer length, in words
WINDOW = 120                                   # demo context window, in words (scaled down)
PADDING = 10                                   # room kept free for the output
QA = "Answer the question using only the context. Question: {q} CONTEXT: "
REFINE = "Question: {q} Improve the existing answer with the new context. EXISTING ANSWER: {a} CONTEXT: "
SUMMARY = "Summarise the context for the question. Question: {q} CONTEXT: "

def nwords(s):
    return len(s.split())

def budget(q):
    """Words left for context in one refine prompt, after template, answer and padding."""
    return WINDOW - PADDING - nwords(REFINE.format(q=q, a=" ".join(["a"] * OUT)))

def pack(texts, room):
    """Greedy packing: join consecutive chunks while they fit in `room` words."""
    packs, cur = [], []
    for t in texts:
        if nwords(t) > room:
            raise ValueError("one chunk is larger than the room left")
        if cur and sum(nwords(x) for x in cur) + nwords(t) > room:
            packs.append(" ".join(cur))
            cur = []
        cur.append(t)
    if cur:
        packs.append(" ".join(cur))
    return packs

class StubLLM:
    def __init__(self):
        self.log = []                          # (kind, prompt length in words)

    def complete(self, kind, prompt):
        self.log.append((kind, nwords(prompt)))
        if kind == "condense":                 # stub rewrite: previous user turn + follow-up
            prev = prompt.split("PREVIOUS:")[1].split("FOLLOW-UP:")[0].strip()
            return prev + " " + prompt.split("FOLLOW-UP:")[1].strip()
        ctx = prompt.split("CONTEXT:")[-1].split()
        return " ".join(ctx[:OUT])

def refine(q, pieces, llm):
    answer = None
    for piece in pieces:
        if answer is None:
            prompt = QA.format(q=q) + piece
        else:
            prompt = REFINE.format(q=q, a=answer) + piece
        answer = llm.complete("refine", prompt)  # the new answer replaces the old one
    return answer

def synthesize(mode, q, chunks, llm):
    b = budget(q)
    if mode == "refine":                        # one piece per chunk
        return refine(q, chunks, llm)
    if mode == "compact":                       # pack chunks first, then refine
        return refine(q, pack(chunks, b), llm)
    if mode == "accumulate":                    # one answer per chunk, concatenated
        return " | ".join(llm.complete("acc", QA.format(q=q) + c) for c in chunks)
    if mode == "compact_accumulate":
        return " | ".join(llm.complete("acc", QA.format(q=q) + p) for p in pack(chunks, b))
    if mode == "simple_summarize":              # everything in one prompt
        return llm.complete("simple", SUMMARY.format(q=q) + " ".join(chunks))
    if mode == "tree_summarize":                # bottom-up: summarise groups until one remains
        level = chunks
        while True:
            outs = [llm.complete("tree", SUMMARY.format(q=q) + g) for g in pack(level, b)]
            if len(outs) == 1:
                return outs[0]
            level = outs
    raise ValueError(mode)

# ---- Chat engine: condense the follow-up, retrieve, then synthesize -----------------
class ChatEngine:
    def __init__(self, llm, k=2):
        self.llm, self.k, self.history = llm, k, []

    def chat(self, msg):
        if self.history:                       # the condense step: one extra call
            standalone = self.llm.complete("condense", f"PREVIOUS: {self.history[-1]} FOLLOW-UP: {msg}")
        else:
            standalone = msg
        hits = retrieve(standalone, self.k)    # retrieval uses the standalone question
        answer = synthesize("compact", msg, [CHUNKS[i] for i, _ in hits], self.llm)
        self.history.append(msg)
        return standalone, [i for i, _ in hits], answer

if __name__ == "__main__":
    print(f"chunks={N} vocab={len(VOCAB)} matrix={X.shape}")

    # 1. Retrieval, worked example
    q1 = "What is the rated flow of the Ferrin P200 pump?"
    print("\nquery:", q1, "| tokens:", tokens(q1))
    for i, s in retrieve(q1, 3):
        print(f"  chunk {i}  score {s:.3f}  {CHUNKS[i][:48]}...")

    # 2. Response synthesizers on the same top-6 chunks
    q2 = "How should I maintain the Ferrin P200 pump?"
    hits = retrieve(q2, 6)
    chunks = [CHUNKS[i] for i, _ in hits]
    print(f"\nquery: {q2}\nretrieved chunks (best first): {[i for i, _ in hits]}")
    print(f"budget per refine prompt: {budget(q2)} words of context (window {WINDOW}, padding {PADDING})")
    for mode in ["refine", "compact", "accumulate", "compact_accumulate", "tree_summarize", "simple_summarize"]:
        llm = StubLLM()
        synthesize(mode, q2, chunks, llm)
        longest = max(n for _, n in llm.log)
        fits = "yes" if longest <= WINDOW else "NO"
        print(f"  {mode:18s} calls={len(llm.log):2d}  longest prompt={longest:3d} words  fits window={fits}")

    llm = StubLLM()
    final = refine(q2, chunks, llm)
    print("\nrefine, final stub answer:", repr(final))
    print("refine, chunk ids in order:", [i for i, _ in hits])
    print("refine, last chunk text:  ", repr(chunks[-1][:60]))

    # 3. Chat engine: raw follow-up vs condensed standalone question
    items = [
        ("What is the rated flow of the Ferrin P200 pump?", "How often do its seals need replacing?", 3),
        ("How is the Ferrin P200 motor powered?", "Where should the pump be installed?", 2),
        ("How do I drain the pump before maintenance?", "Which valves must I close?", 4),
        ("What voltage does the pump motor need?", "Can it run dry for a while?", 5),
    ]
    raw_hit = cond_hit = 0
    for prev, follow, gold in items:
        raw_ids = [i for i, _ in retrieve(follow, 2)]
        eng = ChatEngine(StubLLM(), k=2)
        eng.history = [prev]
        standalone, ids, _ = eng.chat(follow)
        raw_hit += gold in raw_ids
        cond_hit += gold in ids
        print(f"\nfollow-up: {follow!r}  gold chunk {gold}")
        print(f"  raw top-2 {raw_ids}   condensed top-2 {ids}")
        print(f"  standalone: {standalone!r}")
        print(f"  LLM calls this turn: {len(eng.llm.log)} {[k for k, _ in eng.llm.log]}")
    print(f"\nrecall@2 raw follow-up: {raw_hit}/{len(items)}   condensed: {cond_hit}/{len(items)}")
    first = ChatEngine(StubLLM(), k=2)
    first.chat(items[0][0])
    print(f"first turn (no history) LLM calls: {len(first.llm.log)} {[k for k, _ in first.llm.log]}")
    print("\nchunk words in retrieval order:", [nwords(c) for c in chunks], "total", sum(nwords(c) for c in chunks))
    print("compact packs (words each):", [nwords(p) for p in pack(chunks, budget(q2))])
    print("all 10 chunks total words:", sum(nwords(c) for c in CHUNKS))
    # hand-check numbers for chunk 0 and query 1
    df_ = {w: int(df[IDX[w]]) for w in ["ferrin", "p200", "rated", "flow", "pump"]}
    print("df:", df_, "idf:", {w: round(float(IDF[IDX[w]]), 4) for w in df_})
    print("idf of df=1:", round(math.log(11 / 2) + 1, 4), " df=2:", round(math.log(11 / 3) + 1, 4), " df=4:", round(math.log(11 / 5) + 1, 4))
    print("chunk 0 unit-vector check, cosine:", round(float(X[0] @ vec(tokens(q1))), 4))
```

## Reading the output: the synthesis budget

The synthesis demo reads the top six chunks (ids 0, 5, 4, 2, 1, 3) for "How should I maintain the Ferrin P200 pump?". The demo window is 120 words, scaled down from a real window of thousands of tokens. The refine template, the question and a 12-word existing answer take 32 words. Ten words are kept free for the output, which leaves 78 words for chunks. The six chunks hold 103 words, so they cannot share one prompt.

![Six chunk blocks sized by word count, packed into two prompts of 66 and 37 words, with a dashed 78-word budget bar underneath](diagrams/44.2-packing.svg "Compact packing: greedy, in retrieval order.")

Compact packing joins consecutive chunks while they fit. Chunks 0, 5, 4 and 2 make 66 words; adding chunk 1 would make 84, so it starts a second prompt with chunk 1 and chunk 3 (37 words).

The six modes make different numbers of calls:

![Bars for calls per mode (refine 6, compact 2, accumulate 6, compact_accumulate 2, tree_summarize 3, simple_summarize 1) and a bar for each mode's longest prompt against a 120-word window line](diagrams/44.2-synth-calls.svg "Calls and longest prompt per response mode, six retrieved chunks.")

- **refine** makes one call per chunk. The first call uses the QA template; each later call uses the refine template with the previous answer. The final answer is the output of the last call.
- **compact** packs the chunks first, then refines over the packs: 2 calls.
- **accumulate** asks one question per chunk and concatenates the answers: 6 calls. It is the only mode in which every chunk's answer survives.
- **compact_accumulate** packs first, then accumulates: 2 calls.
- **tree_summarize** summarizes groups bottom-up until one answer remains: 2 calls on the chunk groups, then 1 on their summaries, so 3.
- **simple_summarize** puts everything in one prompt: 1 call, but the prompt is 119 words, just under the window. The ten chunks together are 171 words, which would overflow.

A prompt's length counts its template words as well as its context. The refine trace shows why order matters:

![Six chunk boxes in retrieval order, each feeding one call; calls 2 to 6 use the refine template with the previous answer](diagrams/44.2-refine-trace.svg "Refine: each call sees one chunk and the previous answer.")

The stub returns the first 12 words of the context it sees, so its final answer copies chunk 3, the last one. A real LLM is asked to revise its answer, not copy it, so the stub exaggerates the effect. The structural point holds anyway: the last call sees the most recent answer and only one chunk, so its output has the most say. Liu et al. (2023) report that models use information at the start or end of a long context better than information in the middle, so chunk order is a design choice, not a detail.

## Reading the output: the chat turn

![Four boxes in a row: follow-up plus history, LLM call 1 condensing to a standalone question, retriever on the standalone question, LLM call 2 compact synthesis](diagrams/44.2-chat-turn.svg "A chat turn with history makes two LLM calls: condense, then synthesize.")

With history, a turn makes two LLM calls: one to condense the follow-up, one to synthesize. The first turn makes one. Retrieval runs on the standalone question, not on the raw follow-up.

The code runs four follow-up pairs. Recall@2 (the gold chunk in the top two) is 2/4 with the raw follow-up and 2/4 after condensing, so condensing did not help here. The stub condenser only joins the previous user turn and the follow-up. For "How often do its seals need replacing?", the condensed query keeps "rated flow", so chunk 0 takes one of the two slots. Chunk 3, the seal-interval chunk, is missed both ways, because "replacing" does not match "replaced". A real LLM would write a better standalone question, and an embedding retriever might match "replacing" to "replaced". So this result describes our toy setup, not condensing in general. Four items are too few to show anything.

## How LlamaIndex does this

The mode names come from `llama_index/core/response_synthesizers/type.py` in the installed `llama-index-core` 0.14.26 package, the same version as Lessons 44.1 and 44.3. There, `get_response_synthesizer` in `factory.py` defaults to `ResponseMode.COMPACT`. It maps `REFINE` to a `Refine` class and `COMPACT` to a `CompactAndRefine` class, which packs chunks and then runs the refine loop. The chat mode `condense_plus_context` maps to `CondensePlusContextChatEngine`. Its retrieval uses the condensed question, and its default memory is limited to the context window minus 256 tokens. The LlamaIndex docs describe a migration from `ServiceContext` to `Settings`, so tutorials built on `ServiceContext` are out of date.

> [!TRAP] k is not the number of LLM calls
> Refine makes one call per chunk, compact makes one per packed prompt, and tree_summarize makes one per group at each level. The call count depends on the mode and on the budget.

> [!TRAP] Refine is not accumulation
> The default refine loop passes the previous answer forward and returns only the last output. If the last chunk is weak or off-topic, it can dominate the answer. Check the final answer against the earlier chunks.

> [!TRAP] simple_summarize fails when the context is too large
> It makes one call with no size check, because all chunks go into one prompt. Compare the total words with the window before you choose it.

> [!TRAP] Condensing adds a call and can drift
> A rewrite costs an LLM call and can change the meaning. Log the standalone question for each turn, as the code does.

> [!TRAP] Toy retrieval numbers are not evidence
> The TF-IDF recall above comes from ten chunks and four follow-ups. Do not use it to compare retrievers.

## Summary

- A query engine is a retriever followed by a response synthesizer; a chat engine adds memory and a condense step.
- Retrieval scores are cosines of TF-IDF vectors; you derived 0.611 for chunk 0 by hand, and the code agrees.
- The synthesis mode sets the number of LLM calls: for six chunks, refine makes 6, compact 2, tree_summarize 3 and simple_summarize 1.
- Packing is bounded by the window minus the template, the answer and the padding (78 words here).
- A chat turn with history makes two LLM calls, and retrieval quality depends on the standalone question and on the retriever.

## Quiz time

### Question 1: Calculation

Six chunks of 20, 12, 17, 17, 18 and 19 words go to compact synthesis with a 78-word budget. How many prompts are made, and how many chunk words does each hold?

<details><summary>Show solution</summary>

Greedy packing in order: 20 + 12 + 17 + 17 = 66. Adding 18 would give 84, which is over 78, so the first prompt holds 66 words. The second prompt holds 18 + 19 = 37 words. Two prompts, 66 and 37 words.

</details>

### Question 2: Prediction

Ten chunks of 17 words each go to refine and then to compact, with the same 78-word budget. How many LLM calls does each make?

<details><summary>Show solution</summary>

Refine makes one call per chunk: 10. Compact packs first. Four chunks make 68 words, and five would make 85, so the packs hold 4, 4 and 2 chunks. That is 3 calls.

</details>

### Question 3: Bug-spotting

A chat engine retrieves with `retrieve(user_message, k)` on the raw follow-up "How often do its seals need replacing?", then condenses only for the answer. Name the bug and the fix.

<details><summary>Show solution</summary>

The word "its" has no referent in the query, so the retriever scores terms that are not in the conversation. The fix is to retrieve with the condensed standalone question, and to synthesize with the user's original message, as `ChatEngine.chat` does in the code.

</details>

### Question 4: Explanation

Why does `simple_summarize` make the fewest calls but not always the best choice?

<details><summary>Show solution</summary>

It puts all context into one prompt, so its size is limited by the window. The ten chunks here total 171 words, more than the 120-word window, so the single prompt would fail. Its one call is cheap only when everything fits.

</details>

### Question 5: Explanation

In the stub run, why does the refine answer equal the first 12 words of chunk 3, and what would change with a real LLM?

<details><summary>Show solution</summary>

Chunk 3 is the last chunk, and the stub copies the start of the context it receives, so the last call's output replaces all earlier answers. A real LLM would combine the existing answer with the new chunk, so earlier chunks could still shape the answer. The order of chunks still matters, because the last call sees the most recent answer.

</details>
