By the end you will be able to explain why one retrieval call can miss a question with two parts, trace the two steps that LlamaIndex's `SubQuestionQueryEngine` and `RouterQueryEngine` add, and count what each step costs in model calls. The numbers come from a toy corpus of eight sentences, so they show mechanisms, not benchmark results.

**You need:** the query engine and response synthesizer from Lesson 44.2, and the idea of a retrieval budget k: the number of text chunks you pass to the model. (Lesson 44.2 uses "budget" for words of context, which is a different quantity.) The first code block uses only NumPy; the LlamaIndex block needs `pip install llama-index-core`.

## The problem one retrieval call struggles with

A retrieval-augmented generation (RAG) system turns the user's question into a vector, finds the top-k chunks (the k pieces of text whose vectors are closest), and gives them to a large language model (LLM) that writes the answer. The number of chunks passed, k, is the **budget** in this lesson.

Take a question with two parts: "Where will Acme Corp expand its factories and how much revenue did Borealis Ltd report in 2023?" Its answer lives in two chunks: one about Acme's expansion (chunk 6) and one about Borealis's revenue (chunk 2). One embedding of the whole question sits between the two topics. With a budget of two, the Acme words can outweigh the Borealis words. The code below reproduces that failure with a word-count embedding, so you can see every step.

```python
import re
import numpy as np

CHUNKS = [
    "Acme Corp reported revenue of 120 million dollars in 2023.",
    "Acme Corp opened three new factories in Ohio during 2023.",
    "Borealis Ltd reported revenue of 85 million dollars in 2023.",
    "Borealis Ltd hired 400 engineers in Norway during 2023.",
    "Cobalt Inc reported revenue of 40 million dollars in 2023.",
    "Cobalt Inc announced a merger with a robotics startup in 2022.",
    "Acme Corp plans to expand its factories to Texas in 2024.",
    "Borealis Ltd sells wind turbines to farms in Scotland.",
]
STOP = {"what", "was", "of", "and", "in", "how", "many", "did", "where", "will", "its", "to",
        "the", "a", "an", "does", "do", "much", "or", "with", "is", "were", "which", "who",
        "from", "their", "that", "for", "on", "at", "by", "it", "as", "s"}

def words(text):
    return [w for w in re.findall(r"[a-z0-9]+", text.lower()) if w not in STOP]

VOCAB = sorted({w for c in CHUNKS for w in words(c)})
IDX = {w: i for i, w in enumerate(VOCAB)}

def embed(text):
    v = np.zeros(len(VOCAB))
    for w in words(text):
        if w in IDX:
            v[IDX[w]] += 1
    n = np.linalg.norm(v)
    return v / n if n else v

C = np.stack([embed(c) for c in CHUNKS])

def top_k(query, k):
    scores = C @ embed(query)
    return [int(i) for i in np.argsort(-scores, kind="stable")[:k]]

# Part 1: one retrieval call versus sub-questions, same budget of 2 chunks
query = "Where will Acme Corp expand its factories and how much revenue did Borealis Ltd report in 2023?"
gold = {6, 2}
subs = ["Where will Acme Corp expand its factories?",
        "How much revenue did Borealis Ltd report in 2023?"]
single = top_k(query, 2)
decomposed = []
for s in subs:
    for i in top_k(s, 2 // len(subs)):
        if i not in decomposed:
            decomposed.append(i)
print("gold chunks:           ", sorted(gold))
print("single query, top 2:   ", single, "recall", len(gold & set(single)) / len(gold))
print("sub-questions, 1 each: ", decomposed, "recall", len(gold & set(decomposed)) / len(gold))

# Part 2: a router picks a tool by word overlap with each tool description
CLEAR = {"revenue_tool": "company revenue, sales and financial results",
         "operations_tool": "factories, plants, expansion and products",
         "people_tool": "hiring, engineers and staff headcount",
         "deals_tool": "mergers, acquisitions and corporate announcements"}
VAGUE = {"revenue_tool": "companies and their 2023 results",
         "operations_tool": "companies and their 2023 plans",
         "people_tool": "companies and their 2023 staff",
         "deals_tool": "companies and their 2023 news"}

def route(query, tools):
    q = set(words(query))
    scores = {name: len(q & set(words(desc))) for name, desc in tools.items()}
    best = max(scores.values())
    return next(name for name, s in scores.items() if s == best)  # ties go to the first tool listed

for label, tools in (("clear", CLEAR), ("vague", VAGUE)):
    print(f"{label:5} descriptions: route('Which plants does Borealis Ltd run?') ->",
          route("Which plants does Borealis Ltd run?", tools))
```

```output
gold chunks:            [2, 6]
single query, top 2:    [6, 0] recall 0.5
sub-questions, 1 each:  [6, 2] recall 1.0
clear descriptions: route('Which plants does Borealis Ltd run?') -> operations_tool
vague descriptions: route('Which plants does Borealis Ltd run?') -> revenue_tool
```

With a budget of two, the single query returns chunks 6 and 0: both Acme chunks, and the Borealis revenue chunk is missing. Splitting the question into two sub-questions, each with its own top-1 search, returns chunks 6 and 2.

## Two fixes, two different jobs

`SubQuestionQueryEngine` splits one question into several, answers each part with an engine, and then combines the answers. `RouterQueryEngine` does not split anything. It picks which engine should answer the question, given a short description of each engine. Figure 1 shows the sub-question path.

![Flow of SubQuestionQueryEngine: the question generator writes two sub-questions, each goes to an engine that retrieves chunks and answers, and a synthesizer writes the final answer from the sub-answers](diagrams/44.3-subquestion-flow.svg "Figure 1. The sub-question path: N sub-questions, N + 2 LLM calls.")

## How SubQuestionQueryEngine works

I read the three stages in the installed source, `llama-index-core` 0.14.26, file `query_engine/sub_question_query_engine.py`:

1. **Question generation.** `LLMQuestionGenerator` (in `question_gen/llm_generators.py`) sends the question and a JSON map of tool names to descriptions to the LLM, and parses a JSON list of `{sub_question, tool_name}` objects.
2. **Sub-question execution.** Each sub-question runs on the engine named by its `tool_name`. Each engine retrieves chunks and makes one LLM call to write a sub-answer.
3. **Synthesis.** The sub-answers and their source chunks go to a response synthesizer, which makes one more LLM call and writes the final answer.

For N sub-questions, that is N + 2 LLM calls: one to write the sub-questions, one per sub-answer, and one to synthesize. The stub run below counts four calls for a two-part question, which matches. The engine runs sub-questions concurrently by default (`use_async=True`); the code below turns that off so the output order is fixed. `from_defaults` tries to import an OpenAI-based question generator from a separate package, and raises `ImportError` if that package is missing and you did not pass `question_gen`. The code below passes it explicitly.

## Retrieval budget: what the decomposition buys

I ran six compound queries over the same eight chunks (the script `scripts/diagrams/lessons/44.3_experiment.py` in the course repository). The sub-questions are hand-written, standing in for the LLM. Retrieval is bag-of-words cosine similarity with stopwords removed and no stemming. The budget is the same for both methods. At budget 2, the single query takes the top 2 and the decomposed query takes the top 1 per sub-question. At budget 4, the single query takes the top 4 and the decomposed query takes the top 2 per sub-question.

| Budget (total chunks) | Single query, mean recall | Sub-questions, mean recall | Both needed chunks found |
|---|---|---|---|
| 2 | 0.917 | 1.000 | single 5 of 6 queries, sub-questions 6 of 6 |
| 4 | 1.000 | 1.000 | 6 of 6 for both |

![Grouped bars of mean recall for single-query and sub-question retrieval at budgets 2 and 4](diagrams/44.3-compound-recall.svg "Figure 2. Recall of the needed chunks; the budget is the total number of chunks.")

The single query fails on one query only, the Acme-expansion question from the demo, and at budget 4 it finds the missing chunk. The gap is one query and one chunk on a corpus where the two halves are easy to separate. This shows the mechanism under a tight budget. It is not evidence that decomposition wins in general, and a real LLM may write poor sub-questions.

## RouterQueryEngine: the description is the whole signal

`RouterQueryEngine` gives a selector the descriptions of its engines. `LLMSingleSelector` lists them as numbered choices, asks the model for a JSON list such as `[{"choice": 2, "reason": "..."}]`, and runs the engine it picks (parsing in `output_parsers/selection.py`). `get_selector_from_llm` first tries a Pydantic selector that uses function calling and falls back to the text-parsing selector if the model does not support it. `LLMMultiSelector` can return several choices instead of one.

I measured the routing rule with a keyword-overlap score standing in for the selector: each tool gets the count of words it shares with the query, and the highest score wins. Ties go to the first tool listed. With four tools and twelve labelled queries, clear descriptions gave 11 of 12 correct. Vague descriptions such as "companies and their 2023 results" gave 6 of 12. All six vague errors went to `revenue_tool`, the first tool listed, because every score was tied. The one clear miss, "Did Cobalt Inc announce a merger in 2022?", shares no word form with the deals description ("merger" against "mergers", "announce" against "announcements"). An LLM selector reads meaning and would probably not make that miss, so these numbers show how much the descriptions matter, not how well an LLM selector performs.

![One query scored against two sets of tool descriptions: clear descriptions choose operations_tool, vague descriptions tie at zero and choose revenue_tool](diagrams/44.3-router-choice.svg "Figure 3. Same query, two sets of descriptions.")

![Bar chart of router accuracy: 0.92 with clear descriptions, 0.50 with vague descriptions](diagrams/44.3-router-accuracy.svg "Figure 4. Router accuracy on 12 labelled queries, keyword-overlap stand-in.")

## Running the real classes with a stub model

The block below uses the real LlamaIndex classes from `llama-index-core` 0.14.26. The LLM is a stub that returns fixed JSON for the three kinds of prompt it receives, and the embedding is the same word-count idea as above. The output shows that the wiring works. It says nothing about answer quality, which is why the answers read "[stub]".

<details><summary>Run locally: needs pip install llama-index-core</summary>

```python
import json, re, warnings
warnings.filterwarnings("ignore")
import numpy as np
from llama_index.core import Document, Settings, VectorStoreIndex
from llama_index.core.embeddings import BaseEmbedding
from llama_index.core.llms import CompletionResponse, CustomLLM, LLMMetadata
from llama_index.core.query_engine import RouterQueryEngine, SubQuestionQueryEngine
from llama_index.core.question_gen.llm_generators import LLMQuestionGenerator
from llama_index.core.schema import QueryBundle
from llama_index.core.selectors import LLMSingleSelector
from llama_index.core.tools import QueryEngineTool, ToolMetadata
import importlib.metadata

CHUNKS = {
    "c0": "Acme Corp reported revenue of 120 million dollars in 2023.",
    "c1": "Acme Corp opened three new factories in Ohio during 2023.",
    "c2": "Borealis Ltd reported revenue of 85 million dollars in 2023.",
    "c3": "Borealis Ltd hired 400 engineers in Norway during 2023.",
}
WORDS = sorted({w for t in CHUNKS.values() for w in re.findall(r"[a-z0-9]+", t.lower())})
IDX = {w: i for i, w in enumerate(WORDS)}

class BowEmbedding(BaseEmbedding):
    def _vec(self, text):
        v = np.zeros(len(WORDS))
        for w in re.findall(r"[a-z0-9]+", text.lower()):
            if w in IDX:
                v[IDX[w]] += 1
        n = np.linalg.norm(v)
        return (v / n if n else v).tolist()
    def _get_query_embedding(self, query): return self._vec(query)
    def _get_text_embedding(self, text): return self._vec(text)
    async def _aget_query_embedding(self, query): return self._vec(query)

Q_SUB = "What was the revenue of Acme Corp and Borealis Ltd in 2023?"
SUBS = {Q_SUB: [{"sub_question": "What was the revenue of Acme Corp in 2023?", "tool_name": "annual_reports"},
                {"sub_question": "What was the revenue of Borealis Ltd in 2023?", "tool_name": "annual_reports"}]}
DESCS = {"revenue_tool": "Answers questions about company revenue and financial results",
         "operations_tool": "Answers questions about factories and expansion plans"}
Q_ROUTE = ["What was the revenue of Acme Corp in 2023?", "Where did Acme Corp open new factories?"]
STOP = {"what","was","of","and","in","did","where","new","the","a"}

def words(t): return {w for w in re.findall(r"[a-z0-9]+", t.lower())} - STOP

CALLS = [0]

class ScriptedLLM(CustomLLM):
    """Stub LLM: answers the three prompt types LlamaIndex sends, with fixed rules."""
    @property
    def metadata(self):
        return LLMMetadata(context_window=4096, num_output=256, model_name="scripted-stub")
    def complete(self, prompt, formatted=False, **kwargs):
        return CompletionResponse(text=self._respond(prompt))
    def stream_complete(self, prompt, formatted=False, **kwargs):
        raise NotImplementedError
    def _respond(self, prompt):
        CALLS[0] += 1
        if "list of relevant sub-questions" in prompt:
            q = next(k for k in SUBS if k in prompt)
            return json.dumps(SUBS[q])
        if "choice(s) most relevant" in prompt or "Some choices are given" in prompt:
            q = next(k for k in Q_ROUTE if k in prompt)
            order = sorted(DESCS, key=lambda n: prompt.find(DESCS[n]))
            scores = [len(words(q) & words(DESCS[n])) for n in order]
            return json.dumps([{"choice": int(np.argmax(scores)) + 1, "reason": "stub: keyword overlap"}])
        return "[stub] answer drawn from the retrieved context"

llm = ScriptedLLM()
Settings.llm = llm
Settings.embed_model = BowEmbedding()

docs = [Document(text=t, id_=k) for k, t in CHUNKS.items()]
index = VectorStoreIndex.from_documents(docs)
engine = index.as_query_engine(similarity_top_k=2)
tools = [QueryEngineTool(query_engine=engine, metadata=ToolMetadata(
    name="annual_reports", description="Useful for answering questions about company revenue and factories"))]

question_gen = LLMQuestionGenerator.from_defaults(llm=llm)
sub_engine = SubQuestionQueryEngine.from_defaults(query_engine_tools=tools, llm=llm,
                                                  question_gen=question_gen, use_async=False, verbose=False)
print("1) sub-questions generated:")
for sq in question_gen.generate([t.metadata for t in tools], QueryBundle(Q_SUB)):
    print("  ", sq.tool_name, "|", sq.sub_question)
CALLS[0] = 0
resp = sub_engine.query(Q_SUB)
print("   LLM calls for one sub-question query:", CALLS[0])
print("2) final answer:", str(resp))
print("   source nodes returned:", len(resp.source_nodes))

fin = VectorStoreIndex.from_documents([d for d in docs if d.id_ in ("c0", "c2")]).as_query_engine(similarity_top_k=1)
ops = VectorStoreIndex.from_documents([d for d in docs if d.id_ in ("c1", "c3")]).as_query_engine(similarity_top_k=1)
rtools = [
    QueryEngineTool(query_engine=fin, metadata=ToolMetadata(name="revenue_tool", description=DESCS["revenue_tool"])),
    QueryEngineTool(query_engine=ops, metadata=ToolMetadata(name="operations_tool", description=DESCS["operations_tool"])),
]
router = RouterQueryEngine.from_defaults(query_engine_tools=rtools, llm=llm,
                                         selector=LLMSingleSelector.from_defaults(llm=llm))
print("3) router decisions:")
for q in Q_ROUTE:
    r = router.query(q)
    sel = r.metadata["selector_result"].selections[0]
    print(f"   {q!r} -> {rtools[sel.index].metadata.name} (reason: {sel.reason})")
print("llama-index-core:", importlib.metadata.version("llama-index-core"))
```

```output
1) sub-questions generated:
   annual_reports | What was the revenue of Acme Corp in 2023?
   annual_reports | What was the revenue of Borealis Ltd in 2023?
   LLM calls for one sub-question query: 4
2) final answer: [stub] answer drawn from the retrieved context
   source nodes returned: 6
3) router decisions:
   'What was the revenue of Acme Corp in 2023?' -> revenue_tool (reason: stub: keyword overlap)
   'Where did Acme Corp open new factories?' -> operations_tool (reason: stub: keyword overlap)
llama-index-core: 0.14.26
```

## Common traps

> [!TRAP] **Counting sub-questions as free.** Each sub-question adds an LLM call and its retrieved chunks. Five sub-questions cost seven calls (N + 2) and can fill a budget that a single query would not.

> [!TRAP] **Vague tool descriptions.** A router can only use what the descriptions say. If every description says "companies and their 2023 results", the choice is decided by a tie, which in this lesson's stand-in means the first tool listed.

> [!TRAP] **Assuming sub-questions are independent.** `SubQuestionQueryEngine` writes every sub-question before any is answered. A question such as "Who founded the company that bought Cobalt Inc?" needs the first answer before the second query can be written. Iterative patterns such as self-ask (Press et al., 2022) handle that case.

> [!TRAP] **Reading stub output as model output.** The "[stub]" answers and the scripted router choices prove that the classes are wired together. They do not measure retrieval quality or LLM routing quality. Evaluate with the real model on labelled queries before you trust either engine.

## Summary

- A single retrieval call can spend a small budget on the easier half of a two-part question.
- `SubQuestionQueryEngine` writes sub-questions, answers each one on a named engine, and synthesizes the result, at a cost of N + 2 LLM calls.
- In the toy experiment, decomposition improved recall only at the tight budget of 2, by one query and one chunk.
- `RouterQueryEngine` chooses an engine from its description, so overlapping descriptions produce wrong or tied routes.
- Stub runs verify wiring. Measure answer quality and routing with a real model on labelled queries.

### Question 1: Calculation

A question is split into three sub-questions. Counting question generation, the sub-answers and the final synthesis, how many LLM calls does `SubQuestionQueryEngine` make?

<details><summary>Show solution</summary>

Five calls: 1 for question generation, 3 for the sub-answers, and 1 for synthesis. The general count is N + 2 with N = 3.

</details>

### Question 2: Prediction

With budget 2, the single query in the demo returns chunks 6 and 0. Which needed chunk is missing, and what budget fixes it for the single query?

<details><summary>Show solution</summary>

Chunk 2, the Borealis revenue sentence, is missing. The experiment shows the single query finds it at budget 4, where it returns chunks 6, 0, 2 and 1.

</details>

### Question 3: Bug-spotting

Two tools both have the description "Useful for questions about companies". A keyword-overlap router is used on a query about either tool's content. What happens, and what should you change?

<details><summary>Show solution</summary>

The scores tie, so the first tool listed wins every time, whichever tool the query is about. Write a description that names the content the tool holds, such as its revenue figures or its hiring records.

</details>

### Question 4: Explanation

Why is the toy experiment not evidence that decomposition improves RAG in general?

<details><summary>Show solution</summary>

It uses eight chunks, six queries, hand-written sub-questions, bag-of-words retrieval and no answer-quality metric. Only one query changes between the two methods at budget 2. A real test needs a realistic corpus, LLM-written decompositions, and answer metrics on held-out queries.

</details>
