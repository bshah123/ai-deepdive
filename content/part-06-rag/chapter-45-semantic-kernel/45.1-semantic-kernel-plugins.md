In this lesson you will write a Python plugin, register it with a Semantic Kernel kernel, and explain how the kernel turns your function signature into the description a language model reads. You will also run a small pure-Python kernel that shows the same mechanism in your browser.

**You need:** Python decorators (Lesson 8.3) and type annotations (Lesson 14.1).

## The problem the kernel solves

A large language model (LLM) produces text. It cannot read your database or add two numbers unless your program does that work for it. The usual pattern is called function calling. Your program tells the model which functions exist, with their argument names and types. The model replies with a request such as "call `math-add` with these arguments". Your program runs the function and returns the result as text for the model to use.

Doing this by hand for every function means writing descriptions, parsing replies, converting strings to numbers and handling errors. Microsoft's Semantic Kernel (SK) is a software development kit (SDK) that does this bookkeeping. It has C#, Java and Python versions. This lesson uses the Python API. The code and the behaviour described below were run against `semantic-kernel` version 1.36.0.

Microsoft's documentation describes the same loop: "With function calling, LLMs can request (i.e., call) a particular function. Semantic Kernel then marshals the request to the appropriate function in your codebase and returns the results back to the LLM" (reference 1).

![Six steps of one plugin call: register methods, send schemas to the model, the model replies, the kernel checks arguments, the method runs, and the result returns to the model](diagrams/45.1-plugin-call-loop.svg "One plugin call. Amber steps involve the model; blue steps are ordinary Python.")

## Plugins, kernels and functions

Three words carry the lesson.

- A **plugin** is a Python class whose methods you mark with `@kernel_function`.
- A **function** is one marked method. The kernel names it `plugin-function`, for example `math-add`.
- A **kernel** holds the plugins, builds the descriptions the model reads, and runs the calls.

## What the kernel reads from your signature

The kernel needs no separate schema file. For each marked method it reads the parameter names, their type annotations, and the `Annotated` strings, which become parameter descriptions. The plugin name `math` comes from the `add_plugin` call, not from the class name. Semantic Kernel 1.36.0 reports exactly this metadata for the signature below (see the Semantic Kernel section).

![Left: a Python class with an add method whose parameters are annotated float. Right: the metadata the kernel derives, math-add with two required float parameters and a float return](diagrams/45.1-signature-to-metadata.svg "The annotations become the JSON types and descriptions that the model sees.")

## Worked example by hand

Ask the kernel to run `math-add` with `num1` = 5 and `num2` = 3. The arithmetic is $5 + 3 = 8$. Because the model sends JSON text, the arguments arrive as the strings `"5"` and `"3"`. The kernel converts each one to its annotated type, `float`, giving 5.0 and 3.0. The method returns 8.0, and the kernel hands the model the text `"8.0"`.

![Four cards traced left to right: the model's reply text, the values after coercion to float, the method's return value, and the string sent back to the model. Two error boxes sit below](diagrams/45.1-one-call-trace.svg "One call, value by value. The error boxes show what the mini kernel below raises.")

## A mini kernel you can run in the browser

The code below is a teaching model of the mechanism. It is not Semantic Kernel's source code. The decorator stores a name and description on the method. `add_plugin` collects the marked methods. `schema` builds the JSON description from the signature and annotations. `invoke` checks required arguments, converts each argument to its annotated type, calls the method, and returns the result as text. A fixed string stands in for the model, so the example needs no API key.

```python
import inspect
import json
import typing
from typing import Annotated

JSON_TYPE = {float: "number", int: "integer", str: "string", bool: "boolean"}

def kernel_function(name=None, description=""):
    """Mark a method so the kernel can expose it to the model."""
    def mark(fn):
        fn._kf = {"name": name or fn.__name__, "description": description}
        return fn
    return mark

def _base_and_doc(annotation):
    if typing.get_origin(annotation) is Annotated:
        base, doc = typing.get_args(annotation)[:2]
        return base, doc
    return annotation, ""

class MiniKernel:
    def __init__(self):
        self._fns = {}

    def add_plugin(self, plugin, plugin_name):
        for attr in dir(plugin):
            fn = getattr(plugin, attr)
            meta = getattr(fn, "_kf", None)
            if meta is not None:
                self._fns[f"{plugin_name}-{meta['name']}"] = (fn, meta)

    def schema(self, key):
        """Build the description the model sees, from the signature and annotations."""
        fn, meta = self._fns[key]
        hints = typing.get_type_hints(fn, include_extras=True)
        props, required = {}, []
        for pname, param in inspect.signature(fn).parameters.items():
            base, doc = _base_and_doc(hints[pname])
            prop = {"type": JSON_TYPE[base]}
            if doc:
                prop["description"] = doc
            props[pname] = prop
            if param.default is inspect.Parameter.empty:
                required.append(pname)
        return {"name": key, "description": meta["description"],
                "parameters": {"type": "object", "properties": props, "required": required}}

    def invoke(self, key, arguments):
        """Run one function call requested by the model. arguments is a dict."""
        fn, _ = self._fns[key]
        hints = typing.get_type_hints(fn, include_extras=True)
        kwargs = {}
        for pname in inspect.signature(fn).parameters:
            if pname not in arguments:
                raise ValueError(f"{key}: missing required argument '{pname}'")
            base, _ = _base_and_doc(hints[pname])
            kwargs[pname] = base(arguments[pname])   # coerce, e.g. "5" -> 5.0
        return str(fn(**kwargs))

def handle_model_text(kernel, text):
    """The model replies with text such as {"function": ..., "arguments": {...}}."""
    call = json.loads(text)
    return kernel.invoke(call["function"], call["arguments"])

class MathPlugin:
    @kernel_function(description="Adds two numbers together")
    def add(self, num1: Annotated[float, "first number"],
            num2: Annotated[float, "second number"]) -> float:
        return num1 + num2

    @kernel_function(description="Divides num1 by num2")
    def divide(self, num1: float, num2: float) -> float:
        return num1 / num2

if __name__ == "__main__":
    kernel = MiniKernel()
    kernel.add_plugin(MathPlugin(), "math")
    print(json.dumps(kernel.schema("math-add"), indent=2))
    reply = '{"function": "math-add", "arguments": {"num1": "5", "num2": "3"}}'
    print("model reply:", reply)
    print("result:", handle_model_text(kernel, reply))
```

```output
{
  "name": "math-add",
  "description": "Adds two numbers together",
  "parameters": {
    "type": "object",
    "properties": {
      "num1": {
        "type": "number",
        "description": "first number"
      },
      "num2": {
        "type": "number",
        "description": "second number"
      }
    },
    "required": [
      "num1",
      "num2"
    ]
  }
}
model reply: {"function": "math-add", "arguments": {"num1": "5", "num2": "3"}}
result: 8.0
```

The `add` schema above is what the model would receive for that function. Each property's `type` comes from the annotation, and `required` lists every parameter without a default.

Reading the code in order: `kernel_function` attaches a small dictionary to the method, and that is all the decorator does. `add_plugin` uses `dir` to find every method carrying that dictionary and stores it under the key `math-add`. `schema` asks `typing.get_type_hints` for the annotations, with `include_extras=True` so that the `Annotated` strings survive, and writes one JSON property per parameter. `invoke` walks the same information in reverse. It checks that each required name is present, converts each value with its annotated type, and calls the method with keyword arguments.

Semantic Kernel does more, such as supporting async methods and injecting services into a plugin's constructor. Its job still splits the same way: mark, register, describe, dispatch (reference 1).

## Why the number of functions matters

Every registered function adds its schema to the text the model reads. Measured with the mini kernel, one `add`-shaped function takes about 241 characters of compact JSON, and the total grows in a straight line with the number of functions.

![Bar chart of schema size in characters: 242 for one function, 483 for two, 965 for four, 1929 for eight and 3863 for sixteen](diagrams/45.1-schema-size.svg "Schema size grows linearly. Characters are a proxy: the model is billed in tokens.")

Microsoft's guide recommends importing only the plugins a scenario needs, because each function adds input tokens and gives the model another choice it can get wrong (reference 1).

OpenAI's function-calling guide gives the same reason for restraint. It says "Aim for fewer than 20 functions available at the start of a turn at any one time, though this is just a soft suggestion", and that tool definitions "count against the model's context limit and are billed as input tokens" (reference 3).

## The same mechanism in Semantic Kernel

The check below uses the real `semantic-kernel` package. It needs `pip install semantic-kernel`. The API is asynchronous, so the calls run inside `asyncio.run`.

<details><summary>Run locally: needs pip install semantic-kernel</summary>

```python
"""Checks the lesson's claims against the real semantic-kernel package (1.36.0). Needs pip install semantic-kernel."""
import asyncio, logging
from typing import Annotated
from semantic_kernel import Kernel
from semantic_kernel.functions import kernel_function, KernelArguments
logging.disable(logging.CRITICAL)

class MathPlugin:
    @kernel_function(name="add", description="Adds two numbers together")
    def add(self, num1: Annotated[float, "first number"], num2: Annotated[float, "second number"]) -> float:
        return num1 + num2

    @kernel_function(name="divide", description="Divides num1 by num2")
    def divide(self, num1: float, num2: float) -> float:
        return num1 / num2

async def main():
    kernel = Kernel()
    kernel.add_plugin(MathPlugin(), plugin_name="math")
    r = await kernel.invoke(plugin_name="math", function_name="add", num1=5, num2=3)
    print("add(5, 3) =", r.value)
    r = await kernel.invoke(kernel.get_function("math", "add"), KernelArguments(num1="5", num2="3"))
    print("add with string arguments =", r.value)
    for m in kernel.get_full_list_of_function_metadata():
        print(m.fully_qualified_name, [(p.name, p.type_, p.is_required, p.description) for p in m.parameters], "->", m.return_parameter.type_)
    try:
        await kernel.invoke(plugin_name="math", function_name="add", num1=5)
    except Exception as e:
        print("missing argument ->", type(e).__name__)
    try:
        await kernel.invoke(plugin_name="math", function_name="divide", num1=10, num2=0)
    except Exception as e:
        print("divide by zero ->", type(e).__name__, "| cause:", type(e.__cause__).__name__ if e.__cause__ else None)
    try:
        await kernel.invoke(plugin_name="math", function_name="multiply", num1=1, num2=2)
    except Exception as e:
        print("unknown function ->", type(e).__name__)

asyncio.run(main())
```

Output from `semantic-kernel` 1.36.0 on Python 3.12:

```output
add(5, 3) = 8.0
add with string arguments = 8.0
math-add [('num1', 'float', True, 'first number'), ('num2', 'float', True, 'second number')] -> float
math-divide [('num1', 'float', True, None), ('num2', 'float', True, None)] -> float
missing argument -> KernelInvokeException
divide by zero -> KernelInvokeException | cause: ZeroDivisionError
unknown function -> KernelFunctionNotFoundError
```

</details>

Microsoft's plugin guide gives a reason to use classes rather than loose functions: "Within a plugin's constructor, you can inject services that are necessary to perform the work of the plugin (e.g., database connections, HTTP clients, etc.)" (reference 1). The class in this lesson takes no constructor arguments, so it does not show that feature.

Three details differ from the mini kernel. SK reports a failed call as `KernelInvokeException`; for a division by zero, the original `ZeroDivisionError` is its cause. An unknown function name raises `KernelFunctionNotFoundError`. `kernel.invoke` also converts the string `"5"` to `5.0`, as the mini kernel does. The check calls functions directly only to show the mechanism. Microsoft's guide says that while direct invocation is possible, "this is not advised because the AI should be the one deciding which functions to call" (reference 1).

## Common traps

> [!TRAP]
> **Old API names.** Pre-1.0 tutorials use `import_skill`, `sk_function` and `SKContext`. In semantic-kernel 1.36.0, `semantic_kernel.skill_definition` and `semantic_kernel.orchestration` raise `ModuleNotFoundError`, and `Kernel` has no `import_skill` method. Use `add_plugin` and `kernel_function`.

> [!TRAP]
> **A missing argument raises; it does not arrive as `None`.** Both the mini kernel and SK refuse a call without `num2`. In SK the error is `KernelInvokeException`.

> [!TRAP]
> **Conversion depends on annotations.** The string `"5"` becomes 5.0 only because the parameter is annotated `float`. Annotate every parameter. An unannotated parameter gives the kernel no type to write into the schema or convert to. This is my reasoning; I did not test unannotated parameters.

> [!TRAP]
> **Exceptions are not text.** A division by zero inside your method reaches the application as `KernelInvokeException` with `ZeroDivisionError` as its cause (verified above). Returning an error string, as an early draft did, gives the model text it can read and react to. I did not test how SK reports errors to the model during automatic function calling, so choose the error path deliberately.

> [!TRAP]
> **Descriptions are the model's only guide.** The model chooses a function from its name, description and parameter descriptions. Microsoft's guide says that without them "the AI will not correctly call the function" (reference 1). Write each description as if for a colleague who cannot read your code.

> [!TRAP]
> **Direct calls skip the model.** Calling a plugin function from your own code bypasses the model's choice of function. The examples here do it only to show the mechanism.

## Summary

- A plugin is a class of `@kernel_function` methods, and the kernel turns each one into a named, typed description such as `math-add`.
- Parameter types come from annotations, and parameter descriptions come from `Annotated` strings.
- The kernel converts argument strings to the annotated types before calling your method.
- Every registered function adds to the description the model reads. The mini kernel measures about 241 characters per function.
- Current Semantic Kernel uses `add_plugin` and `kernel_function`. The older `import_skill` and `sk_function` no longer exist.

## Quiz time

### Question 1: What does the mini kernel return for this reply?

`{"function": "math-divide", "arguments": {"num1": "9", "num2": "4"}}`

<details><summary>Show Solution</summary>

The string `"2.25"`. The kernel converts `"9"` and `"4"` to 9.0 and 4.0, the method returns 9.0 / 4.0 = 2.25, and `str()` gives `"2.25"`.

</details>

### Question 2: Bug-spotting. A student's code begins with `from semantic_kernel.skill_definition import sk_function` and then calls `kernel.import_skill(MathPlugin(), "math")`. What fails, and what is the fix?

<details><summary>Show Solution</summary>

Both fail on semantic-kernel 1.36.0. The module `semantic_kernel.skill_definition` no longer exists, so the import raises `ModuleNotFoundError`. Even with the import removed, `Kernel` has no `import_skill` method. The fix is `from semantic_kernel.functions import kernel_function`, decorating methods with `@kernel_function`, and calling `kernel.add_plugin(MathPlugin(), plugin_name="math")`.

</details>

### Question 3: From the bar chart, how many characters does going from 4 functions to 8 functions add, and how much is that per function?

<details><summary>Show Solution</summary>

The chart gives 1,929 − 965 = 964 characters. Four more functions cost 964 / 4 = 241 characters each, which matches the per-function figure of about 241.

</details>

### Question 4: Explain why the mini kernel raises `ValueError` for `{"num1": "5"}` instead of filling `num2` with 0.

<details><summary>Show Solution</summary>

Filling in a guess would produce a plausible-looking wrong answer, and the application would not know the model had omitted a value. Raising an error makes the failure visible, and the error text can be returned to the model so it can ask again. This is reasoning about design, not a measured result.

</details>
