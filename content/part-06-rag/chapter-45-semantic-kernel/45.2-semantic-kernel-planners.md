In this lesson you will build the loop that lets a language model call ordinary Python functions: a JSON schema generated from a function signature, a kernel that checks and runs each requested call, and a loop that feeds results back until the model answers in plain text. You will also see why Semantic Kernel's original planners were replaced by this loop.

**You need:** Python functions with type hints and dictionaries (standard library only), and Lesson 45.1 (kernels and plugins). The model here is a scripted stand-in, so no API key is needed.

## The problem a planner solves

Suppose an application has three functions and a user writes: "Greet Alice, add 5 and 7, then save the result to result.json." Something must decide which functions to call, in what order, and with which arguments.

The simplest answer is keyword matching: pick a function whose name appears in the goal. The code below includes that heuristic, `keyword_planner`. It selects only `greet`, because the goal says "add 5 and 7", not `calculate_sum`, and it never mentions `save_to_file`. Rewording the goal as "calculate sum" makes it select nothing. Matching strings is not understanding a goal.

Semantic Kernel's early planners tried to do better by asking the model, in a prompt, to choose the functions and then parsing its text. Microsoft's documentation now says Semantic Kernel uses function calling "as the primary way to plan and execute tasks", and that the Stepwise and Handlebars planners "have been deprecated and removed" [1].

## The loop, not a plan

Function calling replaces the planner with a loop in which the model chooses one step at a time, and the code runs each step. This is the same alternation of model output and tool results studied in ReAct [3]. Semantic Kernel's documentation lists the steps: serialise the functions as JSON schemas, send them with the chat history, read the reply, invoke any function the model requested, return the result to the history, and repeat until the model returns a chat message or the maximum iteration count is reached [2].

![Flow: chat history and JSON schemas go to the model; a reply is either final text or a call that the kernel validates and invokes; the result is added to the history and the loop repeats](diagrams/45.2-function-loop.svg "Each model reply is text, which ends the run, or a call that the kernel runs and records.")

Two details matter. The model sees only names, descriptions and parameter types, never Python objects. And every result is appended to the history, so each later model call sees everything before it. The cost of that is covered below.

## Worked example by hand: from signature to schema

Take `def calculate_sum(a: int, b: int) -> int:` with the docstring "Adds two integers." Build its schema step by step:

1. The name is the function name: `calculate_sum`.
2. The description is the docstring.
3. Each parameter becomes a property. The annotation `int` maps to the JSON type `"integer"`.
4. A parameter with no default goes into `required`. Both `a` and `b` lack defaults, so both are required.
5. The return type `-> int` is not sent. Semantic Kernel's documentation says return types are not serialised into the schema [2].

![A calculate_sum code box, an arrow labelled to_schema, and the resulting JSON with name, description, parameters and required fields](diagrams/45.2-signature-to-schema.svg "A Python signature with type hints and a docstring becomes the JSON the model reads.")

Semantic Kernel does the same serialisation, but only for functions marked with its `kernel_function` decorator [2]. Our `to_schema` skips the marker and serialises every function added to the kernel. The code below is the whole mechanism in standard-library Python. It is not Semantic Kernel. Its class is also named `Kernel`, but it is a separate teaching model, unrelated to the `MiniKernel` of Lesson 45.1 and to Semantic Kernel's `Kernel`. `scripted_model` returns replies written in advance, so the run is deterministic. A real model would choose each reply.

```python
import inspect
import json
from dataclasses import dataclass, field
from typing import Callable, Dict

# Three plain Python functions the kernel can expose to the model.
def greet(name: str) -> str:
    """Greets the user by name."""
    return f"Hello, {name}!"

def calculate_sum(a: int, b: int) -> int:
    """Adds two integers."""
    return a + b

def save_to_file(data: dict, filename: str) -> str:
    """Saves data as JSON to a file (simulated: nothing is written to disk)."""
    return f"Saved {json.dumps(data)} to {filename}"

# Step 1 of the loop: turn a Python signature into the JSON schema the model reads.
PY_TO_JSON = {str: "string", int: "integer", float: "number", bool: "boolean", dict: "object", list: "array"}

def to_schema(fn: Callable) -> dict:
    props, required = {}, []
    for name, p in inspect.signature(fn).parameters.items():
        props[name] = {"type": PY_TO_JSON[p.annotation]}
        if p.default is inspect.Parameter.empty:
            required.append(name)
    return {"name": fn.__name__, "description": inspect.getdoc(fn),
            "parameters": {"type": "object", "properties": props, "required": required}}

@dataclass
class Kernel:
    plugins: Dict[str, Callable] = field(default_factory=dict)
    max_iterations: int = 5

    def add(self, fn: Callable) -> None:
        self.plugins[fn.__name__] = fn

    def schemas(self) -> list:
        return [to_schema(fn) for fn in self.plugins.values()]

    def invoke(self, name: str, args: dict):
        fn = self.plugins.get(name)
        if fn is None:
            raise KeyError(f"unknown function {name!r}")
        sig = inspect.signature(fn)
        try:
            sig.bind(**args)                       # wrong or missing argument names
        except TypeError as e:
            raise ValueError(f"bad arguments for {name}: {e}")
        for pname, value in args.items():          # wrong argument types
            want = sig.parameters[pname].annotation
            if not isinstance(value, want):
                raise ValueError(f"{pname} must be {want.__name__}, got {type(value).__name__}")
        return fn(**args)

def scripted_model(replies):
    """Stand-in for an LLM: returns one scripted reply per call and logs what it was sent."""
    sent = []
    def model(history, schemas):
        sent.append(len(json.dumps(history)) + len(json.dumps(schemas)))  # characters, not tokens
        return replies[len(sent) - 1]
    model.sent = sent
    return model

def run(kernel: Kernel, model, goal: str):
    history = [{"role": "user", "content": goal}]
    for step in range(1, kernel.max_iterations + 1):
        reply = model(history, kernel.schemas())
        if reply["type"] == "text":                # the model answers instead of calling
            history.append({"role": "assistant", "content": reply["content"]})
            print(f"step {step}: final answer: {reply['content']}")
            return reply["content"]
        history.append({"role": "assistant", "tool_call": reply})
        try:
            content = str(kernel.invoke(reply["name"], reply["args"]))
        except (KeyError, ValueError) as e:
            content = f"error: {e}"                # errors go back to the model, not to the caller
        history.append({"role": "tool", "name": reply["name"], "content": content})
        print(f"step {step}: {reply['name']}({reply['args']}) -> {content}")
    print(f"gave up after {kernel.max_iterations} model calls")
    return None

# Keyword planner: a function is chosen only if its name appears in the goal.
def keyword_planner(goal: str, fns) -> list:
    return [fn.__name__ for fn in fns if fn.__name__ in goal.lower()]

goal = "Greet Alice, add 5 and 7, then save the result to result.json"
print("keyword planner picks:", keyword_planner(goal, [greet, calculate_sum, save_to_file]))

print("\nschema the model receives for calculate_sum:")
print(json.dumps(to_schema(calculate_sum), indent=2))

kernel = Kernel()
for fn in (greet, calculate_sum, save_to_file):
    kernel.add(fn)

model = scripted_model([
    {"type": "call", "name": "greet", "args": {"name": "Alice"}},
    {"type": "call", "name": "calculate_sum", "args": {"a": "5", "b": 7}},   # a bad call on purpose
    {"type": "call", "name": "calculate_sum", "args": {"a": 5, "b": 7}},     # the retry
    {"type": "call", "name": "save_to_file", "args": {"data": {"sum": 12}, "filename": "result.json"}},
    {"type": "text", "content": "Greeted Alice; the sum is 12 and it is saved to result.json."},
])
print("\nrun 1: a model that recovers from one bad call")
run(kernel, model, goal)
print("characters sent per model call:", model.sent)

print("\nrun 2: a model that never stops calling")
looping = scripted_model([{"type": "call", "name": "greet", "args": {"name": "Alice"}}] * 5)
run(kernel, looping, goal)

# Cost of the loop: characters sent per run length
import contextlib
import io

schemas = [to_schema(fn) for fn in (greet, calculate_sum, save_to_file)]
print("schema characters for three functions:", len(json.dumps(schemas)))

def characters_sent(n_calls):
    kernel = Kernel(max_iterations=200)
    for fn in (greet, calculate_sum, save_to_file):
        kernel.add(fn)
    replies = [{"type": "call", "name": "calculate_sum", "args": {"a": i, "b": 1}} for i in range(n_calls - 1)]
    replies.append({"type": "text", "content": "done"})
    model = scripted_model(replies)
    with contextlib.redirect_stdout(io.StringIO()):   # hide the per-step trace
        run(kernel, model, "add numbers")
    return model.sent

for n in (5, 10, 20, 40):
    sent = characters_sent(n)
    print(f"{n:2d} calls: last call sent {sent[-1]:5d} characters, total {sum(sent):6d}")
```

## Reading the run

The schema comes from `to_schema`, which reads each parameter's annotation and default. `Kernel.invoke` checks a call in two stages. `sig.bind` catches wrong or missing argument names. The `isinstance` loop catches wrong types. A failed check does not crash the run. The error becomes the text of a tool message, such as `error: a must be int, got str`, and the model sees it on its next call. In run 1 the model retries with integers at step 3. The documentation makes the same point: error messages should say what went wrong and how to fix it, so the model can self-correct [2].

Run 1 has five model calls, one per step, and recovers from one bad call. Its trace is shown below. Run 2 shows the guard against endless calling: `max_iterations` ends a run after five calls, even though the model never answered. The `save_to_file` function here only formats a string; nothing is written to disk.

![Five boxes for the five model calls of run 1: greet succeeds, calculate_sum with a string argument fails in red, the retry succeeds, save_to_file succeeds, and the model gives the final answer](diagrams/45.2-run-trace.svg "Run 1: one error, one retry, and a final answer after five model calls.")

## What the loop costs

Every model call re-sends the whole history and all schemas. The schemas for the three functions above take 610 characters. The run-1 calls sent 704, 865, 1,059, 1,224 and 1,451 characters, each larger than the last, because each step adds a request and a result. Characters are a proxy here: providers bill in tokens, and this lesson does not count tokens.

The last four lines of the output measure the cost. They run the same loop with 5, 10, 20 and 40 model calls and add up everything sent in each run.

![Bar chart of total characters sent for runs of 5, 10, 20 and 40 model calls: 4,910; 13,920; 44,340; 154,980](diagrams/45.2-history-growth.svg "Total characters sent to the model for four run lengths, from the script above.")

Doubling the calls from 20 to 40 multiplies the total by about 3.5, and the ratio approaches 4 for long runs. The reason is that call k re-sends everything before it, so the total is a sum that grows like the square of the number of calls. The fixed schema cost is paid on every call, which keeps the ratio nearer 2 for short runs. These numbers come from a synthetic run in which each result is short; real tool results are often much longer, so real costs are higher.

## Common traps

> [!TRAP] Keyword matching is not planning. `'save_to_file' in goal.lower()` fails on "save the result to a file". A goal that names a function by its description is missed entirely.

> [!TRAP] The schema is paid for on every call. Each description and parameter is sent again in every request. Keep descriptions short and add them only when the model misuses a function [2].

> [!TRAP] String parameters force guessing. A parameter typed `str` makes the model invent a format. Prefer `int`, enumerations or small objects where the value has a fixed shape [2].

> [!TRAP] A loop with no limit can run forever. Without `max_iterations`, a model that keeps calling never returns. Run 2 stops after five calls.

> [!TRAP] The model decides when your code runs. A function that deletes files or charges a card runs whenever the model calls it. Check permissions and arguments inside the function, not only in the prompt.

## Summary

- Semantic Kernel's Stepwise and Handlebars planners were deprecated and removed; function calling is now the basis for planning [1].
- The loop serialises functions as JSON schemas, sends them with the history, runs each requested call, appends the result, and repeats until the model answers in text or a limit is reached [2].
- A signature gives the schema's name, description, typed parameters and required list. Return types are not sent.
- Validate arguments in the kernel, and return errors as text so the model can retry.
- Each call re-sends the history, so total cost grows faster than the number of calls.

## Quiz time

### Question 1: Prediction
What does `keyword_planner("Save the sum to a file", [save_to_file])` return?

<details><summary>Show solution</summary>

It returns `[]`. The test is `'save_to_file' in goal.lower()`. The goal contains the words "save", "sum" and "file", but not the exact string `save_to_file`, so nothing is selected.

</details>

### Question 2: Calculation
For `def scale(x: float, factor: float = 2.0, label: str = "") -> float`, what is the `required` list in its schema?

<details><summary>Show solution</summary>

It is `["x"]`. Only `x` has no default. The return annotation `-> float` does not appear in the schema.

</details>

### Question 3: Bug-spotting
A colleague adds `def double(x: int) -> int` and expects `invoke("double", {"x": True})` to be rejected. It is accepted and returns 2. Why, and what would fix it?

<details><summary>Show solution</summary>

`bool` is a subclass of `int`, so `isinstance(True, int)` is `True`, and the type check passes. One fix is `type(value) is want`, which rejects subclasses as well. Another is to test for `bool` explicitly and reject it. Either way, add a test with a boolean argument.

</details>

### Question 4: Explanation
Why does `Kernel.invoke` return an error string to the model instead of raising the exception to the caller?

<details><summary>Show solution</summary>

The error becomes part of the next model input. In run 1 the model reads `a must be int, got str` and retries with a correct argument. If the exception ended the run, the model could not recover. The cost is that a model can now keep failing, which is why the iteration limit is still needed.

</details>

### Question 5: Explanation
For 10 calls the total is 13,920 characters, and for 20 calls it is 44,340. Why is the ratio 3.2 rather than 2 or 4?

<details><summary>Show solution</summary>

Work out the two terms. The schema and fixed prompt cost is paid once per call, which grows linearly and gives a ratio of 2. The history that is re-sent grows with the call index, which gives a sum that grows like the square of the number of calls, a ratio of 4. At these sizes the two terms are mixed, so the ratio lies between 2 and 4.

</details>
