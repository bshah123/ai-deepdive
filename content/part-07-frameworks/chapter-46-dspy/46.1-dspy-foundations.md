In this lesson you will write a small DSPy-style program: declare what each step takes and returns as a *signature*, call it as a *module*, and see the exact text the model receives. You will also see why DSPy treats the prompt as something a program can optimize.

**You need:** Python classes and `__call__` (Lessons 10.1 and 11.1). No API key and no model weights: the model here is a scripted stand-in, and the code uses only the standard library.

## The problem a prompt string creates

A prompt is a string. A pipeline built from hand-written strings has three fragile parts. The wording is tuned by trial and error. The output format is requested, not enforced. And changing the task means editing the string. Khattab et al. (2023) describe existing pipelines as relying on hard-coded "prompt templates", i.e. lengthy strings discovered via trial and error (arXiv:2310.03714, abstract).

DSPy (the project's README expands the name as "Declarative Self-improving Python") replaces the prompt with three parts: signatures, modules and teleprompters (optimizers). This lesson covers signatures and modules. Lesson 46.3 covers the optimizers.

**Caution on versions.** The 2023 paper describes the first design. The current library has changed its API, and its README links a migration guide for breaking changes. The code below re-implements the core ideas in about 120 lines so you can see the mechanism. It is not the library. Check the current documentation before copying any DSPy call.

## Signatures: an interface, not a prompt

![A signature is rendered into a prompt, the model returns text, and the output fields are parsed back out](diagrams/46.1-signature-pipeline.svg "The programmer writes the signature. The framework renders the prompt and parses the reply.")

A signature such as `question -> answer` declares one input field, `question`, and one output field, `answer`. The paper's shorthand is `dspy.Predict("question -> answer")`, and it says DSPy "will parse this notation and expand the field names into meaningful instructions for the LM" (Khattab et al., 2023, Section 3.1).

Take the question "What is the capital of France?" by hand. The renderer produces four lines: an instruction, a blank line, the input line `Question: What is the capital of France?`, and the marker `Output fields: answer`. The model continues the text with `Answer: Paris`. The parser splits each line at its colon, lower-cases the names, and checks that every output field is present. The caller then reads `pred.answer`, which is `'Paris'`.

Every step is a plain function, so you can run the whole chain offline:

```python
import re

class Signature:
    """Input and output field names, plus an optional instruction."""
    def __init__(self, spec, instructions=None):
        left, right = (part.strip() for part in spec.split("->"))
        self.inputs = [f.strip() for f in left.split(",")]
        self.outputs = [f.strip() for f in right.split(",")]
        self.instructions = instructions or (
            f"Given {', '.join(self.inputs)}, produce {', '.join(self.outputs)}.")

    def with_first_output(self, name):
        """Return a new signature with one extra output field placed first."""
        spec = f"{', '.join(self.inputs)} -> {', '.join([name] + self.outputs)}"
        return Signature(spec, self.instructions)

    def render(self, example, demos=()):
        """Build the prompt text: instruction, demonstrations, then the new input."""
        lines = [self.instructions, ""]
        for demo in demos:
            for f in self.inputs:
                lines.append(f"{f.capitalize()}: {demo[f]}")
            lines.append(f"Output fields: {', '.join(self.outputs)}")
            for f in self.outputs:
                lines.append(f"{f.capitalize()}: {demo[f]}")
            lines.append("")
        for f in self.inputs:
            lines.append(f"{f.capitalize()}: {example[f]}")
        lines.append(f"Output fields: {', '.join(self.outputs)}")
        return "\n".join(lines)

def parse_fields(text, outputs):
    """Pull 'name: value' lines out of a completion; fail loudly if a field is missing."""
    found = {k.lower(): v.strip() for k, v in re.findall(r"^(\w+):(.*)$", text, re.M)}
    missing = [f for f in outputs if f not in found]
    if missing:
        raise ValueError(f"missing fields {missing} in completion: {text!r}")
    return {f: found[f] for f in outputs}

class Prediction(dict):
    """Output fields, readable as attributes: pred.answer."""
    def __getattr__(self, name):
        try:
            return self[name]
        except KeyError:
            raise AttributeError(name)

class Predict:
    def __init__(self, signature, lm):
        self.signature = Signature(signature) if isinstance(signature, str) else signature
        self.lm = lm
        self.demos = []   # the learnable parameters: an optimizer fills these in later

    def __call__(self, **example):
        prompt = self.signature.render(example, self.demos)
        completion = self.lm(prompt)
        return Prediction(parse_fields(completion, self.signature.outputs))

class ChainOfThought(Predict):
    def __init__(self, signature, lm):
        base = Signature(signature) if isinstance(signature, str) else signature
        super().__init__(base.with_first_output("reasoning"), lm)

class ScriptedLM:
    """Stand-in for a real model: returns scripted completions. No network, no weights."""
    def __init__(self, script):
        self.script = script
        self.calls = 0

    def __call__(self, prompt):
        self.calls += 1
        outputs = tuple(re.findall(r"^Output fields: (.*)$", prompt, re.M)[-1].split(", "))
        question = re.findall(r"^Question: (.*)$", prompt, re.M)[-1]
        return self.script[(outputs, question)]

class MultiHopQA:
    """A program: a search step feeds a reasoning step. Plain Python, no framework magic."""
    def __init__(self, lm, corpus):
        self.search = Predict("question -> search_query", lm)
        self.answer = ChainOfThought("question, passage -> answer", lm)
        self.corpus = corpus   # search query -> passage (a toy retriever)

    def __call__(self, question):
        query = self.search(question=question).search_query
        return self.answer(question=question, passage=self.corpus[query])

lm = ScriptedLM({
    (("answer",), "What is the capital of France?"): "Answer: Paris",
    (("answer",), "Who wrote Pride and Prejudice?"): "Answer: Jane Austen",
    (("search_query",), "Which river flows through Cairo?"): "Search_query: Cairo river",
    (("reasoning", "answer"), "Which river flows through Cairo?"):
        "Reasoning: The river through Cairo is the Nile.\nAnswer: Nile",
})

qa = Predict("question -> answer", lm)
print(qa(question="What is the capital of France?").answer)
print(qa.signature.render({"question": "What is the capital of France?"}))
print("--- ChainOfThought: same signature, one extra output field")
cot = ChainOfThought("question -> answer", lm)
print(cot.signature.outputs)
r = cot(question="Which river flows through Cairo?")
print(r.reasoning, "|", r.answer)
print("--- two-step program")
pipe = MultiHopQA(lm, corpus={"Cairo river": "The Nile flows through Cairo."})
before = lm.calls
print(pipe(question="Which river flows through Cairo?").answer)
print("LM calls for one pipeline call:", lm.calls - before)
print("--- a missing field fails loudly")
try:
    parse_fields("The answer is Paris.", ["answer"])
except ValueError as e:
    print("ValueError:", e)
print("--- prompt size vs demonstrations (whitespace words; our renderer)")
trainset = [
    {"question": "What is the capital of France?", "answer": "Paris"},
    {"question": "Which river flows through Cairo?", "answer": "Nile"},
    {"question": "Who wrote Pride and Prejudice?", "answer": "Jane Austen"},
    {"question": "What is 7 times 6?", "answer": "42"},
]
new = {"question": "What is the capital of Japan?"}
for k in [0, 1, 2, 4]:
    p = Predict("question -> answer", lm)
    p.demos = trainset[:k]
    print(f"Predict, demos={k}: words={len(p.signature.render(new, p.demos).split())}")
cot_text = ChainOfThought("question -> answer", lm).signature.render(new)
print(f"ChainOfThought, demos=0: words={len(cot_text.split())}")
```

## Predict: a callable with parameters

![Predict holds a signature, a language model callable and a list of demonstrations; calling it renders, calls the model once and parses](diagrams/46.1-predict-module.svg "Predict is the core building block. Its demos list starts empty.")

The paper says that "like layers in PyTorch, the instantiated module behaves as a callable function" (Section 3.2). Our `Predict` works the same way. It has two fixed parts, the signature and the model, and one learnable part, `demos`. In the code, `demos` is empty at first, so the first prompt has no examples. An optimizer can later fill it with worked input-output pairs. That is the sense in which a DSPy module has parameters: in this stand-in, the demonstrations, not the model weights. Lesson 46.3 shows that the full library's optimizers also rewrite each module's instruction.

## ChainOfThought: change the signature, not the call

![Predict maps question to answer; ChainOfThought inserts a reasoning field between them](diagrams/46.1-chain-of-thought.svg "ChainOfThought adds one output field. The caller's code does not change.")

The paper states that changing `Predict` to `ChainOfThought` "leads to a system that thinks step by step before committing to its output field" (Section 3.2). The mechanism is small. The module prepends a `reasoning` output field to the signature, then calls the same predictor. In the output above, `cot.signature.outputs` is `['reasoning', 'answer']`, and the caller still reads `.answer`.

Treat "thinks step by step" with care. The model writes the rationale as ordinary tokens before the answer. Whether that improves accuracy is an empirical question for each task and model (my own reasoning; the chain-of-thought result itself is a separate paper, which this lesson does not verify).

## Programs are ordinary Python

![A question goes to a Predict module (LM call 1), then to a corpus lookup with no model call, then to a ChainOfThought module (LM call 2) that returns the answer](diagrams/46.1-program-graph.svg "A two-step program. The lookup is plain code, so it costs no model call.")

`MultiHopQA` declares its modules in `__init__` and calls them in `__call__`. This follows the paper's description of a define-by-run interface "inspired directly by PyTorch and Chainer" (Section 3.2). The program makes two model calls per question, and the printed count of 2 confirms it. Adding a stage adds a call, and the latency and cost of the calls add up.

## What it costs: prompt size grows with demonstrations

![Bar chart of whitespace words in the rendered prompt: 14 with no demonstrations, 26 with one, 37 with two, 60 with four; ChainOfThought with none is 15](diagrams/46.1-prompt-size.svg "Measured with the renderer above. The shape holds for any renderer that adds the demonstrations to the prompt.")

The measured counts come from the code above. With zero demonstrations the prompt has 14 words. Going from 0 to 4 demonstrations adds 46 words, which is 11.5 words per demonstration on average. The `ChainOfThought` prompt is one word longer because its output list now names `reasoning`.

These are whitespace words in our renderer, not tokens and not the prompt the real library sends. To estimate cost, count tokens with your model's tokenizer on the real prompt.

## What the paper claims about optimization (not reproduced here)

The abstract reports that, "within minutes of compiling", a few lines of DSPy let GPT-3.5 and llama2-13b-chat "self-bootstrap pipelines that outperform standard few-shot prompting (generally by over 25% and 65%, respectively)" (Khattab et al., 2023, abstract). We have not run these experiments. The mechanism is that a teleprompter runs the program on training examples, keeps the traces that pass a metric, and stores them as demonstrations, which is exactly the `demos` list above. Lesson 46.3 walks through that process.

## Common traps

> [!TRAP]
> The signature is not decoration. Renaming `question` to `q` changes the prompt text and every scripted key in the stand-in model.

> [!TRAP]
> A reply without the expected field raises an error. Do not replace the check with a loose split that returns whatever text it finds. The check is what catches a model that ignores the output format, such as one that answers "The answer is Paris." with no field label.

> [!TRAP]
> Calls multiply. A program with two modules makes two model calls per input, so a 1,000-question evaluation makes 2,000.

> [!TRAP]
> Demonstrations are parameters that lengthen every call. Adding demonstrations can help accuracy and always raises prompt size.

> [!TRAP]
> The scripted model in this lesson tells you nothing about accuracy. Its answers were written by hand, so any score it produces measures the script. Do not compare it with any paper number.

## Summary

- A DSPy signature such as `question -> answer` declares input and output fields. The framework renders the prompt and parses the reply.
- A module such as `Predict` is callable and holds parameters, chiefly a `demos` list that an optimizer can fill.
- `ChainOfThought` adds a `reasoning` output field to the signature. The caller's code stays the same.
- A program is ordinary Python that calls modules. Each model-calling module adds one call per input.
- Demonstrations raise prompt size, and the per-demonstration cost is measurable with your model's tokenizer.

### Question 1: Calculation
Using the measured counts (14 words with zero demonstrations, 60 with four), what is the average number of words each demonstration adds?

<details><summary>Show Solution</summary>

$(60 - 14) / 4 = 11.5$ words per demonstration. The measured counts for one and two demonstrations (26 and 37) are consistent with this, since each step adds 11 or 12 words.
</details>

### Question 2: Prediction
`MultiHopQA` makes 2 model calls per question. If the corpus lookup were replaced by a second `Predict` module, how many model calls would 10 questions make?

<details><summary>Show Solution</summary>

Three calls per question, so 30 in total. The lookup in `MultiHopQA` is plain code, so it costs nothing; a `Predict` module would be a model call.
</details>

### Question 3: Bug-spotting
What happens when this line runs, given the `Predict` class above?

```text
qa = Predict("question, answer", lm)
```

<details><summary>Show Solution</summary>

The string has no `->`. `Signature.__init__` splits on `->`, gets a one-element list, and fails with `ValueError: not enough values to unpack (expected 2, got 1)`. The fix is `Predict("question -> answer", lm)`. The arrow separates inputs from outputs, so a signature without one is not a valid interface.
</details>

### Question 4: Explanation
Why does switching from `Predict` to `ChainOfThought` leave the calling code unchanged?

<details><summary>Show Solution</summary>

`ChainOfThought` changes only the signature. It adds `reasoning` to the output fields and calls the same parse step. The caller passes the same inputs and reads the same `.answer` attribute.
</details>

### Question 5: Prediction
The `ScriptedLM` is keyed on `(output fields, question)`. What happens if you call `ChainOfThought("question -> answer", lm)` on "Who wrote Pride and Prejudice?"

<details><summary>Show Solution</summary>

The key is `(('reasoning', 'answer'), 'Who wrote Pride and Prejudice?')`, and the script has only the `('answer',)` key for that question. The lookup raises `KeyError`. This is a property of the stand-in, not of DSPy. A real model would return some text for any prompt.
</details>
