In this lesson you will explain what a DSPy teleprompter changes in a program, trace how BootstrapFewShot and MIPROv2 collect demonstrations and search over candidates, and measure why the score of a winner chosen on a small minibatch is too optimistic.

**You need:** a DSPy `Signature` and `Module` (Lesson 46.2). Python only; both code blocks run in the browser.

## The problem

A DSPy program is a graph of modules. Each `Predict` module has two things a person normally writes by hand: an **instruction** (a sentence describing the task) and **demonstrations**, or demos (worked input–output examples placed in the prompt). Changing either one changes accuracy, and the best choice depends on the model and the task. Testing variants by hand does not scale. A **teleprompter** (DSPy's name for an optimizer) automates the search, given a training set and a **metric**, which is a function that scores one output.

## The optimizer rewrites state, not code

![A program with empty instruction and demo slots goes into an optimizer with a trainset and a metric, and comes out with the slots filled; the code is unchanged](diagrams/46.3-optimizer-compiles.svg "The optimizer writes state into the program. The forward code is the same before and after.")

The DSPy paper calls this compiling. The compiler takes the program, a few training inputs with optional labels, and a validation metric, and returns a program whose module state is better (Khattab et al., 2023, §4). The paper's first stage generates candidate values for each module's parameters (instructions, field descriptions, demonstrations). The next stage chooses among them (§4). In that version of DSPy the paper focuses on demonstrations, and finds that rejection-sampling-like approaches can bootstrap effective multi-stage systems.

## BootstrapFewShot: keep the traces that pass

BootstrapFewShot is the simplest teleprompter in DSPy (Khattab et al., 2023, §4 and App. E.1). A **teacher** program runs on training inputs. By default the teacher is the zero-shot version of the program being compiled. Every module call is recorded as a **trace** of its inputs and outputs. The metric decides which traces become demos. In the DSPy source (`dspy/teleprompt/bootstrap.py`, read 2026-11-23), a trace is accepted when the metric is truthy, and the loop stops after `max_bootstrapped_demos` accepted traces (default 4).

![Teacher verdicts for training examples 0 to 6: examples 0, 1, 2 and 6 pass and become demos; examples 3, 4 and 5 fail and are discarded; the loop stops at the fourth pass](diagrams/46.3-bootstrap-loop.svg "Pass or fail per training example. Four passes end the loop.")

The stub below replaces the LLM with a hash. A "teacher" passes each training example with probability 0.80. Hashing the example index instead of drawing random numbers makes the output identical on every machine.

```python
import hashlib

def u(*key):
    """Deterministic pseudo-random number in [0, 1) from a key (stdlib only)."""
    digest = hashlib.sha256(":".join(map(str, key)).encode()).digest()
    return int.from_bytes(digest[:8], "big") / 2**64

# Stub teacher: passes training example i with probability 0.80.
# With an exact-match metric, "passes" means the teacher's answer is correct.
verdicts = [u("teacher", i) < 0.80 for i in range(200)]

# BootstrapFewShot's loop: scan in order, keep passing traces, stop at 4 demos.
demos, scanned = [], []
for i, ok in enumerate(verdicts):
    scanned.append(i)
    if ok:
        demos.append(i)
    if len(demos) == 4:
        break

print("verdicts, examples 0-6:", ["pass" if v else "fail" for v in verdicts[:7]])
print("scanned", len(scanned), "examples; demos kept from examples", demos)
print("rejected traces:", len(scanned) - len(demos))
```

```output
verdicts, examples 0-6: ['pass', 'pass', 'pass', 'fail', 'fail', 'fail', 'pass']
scanned 7 examples; demos kept from examples [0, 1, 2, 6]
rejected traces: 3
```

At a pass rate of 0.80, four passes take about $4 / 0.80 = 5$ scans on average. This run took 7, which is ordinary variation for one run. The cap of four demos is the reason the loop stops early.

## Worked example by hand: a minibatch is noisy

Before the search, here is the statistics that matters. Take a minibatch of 5 validation items. Program X gets the flags $[1, 0, 1, 1, 1]$, so its score is $4/5 = 0.8$. Program Y gets $[1, 1, 0, 0, 1]$, so its score is $3/5 = 0.6$. Suppose both have a true accuracy near 0.7. The standard deviation of a $n$-item score is $\sqrt{p(1-p)/n}$, which gives $\sqrt{0.7 \cdot 0.3 / 5} \approx 0.205$. That is larger than the 0.2 gap between X and Y, so five items cannot separate them. With 35 items the standard deviation falls to $\sqrt{0.21 / 35} \approx 0.0775$. The code below reproduces both numbers.

## MIPROv2: search over instructions and demos

MIPROv2 (Opsahl-Ong et al., 2024) builds on this loop. In the DSPy source (`dspy/teleprompt/mipro_optimizer_v2.py`, read 2026-11-23), `compile()` has three stages: bootstrap sets of demos with the BootstrapFewShot-style loop; propose several instructions from the program code, a summary of the data and the demos; then search over combinations, where each trial picks one instruction and one demo set per module. The search uses Optuna's Tree-structured Parzen Estimator (TPE) sampler, and trials score on minibatches, with periodic full evaluations of the current best. The paper's abstract describes the same factorization, "free-form instructions and few-shot demonstrations of every module," and reports gains over baseline optimizers on five of seven programs with an open 8B model, "by as high as 13% accuracy." The abstract does not say whether that 13% is absolute or relative, so treat it as the authors' claim.

![Three boxes in a row: bootstrap demos, propose instructions, search combinations; below, a 3 by 4 grid of 12 candidate programs](diagrams/46.3-mipro-stages.svg "The three stages of a MIPROv2-style optimizer, and the search space they define.")

Our stub does not reproduce MIPROv2's search. It has 12 candidates (think 3 instructions by 4 demo sets) and scores all of them on one 35-item minibatch, so there is no TPE and no surrogate. That is deliberate: it isolates one effect, noise in the minibatch score. Each candidate has a hidden true accuracy from 0.62 to 0.84, set by a fixed shuffle. **These accuracies are assumptions, not measurements.** The numbers show the mechanism. They say nothing about MIPROv2's performance on a real task.

```python
import hashlib

def u(*key):
    """Deterministic pseudo-random number in [0, 1) from a key (stdlib only)."""
    digest = hashlib.sha256(":".join(map(str, key)).encode()).digest()
    return int.from_bytes(digest[:8], "big") / 2**64

# Stub LM: 12 candidate programs (think 3 instructions x 4 demo sets).
# Hidden true accuracies are 0.62, 0.64, ..., 0.84, assigned by a fixed shuffle.
CANDS = list(range(12))
rank = sorted(CANDS, key=lambda c: u("rank", c))
TRUE = {c: round(0.62 + 0.02 * rank.index(c), 2) for c in CANDS}

def correct(c, i):
    """Program c answers example i correctly with probability TRUE[c]."""
    return u("ex", c, i) < TRUE[c]

VAL, CONFIRM, TEST = range(200, 300), range(600, 700), range(300, 600)
VAL_ACC = {c: sum(correct(c, i) for i in VAL) / 100 for c in CANDS}
CONF_ACC = {c: sum(correct(c, i) for i in CONFIRM) / 100 for c in CANDS}
TEST_ACC = {c: sum(correct(c, i) for i in TEST) / 300 for c in CANDS}

p = 0.7
print("sd of a 5-item score at p=0.7:", round((p * (1 - p) / 5) ** 0.5, 4))
print("sd of a 35-item score at p=0.7:", round((p * (1 - p) / 35) ** 0.5, 4))

def run(rep):
    """One optimizer run: score all 12 on a 35-item minibatch, then select three ways."""
    mb = sorted(VAL, key=lambda i: u("mb", rep, i))[:35]
    mb_score = {c: sum(correct(c, i) for i in mb) / 35 for c in CANDS}
    a = max(CANDS, key=lambda c: (mb_score[c], -c))                    # rule A: best minibatch
    top3 = sorted(CANDS, key=lambda c: (-mb_score[c], c))[:3]
    b = max(top3, key=lambda c: (CONF_ACC[c], -c))                     # rule B: top 3, then confirm set
    b_over = max(top3, key=lambda c: (VAL_ACC[c], -c))                 # rule B': top 3, then val (overlaps minibatch)
    return mb_score, a, b, b_over

mb0, a0, b0, _ = run(0)
print("run 0: candidate, true, minibatch, val, test")
for c in sorted(CANDS, key=lambda c: -mb0[c]):
    print(" ", c, TRUE[c], round(mb0[c], 3), round(VAL_ACC[c], 3), round(TEST_ACC[c], 3))
print("run 0 winner A:", a0, "| winner B:", b0)

REPS = 500
oracle = max(TEST_ACC.values())
average = sum(TEST_ACC.values()) / 12
A, B, BO, OPT, hits = [], [], [], [], 0
for r in range(REPS):
    mb_score, a, b, bo = run(r)
    A.append(TEST_ACC[a]); B.append(TEST_ACC[b]); BO.append(TEST_ACC[bo])
    OPT.append(mb_score[a] - TEST_ACC[a])
    hits += TEST_ACC[a] == oracle
mean = lambda xs: sum(xs) / len(xs)
diff = [b - a for a, b in zip(A, B)]
se_diff = (sum((d - mean(diff)) ** 2 for d in diff) / (REPS - 1) / REPS) ** 0.5

print("over", REPS, "runs:")
print("  average candidate, test:              ", round(average, 3))
print("  rule A, best minibatch, test:         ", round(mean(A), 3))
print("  rule B, top 3 then confirm set, test: ", round(mean(B), 3))
print("  rule B', top 3 then val (overlaps), test:", round(mean(BO), 3))
print("  oracle (best test among 12):          ", round(oracle, 3))
print("  rule B minus rule A, paired SE:       ", round(mean(diff), 3), "+/-", round(se_diff, 3))
print("  rule A minibatch minus its test:      ", round(mean(OPT), 3))
print("  runs where rule A picks the oracle:   ", round(hits / REPS, 3))
```

## Run 0 and the winner's curse

The scatter plots run 0, the first run, which was not picked for the picture. The minibatch score and test accuracy are only loosely related. Candidate 3 has a true accuracy of 0.72 but scored 0.571 on its minibatch. Rule A picked candidate 9, which scored 0.857 on the minibatch and 0.837 on test. Rule B picked candidate 6, which scored 0.829 on the minibatch and also 0.837 on test. Two rules can pick different programs, and in this run they tie on test.

![Scatter of 12 candidates in run 0: x is minibatch score, y is test accuracy; points are spread by about 0.08, with the rule A and rule B winners highlighted](diagrams/46.3-minibatch-scatter.svg "Minibatch scores are noisy. The highest minibatch score is not reliably the highest test score.")

Across 500 runs the pattern is clear. Rule A (pick the best minibatch score) reaches mean test accuracy 0.812. Rule B (take the top 3 by minibatch, then compare them on a separate 100-item confirmation set) reaches 0.835. The average candidate reaches 0.741, and the oracle (the best of the 12 on test, which no real optimizer can see) reaches 0.837. Rule A's minibatch score overstates its own test accuracy by 0.057 on average. The gap between rule B and rule A is 0.023, with a paired standard error of 0.002. Rule A picks the oracle in 63% of runs. Using the overlapping validation set for rule B' gives the same mean, 0.835, so the minibatch overlap does not drive the result.

![Bars of mean test accuracy over 500 runs: average candidate 0.741, rule A 0.812, rule B 0.835, oracle 0.837; bars start at zero](diagrams/46.3-selection-rules.svg "The best minibatch is a noisy pick. A second, independent check recovers most of the gap.")

Why does this happen? The winner is the maximum of 12 noisy scores, and the maximum of noisy numbers is biased upward. That is the winner's curse, a selection effect and not a bug. The fix is a set that the selection never saw. Rule B does that, and the 300-item test set reports the result.

The result also rests on an assumption. The stub makes errors independent across candidates. Real programs make correlated errors on the same hard examples, and correlated errors make the minibatch comparison less noisy, which should shrink the optimism. We did not test that here.

## Common traps

> [!TRAP]
> **The metric is a callable, not a string.** The old version of this lesson passed `metric="accuracy"`. BootstrapFewShot calls `metric(example, prediction, trace)` (DSPy source, `bootstrap.py`). A string is not callable and fails with a `TypeError` when the metric is first called. The DSPy paper's own example passes `dspy.evaluate.answer_exact_match` (Khattab et al., 2023, §3.3).

> [!TRAP]
> **`metric_threshold=0` with a boolean metric accepts every trace.** When a threshold is set, the source tests `metric_val >= self.metric_threshold`, and `False >= 0` is `True`. Leave `metric_threshold` unset when the metric returns a boolean. This follows from the source as read; check the line in the version you install.

> [!TRAP]
> **Do not report the score the optimizer selected on.** The winner's minibatch or validation score is optimistic, by 0.057 on average over the 500 simulated runs (0.02 in run 0). Keep a test set that no bootstrapping or selection step touches.

> [!TRAP]
> **Demos come from the training set, so do not evaluate on them.** A demo that is also a test item leaks its answer into the prompt. The score then rises for a reason that is not generalization.

> [!TRAP]
> **MIPROv2's default validation size depends on the training set.** On main, read 2026-11-23, the code by my reading takes 80% of the training set for validation, capped at 1000. Pass `valset` explicitly and check the value in the version you install.

## Summary

- A teleprompter fills module state (instructions and demos) from a training set and a metric. The program's code does not change.
- BootstrapFewShot keeps the teacher's traces that pass the metric, up to four by default.
- MIPROv2 adds instruction proposal and a search over instruction and demo-set combinations, scored on minibatches.
- A winner chosen on a small minibatch overstates its accuracy. In our simulation the overstatement is 0.057 on average.
- Hold out a test set that selection never sees.

## Quiz time

### Question 1: Calculation

A program answers 14 of 20 minibatch items correctly. What is its minibatch score? If its true accuracy is 0.7, what is the standard deviation of the score?

<details><summary>Show Solution</summary>

The score is $14/20 = 0.70$. The standard deviation is $\sqrt{0.7 \cdot 0.3 / 20} = \sqrt{0.0105} \approx 0.1025$. A 20-item minibatch is therefore uncertain by about ten points.

</details>

### Question 2: Prediction

With `metric_threshold=0` and a metric that returns `True` or `False`, which traces does BootstrapFewShot accept?

<details><summary>Show Solution</summary>

All of them. The source tests `metric_val >= 0`, and both `True >= 0` and `False >= 0` are true in Python, because `False` is 0. The threshold does nothing, so every trace becomes a candidate demo.

</details>

### Question 3: Find the bug

A colleague writes `BootstrapFewShot(metric="accuracy", max_bootstrapped_demos=4)` and says the optimizer runs. What goes wrong, and what should the metric be?

<details><summary>Show Solution</summary>

The metric is a string, not a function. The optimizer calls `metric(example, prediction, trace)` on each trace, so the call fails with a `TypeError`. The metric should be a Python function that takes those three arguments and returns `True` or `False` (or a score with a threshold). Compare the predicted answer with the reference answer in the example.

</details>

### Question 4: Explain

Rule A and rule B both score candidates on training data, yet rule B's test accuracy is higher. Why?

<details><summary>Show Solution</summary>

Rule A chooses by the highest minibatch score, which is the maximum of 12 noisy estimates, so it selects candidates that were lucky on those 35 items. Rule B re-scores the top three on a separate 100-item set that the selection did not use, which removes most of that luck. The paired gap is 0.023 ± 0.002 over 500 runs. This is a statistical effect of selection. Its size depends on the stub's assumed accuracy spread (0.62 to 0.84) and on its independent-error assumption, so 0.023 is not a general figure.

</details>
