# 47.3 — Parallel Tool Calling & Structured Outputs Enforcement

## Opening Motivation & Context

In the realm of Large Language Models (LLMs), the ability to call external tools and enforce structured outputs is a powerful capability. This lesson focuses on parallel tool calling and structured outputs enforcement, which are crucial for building robust and efficient AI applications. Parallel tool calling allows multiple tools to be executed simultaneously, significantly improving the speed and efficiency of the application. Structured outputs enforcement ensures that the outputs from these tools are in a consistent and predictable format, making it easier to integrate them into larger systems.

## Core Concepts Breakdown

### Parallel Tool Calling

Parallel tool calling involves executing multiple tools concurrently, which can lead to substantial performance improvements. This is particularly useful in scenarios where multiple independent tasks need to be performed, such as fetching data from multiple sources or processing different parts of a dataset.

> [!KEY-INSIGHT]
> Parallel tool calling leverages the inherent parallelism in modern computing architectures, allowing multiple tasks to be executed simultaneously, thus reducing the overall execution time.

> [!BEST-PRACTICE]
> When implementing parallel tool calling, ensure that the tools are independent of each other and do not share resources that could lead to race conditions. Use thread pools or process pools to manage the concurrent execution of tools.

> [!WARNING]
> Be cautious when dealing with shared resources in parallel tool calling. Ensure proper synchronization mechanisms are in place to avoid race conditions and data corruption.

### Structured Outputs Enforcement

Structured outputs enforcement involves ensuring that the outputs from the tools are in a consistent and predictable format. This is achieved by defining a schema for the outputs and validating them against this schema. This ensures that the outputs can be easily integrated into larger systems and processed by other components.

> [!KEY-INSIGHT]
> Structured outputs enforcement provides a clear contract between the tools and the rest of the system, making it easier to maintain and extend the application.

> [!BEST-PRACTICE]
> Use a schema validation library like `jsonschema` to enforce structured outputs. Define a schema that matches the expected structure of the outputs and validate the outputs against this schema.

> [!WARNING]
> Ensure that the schema is comprehensive and covers all possible output scenarios. Incomplete schemas can lead to unexpected errors and make it difficult to integrate the outputs into larger systems.

## Code Demonstration & Runtime Output

```python
import concurrent.futures
import json
from typing import Dict, List, Any
from jsonschema import validate, ValidationError

# Define the schema for the tool outputs
TOOL_OUTPUT_SCHEMA = {
    "type": "object",
    "properties": {
        "tool_name": {"type": "string"},
        "result": {"type": "object"},
    },
    "required": ["tool_name", "result"]
}

def tool1() -> Dict[str, Any]:
    """Simulate a tool that fetches data from a source."""
    return {
        "tool_name": "tool1",
        "result": {"data": "data from tool1"}
    }

def tool2() -> Dict[str, Any]:
    """Simulate a tool that processes data."""
    return {
        "tool_name": "tool2",
        "result": {"processed_data": "processed data from tool2"}
    }

def validate_tool_output(output: Dict[str, Any]) -> bool:
    """Validate the tool output against the schema."""
    try:
        validate(instance=output, schema=TOOL_OUTPUT_SCHEMA)
        return True
    except ValidationError:
        return False

def execute_tools_parallel(tools: List[callable]) -> List[Dict[str, Any]]:
    """Execute tools in parallel and validate their outputs."""
    with concurrent.futures.ThreadPoolExecutor() as executor:
        futures = [executor.submit(tool) for tool in tools]
        results = [future.result() for future in concurrent.futures.as_completed(futures)]

    validated_results = []
    for result in results:
        if validate_tool_output(result):
            validated_results.append(result)
        else:
            print(f"Invalid output from tool {result.get('tool_name', 'unknown')}")

    return validated_results

if __name__ == "__main__":
    tools = [tool1, tool2]
    results = execute_tools_parallel(tools)
    print(json.dumps(results, indent=2))
```

### How this works (Line-by-Line Breakdown)

1. **Imports**: The necessary libraries are imported, including `concurrent.futures` for parallel execution, `json` for JSON handling, and `jsonschema` for schema validation.
2. **Schema Definition**: The `TOOL_OUTPUT_SCHEMA` defines the structure that the tool outputs must adhere to.
3. **Tool Functions**: `tool1` and `tool2` are simple functions that simulate tools returning structured data.
4. **Validation Function**: `validate_tool_output` uses `jsonschema.validate` to check if the tool output matches the defined schema.
5. **Parallel Execution**: `execute_tools_parallel` uses a `ThreadPoolExecutor` to run the tools in parallel. The results are collected and validated.
6. **Main Block**: The `if __name__ == "__main__":` block demonstrates the usage of the functions, executing the tools in parallel and printing the validated results.

> [!ADVANCED]
> The `ThreadPoolExecutor` manages a pool of threads, allowing multiple tools to be executed concurrently. The `as_completed` method ensures that the results are collected as soon as they are available, improving efficiency. The schema validation ensures that the outputs are in the expected format, making it easier to integrate them into larger systems.

> [!QA]
> Q: When should I prefer parallel tool calling over sequential execution?
> A: Parallel tool calling is preferable when the tools are independent and do not share resources. It can significantly improve performance by leveraging the parallelism available in modern computing architectures. However, if the tools share resources or have dependencies, sequential execution might be more appropriate to avoid race conditions and ensure correctness.
