A tool-calling model never runs anything itself. It writes a structured request, and your program must find that request, check it, run the function and report the result back. In this lesson you will build that loop with a stub model in plain Python, see the three points where it can fail, and measure what the error feedback is worth.

**You need:** Python dictionaries and `json.loads`, and the schema idea from Lesson 47.1.

## The problem this solves

A language model outputs text. It cannot read a database or fetch a web page on its own. Tool calling changes the contract: you describe each tool by name, description and parameter schema, and the model may emit a request to use one. The request is only data. Something in your program has to notice it, turn it into a real call, and return the answer as a message. Because the model must see the answer before it can continue, this is a loop, not a single call. ReAct (Yao et al., 2022) uses the same pattern of alternating model steps with actions and the observations they return.

## The loop

![A flow: messages go to a model call; if the reply has no tool call the final text is returned; otherwise the call is dispatched and its result is appended to messages, and the model is called again](diagrams/47.2-loop.svg "One pass of the loop. The model's reply decides whether the program runs a tool or stops.")

Each pass makes one model call. If the reply contains no tool request, its text is the answer. Otherwise the program runs every requested tool, appends one result message per request, and calls the model again. The request has a different shape in each provider's API. Anthropic returns `stop_reason: "tool_use"` with a `tool_use` block that holds an `id`, a `name` and an `input` object, and expects a `tool_result` block quoting that `id` (Anthropic, "Handle tool calls"). OpenAI's function-calling guide describes a `function_call` item with `call_id`, `name` and `arguments`, where `arguments` is a JSON-encoded string, and a `function_call_output` item that returns the same `call_id` (OpenAI, "Function calling"). One difference matters here: Anthropic hands you a parsed object, OpenAI hands you a string. The code below uses the string form, so its first step is parsing.

Two rules follow from the protocol. The assistant turn that contains the request is appended unchanged, because each result must point at a request still present in the history. And the loop needs a step cap, because nothing in the protocol stops a model from asking for tools indefinitely.

## Three stages between the string and the call

![Three boxes in a row: the argument string, the parsed dict, and the checked call, joined by arrows labelled json.loads and validate; a dashed exit from each arrow leads to an error note](diagrams/47.2-arg-stages.svg "Parse, validate, run. A failure at either check returns an error to the model, and nothing runs.")

The dispatcher does three things in order. It parses the string with `json.loads`. It validates the resulting dict against the schema: every required key present, every value of the declared type, enumerated values inside the allowed set, and no unexpected keys. Only then does it call the function with `**args`. Each stage can fail, and each failure becomes a tool result with `is_error` set, so the model can try again instead of the program crashing.

Validation is not a formality. `json.loads` accepts any valid JSON, so `"unit": 22` parses into a Python `int` without complaint. Parsing tells you the text is well formed; only the schema tells you the value is the right kind of thing.

## Worked example by hand

The user asks how hot Tokyo is in Fahrenheit. The stub model below is a scripted stand-in for a real LLM; a real API call would take its place. It produces three replies.

1. It calls `get_weather` with `unit` set to the number 22. Validation fails because `unit` must be a string. The error goes back as a tool result with `is_error` set to true.
2. It calls `get_weather` again with `unit` set to `"fahrenheit"`. The tool stores Tokyo as 28 °C and converts: $28 \times 9/5 + 32 = 82.4$, and `round(82.4)` is 82. The result is `82 degrees fahrenheit`.
3. It writes the final answer and makes no further calls, so the loop ends.

The code reproduces this trace exactly.

```python
import json

def get_weather(location: str, unit: str) -> str:
    """Toy weather tool. Temperatures in Celsius; converted for Fahrenheit."""
    celsius = {"tokyo": 28, "london": 15, "new york": 22}
    if location.lower() not in celsius:
        raise LookupError(f"no data for {location!r}")
    t = celsius[location.lower()]
    if unit == "fahrenheit":
        t = round(t * 9 / 5 + 32)
    return f"{t} degrees {unit}"

# Schema the model sees, in simplified form: required parameters, types, allowed values.
TOOLS = {
    "get_weather": {
        "fn": get_weather,
        "params": {"location": str, "unit": str},
        "allowed": {"unit": {"celsius", "fahrenheit"}},
    }
}

def validate(args, spec):
    """Return an error message, or None if the arguments fit the schema."""
    if not isinstance(args, dict):
        return "arguments must be a JSON object"
    for name, typ in spec["params"].items():
        if name not in args:
            return f"missing required argument {name!r}"
        if not isinstance(args[name], typ):
            return f"{name!r} must be {typ.__name__}, got {type(args[name]).__name__}"
        allowed = spec["allowed"].get(name)
        if allowed is not None and args[name] not in allowed:
            return f"{name!r} must be one of {sorted(allowed)}"
    extra = set(args) - set(spec["params"])
    if extra:
        return f"unexpected arguments {sorted(extra)}"
    return None

def dispatch(call):
    """Run one tool call. Returns (content, is_error). Never raises."""
    spec = TOOLS.get(call["name"])
    if spec is None:
        return f"unknown tool {call['name']!r}", True
    try:
        args = json.loads(call["arguments"])
    except json.JSONDecodeError as e:
        return f"arguments are not valid JSON: {e.msg}", True
    problem = validate(args, spec)
    if problem:
        return problem, True
    try:
        return str(spec["fn"](**args)), False
    except Exception as e:
        return f"tool error: {e}", True

def run_agent(model, user_text, max_steps=4):
    messages = [{"role": "user", "content": user_text}]
    for _ in range(max_steps):
        reply = model(messages)                 # one model call
        messages.append(reply)                  # keep the assistant turn unchanged
        if not reply["tool_calls"]:
            return reply["content"], messages
        for call in reply["tool_calls"]:
            content, is_error = dispatch(call)
            messages.append({"role": "tool", "tool_call_id": call["id"],
                             "content": content, "is_error": is_error})
    raise RuntimeError(f"no final answer after {max_steps} steps")

def stub_model(script):
    """Stand-in for an LLM: replays scripted replies. A real API call would go here."""
    replies = iter(script)
    return lambda messages: next(replies)

script = [
    {"role": "assistant", "content": "", "tool_calls": [
        {"id": "call_1", "name": "get_weather", "arguments": '{"location": "Tokyo", "unit": 22}'}]},
    {"role": "assistant", "content": "", "tool_calls": [
        {"id": "call_2", "name": "get_weather", "arguments": '{"location": "Tokyo", "unit": "fahrenheit"}'}]},
    {"role": "assistant", "content": "Tokyo is 82 degrees Fahrenheit.", "tool_calls": []},
]
answer, log = run_agent(stub_model(script), "How hot is Tokyo in Fahrenheit?")
for m in log:
    if m["role"] == "user":
        print("user   :", m["content"])
    elif m["role"] == "tool":
        print("tool   :", m["tool_call_id"], "is_error =", m["is_error"], "->", m["content"])
    elif m.get("tool_calls"):
        print("model  : calls", [c["name"] for c in m["tool_calls"]])
    else:
        print("model  : says", repr(m["content"]))
print("answer :", answer)

cases = [
    ("valid", "get_weather", '{"location": "Tokyo", "unit": "celsius"}'),
    ("malformed JSON", "get_weather", "{'location': 'Tokyo', 'unit': 'celsius'}"),
    ("wrong type", "get_weather", '{"location": "Tokyo", "unit": 22}'),
    ("missing argument", "get_weather", '{"location": "Tokyo"}'),
    ("enum violation", "get_weather", '{"location": "Tokyo", "unit": "kelvin"}'),
    ("tool raises", "get_weather", '{"location": "Atlantis", "unit": "celsius"}'),
    ("unknown tool", "get_wether", '{"location": "Tokyo", "unit": "celsius"}'),
]
print(f"{'case':<17}{'is_error':<10}content")
for label, name, args in cases:
    content, is_error = dispatch({"id": "x", "name": name, "arguments": args})
    print(f"{label:<17}{str(is_error):<10}{content}")
```

```output
user   : How hot is Tokyo in Fahrenheit?
model  : calls ['get_weather']
tool   : call_1 is_error = True -> 'unit' must be str, got int
model  : calls ['get_weather']
tool   : call_2 is_error = False -> 82 degrees fahrenheit
model  : says 'Tokyo is 82 degrees Fahrenheit.'
answer : Tokyo is 82 degrees Fahrenheit.
case             is_error  content
valid            False     28 degrees celsius
malformed JSON   True      arguments are not valid JSON: Expecting property name enclosed in double quotes
wrong type       True      'unit' must be str, got int
missing argument True      missing required argument 'unit'
enum violation   True      'unit' must be one of ['celsius', 'fahrenheit']
tool raises      True      tool error: no data for 'Atlantis'
unknown tool     True      unknown tool 'get_wether'
```

The trace shows three properties to keep. `dispatch` never raises; every failure becomes text the model can read. The validator runs before the function, so the function only receives values of the declared types. And `run_agent` returns the whole message log, so every step can be audited afterwards.

## Experiment 2: what the feedback is worth

Experiment 1 shows that failures are caught. It does not show that catching them helps. For that, simulate a toy model under two dispatch policies. Each tool call gets up to three attempts. The first attempt is malformed with probability $p$. A retry after an error message is correct with probability $R$. I set $R = 0.7$ as an assumption, not a measurement.

- **Naive:** in this toy model, a malformed call ends the episode. An episode of $K = 3$ calls succeeds only if no call is malformed, so $P_{\text{naive}} = (1-p)^K$.
- **Validated:** the error goes back and the model retries, up to three attempts per call. A call fails only if all three attempts are malformed, with probability $p(1-R)^2$, so $P_{\text{validated}} = \left(1 - p(1-R)^2\right)^K$.

Setting $R = 0$ makes the validated formula collapse to the naive one. The gain comes from the retry, not from the error message alone, so $R$ must be measured on the model you use before any gain is quoted.

```python
import numpy as np

# Toy model, not a measurement: each tool call needs K=3 attempts' worth of luck.
# p: chance the first attempt is malformed. R: chance a retry after an is_error message
# is correct (assumed here, not measured on a real model).
R, K, N = 0.7, 3, 20_000
rng = np.random.default_rng(47)

print("   p   naive  closed  validated  closed  attempts/call")
for p in (0.05, 0.20, 0.40):
    u = rng.random((N, K, 3))
    a1 = u[..., 0] < p            # attempt 1 malformed
    a2 = u[..., 1] < 1 - R        # attempt 2 malformed (drawn for all calls, used only if a1)
    a3 = u[..., 2] < 1 - R        # attempt 3 malformed (used only if a1 and a2)
    naive = np.mean(~a1.any(axis=1))           # no feedback: first bad call ends the episode
    call_fails = a1 & a2 & a3                  # all three attempts malformed
    validated = np.mean(~call_fails.any(axis=1))
    attempts = np.mean(1 + a1 + (a1 & a2))     # mean attempts per call
    print(f"{p:4.2f}  {naive:6.3f}  {(1-p)**K:6.3f}  {validated:9.3f}  "
          f"{(1-p*(1-R)**2)**K:6.3f}  {attempts:13.3f}")
```

```output
   p   naive  closed  validated  closed  attempts/call
0.05   0.854   0.857      0.987   0.987          1.067
0.20   0.513   0.512      0.949   0.947          1.259
0.40   0.209   0.216      0.898   0.896          1.524
```

![Grouped bars for p equal to 0.05, 0.20 and 0.40: naive success falls from 0.854 to 0.209, validated success stays between 0.898 and 0.987](diagrams/47.2-policy-chart.svg "Episode success under the two policies. The validated bars assume R = 0.7.")

At $p = 0.40$ the validated policy uses about 1.5 attempts per call, so the gain costs model calls. The Monte Carlo and closed-form columns agree to within 0.007. The largest gap, at $p = 0.40$, is about 2.4 standard errors at this sample size, so the simulation is only roughly consistent with the algebra. The closed forms are exact for this toy model; the simulation is a check on them, not independent evidence about real models.

## Common traps

> [!TRAP]
> Never `eval` or `exec` a model's arguments or tool name. Look the name up in a fixed registry, as `dispatch` does, and pass only validated values to the function.

> [!TRAP]
> Parsing is not validation. `json.loads` returns `22` happily for a string field. A tool that does not check its inputs may fail later, far from the cause, or succeed with the wrong value.

> [!TRAP]
> Without a step cap, one confused model can loop indefinitely and spend money on every pass. Cap the steps, and cap retries separately. Anthropic's docs make the same point about `is_error` retries.

> [!TRAP]
> Results must match their requests. Anthropic expects each `tool_result` to quote a `tool_use` `id` from the immediately preceding assistant turn, and it expects `tool_result` blocks before any text in the user message. Text placed before a `tool_result` gives a 400 error.

> [!TRAP]
> A bare error such as "failed" leaves the model guessing. Say what went wrong and what to try next, as the examples in the Anthropic docs do.

## Summary

- A tool call is a request inside the model's output. The loop runs it, checks it, and returns the result as a message.
- The loop ends when a reply has no tool request, and it must also have a step cap.
- Arguments arrive as JSON text (OpenAI) or as a parsed object (Anthropic). Parse, validate, then run, and turn every failure into an `is_error` result.
- Error feedback helps through retries. With $R = 0$ the validated policy is no better than the naive one.

## Quiz time

### Question 1: Why must the assistant's tool-call turn be appended unchanged?

<details><summary>Show Solution</summary>

Each result refers to its request by id: `tool_use_id` in Anthropic, `call_id` in OpenAI. That request must still be in the history for the result to match it. Rewriting or dropping the assistant turn breaks the link, and the API rejects the request.

</details>

### Question 2: Calculate the success rate

With $p = 0.2$, $R = 0.7$ and $K = 3$, what is $P_{\text{validated}}$? Use the closed form.

<details><summary>Show Solution</summary>

$p(1-R)^2 = 0.2 \times 0.09 = 0.018$, so the run succeeds with probability $(1 - 0.018)^3 = 0.982^3 \approx 0.947$. The simulation printed 0.949, which agrees within sampling error.

</details>

### Question 3: Find the bugs

```python
def run_call(call):
    spec = TOOLS[call["name"]]
    args = call["arguments"]
    return spec["fn"](**args)
```

<details><summary>Show Solution</summary>

1. In the OpenAI shape `call["arguments"]` is a JSON string, so `**args` raises `TypeError`. It needs `json.loads` first. (In the Anthropic shape the input is already an object, so no parsing is needed there.)
2. Nothing is validated. A missing key, a wrong type or an extra key reaches the function.
3. `TOOLS[call["name"]]` raises `KeyError` for an unknown name, and the exception escapes the loop instead of becoming an `is_error` result.
4. An exception raised inside the tool also escapes and ends the run. It should be caught and returned as text.

The `dispatch` function in the code above fixes all four.

</details>

### Question 4: Judge a design

A colleague says: "Just return the exception traceback to the model; that is enough feedback." Give one reason this is weaker than a short message, and one reason the traceback is still useful.

<details><summary>Show Solution</summary>

A traceback is long, full of internal file paths, and may leak details you do not want the model or its user to see. A short message that says what was wrong and what to change is easier for the model to act on. (This is my own reasoning, not a sourced result.) The traceback is still useful to you, so log it on the server side and send the model a short version.

</details>
