**In this lesson you will** write a plan as a dependency graph, run it in two schedules, and compute how the chance of success falls as a flat plan gets longer. You will then see how checkpoints change that number.

**You need:** the ReAct loop from Lesson 48.1, where an agent alternates reasoning and tool calls, and the rule that independent events multiply: two steps that must both succeed, each with probability 0.9, succeed together with probability $0.9 \times 0.9 = 0.81$.

## The problem a plan solves

Suppose an agent must answer: "Which of three companies grew revenue fastest from 2023 to 2024?" The answer needs six lookups, three growth calculations, a comparison and a written answer. A ReAct agent does this one step at a time. Each model call sees the latest observation, which helps when the next step depends on what was found. But it pays one model call per step, and it never notices that the six lookups do not depend on each other.

Plan-and-solve separates the two jobs. A planner writes the whole sequence of steps first, and an executor carries them out. Wang et al. (2023) list missing-step errors among the failure modes of zero-shot chain-of-thought prompting, and their plan-first prompt targets them. Least-to-most prompting (Zhou et al., 2022) goes further: it splits a hard problem into subproblems, solves them in sequence, and feeds each answer into the next.

## Intuition: a tree of goals, and a graph of dependencies

![A tree: one question at the top, three company sub-goals below it, each with two revenue lookups as leaves](diagrams/48.2-task-tree.svg "Decomposition of the question. Only the leaves call a tool.")

Read the tree top-down. Each box is a goal, and each leaf is one tool call. The tree says what must be done, but not what waits for what. For that you need a second structure, the dependency graph. Step s7 (Acme's growth) needs s1 and s2, so it cannot run before both. The six lookups need nothing, so they could all run at once.

## Worked example by hand

Eleven steps, s1 to s11. Run them one call at a time and you need 11 rounds. Group them by dependency instead:

- Round 1: the six lookups, s1 to s6. None needs another step.
- Round 2: the three growth steps, s7 to s9. Each needs two round-1 results.
- Round 3: the pick, s10. It needs all three growth values.
- Round 4: the written answer, s11.

Four rounds, and the answer is the company with the largest growth: Cobalt, at 30%. Acme grew 25% (120 to 150) and Bolt 15% (200 to 230), using toy revenue figures invented for this example.

![Eleven boxes in one row for one-at-a-time execution, and four rounds of boxes for the dependency waves](diagrams/48.2-rounds.svg "The same eleven steps on two schedules. Boxes in one wave may run in parallel.")

The code below encodes each step with the ids it needs, then runs the plan both ways. It uses only the standard library, so it runs in the browser.

```python
from dataclasses import dataclass
from graphlib import TopologicalSorter

REVENUE = {("Acme", 2023): 120, ("Acme", 2024): 150,      # millions of dollars, invented for this example
           ("Bolt", 2023): 200, ("Bolt", 2024): 230,
           ("Cobalt", 2023): 80, ("Cobalt", 2024): 104}

@dataclass
class Step:
    id: str
    needs: tuple          # ids of the steps whose results this step reads
    fn: object            # fn(results of the needed steps) -> value

def lookup(company, year):
    return lambda r: REVENUE[(company, year)]

def growth(before, after):
    return lambda r: (r[after] - r[before]) / r[before]

def pick_fastest(r):
    growth_id = {"Acme": "s7", "Bolt": "s8", "Cobalt": "s9"}
    return max(growth_id, key=lambda c: r[growth_id[c]])

PLAN = [
    Step("s1", (), lookup("Acme", 2023)),
    Step("s2", (), lookup("Acme", 2024)),
    Step("s3", (), lookup("Bolt", 2023)),
    Step("s4", (), lookup("Bolt", 2024)),
    Step("s5", (), lookup("Cobalt", 2023)),
    Step("s6", (), lookup("Cobalt", 2024)),
    Step("s7", ("s1", "s2"), growth("s1", "s2")),
    Step("s8", ("s3", "s4"), growth("s3", "s4")),
    Step("s9", ("s5", "s6"), growth("s5", "s6")),
    Step("s10", ("s7", "s8", "s9"), pick_fastest),
    Step("s11", ("s10",), lambda r: f"answer: {r['s10']}"),
]

def validate(steps):
    ids = {s.id for s in steps}
    for s in steps:
        for d in s.needs:
            if d not in ids:
                raise ValueError(f"{s.id} needs unknown step {d}")

def run_sequential(steps):
    results = {}
    for s in steps:                       # plan order, one call at a time
        results[s.id] = s.fn({d: results[d] for d in s.needs})
    return results

def run_waves(steps):
    validate(steps)
    by_id = {s.id: s for s in steps}
    ts = TopologicalSorter({s.id: s.needs for s in steps})
    ts.prepare()
    results, waves = {}, []
    while ts.is_active():
        ready = ts.get_ready()            # every step whose dependencies are done
        waves.append(list(ready))
        for sid in ready:                 # these calls could run in parallel
            s = by_id[sid]
            results[sid] = s.fn({d: results[d] for d in s.needs})
        ts.done(*ready)
    return results, waves

seq = run_sequential(PLAN)
res, waves = run_waves(PLAN)
print("sequential calls:", len(PLAN), "| result:", seq["s11"])
print("parallel rounds :", len(waves))
for i, w in enumerate(waves, 1):
    print(f"  round {i}: {w}")
print("growth:", {c: round(res[i], 3) for c, i in [("Acme", "s7"), ("Bolt", "s8"), ("Cobalt", "s9")]})
print("same answer both ways:", seq["s11"] == res["s11"])

bad = PLAN[:9] + [Step("s10", ("s7", "s8", "s99"), pick_fastest), PLAN[10]]
try:
    run_waves(bad)
except ValueError as e:
    print("rejected:", e)
```

```output
sequential calls: 11 | result: answer: Cobalt
parallel rounds : 4
  round 1: ['s1', 's2', 's3', 's4', 's5', 's6']
  round 2: ['s7', 's8', 's9']
  round 3: ['s10']
  round 4: ['s11']
growth: {'Acme': 0.25, 'Bolt': 0.15, 'Cobalt': 0.3}
same answer both ways: True
rejected: s10 needs unknown step s99
```

`TopologicalSorter` (standard library `graphlib`) keeps track of which steps have finished. `get_ready()` returns every step whose predecessors are done, and `done()` releases their successors. The `validate` check is needed because `graphlib` does not reject unknown names. Calling `TopologicalSorter({"s10": ("s7", "s99"), "s7": ()})` and then `get_ready()` reports `s99` as ready, a step with no work attached. Without the check, the run would fail later, when `s10` reads a result that was never produced.

## Why flat plans fail: errors compound

Model each step as succeeding independently with probability $p$. A flat plan of $n$ steps with no checks then succeeds with probability

$$
P(\text{success}) = p^n
$$

This is reasoning from first principles (not a cited result). Independence is what makes it exact, and it is the weakest assumption here: a bad parse can spoil several steps at once, so real errors are correlated. Treat the numbers as an illustration. The per-step value $p = 0.95$ is assumed, not measured on any model.

Checkpoints change the arithmetic. Split the plan into blocks, verify each block's outcome, and re-run a block that fails. If the verifier is perfect and each attempt is independent, a block of three steps succeeds with $s = p^3 \approx 0.857$. Three attempts succeed with $1 - (1 - s)^3 \approx 0.9971$, and two such blocks succeed with about 0.9942.

```python
import random

P = 0.95              # assumed per-step success probability (illustrative, not measured)

for n in (6, 12, 24):
    print(f"{n:2d} steps, no checks: {P**n:.3f}")

def run_flat(rng, n):
    return all(rng.random() < P for _ in range(n))

def run_checkpointed(rng, block=3, blocks=2, attempts=3):
    for _ in range(blocks):
        for _ in range(attempts):
            if all(rng.random() < P for _ in range(block)):   # a block passes only if all its steps do
                break
        else:
            return False                  # a block failed every attempt
    return True

rng = random.Random(0)
N = 200_000
print(f"Monte Carlo, 6 steps, no checks:     {sum(run_flat(rng, 6) for _ in range(N)) / N:.4f}")
print(f"Monte Carlo, 2 blocks of 3, retried: {sum(run_checkpointed(rng) for _ in range(N)) / N:.4f}")
print(f"Analytic, 2 blocks of 3, retried:    {(1 - (1 - P**3)**3)**2:.4f}")
```

```output
 6 steps, no checks: 0.735
12 steps, no checks: 0.540
24 steps, no checks: 0.292
Monte Carlo, 6 steps, no checks:     0.7365
Monte Carlo, 2 blocks of 3, retried: 0.9943
Analytic, 2 blocks of 3, retried:    0.9942
```

The simulation agrees with the formulas within noise. For the flat plan, the gap is 0.0014, about 1.4 standard errors ($\sqrt{p^n(1-p^n)/N} \approx 0.001$ at $N = 200{,}000$).

![Four bars: success 0.735 for a flat six-step plan, 0.540 for twelve steps, 0.292 for twenty-four steps, and 0.994 for two checkpointed blocks of three](diagrams/48.2-error-bars.svg "Analytic success probability at a per-step success of 0.95.")

Retries are not free. Each block costs three steps per attempt, and the expected number of attempts per block is $1 + (1-s) + (1-s)^2 \approx 1.163$. The expected number of step executions is therefore about $2 \times 3 \times 1.163 \approx 6.98$, against 6 for the flat plan. You trade about 16% more calls for a success rate near 0.99 instead of 0.74. The checkpoint also needs a verifier, which is itself a model call or a test with its own errors, so the perfect-verifier assumption is the one to challenge first.

## Plan-and-solve inside an agent loop

![Planner produces a plan, the executor runs ready steps, and a dashed loop returns to the planner only when a step fails](diagrams/48.2-plan-flow.svg "Plan-and-solve control flow. Replanning is an exception path, not the default.")

The planner is one call. The executor runs ready steps, and only a failure sends control back to the planner. This is cheaper than ReAct when the steps are predictable, and it is worse when an observation changes what should happen next. Two later papers push the parallel idea further. LLMCompiler (Kim et al., 2023) plans a directed acyclic graph of function calls and runs independent calls in parallel; its abstract reports up to 3.7x lower latency and up to 6.7x lower cost than ReAct, on benchmarks that the abstract does not name. ReWOO (Xu et al., 2023) separates reasoning from tool observations so the model does not re-read every result; its abstract reports 5x token efficiency and a 4% accuracy gain on HotpotQA, without naming the baseline behind the 5x.

> [!TRAP]
> A plan is a single model output, not a guarantee. Missing steps are the typical failure, and the executor will run what it is given. Validate the plan's structure (every `needs` id exists, no cycles) before running anything.

> [!TRAP]
> Dropping an edge is silent. A step that omits a dependency runs too early and reads a missing value, or runs in the wrong wave. Check the schedule, not just the final answer.

> [!TRAP]
> Parallel rounds save latency, not tokens. Each call is still paid for, and parallel calls hit rate limits together.

> [!TRAP]
> Checkpoint arithmetic assumes independent attempts and a perfect verifier. A model that makes the same mistake on every retry gains nothing from retrying, so the 0.994 is an upper bound on what checkpoints buy, not a forecast.

> [!TRAP]
> Deeper hierarchies add planner calls and boundaries where errors can enter. Decompose until each leaf is one tool call, and stop there.

## Summary

- Plan-and-solve writes the whole plan first, then executes it. A dependency graph shows what can run in parallel.
- The eleven-step example takes 11 sequential rounds but only 4 dependency waves.
- Under independent per-step success $p$, a flat $n$-step plan succeeds with $p^n$, which falls quickly as $n$ grows.
- Checkpoints with retries recover most of that loss, at the cost of extra calls and a verifier whose own errors you must measure.

## Quiz time

### Question 1: Calculation

A flat eight-step plan has per-step success 0.9 and no checks. What is the probability that the whole plan succeeds?

<details><summary>Show solution</summary>

$0.9^8 = 0.4305$, so about 43%. Each step must succeed, and independence lets the probabilities multiply.

</details>

### Question 2: Bug-spotting

Suppose the list `PLAN` is reversed, so `s11` comes first, and you run it with `run_sequential`. What happens, and why?

<details><summary>Show solution</summary>

It raises `KeyError`. The first step, `s11`, needs `s10`, which is not in `results` yet, because the sequential runner only fills `results` in list order. Reversing the list breaks the dependency order, which is why the sequential runner depends on a valid plan order and the wave runner does not.

</details>

### Question 3: Prediction

Why does the wave schedule put `s10` alone in round 3, rather than in round 2 with the growth steps?

<details><summary>Show solution</summary>

`s10` needs the results of `s7`, `s8` and `s9`. Those are produced in round 2, so `s10` only becomes ready after round 2 is done. A step is placed in the earliest wave in which all of its dependencies have finished.

</details>

### Question 4: Explanation

A web-search agent must read each result before it knows the next query. Is a fixed plan the right design? Explain in terms of the error model.

<details><summary>Show solution</summary>

No. A fixed plan cannot use information that appears after the first step, so a wrong guess about the next query is baked in. The ReAct loop, which observes after each step, fits this case better, or you can replan on failure as in the diagram above. The error model says why it matters: a plan whose later steps depend on unseen results is not independent of its earlier steps in the way the $p^n$ formula assumes.

</details>
