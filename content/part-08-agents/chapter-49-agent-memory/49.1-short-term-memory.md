A chat agent resends its whole history on every turn, so its prompt grows until it reaches the model's limit. In this lesson you will measure how fast that happens, implement two fixes (a sliding window and a rolling summary) in plain Python, and measure what each one costs and what it forgets.

**You need:** the idea of a context window and of attention cost (Lesson 25.1), and comfort with Python lists.

## The problem

A large language model (LLM) keeps no state between calls. To continue a conversation, the agent sends the system prompt, every earlier message and the new message again. The prompt length is what the model reads on each call, and the cost of a call grows with it. The context window is the maximum prompt length the model accepts.

This lesson counts one word as one token. That is a proxy: real tokenizers split words differently, and a real budget must be set in tokens. The mechanism is the same either way.

The simulated chat has 80 turns of about 40 words each. With no limit, the prompt passes a 400-word (proxy-token) budget at turn 10.5 on average over 60 conversations (earliest turn 8, latest 13). By turn 80 one conversation's prompt is about 3,100 words, and the total input over the conversation is about 132,000 words. Summing the prompt over turns gives about $\mu N(N+1)/2$, where $\mu$ is the mean message length and $N$ is the number of turns. With $\mu \approx 40$ and $N = 80$ that is about 130,000, close to the measured value (the extra comes from the planted facts). Total cost therefore grows with the square of the conversation length.

Full history is unbounded.")

## Sliding window: keep the newest messages

The simplest fix drops the oldest messages until the prompt fits the budget. The table below applies a 16-word budget to five messages of 9, 5, 5, 5 and 5 words.

![Table of five messages against five turns: at each turn the newest messages that fit in 16 words are shaded green, and older ones are marked dropped](diagrams/49.1-toy-window.svg "Sliding window, 16-word budget. Green cells are visible to the model at that turn.")

Work it by hand. At turn 3 the history is $9 + 5 + 5 = 19$ words, over 16. Start from the newest message: message 3 (5 words) fits, message 2 brings the total to 10, and message 1 would make 19, so it is dropped. The window is messages 2 and 3, 10 words. At turn 5 the window is messages 3 to 5, 15 words. The code reproduces these numbers:

```python
def sliding_window(messages, budget):
    """Keep the newest whole messages whose word counts fit in the budget."""
    window, used = [], 0
    for name, words in reversed(messages):
        if used + words > budget:
            break
        window.insert(0, (name, words))
        used += words
    return window, used

messages = [("msg 1", 9), ("msg 2", 5), ("msg 3", 5), ("msg 4", 5), ("msg 5", 5)]
for turn in range(1, len(messages) + 1):
    window, used = sliding_window(messages[:turn], budget=16)
    names = [n for n, _ in window]
    print(f"turn {turn}: window = {names}  ({used} / 16 words)")
```

```output
turn 1: window = ['msg 1']  (9 / 16 words)
turn 2: window = ['msg 1', 'msg 2']  (14 / 16 words)
turn 3: window = ['msg 2', 'msg 3']  (10 / 16 words)
turn 4: window = ['msg 2', 'msg 3', 'msg 4']  (15 / 16 words)
turn 5: window = ['msg 3', 'msg 4', 'msg 5']  (15 / 16 words)
```

The window bounds the prompt, but it forgets completely. In the experiment below, each conversation plants five facts such as "the license key for box B12 is 4821". The sliding window at 400 words recalls on average 0.107 of them at the final turn, because only facts in the last few hundred words are still visible.

## Rolling summary: compress what falls out

The alternative keeps a running summary. When the verbatim messages exceed a budget, the oldest one is folded into the summary. The summary is itself rewritten by a summariser, which in a real agent is an LLM call that reads the old summary and the folded message.

![Diagram of three memory blocks: summary (at most 80 words), recent raw messages (at most 240 words) and a new turn; the oldest raw message goes to a summariser that writes back into the summary](diagrams/49.1-memory-layout.svg "Rolling summary layout. Budgets are configuration values, not measurements.")

The code below uses a stub summariser that keeps the leading share of the words it compresses. It is not an LLM. It is deliberately crude so the loss is visible.

```python
import math

def lead_summary(words, keep):
    """Stub summariser: keeps the leading share `keep` of the words. Not an LLM."""
    return words[: math.ceil(keep * len(words))]

class RollingMemory:
    def __init__(self, recent_budget, summary_budget, keep):
        self.recent_budget = recent_budget
        self.summary_budget = summary_budget
        self.keep = keep
        self.summary = []   # words of the running summary
        self.recent = []    # (name, words) kept verbatim, oldest first
        self.rounds = 0     # how many times the summariser ran

    def add(self, name, words):
        self.recent.append((name, words))
        while sum(len(w) for _, w in self.recent) > self.recent_budget:
            _, old = self.recent.pop(0)
            self.summary = self.summary + old
            if len(self.summary) > self.summary_budget:
                self.summary = lead_summary(self.summary, self.keep)
                self.rounds += 1

    def context_words(self):
        return len(self.summary) + sum(len(w) for _, w in self.recent)

memory = RollingMemory(recent_budget=12, summary_budget=8, keep=0.5)
for turn in range(1, 7):
    memory.add(f"msg {turn}", [f"m{turn}w{i}" for i in range(6)])
    print(f"turn {turn}: summary={len(memory.summary):2d} words, "
          f"recent={[n for n, _ in memory.recent]}, context={memory.context_words()} words, rounds={memory.rounds}")
print("summary:", " ".join(memory.summary))
```

```output
turn 1: summary= 0 words, recent=['msg 1'], context=6 words, rounds=0
turn 2: summary= 0 words, recent=['msg 1', 'msg 2'], context=12 words, rounds=0
turn 3: summary= 6 words, recent=['msg 2', 'msg 3'], context=18 words, rounds=0
turn 4: summary= 6 words, recent=['msg 3', 'msg 4'], context=18 words, rounds=1
turn 5: summary= 6 words, recent=['msg 4', 'msg 5'], context=18 words, rounds=2
turn 6: summary= 6 words, recent=['msg 5', 'msg 6'], context=18 words, rounds=3
summary: m1w0 m1w1 m1w2 m1w3 m1w4 m1w5
```

Trace turn 4. After turn 3 the summary holds message 1 (6 words, under the 8-word cap). Folding message 2 makes 12 words, over the cap, so the stub keeps the leading half: still message 1. Message 2 is gone. Every later fold is compressed the same way, so the summary never changes again. The model sees a bounded prompt, but the summary holds nothing from messages 2 to 6.

## Cost against recall

The experiment runs 60 synthetic conversations with the same budgets as the figures (400 words for the window, 240 raw plus an 80-word summary for the rolling strategy). Each conversation plants five facts. The table is the output of the block in the details below.

![Scatter plot of total input tokens against recall of planted facts for the sliding window and three keep ratios of the rolling summary; full history is off the chart](diagrams/49.1-cost-recall.svg "Mean over 60 conversations. Keep ratio is the stub summariser's kept share per round.")

- Full history: over budget at turn 10.5 on average; total input 132,323 words; not feasible under the budget.
- Sliding window (400 words): recall 0.107; total input 28,697.
- Rolling summary, keep 0.5: recall 0.073; total input 21,053.
- Rolling summary, keep 0.75: recall 0.087; total input 26,140.
- Rolling summary, keep 0.9: recall 0.137; total input 41,686.
- Rolling summary, keep 1.0 (no compression): recall 1.000; total input 132,323.

Under this stub, the rolling summary does no better than the sliding window at similar cost: 0.087 at 26,140 words against 0.107 at 28,697. A single conversation's recall ranges from 0 to 0.6 with five facts, so I did not compute confidence intervals; treat differences of a few points as noise. The result says the stub is the bottleneck. It does not say summaries are useless with a real summariser.

<details><summary>Run locally: needs numpy (tested with numpy 2.5.5)</summary>

```python
import math
import numpy as np

KEEP_SWEEP = [0.5, 0.75, 0.9, 1.0]
N, BUDGET, RECENT, SUMMARY_MAX = 80, 400, 240, 80

def make_conversation(seed):
    rng = np.random.default_rng(seed)
    lens = rng.integers(20, 61, size=N)
    fact_turns = set(int(t) for t in rng.choice(np.arange(0, N), size=5, replace=False))
    msgs, codes = [], []
    for t in range(N):
        words = [f"w{int(rng.integers(1000))}" for _ in range(int(lens[t]))]
        if t in fact_turns:
            code = str(int(rng.integers(1000, 10000)))
            pos = int(rng.integers(0, len(words) + 1))
            words = words[:pos] + ["the", "license", "key", "for", "box", f"B{t}", "is", code] + words[pos:]
            codes.append(code)
        msgs.append(words)
    return msgs, codes

def sliding(msgs):
    sizes, final = [], []
    for t in range(N):
        window, used = [], 0
        for m in reversed(msgs[: t + 1]):
            if used + len(m) > BUDGET:
                break
            window.insert(0, m)
            used += len(m)
        sizes.append(used)
        final = [w for m in window for w in m]
    return sizes, final

def rolling(msgs, keep):
    summary, raw, sizes, rounds = [], [], [], 0
    for t in range(N):
        raw.append(msgs[t])
        while sum(len(m) for m in raw) > RECENT:
            summary = summary + raw.pop(0)
            if len(summary) > SUMMARY_MAX:
                summary = summary[: math.ceil(keep * len(summary))]
                rounds += 1
        sizes.append(len(summary) + sum(len(m) for m in raw))
    return sizes, summary + [w for m in raw for w in m], rounds

def full_history(msgs):
    sizes, total = [], 0
    for m in msgs:
        total += len(m)
        sizes.append(total)
    return sizes

rec = {"sliding": [], **{k: [] for k in KEEP_SWEEP}}
tot = {"full": [], "sliding": [], **{k: [] for k in KEEP_SWEEP}}
overflow = []
for seed in range(60):
    msgs, codes = make_conversation(seed)
    fh = full_history(msgs)
    overflow.append(next(t + 1 for t, v in enumerate(fh) if v > BUDGET))
    tot["full"].append(sum(fh))
    sz, final = sliding(msgs)
    rec["sliding"].append(sum(c in final for c in codes) / len(codes))
    tot["sliding"].append(sum(sz))
    for k in KEEP_SWEEP:
        sz, final, _ = rolling(msgs, k)
        rec[k].append(sum(c in final for c in codes) / len(codes))
        tot[k].append(sum(sz))

print(f"full history: over budget by turn {np.mean(overflow):.1f} on average; total input {np.mean(tot['full']):.0f}")
for name in ["sliding"] + KEEP_SWEEP:
    label = "sliding window" if name == "sliding" else f"rolling, keep {name}"
    print(f"{label:20s} recall {np.mean(rec[name]):.3f}   total input {np.mean(tot[name]):.0f}")
```

```output
full history: over budget by turn 10.5 on average; total input 132323
sliding window       recall 0.107   total input 28697
rolling, keep 0.5    recall 0.073   total input 21053
rolling, keep 0.75   recall 0.087   total input 26140
rolling, keep 0.9    recall 0.137   total input 41686
rolling, keep 1.0    recall 1.000   total input 132323
```

## Why compression compounds

Take a summariser that keeps a share $\rho$ of the text it compresses, and a fact at a uniformly random position $p$ in a text of length $L$. A round with lead-keep (keep the first $\lceil \rho L \rceil$ words) preserves the fact exactly when $p < \rho L$. Given survival, the fact's position is still uniform on the shorter text, so each round multiplies the survival probability by $\rho$. After $k$ rounds, survival is $\rho^k$.

The ceiling in $\lceil \rho L \rceil$ makes the measured values differ slightly from $\rho^k$. The script's exact enumeration over 200 positions gives 0.065 at four rounds for $\rho = 0.5$, against 0.0625 for $\rho^4$. The figure plots both.

![Line chart of fact survival against summarisation rounds for keep ratios 0.5 and 0.75: dots are measured by exact enumeration, dashed lines are keep to the power k; both fall geometrically](diagrams/49.1-survival.svg "Survival of a fact under repeated lead-keep compression. Dots: exact enumeration over 200 positions. Dashed: rho to the power k.")

This is arithmetic about a position-blind stub with uniform fact positions. A real summariser can keep salient facts with much higher probability, so $\rho^k$ is a model of the failure mode, not a measured property of LLM summaries.

> [!TRAP]
> A budget counted in words is not a budget in tokens. A 400-word limit can be 600 tokens for code or identifiers. Count tokens with the tokenizer of the model you call.

> [!TRAP]
> A slice such as `messages[-budget:]` counts messages, not words. Five long messages can exceed the budget while the slice reports it fits. Accumulate lengths, as the sliding-window code above does.

> [!TRAP]
> Do not let the window drop the system prompt or the user's stated goal. Pin them outside the window, or they vanish after a few dozen turns.

> [!TRAP]
> Summaries lose exact strings. Identifiers, numbers and version strings are the first things a summary rewrites. Keep them verbatim in a separate store; Lessons 49.2 and 49.3 cover that.

> [!WARNING]
> Long verbatim context is not safe memory either. Liu et al. (2023) report that performance is often highest when the relevant information is at the start or end of a long input and drops in the middle, even for models built for long contexts. Keeping a 3,000-word raw history does not guarantee the model uses a fact from the middle of it.

## Summary

- Re-sending the full history makes each call's prompt, and the total input over a conversation, grow with the number of turns; total input is quadratic.
- A sliding window bounds the prompt by dropping the oldest whole messages, and forgets them completely.
- A rolling summary folds old messages into a bounded summary. Each fold is lossy, so a fact's survival after $k$ rounds is about $\rho^k$ under the model above.
- In the experiment, the stub summariser gave no recall advantage over the sliding window at similar cost. The result depends on the stub, not on summarisation in general.
- Keep exact identifiers outside the summary, and check every summarisation strategy against recall of facts that must survive.

### Question 1: Calculation

Using the 16-word sliding window from this lesson, which messages are visible at turn 4, and how many words do they total?

<details><summary>Show Solution</summary>

Messages 2, 3 and 4, for 15 words. Turn 4 totals 9 + 5 + 5 + 5 = 24 words. Message 1 (9 words) would bring the window to 24, so it is dropped, and 5 + 5 + 5 = 15 fits.

### Question 2: Prediction

A summariser keeps 80% of the text per round and a fact is equally likely to be anywhere in the summary. Ignoring the ceiling, what is the probability the fact survives three rounds?

<details><summary>Show Solution</summary>

$0.8^3 = 0.512$. Each round keeps the fact with probability 0.8, and after a survival the fact is again uniformly placed in the shorter text, so the per-round probabilities multiply. The ceiling changes the result slightly for short texts.

</details>

### Question 3: Find the bug

```python
def window(messages, budget):
    return messages[-budget:]
```

<details><summary>Show Solution</summary>

The slice counts messages, but the budget is in words. With `budget=16` it keeps up to 16 messages, which may be far over 16 words. Accumulate word counts from the newest message backwards and stop when the next message would exceed the budget, as `sliding_window` does.

</details>

### Question 4: Explanation

Why is the total input of a conversation with no compression quadratic in the number of turns, while a sliding window makes it linear?

<details><summary>Show Solution</summary>

With no compression, turn $t$ sends about $\mu t$ words, so the sum over $N$ turns is about $\mu N(N+1)/2$, which grows as $N^2$. A sliding window caps each prompt at $B$ words, so the total is at most $BN$, which grows linearly in $N$.

</details>

### Question 5: Design

Your agent must recall a user's account number across 300 turns. Why is a rolling summary alone a poor choice for this?

<details><summary>Show Solution</summary>

Each summarisation round can rewrite or drop the number, and survival compounds as $\rho^k$ over many rounds. Store the identifier verbatim in a separate store outside the window and retrieve it by key. Lesson 49.2 covers long-term stores and Lesson 49.3 covers entity memory.

</details>
