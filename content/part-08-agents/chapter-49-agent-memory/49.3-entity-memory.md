An agent with entity memory stores what it learns about the people, products and places in a conversation, as facts it can look up by name. In this lesson you will build a small triple store, make a changed fact replace the old one, retrieve facts by hop distance under a fact budget, and measure where name matching goes wrong.

**You need:** the retrieval idea from Lesson 49.2, breadth-first search (a queue that visits neighbours level by level), and Python dictionaries.

## The problem

A vector store (Lesson 49.2) returns text chunks that look similar to the query. That fails on two kinds of question. "What city does Alice live in now?" needs a fact that was updated. "What do Alice's friends like?" needs two facts joined through a shared name.

Entity memory writes each fact as a triple (subject, relation, object) with the turn it was learned. Triples can be followed from one entity to the next, and the store can tell which value of a fact is current. Generative agents keep a complete natural-language record of their experience (Park et al., 2023), but a record of sentences cannot answer a join. Mem0 (Chhikara et al., 2025) also uses graph-based memory; I did not verify its benchmark claims, so this lesson does not use them.

This lesson takes fact extraction as given: the code receives triples and calls no language model, so every number measures the memory mechanism alone. Three problems remain. A changed fact can leave both values in memory (supersession). Two names can refer to one person, or one name to two people (entity resolution). And a graph reaches far more facts than fit in a prompt (retrieval under a budget).

## A worked example

Five events, one per turn:

- Turn 1: Alice lives in Delhi.
- Turn 2: Alice likes Laptop.
- Turn 3: Alice is a friend of Bob.
- Turn 4: Bob likes Phone.
- Turn 5: Alice lives in Mumbai.

The question is "What do Alice's friends like?" The gold answer is the fact (Bob, likes, Phone). The relation lives_in allows one value at a time, so turn 5 supersedes turn 1. Retrieval starts at Alice. Her own live facts sit at hop 0, and Bob's facts sit at hop 1. One hop collects both levels: Mumbai, friend Bob and Laptop at hop 0, plus Bob likes Phone at hop 1. That is 4 facts, 1 of them gold, so precision is 1/4 = 0.25.

![Alice's graph: four solid facts are returned by one-hop retrieval, the Phone fact is the gold answer, and the superseded Delhi fact is dashed](diagrams/49.3-worked-graph.svg "One-hop retrieval from Alice. Solid arrows are returned; the dashed Delhi fact is hidden.")

The code below runs with the standard library alone.

```python
from collections import deque

FUNCTIONAL = {"lives_in"}   # relations with one live value at a time

class Store:
    def __init__(self, supersede):
        self.supersede = supersede
        self.facts = []         # each fact: s, r, o, turn, live

    def add(self, s, r, o, turn):
        if self.supersede and r in FUNCTIONAL:
            for f in self.facts:
                if f["s"] == s and f["r"] == r:
                    f["live"] = False          # keep the history, hide it from retrieval
        self.facts.append({"s": s, "r": r, "o": o, "turn": turn, "live": True})

    def live_facts(self):
        return [f for f in self.facts if f["live"]]

def retrieve(store, start, hops):
    """Live facts whose subject is within `hops` edges of `start`, shallow first, newest first."""
    depth = {start: 0}
    queue = deque([start])
    while queue:
        node = queue.popleft()
        if depth[node] == hops:
            continue
        for f in store.live_facts():
            if f["s"] == node and f["o"] not in depth:
                depth[f["o"]] = depth[node] + 1
                queue.append(f["o"])
    hits = [f for f in store.live_facts() if f["s"] in depth and depth[f["s"]] <= hops]
    return sorted(hits, key=lambda f: (depth[f["s"]], -f["turn"]))

events = [("Alice", "lives_in", "Delhi"), ("Alice", "likes", "Laptop"),
          ("Alice", "friend_of", "Bob"), ("Bob", "likes", "Phone"),
          ("Alice", "lives_in", "Mumbai")]

append_only, supersede = Store(False), Store(True)
for turn, (s, r, o) in enumerate(events, start=1):
    append_only.add(s, r, o, turn)
    supersede.add(s, r, o, turn)

print("lives_in, append-only:", [f["o"] for f in append_only.live_facts() if f["r"] == "lives_in"])
print("lives_in, supersede:  ", [f["o"] for f in supersede.live_facts() if f["r"] == "lives_in"])

got = retrieve(supersede, "Alice", hops=1)
for f in got:
    print(f"{f['s']} {f['r']} {f['o']} (turn {f['turn']})")
gold = {("Bob", "likes", "Phone")}     # what Alice's friends like
hits = gold & {(f["s"], f["r"], f["o"]) for f in got}
print(f"returned {len(got)} facts, gold hits {len(hits)}, precision {len(hits) / len(got):.2f}")
print("append-only 1-hop returns", len(retrieve(append_only, "Alice", hops=1)), "facts")
```

lives_in, supersede:   ['Mumbai']

Alice friend_of Bob (turn 3)

Bob likes Phone (turn 4)

## Supersession: replace, do not append

A relation is functional when a subject can have only one live value of it, such as a home city. A relation is multi-valued when many values can be live at once, such as likes or friend_of. The designer chooses which relations are functional. The store does not infer it.

When a new fact arrives for a functional relation, the store marks the older live facts with the same subject and relation as not live. It keeps them for history but hides them from retrieval. This is the idea behind temporal knowledge graph memory. Zep (Rasmussen et al., 2025) describes a temporally aware knowledge graph that keeps historical relationships. I read only the abstract, so I cannot say how Zep invalidates edges in detail.

![Timeline of Alice's lives_in facts: the Delhi fact is stored from turn 1 to turn 5 but is not live; the Mumbai fact is live from turn 5](diagrams/49.3-supersede-timeline.svg "lives_in for one user. Stored history and live value are different things.")

In a synthetic run of 60 users, 26 moved once. With an append-only store, the old city is in the retrieved context for all 26. With supersession it is in the context for none of them. This measures whether stale facts reach the prompt. It does not measure whether a language model then chooses the newer value.

## Retrieval: hops and budgets

Retrieval is a breadth-first search from the user. A fact belongs to the depth of its subject. Facts whose subject is within h hops are candidates. They are sorted shallow first, newest first, and the first B facts are kept.

The synthetic world has 60 users. Each user has two random friends, and friendship is symmetric, so the average user has about four. Each user likes 3 of 30 products and lives in one of 8 cities. For each user the question is what their friends like, giving 714 gold facts in total.

![Three hop depths for the friends'-likes question, with and without a 20-fact budget; bars show recall and precision](diagrams/49.3-retrieval-bars.svg "Recall and precision of friends'-likes retrieval. Recall is the share of the 714 gold facts returned; precision is the share of returned facts that are gold.")

- **Zero hops:** recall is 0.000 by construction, because friends' facts are never reached. The user has 8.0 facts on average.
- **One hop, no budget:** recall 1.000, precision 0.287, 41.4 facts per user.
- **Two hops, no budget:** recall 1.000, precision 0.083, 143.5 facts per user. Every gold fact is found, but over 90% of what is returned is noise.
- **Budget of 20 facts, one or two hops:** recall 0.259, precision 0.154, in both cases. Shallow facts fill the budget first. Depth 0 holds 8.0 facts per user, leaving 12 slots for depth 1, which holds about 33 facts per user. Depth 2 never gets a slot, so the two rows are identical.

The budget result is a design issue. A fixed budget with shallow-first ordering silently drops deep facts. Ranking by relevance to the question would avoid this; this experiment does not test it.

## Entity resolution: are these the same person?

"A. Rao", "asha rao", "Rao, Asha" and "Asha Rao" may all be the same person. "Asha Roy" is a different person. A string rule has to decide.

The synthetic test set has 40 people. Each contributes one variant: lower case, an initial, a deleted letter (typo) or a reversed name, 10 of each, giving 40 positive pairs. It also has 80 negative pairs: 40 random pairs, 20 pairs that share a last name and 20 that share a first name. The hard negatives are the ones that matter.

Both strings are normalised first: keep only lower-case letters and sort the tokens. That choice makes the reversed name match exactly, so a different normaliser would change that row. The score is `difflib.SequenceMatcher(...).ratio()`, which the Python documentation defines as 2M/T, where M is the number of matching elements and T is the total length of both sequences. A pair is merged when its score is at least a threshold t.

![Recall and precision at five thresholds, with the number of hard negatives merged below each group](diagrams/49.3-resolution-bars.svg "Name matching on 40 positive and 80 negative synthetic pairs. FP is the count of hard negatives merged.")

- **t = 1.0 (exact after normalisation):** recall 0.500, precision 1.000. Lower-case and reversed names match; initials and typos never do.
- **t = 0.9:** recall 0.750, precision 1.000. Typos now match; initials still do not.
- **t = 0.8:** recall 0.825, precision 0.971. One hard negative is merged, and 3 of 10 initials match.
- **t = 0.7:** recall 0.950, precision 0.760. 12 hard negatives are merged.
- **t = 0.6:** recall 1.000, precision 0.667. Every positive matches, but 20 of 40 hard negatives also merge.

Only t = 1.0 and t = 0.9 avoid every hard false merge, and they miss half or a quarter of the variants. t = 0.8 misses 17.5% of the positives and merges one stranger. Character similarity has no idea that "A." stands for "Asha", and a lower threshold merges strangers who share a surname. Production systems add alias tables and context, such as city or employer, before they fall back on string similarity. These 120 pairs were generated by my script, so the numbers show the shape of the trade-off, not accuracy on real names.

"""Lesson 49.3 experiment: entity memory as a triple store.

Stdlib only and seeded. Fact extraction is stubbed (facts come from a generator,
not from an LLM), so every number below measures the memory mechanism alone.
Prints every number the lesson uses and writes 49.3_numbers.json next to this file.

import json
import os
import random
import re
from collections import deque
from itertools import combinations

# ---- 0. Worked example (same code as the lesson's visible block) ----
FUNCTIONAL = {"lives_in"}   # relations with one live value at a time


class Store:
    def __init__(self, supersede):
        self.supersede = supersede
        self.facts = []

    def add(self, s, r, o, turn):
        if self.supersede and r in FUNCTIONAL:
            for f in self.facts:
                if f["s"] == s and f["r"] == r:
                    f["live"] = False          # keep the history, hide it from retrieval
        self.facts.append({"s": s, "r": r, "o": o, "turn": turn, "live": True})

    def live_facts(self):
        return [f for f in self.facts if f["live"]]


def retrieve(store, start, hops):
    depth = {start: 0}
    queue = deque([start])
    while queue:
        node = queue.popleft()
        if depth[node] == hops:
            continue
        for f in store.live_facts():
            if f["s"] == node and f["o"] not in depth:
                depth[f["o"]] = depth[node] + 1
                queue.append(f["o"])
    hits = [f for f in store.live_facts() if f["s"] in depth and depth[f["s"]] <= hops]
    return sorted(hits, key=lambda f: (depth[f["s"]], -f["turn"]))


WORKED = [("Alice", "lives_in", "Delhi"), ("Alice", "likes", "Laptop"),
          ("Alice", "friend_of", "Bob"), ("Bob", "likes", "Phone"),
          ("Alice", "lives_in", "Mumbai")]

    store = Store(supersede)
    for turn, (s, r, o) in enumerate(WORKED, start=1):
        store.add(s, r, o, turn)
    return store


naive_w, sup_w = build_worked(False), build_worked(True)
got_w = retrieve(sup_w, "Alice", hops=1)
gold_w = {("Bob", "likes", "Phone")}          # what Alice's friends like
ret_w = {(f["s"], f["r"], f["o"]) for f in got_w}
worked = {
    "lives_in_append_only": [f["o"] for f in naive_w.live_facts() if f["r"] == "lives_in"],
    "lives_in_supersede": [f["o"] for f in sup_w.live_facts() if f["r"] == "lives_in"],
    "returned_1hop_supersede": len(got_w),
    "returned_1hop_append_only": len(retrieve(naive_w, "Alice", hops=1)),
    "gold_hits": len(gold_w & ret_w),
    "precision_1hop": len(gold_w & ret_w) / len(got_w),
}
print("worked:", worked)
print("worked retrieval order:", [(f["s"], f["r"], f["o"], f["turn"]) for f in got_w])

# ---- 1. Synthetic world: 60 users, 30 products, 8 cities ----
USERS = [f"U{i:02d}" for i in range(60)]
PRODUCTS = [f"P{i:02d}" for i in range(30)]
CITIES = ["Delhi", "Mumbai", "Pune", "Chennai", "Kolkata", "Jaipur", "Lucknow", "Kochi"]

rng = random.Random(49)
friends = {u: set() for u in USERS}
for u in USERS:
    for v in rng.sample([x for x in USERS if x != u], 2):
        friends[u].add(v)
        friends[v].add(u)
likes = {u: rng.sample(PRODUCTS, 3) for u in USERS}
home = {u: rng.choice(CITIES) for u in USERS}
moves = {u: rng.choice([c for c in CITIES if c != home[u]])
         for u in USERS if rng.random() < 0.4}


def stream(supersede):
    store, turn = Store(supersede), 0

    def add(s, r, o):
        nonlocal turn
        turn += 1
        store.add(s, r, o, turn)

    for u in USERS:
        add(u, "lives_in", home[u])
        for p in likes[u]:
            add(u, "likes", p)
        for v in sorted(friends[u]):
            add(u, "friend_of", v)
    for u in USERS:                            # moves arrive after the initial facts
        if u in moves:
            add(u, "lives_in", moves[u])
    return store


naive, sup = stream(False), stream(True)

# ---- 2. Supersession: is the stale city still in the context? ----
def stale_in_context(store):
    return sum(any(f["r"] == "lives_in" and f["o"] == home[u] for f in retrieve(store, u, 0))
               for u in sorted(moves))


supersession = {
    "moved_users": len(moves),
    "stale_in_context_append_only": stale_in_context(naive),
    "stale_in_context_supersede": stale_in_context(sup),
}
print("supersession:", supersession)

# ---- 3. Retrieval: friends' likes, by hop depth and fact budget (micro-averaged) ----
def evaluate(store, hops, budget):
    hit = gold_n = returned = 0
    for u in USERS:
        gold = {(v, "likes", p) for v in friends[u] for p in likes[v]}
        got = retrieve(store, u, hops)
        if budget is not None:
            got = got[:budget]
        ret = {(f["s"], f["r"], f["o"]) for f in got}
        hit += len(gold & ret)
        gold_n += len(gold)
        returned += len(got)
    return {"recall": round(hit / gold_n, 3), "precision": round(hit / returned, 3),
            "facts_per_user": round(returned / len(USERS), 1), "gold_total": gold_n}


retrieval = {f"hops{h}_budget{b if b else 'none'}": evaluate(sup, h, b)
             for h in (0, 1, 2) for b in (None, 20)}
for k, v in retrieval.items():
    print("retrieval", k, v)

# ---- 4. Entity resolution: do name variants merge, and do different people stay apart? ----
FIRST = ["Asha", "Ravi", "Meera", "Arjun", "Nisha", "Kiran", "Vikram", "Anita", "Rohan", "Priya",
         "Sanjay", "Lakshmi", "Dev", "Isha", "Manoj", "Tara", "Suresh", "Gita", "Nikhil", "Divya"]
LAST = ["Rao", "Iyer", "Mehta", "Singh", "Verma", "Nair", "Joshi", "Kapoor", "Reddy", "Shah",
        "Das", "Pillai", "Bose", "Gupta", "Menon", "Sen", "Kumar", "Patel", "Rawat", "Dutta"]

rng = random.Random(49)
people = rng.sample([(f, l) for f in FIRST for l in LAST], 40)
name = lambda p: f"{p[0]} {p[1]}"


def variant(p, kind):
    f, l = p
    if kind == "lower-case":
        return f"{f.lower()} {l.lower()}"
    if kind == "initial":
        return f"{f[0]}. {l}"
    if kind == "typo":                       # delete one letter from the first name
        return (f[:2] + f[3:] if len(f) > 3 else f[:1] + f[2:]) + f" {l}"
    if kind == "reversed":
        return f"{l}, {f}"


KINDS = ["lower-case", "initial", "typo", "reversed"]
pairs = []                                   # (text_a, text_b, same_person, label)
for i, kind in enumerate(KINDS):
    for p in people[10 * i: 10 * i + 10]:
        pairs.append((name(p), variant(p, kind), True, kind))
rand_neg = [tuple(rng.sample(people, 2)) for _ in range(40)]
same_last = [(a, b) for a, b in combinations(people, 2) if a[1] == b[1]]
same_first = [(a, b) for a, b in combinations(people, 2) if a[0] == b[0]]
hard_neg = rng.sample(same_last, 20) + rng.sample(same_first, 20)
for a, b in rand_neg:
    pairs.append((name(a), name(b), False, "random"))
for a, b in hard_neg:
    pairs.append((name(a), name(b), False, "hard"))


def norm(s):                                 # lower-case the letters, sort the tokens
    return " ".join(sorted(re.findall(r"[a-z]+", s.lower())))


def score(a, b):
    return difflib.SequenceMatcher(None, norm(a), norm(b)).ratio()


resolution = {}
for t in (1.0, 0.9, 0.8, 0.7, 0.6):
    tp = sum(1 for a, b, y, _ in pairs if y and score(a, b) >= t)
    fp = sum(1 for a, b, y, _ in pairs if not y and score(a, b) >= t)

                for k in KINDS}
    resolution[str(t)] = {"tp": tp, "fp": fp, "recall": round(tp / 40, 3),
                          "precision": round(tp / (tp + fp), 3) if tp + fp else None,
                          "false_merges_hard": sum(1 for a, b, y, lab in pairs
                                                   if not y and lab == "hard" and score(a, b) >= t),
                          "recall_by_kind": per_kind}

## Common traps

> [!TRAP] Append-only memory feeds stale facts to the model.
> In the synthetic run, every moved user's old city reached the context. Mark functional relations and hide superseded facts from retrieval.

> [!TRAP] Not every relation is functional.
> Marking likes as functional would hide earlier liked products. The schema decides which relations are functional; the store cannot check it.

> [!TRAP] A shallow-first budget hides deep facts without any error.
> With a budget of 20 facts, two-hop and one-hop retrieval returned identical results. Log how many candidate facts were dropped at each budget.

> [!TRAP] A strict name threshold misses variants; a loose one merges strangers.
> At t = 1.0 no initials match, and at t = 0.6 half the hard negatives merge. Measure both recall and false merges on labelled pairs before you pick a threshold.

> [!TRAP] Deleting a user's data means deleting derived state too.
> This is my own reasoning, not a measured result: a summary or a graph index built from deleted facts keeps them alive unless it is rebuilt or purged.

## Summary

- A triple store records facts as (subject, relation, object, turn), so an agent can follow links between entities.
- Functional relations keep one live value; superseded facts stay in storage but are hidden from retrieval.
- The worked example returns 4 facts with precision 0.25; one hop with no budget gives recall 1.000 and precision 0.287 in the synthetic run.
- A 20-fact budget with shallow-first ordering dropped every two-hop fact, so recall fell to 0.259 for both one and two hops.
- String similarity trades recall for false merges: the thresholds that avoid every hard false merge miss at least a quarter of the variants.

## Quiz time

### Question 1: Calculation

In the worked example, how many facts does one-hop retrieval return if the store does not supersede, and what is the precision?

<details><summary>Show solution</summary>

Without supersession the store keeps Delhi and Mumbai, so the one-hop result has 5 facts: Mumbai, Delhi, friend Bob, Laptop and Bob likes Phone. Only Bob likes Phone is gold, so precision is 1/5 = 0.2, down from 0.25 with supersession.

</details>

### Question 2: Prediction

Keep the worked example and set the budget to 2 facts with one hop, taking the first two facts in sorted order. Which facts are returned, and what is recall?

<details><summary>Show solution</summary>

The sort key is (depth, -turn). The hop-0 facts are Mumbai (turn 5), friend Bob (turn 3) and Laptop (turn 2), so the first two are Mumbai and friend Bob. The gold fact (Bob likes Phone) is not returned, so recall is 0 out of 1 gold fact.

</details>

### Question 3: Bug-spotting

A colleague sets `FUNCTIONAL = {"lives_in", "likes"}`. Alice likes Laptop at turn 2 and Phone at turn 6. What does one-hop retrieval return for Alice's likes, and what is wrong?

<details><summary>Show solution</summary>

Only Phone is returned. The Laptop fact is marked not live when the Phone fact arrives, because the store treats likes as having one value at a time. The bug is in the schema, not the store logic: likes is multi-valued and should not be in FUNCTIONAL.

</details>

### Question 4: Calculation

Compute the `difflib` ratio for the normalised strings "a rao" and "asha rao", and say whether a threshold of 0.8 merges them.

<details><summary>Show solution</summary>

The strings have T = 5 + 8 = 13 characters in total. The longest common block is " rao" (4 characters), and the leading "a" matches the "a" of "asha", so M = 5. The ratio is 2 x 5 / 13 = 0.769, which is below 0.8, so t = 0.8 does not merge them. Calling `SequenceMatcher` on these strings returns 0.769.

</details>

### Question 5: Explanation

Why are the one-hop and two-hop rows identical in the budget-20 case?

<details><summary>Show solution</summary>

Facts are sorted shallow first. Depth 0 holds 8.0 facts per user, so only 12 of the 20 slots remain for depth-1 facts, which number about 33 per user. The budget is used up before any depth-2 fact is reached, so the two-hop result equals the one-hop result.
