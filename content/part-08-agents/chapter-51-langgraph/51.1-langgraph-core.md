In this lesson you will describe a multi-step workflow as a LangGraph `StateGraph`: a shared state schema, nodes that return partial updates, normal and conditional edges, and reducers that decide how writes to the same key combine. You will trace one run by hand, rebuild the execution rules in a short standard-library Python engine, and then check the same behaviour with the real library.

**You need:** Python dictionaries, functions and `typing.TypedDict`. No API key or language model is needed; the nodes here are ordinary functions.

## The problem

An agent is a loop: read the state, decide, act, write the result back. Written as nested function calls, the control flow is hidden inside the code, and each step has to know which fields the other steps touch. Two steps that both append to a list also collide: unless you say how their writes combine, one overwrites the other.

LangGraph makes those decisions explicit. You declare the state, name the steps (nodes), declare the edges between them, and the library runs the steps and merges their writes. The example below is a support-ticket triage: a `classify` step picks a branch, and `billing` or `tech` answers the ticket.

## The four parts

- **State** is a schema, a `TypedDict` whose keys every node can read.
- **Nodes** are functions of the form `state -> partial update`. A node returns only the keys it changed. The LangGraph documentation states: "Nodes return partial updates, not the full state."
- **Edges** say what runs next. `START` is the virtual entry point and `END` the terminal. A conditional edge calls a router function; the router returns a key, and a path map turns that key into a node name.
- **Reducers** say how writes to one key combine. A key with no reducer is overwritten (last write wins). `Annotated[list[str], operator.add]` appends instead. `Annotated[T, m]` attaches metadata `m` to a type without changing it (PEP 593).

The schema doubles as documentation: anyone reading the graph can see every field, its type and how it is combined. You build the graph with `add_node`, `add_edge` and `add_conditional_edges`, then call `compile()` to get a runnable object. `invoke(input)` runs it and returns the final state, and `stream(input, stream_mode="updates")` yields each node's partial update as it finishes. The code below uses exactly these calls.

![Triage graph: START goes to classify; a router picks billing or tech; both go to END](diagrams/51.1-triage-graph.svg "Nodes are boxes, edges are arrows. The router reads the state that classify wrote.")

## Worked example by hand

Start with the question "I want a refund for my invoice". The state holds `question`, `log = []`, and `route` is unset.

1. `START` delivers the input to `classify`.
2. `classify` finds "refund" in the text and returns `{"route": "billing", "log": ["classify -> billing"]}`.
3. The merge runs per key (figure below). `route` has no reducer, so the new value replaces the unset one. `log` has `operator.add`, so the new list is appended to `[]`.
4. The router reads `state["route"] == "billing"` and sends the run to `billing`.
5. `billing` returns `{"log": ["billing: refund policy answer"]}`. The reducer appends it, so `log` now has two entries. The edge to `END` ends the run.

The run took two supersteps and produced two log entries. The question "wifi is down" takes the `tech` branch by the same route, with the same two-superstep shape.

Notice what did not happen. `billing` did not touch `route`, and `classify` wrote only the keys it needed. Each node's footprint is the set of keys it returns, which is what makes the graph easy to audit. Before running a graph, write its trace on paper: for each superstep, list the nodes that run, the writes per key, the reducer applied, and the next nodes. If your trace differs from the engine's printed steps, your mental model of the graph is wrong, and that is the bug to find.

![Partial update from classify merged into the state: route is overwritten, log is appended](diagrams/51.1-state-merge.svg "Only the keys a node returns are touched. The reducer on each key decides how they are written.")

## Supersteps: what runs when

LangGraph's documentation calls each round of execution a **superstep**. Our runs show what happens inside one: every node scheduled for the round runs against the same snapshot of the state, and the writes are applied when the round ends. The next nodes are then chosen from the new state. The documentation says that the destinations of a fan-out edge (one node with several outgoing edges) "run in parallel in the next super-step".

![Nodes a and b both start from START, run in superstep 1; join runs in superstep 2](diagrams/51.1-supersteps.svg "Fan-out: a and b read the same snapshot, so neither sees the other's write.")

The engine below implements these rules in standard-library Python. It is a teaching model, not LangGraph's implementation. It runs the triage example, a fan-out, a conflicting write and a sequence of writes.

```python
import functools
import operator

START, END = "__start__", "__end__"


class MiniGraph:
    def __init__(self, reducers=None):
        self.reducers = reducers or {}          # key -> function(old, new) that merges writes
        self.nodes, self.edges, self.routers = {}, {}, {}
        self.entry = []

    def add_node(self, name, fn):
        self.nodes[name] = fn

    def add_edge(self, src, dst):
        if src == START:
            self.entry.append(dst)
        else:
            self.edges.setdefault(src, []).append(dst)

    def add_conditional_edges(self, src, router, path_map):
        self.routers[src] = (router, path_map)

    def invoke(self, state):
        frontier, step = list(self.entry), 0
        while frontier:
            step += 1
            # 1. every node in the frontier reads the same snapshot and returns a partial update
            updates = [(name, self.nodes[name](dict(state))) for name in frontier]
            # 2. group writes by key, then apply them together at the end of the step
            writes = {}
            for name, update in updates:
                for key, value in update.items():
                    writes.setdefault(key, []).append((name, value))
            for key, pairs in writes.items():
                if key in self.reducers:
                    state[key] = functools.reduce(self.reducers[key], [v for _, v in pairs], state[key])
                elif len(pairs) == 1:
                    state[key] = pairs[0][1]
                else:
                    raise ValueError(f"step {step}: nodes {[n for n, _ in pairs]} both wrote {key!r} without a reducer")
            print(f"step {step}: ran {frontier} -> {state}")
            # 3. choose the next frontier from the new state
            nxt = []
            for name in frontier:
                if name in self.routers:
                    router, path_map = self.routers[name]
                    nxt.append(path_map[router(state)])
                else:
                    nxt += self.edges.get(name, [END])
            frontier = [t for t in dict.fromkeys(nxt) if t != END]
        return state


def classify(state):
    q = state["question"]
    route = "billing" if ("refund" in q or "invoice" in q) else "tech"
    return {"route": route, "log": [f"classify -> {route}"]}


def billing(state):
    return {"log": ["billing: refund policy answer"]}


def tech(state):
    return {"log": ["tech: restart answer"]}


def build_triage():
    g = MiniGraph(reducers={"log": operator.add})
    g.add_node("classify", classify)
    g.add_node("billing", billing)
    g.add_node("tech", tech)
    g.add_edge(START, "classify")
    g.add_conditional_edges("classify", lambda s: s["route"], {"billing": "billing", "tech": "tech"})
    g.add_edge("billing", END)
    g.add_edge("tech", END)
    return g


print("--- triage, refund question")
print(build_triage().invoke({"question": "I want a refund for my invoice", "log": []}))
print("--- triage, wifi question")
print(build_triage().invoke({"question": "wifi is down", "log": []}))

print("--- fan-out: a and b run in the same step")
g = MiniGraph(reducers={"log": operator.add})
g.add_node("a", lambda s: {"log": ["a ran"]})
g.add_node("b", lambda s: {"log": ["b ran"]})
g.add_node("join", lambda s: {"n": len(s["log"])})
g.add_edge(START, "a"); g.add_edge(START, "b")
g.add_edge("a", "join"); g.add_edge("b", "join"); g.add_edge("join", END)
print(g.invoke({"n": 0, "log": []}))

print("--- same key written in one step, no reducer")
g = MiniGraph()
g.add_node("a", lambda s: {"x": 1})
g.add_node("b", lambda s: {"x": 2})
g.add_edge(START, "a"); g.add_edge(START, "b")
g.add_edge("a", END); g.add_edge("b", END)
try:
    g.invoke({"x": 0})
except ValueError as err:
    print("ValueError:", err)

print("--- same key written in two steps, no reducer")
g = MiniGraph()
g.add_node("a", lambda s: {"x": s["x"] + 1})
g.add_node("b", lambda s: {"x": s["x"] * 10})
g.add_edge(START, "a"); g.add_edge("a", "b"); g.add_edge("b", END)
print(g.invoke({"x": 0}))
```

```output
--- triage, refund question
step 1: ran ['classify'] -> {'question': 'I want a refund for my invoice', 'log': ['classify -> billing'], 'route': 'billing'}
step 2: ran ['billing'] -> {'question': 'I want a refund for my invoice', 'log': ['classify -> billing', 'billing: refund policy answer'], 'route': 'billing'}
{'question': 'I want a refund for my invoice', 'log': ['classify -> billing', 'billing: refund policy answer'], 'route': 'billing'}
--- triage, wifi question
step 1: ran ['classify'] -> {'question': 'wifi is down', 'log': ['classify -> tech'], 'route': 'tech'}
step 2: ran ['tech'] -> {'question': 'wifi is down', 'log': ['classify -> tech', 'tech: restart answer'], 'route': 'tech'}
{'question': 'wifi is down', 'log': ['classify -> tech', 'tech: restart answer'], 'route': 'tech'}
--- fan-out: a and b run in the same step
step 1: ran ['a', 'b'] -> {'n': 0, 'log': ['a ran', 'b ran']}
step 2: ran ['join'] -> {'n': 2, 'log': ['a ran', 'b ran']}
{'n': 2, 'log': ['a ran', 'b ran']}
--- same key written in one step, no reducer
ValueError: step 1: nodes ['a', 'b'] both wrote 'x' without a reducer
--- same key written in two steps, no reducer
step 1: ran ['a'] -> {'x': 1}
step 2: ran ['b'] -> {'x': 10}
{'x': 10}
```

The engine prints keys in the order they were first written, so `route` appears after `log`. LangGraph keeps the schema's order. The values agree.

Read the trace. Step 1 runs `['a', 'b']` together, and `join` appears only in step 2, after both of their writes have been merged. In the refund run, the router chooses the branch after `classify`'s writes are merged, so `route` is already set when the router reads it. The engine applies the reducers, then computes the next frontier, in that order.

## Conflicts: when two writes meet

The fan-out above worked because `log` has a reducer. Remove it, and the same shape fails. Two nodes writing `x` in one superstep give the engine no rule for choosing a value, so it refuses. The same key written in two different supersteps is fine: the second write simply overwrites the first.

![Left: two nodes write x in one step with no reducer, which fails. Right: operator.add merges both lists](diagrams/51.1-same-key.svg "Conflicts happen within a superstep. Across supersteps, the last write wins.")

LangGraph does the same thing for real. The library is needed to reproduce its exact error, so it is shown below.

<details><summary>Run locally: needs pip install langgraph</summary>

```python
import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END


class TicketState(TypedDict):
    question: str
    route: str
    log: Annotated[list[str], operator.add]


def classify(state: TicketState) -> dict:
    route = "billing" if ("refund" in state["question"] or "invoice" in state["question"]) else "tech"
    return {"route": route, "log": [f"classify -> {route}"]}


def billing(state: TicketState) -> dict:
    return {"log": ["billing: refund policy answer"]}


def tech(state: TicketState) -> dict:
    return {"log": ["tech: restart answer"]}


builder = StateGraph(TicketState)
builder.add_node("classify", classify)
builder.add_node("billing", billing)
builder.add_node("tech", tech)
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", lambda s: s["route"], {"billing": "billing", "tech": "tech"})
builder.add_edge("billing", END)
builder.add_edge("tech", END)
graph = builder.compile()

print(graph.invoke({"question": "I want a refund for my invoice", "log": []}))
for update in graph.stream({"question": "wifi is down", "log": []}, stream_mode="updates"):
    print(update)


class XState(TypedDict):
    x: int


conflict = StateGraph(XState)
conflict.add_node("a", lambda s: {"x": 1})
conflict.add_node("b", lambda s: {"x": 2})
conflict.add_edge(START, "a"); conflict.add_edge(START, "b")
conflict.add_edge("a", END); conflict.add_edge("b", END)
try:
    conflict.compile().invoke({"x": 0})
except Exception as err:
    print(type(err).__name__, str(err).splitlines()[0])

bad = StateGraph(XState)
bad.add_node("a", lambda s: {"y": 1})
bad.add_edge(START, "a"); bad.add_edge("a", END)
print(bad.compile().invoke({"x": 0}))
```

```output
{'question': 'I want a refund for my invoice', 'route': 'billing', 'log': ['classify -> billing', 'billing: refund policy answer']}
{'classify': {'route': 'tech', 'log': ['classify -> tech']}}
{'tech': {'log': ['tech: restart answer']}}
InvalidUpdateError At key 'x': Can receive only one value per step. Use an Annotated key to handle multiple values.
{'x': 0}
```

Output from langgraph 1.2.24 (Python 3.12). The `stream` lines show each node's partial update, not the merged state. The last line is discussed in the traps below.

</details>

Why an error rather than a silent choice? Any rule that keeps one value, the first, the last, or whichever node finished first, would depend on an ordering the graph does not define. The library's troubleshooting page calls this "uncertainty around how to update the internal state" and recommends a reducer for keys that parallel nodes write. The fix is a decision about the data, such as "append" or "sum", and only you can make it.

Lesson 51.2 builds on this with conditional routing, cycles and subgraphs, and lesson 51.3 covers checkpointers (saving and restoring state) and human-in-the-loop pauses.

## Common traps

> [!TRAP]
> **Forgetting the reducer on a list you append to.** With no reducer, the documentation says "updates overwrite the previous value". Without `operator.add`, the triage `log` would hold only the last node's entry, not both.

> [!TRAP]
> **Parallel writes to a key with no reducer.** Two nodes in the same superstep that write one key raise `InvalidUpdateError` in langgraph 1.2.24. Give the key a reducer, or let only one node write it.

> [!TRAP]
> **A typo in a state key can be silent.** In our run, a node that returned `{"y": 1}` for a schema with only `x` produced `{'x': 0}`, with no error. Check the output keys of every run while you build a graph.

> [!TRAP]
> **Reading `stream` output as state.** `stream_mode="updates"` yields each node's partial update, not the state after the merge. Use `invoke` for the final state.

## Summary

- A `StateGraph` is a schema (the state), nodes (functions that return partial updates), and edges (normal or conditional).
- Each key's reducer decides how writes combine. No reducer means last write wins; `Annotated[..., operator.add]` appends.
- A run proceeds in supersteps. In our runs, nodes in one superstep read the same snapshot, and their writes are applied together at the end.
- Two writes to one key in one superstep need a reducer. Otherwise the run fails.

## Quiz time

### Question 1: Prediction

The fan-out graph (START to `a` and `b`, both to `join`, then `END`) starts with `n = 0` and `log = []`, and `log` has `operator.add`. How many supersteps does it take, and what is the final `n`?

<details><summary>Show solution</summary>

Two supersteps. Superstep 1 runs `a` and `b`, so `log` becomes `['a ran', 'b ran']`. Superstep 2 runs `join`, which sets `n = len(log) = 2`. The engine output above shows exactly this.
</details>

### Question 2: Bug-spotting

A graph has `x: int` in its schema (no reducer), and nodes `a` and `b` both start from `START` and both write `x`. What happens, and how would you fix it?

<details><summary>Show solution</summary>

In langgraph 1.2.24 the run raises `InvalidUpdateError` ("Can receive only one value per step"), because `a` and `b` write `x` in the same superstep. Fix it in one of two ways: give `x` a reducer that combines the two values, or make only one node write `x`.
</details>

### Question 3: Calculation

The state has `x = 3` and no reducers. Node `a` sets `x = x + 2`, and node `b` runs after `a` and sets `x = x * 3`. What is the final `x`?

<details><summary>Show solution</summary>

Superstep 1: `a` gives `3 + 2 = 5`. Superstep 2: `b` gives `5 * 3 = 15`. The final value is 15. Because the two writes are in different supersteps, there is no conflict.
</details>

### Question 4: Explanation

Why should `classify` return `{"route": ..., "log": [...]}` rather than the whole state dictionary?

<details><summary>Show solution</summary>

A partial update lets each reducer see only the keys the node changed. If `classify` returned the whole old state, its old `log` entries would be sent to the `operator.add` reducer again and duplicated. This is my own reasoning from how the reducer is applied; the mini engine shows that each key's write goes through its reducer once.
</details>
