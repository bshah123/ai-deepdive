In this lesson you will pause a LangGraph run until a person answers, resume it on the same thread, and rewind it to an earlier checkpoint to see what happens on a different branch. You will also learn the rule that catches most people: a paused node runs again from its first line when it resumes.

**You need:** `StateGraph`, nodes and conditional edges (Lessons 51.1 and 51.2), and the idea that state is a dictionary. The first code block uses only the standard library. The LangGraph block is optional and runs locally.

## The problem this solves

An agent that can publish a post or send a payment should not run unchecked to the end. It must stop before the risky step, wait for a person (perhaps for hours), and then continue from the same place. Two mechanisms make this work. An **interrupt** pauses a run inside a node and hands a value to the caller. A **checkpointer** saves the state at each step, keyed by a **thread ID**, the name of one run. The same saved history supports **time travel**: you choose an earlier checkpoint and run again from it, which is how you debug what an agent did.

LangGraph's `interrupt()` accepts any JSON-serializable value and passes it to the caller (LangGraph "Interrupts" documentation). Plain strings and dictionaries meet that condition, so every value in this lesson is one.

## Intuition: a pause is a saved checkpoint

Our example has three nodes. `draft` writes a post, `approve` asks a person, and `send` publishes the post.

![Four boxes in a row, draft, approve, a dashed human box, and approve again, then send; captions show how many times each ran](diagrams/51.3-pause-resume.svg "A pause saves a checkpoint. The resume reruns approve from its first line and gets the human's answer back.")

When `approve` calls `interrupt()`, LangGraph saves the state, records `approve` as the next node, and returns the question to the caller. Later, the caller resumes with `Command(resume="yes")` on the same thread. LangGraph runs `approve` again from its first line, and `interrupt()` now returns `"yes"` instead of pausing.

## Worked example by hand

Trace the run with those rules.

1. The input `{"topic": "LangGraph"}` starts the run. `draft` runs once and sets `draft` to "Post about LangGraph". A checkpoint now says the next node is `approve`.
2. `approve` runs (count 1) and calls `interrupt()`. The run pauses, and nothing else runs.
3. The caller resumes with "yes". `approve` runs again from its first line (count 2). `interrupt()` returns "yes", so `approved` becomes `True`. The route sends the run to `send`, which runs once.

After the run, the counts are draft 1, approve 2 and send 1. The plan entered `approve` once, but its first line ran twice. Any side effect before `interrupt()` runs again on every resume.

The LangGraph "Interrupts" documentation states the rule: "the runtime restarts the entire node from the beginning". Our counts agree with it.

## The mechanism in standard-library Python

The engine below stores each checkpoint as a dictionary holding the state and the index of the next node. A pause raises an exception, and a resume reruns the paused node. A fork copies an old checkpoint and appends the copy, so the old checkpoints stay. This is a teaching model, not LangGraph's code. It runs in the browser.

The pause needs no waiting process. The run's state lives in the checkpoint list, not in a call stack. When `ask()` raises, the function returns and nothing keeps waiting. A resume is a new call that reads the newest checkpoint, so a pause can last for days without holding a process open. This follows from the design, and the engine demonstrates it, but it does not measure durability.

```python
class Interrupt(Exception):
    """Raised by ask() to pause the run. Carries the value shown to the human."""
    def __init__(self, value):
        self.value = value

class MiniGraph:
    def __init__(self, nodes):
        self.nodes = nodes                 # ordered list of (name, function(state, ask))
        self.history = {}                  # thread_id -> list of checkpoints, oldest first

    def run(self, thread, inp=None, resume=None):
        hist = self.history.setdefault(thread, [])
        if inp is not None:                # a fresh input starts a new checkpoint
            hist.append({"state": dict(inp), "next": 0})
        cp = hist[-1]                      # always continue from the newest checkpoint
        state, i = dict(cp["state"]), cp["next"]
        while i < len(self.nodes):
            name, fn = self.nodes[i]
            def ask(value):
                if resume is None:
                    raise Interrupt(value)
                return resume              # on resume, ask() returns the human's answer
            try:
                update = fn(state, ask)
            except Interrupt as pause:     # no new checkpoint: the newest one already waits at this node
                return {"paused_at": name, "question": pause.value}
            state.update(update)
            i += 1
            resume = None
            hist.append({"state": dict(state), "next": i})
        return {"done": True, "state": state}

    def fork(self, thread, index, **edits):
        """Copy checkpoint `index`, apply edits, and append it as the newest checkpoint.
        Older checkpoints are kept, so the original branch is still there."""
        old = self.history[thread][index]
        new = {"state": {**old["state"], **edits}, "next": old["next"]}
        self.history[thread].append(new)
        return new

calls = {"draft": 0, "approve": 0, "send": 0}

def draft(state, ask):
    calls["draft"] += 1
    return {"draft": "Post about " + state["topic"]}

def approve(state, ask):
    calls["approve"] += 1                  # side effect before ask(): runs again on resume
    answer = ask({"question": "Approve?", "draft": state["draft"]})
    return {"approved": answer == "yes"}

def send(state, ask):
    if state["approved"]:                  # stands in for the conditional edge to END
        calls["send"] += 1
    return {}

g = MiniGraph([("draft", draft), ("approve", approve), ("send", send)])
t = "t1"
print("1. run:", g.run(t, inp={"topic": "LangGraph"}), calls)
print("2. resume:", g.run(t, resume="yes"), calls)
for n, cp in enumerate(g.history[t]):
    print("   checkpoint", n, "next =", cp["next"], "draft =", cp["state"].get("draft"))
g.fork(t, 1, draft="Edited draft")      # index 1 = waiting at approve
print("3. fork + run:", g.run(t), calls)
print("4. resume fork:", g.run(t, resume="no"), calls)
print("   checkpoints:", len(g.history[t]), "| checkpoint 1 draft kept:", g.history[t][1]["state"]["draft"])
```

4. resume fork: {'done': True, 'state': {'topic': 'LangGraph', 'draft': 'Edited draft', 'approved': False}} {'draft': 1, 'approve': 4, 'send': 1}

Read the output in order. Line 1 shows the pause, with `approve` counted once. Line 2 shows the resume, where `approve` is counted again. The checkpoint lines show one checkpoint per step. Line 3 forks from checkpoint 1, the one waiting at `approve`, and the new branch pauses again. Line 4 resumes the fork with "no", so `send` does not run. The old checkpoints are still in the list.

## The same graph in LangGraph

The code below is the same graph built with LangGraph 1.2.24, with `interrupt`, `Command`, `InMemorySaver` and `update_state`. Only the wiring differs from the engine above. The node bodies are the same, the conditional edge is a function that returns a node name, and the checkpointer is passed to `compile()`. The output was produced with langgraph 1.2.24; other versions may print different text.

<details><summary>Run locally: needs pip install langgraph (run with langgraph 1.2.24)</summary>

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
import importlib.metadata as md

calls = {"draft": 0, "approve": 0, "send": 0}

class State(TypedDict):
    topic: str
    draft: str
    approved: bool

def draft(state):
    calls["draft"] += 1
    return {"draft": "Post about " + state["topic"]}

def approve(state):
    calls["approve"] += 1                  # side effect before interrupt(): runs again on resume
    answer = interrupt({"question": "Approve?", "draft": state["draft"]})
    return {"approved": answer == "yes"}

def send(state):
    calls["send"] += 1
    return {}

b = StateGraph(State)
b.add_node("draft", draft)
b.add_node("approve", approve)
b.add_node("send", send)
b.add_edge(START, "draft")
b.add_edge("draft", "approve")
b.add_conditional_edges("approve", lambda s: "send" if s["approved"] else END)
b.add_edge("send", END)
graph = b.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "t1"}}

print("langgraph", md.version("langgraph"))
r1 = graph.invoke({"topic": "LangGraph"}, cfg)
print("1. paused with", r1["__interrupt__"][0].value, "| next =", graph.get_state(cfg).next, calls)
r2 = graph.invoke(Command(resume="yes"), cfg)
print("2. resumed: approved =", r2["approved"], "|", calls)

hist = list(graph.get_state_history(cfg))            # newest first
for h in hist:
    print("   step", h.metadata["step"], "next =", list(h.next), "draft =", h.values.get("draft"))
before_approve = [h for h in hist if h.next == ("approve",)][0]
new_cfg = graph.update_state(before_approve.config, {"draft": "Edited draft"})
r3 = graph.invoke(None, new_cfg)                     # runs approve again on the new branch
print("3. fork paused with", r3["__interrupt__"][0].value["draft"], "|", calls)
r4 = graph.invoke(Command(resume="no"), cfg)
print("4. fork resumed: approved =", r4["approved"], "|", calls)
print("   checkpoints:", len(list(graph.get_state_history(cfg))), "| original final draft kept:",
      [h.values["draft"] for h in graph.get_state_history(cfg) if h.metadata["step"] == 3][-1])
```

2. resumed: approved = True | {'draft': 1, 'approve': 2, 'send': 1}
   step 3 next = [] draft = Post about LangGraph
   step 2 next = ['send'] draft = Post about LangGraph
   step 1 next = ['approve'] draft = Post about LangGraph
   step 0 next = ['draft'] draft = None
   step -1 next = ['__start__'] draft = None
3. fork paused with Edited draft | {'draft': 1, 'approve': 3, 'send': 1}
4. fork resumed: approved = False | {'draft': 1, 'approve': 4, 'send': 1}

The history is listed newest first. LangGraph counts the input as step -1, so there are five checkpoints before any fork. Step numbers are not identifiers. After the fork, steps 2 and 3 appear on both branches, so use the checkpoint's `config` (which holds its `checkpoint_id`) to tell them apart.

Time travel works like this. Calling `update_state` on the checkpoint whose next node is `approve` writes a new checkpoint with the edited draft. The LangGraph "Use time travel" documentation says it "creates a new checkpoint that branches from the specified point" and that "the original execution history remains intact." Running the new branch pauses at `approve` again, so approve's count goes to 3. Resuming with "no" finishes the run without `send`. The checkpoint count goes from 5 to 7, and the original final draft is still "Post about LangGraph".

## Common traps

> [!TRAP]
> **Side effects before `interrupt()` run again.** Our `approve` node increments a counter before it pauses, and the counter reached 2. In real code, that line might charge a card or send an email. Move it after the interrupt into a later node, or make it idempotent (safe to repeat). The LangGraph documentation says side effects before an interrupt "should (ideally) be idempotent."

> [!TRAP]
> **An in-memory checkpointer does not survive a restart.** `InMemorySaver` keeps checkpoints in RAM. If the process stops during a three-day approval, the paused run is gone. The LangGraph persistence documentation recommends a persistent checkpointer for production and names PostgresSaver and SqliteSaver as options.

> [!TRAP]
> **Keep one thread ID per run.** Checkpoints are kept per thread, and a resume finds its pending interrupt through the thread ID in the config.

> [!TRAP]
> **Replay repeats the work after the checkpoint.** Every node after the chosen checkpoint runs again, including LLM calls and API requests, so the results can differ. A checkpoint with no pending node replays as a no-op, according to the "Use time travel" documentation.

> [!TRAP]
> **Step numbers are not branch IDs.** The history after the fork lists steps 2 and 3 twice. Select checkpoints by their `config` or `checkpoint_id`, not by step number.

## Summary

- An interrupt pauses a node and returns a value. `Command(resume=...)` makes that value the return value of `interrupt()`.
- The paused node runs again from its first line on resume, so keep side effects after the interrupt.
- A checkpointer saves state per thread. The history is a list you can walk, newest first.
- A fork from an old checkpoint adds a new branch and keeps the original history.
- Use a persistent checkpointer for any pause longer than one process lifetime.

## Quiz time

### Question 1: Predict the output

The `approve` node in the standard-library engine prints "approve ran" before it calls `ask()`. A run pauses once and then resumes once. How many times does "approve ran" print?

<details><summary>Show Solution</summary>

Twice. The first run prints it before the pause. The resume runs `approve` again from its first line, so it prints again. Nothing in the second run skips the first line.

</details>

### Question 2: Calculation

The LangGraph run in this lesson has 5 checkpoints before any fork. One fork with `update_state` and one resume bring the history to 7. Where do the 2 new checkpoints come from?

<details><summary>Show Solution</summary>

The `update_state` call writes one checkpoint on the new branch, at step 2 with the edited draft and `approve` as the next node. The resume with "no" writes the final checkpoint on that branch, at step 3 with no next node. The pause in between writes nothing. The output shows this as two entries with draft "Edited draft".

</details>

### Question 3: Find the bug

```python
def approve(state):
    receipt = charge_card(state["amount"])       # a real payment
    answer = interrupt("Approve charge?")
    return {"approved": answer == "yes", "receipt": receipt}
```

<details><summary>Show Solution</summary>

The charge runs before the interrupt, so every resume charges the card again, including when the person answers "no". Move the charge into a node after `approve`, reached only when `approved` is true, through a conditional edge like the `lambda` in the lesson's `add_conditional_edges` call.

</details>

### Question 4: Explain

Why is `InMemorySaver` unsuitable for an approval that may take three days?

<details><summary>Show Solution</summary>

`InMemorySaver` keeps checkpoints in the memory of one process. A restart during the wait deletes them, so the resume has nothing to continue from. A persistent checkpointer stores the same thread history outside the process, so the resume can find it under the same thread ID.

</details>
