# 51.2 — Conditional Routing, Subgraphs & Cyclic State Machines

## Opening Motivation & Context

Conditional routing, subgraphs, and cyclic state machines are fundamental concepts in the design and implementation of autonomous agents and tool calling systems. These concepts allow for more complex and flexible workflows, enabling systems to make decisions based on the current state and context, and to handle loops and cycles in the state machine.

In this lesson, we will explore these concepts in the context of LangGraph, a library for building state machines and workflows. We will learn how to create conditional routes, define subgraphs, and implement cyclic state machines. These concepts are crucial for building robust and scalable autonomous agents that can handle complex tasks and adapt to changing conditions.

## Core Concepts Breakdown

### Conditional Routing

Conditional routing allows a state machine to transition to different states based on certain conditions. This is achieved by defining a router function that evaluates the current state and returns the next state based on the conditions.

> [!KEY-INSIGHT]
> Conditional routing enables state machines to make decisions based on the current state and context, allowing for more dynamic and flexible workflows.

> [!BEST-PRACTICE]
> When designing conditional routes, ensure that all possible conditions are covered to avoid unexpected behavior. Use clear and concise conditions to make the state machine easier to understand and maintain.

> [!WARNING]
> Be careful when defining conditions that can lead to infinite loops or cycles. Ensure that the state machine can eventually reach a terminal state to avoid infinite execution.

### Subgraphs

Subgraphs are smaller, self-contained state machines that can be integrated into a larger state machine. They allow for modular design, where complex workflows can be broken down into smaller, manageable components.

> [!KEY-INSIGHT]
> Subgraphs promote modular design and code reuse, making state machines easier to understand, maintain, and extend.

> [!BEST-PRACTICE]
> When defining subgraphs, ensure that they are self-contained and can operate independently. This makes it easier to integrate them into larger state machines and reuse them in other projects.

> [!WARNING]
> Be careful when integrating subgraphs into larger state machines. Ensure that the subgraphs do not interfere with each other and that the overall state machine behaves as expected.

### Cyclic State Machines

Cyclic state machines are state machines that can transition back to previous states, creating loops or cycles. This allows for more complex workflows that can handle iterative processes and feedback loops.

> [!KEY-INSIGHT]
> Cyclic state machines enable the implementation of iterative processes and feedback loops, making them suitable for tasks that require repeated execution or adaptation.

> [!BEST-PRACTICE]
> When designing cyclic state machines, ensure that the conditions for transitioning back to previous states are well-defined and that the state machine can eventually reach a terminal state to avoid infinite execution.

> [!WARNING]
> Be careful when implementing cyclic state machines, as they can lead to infinite loops if not designed properly. Ensure that the state machine can eventually reach a terminal state to avoid infinite execution.

## Code Demonstration & Runtime Output

Let's start by importing the necessary libraries and defining the state machine.

```python
from typing import Dict, TypedDict, Annotated, Literal
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]
    next: str

def router(state: State) -> Literal["action_1", "action_2", "end"]:
    if state["messages"][-1].content == "action_1":
        return "action_1"
    elif state["messages"][-1].content == "action_2":
        return "action_2"
    else:
        return "end"

def action_1(state: State) -> Dict:
    return {"messages": [{"content": "Action 1 executed", "type": "ai"}], "next": "action_2"}

def action_2(state: State) -> Dict:
    return {"messages": [{"content": "Action 2 executed", "type": "ai"}], "next": "end"}

def end(state: State) -> Dict:
    return {"messages": [{"content": "Workflow completed", "type": "ai"}], "next": END}

workflow = StateGraph(State)
workflow.add_node("action_1", action_1)
workflow.add_node("action_2", action_2)
workflow.add_node("end", end)
workflow.add_conditional_edges("action_1", router, {"action_1": "action_1", "action_2": "action_2", "end": "end"})
workflow.add_conditional_edges("action_2", router, {"action_1": "action_1", "action_2": "action_2", "end": "end"})
workflow.set_entry_point("action_1")

app = workflow.compile()

if __name__ == "__main__":
    inputs = {"messages": [{"content": "action_1", "type": "human"}]}
    for output in app.stream(inputs):
        for key, value in output.items():
            print(f"Node '{key}':")
            print(value)
```

Node 'end':

### How this works (Line-by-Line Breakdown)

1. **Imports**: We import the necessary libraries and modules, including `Dict`, `TypedDict`, `Annotated`, `Literal` from the `typing` module, and `StateGraph`, `END` from `langgraph.graph`, and `add_messages` from `langgraph.graph.message`.
2. **State Definition**: We define the `State` class as a `TypedDict` with two keys: `messages` and `next`. The `messages` key is annotated with `add_messages` to handle message accumulation, and the `next` key is used to specify the next state.
3. **Router Function**: The `router` function evaluates the current state and returns the next state based on the conditions. If the last message content is "action_1", it returns "action_1". If the last message content is "action_2", it returns "action_2". Otherwise, it returns "end".
4. **Action Functions**: The `action_1` and `action_2` functions execute the corresponding actions and return the updated state with the next state set to "action_2" and "end", respectively.
5. **End Function**: The `end` function marks the end of the workflow and returns the updated state with the next state set to `END`.
6. **Workflow Definition**: We create a `StateGraph` instance and add the nodes for the actions and the end state. We add conditional edges from the actions to the router, specifying the possible transitions. We set the entry point to "action_1".
7. **Compilation**: We compile the workflow to create the executable application.
8. **Execution**: In the `__main__` block, we define the initial inputs and stream the outputs of the application. We print the outputs for each node in the workflow.

> [!ADVANCED]
> The `StateGraph` class uses a directed graph data structure to represent the state machine. Each node in the graph represents a state or action, and the edges represent the transitions between states. The `add_conditional_edges` method allows for conditional transitions based on the current state, enabling the implementation of complex workflows.

> [!QA]
> Q: When should I prefer conditional routing over direct transitions?
> A: Conditional routing is useful when the next state depends on the current state or context. It allows for more dynamic and flexible workflows, where the transitions can be determined at runtime. Direct transitions are simpler and more straightforward but lack the flexibility of conditional routing.
