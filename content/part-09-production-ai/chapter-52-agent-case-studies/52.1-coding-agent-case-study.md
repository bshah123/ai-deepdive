A coding agent is a loop around a language model: the model reads what its tools return, chooses the next tool call, and stops when the tests pass. In this lesson you will build the tool layer and the loop for a toy repository, measure two costs that decide whether such an agent works, and check the design against the rules of a published benchmark.

**You need:** function calling and the tool loop (Lesson 47.2), and exception types (Lesson 12.1).

## The problem a coding agent solves

A language model turns text into text. It cannot open a file, run a test suite or read a stack trace unless a program puts that text in front of it. Repository tasks are harder than single functions: a bug report may need edits in three files and a test run over the whole package.

SWE-bench (Jimenez et al., 2023) turns this into a measurable task. A model receives a Python repository and a GitHub issue, and must produce a patch. The benchmark has 2,294 task instances drawn from 12 popular Python repositories. A patch counts as resolved only if it applies and every test passes. The tests come in two groups. FAIL_TO_PASS tests fail before the patch and pass after it, so they check that the issue is fixed. PASS_TO_PASS tests pass both before and after, so they check that nothing else broke.

Three things are therefore needed: a way to act (tools), a way to observe the result (tool output goes back into the context), and a stop rule that does not rely on the model's own opinion (the tests).

## Intuition: the loop

![Model proposes one tool call, the tool layer validates and runs it against the repository, and the observation returns to the context; the loop stops when all tests pass or the budget runs out](diagrams/52.1-agent-loop.svg "The agent loop. The model never touches the repository directly; the tool layer sits between them.")

The picture has two consequences. First, every observation is added to the context, so the context grows at each step and the model pays for everything it has seen. Second, the tool layer is the only place where a bad action can be caught cheaply. A wrong edit that the tool layer refuses costs one step. A wrong edit that reaches the repository costs every later step that has to recover from it.

## The tool interface is part of the agent

SWE-agent (Yang et al., 2024) calls this tool layer an agent-computer interface (ACI) and argues that its design changes results. Its file viewer shows at most 100 lines per call. Its search commands return at most 50 results, and above that they ask the agent for a narrower query. Its edit command runs a subset of the flake8 linter and discards an invalid edit, returning the error and a preview of the file to the agent (SWE-agent, Section 3 and Appendix A.1, arXiv HTML v3). In the paper's ablation, removing the linter lowered resolution from 18.0% to 15.0% on its benchmark setting. That is one system in one version of the paper, not a general law.

![Table of four agent tools, view, search, edit and run_tests, with what each returns and the guard it applies](diagrams/52.1-tool-interface.svg "The four tools and their guards. The model sees only what these limits allow.")

The toy agent below copies the three guards: a 100-line viewer window, a 50-result search cap, and an edit that is refused unless its old text matches exactly once and the result still compiles.

## Worked example by hand

The toy repository has one bug. `median` returns `s[mid] + 1` for odd-length lists, so the test `median([3, 1, 2]) == 2` should fail. Work it by hand: the sorted list is `[1, 2, 3]`, `len(s)` is 3, `mid` is 1, the odd branch returns `s[1] + 1 = 2 + 1 = 3`, and 3 is not 2. The even-length test passes: `median([1, 2, 3, 4])` gives `(s[1] + s[2]) / 2 = (2 + 3) / 2 = 2.5`.

The code below replaces the language model with a fixed script of seven tool calls, two of which are mistakes on purpose. The script is a stand-in; the tool layer and the loop are the parts being taught. Each block is standalone and runs in the browser.

```python
# A toy repository: file name -> source text. Stands in for a git checkout.
REPO = {
    "stats.py": (
        "def mean(xs):\n"
        "    return sum(xs) / len(xs)\n"
        "\n"
        "def median(xs):\n"
        "    s = sorted(xs)\n"
        "    mid = len(s) // 2\n"
        "    if len(s) % 2 == 0:\n"
        "        return (s[mid - 1] + s[mid]) / 2\n"
        "    return s[mid] + 1\n"
    ),
    # Tests run in the same namespace as stats.py, so no import line is needed.
    "test_stats.py": (
        "def test_mean():\n"
        "    assert mean([1, 2, 3]) == 2\n"
        "\n"
        "def test_median_odd():\n"
        "    assert median([3, 1, 2]) == 2\n"
        "\n"
        "def test_median_even():\n"
        "    assert median([1, 2, 3, 4]) == 2.5\n"
    ),
}

WINDOW = 100      # max lines the viewer shows per call
SEARCH_CAP = 50   # above this many hits, report a count and ask for a narrower query


def view(path, start=1):
    chunk = REPO[path].splitlines()[start - 1:start - 1 + WINDOW]
    return "\n".join(f"{i:3d} {line}" for i, line in enumerate(chunk, start))


def search(term):
    hits = [f"{p}:{i}: {line}"
            for p, src in REPO.items()
            for i, line in enumerate(src.splitlines(), 1) if term in line]
    if len(hits) > SEARCH_CAP:
        return f"{len(hits)} matches; refine the query"
    return "\n".join(hits) or "no matches"


def edit(path, old, new):
    count = REPO[path].count(old)
    if count != 1:                      # exact-replace must be unambiguous
        return f"error: old text matches {count} times; it must match exactly once"
    candidate = REPO[path].replace(old, new)
    try:
        compile(candidate, path, "exec")  # cheap syntax gate before the file is changed
    except SyntaxError as e:
        return f"error: edit rejected, SyntaxError on line {e.lineno}: {e.msg}"
    REPO[path] = candidate
    return "edit applied"


def run_tests():
    ns = {}
    try:
        exec(REPO["stats.py"], ns)
        exec(REPO["test_stats.py"], ns)
    except Exception as e:
        return f"error while loading: {type(e).__name__}"
    results = []
    for name in sorted(k for k in ns if k.startswith("test_")):
        try:
            ns[name]()
            results.append(f"{name} PASS")
        except AssertionError:
            results.append(f"{name} FAIL")
        except Exception as e:
            results.append(f"{name} ERROR {type(e).__name__}")
    failed = sum(1 for r in results if not r.endswith("PASS"))
    return "\n".join(results) + f"\n{len(results) - failed} passed, {failed} failed"


TOOLS = {
    "search": lambda a: search(a),
    "view": lambda a: view(a),
    "edit": lambda a: edit(*a),
    "run_tests": lambda a: run_tests(),
}

# Scripted stand-in for the model: a fixed sequence of tool calls, including two mistakes.
SCRIPT = [
    ("search", "median"),
    ("view", "stats.py"),
    ("edit", ("stats.py", "return", "return")),                  # mistake 1: not unique
    ("edit", ("stats.py", "return s[mid] + 1", "return s[mid] + ")),  # mistake 2: syntax
    ("run_tests", None),
    ("edit", ("stats.py", "return s[mid] + 1", "return s[mid]")),
    ("run_tests", None),
]


def agent(script, max_steps=8):
    for step, (tool, args) in enumerate(script[:max_steps], 1):
        obs = TOOLS[tool](args)
        print(f"[{step}] {tool}({'' if args is None else repr(args)})")
        print("    " + obs.replace("\n", "\n    "))
        if tool == "run_tests" and obs.endswith("0 failed"):
            print("stop: all tests pass")
            return True
    print(f"stop: step budget of {max_steps} exhausted")
    return False


agent(SCRIPT)
```

Read the trace. Step 3 is refused because `return` occurs three times, so a plain string replace would have edited the wrong lines. Step 4 is refused by `compile()`, which catches the syntax error before the file is written, so `stats.py` is unchanged. Step 5 shows the real failure, and steps 6 and 7 fix it and stop the loop at the first run where every test passes.

> [!WARNING]
> `run_tests` calls `exec` on the repository's code inside this Python process. That is acceptable for a teaching example and dangerous for real repositories. A production agent runs tests in a container with no credentials and no network access, because the code it runs was written by a model.

## Measuring the costs

Two numbers decide much of the design. The first is how fast the context fills. The second is how often a text-matching edit is ambiguous. A third number, how the success rate grows with retries, sets the budget. Each comes from the local experiment below, run on the CPython 3.12.13 standard library, a set of real files. Re-running on another Python version changes the file sizes but not the mechanism.

<details><summary>Run locally: reads your CPython standard library files (no pip install)</summary>

```python
import sysconfig, os, random, math, collections, sys
STD = sysconfig.get_paths()['stdlib']
FILES = ['json/decoder.py', 'json/encoder.py', 'json/scanner.py', 'argparse.py', 'dataclasses.py', 'pathlib.py']
WINDOW = 100  # SWE-agent file viewer window (lines)
print('python', sys.version.split()[0])

# E1: context cost of a whole-file view versus one 100-line window (chars/4 as a rough token estimate)
print('\nE1 context cost, CPython stdlib files')
print(f"{'file':22s}{'lines':>7s}{'chars':>9s}{'whole~tok':>11s}{'window~tok':>12s}{'ratio':>7s}")
tot_w = tot_win = 0
for f in FILES:
    p = os.path.join(STD, f)
    text = open(p, encoding='utf-8').read()
    lines = text.splitlines(keepends=True)
    whole = len(text) / 4
    win = len(''.join(lines[:WINDOW])) / 4
    tot_w += whole; tot_win += win
    print(f"{f:22s}{len(lines):7d}{len(text):9d}{whole:11.0f}{win:12.0f}{whole/win:7.2f}")
print(f"{'TOTAL':22s}{'':7s}{'':9s}{tot_w:11.0f}{tot_win:12.0f}{tot_w/tot_win:7.2f}")

# E2: edit ambiguity. Fraction of substantive lines that occur more than once in their own file
print('\nE2 non-unique substantive lines (stripped length >= 12) per file')
tot_lines = tot_nu = 0
for f in FILES:
    lines = [l.strip() for l in open(os.path.join(STD, f), encoding='utf-8')]
    sub = [l for l in lines if len(l) >= 12]
    counts = collections.Counter(lines)
    nu = sum(1 for l in sub if counts[l] > 1)
    tot_lines += len(sub); tot_nu += nu
    print(f"{f:22s} substantive={len(sub):5d} non_unique={nu:5d} frac={nu/len(sub):.3f}")
print(f"{'TOTAL':22s} substantive={tot_lines:5d} non_unique={tot_nu:5d} frac={tot_nu/tot_lines:.3f}")

# E3: attempt budget. Independent attempts, each correct with prob p (assumption: attempts are independent; real attempts are correlated)
print('\nE3 P(at least one correct in B independent attempts), p=0.3, 200000 trials, seed 52')
rng = random.Random(52)
p = 0.3
N = 200000
for B in (1, 2, 4, 8):
    hits = 0
    for _ in range(N):
        if any(rng.random() < p for _ in range(B)):
            hits += 1
    print(f"B={B} analytic={1-(1-p)**B:.4f} monte_carlo={hits/N:.4f}")
```

### Context cost

A whole-file view of six stdlib files costs 61,332 tokens, against 4,554 for their first 100 lines. That is about 13.5 times more, using characters divided by four as a rough token count. The ratio is largest for big files: `argparse.py` costs 25,289 tokens in full and 898 in a window. For `json/scanner.py`, which has 73 lines, the window is the whole file and the ratio is 1.00 (Diagram 3). A real tokenizer will give different counts; the point is the order of magnitude, not the exact figure.

![Bar chart comparing whole-file and first-100-line token estimates for six standard library files; the whole-file bars are far taller except for the 73-line scanner file](diagrams/52.1-context-cost.svg "Estimated tokens per view. Whole-file bars dwarf the 100-line windows for every file longer than the window.")

### Edit ambiguity

An exact-replace edit only works if its old text is unique. Across the six files, 981 of 4,760 substantive lines (20.6%) occur more than once in their own file. Per file the share runs from 0.0% (`json/scanner.py`) to 27.9% (`json/decoder.py`) (Diagram 4). A repeated line is not a failed edit, because the agent can add surrounding lines until the match is unique. It is a reason to make the tool refuse ambiguous matches, not replace the first one it finds.

![Horizontal bars showing the share of substantive lines that occur more than once in their file, per file and in total, which is 0.206](diagrams/52.1-edit-ambiguity.svg "Share of non-unique lines. Substantive means a stripped length of at least 12 characters.")

### Attempt budget

Suppose each attempt succeeds with probability $p$, and attempts are independent. The chance that all $B$ attempts fail is $(1 - p)^B$, so the chance of at least one success is $1 - (1 - p)^B$. With $p = 0.3$ the values are 0.300, 0.510, 0.760 and 0.942 for $B = 1, 2, 4, 8$. A Monte Carlo check (200,000 trials, fixed seed) agrees within 0.003 (Diagram 5). The gains flatten quickly.

![Bar chart of the probability of at least one success for budgets of one, two, four and eight attempts, rising from 0.300 to 0.942](diagrams/52.1-attempt-budget.svg "Probability of at least one correct attempt, p = 0.3, under an independence assumption.")

The independence assumption is the weak point. Real agent attempts repeat the same misreading of the issue, so they are correlated and the true curve is flatter. This is my own reasoning, not a measured result; I have not measured correlation for any model.

A verification gate is what makes retries useful at all. The loop above stops on `run_tests`, not on the model saying it is finished. Without that gate, a wrong patch that looks plausible is reported as done.

The strongest alternative design is a fixed pipeline with no open-ended loop. Agentless (Xia et al., 2024) runs localization, repair and patch validation in three phases, with the model choosing no later actions and using no complex tools. Its abstract claims the highest SWE-bench Lite performance among open-source agents at low cost. I have not checked the cost comparison against the full paper.

## Common traps

> [!TRAP]
> Passing tests show only that the tests you have run pass. A suite that never exercises the buggy path accepts a wrong patch. Check that the FAIL_TO_PASS tests fail on the original code before you trust them.

> [!TRAP]
> Dumping whole files into the context looks harmless for one file and costs about 13 times more across six files. Put a window limit on every view tool.

> [!TRAP]
> `str.replace` replaces every occurrence, not the one you meant. Refuse the edit unless the old text matches exactly once.

> [!TRAP]
> A model that writes "I ran the tests, they pass" has made a claim, not an observation. Believe the tool output, and make the loop's stop condition read it.

> [!TRAP]
> The `exec` call in the teaching code runs generated code in your own process. Real agents run tests in an isolated container.

## Summary

- A coding agent is a loop: the model proposes one tool call, the tool layer runs it, and the observation returns to the context.
- The tool layer is where cheap checks belong: window limits, result caps, unique-match edits and syntax gates.
- Whole-file views cost about 13.5 times more than 100-line windows across six stdlib files, so windows are a design requirement.
- About 20.6% of substantive lines are non-unique within their file, so exact-replace edits must refuse ambiguous matches.
- Retry gains flatten fast under independence, and real attempts are correlated, so the true gain is smaller still.

## Quiz time

### Question 1: Calculation

An agent makes $B = 3$ independent attempts, each correct with probability $p = 0.3$. What is the probability that at least one attempt is correct?

<details><summary>Show Solution</summary>

The complement is that all three fail: $(1 - 0.3)^3 = 0.7^3 = 0.343$. So the probability of at least one success is $1 - 0.343 = 0.657$.

</details>

### Question 2: Prediction

In the toy agent, suppose step 4 had used the new text `return s[mid] + ` but with a closing parenthesis, `return s[mid] + 1)`. Does `stats.py` change, and what does the agent see?

<details><summary>Show Solution</summary>

No, the file does not change. `compile()` raises a `SyntaxError` on the candidate source, the `except` branch returns an error string, and `REPO[path]` is never assigned. The agent sees `error: edit rejected, SyntaxError on line 9`, followed by the syntax message, and the next run of `run_tests` still shows `test_median_odd FAIL`.

</details>

### Question 3: Bug-spotting

A colleague writes this edit tool. What is wrong with it?

```python
def edit(path, old, new):
    REPO[path] = REPO[path].replace(old, new)
    return "edit applied"
```

<details><summary>Show Solution</summary>

It has no uniqueness check, so `edit("stats.py", "return", "return")`-style calls replace every occurrence silently. It also has no syntax gate, so a broken replacement is written to the file and the error appears only later, when the tests run. The fix is the two-check version in the lesson: count the matches and refuse unless the count is 1, then compile the candidate before writing it.

</details>

### Question 4: Explanation

Why does SWE-bench require PASS_TO_PASS tests in addition to FAIL_TO_PASS tests?

<details><summary>Show Solution</summary>

A patch can make the FAIL_TO_PASS tests pass while breaking behaviour the issue never mentioned. PASS_TO_PASS tests exist to catch that regression. The SWE-bench paper describes them as ensuring "that the revision does not break or violate any existing expected behavior" (Appendix A.5).

</details>
