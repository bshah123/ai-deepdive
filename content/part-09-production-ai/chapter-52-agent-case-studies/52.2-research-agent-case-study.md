A research agent answers a question by planning sub-questions, searching for sources, reading them, checking what it found, and only then writing a cited report. In this lesson you will build a small version of that loop, measure how a verification step changes the report, and see where the design still fails.

**You need:** Python dictionaries, lists and loops. The search code uses TF-IDF (term frequency–inverse document frequency), a word-weighted similarity score, which is explained where it appears.

## The problem a single call cannot solve

Suppose you ask a language model for a cited brief on the Halden battery pilot: capacity, installed cost, cycle life, grid service, main risk and commissioning date. Three things go wrong. The model may not know the facts, or may know stale ones. A brief needs many sources, and a long input does not guarantee that the model uses all of it: Liu et al. (2023) found that accuracy drops when the relevant information sits in the middle of a long context. And nothing checks that a citation supports the sentence it is attached to.

Retrieval-augmented generation (RAG) puts a search step in front of generation (Lewis et al., 2020). ReAct interleaves reasoning steps with actions such as searches, so the model decides what to look up next (Yao et al., 2022). A research agent combines both. The architecture below spells out the stages.

## Architecture: five stages around one loop

![Five boxes in a row, Planner, Search loop, Evidence, Verifier and Writer, with a red arrow from Verifier back to Search loop for rejected claims](diagrams/52.2-architecture.svg "The planner splits the question, the search loop reads pages, the verifier gates every claim, and the writer cites only what passed.")

- **Planner:** splits the question into sub-questions and writes one search query for each.
- **Search loop:** for each open sub-question (a *gap*), reads the best unread page.
- **Evidence store:** keeps each claim together with the id of the page it came from.
- **Verifier:** accepts a claim only if the cited page supports it. A rejected claim leaves its gap open.
- **Writer:** writes one cited sentence per accepted claim.

Anthropic's engineering post on its multi-agent research system (June 2025) follows a similar split: a lead agent plans and starts subagents that search in parallel, and a separate CitationAgent attaches sources to claims. The post describes no runtime fact-checking stage; its claim-level citation check is an offline evaluation. It also reports that multi-agent systems use about 15 times more tokens than chat. The loop is paid for in tokens.

## A worked example by hand

The corpus has 36 pages. Each of six facts has one Halden page and five look-alike pages from other pilots, built from the same sentence template with different numbers:

- Halden: "Installed cost at the Halden pilot was 310 euros per kWh in its first year."
- Varna: "Installed cost at the Varna pilot was 270 euros per kWh in its first year."

The planner makes a mistake on the cost question. Its query is "installed cost per kWh first year", with no pilot name. Every cost page contains those six words, so all six score the same. Ties go to page order, and the Halden page comes sixth. Three of the six planner queries drop the pilot name this way; the experiment does this on purpose.

Now run the two strategies with a budget of nine pages (a page is opened and read, and each read costs one unit of budget):

![Two panels listing pages read in order. Without verification, six pages are read and three wrong-pilot pages are accepted. With verification, nine pages are read and only Halden pages are accepted](diagrams/52.2-trace.svg "Same six sub-questions, same budget. The verifier spends extra pages to avoid accepting the look-alike pilots.")

Without verification, the agent accepts the first page with the right attribute, Varna's cost, and closes the gap. With verification, that page is rejected because it does not name Halden and does not contain 310 euros per kWh. The agent keeps reading down the ranking until it finds the Halden page.

## How the retriever scores a page

The retriever is cosine similarity over TF-IDF vectors (standard form; see any information-retrieval text). Each page $d$ becomes a vector with one weight per word $t$: $w_{t,d} = \mathrm{tf}_{t,d} \cdot \mathrm{idf}_t$, where $\mathrm{tf}_{t,d}$ counts the word in the page and $\mathrm{idf}_t = \ln\frac{1+N}{1+\mathrm{df}_t} + 1$ down-weights words found in many pages ($N$ pages in total, $\mathrm{df}_t$ pages containing $t$). The query $q$ gets the same weights, and

$$
\mathrm{score}(q, d) = \frac{\sum_t w_{t,q}\, w_{t,d}}{\lVert w_q \rVert\, \lVert w_d \rVert}
$$

A rare word such as "halden" therefore counts for more than a common word such as "pilot". The `+1` and the `1+` terms are smoothing choices that stop the logarithm from going to zero or dividing by zero.

## The code

The whole experiment uses only the standard library, so it runs in the browser as written. Three strategies are compared: `one-shot` (one broad query, then cite whatever pages came back), `loop` (one query per gap, accept the first matching page), and `loop+verify` (the same loop, but a claim is accepted only if the page names Halden and contains the gold value).

```python
import math
import re
from collections import Counter

# 1. A synthetic corpus. "Halden" is the pilot we want. Five look-alike pilots
#    use the same sentence templates with different numbers.
OTHER_PILOTS = ["Varna", "Osko", "Brenn", "Corvo", "Ilse"]
ATTRS = {
    # attribute: (sentence template, gold value for Halden, look-alike values, planner query)
    "capacity":   ("The {p} pilot stores {v} of lithium iron phosphate capacity.",
                   "40 MWh", ["18 MWh", "25 MWh", "12 MWh", "60 MWh", "22 MWh"],
                   "Halden capacity MWh"),
    "cost":       ("Installed cost at the {p} pilot was {v} in its first year.",
                   "310 euros per kWh", ["270 euros per kWh", "415 euros per kWh", "198 euros per kWh",
                                         "340 euros per kWh", "255 euros per kWh"],
                   "installed cost per kWh first year"),
    "cycles":     ("The cells at the {p} pilot are rated for {v} at 80 percent depth of discharge.",
                   "6,000 cycles", ["4,500 cycles", "8,000 cycles", "3,000 cycles", "5,200 cycles", "7,000 cycles"],
                   "cells rated cycles depth of discharge"),
    "service":    ("The {p} pilot provides {v} to the regional grid operator.",
                   "frequency regulation", ["peak shaving", "voltage support", "black start",
                                            "spinning reserve", "energy arbitrage"],
                   "Halden grid service"),
    "risk":       ("The main risk reported at the {p} pilot is {v} during summer peaks.",
                   "thermal runaway", ["cell swelling", "inverter overheating", "connector corrosion",
                                       "cooling pump failure", "fuse fatigue"],
                   "main risk summer peaks"),
    "commission": ("The {p} pilot was commissioned in {v}.",
                   "March 2026", ["2024", "June 2025", "January 2025", "November 2024", "2023"],
                   "Halden commissioned"),
}
BROAD = "pilot storage capacity installed cost cycles grid service risk commissioned"  # one query, no pilot name

DOCS = []
for k, (attr, (template, gold, others, _)) in enumerate(ATTRS.items()):
    pairs = [("Halden", gold)] + list(zip(OTHER_PILOTS, others))
    pairs = pairs[k:] + pairs[:k]   # rotate so the Halden page is not always first among ties
    for pilot, value in pairs:
        DOCS.append({"id": f"{pilot}-{attr}", "pilot": pilot, "attr": attr,
                     "text": template.format(p=pilot, v=value)})

# 2. A TF-IDF retriever in pure Python.
def tokens(text):
    return re.findall(r"[a-z0-9]+", text.lower())

DF = Counter()
for d in DOCS:
    d["tf"] = Counter(tokens(d["text"]))
    DF.update(d["tf"].keys())
N = len(DOCS)
IDF = {t: math.log((1 + N) / (1 + df)) + 1 for t, df in DF.items()}

def tfidf(counts):
    w = {t: c * IDF[t] for t, c in counts.items() if t in IDF}
    norm = math.sqrt(sum(x * x for x in w.values())) or 1.0
    return {t: x / norm for t, x in w.items()}

for d in DOCS:
    d["vec"] = tfidf(d["tf"])

def search(query, exclude=()):
    q = tfidf(Counter(tokens(query)))
    scored = [(-sum(q[t] * d["vec"].get(t, 0.0) for t in q), i)
              for i, d in enumerate(DOCS) if i not in exclude]
    return [i for _, i in sorted(scored)]

# 3. Three strategies that each open at most `budget` pages.
def run(strategy, budget):
    claims, log, opened = {}, [], set()
    if strategy == "one-shot":
        for i in search(BROAD)[:budget]:
            opened.add(i)
            attr = DOCS[i]["attr"]
            if attr not in claims:
                claims[attr] = DOCS[i]   # cite the first page on this attribute, whatever pilot it is about
        return claims, len(opened), log
    verify = strategy == "loop+verify"
    open_attrs = list(ATTRS)
    while open_attrs and len(opened) < budget:
        for attr in list(open_attrs):
            if len(opened) >= budget:
                break
            ranked = search(ATTRS[attr][3], exclude=opened)
            if not ranked:
                break
            i = ranked[0]                 # best unread page for this sub-question
            opened.add(i)
            doc = DOCS[i]
            if verify:
                ok = doc["attr"] == attr and "Halden" in doc["text"] and ATTRS[attr][1] in doc["text"]
            else:
                ok = doc["attr"] == attr
            log.append((len(opened), attr, doc["id"], ok))
            if ok:
                claims[attr] = doc
                open_attrs.remove(attr)
    return claims, len(opened), log

def score(claims):
    correct = sum(1 for d in claims.values() if d["pilot"] == "Halden")
    coverage = correct / len(ATTRS)
    precision = correct / len(claims) if claims else float("nan")
    return coverage, precision

if __name__ == "__main__":
    print(f"corpus: {len(DOCS)} pages = {len(ATTRS)} facts x (1 Halden + {len(OTHER_PILOTS)} look-alikes)")
    print("top 6 for the 'cost' query:", [DOCS[i]["id"] for i in search(ATTRS['cost'][3])[:6]])
    print("top 6 for the broad query:", [DOCS[i]["id"] for i in search(BROAD)[:6]])
    print()
    budgets = [3, 6, 9, 12, 18, 24]
    print("pages opened   " + "".join(f"{b:>7}" for b in budgets))
    for name in ["one-shot", "loop", "loop+verify"]:
        cov, prec = [], []
        for b in budgets:
            c, p = score(run(name, b)[0])
            cov.append(c)
            prec.append(p)
        print(f"{name:<13} cov " + "".join(f"{c:7.2f}" for c in cov))
        print(f"{'':<13} prec" + "".join(f"{p:7.2f}" for p in prec))
    claims, used, _ = run("loop+verify", 36)
    print(f"\nloop+verify to full coverage: pages opened = {used}, coverage = {score(claims)[0]:.2f}")
    for name in ["loop", "loop+verify"]:
        claims, used, log = run(name, 9)
        print(f"\ntrace, {name}, budget 9:")
        for n, attr, doc_id, ok in log:
            print(f"  page {n}: {attr:<10} opened {doc_id:<18} accepted={ok}")
    claims, used, _ = run("loop+verify", 24)
    print("\nreport, loop+verify, budget 24:")
    for attr, d in claims.items():
        print(f"  {d['text']} [{d['id']}]")
```

Read the table this way. Coverage is the share of the six facts reported with a Halden page. Precision is the share of reported claims whose cited page is a Halden page.

![Line chart of coverage against pages opened. The verify line rises to 1.00 by 18 pages, the no-verify line levels off at 0.50, and one-shot stays near zero](diagrams/52.2-coverage.svg "Coverage against pages opened. The verify line also has precision 1.00 at every budget; the other two do not.")

Three results follow from the run:

- **Without verification, more budget does not help.** Coverage stops at 0.50 from a budget of six. Each gap closes on its first accepted page, so the loop finishes after six pages and has nothing left to spend the rest of the budget on.
- **With verification, coverage reaches 1.00,** and the run reaches it after 15 pages. Its precision is 1.00 at every budget, because wrong-pilot pages are never accepted.
- **The one-shot result reflects my choices, not single queries in general.** The broad query omits the pilot name, so look-alike pages fill the top ranks. Change the query or the tie order and this number changes.

## Where the design fails

- **The corpus is synthetic and the reader is a stub.** A page's attribute label stands in for a language model reading it. The numbers show a mechanism, not rates for real agents.
- **The verifier is a string test.** Its precision of 1.00 is a property of this test, not evidence about language-model verifiers. A learned verifier can miss unsupported claims or accept paraphrases that are wrong (my reasoning, not measured here).
- **A supported claim can still be out of date.** The check asks whether the page contains the value, not whether the page is current. Nothing here tests dating.
- **The writer's behaviour on open gaps is not tested.** The code's writer leaves an unanswered sub-question out. A real writer may fill the gap from its own memory and cite a page that does not say so. That is the failure the verifier exists to catch, and this experiment does not measure it.
- **The planner sets the ceiling.** If no query can reach a page, no amount of budget or verification will find it.

> [!TRAP]
> Matching the attribute is not matching the subject. The no-verify loop reads Varna's cost and reports it as Halden's, and the claim looks well-formed.

> [!TRAP]
> A bigger budget is not a fix. The no-verify loop stopped after six pages, so no budget changes its answer.

> [!TRAP]
> A citation is not a verification. The one-shot writer cites whatever page it read. The report looks cited and is wrong.

> [!TRAP]
> Substring checks match inside longer strings. The check `"40 MWh" in text` is also true for "140 MWh". The code does not guard against this, and no page in this corpus triggers it, but a real corpus would.

## Summary

- A research agent is a loop: plan sub-questions, read pages for each open gap, verify each claim against its cited page, then write.
- Verification is what keeps the report's citations honest. Without it, a loop can close gaps with pages about the wrong subject.
- In the run, verification raised coverage from 0.50 to 1.00 and kept precision at 1.00. It cost 15 pages instead of 6.
- The planner's queries limit what the agent can find, and a verifier that only checks string presence can pass stale or mismatched evidence.

### Question 3: Bug-spotting

A colleague simplifies the verifier to `ok = doc["attr"] == attr and ATTRS[attr][1] in doc["text"]`. What breaks?

<details><summary>Show Solution</summary>

The entity check is gone. A look-alike page that contains the same value string would pass. No page in this corpus has that collision, so the printed output would not show the bug. It would appear once two pilots report the same number.

</details>

### Question 4: Explanation

Why does the no-verify coverage stay at 0.50 even with a larger budget?

<details><summary>Show Solution</summary>

Every gap closes on the first page the loop reads. Three of those pages are about the wrong pilot, so three facts are reported wrongly and never reopen. Once all six gaps close, the loop stops after six pages. A larger budget has nothing left to do.

</details>
