In this lesson you will define the numbers a serving team tracks for a language model: time to first token (TTFT), inter-token latency (ITL), tokens per second and throughput. You will compute them from a log of token timestamps, and you will see why the setting that maximises total throughput makes each user's experience worse.

**You need:** how autoregressive generation makes one token per step with a key-value (KV) cache (Lesson 27.2), and basic NumPy arrays.

## The problem: one number hides three waits

A chat user waits three times. First, before anything appears. Then, between words. Finally, until the answer is complete. A single "tokens per second" figure merges these, so a server can post a good average while one user waits seconds for the first word.

![A timeline of one request: arrival, a 0.42 s wait before the first token, then 99 gaps of 21.0 ms each up to the last token at 2.50 s](diagrams/53.1-request-timeline.svg "One request, measured from the moment it arrives.")

## Definitions

Let a request arrive at time $t_a$ and emit $n$ output tokens at times $t_1 < t_2 < \dots < t_n$.

| Metric | Definition | Unit |
|---|---|---|
| TTFT (time to first token) | $t_1 - t_a$; includes queueing and the prefill pass over the prompt | ms |
| ITL (inter-token latency) | each gap $t_{k+1} - t_k$ | ms |
| TPOT (time per output token) | $(t_n - t_1)/(n-1)$, the mean ITL of one request | ms |
| E2E (end-to-end) latency | $t_n - t_a$ | s |
| Tokens/s per request | $n/\text{E2E}$, or $1/\text{TPOT}$ for decode only | tokens/s |
| System throughput | total output tokens across all requests, divided by the wall-clock span of the run | tokens/s |

Prefill is the single pass that processes the whole prompt before the first output token can exist; decode is the step-by-step phase after it. DistServe (Zhong et al., 2024) uses TTFT for the prefill phase and TPOT for the decode phase, and it is a good reference for these names.

Two traps follow from the table. "Tokens per second" is used both for one request and for the whole system. And dashboards do not always agree on whether ITL means each gap or the mean gap. Check which one a chart means before you compare numbers.

## Worked example, by hand

A request arrives at $t_a = 0$. Its first token appears at 0.42 s and its 100th token at 2.50 s.

- TTFT = 0.42 s.
- There are 99 gaps between the first and last token. They cover $2.50 - 0.42 = 2.08$ s, so TPOT = $2.08 / 99 = 0.0210$ s = 21.0 ms.
- E2E = 2.50 s.
- Tokens/s end to end: $100 / 2.50 = 40.0$. Tokens/s for decode only: $1 / 0.0210 = 47.6$.

The two tokens/s figures differ by 19% because one includes the 0.42 s wait. Neither is wrong; they answer different questions. The code below reproduces these numbers from the timestamps:

```python
import numpy as np

# One request: arrives at t = 0 s, first token at 0.42 s, 100th token at 2.50 s
arrival = 0.00
token_times = np.linspace(0.42, 2.50, 100)

ttft = token_times[0] - arrival
itl = np.diff(token_times)              # the 99 gaps
mean_itl = itl.mean()
e2e = token_times[-1] - arrival

print(f"TTFT        = {ttft:.3f} s")
print(f"mean ITL    = {mean_itl*1000:.1f} ms over {len(itl)} gaps")
print(f"E2E         = {e2e:.3f} s")
print(f"tokens/s, end-to-end  = {len(token_times)/e2e:.1f}")
print(f"tokens/s, decode only = {1/mean_itl:.1f}")
```

```output
TTFT        = 0.420 s
mean ITL    = 21.0 ms over 99 gaps
E2E         = 2.500 s
tokens/s, end-to-end  = 40.0
tokens/s, decode only = 47.6
```

## Why throughput and per-user speed trade off

Each decode iteration produces one token for every running sequence, and it must read all the model weights once. Pope et al. (2022, Section 2) state that at small batch sizes the time to load weights dominates. Each sequence also reads its own KV cache. So an iteration with $B$ running sequences takes roughly

$$t(B) = T_0 + c\,B$$

Every user then sees ITL = $t(B)$, the per-user rate is $1/t(B)$, and the system throughput is $B/t(B)$.

The constants below are assumptions, not measurements on any device. $T_0 = 14$ ms is the time to read 14 GB (gigabytes) of 16-bit float (fp16) weights, which is a 7-billion-parameter model at 2 bytes per parameter, from memory at 1 TB/s (terabyte per second): $14 / 1000 \text{ s} = 14$ ms. $c = 0.25$ ms is the KV-cache read for one sequence at 512 tokens of context, which assumes 0.5 MB (megabytes) of cache per token: $0.5 \times 512 = 256$ MB, and $256 \text{ MB} / 1 \text{ TB/s} = 0.256$ ms.

```python
import numpy as np

# Assumed cost model (not measured): ms per decode iteration
T0 = 14.0     # read all weights once
C_SEQ = 0.25  # KV-cache reads per running sequence

for B in [1, 2, 4, 8, 16, 32, 64]:
    itl_ms = T0 + C_SEQ * B
    print(f"B={B:2d}: ITL {itl_ms:6.2f} ms, per-user {1000/itl_ms:6.1f} tok/s, system {B*1000/itl_ms:6.0f} tok/s")
```

```output
B= 1: ITL  14.25 ms, per-user   70.2 tok/s, system     70 tok/s
B= 2: ITL  14.50 ms, per-user   69.0 tok/s, system    138 tok/s
B= 4: ITL  15.00 ms, per-user   66.7 tok/s, system    267 tok/s
B= 8: ITL  16.00 ms, per-user   62.5 tok/s, system    500 tok/s
B=16: ITL  18.00 ms, per-user   55.6 tok/s, system    889 tok/s
B=32: ITL  22.00 ms, per-user   45.5 tok/s, system   1455 tok/s
B=64: ITL  30.00 ms, per-user   33.3 tok/s, system   2133 tok/s
```

![Two bar charts over batch sizes 1 to 64: system tokens per second rises from 70 to 2,133, while per-user tokens per second falls from 70.2 to 33.3](diagrams/53.1-batch-tradeoff.svg "The same batch, read two ways: total output rises, each user's speed falls.")

Going from $B = 1$ to $B = 32$ multiplies system throughput by about 21 (70 to 1,455 tokens/s), while each user's rate falls by 35% (70.2 to 45.5 tokens/s). This model has no compute limit, so at large $B$ its numbers are optimistic. That is my reasoning, not a measurement.

## Arrivals, prefill and the tail

Real requests arrive at random times, and a new prompt must be prefilled before its first token exists. Sarathi-Serve (Agrawal et al., 2024, Section 3.2) states that prefill-prioritizing schedulers "can introduce generation stalls for ongoing decodes resulting in latency spikes."

The simulator below serves a Poisson stream of requests on one GPU (graphics processing unit) with a batch cap of 32. Each request has 256 prompt tokens and 64 to 192 output tokens. At each iteration it runs a prefill for any waiting requests first, and otherwise one decode step for all running requests. Prefill costs an extra $A = 0.1$ ms per prompt token (also assumed). The clock is simulated, so the output does not depend on your machine.

```python
import numpy as np

# Assumed cost model (not measured), in ms
T0 = 14.0        # per iteration: read all weights once
C_SEQ = 0.25     # per running sequence per decode iteration: KV reads
A_PROMPT = 0.1   # per prompt token in prefill
PROMPT = 256     # prompt tokens per request
MAX_BATCH = 32   # sequences per iteration

def simulate(rate_per_s, n_req=300, seed=53):
    rng = np.random.default_rng(seed)
    arrivals = np.cumsum(rng.exponential(1000.0 / rate_per_s, n_req))  # ms
    out_len = rng.integers(64, 193, n_req)                              # output tokens per request
    tokens = [[] for _ in range(n_req)]                                 # emission times (ms)
    waiting, running, now, nxt = [], [], 0.0, 0
    while nxt < n_req or waiting or running:
        while nxt < n_req and arrivals[nxt] <= now:
            waiting.append(nxt)
            nxt += 1
        if waiting and len(running) < MAX_BATCH:          # prefill first: new prompts block decodes
            batch = waiting[:MAX_BATCH - len(running)]
            del waiting[:len(batch)]
            now += T0 + A_PROMPT * PROMPT * len(batch)
            for r in batch:
                tokens[r].append(now)                     # first token comes out of prefill
            running.extend(batch)
        elif running:                                     # one decode iteration: one token per running request
            now += T0 + C_SEQ * len(running)
            for r in running:
                tokens[r].append(now)
            running = [r for r in running if len(tokens[r]) < out_len[r]]
        else:                                             # idle until the next arrival
            now = arrivals[nxt]
    return arrivals, tokens

def summarise(rate):
    arrivals, tokens = simulate(rate)
    ttft = np.array([t[0] - a for a, t in zip(arrivals, tokens)])
    itl_all = np.concatenate([np.diff(t) for t in tokens])   # every gap of every request
    total_tokens = sum(len(t) for t in tokens)
    span_s = (max(t[-1] for t in tokens) - arrivals[0]) / 1000
    return dict(rate=rate, ttft_p50=np.percentile(ttft, 50), ttft_p99=np.percentile(ttft, 99),
                itl_p50=np.percentile(itl_all, 50), itl_p99=np.percentile(itl_all, 99),
                itl_mean=itl_all.mean(), system_tps=total_tokens / span_s)

print(f"{'req/s':>5} {'TTFT p50':>9} {'TTFT p99':>9} {'ITL p50':>8} {'ITL p99':>8} {'ITL mean':>9} {'sys tok/s':>10}")
for s in [summarise(r) for r in [1, 3, 5, 7, 9]]:
    print(f"{s['rate']:>5} {s['ttft_p50']:>9.0f} {s['ttft_p99']:>9.0f} {s['itl_p50']:>8.1f} "
          f"{s['itl_p99']:>8.1f} {s['itl_mean']:>9.1f} {s['system_tps']:>10.0f}")

# One request at 7 req/s that overlapped other requests' prefills
arrivals7, tokens7 = simulate(7)
gaps = [np.diff(t) for t in tokens7]
worst = int(np.argmax([g.max() for g in gaps]))
series = gaps[worst]
med = float(np.median(series))
print()
print(f"request {worst}: tokens={len(series)+1}, median ITL={med:.1f} ms, max ITL={series.max():.1f} ms, "
      f"tokens above 1.5x median={int((series > 1.5*med).sum())}")
print(f"spike sizes (ms): {np.round(np.sort(series)[-5:], 1).tolist()}")
```

```output
req/s  TTFT p50  TTFT p99  ITL p50  ITL p99  ITL mean  sys tok/s
    1        46        75     14.8     54.4      15.3        126
    3        49        82     16.0     56.8      18.0        370
    5        51        90     17.8     96.5      21.9        606
    7        56       749     20.8    100.5      26.9        828
    9      2131      4499     22.0     87.2      30.0        936

request 50: tokens=163, median ITL=19.0 ms, max ITL=230.4 ms, tokens above 1.5x median=19
spike sizes (ms): [98.5, 124.1, 124.6, 163.7, 230.4]
```

Read the sweep row by row (req/s means requests per second):

- At 1 req/s the median ITL is 14.8 ms, but the 99th percentile (p99) is 54.4 ms. The tail comes from other users' prefills, which pause everyone's decode.
- At 7 req/s the median ITL is still 20.8 ms, but the p99 TTFT has risen to 749 ms, because requests now wait in a queue.
- At 9 req/s the median TTFT is 2.1 s and system throughput flattens near 940 tokens/s. The offered load exceeds what this server can serve, so the queue, not decode speed, sets TTFT.

The figure shows one request from the 7 req/s run. Its median gap is 19.0 ms, but its largest gap is 230.4 ms. A decode step with 32 sequences takes only 22 ms in this model, so a gap that long must contain prefill iterations of other requests.

## Common traps

> [!TRAP] Means hide tails.
> At 7 req/s the mean ITL is 26.9 ms, the median is 20.8 ms, and the p99 is 100.5 ms. Report percentiles, not only the mean.

> [!TRAP] TTFT includes queueing.
> At 1 req/s, TTFT is almost pure prefill, about 46 ms in the table. At 9 req/s, the median is 2.1 s, mostly queue. Making the prefill faster does not fix a queue that is longer than the server can clear.

> [!TRAP] Per-user and system rates move in opposite directions.
> Batching raises system tokens/s and lowers each user's tokens/s. A "faster server" claim needs both numbers.

> [!TRAP] Client-side clocks include more.
> E2E measured at the server excludes network time. A client that starts its clock at the button press sees more. This is my reasoning, not a measured effect.

> [!TRAP] Simulated clocks are not benchmarks.
> Every number here follows from the assumed constants. Compare the trends, not the magnitudes, and measure real latency on your own hardware before you plan capacity.

## Summary

- TTFT is the wait before the first token; it includes queueing and the prefill of the prompt.
- ITL is each gap between tokens; TPOT is the mean gap of one request.
- Decode is memory-bound at small batch sizes, so batching raises system throughput while each user's speed falls.
- Prefill of new requests can stall decodes of running ones, which shows up in the p99 ITL, not the median.

## Quiz time

### Question 1: Calculation

A request arrives at $t_a = 0$. Its first token appears at 0.30 s and its 201st token at 4.30 s. Find its TPOT in ms, its end-to-end tokens/s, and its decode-only tokens/s.

<details><summary>Show solution</summary>

TPOT = $(4.30 - 0.30)/200 = 0.020$ s = 20.0 ms. E2E = 4.30 s, so end-to-end tokens/s = $201/4.30 = 46.7$. Decode-only tokens/s = $1/0.020 = 50.0$.

</details>

### Question 2: Prediction

In the cost model above, which has a higher per-user rate, $B = 8$ or $B = 32$? By what factor does system throughput change between them, and is that factor larger or smaller than the change in batch size?

<details><summary>Show solution</summary>

$B = 8$ has the higher per-user rate: 62.5 tokens/s against 45.5 tokens/s. System throughput rises from 500 to 1,455 tokens/s, a factor of about 2.9. The batch size rises by a factor of 4, so system throughput grows less than the batch size because the weight read is paid once per iteration and the per-sequence cost grows slowly.

</details>

### Question 3: Bug spotting

A colleague computes TPOT as `(t[-1] - t[0]) / len(t)`. What is wrong, and how do you fix it?

<details><summary>Show solution</summary>

There are $n - 1$ gaps between $n$ tokens, but the code divides by $n$. This underestimates TPOT by a factor of $(n-1)/n$, which is about 1% for 100 tokens but matters when $n$ is small. The fix is `(t[-1] - t[0]) / (len(t) - 1)`.

</details>

### Question 4: Explanation

At 1 req/s the median ITL is 14.8 ms but the p99 is 54.4 ms. Why does the tail sit so far above the median, when no request is queued?

<details><summary>Show solution</summary>

Some gaps contain a prefill of another request. A prefill of a 256-token prompt costs $T_0 + 0.1 \times 256 = 39.6$ ms in this model, which pauses the running decode for that long. Gaps that include such a prefill sit near 40 ms plus a decode step, around 54 ms, and they are rare enough to appear only in the tail.

</details>
