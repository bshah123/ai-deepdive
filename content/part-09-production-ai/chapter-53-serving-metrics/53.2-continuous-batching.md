A model server runs many requests on one GPU at once. In this lesson you will simulate two batching policies, count the GPU slot-steps each one wastes, and read the throughput and latency numbers they produce.

**You need:** time to first token (TTFT), inter-token latency (ITL) and tokens per second from Lesson 53.1, and basic Python. The code runs in the browser.

## The problem static batching creates

A language model produces one token at a time. Each **decode step** runs the model once and gives every active request its next token. A batch of requests shares that step. While decoding is memory-bound (limited by reading the weights and cache, not by arithmetic), a step costs roughly the same whether the batch holds 2 requests or 8. The model below assumes this.

Requests want different numbers of tokens. Under **static batching** a group of requests starts together and runs until the longest one finishes. Requests that finish early keep their slot, and new arrivals wait in the queue until the whole batch is done. In our workload the mean output is 84.6 tokens but the longest is 1,024, so one long request keeps its batch running while the other slots fall idle as their requests finish.

## The idea: decide after every step

**Continuous batching** (also called iteration-level scheduling) makes the batch decision once per decode step. A finished request leaves immediately and frees its slot. A waiting request takes the slot at the next step. Yu et al. (2022) introduced this granularity in the Orca serving system.

![A waiting queue feeds free slots, one decode step gives each running request one token, and finished requests return to the client and free their slot for the next admission](diagrams/53.2-scheduler-loop.svg "The loop repeats every decode iteration, not once per batch.")

## Worked example, by hand

Four requests arrive at time 0 with output lengths 2, 6, 2 and 4 tokens. There are two slots, and each decode step takes one time unit whatever the batch size.

**Static.** Batch 1 is {r1, r2}. It runs 6 steps, because r2 needs 6, and r1 sits idle from step 3 on. Batch 2 is {r3, r4} and runs for max(2, 4) = 4 steps. The makespan (time until the last request finishes) is 6 + 4 = 10. Useful slot-steps: 2 + 6 + 2 + 4 = 14, out of 2 × 10 = 20 available, which is 70%. TTFT is 1, 1, 7, 7, mean 4.0.

**Continuous.** r1 and r2 start at time 0. r1 finishes at time 2, so r3 takes its slot and finishes at time 4. At time 4, r3's slot is free again, so r4 starts and finishes at time 8. r2 finishes at time 6. The makespan is 8. Useful slot-steps: 14 out of 2 × 8 = 16, which is 87.5%. TTFT is 1, 1, 3, 5, mean 2.5.

![Two timelines for the same four requests on two slots: static batching holds finished slots idle until the longest request ends, while continuous batching refills them](diagrams/53.2-static-vs-continuous.svg "Blue: a token is generated. Amber: the slot is held but idle.")

The same 14 tokens take 10 steps under one policy and 8 under the other. The code below reproduces both timelines.

## Runnable simulator

The model is deliberately simple. One decode step for a batch of $B$ requests takes $t(B) = T_0 + T_1 B$ time units, with $T_0 = 1$ and $T_1 = 0.02$. These two values are **assumptions, not measurements**. Decode is usually memory-bound, so a step grows slowly with batch size, and $T_1$ sets how fast. The simulator also leaves out prefill (processing the prompt), memory limits on the KV cache and preemption. The section "Under the hood: what the model leaves out" explains why each of these matters.

```python
import math
import random
from dataclasses import dataclass

T0, T1 = 1.0, 0.02  # assumed step-time model: one decode iteration takes T0 + T1*B time units (not measured)


@dataclass
class Req:
    rid: int
    arrival: float
    out_len: int          # tokens to generate
    done: int = 0         # tokens generated so far
    first: float = None   # time the first token is ready (TTFT = first - arrival)
    finish: float = None  # time the last token is ready (end-to-end latency = finish - arrival)


def clone(reqs):
    return [Req(r.rid, r.arrival, r.out_len) for r in reqs]


def step_time(b, t0=T0, t1=T1):
    return t0 + t1 * b


def run_static(reqs, max_batch, t0=T0, t1=T1):
    """Static batching: take up to max_batch waiting requests, run until the longest one finishes."""
    queue = sorted(reqs, key=lambda r: r.arrival)
    i, t, busy, waiting = 0, 0.0, 0.0, []
    while i < len(queue) or waiting:
        if not waiting:
            t = max(t, queue[i].arrival)
        while i < len(queue) and queue[i].arrival <= t:
            waiting.append(queue[i])
            i += 1
        batch, waiting = waiting[:max_batch], waiting[max_batch:]
        dt = step_time(len(batch), t0, t1)      # padded batch: finished slots still cost compute
        for s in range(max(r.out_len for r in batch)):
            t_end = t + dt
            for r in batch:
                if r.out_len > s:               # request still live: its slot is useful
                    busy += dt
                    r.done += 1
                    if s == 0:
                        r.first = t_end
                    if s == r.out_len - 1:
                        r.finish = t_end
            t = t_end
    return busy, t


def run_continuous(reqs, max_batch, t0=T0, t1=T1):
    """Continuous batching: re-decide the batch after every decode iteration."""
    queue = sorted(reqs, key=lambda r: r.arrival)
    i, t, busy = 0, 0.0, 0.0
    waiting, running = [], []
    while i < len(queue) or waiting or running:
        if not running and not waiting:
            t = max(t, queue[i].arrival)
        while i < len(queue) and queue[i].arrival <= t:
            waiting.append(queue[i])
            i += 1
        while waiting and len(running) < max_batch:   # admit into free slots
            running.append(waiting.pop(0))
        dt = step_time(len(running), t0, t1)
        t_end = t + dt
        busy += len(running) * dt
        still = []
        for r in running:
            r.done += 1
            if r.done == 1:
                r.first = t_end
            if r.done == r.out_len:                   # finished: leave now, free the slot
                r.finish = t_end
            else:
                still.append(r)
        running = still
        t = t_end
    return busy, t


def make_workload(n, rate, seed, mu=4.0, sigma=1.0, cap=1024):
    """rate=None: all requests present at t=0 (offline). Otherwise Poisson arrivals."""
    rng = random.Random(seed)
    t, reqs = 0.0, []
    for k in range(n):
        if rate is not None:
            t += rng.expovariate(rate)
        length = min(cap, max(1, round(rng.lognormvariate(mu, sigma))))
        reqs.append(Req(k, t, length))
    return reqs


def pct(xs, p):
    s = sorted(xs)
    return s[math.ceil(p / 100 * len(s)) - 1]   # nearest-rank percentile


def summarize(reqs, busy, makespan, max_batch):
    lat = [r.finish - r.arrival for r in reqs]
    ttft = [r.first - r.arrival for r in reqs]
    tokens = sum(r.out_len for r in reqs)
    return {
        "tok_per_unit": tokens / makespan,
        "util": busy / (max_batch * makespan),
        "p50_lat": pct(lat, 50),
        "p95_lat": pct(lat, 95),
        "mean_lat": sum(lat) / len(lat),
        "mean_ttft": sum(ttft) / len(ttft),
        "makespan": makespan,
    }


def main():
    # 1. Worked example: step time fixed at 1 (T1 = 0), batch of 2, four requests at t = 0
    trace = [Req(1, 0.0, 2), Req(2, 0.0, 6), Req(3, 0.0, 2), Req(4, 0.0, 4)]
    for name, fn in [("static", run_static), ("continuous", run_continuous)]:
        rs = clone(trace)
        busy, mk = fn(rs, 2, t0=1.0, t1=0.0)
        s = summarize(rs, busy, mk, 2)
        print(f"{name}: makespan={mk:.1f} utilisation={s['util']:.3f} mean latency={s['mean_lat']:.2f} mean TTFT={s['mean_ttft']:.2f}")
        for r in sorted(rs, key=lambda r: r.rid):
            print(f"  r{r.rid} out_len={r.out_len} first={r.first:.1f} finish={r.finish:.1f}")

    # 2. Offline throughput: 400 requests all present at t = 0
    base = make_workload(400, None, seed=7)
    lens = [r.out_len for r in base]
    print(f"\nworkload: n={len(base)} mean out_len={sum(lens)/len(lens):.1f} median={pct(lens, 50)} max={max(lens)}")
    print("B   static tok/unit   continuous tok/unit   ratio   static util   continuous util")
    for B in [1, 2, 4, 8, 16, 32]:
        rs = clone(base); bs, ms = run_static(rs, B); ss = summarize(rs, bs, ms, B)
        rc = clone(base); bc, mc = run_continuous(rc, B); sc = summarize(rc, bc, mc, B)
        print(f"{B:<3} {ss['tok_per_unit']:>14.2f}   {sc['tok_per_unit']:>18.2f}   {sc['tok_per_unit']/ss['tok_per_unit']:>5.2f}"
              f"   {ss['util']:>11.3f}   {sc['util']:>15.3f}")

    # 3. Sensitivity of the batch-size trade-off to the step-time growth T1
    print("\nsensitivity, continuous tok/unit by step-time slope T1 (T0 = 1):")
    for t1 in [0.0, 0.02, 0.05]:
        vals = []
        for B in [8, 16, 32]:
            rc = clone(base); bc, mc = run_continuous(rc, B, t1=t1)
            vals.append(f"B={B}: {summarize(rc, bc, mc, B)['tok_per_unit']:.2f}")
        print(f"  T1={t1:<5} " + "  ".join(vals))

    # 4. Online: Poisson arrivals at 0.015 requests per unit time, B = 8
    wl = make_workload(400, 0.015, seed=11)
    print("\nonline: 400 requests, Poisson rate 0.015 req/unit, B = 8")
    for name, fn in [("static", run_static), ("continuous", run_continuous)]:
        rs = clone(wl); busy, mk = fn(rs, 8); s = summarize(rs, busy, mk, 8)
        print(f"{name:<11} p50 latency={s['p50_lat']:.1f}  p95 latency={s['p95_lat']:.1f}  mean TTFT={s['mean_ttft']:.1f}"
              f"  tok/unit={s['tok_per_unit']:.2f}  util={s['util']:.3f}")

    # 5. Robustness: the same online comparison over five random seeds
    print("\nseeds 1-5, online, B = 8 (p50 / p95 latency):")
    for seed in range(1, 6):
        wl = make_workload(400, 0.015, seed=seed)
        cells = []
        for name, fn in [("static", run_static), ("continuous", run_continuous)]:
            rs = clone(wl); busy, mk = fn(rs, 8); s = summarize(rs, busy, mk, 8)
            cells.append(f"{name} {s['p50_lat']:.0f} / {s['p95_lat']:.0f}")
        print(f"  seed {seed}: " + "   ".join(cells))


if __name__ == "__main__":
    main()
```

The first block reproduces the hand-worked timelines exactly: makespan 10 and 8, utilisation 0.700 and 0.875, mean TTFT 4.0 and 2.5.

## What the simulation shows

**Offline throughput.** With all 400 requests present at time 0 (the "offline" setting, where a batch job is sent all at once), batch size 1 is identical under both policies. At $B = 8$ continuous batching delivers 6.23 tokens per time unit against 2.16 for static, a 2.9× gain. At $B = 32$ the gain is 4.3×. Static throughput levels off early, because each batch runs as long as its longest member.

![Grouped bars of offline throughput in tokens per time unit for batch sizes 1 to 32: continuous batching rises from 0.98 to 13.3, static from 0.98 to 3.1](diagrams/53.2-offline-throughput.svg "Same 400 requests, same lengths, only the policy differs.")

Continuous utilisation falls as $B$ grows, from 0.90 at $B = 8$ to 0.66 at $B = 32$. My reading: with only 400 requests, the last part of the run has fewer requests than slots, so slots drain and sit empty. Batching gains also depend on $T_1$. At $B = 32$ continuous throughput is 18.06 with $T_1 = 0$, 13.27 with $T_1 = 0.02$, and 9.49 with $T_1 = 0.05$. The larger the step-time growth, the less a bigger batch buys, so the best batch size depends on the hardware, not only on the scheduler.

**Online latency.** Now requests arrive at random (Poisson arrivals at 0.015 requests per time unit; for seed 11 the 400 requests average 88.3 output tokens, so the offered load is about 1.3 tokens per unit) and the server runs with $B = 8$. Both policies finish the same work, so throughput is equal; the difference is waiting.

![Bars of p50 latency, p95 latency and mean TTFT for static and continuous batching at batch size 8: static is 272, 848 and 257 time units, continuous 56, 268 and 1.5](diagrams/53.2-online-latency.svg "One arrival rate, one seed in the chart; five more seeds are in the output above.")

Static p50 latency is 272 time units against 56 for continuous. Across five seeds the p50 ranges are 153 to 225 for static and 52 to 60 for continuous. Static batching also saturates at a lower rate. Its offline throughput at $B = 8$ is 2.16 tokens per unit, and the workload averages 84.6 tokens per request, so a rough capacity estimate is 2.16 / 84.6 ≈ 0.026 requests per unit. Above that rate the static queue grows without bound. This is an estimate from offline throughput, not a measured saturation point. Continuous batching has more headroom at the same $B$.

## Under the hood: what the model leaves out

- **KV cache memory.** Each running request stores keys and values for every token so far (the KV cache). The simulator caps the batch by slots only. Kwon et al. (2023) argue that fragmentation and redundant duplication of this memory waste it and limit the batch size; their PagedAttention method is a better manager for it. The paper reports 2–4× throughput over prior systems, including Orca, on its own benchmarks. I have not reproduced those numbers.
- **Prefill.** Processing a new prompt costs compute before its first token. A long prompt admitted into a running batch will, in my reasoning, slow every decode step in that iteration. The simulator ignores this, so it overstates continuous batching's TTFT advantage for long prompts.
- **Preemption.** When KV memory runs out, a server must evict a running request and recompute or swap its cache. This is not modelled.

> [!TRAP]
> Offline throughput and online latency answer different questions. A higher tokens-per-second number at saturation says nothing about the wait a user sees at moderate load.

> [!TRAP]
> $T_0$ and $T_1$ are assumptions. The batch-size trade-off moves with $T_1$ (see the sensitivity table), so do not read the 4.3× as a property of any real GPU.

> [!TRAP]
> One seed is not a result. A single workload draw can flatter one policy, which is why the online comparison reports five seeds.

> [!TRAP]
> Continuous batching does not remove queueing. A new request still waits for a free slot. When all $B$ slots are busy, its TTFT grows with the queue length.

> [!TRAP]
> Static batching is not wrong for every workload. If all requests have nearly the same length, the idle slots are few and the simpler policy costs little.

## Summary

- Static batching runs a batch until its longest request finishes, so finished slots sit idle. Heavy-tailed output lengths make this worse.
- Continuous batching decides the batch after every decode step. Finished requests leave at once, and waiting requests take their slots.
- In the worked example, continuous batching cuts the makespan from 10 to 8 steps and raises slot utilisation from 70% to 87.5%.
- In the simulator, continuous batching lifts offline throughput 2.9× at $B = 8$, and cuts online p50 latency from 272 to 56 time units at one arrival rate.
- Real gains depend on the step-time curve, KV memory and prefill, none of which the simple model includes.

### Question 1: Calculation

Three requests with output lengths 1, 3 and 2 tokens arrive at time 0. There are two slots and each step takes one time unit. What are the makespans under static and under continuous batching?

<details><summary>Show solution</summary>

Static: batch {r1 (1), r2 (3)} runs 3 steps. Batch {r3 (2)} runs 2 more. Makespan 5.

Continuous: r1 and r2 start. r1 finishes at time 1, and r3 takes its slot. r3 finishes at time 3, and r2 also finishes at time 3. Makespan 3.

### Question 2: Prediction

Continuous batching runs with $B = 8$, and all 8 slots are busy when a new request arrives. What does its TTFT include, and what happens to mean TTFT as the arrival rate rises toward capacity?

<details><summary>Show solution</summary>

TTFT includes the time the request waits in the queue for a free slot, plus the step that produces its first token. The queue wait is the large term. As the arrival rate approaches capacity, queues grow and mean TTFT rises sharply, the same effect the static run shows in the online table (mean TTFT 257 units against 1.5 for continuous at a moderate rate).

</details>

### Question 3: Bug spotting

Here is an admission step from a scheduler:

```python
if waiting and len(running) < max_batch:
    running.append(waiting.pop(0))
```

Describe the bug and its effect.

<details><summary>Show solution</summary>

The `if` admits at most one request per iteration. If the batch is empty and five requests are waiting, the server runs four slots empty for several steps before filling them. The fix is `while`, as in the simulator: it fills every free slot before the decode step. The bug does not change the output of a single request, only the throughput and TTFT.

</details>

### Question 4: Explanation

Two workloads have the same mean output length. In workload A every request needs 44 tokens. In workload B most need 20 tokens, but one in twenty needs 500. Which one makes static batching's utilisation worse, and why?

<details><summary>Show solution</summary>

Workload B. Under static batching each batch runs for its longest member. A batch that contains one 500-token request holds its other slots idle for up to 480 steps. Workload A has no slack, so static batching does nearly as well as continuous. The heavy tail is what creates the waste.

</details>
