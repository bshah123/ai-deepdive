In this lesson you will explain why a serving engine can reuse another request's attention keys and values (KV) only when the prompts match exactly from the start, and why the reusable part must be aligned to whole blocks. You will build a small prefix cache, run four experiments on it, and size its memory.

**You need:** the KV cache and why it grows with context (Lesson 29.1), paged KV blocks (Lesson 29.2), and continuous batching (Lesson 53.2).

## The problem: the same start, computed again

Most production requests begin with the same text: a system prompt of instructions, tool definitions or few-shot examples. Before the first output token, the server runs prefill over the whole prompt and computes keys and values for every token at every layer. Time to first token (TTFT, Lesson 53.1) grows with that work. If 2,048 of a request's 2,176 prompt tokens match the previous request, prefill recomputes 2,048 tokens for nothing.

Prefix caching keeps the KV of earlier prompts and reuses it when a new prompt starts the same way. Two questions decide how well it works: what counts as "the same start", and how much memory the cache can hold.

## Intuition: blocks, keyed by their whole prefix

Serving engines store KV in fixed-size blocks, and a block is the unit of reuse. The vLLM default is 16 tokens per block (Kwon et al., 2023, §7.2). The obvious key for a block is a hash of its own tokens. That key is wrong. Attention makes the keys and values of a token depend on every earlier token (Lesson 25.1), so the same four tokens after two different prefixes have different KV. The fix is to chain the hashes: each block's hash covers its parent block's hash and its own tokens (vLLM design document). A block's identity then covers its whole prefix.

![Three prompts drawn as rows of blocks, each block with its chained hash; P1 and P3 share the first two hashes, and P2's second block has the same tokens as P1's but a different hash](diagrams/53.3-block-chain.svg "Chained hashes. The same tokens after a different prefix get a different key.")

## Worked example, by hand

Use a toy block size of 4 tokens. Prompt P1 has 10 tokens: two full blocks, then a 2-token tail. Only full blocks are hashed, so the tail is never cached (vLLM design document: "We only cache full blocks"). P2 has the same second block, [9, 9, 9, 9], but a different first block, so its second hash changes too. P3 shares P1's first two blocks, so 8 tokens of P3 can come from cache. The code reproduces every hash and count.

The code is standard-library Python. It runs as printed, and every number in the lesson comes from it.

```python
import hashlib
import random
from collections import OrderedDict


def block_hashes(tokens, B):
    """Hash each FULL block of B tokens. Each hash also folds in the previous block's
    hash, so a block's identity covers its whole prefix. A partial last block gets no hash."""
    out, parent = [], "root"
    for i in range(len(tokens) // B):
        chunk = tuple(tokens[i * B:(i + 1) * B])
        parent = hashlib.sha256(repr((parent, chunk)).encode()).hexdigest()[:8]
        out.append(parent)
    return out


def content_only_hashes(tokens, B):
    """Wrong on purpose: hash each block's tokens alone, ignoring what came before."""
    return [hashlib.sha256(repr(tuple(tokens[i * B:(i + 1) * B])).encode()).hexdigest()[:8]
            for i in range(len(tokens) // B)]


class PrefixCache:
    """Toy LRU cache of KV blocks, keyed by chained block hash. Capacity is in blocks."""

    def __init__(self, capacity, B=16):
        self.cap, self.B = capacity, B
        self.lru = OrderedDict()              # oldest first; the first key is evicted first

    def serve(self, tokens):
        """Return (prompt tokens reused from cache, prompt length), then cache this prompt."""
        hs = block_hashes(tokens, self.B)
        hit = 0
        while hit < len(hs) and hs[hit] in self.lru:   # longest cached prefix
            hit += 1
        for h in reversed(hs):                # last block first, so the first block ends up newest
            if h in self.lru:
                self.lru.move_to_end(h)
            else:
                self.lru[h] = None
        while len(self.lru) > self.cap:       # evict least recently used
            self.lru.popitem(last=False)
        return hit * self.B, len(tokens)


def rand_tokens(rng, n):
    return [rng.randrange(50000) for _ in range(n)]


def toy_demo():
    P1 = [1, 2, 3, 4, 9, 9, 9, 9, 7, 7]      # 10 tokens: two full blocks of 4, plus 2 leftover
    P2 = [5, 6, 7, 8, 9, 9, 9, 9, 7, 7]      # same second block content, different first block
    P3 = [1, 2, 3, 4, 9, 9, 9, 9, 5, 5]      # shares the first two blocks with P1
    chain = {k: block_hashes(p, 4) for k, p in [("P1", P1), ("P2", P2), ("P3", P3)]}
    leading = lambda a, b: next((i for i, (x, y) in enumerate(zip(a, b)) if x != y), min(len(a), len(b)))
    naive_p1 = set(content_only_hashes(P1, 4))
    naive_false = sum(h in naive_p1 for h in content_only_hashes(P2, 4))
    return {
        "chain": chain,
        "leading_P1_P2": leading(chain["P1"], chain["P2"]),
        "leading_P1_P3": leading(chain["P1"], chain["P3"]),
        "naive_false_hits_P2": naive_false,
    }


def granularity(S, B=16):
    """Two prompts share a system prompt of S tokens. Full-block reuse vs token-level reuse."""
    rng = random.Random(S)
    sys_p = rand_tokens(rng, S)
    p1 = sys_p + rand_tokens(rng, 20)
    p2 = sys_p + rand_tokens(rng, 20)
    cache = PrefixCache(10**6, B)
    cache.serve(p1)
    block_reuse, _ = cache.serve(p2)
    lcp = 0
    while lcp < min(len(p1), len(p2)) and p1[lcp] == p2[lcp]:
        lcp += 1
    return {"S": S, "block_reuse": block_reuse, "token_reuse": lcp}


def trap(where, n=50, B=16):
    """One per-request ID (a timestamp, say) placed at the front or the back of a shared prefix."""
    rng = random.Random(3)
    prefix = rand_tokens(rng, 96)
    cache = PrefixCache(10**6, B)
    hit = total = 0
    for i in range(n):
        suffix = rand_tokens(rng, 32)
        rid = [900000 + i]
        p = rid + prefix + suffix if where == "front" else prefix + suffix + rid
        h, t = cache.serve(p)
        hit, total = hit + h, total + t
    return hit / total


def workload(seed=7, n_req=2000, tenants=8, sys_len=256):
    """Zipf-like tenant popularity; each request has a shared system prompt and a unique user suffix."""
    rng = random.Random(seed)
    sys_prompts = [rand_tokens(rng, sys_len) for _ in range(tenants)]
    weights = [1 / (k + 1) for k in range(tenants)]
    reqs = []
    for _ in range(n_req):
        t = rng.choices(range(tenants), weights)[0]
        reqs.append(sys_prompts[t] + rand_tokens(rng, rng.randrange(40, 201)))
    return reqs


def hit_rate(cap, reqs, B=16):
    cache = PrefixCache(cap, B)
    hit = total = 0
    for p in reqs:
        h, t = cache.serve(p)
        hit, total = hit + h, total + t
    return hit / total


def memory_and_prefill(layers=32, kv_heads=8, head_dim=128, bytes_per=2, sys_len=2048, users=64, suffix=128):
    """Arithmetic for an illustrative config (not any named model): K and V per token, fp16."""
    per_token = 2 * layers * kv_heads * head_dim * bytes_per
    MiB = 2**20
    computed = suffix                          # uncached prompt tokens, if sys_len is fully cached
    total = sys_len + suffix
    return {
        "bytes_per_token": per_token,
        "block16_MiB": per_token * 16 / MiB,
        "sys_copy_MiB": per_token * sys_len / MiB,
        "no_sharing_GiB": users * per_token * sys_len / 2**30,
        "shared_GiB": per_token * sys_len / 2**30,
        "prefill_fraction_computed": computed / total,
    }


def results():
    reqs = workload()
    caps = [0, 16, 32, 64, 128, 256, 512, 1024, 4096]
    return {
        "toy": toy_demo(),
        "granularity": [granularity(S) for S in [16, 40, 100, 2048]],
        "trap_front": trap("front"),
        "trap_back": trap("back"),
        "sweep": [{"cap": c, "hit": hit_rate(c, reqs)} for c in caps],
        "memory": memory_and_prefill(),
    }


if __name__ == "__main__":
    R = results()
    T = R["toy"]
    print("P1 chain:", T["chain"]["P1"])
    print("P2 chain:", T["chain"]["P2"])
    print("P3 chain:", T["chain"]["P3"])
    print("leading blocks shared, P1 vs P2:", T["leading_P1_P2"], "->", 4 * T["leading_P1_P2"], "tokens")
    print("leading blocks shared, P1 vs P3:", T["leading_P1_P3"], "->", 4 * T["leading_P1_P3"], "tokens")
    print("content-only hashing would call P2's block 2 a hit:", T["naive_false_hits_P2"], "block")
    print()
    for g in R["granularity"]:
        print(f"system prompt {g['S']:5d} tokens: block-level reuse {g['block_reuse']:5d}, token-level reuse {g['token_reuse']:5d}")
    print()
    print(f"trap: request ID at the front of the prompt -> hit rate {R['trap_front']:.3f}")
    print(f"trap: request ID at the back of the prompt  -> hit rate {R['trap_back']:.3f}")
    print()
    for row in R["sweep"]:
        print(f"cache capacity {row['cap']:5d} blocks -> token hit rate {row['hit']:.3f}")
    print()
    M = R["memory"]
    print(f"KV bytes per token: {M['bytes_per_token']}")
    print(f"one 16-token block: {M['block16_MiB']:.1f} MiB")
    print(f"one copy of a 2048-token system prompt: {M['sys_copy_MiB']:.0f} MiB")
    print(f"64 users, no sharing: {M['no_sharing_GiB']:.0f} GiB; shared: {M['shared_GiB']:.2f} GiB")
    print(f"prefill tokens computed for a 2048+128 prompt with the system prompt cached: {M['prefill_fraction_computed']:.3f} of the prompt")
```

Two results matter. P1 and P2 share no leading block, so the chained cache gives zero hits. A content-only hash would call P2's second block a hit, because [9, 9, 9, 9] appears in P1. That would reuse KV computed after the wrong prefix. The simulator's `PrefixCache` uses the chained hashes, and the experiments below use it.

## Experiment 1: only full blocks are reusable

A system prompt of S tokens followed by different user text is the common case. Reuse is block-aligned: the cache can only reuse $\lfloor S/16 \rfloor \times 16$ tokens. A token-level structure can reuse all S.

![Bars showing tokens a block-aligned cache cannot reuse: 0 for S equal to 16, 8 for 40, 4 for 100, and 0 for 2048; the dashed line marks the worst case of 15 tokens](diagrams/53.3-granularity.svg "Alignment loss is at most B minus 1 tokens per request, here B = 16.")

Here $B$ is the block size (16 in this experiment), not the batch size $B$ of Lesson 53.2. Each request loses at most $B-1 = 15$ tokens, so the loss is small when prompts are long. It is not zero, and it matters for short shared prefixes. SGLang's RadixAttention keys a radix tree by token sequences and stores its KV in pages of one token, so it can reuse at token boundaries (Zheng et al., 2023, §3). vLLM trades this granularity for a simpler, hash-based block table.

## Experiment 2: one ID in the wrong place

A common production bug puts a per-request value, such as a timestamp or request ID, at the top of the system prompt. Chained hashes make that bug total. The first block changes, so every later block changes too. The simulator runs 50 requests with a shared 96-token prefix in two layouts.

![Two bars: hit rate 0.000 when the request ID is first, and 0.729 when it is last](diagrams/53.3-request-id-trap.svg "The same content, reordered. Only the position of one token changed.")

With the ID last, each request reuses 96 of its 129 prompt tokens once the first request has warmed the cache. The average over all 50 requests is 0.729, because the first request reuses nothing. Put stable text first, and volatile text last.

## Experiment 3: how much cache, and what evicts it

The workload has eight tenants with Zipf-like popularity (tenant $k$ has weight $1/k$). Each tenant has a 256-token system prompt, or 16 blocks. Each request adds a unique suffix of 40 to 200 tokens. The simulator uses least-recently-used (LRU) eviction and touches a request's blocks so that its first block is the newest. The last block is evicted first, a leaf-first rule that matches both the vLLM design (the last block of a request "is less likely to be reused") and SGLang (it "evicts the least recently used leaf first", §3).

![Bars of token hit rate for capacities from 0 to 4096 blocks, rising from 0.000 to about 0.68, with a dashed ceiling at 0.681; the 128-block bar is highlighted](diagrams/53.3-capacity-sweep.svg "Hit rate versus cache capacity, 2,000 requests.")

The ceiling is set by the workload, not by the cache. Each request has 256 shared tokens out of about 376 on average, so about 68% of tokens are shareable, which matches 0.681 (reasoning from the workload). The more interesting point is at 128 blocks. That holds all eight system prompts, yet the hit rate is only 0.502. Unique suffixes push the less popular tenants' blocks out between their requests. For this workload, 512 to 1,024 blocks come within 1% of the ceiling.

## Experiment 4: memory and prefill arithmetic

Take an illustrative config: 32 layers, 8 KV heads, head dimension 128, fp16 (2 bytes). Each token stores a key and a value at every layer, so the cost is $2 \times 32 \times 8 \times 128 \times 2 = 131{,}072$ bytes, or 128 KiB per token. A 16-token block is 2 MiB, and a 2,048-token system prompt is 256 MiB per copy.

![Left: a grid of 64 tiles, one per user, each holding its own 256 MiB copy, totalling 16 GiB. Right: one tile for the shared copy, 0.25 GiB](diagrams/53.3-memory-sharing.svg "The same prompt, stored once or 64 times.")

Without sharing, 64 users with this prompt need 16 GiB. With one shared copy they need 0.25 GiB. Prefill also shrinks. For a 2,048 + 128 token prompt with the system prompt cached, only 128 of 2,176 tokens need new computation, which is 5.9%. This assumes prefill cost is roughly proportional to uncached tokens. New tokens still attend to the cached KV, so the saving is an approximation (reasoning, not a measurement).

## How production engines implement this

vLLM keeps a hash-to-block map and a free queue ordered for LRU, and it caches only full blocks (vLLM design document). Its hashes also include extra keys, such as LoRA adapter IDs and a `cache_salt`, so tenants can be isolated from one another. The design document warns that hashes may not be reproducible across Python or vLLM versions.

PagedAttention describes the underlying data structure. Each request has a block table that maps logical blocks to physical blocks. Each physical block has a reference count, and a write to a shared block triggers copy-on-write at block granularity (Kwon et al., 2023, §4.2–4.4).

SGLang's RadixAttention stores the prefix structure as a radix tree with a reference counter per node. Its scheduler orders requests by longest matched prefix, which the paper equates with depth-first order for an offline batch (Zheng et al., 2023, §3); the order is disrupted for online arrivals. The paper reports a 52.4% hit rate for one model in its one-month Chatbot Arena deployment (§6.2). That number depends on that workload and should not be used as a general figure.

> [!TRAP]
> Hashing the block's tokens without the parent hash gives false hits. The reused KV was computed under a different prefix, so the output is silently wrong.

> [!TRAP]
> A timestamp, request ID or user name at the top of the system prompt makes the hit rate 0 in the experiment. Move volatile text to the end of the prompt.

> [!TRAP]
> A prompt of length $n$ may lose up to $B-1$ tokens of reuse, because partial blocks are not cached. Short shared prefixes are hit hardest.

> [!TRAP]
> The measured hit rate is a property of one workload. The 0.681 ceiling comes from this simulator's 256-token prompts and suffix lengths. Measure your own traffic before you size a cache.

> [!TRAP]
> Sharing covers only the prompt prefix. Each request still needs its own blocks for its suffix and for every generated token.

## Summary

- A prefix cache reuses KV blocks only when the whole prefix up to the block matches. Chained hashes encode this.
- Only full blocks are reusable, so each request can lose up to B minus 1 tokens of reuse. Token-level structures such as RadixAttention avoid that loss.
- A volatile token at the front of a prompt can drop the hit rate to zero. Put volatile content last.
- Hit rate is capped by the shared fraction of traffic and limited by cache capacity. Unique suffixes evict shared prompts unless capacity is large enough.
- Sharing one copy of a long system prompt saves most of its memory when many users share it.

### Question 1: Calculation

A system prompt of 1,000 tokens is shared by all requests. The engine uses block size 16 and caches only full blocks. How many prompt tokens can be reused, and how many are recomputed?

<details><summary>Show solution</summary>

$\lfloor 1000/16 \rfloor = 62$ full blocks, so $62 \times 16 = 992$ tokens are reusable. The remaining 8 tokens are recomputed. That is consistent with the bound of $B-1 = 15$ tokens.

</details>

### Question 2: Prediction

In Experiment 2, the request ID moves from the front of the prompt to the end. Predict the hit rate and explain why.

<details><summary>Show solution</summary>

The hit rate rises from 0.000 to 0.729. With the ID first, block 0 changes on every request, so the chained hash of every later block changes too. With the ID last, the 96-token prefix forms six identical blocks, and the suffix is always new.

</details>

### Question 3: Bug-spotting

A teammate says: "The cache hash is `sha256(block_tokens)`. It is fast, and the tests pass." Find the bug.

<details><summary>Show solution</summary>

The hash ignores the prefix. A block with identical tokens after a different prefix gets the same key, so the cache returns KV computed under the wrong context. In the toy example, P2's second block [9, 9, 9, 9] would hit P1's cache entry. The tests pass because they probably do not contain the same block after two different prefixes. The fix is to chain the parent hash into each block's hash.

</details>

### Question 4: Explanation

Why is the hit rate at 128 blocks (0.502) below the ceiling (0.681), even though 128 blocks is exactly enough to hold all eight system prompts?

<details><summary>Show solution</summary>

Every request also writes its unique suffix blocks into the cache. Under LRU, those blocks push out the system prompt blocks of less popular tenants before their next request arrives. The system prompts fit on their own, but not alongside the suffixes. The ceiling is reached only when the cache is large enough to keep the system prompts resident between requests.

</details>

### Question 5: Calculation

A model has 80 layers, 8 KV heads, head dimension 128, and fp16 KV. A 4,096-token prompt is shared by 32 users. How much memory do the 32 users need without sharing, and with one shared copy?

<details><summary>Show solution</summary>

Per token: $2 \times 80 \times 8 \times 128 \times 2 = 327{,}680$ bytes. One 4,096-token copy is $4{,}096 \times 327{,}680 = 1{,}342{,}177{,}280$ bytes, or 1.25 GiB. Without sharing, 32 copies need 40 GiB. With one shared copy, they need 1.25 GiB. Shared copies ignore each user's suffix and generated tokens, so the real total is higher.

</details>
