This lesson explains why a server for large language models (LLMs) runs out of GPU memory long before it runs out of compute, and how the open-source engine vLLM avoids that with a paged key-value (KV) cache and continuous batching. You will be able to size a KV cache from a model's configuration, read a block table, and say why a fixed-slot server stalls. You will also see how to start a real vLLM server, but every measurement here comes from a simulation, not a GPU.

**You need:** the KV cache from Lesson 27.2, the memory arithmetic from Lesson 29.1, and basic Python.

## The problem serving solves

Serving an LLM runs two phases per request. *Prefill* reads the whole prompt once. *Decode* then produces one token per step. To avoid recomputing the past at every step, each request keeps the keys and values of all its earlier tokens in GPU memory. That store is the KV cache. Three things make it hard to serve many requests at once: the cache is large, the output length is unknown, and batches wait for their slowest member.

**The cache is large.** For a decoder with $L$ layers, $H_{kv}$ key-value heads, head dimension $d$ and $b$ bytes per element, each token costs

$$
\text{bytes per token} = 2 \cdot L \cdot H_{kv} \cdot d \cdot b
$$

where the factor 2 is one key vector and one value vector. Take an illustrative configuration (not any specific model) with $L = 32$, $H_{kv} = 8$, $d = 128$ and fp16 (16-bit floats, $b = 2$). Each token then costs 131,072 bytes, or 128 KiB (kibibytes, $2^{10}$ bytes). A 16 GiB cache holds 131,072 such tokens, and a 2,048-token conversation takes 256 MiB.

**The output length is unknown.** The server cannot know when a request will stop. A system that reserves room for the longest allowed sequence leaves most of that room empty for short answers.
**Batches wait for their slowest member.** If a fixed group of requests runs until every one finishes, a request that needs 3 tokens holds its slot until a 200-token request ends.

## Intuition: paging, borrowed from operating systems

The vLLM paper (Kwon et al., 2023) names the waste directly: KV memory is lost to "fragmentation and redundant duplication". It measures that existing systems use only 20.4% to 38.2% of their KV memory for actual token states. Its method, PagedAttention, borrows virtual memory from operating systems. The cache is split into fixed-size blocks. Each request has a block table that maps its logical blocks, in order, to physical blocks in any position. A block is allocated only when the previous one is full.

![Request path: client to HTTP API server to engine core with queue and scheduler to GPU worker holding model and KV blocks](diagrams/54.1-serving-path.svg "One request's path through the server. The arrows are the only places a request waits.")

The vLLM architecture documentation describes the engine in these terms. Each accelerator is controlled by one worker process. A scheduler fills a per-step token budget with tokens from running and waiting requests. When a request cannot get new KV blocks, the scheduler preempts running requests and frees their blocks. Under first come first served (FCFS), the last-admitted request is preempted first, and it is recomputed later rather than swapped back from CPU memory.

## Worked example: a block table

The paper's default block size is 16 tokens (Section 7.2). A 40-token prompt needs $\lceil 40/16 \rceil = 3$ blocks, and the last block holds $40 - 32 = 8$ tokens. Token $t$ sits in logical block $\lfloor t/16 \rfloor$ at offset $t \bmod 16$. The block table converts the logical block into a physical one, and the physical ids need not be consecutive.

![Three logical blocks of request A point to physical blocks 7, 2 and 9 in a 10-block pool; the other physical blocks are free](diagrams/54.1-block-table.svg "Logical blocks are contiguous for the request. Physical blocks are not.")

## Code: arithmetic and a scheduler simulation

The script below uses only the standard library, so it runs in the browser. It computes the cache size, builds a block table, compares reservation with paging over 200 requests, and compares static with continuous batching. The model is deliberately simple: each step, every running request produces one token; prefill cost is ignored; a step takes the same time whatever the batch size; and there is no GPU. Every number it prints is the output of this code.

```python
import random
from collections import deque

# ---- 1. How big is the KV cache? (arithmetic with an illustrative config) ----
LAYERS, KV_HEADS, HEAD_DIM, BYTES = 32, 8, 128, 2     # BYTES = 2 for fp16
per_token = 2 * LAYERS * KV_HEADS * HEAD_DIM * BYTES   # 2 = one key and one value vector
print("bytes per token:", per_token)
print("tokens that fit in 16 GiB:", 16 * 2**30 // per_token)

BLOCK = 16                                             # tokens per KV block (vLLM default)
print("bytes per block:", BLOCK * per_token)

# ---- 2. Block table: logical positions -> physical blocks ----
class BlockPool:
    def __init__(self, free_ids):
        self.free = deque(free_ids)                    # physical block ids not in use
    def alloc(self):
        return self.free.popleft() if self.free else None
    def release(self, ids):
        self.free.extend(ids)

def blocks_for(n_tokens):
    return -(-n_tokens // BLOCK)                       # ceiling division

pool = BlockPool(free_ids=[7, 2, 9, 0, 1, 3, 4, 5, 6, 8])   # earlier requests left this order
n_prompt = 40
table = [pool.alloc() for _ in range(blocks_for(n_prompt))]
print("block table:", table)
for t in (0, 15, 16, 37):
    logical, offset = divmod(t, BLOCK)
    print(f"token {t:2d} -> logical block {logical}, offset {offset:2d} -> physical block {table[logical]}")
print("tokens in last block:", n_prompt - BLOCK * (len(table) - 1))

# ---- 3. Reserve-max versus allocate-per-block (simulation, decode only) ----
MAX_LEN = 2048                                         # max_model_len: reserved per request by contiguous systems
POOL = 8192                                            # KV slots on the device = 512 blocks of 16
rng = random.Random(0)
reqs = [(rng.randint(16, 512), rng.randint(16, 512)) for _ in range(200)]   # (prompt tokens, output tokens)
total_out = sum(o for _, o in reqs)

def run_contiguous(reqs):
    queue, running, lens = deque(reqs), [], []         # running: tokens left to generate
    free, steps, stored, reserved, batch = POOL, 0, 0, 0, 0
    while queue or running:
        while queue and free >= MAX_LEN:
            p, o = queue.popleft()
            running.append(o); lens.append(p); free -= MAX_LEN
        steps += 1
        lens = [n + 1 for n in lens]; running = [r - 1 for r in running]
        stored += sum(lens); reserved += len(running) * MAX_LEN; batch += len(running)
        keep = [i for i, r in enumerate(running) if r > 0]
        free += (len(running) - len(keep)) * MAX_LEN
        running = [running[i] for i in keep]; lens = [lens[i] for i in keep]
    return steps, batch / steps, stored / reserved

def run_paged(reqs):
    pool = BlockPool(free_ids=range(POOL // BLOCK))
    queue = deque(reqs)
    running = []                                       # dict per request
    steps = preempts = wasted = stored = reserved = batch = 0
    while queue or running:
        while queue and len(pool.free) >= blocks_for(queue[0][0]):
            p, o = queue.popleft()
            running.append({"prompt": p, "out": o, "n": p, "left": o,
                            "blocks": [pool.alloc() for _ in range(blocks_for(p))]})
        while running and sum(blocks_for(r["n"] + 1) - len(r["blocks"]) for r in running) > len(pool.free):
            victim = running.pop()                     # last admitted is preempted first
            pool.release(victim["blocks"])
            wasted += victim["out"] - victim["left"]   # tokens that must be regenerated
            preempts += 1
            queue.appendleft((victim["prompt"], victim["out"]))
        for r in running:                              # one decode step: one new token each
            while len(r["blocks"]) < blocks_for(r["n"] + 1):
                r["blocks"].append(pool.alloc())
            r["n"] += 1; r["left"] -= 1
        steps += 1; batch += len(running)
        stored += sum(r["n"] for r in running)
        reserved += sum(len(r["blocks"]) for r in running) * BLOCK
        for r in running:
            if r["left"] == 0:
                pool.release(r["blocks"])
        running = [r for r in running if r["left"] > 0]
    return steps, batch / steps, stored / reserved, preempts, wasted

s_steps, s_batch, s_util = run_contiguous(reqs)
print(f"contiguous: steps={s_steps} mean_batch={s_batch:.2f} tokens_per_step={total_out / s_steps:.2f} "
      f"utilization={s_util:.3f}")
p_steps, p_batch, p_util, pre, waste = run_paged(reqs)
print(f"paged:      steps={p_steps} mean_batch={p_batch:.2f} tokens_per_step={total_out / p_steps:.2f} "
      f"utilization={p_util:.3f} preemptions={pre} regenerated_tokens={waste}")

# ---- 4. Static versus continuous batching (4 slots, decode only) ----
def run_batching(outs, slots, continuous):
    queue, running, steps, work = deque(outs), [], 0, 0
    while queue or running:
        if continuous:
            while queue and len(running) < slots:
                running.append(queue.popleft())
        elif not running:
            running = [queue.popleft() for _ in range(min(slots, len(queue)))]
        steps += 1; work += len(running)
        running = [r - 1 for r in running if r > 1]
    return steps, work / (steps * slots)

rng2 = random.Random(1)
outs = [rng2.randint(8, 256) for _ in range(64)]
st, su = run_batching(outs, 4, continuous=False)
ct, cu = run_batching(outs, 4, continuous=True)
print(f"static:     steps={st} slot_utilization={su:.3f} tokens_per_step={sum(outs) / st:.2f}")
print(f"continuous: steps={ct} slot_utilization={cu:.3f} tokens_per_step={sum(outs) / ct:.2f}")

# ---- 5. Schedule trace for a small example: which request occupies each slot at each step ----
def trace(outs, slots, continuous):
    queue, running, log = deque(enumerate(outs)), [], []
    while queue or running:
        if continuous:
            while queue and len(running) < slots:
                running.append(list(queue.popleft()))  # [request id, tokens left]
        elif not running:
            running = [list(queue.popleft()) for _ in range(min(slots, len(queue)))]
        log.append([rid for rid, _ in running])
        for r in running:
            r[1] -= 1
        running = [r for r in running if r[1] > 0]
    return log

small = [3, 8, 2, 5, 4, 6]                              # output tokens per request
for name, cont in (("static", False), ("continuous", True)):
    log = trace(small, 3, cont)
    print(f"{name} trace ({len(log)} steps):", log)
```

```output

bytes per block: 2097152
block table: [7, 2, 9]
token  0 -> logical block 0, offset  0 -> physical block 7
token 15 -> logical block 0, offset 15 -> physical block 7
token 16 -> logical block 1, offset  0 -> physical block 2

```

Read the output in three parts.

- **Block table.** Token 37 is in logical block 2 at offset 5, so it lives in physical block 9 at offset 5. The last block of a 40-token prompt holds 8 tokens.
- **Reservation versus paging.** With reservation, the 8,192-slot pool holds only four requests of 2,048 slots, and the mean batch is 3.96. Only 22% of the reserved slots hold tokens. With paging, 17.23 requests run on average and 98% of the allocated slots hold tokens. The remaining 2% is the unfilled tail of each last block. The price is 305 preemptions that discard 3,777 tokens, which must be generated again.
- **Batching.** With four slots and 64 requests, static batching keeps 60% of slot-steps busy and continuous batching keeps 95%.

![Bar chart: KV memory utilisation 0.22 for reservation and 0.98 for paging; decode slot utilisation 0.60 for static and 0.95 for continuous batching](diagrams/54.1-kv-utilization.svg "Results of the simulation. These come from one seeded workload and one set of assumptions.")

The simulated tokens per step rise from 3.96 to 16.11. That is a fact about the model, not a prediction for a GPU. Real step time grows with batch size, because each step reads more cache and does more arithmetic. The paper's measured claim is narrower: vLLM improves throughput by 2–4× over FasterTransformer and Orca at the same latency, on the authors' models, hardware and workloads (Kwon et al., 2023).

Continuous batching is the mechanism behind the 95%. Orca (Yu et al., 2022) calls the idea iteration-level scheduling: the batch is re-decided at every step, not once per group of requests. Six requests with 3, 8, 2, 5, 4 and 6 output tokens on three slots show the difference. Both schedules produce 28 tokens. Static needs 14 steps and continuous needs 13.

![Two timelines of six requests on three slots: static batching finishes in 14 steps with idle slots after each group; continuous batching refills freed slots and finishes in 13 steps](diagrams/54.1-batching-timeline.svg "Each column is one decode step. Dashed cells are idle slots.")

## Common traps

> [!TRAP] **Reserved slots are not free.** In the simulation, reservation at a 2,048-token maximum used 22% of its memory. A shorter maximum helps, but no request longer than the whole cache can run at all.

> [!TRAP] **The simulation is not a benchmark.** Its tokens per step assume a constant step time and no prefill. Use it to see the mechanism, not to predict throughput.

> [!TRAP] **Preemption repeats work.** The 3,777 regenerated tokens are computed twice. Preemption therefore lowers throughput even though no request fails.

> [!TRAP] **A utilisation above 1 is a bug.** Busy slot-steps divided by all slot-steps cannot exceed 1. A value above 1 means the numerator counts something a slot cannot produce, or the denominator counts too few steps.

## Summary

- A KV cache costs $2 L H_{kv} d b$ bytes per token and grows with every generated token.
- Reserving the maximum length per request wasted most of the memory in the simulation (22% used).
- PagedAttention allocates 16-token blocks on demand through a block table, so physical blocks need not be adjacent.
- Continuous batching refills a slot as soon as its request ends. Static batching waits for the whole group.
- The simulation teaches the mechanism. Speed on real hardware needs a GPU run.

## Quiz time

### Question 1: Cache sizing (calculation)

A model has 48 layers, 8 KV heads, head dimension 128, and fp16 values. How many full 16-token blocks fit in 8 GiB?

<details><summary>Solution</summary>

Bytes per token $= 2 \cdot 48 \cdot 8 \cdot 128 \cdot 2 = 196{,}608$. Bytes per block $= 16 \cdot 196{,}608 = 3{,}145{,}728$, which is 3 MiB. Eight GiB is 8,192 MiB, and $8192 / 3 = 2730.67$. So 2,730 full blocks fit. They use 8,190 MiB, leaving 2 MiB.

</details>

### Question 2: Block arithmetic (prediction)

Blocks hold 16 tokens. Which logical block and offset hold token 35 (counting from 0)? How many slots of the last block are in use after a 33-token prompt has been prefilled?

<details><summary>Solution</summary>

Token 35 is in logical block $\lfloor 35/16 \rfloor = 2$ at offset $35 - 32 = 3$. Its physical block depends on the table. A 33-token prompt needs 3 blocks, and only the first slot of block 2 is used, so the answer is 1.

</details>

### Question 3: Bug-spotting

A colleague reports "slot utilisation 1.3" for a four-slot server. The code divides total generated tokens by (steps × 4). What is wrong?

<details><summary>Solution</summary>

In a decode-only model, each busy slot produces exactly one token per step, so tokens divided by slot-steps is at most 1. A value of 1.3 means the numerator counts something a slot does not produce per step, such as prompt tokens, or the step count is too small, for example because steps with an empty batch were dropped. Check both counts against the trace.

</details>

### Question 4: Explanation

Suppose every request in a static batch has the same output length. Why does the schedule then lose no slot-steps?

<details><summary>Solution</summary>

All requests in the batch finish at the same step, so no slot sits idle before the batch ends. Within one batch, busy fraction equals mean length divided by maximum length, so the loss comes entirely from variance in output lengths. This is reasoning from the definition, not a measured result.

</details>
