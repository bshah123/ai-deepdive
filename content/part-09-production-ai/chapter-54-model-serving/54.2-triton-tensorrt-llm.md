After this lesson you can explain why a serving stack compiles a model for fixed shapes, how a dynamic batcher trades queueing delay for throughput, and how the key-value (KV) cache sets the batch size a GPU can hold. **You need:** the vLLM serving lesson (Lesson 54.1), and the idea that a graphics processing unit (GPU) runs one kernel over many values at once.

No GPU is needed. Every number comes from a counting model or a simulation in the code, and the Triton configuration is written and checked, not deployed.

## The problem

A server that handles one request at a time wastes the GPU. Each request pays a fixed launch cost, and the matrix units sit idle between small kernels. A serving stack attacks this in three ways. It makes each kernel cheaper by compiling the model. It shares fixed costs across requests by batching them. It fits per-request memory into the device.

Triton Inference Server (Triton) is the server that accepts requests and runs batches. TensorRT-LLM is NVIDIA's library for large language model (LLM) inference. The two are often paired, but they are separate layers.

![Two paths: an offline compile step produces an engine file, which is loaded into the model repository; online, client requests pass through Triton's queue and batcher to the engine on the GPU](diagrams/54.2-pipeline.svg "Compile once offline, then serve online.")

## Lever 1: compile, and fuse kernels

Consider bias add, then GELU (Gaussian Error Linear Unit, a common transformer activation), then a residual add. Run as three kernels, each one writes its result to GPU memory. Fusion runs all three in one kernel, so the intermediate values stay in fast on-chip storage. The arithmetic is identical; only memory traffic changes.

Worked by hand: take an activation of 8 by 4096 values, so $S = 32{,}768$ values. At 2 bytes each in fp16 (16-bit floating point), the unfused chain moves 7 tensor passes: bias reads $x$ and writes $t_1$ ($2S$), GELU reads $t_1$ and writes $t_2$ ($2S$), the residual reads $t_2$ and $r$ and writes $y$ ($3S$). That is $7 \times 32{,}768 \times 2 = 458{,}752$ bytes. The fused kernel reads $x$ and $r$ and writes $y$, which is $3S$, or $196{,}608$ bytes. The ratio is $7/3 \approx 2.33$.

Check the counts and the equivalence in NumPy:

```python
import numpy as np

def gelu(x):   # tanh approximation of GELU, a common transformer activation
    return 0.5 * x * (1.0 + np.tanh(np.sqrt(2.0 / np.pi) * (x + 0.044715 * x**3)))

rng = np.random.default_rng(54)
batch, hidden = 8, 4096
x = rng.standard_normal((batch, hidden)).astype(np.float32)
r = rng.standard_normal((batch, hidden)).astype(np.float32)
bias = rng.standard_normal(hidden).astype(np.float32)

def unfused(x, bias, r):      # three kernels; each writes a full tensor back to GPU memory
    t1 = x + bias             # reads x, writes t1
    t2 = gelu(t1)             # reads t1, writes t2
    return t2 + r             # reads t2 and r, writes y

def fused(x, bias, r):        # one kernel; intermediates stay in fast on-chip registers
    return gelu(x + bias) + r # reads x and r, writes y

S = batch * hidden
B = 2                                 # bytes per fp16 element
unfused_bytes = (2 + 2 + 3) * S * B   # 2S + 2S + 3S element transfers
fused_bytes = 3 * S * B               # read x, read r, write y

print(f"elements per tensor: {S}")
print(f"unfused traffic: {unfused_bytes} bytes")
print(f"fused traffic:   {fused_bytes} bytes")
print(f"ratio: {unfused_bytes / fused_bytes:.3f}")
print("max |unfused - fused| =", float(np.max(np.abs(unfused(x, bias, r) - fused(x, bias, r)))))
```

```output
elements per tensor: 32768
unfused traffic: 458752 bytes
fused traffic:   196608 bytes
ratio: 2.333
max |unfused - fused| = 0.0
```

![Two bars: the unfused chain moves 0.459 MB and the fused kernel moves 0.197 MB](diagrams/54.2-fusion-traffic.svg "Counted bytes for one activation tensor. Fewer passes, same numbers.")

This counts bytes, not time. For elementwise operations, run time is often close to bytes moved divided by memory bandwidth (my own reasoning; not measured here). Large matrix multiplications are limited differently, so fusion is not a universal speed-up.

## Lever 2: dynamic batching

Triton's dynamic batcher combines individual requests into one batch. The Triton documentation says requests are added in the order received, and that the batcher delays sending a batch only as long as no request has waited longer than `max_queue_delay_microseconds`. When that delay expires, it sends the batch as it stands, even if the batch is not full.

To study this, the code below simulates one server with first-in-first-out (FIFO) queueing and Poisson arrivals. The costs are assumptions: 8 ms of fixed work per batch plus 0.5 ms per request in it. A server doing one request at a time can therefore handle about 118 requests per second. Batches of 8 can handle about 667.

```python
import numpy as np

A_FIXED, A_PER_REQ = 0.008, 0.0005   # assumed costs: 8 ms per batch + 0.5 ms per request in it

def simulate(rate, max_batch, delay, n=20000, seed=54):
    rg = np.random.default_rng(seed)
    arr = np.cumsum(rg.exponential(1.0 / rate, n))    # Poisson arrivals, in seconds
    lat = np.empty(n)
    sizes = []
    t_free, i = 0.0, 0
    while i < n:
        s0 = max(t_free, arr[i])                              # server free and request i waiting
        full_t = arr[i + max_batch - 1] if i + max_batch - 1 < n else np.inf
        d = min(max(s0, full_t), max(s0, arr[i] + delay))     # dispatch: batch full OR oldest waited `delay`
        k = 0
        while i + k < n and k < max_batch and arr[i + k] <= d:
            k += 1
        done = d + A_FIXED + A_PER_REQ * k
        lat[i:i + k] = done - arr[i:i + k]
        sizes.append(k)
        t_free, i = done, i + k
    return dict(mean_ms=1e3 * lat.mean(), p95_ms=1e3 * np.percentile(lat, 95),
                mean_batch=float(np.mean(sizes)), throughput=n / (t_free - arr[0]))

print(f"capacity, one request per batch: {1 / (A_FIXED + A_PER_REQ):.1f} req/s")
print(f"capacity, batches of 8:          {8 / (A_FIXED + 8 * A_PER_REQ):.1f} req/s")
r = simulate(200.0, 1, 0.0)
print(f"max_batch=1, 200 req/s: mean {r['mean_ms']:.0f} ms, p95 {r['p95_ms']:.0f} ms, "
      f"batch {r['mean_batch']:.2f}, served {r['throughput']:.1f}/s")
for delay_ms in [0, 1, 2, 5, 10]:
    r = simulate(200.0, 8, delay_ms / 1e3)
    print(f"max_batch=8, delay={delay_ms:>2} ms, 200 req/s: mean {r['mean_ms']:.1f} ms, "
          f"p95 {r['p95_ms']:.1f} ms, batch {r['mean_batch']:.2f}, served {r['throughput']:.1f}/s")
```

```output
capacity, one request per batch: 117.6 req/s
capacity, batches of 8:          666.7 req/s
max_batch=1, 200 req/s: mean 34703 ms, p95 66495 ms, batch 1.00, served 117.6/s
max_batch=8, delay= 0 ms, 200 req/s: mean 13.5 ms, p95 18.2 ms, batch 1.96, served 199.7/s
max_batch=8, delay= 1 ms, 200 req/s: mean 13.5 ms, p95 18.1 ms, batch 2.01, served 199.7/s
max_batch=8, delay= 2 ms, 200 req/s: mean 13.6 ms, p95 18.1 ms, batch 2.05, served 199.7/s
max_batch=8, delay= 5 ms, 200 req/s: mean 14.1 ms, p95 18.2 ms, batch 2.26, served 199.7/s
max_batch=8, delay=10 ms, 200 req/s: mean 16.5 ms, p95 20.5 ms, batch 3.01, served 199.7/s
```

At 200 requests per second, one-at-a-time serving is overloaded. Its capacity is 118 requests per second, so the queue grows for the whole 20,000-request run and the mean latency reaches 34.7 seconds. Batching of up to 8 serves the same load at 13.5 ms mean.

The delay parameter trades latency for batch size. Here throughput equals the arrival rate, so a longer delay buys no extra throughput; it only adds waiting. A delay pays off when arrivals fill a batch within the window and the server is the bottleneck. That is my reasoning from the simulation, not a result I measured on hardware.

## The model repository and the config file

Triton loads models from a repository on disk. The Triton documentation specifies the TensorRT plan layout as `<model-name>/config.pbtxt` plus a numerically named version directory holding `model.plan`, and says that version directories whose names start with "0" are ignored. The configuration's `dims` exclude the batch dimension: for a batching model the full shape is the batch dimension followed by `dims`.

The code below builds that layout in a temporary folder and checks it against the rules above. It writes a configuration with a 2 ms batching window. The `model.plan` file is an empty placeholder, since a real plan is the compiled engine.

```python
import tempfile
from pathlib import Path

CONFIG = """name: "toy_engine"
platform: "tensorrt_plan"
max_batch_size: 8
dynamic_batching {
  max_queue_delay_microseconds: 2000
}
"""

def build_repo(root):
    model_dir = root / "toy_engine"
    (model_dir / "1").mkdir(parents=True)
    (model_dir / "config.pbtxt").write_text(CONFIG)
    (model_dir / "1" / "model.plan").write_bytes(b"")   # placeholder; a real plan is the compiled engine
    return model_dir

def check_layout(model_dir):
    versions = [p for p in model_dir.iterdir() if p.is_dir() and p.name.isdigit() and not p.name.startswith("0")]
    assert (model_dir / "config.pbtxt").exists(), "config.pbtxt missing"
    assert versions, "need at least one numeric version directory"
    for v in versions:
        assert (v / "model.plan").exists(), f"{v.name}/model.plan missing"
    return sorted(p.relative_to(model_dir.parent).as_posix() for p in model_dir.rglob("*") if p.is_file())

with tempfile.TemporaryDirectory() as tmp:
    model_dir = build_repo(Path(tmp) / "model_repository")
    print("\n".join(check_layout(model_dir)))
    print("--- config.pbtxt ---")
    print((model_dir / "config.pbtxt").read_text(), end="")
```

```output
toy_engine/1/model.plan
toy_engine/config.pbtxt
--- config.pbtxt ---
name: "toy_engine"
platform: "tensorrt_plan"
max_batch_size: 8
dynamic_batching {
  max_queue_delay_microseconds: 2000
}
```

This config omits the `input` and `output` declarations, which a real deployment needs. I did not verify the tensor declarations for TensorRT-LLM engines, so treat this file as a layout example only.

## Lever 3: the KV cache sets the batch size

During generation, each layer stores one key vector and one value vector per token, for each key-value head. That store is the KV cache, and it grows with batch size times sequence length.

Worked by hand, for an assumed 7B-class shape of 32 layers, 32 heads, head dimension 128 and fp16: $2 \times 32 \times 32 \times 128 \times 2 = 524{,}288$ bytes, which is 512 KiB per token. Batch 8 at 4,096 tokens holds $32{,}768$ tokens, so the cache is 16 GiB. Subtract about 14 GB of weights (7 billion parameters at 2 bytes) and an assumed 6 GB reserve from an 80 GB GPU, and 60 GB remains. At 4,096 tokens per sequence, that holds 27 sequences.

```python
layers, kv_heads, head_dim, bytes_per_value = 32, 32, 128, 2   # assumed 7B-class shape, fp16
per_token = 2 * layers * kv_heads * head_dim * bytes_per_value # 2 = one key and one value vector
print("KV bytes per token:", per_token)

GB = 1e9
weights = 7e9 * bytes_per_value    # assumed 7e9 parameters
reserve = 6e9                      # assumed activations and workspace
budget = 80 * GB - weights - reserve
print(f"weights {weights / GB:.0f} GB, budget for KV cache {budget / GB:.0f} GB")

seq = 4096
for batch in [8, 16, 32]:
    kv = batch * seq * per_token
    total = weights + reserve + kv
    print(f"batch {batch:>2} x {seq} tokens: KV {kv / GB:5.1f} GB, total {total / GB:5.1f} GB, "
          f"fits: {total <= 80 * GB}")
print("max batch at 4096 tokens:", int(budget // (seq * per_token)))
```

```output
KV bytes per token: 524288
weights 14 GB, budget for KV cache 60 GB
batch  8 x 4096 tokens: KV  17.2 GB, total  37.2 GB, fits: True
batch 16 x 4096 tokens: KV  34.4 GB, total  54.4 GB, fits: True
batch 32 x 4096 tokens: KV  68.7 GB, total  88.7 GB, fits: False
max batch at 4096 tokens: 27
```

![Stacked bars of weights, reserve and KV cache for batch sizes 8, 16 and 32 at 4,096 tokens, against a dashed 80 GB line; batch 32 exceeds it](diagrams/54.2-kv-budget.svg "Memory budget on an 80 GB GPU. The KV cache grows with batch size; the weights do not.")

The 512 KiB per token and the 7 billion parameter count are assumptions. Llama 2 7B has a 4k context and no grouped-query attention (Touvron et al., 2023, Table 1), but the layer and head counts were not in the text I read. Check the model's configuration file before sizing a real deployment.

An engine is compiled for a maximum batch size and maximum lengths, which fix its buffer sizes. This is my reasoning about fixed-shape engines, not something I confirmed in TensorRT-LLM documentation. Choosing the maximum batch is therefore a memory decision as much as a throughput decision.

## Common traps

> [!TRAP]
> `dims` excludes the batch dimension. Writing the batch size into `dims` as well gives Triton a shape it will not expect.

> [!TRAP]
> A server that looks fine at 60 requests per second can collapse at 200. The one-at-a-time run averages 12.9 ms at 60 requests per second and 34.7 seconds at 200. Benchmark at the load you will serve.

> [!TRAP]
> A longer batching delay does not add throughput when arrivals are the limit. It only adds waiting, as the delay sweep shows.

> [!TRAP]
> Fusion lowers memory traffic, not necessarily run time. Compute-bound matrix multiplications gain little from it.

> [!TRAP]
> The simulation numbers depend on the assumed costs. They show trends, not hardware benchmarks.

## Summary

- Compiling and fusing kernels cuts memory passes; the chain here moves 7 tensor passes unfused and 3 fused.
- Dynamic batching shares fixed costs across requests, lifting capacity from about 118 to about 667 requests per second in the simulation.
- The batching delay trades waiting for batch size, and it buys nothing when arrivals are the limit.
- The config's `dims` exclude the batch dimension, and the repository layout follows the Triton documentation.
- The KV cache grows with batch size times sequence length, so the maximum batch is a memory decision.

## Quiz time

### Question 1: Calculation

A fused kernel reads two tensors and writes one, each with $S = 16 \times 4096$ fp16 values. How many bytes does it move? How many does the unfused three-kernel chain move?

<details><summary>Show solution</summary>

$S = 65{,}536$ values at 2 bytes. Fused: $3S \times 2 = 393{,}216$ bytes. Unfused: $7S \times 2 = 917{,}504$ bytes.

</details>

### Question 2: Prediction

At 200 requests per second, does raising the batching delay from 0 to 10 ms increase served throughput?

<details><summary>Show solution</summary>

No. Served throughput stays at about 199.7 requests per second at every delay. The arrival rate limits it. The delay only raises mean latency, from 13.5 ms to 16.5 ms in the simulation.

</details>

### Question 3: Bug spotting

A config declares `max_batch_size: 8` and an input with `dims: [8, 1024]`. What is wrong?

<details><summary>Show solution</summary>

The batch dimension is already implicit. Triton adds it from `max_batch_size`, and the Triton documentation says `dims` excludes it. The `8` in `dims` is a second batch dimension. The input should be `dims: [1024]`.

</details>

### Question 4: Explanation

Why does a larger maximum batch need more memory even though the weights stay the same?

<details><summary>Show solution</summary>

The KV cache stores a key and a value for every token, in every layer, for every sequence in the batch. Its size is batch times sequence length times bytes per token. Here that is 512 KiB per token, so batch 32 at 4,096 tokens needs about 68.7 GB, more than the 60 GB left after the weights and reserve.

</details>
