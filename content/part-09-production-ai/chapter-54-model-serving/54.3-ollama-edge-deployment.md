In this lesson you will estimate whether a language model fits on a laptop, quantize weights by hand, and read the request and response shapes of a local model server. Ollama is a tool that runs open-weight models on your own machine, so no data leaves the device.

**You need:** matrix and vector arithmetic (NumPy), and the idea that a model is a large set of numbers called *weights* (Lesson 54.1 covers the cloud-serving side).

## The problem local deployment solves

A cloud API hides the model's size, but a local machine does not. Consider an 8-billion-parameter model (8B; "parameter" here means one learned number). Stored as 16-bit floats, its weights alone take about 16 GB, which is more RAM than many laptops have free. Privacy, offline use and latency push people toward running locally anyway, so the question becomes: how do we shrink the weights, and what does the server do with them?

## Weight memory: how much does a precision cost?

![Three bars: F16 16.06 GB, Q8_0 8.53 GB, Q4_K_M 4.91 GB, bar length proportional to size](diagrams/54.3-weight-budget.svg "Weight memory for 8.03 billion parameters at three precisions. Bits per weight from the llama.cpp table.")

Memory for weights is simple arithmetic: parameters × bits per weight ÷ 8 bytes. The llama.cpp quantization README prints measured bits per weight for Llama-3.1-8B: 16.0005 for F16, 8.5008 for Q8_0 and 4.8944 for Q4_K_M, where Q4_K_M is one of llama.cpp's 4-bit "k-quant" formats. Using 8.03 billion parameters gives 16.06, 8.53 and 4.91 GB. The table's own sizes (14.96, 7.95 and 4.58 GiB) agree with these numbers once you convert units (1 GiB = 2³⁰ bytes, so 4.58 GiB ≈ 4.91 GB).

## Quantization: a grid and a scale

Quantization stores each weight as a small integer and one floating-point *scale* per group of weights. Symmetric int4 means the integer codes run from −8 to 7, and the scale maps them back to real values:

$$
\text{scale} = \frac{\max |w|}{7}, \qquad q = \mathrm{round}(w / \text{scale}), \qquad \hat{w} = q \cdot \text{scale}
$$

![Four weights, each mapped to a code (1, -4, 3, 7) and back to a value (0.129, -0.514, 0.386, 0.900)](diagrams/54.3-int4-grid.svg "Symmetric int4 on four weights. The rounding error is the difference between the bottom row and the top row.")

Worked by hand for $w = [0.12, -0.50, 0.33, 0.90]$: the scale is $0.90 / 7 = 0.1286$. Then $0.12 / 0.1286 \approx 0.93$ rounds to code 1, and $0.33 / 0.1286 \approx 2.57$ rounds to code 3. The reconstructed 0.33 is $3 \times 0.1286 = 0.3857$, an error of $0.056$. Run the same steps in NumPy (this block runs in the browser):

```python
import numpy as np

# Symmetric int4: integer codes -8..7, one scale per group of weights.
w = np.array([0.12, -0.50, 0.33, 0.90])
scale = np.abs(w).max() / 7.0
codes = np.clip(np.round(w / scale), -8, 7).astype(int)
deq = codes * scale
print("scale:", round(float(scale), 6))
print("codes:", codes)
print("back :", np.round(deq, 4))
print("error:", np.round(deq - w, 4))

# Relative error on 32768 Gaussian weights, for int8 and int4 and three group sizes.
rng = np.random.default_rng(0)
W = rng.standard_normal(32768)

def quant_dequant(x, bits, group):
    qmax = 2 ** (bits - 1) - 1
    g = x.reshape(-1, group)
    s = np.abs(g).max(axis=1, keepdims=True) / qmax
    q = np.clip(np.round(g / s), -qmax - 1, qmax)
    return (q * s).reshape(-1)

for bits in (8, 4):
    for group in (32, 128, 4096):
        d = quant_dequant(W, bits, group)
        print(f"int{bits} group {group:5d}: relative error {np.linalg.norm(d - W) / np.linalg.norm(W):.4f}")
```

```output
scale: 0.128571
codes: [ 1 -4  3  7]
back : [ 0.1286 -0.5143  0.3857  0.9   ]
error: [ 0.0086 -0.0143  0.0557  0.    ]
int8 group    32: relative error 0.0054
int8 group   128: relative error 0.0065
int8 group  4096: relative error 0.0088
int4 group    32: relative error 0.0982
int4 group   128: relative error 0.1185
int4 group  4096: relative error 0.1590
```

Two things to read from the output. Going from int8 to int4 raises the error about 18-fold at group size 32 (0.0982 against 0.0054), because int4 has 16 levels where int8 has 256. Smaller groups lower the error, because each scale fits fewer weights. The per-group scale costs bits too: a 16-bit scale over 32 weights adds 0.5 bit per weight, so int4 with group 32 costs 4.5 bits. This NumPy version is simpler than the k-quants in GGUF (the file format llama.cpp and Ollama use), which add super-blocks and a few extra scales. The error numbers here describe the mechanism, not any GGUF file. Published methods reduce the error on real models: GPTQ (Frantar et al., 2022) uses second-order information to choose the rounding, and reports 3–4 bits per weight with "negligible accuracy degradation" on GPT models (arXiv abstract). AWQ (Lin et al., 2023) observes that "protecting only 1% salient weights can greatly reduce quantization error", where salience comes from activation statistics (arXiv abstract).

## Ollama's path from a file to a token

![Client sends JSON to the REST server on port 11434, which loads a GGUF file into a runner; weights and KV cache sit in RAM](diagrams/54.3-serving-path.svg "One request through a local server. The model file is read once; the cache grows with every token.")

Ollama runs a small HTTP server on your machine. The examples in its documentation use `http://localhost:11434`. A request goes to `/api/generate` (or `/api/chat`) with a JSON body. The fields that matter here, from the Ollama API documentation I read: `model`, `prompt`, `stream` (set `false` to get one response object), `options` (including `num_predict` for the number of tokens to generate and `num_ctx` for the context length), and `keep_alive` (how long the model stays in memory after the request, default `"5m"`). The response carries `response` (the text), `load_duration`, `prompt_eval_count`, `eval_count`, `eval_duration`, and durations in nanoseconds. Tokens per second is `eval_count / eval_duration × 10⁹`.

Ollama's README lists llama.cpp among its supported backends. The model itself is a GGUF file: weights, quantization types and tokenizer data in one file that a runner can load directly. The cache that dominates long conversations is the **KV cache**, which stores one key and one value vector per layer, per token, so it grows with context length.

![Bars for KV cache at 2048, 8192 and 32768 tokens: 0.25, 1.00 and 4.00 GiB, plus the Q4_K_M weights at 4.58 GiB](diagrams/54.3-kv-growth.svg "KV cache sizes for an illustrative fp16 configuration. For a 32K context the cache approaches the weights themselves.")

The size per token is $2 \times \text{layers} \times \text{KV heads} \times \text{head dim} \times \text{bytes}$. With an illustrative shape of 32 layers, 8 KV heads, head dimension 128 and fp16 (2 bytes), that is 131072 bytes, or 128 KiB, per token. This shape is an assumption I chose for arithmetic; I did not check it against a model card.

## Why generation speed is set by memory bandwidth

At batch size 1, generating one token means reading every weight once. If the machine can move $B$ bytes per second, the decode speed is at most $B$ divided by the bytes read per token. Assuming 100 GB/s (an assumed value, not measured on any machine):

![Upper bounds of 6.2, 11.7 and 20.4 tokens per second for F16, Q8_0 and Q4_K_M](diagrams/54.3-decode-bound.svg "Decode speed upper bound at 100 GB/s. A reasoning estimate, not a benchmark.")

Quantization therefore helps speed as well as memory: Q4_K_M reads about a third of the bytes that F16 reads. The bound ignores compute, cache misses and prompt processing, so real speed is lower. The request in the next block has the same structure. The stub is not Ollama and loads no weights; it reports durations from the same cost model, so the output is deterministic.

<details><summary>Run locally: standard library only, opens a local port</summary>

```python
import json, threading, urllib.request
from http.server import BaseHTTPRequestHandler, HTTPServer

BYTES_PER_TOKEN = 4.913e9   # Q4_K_M weights, GB
BW = 100e9                  # assumed bandwidth, bytes/s
LOAD_NS = 1_200_000_000     # simulated cold-load time, ns
WORDS = ["local", "models", "run", "on", "your", "own", "hardware"]

class H(BaseHTTPRequestHandler):
    def do_POST(self):
        req = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        n = req.get("options", {}).get("num_predict", 5)
        words = [WORDS[i % len(WORDS)] for i in range(n)]
        per_tok_ns = int(BYTES_PER_TOKEN / BW * 1e9)
        body = {
            "model": req["model"], "created_at": "stub", "response": " ".join(words),
            "done": True, "done_reason": "length",
            "total_duration": LOAD_NS + n * per_tok_ns + 1, "load_duration": LOAD_NS,
            "prompt_eval_count": len(req["prompt"].split()), "eval_count": n,
            "eval_duration": n * per_tok_ns,
        }
        data = json.dumps(body).encode()
        self.send_response(200); self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data))); self.end_headers(); self.wfile.write(data)
    def log_message(self, *a): pass

srv = HTTPServer(("127.0.0.1", 0), H)
threading.Thread(target=srv.serve_forever, daemon=True).start()
url = f"http://127.0.0.1:{srv.server_port}/api/generate"
payload = {"model": "llama3.1:8b-q4_K_M", "prompt": "Why run models locally",
           "stream": False, "options": {"num_predict": 8}}
req = urllib.request.Request(url, data=json.dumps(payload).encode(),
                             headers={"Content-Type": "application/json"})
with urllib.request.urlopen(req) as r:
    resp = json.loads(r.read())
print(json.dumps({k: resp[k] for k in resp if k != "response"}, indent=2))
print("response:", repr(resp["response"]))
tok_s = resp["eval_count"] / resp["eval_duration"] * 1e9
print("tokens/s from eval_count / eval_duration:", round(tok_s, 2))
srv.shutdown()
```

```output
{
  "model": "llama3.1:8b-q4_K_M",
  "created_at": "stub",
  "done": true,
  "done_reason": "length",
  "total_duration": 1593040001,
  "load_duration": 1200000000,
  "prompt_eval_count": 4,
  "eval_count": 8,
  "eval_duration": 393040000
}
response: 'local models run on your own hardware local'
tokens/s from eval_count / eval_duration: 20.35
```

</details>

The 20.35 tokens per second matches the 20.4 bound above, as it must: the stub's durations come from the same bandwidth model. A real measurement would differ, and its timings depend on hardware and load.

## Common traps

> [!TRAP]
> **Fitting the weights is not enough.** A 4.9 GB model can still fail on an 8 GB laptop once the operating system, the KV cache and other applications take their share. Add the cache for your context length before you decide.

> [!TRAP]
> **The response field is `response`.** `/api/generate` returns the text in `response`. Code that reads `response["text"]` or `response["generated_text"]` raises a `KeyError` or returns nothing.

> [!TRAP]
> **Streaming is on unless you turn it off.** The API documentation describes `/api/generate` as a streaming endpoint and only shows `"stream": false` as the way to get one object, so a client that expects one JSON object must send `"stream": false`.

> [!TRAP]
> **Quantization changes outputs.** A quantized model can give different answers from the F16 model on the same prompt. Evaluate the quantized model on your own task before you trust it.

> [!TRAP]
> **Long contexts cost memory quickly.** Setting `num_ctx` high raises the KV cache linearly (see the KV-cache figure). Set it to what the task needs.

## Summary

- Weight memory is parameters × bits per weight ÷ 8. An 8B model takes about 16 GB in F16 and about 4.9 GB in Q4_K_M.
- Symmetric quantization maps each weight to a small integer code times a scale; smaller groups lower the error but cost extra bits per weight.
- A local server such as Ollama receives JSON on port 11434, loads a GGUF file, and keeps the KV cache in memory.
- At batch size 1, decode speed is bounded by memory bandwidth divided by bytes read per token.

## Quiz time

### Question 1: Calculation

An 8.03-billion-parameter model is stored in F16 (16.0005 bits per weight). How many gigabytes do the weights take, using 1 GB = 10⁹ bytes?

<details><summary>Show solution</summary>

$8.03 \times 10^9 \times 16.0005 / 8 \approx 16.06 \times 10^9$ bytes, so about 16.06 GB (14.96 GiB).

</details>

### Question 2: Prediction

Using the worked int4 example (scale 0.9/7 ≈ 0.1286), what integer code does the weight $-0.50$ get, and what value does it reconstruct to?

<details><summary>Show solution</summary>

$-0.50 / 0.1286 \approx -3.89$, which rounds to $-4$. The reconstruction is $-4 \times 0.1286 = -0.5143$.

</details>

### Question 3: Bug-spotting

A script calls `/api/generate` with the default settings and reads `json.loads(body)["text"]`. Name two problems.

<details><summary>Show solution</summary>

The text is in `response`, not `text`. Also, `/api/generate` streams by default, so unless the request sends `"stream": false`, the body is a sequence of JSON lines, not one object, and `json.loads` on the whole body fails.

</details>

### Question 4: Explanation

Why does quantizing from F16 to Q4_K_M raise the upper bound on decode speed, even though the arithmetic is no faster?

<details><summary>Show solution</summary>

At batch size 1, each token reads all weights once, so the bound is bandwidth divided by bytes per token. Q4_K_M stores about 4.9 bits per weight instead of 16, so each token reads about a third as many bytes, and the bound rises by roughly three times. The arithmetic is not faster; the memory traffic is smaller.

</details>
