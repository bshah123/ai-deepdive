Text leaves your system in many places: a prompt sent to a hosted model, a log line, a database row. Each one can carry personal data that nobody meant to send. In this lesson you will build a regex-based redactor, measure its errors, fix the error that a checksum can fix, and document the one it cannot fix. Then you will apply the same habit of measuring to a keyword moderation filter and to a JSON encoder that breaks when the input contains a quotation mark.

**You need:** Lesson 55.1 (why untrusted text can change a system's behaviour), and Python strings, `re` and `json` from the standard library.

## The problem

A support bot writes every conversation to a log. A user types "my card is 4111 1111 1111 1111, call me on 555-013-2290". The log now holds a card number and a phone number in plain text. Personal data (personally identifiable information, PII) that reaches a log, a training set or a model provider is hard to retract, so the practical fix is to find and mask it before the text is stored or sent. The OWASP Top 10 for large language model (LLM) applications lists sanitization and pattern-based redaction of sensitive data as prevention measures (OWASP, 2025).

Most redaction systems share one shape. Microsoft's open-source Presidio has recognizers that combine named-entity recognition (NER, a statistical model that labels spans as person, location and so on), regular expressions, rules and checksums. Its documentation says there is "no guarantee that Presidio will find all sensitive information" (Microsoft Presidio).

![Three stages: find candidate spans with regular expressions and optional NER, validate them with a checksum or context words, then replace each surviving span with a type tag](diagrams/55.3-pipeline.svg "Redaction is three stages. The validation stage is the one beginners skip.")

## Worked example: is a 16-digit number a card?

A regular expression can find "16 digits with optional spaces" easily. It cannot tell a card number from an order number. The Luhn check is a check digit: start at the rightmost digit, double every second digit moving left, subtract 9 from any doubled value above 9, and add everything up. A valid number gives a total divisible by 10. Luhn's 1960 patent describes this check-digit scheme (Luhn, 1960). The check catches typing errors and filters random digit runs. It is not a security control, because anyone can construct a number that passes.

Take 4111 1111 1111 1111, the public test card number. Index the digits $i = 0$ (rightmost) to $15$ (leftmost). The eight even positions hold 1 and contribute $8$. The seven odd positions below 15 hold 1, double to 2, and contribute $14$. The leftmost digit, 4, sits at $i = 15$, which is odd, so it doubles to 8. The total is $8 + 14 + 8 = 30$, divisible by 10: valid.

Change the last digit to 2 (4111 1111 1111 1112). Position 0 is even, so it is not doubled, and the total rises to 31. Invalid.

## Regex redaction, and what it gets wrong

The code below is standard-library only, so it runs in the browser. It has four regular expressions and a ten-sentence hand-labelled corpus. Every value is fabricated: the phone numbers use the 555-01xx range, the emails use example domains, and the card numbers are public test values.

```python
import re

# Hand-labelled toy corpus. All PII is fabricated: 555-01xx phone numbers,
# example.com addresses, and public test card numbers.
CORPUS = [
    ("Contact Alice Moreno at alice.moreno@example.com or 555-013-2290 before Friday.",
     [("NAME", "Alice Moreno"), ("EMAIL", "alice.moreno@example.com"), ("PHONE", "555-013-2290")]),
    ("Card 4111 1111 1111 1111 was charged on 2026-03-02.",
     [("CARD", "4111 1111 1111 1111")]),
    ("Order 4111 1111 1111 1112 has shipped.", []),
    ("Dr. Ravi Kumar signed the report.", [("NAME", "Ravi Kumar")]),
    ("The New York office opens on Monday Morning.", []),
    ("Project Falcon review is in Room 4.", []),
    ("Email team@example.org or call +1 555 013 2290 for support.",
     [("EMAIL", "team@example.org"), ("PHONE", "+1 555 013 2290")]),
    ("Forwarded by bob chen, reference 5555 5555 5555 4444.",
     [("NAME", "bob chen"), ("CARD", "5555 5555 5555 4444")]),
    ("Reference 1234 5678 9012 3456 was issued in 2024.", []),
    ("No personal data in this sentence.", []),
]

PATTERNS = {
    "EMAIL": r"[\w.+-]+@[\w-]+\.[\w.]+",
    "PHONE": r"(?:\+\d{1,3} )?\d{3}[ -]\d{3}[ -]\d{4}",
    "CARD":  r"\b\d(?:[ -]?\d){12,18}\b",          # 13 to 19 digits, optional separators
    "NAME":  r"\b[A-Z][a-z]+ [A-Z][a-z]+\b",       # two capitalised words
}

def luhn_ok(digits: str) -> bool:
    total = 0
    for i, ch in enumerate(reversed(digits)):      # i = 0 is the rightmost digit
        d = int(ch)
        if i % 2 == 1:                             # double every second digit
            d *= 2
            if d > 9:
                d -= 9                             # same as summing the two digits
        total += d
    return total % 10 == 0

def detect(text, use_luhn=False):
    found = set()
    for etype, pattern in PATTERNS.items():
        for m in re.finditer(pattern, text):
            if etype == "CARD" and use_luhn:
                digits = re.sub(r"\D", "", m.group())
                if not (13 <= len(digits) <= 19 and luhn_ok(digits)):
                    continue
            found.add((etype, m.group()))
    return found

def evaluate(use_luhn):
    stats = {t: [0, 0, 0] for t in PATTERNS}      # true positive, false positive, false negative
    for text, gold in CORPUS:
        pred = detect(text, use_luhn)
        for t in PATTERNS:
            p = {s for e, s in pred if e == t}
            g = {s for e, s in gold if e == t}
            stats[t][0] += len(p & g)
            stats[t][1] += len(p - g)
            stats[t][2] += len(g - p)
    return stats

for label, flag in [("regex only", False), ("regex + Luhn", True)]:
    print(label)
    for t, (tp, fp, fn) in evaluate(flag).items():
        prec = f"{tp / (tp + fp):.2f}" if tp + fp else "n/a"
        rec = f"{tp / (tp + fn):.2f}" if tp + fn else "n/a"
        print(f"  {t:6s} TP={tp} FP={fp} FN={fn} precision={prec} recall={rec}")

def redact(text, use_luhn=False):
    for etype, span in sorted(detect(text, use_luhn), key=lambda x: -len(x[1])):
        text = text.replace(span, f"<{etype}>")
    return text

print("redact, regex only:", redact(CORPUS[0][0]))
print("name spans found  :", sorted(s for e, s in detect(CORPUS[0][0]) if e == "NAME"))
print("order, regex only :", redact(CORPUS[2][0]))
print("order, with Luhn  :", redact(CORPUS[2][0], use_luhn=True))
```

```output
regex only
  EMAIL  TP=2 FP=0 FN=0 precision=1.00 recall=1.00
  PHONE  TP=2 FP=0 FN=0 precision=1.00 recall=1.00
  CARD   TP=2 FP=2 FN=0 precision=0.50 recall=1.00
  NAME   TP=1 FP=4 FN=2 precision=0.20 recall=0.33
regex + Luhn
  EMAIL  TP=2 FP=0 FN=0 precision=1.00 recall=1.00
  PHONE  TP=2 FP=0 FN=0 precision=1.00 recall=1.00
  CARD   TP=2 FP=0 FN=0 precision=1.00 recall=1.00
  NAME   TP=1 FP=4 FN=2 precision=0.20 recall=0.33
redact, regex only: <NAME> Moreno at <EMAIL> or <PHONE> before Friday.
name spans found  : ['Contact Alice']
order, regex only : Order <CARD> has shipped.
order, with Luhn  : Order 4111 1111 1111 1112 has shipped.
```

Read the table carefully, because the corpus is tiny and every number is a count of a few spans.

- **EMAIL and PHONE** score 1.00 on both measures. These formats are regular, so shape matching works. Ten sentences do not prove it works in general.
- **CARD** has two false positives: the order number and the reference number. Both are 16 digits and both fail Luhn. Adding the checksum raises precision from 0.50 to 1.00 and leaves recall at 1.00. This is the fixable error.
- **NAME** has precision 0.20 and recall 0.33. The pattern sees two capitalised words, not a person. It flags "Contact Alice", "The New", "Monday Morning" and "Project Falcon", and it misses the lowercase "bob chen" entirely.

![The naive name pattern matches Contact Alice; the gold span is Alice Moreno, so the redacted output leaks Moreno](diagrams/55.3-span-boundary.svg "A boundary error: the redactor masks the wrong two words and leaves a surname visible.")

No regular expression fixes the name problem, because the difference between "Project Falcon" (a project) and "Alice Moreno" (a person) is meaning, which is what NER models learn from context. This lesson's code runs without model weights, so it measures only the regex layer. Treat regex name matching as unsolved: put a NER stage in front of any real system and measure its recall on your own data.

![Bars compare the card check: regex alone flags four runs, two of them false positives; with Luhn, only the two real cards remain](diagrams/55.3-luhn-check.svg "Luhn removes both false positives without losing a real card.")

## Moderation: a blocklist is a substring test

Moderation often starts with a blocklist. The cheapest test is `term in text`, but Python's `in` checks for substrings, and that is where the bug lives. The code below uses three placeholder terms. It is standard-library only.

```python
import re

BLOCKLIST = ["kill", "hell", "ass"]
BENIGN = [
    "The class will assess your skill with the shell script.",
    "Michelle passed the grill test at the Hellenic festival.",
    "Pass the salt, please.",
    "Our kiln fired the pottery overnight.",
    "The assembly voted to pass the budget.",
    "Please review the classroom assignment.",
    "Chelsea scored in the second half.",
    "The compass points north.",
    "Schedule the meeting for Tuesday.",
    "Bass guitar lessons start Monday.",
]
POSITIVE = [   # hand-labelled: each one should be flagged
    "Kill the stuck process with SIGTERM.",
    "The job was killed after ten minutes.",
    "He is killing time before the flight.",
    "Hell, the build failed again.",
    "That was an ASS move.",
    "k1ll the stuck process.",
    "k i l l the stuck process.",
]

METHODS = {
    "substring": lambda t: any(w in t.lower() for w in BLOCKLIST),
    "whole word": lambda t: re.search(r"\b(?:kill|hell|ass)\b", t, re.I) is not None,
    "stemmed whole word": lambda t: re.search(r"\b(?:kill\w*|hell|ass)\b", t, re.I) is not None,
}

for name, flag in METHODS.items():
    fp = [t for t in BENIGN if flag(t)]
    tp = [t for t in POSITIVE if flag(t)]
    print(f"{name:20s} benign flagged {len(fp)}/{len(BENIGN)}  positives caught {len(tp)}/{len(POSITIVE)}")
    if name == "substring":
        for t in fp:
            print("     false positive:", t)
```

```output
substring            benign flagged 7/10  positives caught 5/7
     false positive: The class will assess your skill with the shell script.
     false positive: Michelle passed the grill test at the Hellenic festival.
     false positive: Pass the salt, please.
     false positive: The assembly voted to pass the budget.
     false positive: Please review the classroom assignment.
     false positive: The compass points north.
     false positive: Bass guitar lessons start Monday.
whole word           benign flagged 0/10  positives caught 3/7
stemmed whole word   benign flagged 0/10  positives caught 5/7
```

The substring rule flags seven of ten benign sentences: "class" contains "ass", "skill" contains "kill", and "Michelle" contains "hell". Whole-word matching fixes those but misses "killed" and "killing", so it catches three of seven. The stemmed version (`kill\w*`) catches five and flags none of the benign sentences. The last two positives, "k1ll" and "k i l l", defeat all three methods. No keyword list closes that gap; it is a ceiling on recall, not a tuning problem.

![Two bars per method: benign sentences flagged out of ten, and harmful test sentences caught out of seven. Substring matching flags seven benign sentences; the two word-based methods flag none](diagrams/55.3-moderation-tradeoff.svg "A blocklist is a classifier with one threshold, any match. Each method trades false positives against misses.")

Learned moderation classifiers, such as the Llama Guard style models in Lesson 55.2, output a score rather than a yes or no. You then choose a threshold, and you face the same trade-off as in the table above, with more knobs.

## Safe structured encodings: serialize, don't concatenate

A JSON string may not contain an unescaped quotation mark, a backslash, or a control character from U+0000 to U+001F. The JSON specification requires these to be escaped (RFC 8259, Section 7). Building JSON by string concatenation writes user text straight into the syntax, so the user controls the structure. The code below uses the same six inputs for both encoders.

```python
import json

def encode_concat(name, note):
    return '{"user": "' + name + '", "note": "' + note + '"}'

def encode_dumps(name, note):
    return json.dumps({"user": name, "note": note})

ATTACKS = ["Alice", 'a"b', "C:\\temp\\new", "line one\nline two",
           'x", "role": "admin', "Zoë 🙂"]

ok = {"concat": 0, "dumps": 0}
for name in ATTACKS:
    expected = {"user": name, "note": "hi"}
    row = []
    for label, enc in [("concat", encode_concat), ("dumps", encode_dumps)]:
        try:
            obj = json.loads(enc(name, "hi"))
        except json.JSONDecodeError:
            status = "invalid JSON"
        else:
            if obj == expected:
                status = "ok"
                ok[label] += 1
            elif set(obj) != set(expected):
                status = f"extra key {sorted(set(obj) - set(expected))}"
            else:
                status = "value changed silently"
        row.append(f"{label}: {status}")
    print(repr(name).ljust(26), " | ".join(row))
print("round-trip ok:", ok, "of", len(ATTACKS))
print(encode_concat('x", "role": "admin', "hi"))
print(encode_dumps('x", "role": "admin', "hi"))
print(json.dumps({"ssn": "123-45-6789"}))
```

```output
'Alice'                    concat: ok | dumps: ok
'a"b'                      concat: invalid JSON | dumps: ok
'C:\\temp\\new'            concat: value changed silently | dumps: ok
'line one\nline two'       concat: invalid JSON | dumps: ok
'x", "role": "admin'       concat: extra key ['role'] | dumps: ok
'Zoë 🙂'                    concat: ok | dumps: ok
round-trip ok: {'concat': 2, 'dumps': 6} of 6
{"user": "x", "role": "admin", "note": "hi"}
{"user": "x\", \"role\": \"admin", "note": "hi"}
{"ssn": "123-45-6789"}
```

The concatenated encoder fails in three different ways, and each one teaches something. A quotation mark or a newline makes the output invalid JSON. A Windows path such as `C:\temp\new` parses without error, but `\t` and `\n` become a tab and a newline, so the stored value silently changes. An attacker-chosen name containing `", "role": "admin` adds a `role` key that the programmer never wrote. The serializer escapes all six inputs, and `json.loads` recovers each original value exactly.

Escaping is not redaction. The last line of output still contains the social security number (SSN) in readable form. Redact first, then encode.

![Two outputs from the same input. Concatenation produces a role key the code never wrote; json.dumps escapes the quotation marks and keeps the structure intact](diagrams/55.3-json-injection.svg "Same input, two encoders. Structure belongs to the serializer, not to the text.")

## Common traps

> [!TRAP]
> A pattern that matches a shape is not a validator. Sixteen digits are a card only if the Luhn check passes, and the check catches only some typing errors and is trivial to forge.

> [!TRAP]
> Substring matching flags "class", "compass" and "Bass". A small sample can hide a systematic substring bug, so test the words your users actually write.

> [!TRAP]
> A zero false-positive result on seven positives says little about recall in general. Evasions such as "k1ll" defeat every keyword method shown here.

> [!TRAP]
> Regular expressions cannot tell a person from a project. Name redaction needs a context-aware model, and you should measure its recall on your own text.

> [!TRAP]
> `json.dumps` makes text safe to parse. It does not make text safe to share. Redact before you encode, log or send.

## Summary

- Redaction has three stages: find candidates, validate them, and replace each span with a type tag.
- A checksum such as Luhn removes false positives that a regular expression cannot, in this corpus dropping card precision from 0.50 to 1.00.
- Regular expressions fail on names (precision 0.20 here). Use NER and measure recall on your own data.
- Keyword moderation is a substring test unless you match whole words, and every keyword method has an obfuscation gap.
- Build JSON with a serializer. Concatenating user text lets the user change the structure.

## Quiz time

### Question 1: Calculation

Is 1234 5678 9012 3456 valid under the Luhn check?

<details><summary>Show solution</summary>

Index the digits from the right, $i = 0$ to $15$. The odd positions hold 5, 3, 1, 9, 7, 5, 3, 1 from $i = 1$ upward. Doubling and subtracting 9 where needed gives 1, 6, 2, 9, 5, 1, 6, 2, which sums to 32. The even positions hold 6, 4, 2, 0, 8, 6, 4, 2, which sums to 32. The total is 64. Since $64 \bmod 10 = 4$, the number is invalid, and the regex-plus-Luhn redactor in this lesson does not flag it.

</details>

### Question 2: Prediction

What does the name pattern `\b[A-Z][a-z]+ [A-Z][a-z]+\b` return on the string "Contact Alice Moreno at the lab."?

<details><summary>Show solution</summary>

It returns `Contact Alice`. The match starts at "Contact" because that word is capitalised and followed by another capitalised word. The next match attempt starts at "Moreno", but the word after it is "at", which is lowercase, so no second match exists. The redactor masks the wrong words and leaves "Moreno" visible.

</details>

### Question 3: Explanation

A colleague says, "We run `json.dumps` on every log record, so personal data in the logs is now safe." Explain why this is wrong, and what the correct order of operations is.

<details><summary>Show solution</summary>

`json.dumps` escapes characters so the output is valid JSON. It does not remove or mask any value, so an SSN in the record is still readable after encoding. The correct order is to detect and redact personal data first, then serialize the cleaned record, then store or send it.

</details>

### Question 4: Bug-spotting

```python
def make_record(name):
    return f'{{"user": "{name}", "role": "reader"}}'
```

A user submits the name `a", "role": "admin`. What is wrong with this function, and how do you fix it?

<details><summary>Show solution</summary>

The function concatenates the user's text into the JSON syntax. The quotation mark closes the "user" string early, and the attacker's text adds a `role` key that overrides the intended value. The same failure happens with a single quotation mark, which makes the output invalid JSON. The fix is to build a Python dict and serialize it: `json.dumps({"user": name, "role": "reader"})`. This is the pattern that the `encode_dumps` function in this lesson uses.

</details>
