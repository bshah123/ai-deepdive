In this lesson you will read the trace of one request to a large language model (LLM) application, pass a trace from one service to another with the `traceparent` header, and instrument a small pipeline with OpenTelemetry (OTel), the open standard for telemetry data. You will also see why tracers keep only a sample of traces.

**You need:** Python functions and `with` blocks, and the idea of a HyperText Transfer Protocol (HTTP) request, one program sending a message to another over a network.

## The problem tracing solves

A chat request takes 2,410 ms (milliseconds). It embeds the question, searches a vector store, calls an LLM, calls a weather tool that times out, and calls the LLM again. Your log says "request finished in 2410 ms." That line does not say which step was slow or which step failed. If the search service and the LLM service each write their own log lines, nothing links the lines that belong to one request.

Tracing fixes this by giving each request one shared identifier and recording every step as a timed record that points to the step that caused it.

## Trace, span, context

A **span** is one timed unit of work: a function call, a database query, a model call. The OTel documentation lists what a span holds: a name, a parent span ID, start and end timestamps, a span context, attributes, events, links and a status. The span context groups the trace ID, the span's own ID and the trace flags. Each span also has a kind (client, server, internal, producer or consumer) that says which side of a call it represents.

A **trace** is the set of spans that share one trace identifier (trace ID). Each span has at most one parent, so the spans form a tree whose root has no parent. Google's Dapper paper (Sigelman et al., 2010) uses the same model: "We tend to think of a Dapper trace as a tree of nested RPCs," where RPC means remote procedure call.

## A worked example by hand

![Waterfall of one chat request: chat_request 2410 ms with embed_query 38 ms, vector_search 71 ms, two llm_call spans of 1000 ms each, and a tool_call of 300 ms that ends in ERROR](diagrams/56.1-waterfall.svg "Each bar starts where its parent step started and is drawn to scale.")

Read the waterfall left to right. The root span `chat_request` starts at 0 ms and ends at 2,410 ms. Its children run one after another: `embed_query` takes 38 ms (0 to 38), `vector_search` takes 71 ms (38 to 109), the first `llm_call` takes 1,000 ms (109 to 1,109), the `tool_call` takes 300 ms (1,109 to 1,409) and ends in an error, and the second `llm_call` takes 1,000 ms (1,409 to 2,409). The root's own time is the last 1 ms.

Two numbers follow. The LLM calls take 1,000 + 1,000 = 2,000 ms, which is 2,000 / 2,410 = 83% of the request. And `vector_search` takes 71 ms, so even a free search would save at most 71 / 2,410 = 3%. The trace shows where to look; the total alone does not.

## Code: a toy tracer you can run in the browser

The toy below has the shape of the OpenTelemetry tracer. `start_span` finds the current span through a `contextvars.ContextVar`, creates a child with the same trace ID, and records the end time in a `finally` block, so the end time is set even when the step fails. The IDs are counters, so the output is the same on every run. A real SDK draws random IDs.

```python
import contextvars
import itertools
from contextlib import contextmanager
from dataclasses import dataclass, field

# A toy tracer with the same shape as OpenTelemetry's. IDs are counters so the
# output is reproducible; a real SDK uses random 128-bit trace IDs.
ids = itertools.count(1)
clock_ms = [0.0]                       # simulated clock, advanced explicitly
current = contextvars.ContextVar("current_span", default=None)
finished = []                          # spans, in the order they ended

@dataclass
class Span:
    name: str
    trace_id: str
    span_id: str
    parent_id: str | None
    start_ms: float
    end_ms: float = 0.0
    attributes: dict = field(default_factory=dict)
    status: str = "OK"

@contextmanager
def start_span(name, trace_id=None, parent_id=None, attributes=None):
    local = current.get()
    if trace_id is None and local is not None:   # inherit from the current span
        trace_id, parent_id = local.trace_id, local.span_id
    if trace_id is None:                         # nothing to inherit: a new root trace
        trace_id = f"{next(ids):032x}"
    span = Span(name, trace_id, f"{next(ids):016x}", parent_id,
                clock_ms[0], attributes=dict(attributes or {}))
    token = current.set(span)
    try:
        yield span
    except Exception as exc:
        span.status = f"ERROR: {exc}"
        raise
    finally:
        span.end_ms = clock_ms[0]
        finished.append(span)
        current.reset(token)

def advance(ms):
    clock_ms[0] += ms

def inject(span):
    """Write the span context into a W3C traceparent header value."""
    return f"00-{span.trace_id}-{span.span_id}-01"

def extract(header):
    """Read trace_id and parent_id back out of a traceparent header."""
    version, trace_id, parent_id, flags = header.split("-")
    return trace_id, parent_id

def retrieve(header):                    # runs in the retrieval service
    trace_id, parent_id = extract(header)
    with start_span("vector_search", trace_id, parent_id, {"db.system": "vector-store"}):
        advance(71)

def llm_call(step, input_tokens, output_tokens, ms):
    attrs = {"step": step, "gen_ai.request.model": "example-model",
             "gen_ai.usage.input_tokens": input_tokens,
             "gen_ai.usage.output_tokens": output_tokens}
    with start_span("llm_call", attributes=attrs):
        advance(ms)

def get_weather(city):
    with start_span("tool_call", attributes={"tool.name": "get_weather"}):
        advance(300)
        raise TimeoutError("weather API timed out after 300 ms")

def chat_request(question):
    with start_span("chat_request", attributes={"question_chars": len(question)}) as root:
        with start_span("embed_query", attributes={"model": "example-embedder"}):
            advance(38)
        retrieve(inject(root))           # the HTTP call carries the header
        llm_call(1, 1840, 64, 1000)
        try:
            get_weather("Roorkee")
        except TimeoutError:
            pass                         # the request goes on without weather data
        llm_call(2, 2310, 58, 1000)
        advance(1)

def print_tree(spans):
    children = {}
    for s in spans:
        children.setdefault(s.parent_id, []).append(s)
    def walk(parent_id, depth):
        for s in sorted(children.get(parent_id, []), key=lambda s: s.start_ms):
            print(f"{'  ' * depth}{s.name:<14}{s.start_ms:>6.0f} -> {s.end_ms:>6.0f} ms"
                  f"  ({s.end_ms - s.start_ms:.0f} ms)  {s.status}")
            walk(s.span_id, depth + 1)
    walk(None, 0)

chat_request("What is the weather in Roorkee today?")
print_tree(finished)
root = next(s for s in finished if s.parent_id is None)
llm = sum(s.end_ms - s.start_ms for s in finished if s.name == "llm_call")
print("header:", inject(root))
print("total ms:", root.end_ms - root.start_ms, " llm ms:", llm, f" share: {llm / (root.end_ms - root.start_ms):.0%}")
print("spans:", len(finished), " distinct trace IDs:", len({s.trace_id for s in finished}))
```

```output
chat_request       0 ->   2410 ms  (2410 ms)  OK
  embed_query        0 ->     38 ms  (38 ms)  OK
  vector_search     38 ->    109 ms  (71 ms)  OK
  llm_call         109 ->   1109 ms  (1000 ms)  OK
  tool_call       1109 ->   1409 ms  (300 ms)  ERROR: weather API timed out after 300 ms
  llm_call        1409 ->   2409 ms  (1000 ms)  OK
header: 00-00000000000000000000000000000001-0000000000000002-01
total ms: 2410.0  llm ms: 2000.0  share: 83%
spans: 6  distinct trace IDs: 1
```

Three details matter. The `vector_search` span runs with a trace ID and parent ID that came from another service, so `start_span` takes them as arguments instead of looking at the current span. The `except` block records the error on the span and then re-raises, so the caller decides whether the request fails. The `tool_call` span is ERROR, yet the root is OK, because `chat_request` caught the exception: a failed step does not have to fail the request.

## Crossing a service boundary: traceparent

Context moves between services as a header. The World Wide Web Consortium (W3C) Trace Context Recommendation defines the header `traceparent` with four dash-separated fields: `version`, `trace-id`, `parent-id` and `trace-flags`. The lengths are 2, 32, 16 and 2 hexadecimal characters, 55 characters in total. The version is `00`, the only version this lesson uses, all-zero trace and parent IDs are invalid, and the sampled flag is bit 0 (value `01`). The spec calls the flags "recommendations given by the caller rather than strict rules to follow."

![Two services joined by one HTTP header; the header string is broken into version 00, a 32-character trace-id, a 16-character parent-id and flags 01](diagrams/56.1-propagation.svg "The receiver reads trace-id and parent-id and starts its span as a child.")

The sender writes the header before it makes the call, and the receiver reads it before it starts its span. If the sender forgets to write the header, the receiver has no parent and starts a new trace. That is why the gateway in the toy calls `inject` before `retrieve`.

## Under the hood: the real OpenTelemetry interface

The toy mirrors the real API. The OpenTelemetry software development kit (SDK) for Python provides `tracer.start_span`, a `context=` argument that takes a parent, and `inject` and `extract` functions that read and write the header. The block below runs the same request with the real SDK. Explicit start and end times make the durations exact, and a seed makes the IDs repeatable.

<details><summary>Run locally: needs pip install opentelemetry-sdk (output below used version 1.45.2)</summary>

```python
import random
from concurrent.futures import ThreadPoolExecutor
from opentelemetry import trace
from opentelemetry.propagate import extract, inject
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter
from opentelemetry.sdk.trace.sampling import ParentBased, TraceIdRatioBased
from opentelemetry.trace import SpanKind

random.seed(0)                                    # the SDK draws span and trace IDs from random
NS = 1_000_000  # nanoseconds per millisecond
exporter = InMemorySpanExporter()
provider = TracerProvider()
provider.add_span_processor(SimpleSpanProcessor(exporter))
tracer = provider.get_tracer("rag-demo")

t0 = 1_000 * NS
root = tracer.start_span("chat_request", kind=SpanKind.SERVER, start_time=t0)
ctx = trace.set_span_in_context(root)
embed = tracer.start_span("embed_query", context=ctx, start_time=t0)
embed.end(end_time=t0 + 38 * NS)
headers = {}
inject(headers, context=ctx)                      # writes the traceparent header
remote = extract(headers)                         # what the retrieval service does
search = tracer.start_span("vector_search", context=remote, kind=SpanKind.CLIENT,
                           start_time=t0 + 38 * NS)
search.end(end_time=t0 + 109 * NS)
root.end(end_time=t0 + 2410 * NS)

for s in exporter.get_finished_spans():
    parent = format(s.parent.span_id, "016x") if s.parent else None
    print(f"{s.name:<14} span={format(s.context.span_id, '016x')} parent={parent} "
          f"ms={(s.end_time - s.start_time) / NS:.0f}")
print("traceparent:", headers["traceparent"])

# Context does not follow work into a new thread by itself.
with tracer.start_as_current_span("outer"):
    with ThreadPoolExecutor(1) as pool:
        print("span valid inside worker thread:",
              pool.submit(lambda: trace.get_current_span().get_span_context().is_valid).result())

# Head sampling: keep about 10% of traces, decided from the trace ID.
random.seed(0)
sampled_tracer = TracerProvider(sampler=ParentBased(TraceIdRatioBased(0.1))).get_tracer("s")
kept = 0
for _ in range(10_000):
    s = sampled_tracer.start_span("root")
    kept += s.is_recording()
    s.end()
print("kept", kept, "of 10000")
```

```output
embed_query    span=f728b4fa42485e3a parent=0a5d2f346baa9455 ms=38
vector_search  span=7c65c1e582e2e662 parent=0a5d2f346baa9455 ms=71
chat_request   span=0a5d2f346baa9455 parent=None ms=2410
traceparent: 00-e3e70682c2094cac629f6fbed82c07cd-0a5d2f346baa9455-03
span valid inside worker thread: False
kept 956 of 10000
```

</details>

The SDK output agrees with the toy: `vector_search` and `embed_query` have the root as parent, and the header is in the W3C format. The line `span valid inside worker thread: False` is a trap, covered below. The header ends in `03`, not `01`. Bit 0 is the sampled flag, as before. The SDK also sets bit 1 (`02`), which its source names `RANDOM_TRACE_ID`; that bit comes from a newer revision of the W3C spec than the one this lesson read, so this lesson does not explain it further.

## Sampling: you cannot keep every trace

Recording every span costs central processing unit (CPU) time and storage. Dapper measured this on a Google web-search cluster in 2010. Sampling at 1/1 (every trace) raised average latency by 16.3%. Sampling at 1/1024 changed latency by −0.20%, which is inside the paper's measurement error of 2.5% (Sigelman et al., 2010, Table 2). Those are 2010 numbers from one system; they show the shape of the trade-off, not a benchmark for your stack.

Head sampling, the simplest design, has the root span decide once, and its children follow the decision through the flag. The SDK's `TraceIdRatioBased(rate)` keeps a trace when the low 64 bits of its trace ID fall below `rate` × 2^64, so every service that sees the same trace ID reaches the same answer. The run above used `ParentBased(TraceIdRatioBased(0.1))`, which follows the parent's sampling decision when there is one. Of 10,000 root spans, 956 were kept, which is 9.6%, close to 10%. For a binomial count with p = 0.1 over 10,000 trials, the standard deviation is sqrt(10,000 × 0.1 × 0.9) = 30, so 956 is within one standard deviation of 1,000. This is my own calculation from the binomial model.

## Attributes for LLM calls

The attributes in the waterfall follow the OpenTelemetry generative AI (GenAI) conventions: `gen_ai.request.model`, `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens`. A token is a piece of text, often part of a word, that the model reads or writes. I checked these names in the `opentelemetry-semconv` 0.66b2 Python package, where the constants are defined. The GenAI conventions are still being developed and have moved to a separate repository, and the same package marks `gen_ai.operation.name` as deprecated. Check the repository before you depend on a name.

## Common traps

> [!TRAP]
> A new thread does not inherit the current span. In the experiment, the current span inside a `ThreadPoolExecutor` worker was not valid (`span valid inside worker thread: False`). Capture the context in the caller and run the worker inside it, for example with `contextvars.copy_context().run` (my own reasoning; not run here).

> [!TRAP]
> Forgetting to write the header splits one request into two traces. The downstream service sees no parent and starts a new trace ID. Check that every outgoing HTTP call carries `traceparent` (my own reasoning from the header format).

> [!TRAP]
> Head sampling cannot keep only the failed requests. The keep-or-drop decision is made when the root span starts, before anyone knows whether the request will fail. Keeping only errors needs a rule that waits until the trace ends, which head sampling does not do (my own reasoning).

> [!TRAP]
> Prompts and answers as attributes can fill storage and expose private text. Store lengths and token counts, and decide deliberately before you store content (my own reasoning).

> [!TRAP]
> Clocks on different machines disagree, so a child span can appear to start before its parent. Compare durations inside one service more than absolute times across services (my own reasoning).

## Summary

- A span is one timed step with a name, IDs, timestamps, attributes and a status; a trace is the tree of spans that share one trace ID.
- A `traceparent` header carries the trace ID and the parent span ID across a service boundary in four fixed-length fields.
- In the worked example, LLM calls took 83% of the request, and a free vector search would have saved at most 3%.
- Context does not follow work into new threads on its own; pass it explicitly.
- Head sampling keeps a fixed share of traces from the root's decision, and the decision cannot depend on how the request ends.

### Question 4: Explanation

Why does `TraceIdRatioBased` decide from the trace ID rather than from a fresh random draw in each service?

<details><summary>Show Solution</summary>

Every service sees the same trace ID, so every service computes the same decision. A fresh draw in each service would keep some spans of a trace and drop others, leaving broken trees. This is my own reasoning from the sampler's definition.

</details>
