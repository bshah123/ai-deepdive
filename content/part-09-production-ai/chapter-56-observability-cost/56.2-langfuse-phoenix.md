A language model application is a chain of steps, and when a user says the answer was slow or wrong, the final text alone does not tell you which step failed. In this lesson you will build the mechanism behind observability tools such as Langfuse, Phoenix and Arize AX: a tracer that records every step as a timed, nested record with its model and token counts, sends those records in batches, and turns token counts into cost. You will then map the mechanism onto the three products and see why the sampling policy decides which failures you can still debug.

**You need:** Lesson 56.1 (traces and spans in OpenTelemetry), Python context managers (`with`) and `dataclasses`.

## The problem

Take a retrieval-augmented generation (RAG) answer: a system that first retrieves passages from a document store, then uses a small model to rerank them, then asks a large language model (LLM) to write the answer. A log line that says "request took 1.2 s, answer was poor" cannot separate the possible causes. Did retrieval return the wrong documents? Did the large model ignore them? Did the request cost more because the prompt was long? You need one record per step, with timing, inputs, outputs and token counts, and the records must be linked to the request they belong to.

![A trace tree for one request drawn on a time axis: answer_question contains retrieve, a small-model call and a large-model call, and each bar is labelled with its duration, tokens and cost](diagrams/56.2-trace-tree.svg "One request as a trace: child bars sit inside the parent's time span.")

## The data model

A **trace** is one request. An **observation** is one step inside it. Three kinds recur across the tools: a **span** for timed work, a **generation** for a model call (it also records the model name and the input and output token counts), and an **event** for an instant with no duration. Each observation stores its trace id and the id of its parent, so a backend can rebuild the tree even though children finish before their parents.

Langfuse uses this vocabulary. Its documentation describes a trace as one request or operation, and a generation as the record of a model call, including its prompt and token usage [1][2]. Phoenix is built on OpenTelemetry, whose spans carry a trace id, a parent id, start and end times and attributes [3][5].

**Worked example, by hand.** The small-model rerank call in the trace above has 271 input tokens and 2 output tokens. The illustrative prices in the code are 0.0005 USD per 1,000 input tokens and 0.0015 USD per 1,000 output tokens, so its cost is 271 / 1000 × 0.0005 + 2 / 1000 × 0.0015 = 0.0001355 + 0.000003 = 0.0001385 USD. The code prints 0.000139. Its latency model gives 60 + 0.05 × 271 + 3 × 2 = 79.55 ms, which the trace prints as 79.5 ms because of floating-point formatting.

## A tracer with batching, in one file

The code below is a complete, dependency-free tracer. It records a tree of observations with `observe()`, sends them in batches, and then reports the latency and cost of 200 simulated requests. Only the standard library is used.

```python
import contextvars
import itertools
import random
import statistics
from contextlib import contextmanager
from dataclasses import dataclass
from typing import Any, Optional

CLOCK = {"now": 0.0}          # simulated time in ms; a real SDK reads the wall clock
IDS = itertools.count(1)
CURRENT = contextvars.ContextVar("current_observation", default=None)

# Illustrative prices (USD per 1,000 tokens) and latency coefficients. Invented for arithmetic.
PRICE = {"small-model": (0.0005, 0.0015), "large-model": (0.003, 0.015)}
# (fixed ms, ms per input token, ms per output token)
LATENCY = {"small-model": (60, 0.05, 3.0), "large-model": (200, 0.2, 12.0)}


@dataclass
class Observation:
    id: int
    trace_id: int
    parent_id: Optional[int]
    name: str
    kind: str                 # "span", "generation" or "event"
    start_ms: float
    end_ms: float = 0.0
    model: Optional[str] = None
    input_tokens: int = 0
    output_tokens: int = 0
    output: Any = None

    @property
    def duration_ms(self):
        return self.end_ms - self.start_ms

    @property
    def cost_usd(self):
        if self.model is None:
            return 0.0
        p_in, p_out = PRICE[self.model]
        return self.input_tokens / 1000 * p_in + self.output_tokens / 1000 * p_out


class BatchExporter:
    """Buffers finished observations and sends them in batches: one 'POST' per batch."""

    def __init__(self, batch_size):
        self.batch_size = batch_size
        self.buffer = []
        self.posts = []           # what the backend received, one list per POST

    def submit(self, obs):
        self.buffer.append(obs)
        if len(self.buffer) >= self.batch_size:
            self.flush()

    def flush(self):
        if self.buffer:
            self.posts.append(self.buffer)
            self.buffer = []


EXPORTER = BatchExporter(batch_size=50)


@contextmanager
def observe(name, kind="span", **fields):
    parent = CURRENT.get()
    if parent is None:                    # a root observation starts a new trace
        trace_id, parent_id = next(IDS), None
    else:                                 # a child joins its parent's trace
        trace_id, parent_id = parent.trace_id, parent.id
    obs = Observation(next(IDS), trace_id, parent_id, name, kind, CLOCK["now"], **fields)
    token = CURRENT.set(obs)
    try:
        yield obs
    finally:
        obs.end_ms = CLOCK["now"]
        CURRENT.reset(token)
        EXPORTER.submit(obs)              # children finish first; the backend re-links by parent_id


def llm_call(model, prompt, reply):
    with observe(f"llm:{model}", kind="generation", model=model) as g:
        g.input_tokens = len(prompt.split())    # crude stand-in for a real tokenizer
        g.output_tokens = len(reply.split())
        fixed, per_in, per_out = LATENCY[model]
        CLOCK["now"] += fixed + per_in * g.input_tokens + per_out * g.output_tokens
        g.output = reply
    return reply


def retrieve(k):
    with observe("retrieve") as s:
        CLOCK["now"] += 35                    # pretend vector search takes 35 ms
        s.output = [f"doc-{i}" for i in range(k)]
    return s.output


def answer_question(rng, question):
    with observe("answer_question") as root:
        docs = retrieve(k=3)
        passages = " ".join(" ".join(["passage"] * rng.randint(60, 120)) for _ in docs)
        best = llm_call("small-model", passages + " " + question, reply="doc-1 doc-0")
        final = llm_call("large-model", passages + " " + question + " " + best,
                         reply=" ".join(["answer"] * rng.randint(40, 90)))
        root.output = final
    return root


def print_trace(trace_id, observations):
    children = {}
    for o in observations:
        if o.trace_id == trace_id:
            children.setdefault(o.parent_id, []).append(o)

    def walk(parent_id, depth):
        for o in sorted(children.get(parent_id, []), key=lambda o: o.start_ms):
            tokens = ""
            if o.kind == "generation":
                tokens = f"  in={o.input_tokens} out={o.output_tokens} cost=${o.cost_usd:.6f}"
            print(f"{'  ' * depth}{o.name:<20}{o.start_ms:8.1f}{o.duration_ms:8.1f} ms{tokens}")
            walk(o.id, depth + 1)

    walk(None, 0)


rng = random.Random(56)
roots = [answer_question(rng, f"question {i}") for i in range(200)]
EXPORTER.flush()
observations = [o for post in EXPORTER.posts for o in post]

print("== one request (start ms, duration ms) ==")
print_trace(roots[0].trace_id, observations)
print()
print(f"observations: {len(observations)}  POST calls (batch 50): {len(EXPORTER.posts)}  "
      f"POST calls (unbatched): {len(observations)}")
print()
total_cost = sum(o.cost_usd for o in observations)
print(f"{'step':<20}{'n':>5}{'p50 ms':>10}{'p95 ms':>10}{'share of cost':>16}")
for name in ["answer_question", "retrieve", "llm:small-model", "llm:large-model"]:
    durs = sorted(o.duration_ms for o in observations if o.name == name)
    cost = sum(o.cost_usd for o in observations if o.name == name)
    p95 = durs[round(0.95 * (len(durs) - 1))]
    print(f"{name:<20}{len(durs):>5}{statistics.median(durs):>10.1f}{p95:>10.1f}{cost / total_cost:>15.1%}")
print()
per_request = {}
for o in observations:
    per_request[o.trace_id] = per_request.get(o.trace_id, 0.0) + o.cost_usd
costs = sorted(per_request.values())
print(f"cost per request: mean ${statistics.mean(costs):.6f}  max ${costs[-1]:.6f}")

```

answer_question          0.0  1209.1 ms
  retrieve                 0.0    35.0 ms
  llm:small-model         35.0    79.5 ms  in=271 out=2 cost=$0.000139
  llm:large-model        114.5  1094.6 ms  in=273 out=70 cost=$0.001869

observations: 800  POST calls (batch 50): 16  POST calls (unbatched): 800

answer_question       200    1162.2    1424.2           0.0%
retrieve              200      35.0      35.0           0.0%
llm:small-model       200      79.7      81.7           7.1%
llm:large-model       200    1049.5    1309.8          92.9%

cost per request: mean $0.001945  max $0.002410

Three mechanisms do the work. `observe()` is a context manager: it records the start time on entry and the end time on exit, even if the body raises an error (the `finally` clause), so a failed step still leaves a record. `CURRENT` is a `contextvars.ContextVar`, which holds the innermost open observation, so a nested call finds its parent without the parent being passed as an argument. The exporter appends each finished observation to a buffer and sends the buffer when it is full.

The clock is simulated. Each step adds a fixed amount of time to `CLOCK`, using a latency model with three coefficients per model: a fixed overhead, a cost per input token (prefill, the processing of the prompt) and a cost per output token (decoding, one token at a time). This model is a teaching device, not a benchmark. Real latencies vary from run to run, and the prices are invented so that the arithmetic is easy to check.

## Where the three tools fit

![Your app emits one trace tree; Langfuse, Phoenix and Arize AX each consume it in a different way](diagrams/56.2-three-tools.svg "The shared contract is the tree and the token counts. The products differ in hosting and tooling.")

All three products need the same input from your code: a tree of timed steps, the model name, and the token counts. What differs is where the data goes and what you can do with it.

- **Langfuse** records traces and observations (span, generation, event). A generation takes model and usage details, such as input and output token counts [1][2]. The documentation pages I read do not say how cost is derived from usage, so check its token and cost page before relying on a cost figure.
- **Phoenix** is the open-source product from Arize. It accepts traces over the OpenTelemetry Protocol (OTLP), with auto-instrumentation for common frameworks, and it offers tracing, evaluations (scoring outputs with a model judge, code checks or human labels) and datasets with experiments [3].
- **Arize AX** is the managed commercial platform. The Arize documentation describes Phoenix as its open-source sibling [4].

I did not verify the current OpenTelemetry attribute names for generative AI calls. The OpenTelemetry conventions for generative AI have moved to a separate repository, so this lesson uses plain fields and does not claim the standard names [5].

## Export: batching, not blocking

![Observations pass from app code to a buffer, then in one POST per batch of 50 to the backend, which re-links them by parent_id](diagrams/56.2-export-batches.svg "Batching turns 800 small network calls into 16.")

The code appends to a list and sends it in batches of 50, so 800 observations need 16 POST calls. Sending each observation separately would need 800. Each POST is a network round trip, and an observability layer that waits for the network on every step would add latency to the very requests it measures. Real SDKs usually send from a background thread or queue. That is my own reasoning, not a verified claim about any one product: check how your SDK behaves when the backend is slow. A bounded buffer that drops data under overload is a common design, because the observability layer should never block the application.

## Latency and cost, from the trace data

![Horizontal bars of p50 and p95 latency for answer_question, retrieve, the small model and the large model over 200 requests](diagrams/56.2-latency-bars.svg "Over 200 requests, the large model's p95 latency is about 1310 ms.")

The table printed by the code gives the step-level view. The end-to-end time of a request (`answer_question`) has a median of 1162.2 ms and a 95th percentile of 1424.2 ms. The large model accounts for 92.9% of the cost, because it is both the more expensive model per token and the one that writes the longest outputs. In this simulation retrieval always takes 35 ms, so it adds nothing to the spread. In a real system, retrieval time varies, and that variation is the first thing a latency dashboard should show.

Percentiles matter more than means here. A median hides the slow tail that users notice. The p50 and p95 values come from the same records that the trace view uses, so the dashboard and the trace agree.

## Sampling decides which traces survive

Storing every observation is expensive, so tools sample: they keep only a fraction of requests. The decision point matters. The code below compares two policies on 10,000 requests with four observations each (the root and three children), keeping 50% of decisions. "Head-based" makes one decision per trace and every child follows it. "Per-observation" makes an independent decision for each observation.

```python
import random

RATE, STEPS, TRACES = 0.5, 4, 10_000      # keep 50% of decisions; 4 observations per request
rng = random.Random(56)

# Head-based: one coin flip per trace, inherited by every child observation.
head_complete = sum(rng.random() < RATE for _ in range(TRACES))

# Per-observation: an independent coin flip for every observation.
obs_complete = sum(all(rng.random() < RATE for _ in range(STEPS)) for _ in range(TRACES))

print(f"head-based:      complete traces {head_complete / TRACES:6.1%}  (expected {RATE:.1%})")
print(f"per-observation: complete traces {obs_complete / TRACES:6.1%}  (expected {RATE ** STEPS:.1%})")

```

```output
head-based:      complete traces  49.8%  (expected 50.0%)
per-observation: complete traces   5.8%  (expected 6.2%)
```

![Two bars: head-based sampling keeps 49.8% of traces complete; per-observation sampling keeps 5.8%, against an expected 6.25%](diagrams/56.2-sampling.svg "Both policies keep half the decisions, but only one keeps whole trees.")

Per-observation sampling keeps a complete trace only when all four of its observations survive, which happens with probability 0.5 to the power 4, or 6.25%. The simulated 5.8% differs from that by about 2 standard errors (the standard error of a proportion near 6% over 10,000 trials is about 0.24 percentage points), so it is within chance for this seed. A broken tree is hard to debug: you see a generation with no parent request. Head-based sampling keeps whole trees, which is why most tools decide at the root. That is my reasoning from how parent ids work; check the sampler documentation of the SDK you use.

## Common traps

> [!TRAP]
> Word counts are not token counts. The `split()` in the tracer counts words, and a real tokenizer gives different counts (Lesson 23.1 explains how). Cost computed from word counts is wrong by an amount that depends on the language and the tokenizer.

> [!TRAP]
> The prices in this lesson are invented. Vendor prices change, and a stored cost is only as good as the price table and date behind it. Store the price version with each cost record.

> [!TRAP]
> Context does not cross thread boundaries automatically. The example below runs a child step on a worker thread and gets `None` for the parent.

```python
from concurrent.futures import ThreadPoolExecutor
import contextvars

CURRENT = contextvars.ContextVar("current_observation", default=None)
CURRENT.set("root-observation")

def child_step():
    return CURRENT.get()

with ThreadPoolExecutor(max_workers=1) as pool:
    print("inside worker thread:", pool.submit(child_step).result())
print("in main thread:", CURRENT.get())

```

```output
inside worker thread: None
in main thread: root-observation
```

> [!TRAP]
> Observability data contains user text. Mask personal data in your code before export, not after. The product's storage is the last place to fix it.

> [!TRAP]
> Per-observation sampling breaks trees, as shown above. Sample by request.

## Summary

- A trace is one request, and observations (spans, generations, events) form a tree through parent ids.
- A generation record needs the model name and input and output token counts, from which cost is computed.
- Batched export keeps the request path off the network; the buffer should drop data under overload rather than block.
- Latency is best read as percentiles per step; the large model dominated both time and cost in the simulation.
- Sampling should decide per request, so that every kept request comes with its whole tree. Keeping only failures needs a rule that waits until the trace ends, which head sampling cannot do (Lesson 56.1).

## Quiz time

### Question 1: Calculation

A large-model generation has 1,000 input tokens and 200 output tokens. Using the prices in the code (0.003 and 0.015 USD per 1,000 tokens), what is its cost?

<details><summary>Show solution</summary>

1,000 / 1000 × 0.003 = 0.003 USD for the input, and 200 / 1000 × 0.015 = 0.003 USD for the output. The total is 0.006 USD.

</details>

### Question 2: Prediction

The tracer sends a batch whenever the buffer reaches `batch_size`, and `flush()` sends whatever remains. How many POST calls does the code make for 800 observations with `batch_size=1000`?

<details><summary>Show solution</summary>

One. `submit()` never reaches 1000 entries, so no batch is sent during the run, and the final `flush()` sends all 800 in one POST. A larger batch means fewer requests, but observations wait in memory longer and are lost if the process crashes before the flush.

</details>

### Question 3: Bug-spotting

A colleague runs the rerank step in a thread pool and sees the rerank call appear as a separate trace with no parent. Using the output above, explain why, and name a fix.

<details><summary>Show solution</summary>

The worker thread starts with a fresh context, so `CURRENT.get()` returns `None` there and the child becomes a new root. The fix is to capture the context in the calling thread and run the child inside it, for example by submitting `contextvars.copy_context().run` with the function, or by passing the parent observation explicitly as an argument.

</details>

### Question 4: Explanation

With 50% sampling and four observations per request, why does per-observation sampling leave a much smaller share of complete traces than head-based sampling, even though both keep half the decisions?

<details><summary>Show solution</summary>

A trace is complete only if every one of its observations survives. Under per-observation sampling those survivals are independent, so the probability is 0.5 to the power 4 = 6.25%. Under head-based sampling a single decision keeps or drops all four, so the probability is 50%.

</details>

### Question 5: Explanation

Why should a masking step run inside the application rather than in the observability backend?

<details><summary>Show solution</summary>

Once data leaves the process it has been transmitted, and it may be buffered, logged or stored before any backend-side rule runs. Masking in the application means the sensitive text never leaves the machine in readable form.

</details>
