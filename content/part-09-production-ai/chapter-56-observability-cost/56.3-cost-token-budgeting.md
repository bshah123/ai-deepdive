By the end of this lesson you will be able to price one call to a hosted large language model (LLM) from its token counts, enforce a spending limit that still holds when many requests run at once, and route around a failing provider with a circuit breaker, a switch that stops calling a dependency after repeated failures. You will build all three in plain Python and measure what each one changes.

**You need:** Python classes, dictionaries and f-strings. Tokens are covered in Lesson 23.1; the usage fields that a tracing span records are covered in Lesson 56.1.

## The problem: a bill, a limit and an outage

A hosted LLM API charges per token. Three things go wrong in production:

1. One customer's long prompts cost several times more than another's short ones, and nobody sees it until the invoice arrives.
2. Ten users, each under their own quota, exhaust a shared budget together, because their checks run in parallel.
3. The primary provider starts failing at 14:00, and every request waits for a timeout before it falls back to a second provider.

Each problem needs its own mechanism: cost accounting for the first, budget reservations for the second, and a circuit breaker with fallback routing for the third.

## 1. Cost accounting: price each call from its usage

Every response reports how many input tokens and output tokens it used. Providers price the two separately, per million tokens, and the price differs by model. The cost of one call is:

$$\text{cost} = \frac{n_{\text{in}} \cdot p_{\text{in}} + n_{\text{out}} \cdot p_{\text{out}}}{10^6}$$

**Worked example by hand.** A request has 1,200 input tokens and 300 output tokens. On the small model (0.25 USD in, 1.00 USD out per million tokens), input costs 1200 × 0.25 / 10^6 = 0.0003 USD and output costs 300 × 1.00 / 10^6 = 0.0003 USD, a total of 0.0006 USD. On the large model (3.00 in, 15.00 out), input costs 0.0036 USD and output costs 0.0045 USD, a total of 0.0081 USD. The large model costs 13.5 times as much, and output is 56% of its bill, although output is only a fifth of the tokens.

The prices are illustrative, not a real price list. Check your provider's current page before you use any number.

![Two stacked bars: cost per 10,000 requests split into input and output tokens, for a small and a large model](diagrams/56.3-cost-anatomy.svg "Cost per 10,000 requests, split into input and output tokens.")

```python
# Cost of one call from the token counts a provider returns.
# Prices are ILLUSTRATIVE, in USD per million tokens (not a real price list).
PRICES = {
    "small": {"in": 0.25, "out": 1.00},
    "large": {"in": 3.00, "out": 15.00},
}

def call_cost(model, input_tokens, output_tokens):
    p = PRICES[model]
    return (input_tokens * p["in"] + output_tokens * p["out"]) / 1_000_000

for model in PRICES:
    c = call_cost(model, input_tokens=1200, output_tokens=300)
    print(f"{model:5s} {c:.4f} USD per request, {c * 10_000:6.2f} USD per 10,000")

ratio = call_cost("large", 1200, 300) / call_cost("small", 1200, 300)
print(f"large costs {ratio:.1f}x the small model for this request")
```

```output
small 0.0006 USD per request,   6.00 USD per 10,000
large 0.0081 USD per request,  81.00 USD per 10,000
large costs 13.5x the small model for this request
```

Cost accounting means keeping one record per call, with the model, the tenant (the customer or team) and the feature, and then summing those records. Build the record from the usage the provider returns, not from a token estimate of your own, because the provider's count is what you are billed for.

## 2. Token budgets under concurrency

A budget is a spending limit per tenant, for example per day. The obvious check is "is spent so far below the limit?" followed by the call and then a charge of the actual cost. That check fails under concurrency. Requests that run at the same time all read the same spent total before any of them has been charged.

The fix is a **reservation**. Before the call starts, the request holds its worst-case cost: the largest cost it could possibly incur, which is the input tokens plus the `max_tokens` output limit at the model's prices. When the call finishes, the hold is released and the actual cost is charged. This only works if the server enforces `max_tokens`, so the hold is a true upper bound.

The code below shows both behaviours. The first part is a race in which four requests start before any of them finishes. The second part runs 200 requests in waves of K, where K is the number of requests in flight at once.

```python
import random

WORST = (1200 * 3.00 + 1000 * 15.00) / 1_000_000   # max_tokens=1000 output, large-model prices

class Budget:
    """Spend limit where in-flight calls hold their worst-case cost."""
    def __init__(self, limit):
        self.limit = limit
        self.spent = 0.0   # actual cost of finished calls
        self.held = 0.0    # worst-case cost of calls still running

    def reserve(self, worst):
        if self.spent + self.held + worst > self.limit:
            return False           # admitting this call could breach the limit
        self.held += worst
        return True

    def settle(self, worst, actual):
        self.held -= worst         # release the hold
        self.spent += actual       # charge what was really used

# Race: four requests start before any of them finishes. Limit 0.05 USD.
naive_spent = 4 * 0.018            # the naive check sees spent = 0 for all four
print(f"naive: admitted 4, charged {naive_spent:.3f} USD against a limit of 0.050")
b = Budget(0.05)
admits = [b.reserve(WORST) for _ in range(4)]
print(f"reserved: admits {admits}, holding {b.held:.4f} USD")
for _ in range(sum(admits)):
    b.settle(WORST, 0.018)         # each admitted call really cost 0.018
print(f"after settling: spent {b.spent:.3f} USD, held {max(0.0, b.held):.4f} USD")

def simulate(limit, K, n_requests, use_holds, seed=1):
    """Requests run in waves of K. Nothing in a wave has settled when the wave starts."""
    rng = random.Random(seed)
    b = Budget(limit)
    admitted, pending = 0, n_requests
    while pending > 0:
        wave = min(K, pending)
        pending -= wave
        in_flight = []
        for _ in range(wave):
            if use_holds:
                if b.reserve(WORST):
                    in_flight.append(WORST)
                    admitted += 1
            elif b.spent < limit:      # naive: looks only at money already charged
                in_flight.append(0.0)
                admitted += 1
        for worst in in_flight:
            b.settle(worst, rng.uniform(0.005, WORST))   # actual cost is below the worst case
    return admitted, b.spent

print("K    naive: admitted   spent   over    reserved: admitted   spent")
for K in (1, 4, 16, 64):
    a1, s1 = simulate(1.00, K, 200, use_holds=False)
    a2, s2 = simulate(1.00, K, 200, use_holds=True)
    print(f"{K:<4d} {a1:17d} {s1:7.4f} {max(0.0, s1 - 1.0):7.4f}    {a2:17d} {s2:7.4f}")
```

```output
naive: admitted 4, charged 0.072 USD against a limit of 0.050
reserved: admits [True, True, False, False], holding 0.0372 USD
after settling: spent 0.036 USD, held 0.0000 USD
K    naive: admitted   spent   over    reserved: admitted   spent
1                   86  1.0131  0.0131                   84  0.9832
4                   88  1.0372  0.0372                   84  0.9832
16                  96  1.1453  0.1453                   84  0.9832
64                 128  1.5110  0.5110                   83  0.9750
```

![Bar chart of USD spent above the limit for naive admission at K equal to 1, 2, 4, 8, 16, 32 and 64; reserved admission stays at zero](diagrams/56.3-budget-overshoot.svg "Naive admission overspends more as more requests run at once; reservations never exceed the limit in this run.")

The naive overspend is bounded by K times the worst-case cost of one request, because each wave admits up to K calls against a total that is out of date. The observed overspend at K=64 (0.5110 USD) is well inside that bound of about 1.19 USD. The reservation version never overspends, because spent plus held never exceeds the limit. It does admit fewer requests, even at K=1 (84 against 86), since a hold reserves the worst case (0.0186 USD) and the average call costs less.

## 3. Fallback routing and the circuit breaker

A **fallback chain** is an ordered list of providers. You call the first one, and if it returns an error (a timeout, a rate-limit response or a server error) you call the next. This is failure routing. It is different from **quality routing**, where a cheap model answers first and a scorer escalates to a stronger model when the answer looks weak. FrugalGPT (Chen, Zaharia and Zou, 2023) is a quality cascade; the abstract reports reductions "up to 98%" against the best single model, and that figure is a best case, not a typical one.

Failure routing has a cost. If the primary provider is down, every request waits for the full timeout before it falls back. A **circuit breaker** fixes this. It has three states (Fowler, 2014):

- **Closed:** calls go to the primary. Each failure adds to a counter; a success resets it. When the counter reaches a threshold, the breaker opens.
- **Open:** the primary is skipped, and the request goes straight to the fallback. After a cooldown, the breaker moves to half-open.
- **Half-open:** one trial call goes to the primary. Success closes the breaker; failure reopens it and restarts the cooldown.

![Three boxes for the closed, open and half-open states, with arrows for the transitions and their conditions](diagrams/56.3-breaker-states.svg "The breaker's three states and the transitions the code below uses.")

The simulation sends one request every 0.5 s for 120 s. The primary is down from t = 30 s to t = 90 s, and each failed call wastes a 5 s timeout. The breaker opens after 3 consecutive failures and waits 10 s before probing.

```python
class CircuitBreaker:
    def __init__(self, threshold, cooldown):
        self.threshold = threshold     # consecutive failures before opening
        self.cooldown = cooldown       # seconds to wait before a probe
        self.failures = 0
        self.opened_at = None          # None means closed

    def allow(self, now):
        return self.opened_at is None or now - self.opened_at >= self.cooldown

    def record(self, now, ok):
        if ok:
            self.failures, self.opened_at = 0, None
        else:
            self.failures += 1
            if self.failures >= self.threshold:
                self.opened_at = now   # (re)open, restart the cooldown

def primary_down(t):
    return 30.0 <= t < 90.0            # outage window, in seconds

TIMEOUT = 5.0                          # seconds a failed primary call wastes

def serve(n_requests, use_breaker):
    breaker = CircuitBreaker(threshold=3, cooldown=10.0)
    primary_calls, wasted, served = 0, 0.0, {"primary": 0, "fallback": 0}
    for i in range(n_requests):
        now = i * 0.5
        if not use_breaker or breaker.allow(now):
            primary_calls += 1
            ok = not primary_down(now)
            if use_breaker:
                breaker.record(now, ok)
            if ok:
                served["primary"] += 1
                continue
            wasted += TIMEOUT
        served["fallback"] += 1
    return primary_calls, wasted, served

for use in (False, True):
    calls, wasted, by = serve(240, use)
    print(f"breaker={use!s:5}: primary calls {calls:3d}, wasted {wasted:5.1f} s, served {by}")
```

```output
breaker=False: primary calls 240, wasted 600.0 s, served {'primary': 120, 'fallback': 120}
breaker=True : primary calls 126, wasted  40.0 s, served {'primary': 118, 'fallback': 122}
```

![Two bar panels: primary calls (240 without the breaker, 126 with it) and seconds lost to timeouts (600 s and 40 s)](diagrams/56.3-outage-cost.svg "Same 240 requests during a 60 s outage, with and without the breaker.")

Without the breaker, all 120 outage requests wait 5 s each, which is 600 s of lost time. With the breaker, only 8 calls fail: three to open it, then five half-open probes at 10 s intervals. The breaker also sends 2 fewer requests to the primary (118 against 120). The requests at 90.0 s and 90.5 s would have succeeded, but the breaker is still in its cooldown after the failed probe at 81 s, so they go to the fallback.

**Availability.** If the two providers fail independently, with success probabilities p = 0.99 and q = 0.98, a request fails only when both fail: 1 − (1 − 0.99)(1 − 0.98) = 0.9998. This is reasoning from an assumption (b), not a measurement. Real outages are often correlated, for example when two providers depend on the same network path or region, and then the true figure is lower.

## Common traps

> [!TRAP]
> Estimated cost is not an upper bound. A budget that holds an estimate can still be exceeded by a long completion. Hold the worst case, and enforce `max_tokens` on the server side.

> [!TRAP]
> A breaker that never resets its failure count opens on failures that are far apart in time. Reset the counter on every success, so only consecutive failures count.

> [!TRAP]
> Reservations are conservative. In the run above, reservations admitted 84 requests against 86 with naive admission at K=1. That gap is the price of never overspending.

> [!TRAP]
> A fallback to a second provider is not independent insurance if both depend on the same upstream network path, region or account. Test the failover path under a real outage, not only in unit tests.

> [!TRAP]
> A cheaper fallback is not a safe fallback. Failover changes the model that answers, so check quality on the fallback as well as its latency and cost.

## Summary

- A call costs input tokens times the input price plus output tokens times the output price, per million tokens. The output price is usually the larger share of the bill.
- Per-call records, built from the provider's usage fields, are the basis for cost accounting by tenant, model and feature.
- Naive budget checks overspend under concurrency, by up to K times the worst-case cost of one request. Reservations of the worst case never overspend, at the cost of admitting fewer requests.
- A circuit breaker turns repeated failures into a fast skip to the fallback, which cut wasted primary time from 600 s to 40 s in the simulation.
- Failover helps only if the fallback fails independently of the primary. Measure it under a real outage.

### Question 3: Bug-spotting

This breaker is supposed to open after three consecutive failures. What is wrong with it?

```python
class CircuitBreaker:
    def __init__(self, threshold):
        self.threshold, self.failures, self.opened = threshold, 0, False

    def record(self, ok):
        if not ok:
            self.failures += 1
            if self.failures >= self.threshold:
                self.opened = True
```

<details><summary>Show solution</summary>

**The failure counter is never reset on success.** Failures at calls 1, 3 and 5, with successes in between, open the breaker on the fifth call even though no three failures were consecutive. The fix is `if ok: self.failures = 0` at the start of the method. The breaker also never closes again, because `opened` is never reset. The version in this lesson handles both cases.

</details>

### Question 4: Explanation

Why must the reserved amount be the worst case rather than an average cost?

<details><summary>Show solution</summary>

**An average can be exceeded by any single long call, and the budget then overspends.** The reservation is only a guarantee if no call can cost more than its hold. That holds only when the server caps output with `max_tokens`. Without the cap, the worst case is unbounded and no reservation is safe.

</details>
