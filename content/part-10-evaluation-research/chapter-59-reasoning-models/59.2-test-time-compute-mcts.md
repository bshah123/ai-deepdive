Test-time compute means spending more computation when a model answers, not when it is trained. In this lesson you will compare three ways to spend a fixed budget of model calls: best-of-N with an outcome reward, beam search with a process reward, and Monte Carlo tree search (MCTS) with a process reward. You will implement all three in NumPy, check the simulator against a closed-form result, and see where each one wins.

**You need:** chain-of-thought prompting (Lesson 59.1), the mean of a sample, and the idea that independent events multiply their probabilities.

## The problem: one sample is one gamble

Suppose a solution has $D = 4$ steps and each step is correct with probability $Q = 0.5$. If the steps are independent (a strong assumption, which the simulation below relaxes only partly), one sampled solution is fully correct with probability $Q^D = 0.5^4 = 0.0625$. Drawing more solutions helps only if you can tell the good ones from the bad ones. The methods in this lesson differ in how they spend the budget and in what they use to judge candidates.

Two terms:

- A **verifier** scores a candidate. An **outcome reward model (ORM)** scores only the final answer. A **process reward model (PRM)** scores each intermediate step. Lightman et al. (2023) compared the two as training signals on MATH, a benchmark of competition mathematics. Their abstract reports that process supervision "significantly outperforms" outcome supervision.
- The **budget** is the number of generator calls, one per sampled step or sampled solution. In this lesson verifier calls are free. That matters in practice (see the traps).

![Left: a single chain of four steps, step 3 wrong, so the answer is wrong. Right: a tree in which two of four first-level candidates are kept and two are pruned](diagrams/59.2-chain-vs-tree.svg "One chain can only be right or wrong at the end. Tree search can drop a bad branch before it grows.")

## Intuition: search over partial solutions

A single chain commits to each step. Tree-of-Thoughts (Yao et al., 2023) turns the chain into a tree: at each step the model proposes several candidate thoughts, a scorer rates them, and the search keeps the promising ones and drops the rest. The paper reports gains on tasks that need lookahead, such as Game of 24. Its abstract gives 74% success for the method against 4% for chain-of-thought prompting on that task, with GPT-4. These are the authors' numbers for their own setup, and I have not re-run them.

The choice of what to score matters as much as the search itself. An ORM can only say whether a finished answer is right, so every good partial chain has to survive to the end to be rewarded. A PRM can reward a good step as soon as it is written.

![Two panels: an outcome reward gives one score to the final answer; a process reward gives one score per step](diagrams/59.2-orm-vs-prm.svg "Same chain, two supervision signals. The process reward arrives earlier and more often.")

## Worked example by hand

Best-of-N with an outcome reward samples $N$ complete chains. With a perfect verifier, the run succeeds if at least one chain is fully correct:

$$
P(\text{success}) = 1 - (1 - Q^D)^N
$$

With budget 16 generator calls, $N = 16 / 4 = 4$ chains, so $P = 1 - 0.9375^4 = 0.2275$. With budget 64, $N = 16$, so $P = 1 - 0.9375^{16} = 0.644$. Quadrupling the budget raises success from about 0.23 to about 0.64. It does not reach 1, because the chains are sampled blindly. A real verifier is noisy, so these numbers are upper bounds for outcome-only selection.

## The simulation

The toy problem has four rules:

1. Each candidate step is correct with probability 0.5, independently of earlier steps.
2. A PRM returns 1 for a correct step and 0 for a wrong one, plus Gaussian noise with standard deviation `sigma`.
3. An ORM returns the same kind of noisy score once per chain, for the final answer.
4. Each strategy gets the same budget of generator calls. Each setting is run on 400 problems, so the standard error of a success rate is at most $\sqrt{0.25 / 400} = 0.025$.

The script below implements the three strategies and the closed-form check. It runs in about 3 seconds in NumPy.

```python
import numpy as np

D = 4          # steps in one solution
Q = 0.5        # chance that a freshly proposed step is correct
K = 4          # maximum children per MCTS node
C_EXPLORE = 1.0

def propose(rng, sigma):
    """One generator call. Returns (is_correct, noisy process reward)."""
    correct = bool(rng.random() < Q)
    return correct, float(correct) + sigma * rng.standard_normal()

def orm_best_of_n(budget, rng, sigma):
    """Sample budget // D full chains; the outcome verifier scores only the final answer."""
    best_ok, best_score = False, -np.inf
    for _ in range(budget // D):
        ok = all([rng.random() < Q for _ in range(D)])
        score = float(ok) + sigma * rng.standard_normal()
        if score > best_score:
            best_ok, best_score = ok, score
    return best_ok

def beam_prm(budget, rng, sigma, beam=4):
    """At each depth, expand every beam item and keep the top `beam` partial chains by summed step reward."""
    k = budget // (beam * D)
    beams = [(0.0, True)] * beam          # (summed process reward, all steps correct so far)
    for _ in range(D):
        cands = []
        for total, ok in beams:
            for _ in range(k):
                c, s = propose(rng, sigma)
                cands.append((total + s, ok and c))
        cands.sort(key=lambda t: -t[0])
        beams = cands[:beam]
    return beams[0][1]

class Node:
    def __init__(self, depth, ok, cum, parent=None):
        self.depth, self.ok, self.cum, self.parent = depth, ok, cum, parent
        self.children, self.visits, self.total = [], 0, 0.0
        self.done = depth == D           # a finished path (depth D) is terminal and never expanded

def backprop(node, reward):
    while node is not None:
        node.visits += 1
        node.total += reward
        node = node.parent

def mcts_prm(budget, rng, sigma, decode="mean"):
    """UCT with one expansion per iteration (one generator call); the PRM scores each new step."""
    root = Node(0, True, 0.0)
    spent = 0
    while spent < budget and not root.done:
        node = root
        while len(node.children) == K:            # fully expanded: select a live child by UCB1
            parent = node
            live = [ch for ch in node.children if not ch.done]
            node = max(live, key=lambda ch: ch.total / ch.visits
                       + C_EXPLORE * np.sqrt(np.log(parent.visits) / ch.visits))
        c, s = propose(rng, sigma)                # expand: one new child, one generator call
        child = Node(node.depth + 1, node.ok and c, node.cum + s, node)
        node.children.append(child)
        backprop(child, child.cum)                # back up the partial-path PRM score
        spent += 1
        p = node                                  # a node whose K children are all done is done
        while p is not None and len(p.children) == K and all(ch.done for ch in p.children):
            p.done = True
            p = p.parent
    node = root
    while node.children:                          # answer: follow the best mean (or most visited)
        if decode == "mean":
            node = max(node.children, key=lambda ch: ch.total / ch.visits)
        else:
            node = max(node.children, key=lambda ch: ch.visits)
    return node.depth == D and node.ok

def success(strategy, budget, sigma, n=400, seed=0):
    rng = np.random.default_rng(seed)
    return sum(strategy(budget, rng, sigma) for _ in range(n)) / n

def se(p, n=400):
    return float(np.sqrt(p * (1 - p) / n))

STRATS = [("ORM best-of-N", orm_best_of_n), ("PRM beam", beam_prm), ("PRM MCTS", mcts_prm)]

print(f"single chain, closed form Q^D = {Q ** D:.4f}")
for budget in [16, 64]:
    sim = success(orm_best_of_n, budget, 0.0, n=4000)
    exact = 1 - (1 - Q ** D) ** (budget // D)
    print(f"sanity, ORM sigma=0, budget {budget}: simulated {sim:.3f}, closed form {exact:.3f}")
print(f"sanity, PRM beam sigma=0, budget 64: simulated {success(beam_prm, 64, 0.0):.3f}")

print("success rate, sigma = 0.5 (400 problems; +/- one standard error)")
for name, strat in STRATS:
    cells = []
    for budget in [16, 32, 64, 128]:
        p = success(strat, budget, 0.5)
        cells.append(f"B={budget}: {p:.3f}+/-{se(p):.3f}")
    print(f"{name:14s}", "  ".join(cells))

print("success rate at budget 64 as the verifier noise grows")
for sigma in [0.25, 0.5, 1.0, 2.0]:
    cells = [f"{name}: {success(strat, 64, sigma):.3f}" for name, strat in STRATS]
    print(f"sigma={sigma:4.2f}  " + "  ".join(cells))

print("ablation, MCTS answer by visit count instead of mean, sigma = 0.5:",
      " ".join(f"B={b}: {success(lambda bu, r, s: mcts_prm(bu, r, s, decode='visits'), b, 0.5):.3f}"
               for b in [16, 64, 128]))

# UCB1 worked example: (visits, total reward) per child; parent visits = sum of child visits
stats = {"A": (3, 2.4), "B": (1, 0.9), "C": (2, 1.1), "D": (1, 1.0)}
N = sum(v for v, _ in stats.values())
print(f"UCB1 with parent visits N = {N}, c = {C_EXPLORE}")
for name, (n_i, w_i) in stats.items():
    ucb = w_i / n_i + C_EXPLORE * np.sqrt(np.log(N) / n_i)
    print(f"child {name}: mean {w_i / n_i:.3f}, UCB {ucb:.3f}")
```

The sanity lines check the simulator before any strategy comparison. The outcome-only closed form is $1 - (1 - Q^D)^N$. At budget 16 the simulation agrees with it to within sampling error. At budget 64 it is slightly lower in this run, about two standard errors below. Re-running with seeds 1 to 3 gave values of 0.650 to 0.660, above the closed form, so the gap is sampling noise and not a bug. The beam result at $\sigma = 0$ is 1.000 by construction, which is a wiring check and not a finding (see the traps).

### Beam search with a process reward

Beam search keeps four partial chains. At each depth, every kept chain proposes $k = B / (4 \cdot D)$ candidate steps. The PRM scores each candidate, and the four best partial chains by summed step reward survive to the next depth. The summed reward is the sum of the PRM scores along the chain. With a noiseless PRM, a chain's summed reward equals its number of correct steps, so a fully correct chain beats every chain with an error. This is why the beam result at $\sigma = 0$ is 1.000.

### MCTS with UCB1 selection

MCTS grows the tree one node at a time. Each iteration costs one generator call and has four phases:

![Four boxes in a loop: 1 Select walks down by UCB1 to a node with a free slot; 2 Expand adds one child; 3 Score lets the PRM rate the new step; 4 Back up adds the path score to every ancestor](diagrams/59.2-mcts-loop.svg "One MCTS iteration. The loop repeats until the budget is spent.")

Selection uses the UCB1 score, which balances the mean reward of a child against how rarely it has been visited:

$$
\text{UCB}(i) = \bar{x}_i + c \sqrt{\frac{\ln N}{n_i}}
$$

Here $\bar{x}_i$ is the mean backed-up reward of child $i$, $n_i$ its visit count, $N$ the parent's visit count, and $c$ the exploration constant. The bonus term shrinks as a child is visited, so rarely tried children get a second look. This is the standard bandit formula; I did not open its original paper, so I give no citation for it.

![Bar chart of UCB1 scores for four children, each split into a solid mean part and a hatched exploration bonus. Child D has the highest score and would be expanded next](diagrams/59.2-ucb-example.svg "UCB1 at one node. Solid is the mean reward; hatched is the exploration bonus. The bars use the same numbers as the script.")

Child D wins here because its mean is highest, and its bonus is as large as B's, since both have one visit. Child A has a smaller bonus because it has three visits.

**The answer rule.** After the budget is spent, the script follows the child with the highest mean value to a complete path. I first tried following the most-visited child, which is the common "robust child" rule. The ablation line in the output shows it does much worse on this toy: 0.255, 0.170 and 0.113 at budgets 16, 64 and 128, against 0.340, 0.615 and 0.645 for the mean rule. I chose the mean rule after seeing both results on the same simulation, so treat it as a design choice and not as a tuned result. Visits in UCT measure how much effort went into a subtree, and effort is not the same as quality.

## Results

![Two bar charts with error bars. Left: success rate against budget for three strategies at sigma 0.5. Right: success rate at budget 64 against verifier noise sigma from 0.25 to 2.0](diagrams/59.2-accuracy-vs-compute.svg "Success rate in the toy simulation. Error bars are one standard error on 400 problems.")

At sigma 0.5 and budget 64, beam search succeeds on 0.800 of problems (standard error 0.020), MCTS on 0.615 (0.024), and outcome best-of-N on 0.400 (0.024). At budget 128 the values are 0.917, 0.645 and 0.590. At budgets 16 and 32, MCTS is ahead of beam search (0.340 against 0.188, and 0.630 against 0.550). So in this toy, beam search is the best of the three only from budget 64 up. My guess at the reason is that every candidate here has the same prior correctness, so MCTS's exploration has no structure to exploit, and beam search spends its calls broadly with little waste. The experiment does not isolate this explanation.

Verifier noise changes the picture. At budget 64, the beam search PRM falls from 0.993 at sigma 0.25 to 0.223 at sigma 2.0. The outcome verifier falls from 0.603 to 0.113. MCTS falls from 0.823 to 0.190. The PRM stays ahead of the ORM at every noise level tested, but its advantage shrinks as its readings become unreliable.

## Common traps

> [!TRAP]
> The simulation is a toy. Steps are independent, the correct rate is fixed at 0.5, and verifier noise is independent across steps and calls. Real reasoning steps depend on earlier steps, and a real PRM makes correlated errors. Both effects reduce the advantage of process rewards. Do not read these numbers as predictions for any model.

> [!TRAP]
> Compare methods at equal generator calls, and say what verifier calls cost. Here each PRM read is free. In practice a PRM is itself a model call, so one PRM step can cost as much as one generator step. That could change the ranking.

> [!TRAP]
> A result that looks perfect is a bug hypothesis first. The beam search at sigma 0 scores 1.000, but only because a noiseless PRM always keeps correct chains when they exist. Confirm the code is wired correctly, then treat the number as a sanity check.

> [!TRAP]
> The answer rule changes MCTS a lot. Visit counts and mean values gave very different results here. Report which rule you used and show the alternative, as the ablation does.

> [!TRAP]
> Published numbers from Yao et al. (2023) and Snell et al. (2024) come from specific tasks, models and baselines. Snell et al.'s abstract also limits its "14x larger" comparison to problems where the smaller model has non-trivial success. Do not transfer those figures to a different task.

## Summary

- A single 4-step chain with per-step accuracy 0.5 is fully correct 6.25% of the time. Extra compute helps only when you can tell good candidates from bad ones.
- Outcome-only best-of-N has diminishing returns: with a perfect verifier, quadrupling the budget at $D = 4$ moved success from about 0.23 to about 0.64.
- Process rewards let beam search prune early. In the toy, beam search beat MCTS and outcome best-of-N at budgets 64 and 128, while MCTS was ahead at budgets 16 and 32. The beam lead over MCTS narrows as verifier noise grows.
- MCTS needs UCB1 exploration and a rule for the final answer. The mean-value rule beat the visit-count rule here.
- The whole comparison rests on a toy problem. Use it to understand the mechanisms, not to predict accuracy on real models.

### Question 1: Calculation

Each step of a 5-step chain is correct with probability 0.9, independently. What is the probability that the whole chain is correct?

<details><summary>Show Solution</summary>

$0.9^5 = 0.59049$, so about 0.590. Independence lets the probabilities multiply.

</details>

### Question 2: Calculation

With a perfect outcome verifier and $Q^D = 0.0625$ per chain, what is the smallest number of chains $N$ that reaches at least 90% success, and what generator-call budget does that cost at $D = 4$?

<details><summary>Show Solution</summary>

We need $1 - 0.9375^N \geq 0.9$, so $0.9375^N \leq 0.1$. Taking logs, $N \geq \ln 0.1 / \ln 0.9375 \approx 35.7$, so $N = 36$. Each chain costs 4 calls, so the budget is $36 \times 4 = 144$ calls.

</details>

### Question 3: Find the bug

In a beam search over partial chains, the code keeps the best candidates like this:

```python
cands.sort(key=lambda t: t[0])
beams = cands[:beam]
```

What goes wrong?

<details><summary>Show Solution</summary>

`sort` is ascending, so `cands[:beam]` keeps the four lowest summed rewards, which are the worst partial chains. The fix is `cands.sort(key=lambda t: -t[0])`, as in the lesson code. The bug produces a number without raising an error, so only a comparison against a baseline would reveal it.

</details>

### Question 4: Explanation

In the UCB1 score, why does the exploration bonus $c\sqrt{\ln N / n_i}$ shrink as a child is visited more often, and why does it grow with the parent's visit count $N$?

<details><summary>Show Solution</summary>

Each visit to child $i$ adds to $n_i$, which shrinks the bonus, so a child that has been explored often relies more on its measured mean. The parent's visit count $N$ grows with every iteration through the node, so the bonus for less-visited children grows slowly, which keeps them from being neglected forever. The formula is a standard heuristic rather than a guarantee for this setting. Its constant $c$ has to be tuned to the reward scale.

</details>

### Question 5: Interpretation

The visit-count answer rule chose a worse child than the mean rule in this toy. Give one reason why the most-visited child could be a poor final answer.

<details><summary>Show Solution</summary>

Visit counts accumulate where UCB1 keeps exploring, including subtrees whose means are only moderately high. A child can be visited often because the bonus keeps pulling the search back to it, even when its mean is below that of a less-visited sibling. Mean value estimates quality, which is what the final answer should reflect.

</details>
